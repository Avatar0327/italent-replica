## 二、值得坚持的做法

1. **取证领先开发**：`evidence-gate` 门禁 + 开工前扫描，在开工前拦下 R1-T13（Q-M0-70）、R3-T00 / R2-T03（各 4 项）、F-022（4 项）等问题。原站没查清的点，开发先按最保守做法处理（fail-closed），同时开需取证 issue（#78、#80、#81），开发不必停等。
2. **决策显式登记**：口径一律登记 DEC；与原站的有意差异单独标明（DEC-206、209）；选项注明改的是复刻系统还是北森测试租户；审查中冒出的产品问题回到用户决定（DEC-203、206），不由开发方或审查方代定。
3. **独立审查方把关合并**：astra 事后补审 #63 / #64 / #68，发现 Claude 交叉审查漏报 6 个 P1，因此定了 DEC-179：所有 PR 以 astra“可以合并”为准。合并 main 后对冲突处再复核，抓到了两边逻辑叠加的缺陷（#77 P2-M1、#74 与 #73 的冲突）。
4. **三窗口分工 + 拟派发互核**：派发前核对依赖、文件重叠、合并顺序与产品范围，拦下了 R1-T10 合并顺序、R1-T13 / T14 共享组件归属、R1-T14 汇报关系页范围、#74 的 TODO(F-016)、#86 漏在审计提醒名单外、F-022 与 F-021 / F-007 的版本继承耦合等问题。
5. **连续 3 轮仍有 P0～P2 就问用户**：避免无限返工，每次都由用户决定继续还是换方案。
6. **交接有据**：恢复点（RP）+ 交接提示词 + 看板，总编排换窗口时没有断档。

## 四、对 R2、R3 的建议

1. **R1 收尾做一次端到端验收**：R1-T13 合并后，按路线图 R1 出口标准走一遍（员工发起调动 → 审批 → HR 执行 → 生效 → 版本链与向后更新正确 → 员工与经理侧可见变更），并核对 AC 覆盖。R1 至今没有做过整体验收。
2. **R2 与任职模块排队**：离职（R2-T03）、入职（R2-T01）、兼职（R2-T05）都改任职流转核心，建议依次派发而非同时；与 R1 已有能力的边界派发前写成分界表（参照 `后续任务.md` §16），如 R2-T09 职责转交与 R1-T10 调动转交。
3. **R3 取证提前排**：R3 规则多来自官方文档（🟡），原站未做写入实测，开工前扫描会冒出更多项；先做 R3-T00，后续每个 R3 任务的扫描至少提前一个任务排上。
4. **修正任务定期清**：每个阶段结束前，把挂着的 F 任务和“可后补”取证排一次，决定本阶段做完还是明确推后。
5. **以后的版本**：保留“取证 → 决策 → 派发核对 → 独立审查 → 合并复核”主线，把自查清单、在途上限、迁移编号预分配写进 `docs/09_派发/` 的派发规则，作为默认做法。
