## 4. 八条最容易做错的硬规则（开发前必读）

| # | 规则 | 证据 |
|---|---|---|
| 1 | **数据范围默认值是空，不是全部**（原站 UI 原文「默认管理单元无数据范围权限」） | 🟢 |
| 2 | **任职记录是事件溯源版本链**：每次业务新增一条，不 UPDATE；「变更前」值经 `EmploymentChangeLookUp` 取上一条，**不建前/后两列** | 🟢 + 🟡 |
| 3 | **`IsCurrentRecord` ≠ `IsLatestRecord`**：前者是今天落在有效期内，后者是时间轴最后一条（可能未来生效） | 🟢 字段说明原文 |
| 4 | **审批通过 ≠ 生效**：审批通过日期早于生效日期时，由定时任务到期生效 | 🟡 |
| 5 | **向后更新是值匹配替换**，不是覆盖；「是否部门负责人」不向后更新 | 🟡 |
| 6 | **“直改”和“申请”靠身份持有的按钮区分**：权限粒度是 按钮编码 × 级别（列表/行/详情/应用页），不是“动作” | 🟢 配置证据（人事管理员 274 个 vs 部门负责人 67 个） |
| 7 | **“看全部”没有旁路标志**：要么用根管理单元，要么用身份数据权限；用户授权里直接选的组织范围存为（用户×应用）的**虚拟管理单元** | 🟢 |
| 8 | **流程匹配必须按业务类型隔离**：原站调动申请按实体扫描流程、与审批类型无关，实测被无条件的离职流程接住（C-006）。另外列表显示“草稿”不等于停用，旧发布版本仍可能生效 | 🟢 2026-09-27 实测 |
