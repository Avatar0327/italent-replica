# 分期路线图与开发任务书

> 版本：v0.3（2026-09-27）｜ 状态：**分期与里程碑已定**
> 资源（DEC-008）：**1 人 + Claude Code / Codex，无截止日期** → **不给日历工期**。「工期」列改为「里程碑」：按依赖串行排序（M1 → M2 → …），每个任务都要能由单人 + AI 一次交付并自验。
> 范围（DEC-006）：**多租户 SaaS** → 新增 R1-T00（租户隔离底座）与 R1-T17（平台运营层）。
> 每个任务的「实现版本」「测试结果」一律留空 —— 开发尚未发生。

---

## 0. 分期原则

1. **按可验收闭环分期**，不按技术层分期。每期结束必须有一条端到端可演示的业务链路。
2. **基础能力优先于业务模块**。权限、任职记录版本链、审批这三项是所有模块的地基，做错会全盘返工。
3. **每个任务必须可追溯**至需求文档与验收场景编号。
4. 标记 🔴 的任务**尚有关键规则未取证**，不得开工（见各任务的"前置取证"列）。

### R1 的跨任务硬约束
| 约束 | 说明 |
|---|---|
| 数据范围默认值 | **必须为空**，不得为"全部"。违反即系统性越权。 |
| 任职记录 | **必须**事件溯源版本链。用单表 UPDATE 实现会导致 R1-T06 无法完成。 |
| 「变更前」字段 | **不得**单独建列，必须从版本链上一条取（原站实证为关系路径）。 |
| 审批通过 ≠ 生效 | 状态机必须区分这两个状态。 |
| 组织层级 | **不得**用单一 parent_id。 |
| 身份↔数据范围 | **多对一**，不是一对一。撤销身份不得连带删除范围。 |
| 租户隔离（DEC-006） | 所有表、缓存、文件、流程实例、定时任务都必须带租户维度；跨租户访问一律拒绝。 |
| 流程匹配（DEC-017） | 先按审批类型过滤，再按优先级判断发起条件；同类型内都不满足时报错，不跨业务兜底。“草稿”不等于停用。 |
