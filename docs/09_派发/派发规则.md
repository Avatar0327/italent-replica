# 派发规则（DEC-221，2026-10-06 依据 R1 复盘，用户采纳）

> 来源：`docs/10_进度/R1复盘.md`。本文件是总编排窗口派发、审查、合并的默认做法；与 `取证与开发衔接.md`、`02_已确认决策.md` 冲突时以 DEC 为准。

## 1. 每个派发提示词必须附“提交前自查清单”
派发提示词末尾原样附下列清单，要求开发方在 PR 描述中逐项勾选（不适用的写“不适用 + 原因”）：

```text
提交前自查清单（PR 描述逐项勾选，不适用写原因）：
- [ ] 所有接收员工 / 组织 / 职位 ID 的入口统一做 UUID 规范化（复用 F-017 的实现，DEC-194）。
- [ ] 每个新接口、被改动的旧接口、幂等重放路径，都在服务端重新校验当前范围（复用 visibility.ts），范围外返回 404 / 403 且不泄露信息。
- [ ] 响应的每一层（顶层、嵌套对象、候选列表、预览、汇总计数）都按字段权限裁剪。
- [ ] 显式清空字段同样检查编辑权限；盲审能识别嵌套字段与清空操作。
- [ ] 跨对象写入遵守取锁顺序（员工闭包 → 业务 → 组织 → 编制 → 审批实例，见 org/locks.ts），并发场景有真实 PostgreSQL 交错测试。
- [ ] 删除、作废、撤销的数据不参与统计、判定与占用。
- [ ] 追加任职版本时继承上一版本的派生字段（如 F-022 的人员状态 / 入职状态）。
- [ ] 新增写入口接入审计（DEC-216），并在 audit/visibility.ts 登记审计查看规则。
- [ ] 迁移按派发时给的临时编号段生成；合并前合并 main，按实际合并顺序顺延编号，冲突处理在 PR 描述逐项列出。
```

## 2. 合并顺序与迁移编号
- 默认“谁先通过全部审查谁先合”（DEC-201 / 216 精神）；改动面大的 PR 过审后尽早合并。
- 派发时给每个任务一个**临时迁移编号段**写进提示词，避免并行开发时撞号；最终编号以实际合并顺序为准，合并时由后合并方顺延，编排窗口逐项核对 SQL 不变、快照链与 `_journal`、两个迁移守卫。
- 每次合并后，按在途名单提醒各开发任务合并 main。

## 3. 在途数量与开发方式（按额度决定，不设固定上限）
- 在途 PR 数量、同一模块并行数、由 Codex 还是 Claude 开发，**派发前按当时的 Claude / Codex 额度与审查负荷逐个决定**，不设固定上限，不整体切换开发方式。
- 同一模块并行时，拟派发核对中必须写明共享文件、合并顺序与可能的逻辑叠加点（如 F-022 与 F-021 / F-007 的版本继承）。

## 4. 阶段节点
- **R1 端到端验收**：R1-T13（#84）合并后，按路线图 R1 出口标准走一遍端到端流程（员工发起调动 → 审批 → HR 执行 → 生效 → 版本链与向后更新 → 员工与经理侧可见），并核对 R1 的 AC 覆盖，结果写入恢复点。
- **R2 依次派发**：离职（R2-T03）、入职（R2-T01）、兼职（R2-T05）依次派，不同时派；每个派发前写与 R1 已有能力的分界表（参照 `后续任务.md` §16）。
- **阶段收尾清理**：每个阶段结束前，把挂着的 F 任务和“可后补”取证排一次，决定本阶段做完还是明确推后，登记到 `后续任务.md` 与取证清单。
