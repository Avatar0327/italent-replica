# 派发规则（DEC-221，2026-10-06 依据 R1 复盘，用户采纳）

> 来源：`docs/10_进度/R1复盘.md`。本文件是总编排窗口派发、审查、合并的默认做法；与 `取证与开发衔接.md`、`02_已确认决策.md` 冲突时以 DEC 为准。

## 1. 每个派发提示词必须附“提交前自查清单”
派发提示词末尾原样附下列清单，要求开发方在 PR 描述中逐项勾选（不适用的写“不适用 + 原因”）：

```text
提交前自查清单（PR 描述逐项勾选，不适用写原因）：
- [ ] 所有接收员工 / 组织 / 职位 ID 的入口统一做 UUID 规范化（复用 F-017 的实现，DEC-194）。
- [ ] 每个新接口、被改动的旧接口、幂等重放路径，都在服务端重新校验当前范围（复用 visibility.ts），范围外返回 404 / 403 且不泄露信息。
- [ ] 响应的每一层（顶层、嵌套对象、候选列表、预览、汇总计数）都按字段权限裁剪。
- [ ] 显式清空字段同样检查编辑权限；盲审能识别嵌套字段与清空操作。
- [ ] 跨对象写入遵守取锁顺序（员工闭包 → 业务 → 组织 → 编制 → 审批实例，见 org/locks.ts），并发场景有真实 PostgreSQL 交错测试。
- [ ] 删除、作废、撤销的数据不参与统计、判定与占用。
- [ ] 负向用例断言具体响应码（403 / 404 / 409 等），并前后各读一次对比，证明业务数据未被改动；不得用吞错或“没报错”代替。
- [ ] 可见性用例核对允许查看字段的实际值与被裁剪字段的缺席，不能只核对 ID。
- [ ] 追加任职版本时继承上一版本的派生字段（如 F-022 的人员状态 / 入职状态）。
- [ ] 新增写入口接入审计（DEC-216），并在 audit/visibility.ts 登记审计查看规则。
- [ ] 涉及任职 / 编制 / 调动 / 离职等业务写入的 PR，在描述中列“写入口 × 值来源”穷举表（DEC-251）：行为全部写入口（页面、导入、批量、草稿修改、驳回重提、审批编辑、向后更新、迟到重建、调度等），列为值来源（人工输入、继承、传播、派生、可信系统值），逐格写处理方式与对应测试；审查方据此核对是否列全。
- [ ] 迁移基于最新 main 用 pnpm db:generate 连续编号生成（不手工跳号），PR 描述写明占用的迁移；合并前合并 main，按实际合并顺序顺延，冲突处理逐项列出。
```

## 2. 合并顺序与迁移编号
- 默认“谁先通过全部审查谁先合”（DEC-201 / 216 精神）；改动面大的 PR 过审后尽早合并。
- 派发时在提示词里**登记**该任务预计占用的迁移（数量与用途），编排窗口据此预见撞号与合并顺序。Drizzle 的 `_journal` 编号必须连续，**不得手工跳号**：开发方始终基于最新 main 用 `pnpm db:generate` 生成；最终编号以实际合并顺序为准，由后合并方顺延，编排窗口逐项核对 SQL 不变、快照链与 `_journal`、两个迁移守卫。
- 每次合并后，按在途名单提醒各开发任务合并 main。

## 3. 在途数量与开发方式（按额度决定，不设固定上限）
- 在途 PR 数量、同一模块并行数、由 Codex 还是 Claude 开发，**派发前按当时的 Claude / Codex 额度与审查负荷逐个决定**，不设固定上限，不整体切换开发方式。
- 同一模块并行时，拟派发核对中必须写明共享文件、合并顺序与可能的逻辑叠加点（如 F-022 与 F-021 / F-007 的版本继承）。

## 4. 阶段节点
- **R1 端到端验收**：R1-T13（#84）合并后，按路线图 R1 出口标准走一遍端到端流程（员工发起调动 → 审批 → HR 执行 → 生效 → 版本链与向后更新 → 员工与经理侧可见），并核对 R1 的 AC 覆盖，结果写入恢复点。
- **R2 依次派发**：离职（R2-T03）、入职（R2-T01）、兼职（R2-T05）依次派，不同时派；每个派发前写与 R1 已有能力的分界表（参照 `后续任务.md` §16）。
- **阶段收尾清理**：每个阶段结束前，把挂着的 F 任务和“可后补”取证排一次，决定本阶段做完还是明确推后，登记到 `后续任务.md` 与取证清单。

## 5. 决策项统一汇总到总编排窗口（用户 2026-10-07 要求）
- 开发会话（Codex / Claude）、取证窗口、进度窗口遇到需要用户决定的事项（产品口径、D 差异、范围取舍、是否写入北森测试租户、测试数据是否回退等），**不直接问用户**，一律发给总编排窗口：附编号、背景与证据、选项（注明改复刻系统还是北森测试租户）、推荐与理由、影响的任务。
- 开发会话在 PR 描述“需要产品决策的问题”一节列出并停下等待；取证窗口与进度窗口用跨窗口消息发给总编排。
- 总编排窗口统一向用户提问（带例子、标推荐项），用户选定后登记 DEC，并通知相关窗口 / 会话。
- 派发提示词须写明本条：“遇到需要用户决定的事项，不要自行决定或直接问用户，写进 PR 描述‘需要产品决策的问题’并停下，等总编排窗口转达用户决定。”

## 7. 审查、子代理、默认决策与分工（DEC-235～256，2026-10-07 用户确认）
- 审查模型错开（DEC-235）：Opus 5.5 开发 → GPT-6.1 Sol Ultra；Fable 5.1 开发 → GPT-6 Astra Ultra；Codex-Astra 开发 → 各轮 Opus 5.5 High（单开审查会话，见 DEC-240）；Codex-Sol 开发 → 首轮 Opus 5.5 High、之后 astra High。
- 档位：A 纯文档 / CI 不审；B 审查模型 High；C 首轮 Ultra（Opus 审查为 High）、之后 High，Codex 开发的 C 档合并前做一次错开的 GPT Ultra 最终复查并记录 Opus 漏报；D 同类问题连续两轮 → 换另一个 GPT 模型 Ultra，要求列出全部同类实例；E 机械变更不重审，业务冲突 astra High 只审冲突处。
- 子代理（DEC-236，DEC-240 修订）：.claude/agents/prompt-writer（Fable / high）、merge-helper（Sonnet / high）。审查不用子代理。
- 默认决策（DEC-237）：照原站（不涉及收紧）、返工 3～4 轮继续并升级审查、按难度分配开发方（额度 >70% 再问）、北森写入与测试数据保留默认同意；均登记后告知用户。
- 北森写入（DEC-238）：取证窗口直接执行并记台账；被拦截、输入密码、永久删除仍由用户亲手做。
- 分工（DEC-239）：发起审查时在 PR 贴一行“第 k 轮审查已发起（档位 / 模型）”；进度窗口自读 GitHub 状态，总编排只在派发、DEC、要用户决定、合并顺序变化、PR 看不到的信息时通知。
- 会话命名与审查会话（DEC-240）：开发会话命名“编号 开发”（如“F-022 开发”），审查会话命名“编号 审查”（如“F-027 审查”）。Opus 审查一律在 claude.ai/code 单开“编号 审查”会话（环境「北森iTalent复刻」、Opus 5.5 High），加载 .claude/skills/cross-review，只读审查、不推送不评论，输出与 astra 一致；同一任务多轮复审在同一会话续审。ChatGPT 侧 astra / Sol 审查对话同样命名。派发与发起审查时把开发 / 审查会话链接发进度窗口。
- 同模型审查合并（DEC-242 ②）：返工后的复审模型与合并前最终复查模型相同时，合并为一次该模型 Ultra 审查。
- 前置会签与派单在后（DEC-248）：要问用户的事项先发进度窗口“拟提问”，其意见作为独立选项或备注写进提问，最多等 5 分钟（超时注明“进度窗口未回复”）；审查合并窗口只在对应 DEC 登记后才发结构性返工 / 拆分 / 换开发方清单，普通 P2 清单照常；进度窗口在第 3 轮及以上审查结论出来时主动发方案分析。
- 减少返工三条（DEC-249）：C 档核心任务先交设计、设计审过再写代码；任职版本链 / 编制 / 调动 / 离职·入职·兼职流转各自同时只放 1 个 PR（其他同模块最多 2 个，在途不追溯）；P2 分级——权限 / 安全 / 泄露 / 数据正确性类挡合并，体验类与极端并发边角 P2 由审查方标“可后补”转 F 任务不挡合并，有争议按挡合并。审查提示词须要求审查方对每个 P2 标注类别与是否“可后补”。
- Opus 审查最高强度与穷举表（DEC-250）：“编号 审查”会话用 Opus 5.5 最高强度；提示词强制先列“写入口 × 值来源”穷举表并逐格给结论；再观察 2 个 PR，仍漏报数据正确性类 P2 时再问用户。
- 开发方穷举表（DEC-251）：§1 自查清单新增“写入口 × 值来源”穷举表，开发方在 PR 描述列出，审查方核对是否列全。
- Codex 一律 Ultra 与会话命名（DEC-253）：Codex 开发与审查一律 Ultra（直到用户撤销，ChatGPT 周额度超 70% 时问用户）；所有会话命名“#PR号 编号 开发 / 审查 / 其他 具体任务”（如“#100 R2-T03 开发 离职管理”），未开 PR 写“编号 开发 具体任务”，开 PR 后补 #号（取代 DEC-240 的“编号 开发 / 审查”）。派发提示词首段注明会话名。
- 开发全部由 Claude 做（DEC-256）：C 档核心 Fable 5.1、一般 Opus 5.5 High；Codex 只审查（Opus 开发 → Sol Ultra，Fable 开发 → Astra Ultra）；不再有 Opus 审查环节，DEC-235 Codex 开发分支、DEC-240 Opus 审查会话、DEC-250 观察期失效；派发提示词的开发方只写 claude.ai/code + 模型 / 强度。
