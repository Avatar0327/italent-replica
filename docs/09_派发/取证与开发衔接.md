# 取证与并行开发的衔接规则

> 2026-10-03 制定。适用于三个窗口：**取证窗口**（本地，登录北森只读取证）、**编排窗口**（本地“云端并行开发工作流”，派发任务、登记 DEC、搬运审计）、**进度窗口**（本地，维护进度看板）。云端开发会话与 Codex 审查不访问原站。

## 1. 为什么会“取证后又返工”

2026-10-03 的实例：PR #35 第二轮按 DEC-093（重提时重新匹配流程）、DEC-100（意见按写的一方限定受众）实现完，取证 Q-M0-45/47 才查明原站做法相反，用户选了照搬（D-020②、D-021②），第二轮的这部分要再改一次。同类的还有 D-024（推翻 DEC-077，影响已合并的 PR #12）、D-025/D-026（影响已合并的 PR #16）。

根因有两条：

1. **先定决策、后取证**：DEC 是在没有原站证据时按推断定的，取证排在开发之后。
2. **门禁只写“后续”**：需取证清单里大部分条目的“阻塞”列写的是“某任务后续”，开发窗口因此照常开工，没有人被提醒要等。

## 2. 规则

1. **取证领先开发一到两个任务**。编排窗口派发任务 X 前，取证窗口先对 X 做一次**开工前取证扫描**：读 X 在路线图、需求基线和规格文档中的条目，把仍是 🟡 推断或“未取证”的行为补成 Q-M0 条目并取证。扫描完成之前，X 不派发。
2. **门禁分级**（写在需取证清单“阻塞”列）：
   - `X（开工前）`：会改动数据模型、状态机、接口语义或推翻 DEC 的，一律开工前完成；
   - `X 后续`：只影响文案、界面细节、默认值，且暂定做法改起来成本很低的，才允许合并后补。
   - 拿不准就按开工前处理。
3. **没有证据的决策标“暂定”**。新登记的 DEC 如果依据不是原站证据，在 DEC 正文写明“暂定，待 Q-M0-xx”；开发实现暂定 DEC 时，把相关逻辑收在一处，便于取证后替换。
4. **取证结论当天回传**。取证窗口每推送一批，立即用会话消息通知编排窗口：commit、每项结论属于“与现有一致 / 需用户决定 D-xxx / 用户已选待登记 DEC”中的哪一类，以及受影响的任务和 PR。
5. **编排窗口收到后**：当天把用户已选的 D 登记为 DEC；对受影响的未合并 PR 发修改清单，对已合并的 PR 开后续任务；需要用户决定的 D 立即提醒用户。
6. **开工和合并前跑门禁**：

   ```bash
   node scripts/evidence-gate.mjs R1-T08
   ```

   输出 ⛔ 的项未完成，或存在涉及本任务的待决 D，编排窗口不派发、不合并，并告诉用户“要等哪几项、在等谁”。退出码 1 表示有阻塞。
   待决 D 默认拦所有任务；只有登记册该行显式写了 `影响任务：R1-T03、F-007` 时才只拦所列任务（行里顺带提到的任务号不算范围）。取证窗口登记 D 时，能确定影响范围就写上这一项。
7. **登记分工**：取证窗口只写需取证清单、规格文档和登记册中的 D 条目（含选项）；DEC 由编排窗口登记；进度看板由进度窗口维护。各窗口推送前先 `git pull --rebase`。
