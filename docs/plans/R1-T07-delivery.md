## 规则落地

- **版本**（REQ-APV-001 R1~R3、R6）：草稿整体替换；已发布不能直接改（409 `APPROVAL_VERSION_PUBLISHED`），只能“编辑最新版本”以当前生效版本为底稿生成下一版草稿；发布只影响新实例；在途实例按冻结版本流转；废弃移出可用列表且不参与匹配。
- **发布校验**：发起条件为空且未声明兜底 → 400 `APPROVAL_CONDITION_REQUIRED`（DEC-018）；未配置异常管理员 → 400 `APPROVAL_EXCEPTION_ADMIN_REQUIRED`（DEC-054）；同类型普通流程优先级相同 → 409（DEC-096，咨询锁防并发）；异常管理员须为有效成员。并发创建同编码 → 409（冲突安全插入，X-21）。
- **匹配**（DEC-017 / DEC-096）：先按审批类型过滤已发布的当前版本，再按优先级评估发起条件，兜底流程始终排在同类型条件流程之后；同类型都不满足 → 409 `APPROVAL_PROCESS_NOT_MATCHED`，不跨业务兜底。候选流程按编码键集分批读取（每批 200），流程数量不设总量上限（DEC-101）。
- **审批类型与流程编码**（清单 14 / 18，`14` §11.1）：不接受发起人指定；服务端按业务派生原站标准编码——入职 `EntryProcessNew`、转正 `ProbationProcessNew`、实习转正 `TraineeEntryProcess`、离职 `DimissionProcessNew`、调动 `TransferProcessNew`、退休 `RetireProcess`；员工子集变更按子集取各自编码（如 `ChangeEducationProcess`）。DEC-116（F12）补齐「新增员工」`AddEmployeeProcess`（任职记录对象）与「个人信息变更」`EmpInfoChangeProcess`（员工信息对象）两个类型及草稿预置，发起入口随后续业务接入。原站没有“重聘”审批类型：重聘入职、退休返聘归入「入职」（`07` §2）。任职记录上的组织调整异动没有标准编码（原站「组织调整」挂在组织调整申请对象上）。
- **发起条件**：字段路径白名单 + 运算符 eq / ne / in / not_in / is_empty / not_empty / in_org_tree，高级表达式支持 and / or / not / 括号。
- **重提**（DEC-103 / DEC-113，`14` §11.8）：驳回或撤回后再提交一律沿用原实例与原流程版本，不重新匹配（即使改了发起条件字段），也不再触发“流程发起”；驳回后按驳回节点的「驳回后提交方式」，撤回后从第一个节点重新审批。只有原发起人能重新提交，并按首次提交复核其当前权限（F3）：员工子集变更须仍持有自助申请按钮、账号仍绑定异动本人，且“旧载荷 + 本次修正”合成的完整载荷每个字段都仍在员工自助修改清单内（与首次提交共用 `assertSelfServiceFields`，空修正也复核，第四轮 N1），否则 403。员工子集变更撤回后在审批侧沿原实例重提，申请回到待审批、修正追加为新版本（F9）。
- **审批人**（REQ-APV-002）：五种表达式；组织负责人 / HRBP 取业务日期的现行版本，人员经账号绑定落到用户；解析到没有账号、成员关系已撤销或全局账号已停用（`users.status`，第五轮 R4-3）的人员按“审批人为空”处理（DEC-098）；离职 / 退休已生效但账号仍有效的人员同样视为审批人为空（F6，`14` §11.7，只在审批候选资格里判断，不改通用账号绑定查询）；派单前复核资格（C-非5）。所有派出新任务的入口统一按 `isEligibleApprover` 复核：表达式解析、加签激活与回到原审批人、普通转交、加签名单、管理员转交 / 改派、异常管理员交接的替代人（第四轮 N2，不合格返回 400 `APPROVAL_USER_INVALID`）；离职前已有的待办不自动撤销，由管理员转交（`14` §11.7）。同一次推进内路由查询按主体缓存（X-20）。
- **成员停用与派单的串行协议**（第五轮 R4-2，第六轮 R5-1 / R5-2 改用派单闸）：审批中心用租户 × 用户的事务级咨询锁作“派单闸”（`resolver.closeAssigneeGate` / `isAssignable`），成员行与 users 行不再兼作派单信号；锁键里的租户与用户 ID 先按数据库 UUID 语义规范化（`::uuid::text`，第七轮 R6-1），请求头、请求体里大小写不同的同一 UUID 取到的是同一把闸。停用方（撤销成员关系 / 全局停用账号）在挂接点里先以排他方式关闸（可以等），再逐单锁业务单 → 实例接管其在途待办；审批方把某人当作接手人（派单、交接、接管）或以其身份操作时，以共享方式试取闸，拿不到即视为正在停用，从不等待——操作人本人在入口试取（`openRun` / `startOrResume`），候选人、异常管理员、回退的租户管理员、交接替代人在选用时试取，写入新待办前再复核一次（`insertTask`）。撤销在接管完成后的最后一步才锁成员行改状态，锁模式为 `FOR NO KEY UPDATE`（只改非键列；与其他事务引用该成员的外键 `KEY SHARE` 相容，如首次交接插入替代人记录——F-008 / R6-2，原为 `FOR UPDATE` 会与之成环）；一个事务处理多张单时（停用接管、手动交接的一批）按全局取锁顺序（异动员工, 实例编号）升序逐单处理，停用接管跨页用同一顺序的键集游标延续，手动交接的选批与对外游标仍按实例编号、批内按该顺序处理（F-008 / R6-3，`handover.LOCK_ORDER`）；全局停用以 `FOR NO KEY UPDATE` 锁 users 行（与审计等外键检查的 `KEY SHARE` 相容，R5-1），授予 / 重新激活成员关系先以 `FOR SHARE` 锁 users 行（与全局停用互斥，停用期间该用户不会在任何租户新变成有效成员，R5-2）。因此停用方只等闸与业务锁，审批方从不等停用方持有的锁，不成环。通知接收人与抄送对象只按已提交的状态判断：已停用不发；停用尚在进行时照常登记通知（R5-4，发送意图不因可能回滚的停用而丢失）。
- **审批人为空与异常管理员**：首节点为空 → 提交报错（409 `APPROVAL_FIRST_NODE_EMPTY`）；中间节点一律转异常管理员（DEC-054，不再接受自动跳过 / 自动同意配置）。异常管理员恰为发起人或异动本人时转其有效直线经理，没有则拒绝提交（DEC-091，提交与仿真共用 `submitBlockers` 预检）；流程上的异常管理员已停用时由租户管理员接管（DEC-098）。异常管理员停用前必须交接（`POST /exception-admins/handover`；迁移 0030 触发器拦截未交接的停用）：替换流程配置只需流程配置权（DEC-102），改派在途实例逐单复核操作人的实例转交按钮、数据范围与 DEC-092 本人回避（F2）：数据范围在查询限量之前过滤（第四轮 N4），调用者范围外的实例只计入 `unlisted`、不返回编号与原因（N3）；范围内因本人回避等原因跳过的实例在 `skipped` 里列出，超过单批 200 个时返回 `remaining` 与 `nextCursor`，下次带 `cursor` 翻过（N4）；拿到锁后实例已结束或已无待转任务时什么都不写（N5）。交接同时记下替代人（并发首次指定时审计旧值记实际被覆盖的值，R4-5）；交接的来源用户须是本租户成员，否则 400（R4-6）；交接结果（含幂等重放）按调用者当前的范围裁剪，不可见的实例只计入 `unlisted`（R4-1），范围谓词为 NULL 的实例同样计入（R4-7）。该成员停用时（平台撤销成员关系或全局停用账号的同一事务内，R4-3），先做停用保护（仍是可用流程的异常管理员即拒绝），再把其剩余在途异常待办自动转给替代人——替代人须具备审批资格、数据范围覆盖该实例、不是发起人或异动本人，否则转给租户管理员：按开通先后逐个复核审批资格，已离职或不可用的跳过（R4-4），候选分批扫描、不在资格过滤前截断（R5-3），恰为发起人或异动本人的按 DEC-091 回避；无人可接手即拒绝停用；转派写审计与 outbox（DEC-123）。
- **自审与同人自动处理**：自审（发起人或异动本人）→ 跳过且不计同意，转其直线经理（DEC-068，优先于同人自动处理），被跳过的人不因此成为参与人（C-非3）。相同 / 历史相同审批人自动处理的结果按节点配置（DEC-106）：「同意」记为该审批人同意（任务 `approved`、日志 `auto_approve`），并触发同意消息规则（X-14）；「跳过」沿同意路径流转、处理人记为系统（任务 `skipped` 无审批人、日志 `skip`），不计为任何人的同意。“与上一节点相同”比较上一节点解析出的候选人（DEC-114，暂定待 Q-M0-43），所以 A→A（跳过）→A 可连续跳过。“历史”只认本轮——驳回或撤回后重提，上一轮的同意不参与自动处理（DEC-124 暂定，TODO 需取证 Q-M0-43 / #39），且管理员干预 / 跳转之后，之前的节点不再算历史（F7，`14` §11.6）：实例记有效历史边界，失效的同意保留在任务与审计中、不参与自动处理。自动处理前按候选人当前字段权限做盲审，受阻按 DEC-069 转异常管理员（清单 5）。
- **会签节点**（F-003，DEC-117 / DEC-144，`14` §11.4、§12）：多个审批人表达式逐人解析，审批人同时审批、无先后；审批人为空（DEC-054 / 098：中间节点该位转异常管理员，首节点任一人为空即拒绝提交）、自审（DEC-068）、相同 / 历史相同审批人自动同意（会签只有「同意」，DEC-106）都逐人生效；两个表达式解析为同一人或落到同一接手人时只派一条任务，被合并那一席的候选人随保留的一席留存，下一节点按全部候选人比较（DEC-114，与仿真一致）。流转规则照搬原站三种：任一人同意即可（新节点默认，每个出口动作整数 1）、需所有人同意（同意 100%、其他出口动作整数 1）、自定义审批方式（按出口动作设整数或百分比，百分比向上取整）；某出口动作的点击人数先达到其规则即沿该动作流转，自动同意与并加签人都计入；系统接管合并席位使多个出口动作同时达标时“不同意”优先（DEC-155，`countersign.EXIT_PRIORITY`）。「不同意」是出口动作、按规则计数，达标即沿不同意连线流转到结束（`14` §12.2：本租户不同意连线都连到结束）——实例“未通过”（disapproved），任职申请、员工子集变更申请办结为“未通过”、不生效、不能撤回或重提（`types.EXIT_TARGETS`、`engine.followExit`）。「驳回」是节点开关（缺省开启）、不进流转规则，任一人驳回即整单退回。节点流转后其余未处理待办自动结束（暂定，Q-M0-57 / #56）；自定义规则在全部处理完仍无法达成时按不通过退回（暂定，#57）。结算在实例行锁下进行（入口按 F-008 的取锁顺序锁员工 → 业务单 → 实例），同一节点只结算一次（真 PG 交错测试 AC-APV-30；`settleCountersign` 另有守卫，变异检查确认测试能区分）。一人一票（第二轮 P2-1）：用户 ID 在审批入口按数据库 UUID 语义规范化（与 R6-1 同口径）；同一次激活内按有效人员计票；转交、加签、管理员转交 / 改派不能派给本节点已有任务（在办或已同意 / 不同意）的人；异常管理员交接、停用接管、盲审转异常管理员等系统接管让同一人承接多席时，多出的一席记为“由同一人接手、不重复计票”（merged）并重新结算；业务单在审批中被改动时结算不推进（第三轮 P2-N1：`settleCountersign` 复核业务版本，与审批动作的 `APPROVAL_BUSINESS_CHANGED` 冻结一致）。会签前加签（DEC-152，暂定）：按席位生效，原席位挂起，前加签人依次先审、不计入流转规则（不能点「不同意」），全部同意后原席位恢复为待办。审批人撤回：节点未流转时只重开本人；已沿同意流转时取消其后的待办、重开本人并恢复因流转而结束的席位（每人一席，进行中的前加签不恢复）。系统自动结束 / 合并的任务、之前那次流转被撤回取消的下游待办不算人工处理（第二轮 P2-3）；流转时还有未完成的前加签的不能撤回，避免原审批人绕过前加签（第三轮 P2-N2，同 F4）。
- **节点动作**：同意、不同意按节点出口动作提供（DEC-144；缺省只有同意，发布时勾选加签或开启相同 / 历史相同审批人自动处理须有「同意」出口动作，提示照原站“勾选加签的XXX节点必须配置同意出口线”）；驳回（实例“退回”，节点开关，缺省开启；关闭后单人与会签节点、加签人都不能驳回，详情不公布）；转交；加签按节点类型：单人节点分前加签与后加签（DEC-095，`14` §11.4），会签节点有前加签（DEC-152）与并加签（F-003：加签人与原审批人同时审批、计入流转规则；单人节点请求并加签、会签节点请求后加签返回 409 `APPROVAL_ADD_SIGN_TYPE_UNSUPPORTED`）。单人节点：一次可选多人（≤10），按选择顺序依次审批，第一位立即派待办、其余排队；前加签全部同意后回到原审批人，后加签全部完成才离开本节点；任一加签人驳回即整单驳回；加签人不能审批中编辑（§11.3）；加签人不能再加签，入口返回 409 `APPROVAL_ADD_SIGN_NESTED`（F5）；加签链上的同意（加签人的同意、发起了后加签的原审批人的同意）不能撤回，以免丢失未完成的加签义务（F4）；排队加签人激活前、回到原审批人前都复核资格，已停用或已离职即转异常管理员并保留原链（F8）；抄送（节点开关，被抄送人收到通知、可查看本节点表单，DEC-097）；审批人撤回（节点开关，下一节点尚未人工处理时可撤回本人的同意，任务回到本人，DEC-097，时限待取证 #37）；催办（节点“继承 / 开启 / 关闭”覆盖流程设置，同一实例 30 分钟一次，X-15 / C-非5）；发起人撤回（审批侧与业务单入口都只允许发起人，并复核其当前撤回权限，清单 10 / C-非5）。
- **审批中的单据**（清单 1）：任职申请审批中，业务端 PATCH 返回 409 `APPROVAL_IN_PROGRESS`，只有审批适配器能按节点可编辑字段修改；实例绑定审批人所读载荷的业务版本，载荷被改过时携旧 revision 的同意返回 409。
- **审批中编辑**（清单 2~4）：可编辑字段 = 节点开放 ∩ 审批人当前字段编辑权，并校验对象更新权限；快照覆盖预置字段、自定义字段（`custom:<id>`）、生效日期（一律计为变化）与离职最后工作日（写入业务顶层并重算生效日）。【编辑并同意】刷新快照后按新快照重新做盲审，受阻则整单回滚（编辑不生效、任务仍在本人名下）并返回 403。
- **重提入口**：任职申请在申请单上修改后提交（详情不公布审批侧“重提”，X-16）；员工信息变更可在同一张单上修正重提，修正内容追加为新版本（DEC-099）；员工子集变更不做审批中编辑（DEC-105，F14）：配置时拒绝子集节点的编辑设置（400 `APPROVAL_DEFINITION_INVALID`），详情不公布 `edit`，历史配置下执行编辑返回 409 `APPROVAL_EDIT_UNSUPPORTED`。
- **管理员**（DEC-063 / DEC-070 / DEC-092）：持有 `ApprovalInstance` 的转交 / 干预按钮且实例在其数据范围内（人员维度取异动员工、“使用用户”维度取任职业务的真实创建人），才能转交或干预；不能以他人名义同意 / 驳回；不能干预本人发起或本人为异动对象的实例，详情也不公布这两个动作（F16）；转交、干预两个动作按各自按钮的权限分别公布（第四轮 N8）；转交给自己须填理由并留痕。审批侧撤回同样按真实创建人维度复核范围（F10）。
- **流程配置权**（DEC-102）：仅限持有 `admin.process_matrix` 能力的租户级管理员身份；部门级身份即使持有流程对象按钮也不能配置；查看与仿真仍可凭流程对象查看权。与实例干预权分开。
- **最小披露**（DEC-057）：详情只显示查看人所在节点（被抄送人为抄送节点）的表单字段，再按其字段权限裁剪；标题只含审批类型名称，不含个人数据（清单 8）；用户可见日志里的字段名按“节点表单 + 字段查看权”共同过滤（X-13 / DEC-119）。查看人所在节点、记录隐藏与可用动作一律按完整任务计算，最新 200 条只是展示窗口（F1）。
- **审批记录查看权限**（DEC-100 / DEC-104 / DEC-115，`14` §11.9）：审批记录与意见默认对所有能打开详情页的人可见，详情带“勿在意见中填写敏感信息”提示；节点开关是查看方的设置——查看人参与过的任一节点勾选了开关，或查看人是发起人且开始节点勾选了开关，详情与历史接口即隐藏审批记录与已处理的任务（含本人的历史与意见），PC 端只留当前待办，返回 `recordsHidden: true`；被抄送人、范围内管理员不受限制；开关随流程版本冻结。
- **盲审**（DEC-058 / DEC-069 / DEC-119）：只看审批人对本单变化字段的查看权，节点表单白名单不参与拦截；先校验 revision 与任务状态，再判断盲审；变化字段中有审批人不可见的 → 403 `APPROVAL_BLIND_REVIEW`，在办任务转异常管理员；异常管理员本人也看不到时不循环给自己建任务，详情不显示其无法执行的同意 / 驳回（C-非4）。
- **审计与 outbox**（清单 12 / 13）：任务的创建（含自动跳过）、取消、盲审转交、交接都按任务 ID 写字段级审计；管理员跳转 / 转交 / 干预、审批中编辑、盲审转交都写 outbox 事件。
- **加锁顺序**（清单 11）：所有入口先锁业务（适配器 `lock`），再锁实例；冲突返回 409，不自动重试。
- **容量**（DEC-101）：去掉单实例任务 / 日志的总量上限；详情默认给出最新 200 条，完整历史经 `/instances/:id/tasks|logs` 分页读取；同一审批单同时在办的任务不超过 50 个（413）；自动跳过链在内存中维护任务，不逐节点重查。
- **仿真**（DEC-036）：只用虚拟数据——审批人关系、直线经理、组织上下级都由输入给出，不读取真实人员、组织负责人或账号绑定（清单 7）；输入按条件字段类型校验，格式错误返回 400（X-18）；单流程仿真与按对象仿真都复用提交预检（首节点为空、异常管理员本人回避后无人接替），给出 `startable` / `blockers` 或 `replicaStartable` / `replicaError`（X-17 / F13）。
- **出厂预置**（DEC-018 / DEC-094 / DEC-116）：`POST /presets/install` 只接受 If-Match: 0（F17），幂等、并发安全；每个审批类型一条草稿，有标准编码的都带“流程编码 = 标准编码”条件：调动照搬已取证结构，各节点相同 / 历史相同审批人自动处理全部关闭（F11，`14` §11.10 更正）；离职为“直接上级 → HR 访谈”近似；其余类型为“部门负责人审批 → HRBP 审核”草稿，节点结构待取证（#38）。异常管理员由租户指定后发布。
- **调动审批表单**（DEC-118 / DEC-122 / F15 / N6，`14` §11.2）：`transfer-view.ts` 对 TransferDetailView 的 33 个标准字段 / 区块逐项登记——已交付 15 项：调动人员（实例抬头）与调动日期、工号、性别、年龄、新部门、新职务、新职级、新职等、新职务序列、新职位、新直线经理、用工形式、人员类别、调动后是否部门负责人。任职字段的审批表单值、字段权限、节点表单共用任职记录字段编码；性别、年龄取员工档案（年龄按业务日期由出生日期计算），是只读带出字段（不能配置为可编辑），按“节点表单 + 员工信息对象的字段查看权”裁剪。其余 18 项登记延期——异动类型、调动原因、是否带编制调动 → R1-T09，交接人、薪资 / 合同 / 履历标志、试岗四项、新增下属、兼职调整、薪资调整、合同变更、职责转交、目标调整（两项未列入任务书，派发时确认） → R1-T10。预置调动表单只取已交付且在表单上的字段。

## 接口

`/api/tenant/approval`：`GET /types`；`GET|POST /processes`；`GET /processes/:id`；`PUT /processes/:id/draft`；`POST /processes/:id/{versions,publish,discard,simulate}`；`POST /presets/install`；`POST /exception-admins/handover`；`POST /simulate`；`GET /todos`；`GET /notifications`；`GET /instances?role=initiated|participated&businessId=`；`GET /instances/:id`；`GET /instances/:id/{tasks,logs}`（分页，带 `recordsHidden`）；`GET /admin-logs`；`POST /tasks/:id/{approve,disagree,reject,transfer,add-sign,cc,retrieve,edit}`（加签请求体为 `userIds`（按顺序，≤10）与 `type`：`before` / `after` / `parallel`）；`POST /instances/:id/{urge,withdraw,resubmit,admin-transfer,admin-intervene}`（干预 `kind` 为 `reassign` 改派或 `jump` 跳转节点）。

任职申请仍用原入口 `POST /api/tenant/employment/businesses/:id/submit`（请求体为空对象，流程编码由服务端派生），提交即在同一事务里发起审批；撤回、删除同步结束在途实例。员工信息变更的同单修正经 `POST /instances/:id/resubmit` 的 `fields` 提交。
