## 1. 总体思路与 main 现状

**退休 = 任职业务 `kind='retirement'` 的申请单层 + 离职扩展行 `exit_requests` + 退休薄扩展行 `retirement_requests`**。退休与离职共用离职全部机制，差异只在：按钮、表单字段、退休类型派生、实际退休日期回写、同时返聘、视图谓词、审计动作名。不新建第二套申请单，也不新建第二个编排器。

## 2. 数据模型与迁移清单

### 2.1 退休用 `exit_requests`（不加列）

退休创建时写一行 `exit_requests`（与离职同列，`R2-T03 §2.1`）：`staff_id`、`mode`、`initiator`、`initiator_user_id`、`process_code`、`handover_employee_id`、`add_to_blacklist`、`pending_transfer_ack`（含 #430 的超限标记）、`duty_transfer_timing`、`pre_release_date`、`batch_id` 照用。离职专用列对退休**必须为空**：`exit_type_code`、`reason_code`、`whereabouts_code`、Q-M0-85 结算字段、`actual_leave_date`（R2d 退休申请字段清单不含这些，服务层校验，§3.2）。编制预减、停用计数、§6B 投影、作废、合同、转交、#432 撤销全部按扩展行生效，无需按 kind 分叉。

**A-20 一致性规则（手工与批处理同一函数）**：`personnel/validation.ts` 新增 `normalizeRetirementRange(after)`，在 `appendEmployee`（`employee-write.ts:33` `validateDates(after)` 同处）对所有写入入口生效——人事 PATCH、子集反写、5c2 批处理、5d2 写回：P 为空时上下限一律置空（**清空优先于“弹性范围已核准”**，A-20 推荐值，核准标志本身不动）；P 为空而请求显式给了非空上下限 → 400 `RETIREMENT_RANGE_WITHOUT_EXPECTED_DATE`；上下限都非空时只校验自身次序 `earliest ≤ latest`（否则 400 `RETIREMENT_RANGE_INVALID`）。**不校验 P 是否落在上下限之内**（v1.1 的 `earliest ≤ P ≤ latest` 已删：规格没有该约束，且会拦住“P 未核准可重算、范围已核准冻结”的合法写入，第 2 轮 P2-1）；P 重算后移出已核准的旧范围是允许的状态，由 HR 决定是否解除弹性核准，AC-RT-23 固定其结果。

## 8. 退休同时返聘（5b）

### 8.1 日期口径（DEC-296①，A-1【须 00】）

退休记录生效日 E = L + 1；返聘任职 `retire_rehire` 生效日 **R = E′ + 1**；退休记录只覆盖 E′ 当天（时间轴 `[E′, E′+1)`），次日接返聘（新任职周期，`employment_cycles.entry_type = 'retire_rehire'`）。与 AC-RT-01 字面“返聘日 = 最后工作日 + 1”冲突（那会让退休记录长度为 0）：按 DEC-296① 与原站样本（规格第 228～230 行）取 E′ + 1，由 00 拍板后登记差异。`retireRehireStartDate(E′)` 是唯一决定 R 的函数。

### 8.2 一体化入口与创建时校验

- 同一 `POST retirements/employees/:id`（直接 / 申请均可）请求体带 `reEmployed: true` 与 `rehire`：`{ fields, customFields, formId?, entry: { probation, probationMonths?, probationEndDate? }, contract? }`，结构与 `POST employees/:id/businesses kind=retire_rehire` 一致（`entry-options.ts` 的 `entryControls`，不允许 `pendingEntry`）；`contract` 用 `contracts/input.ts fieldsSchema`。不接受 `loginEmail`：沿用原账号。通用入口不接受 `rehire`（同时返聘只经专用入口，400 `RETIREMENT_REHIRE_USE_ENDPOINT`）。
- 创建时校验在 §3.2 第 1 步（结构）与第 6 步（业务）：字段权限按 `Employment.Create`（返聘写的是新任职）+ 合同对象创建权与范围（照 `entry-contract.ts` 的重验口径）；返聘部门 / 职位在 R 日可用（`validatePreparedEmployment` 干跑）；黑名单互斥（§4.4）。
- 判定复用：“前一条是退休才能返聘”只经 `write-service.ts:410`；Offer 同步的退休返聘仍由 `offer/sync.ts:101` 判定，不改；`rehire-match.ts` 不改。

### 8.3 生效时生成返聘（`runSteps` R-2，保存点内）

1. **资源预锁**：`lockExitOrganizationResources`（`exit-void-applications.ts:82`）对 `re_employed` 的退休把返聘目标部门 / 职位所在组织与编制一并纳入 ④⑤（与离职的组织锁同一次取，先于审批实例），不在保存点里新取组织 / 编制锁。
2. **受信上下文**：`retirementRehireContext(ctx, business)` 只在编排器内构造：`commandId = ${ctx.commandId}:rehire`、`expectedRevision` = 员工行在退休落地后的当前 revision（同事务内读，不比外部 revision）、`trustedRehire: true`；不对外暴露，不经离职门禁（返聘不是终止业务）。
3. `createEmploymentBusiness(tx, rehireCtx, employeeId, { kind: 'retire_rehire', mode: 'direct', effectiveDate: R, fields, customFields }, { entry: { ...plan.entry, pendingEntry: false } })`：经 `assertBusinessSequence`（前一条 = 刚落地的退休，满足 `:410`）、`prepareInheritance`（新周期）、黑名单拦截（`write-service.ts:153`）、编制与部门可用性；直接业务当场写入时间轴（R 在未来时为已落地的未来记录）。
4. `plan.contract` 存在时调 `generateContractForBusiness`（`contracts/ports.ts`，与 `entry-contract.ts` 同一端口），起始日 R；合同授权在创建时已按发起人重验，生效时以发起人身份记审计（调度生效时 actor = 系统，`detail.initiatorUserId` 记原发起人）。
5. 写 `retirement_requests.rehire_business_id`、`exit_effects(kind='rehire_created')`，审计 `employment.retirement.rehired`。
6. 任一步失败（部门 R 日已停用、黑名单、合同冲突等）→ 整个退休生效失败（保存点回滚，记 failed，HR 待办、可重试），**不出现“已退休、未返聘”的半套**。

## 9. 预计退休日期规则与弹性范围（5c1 / 5c2）

### 9.1 规则、字典与匹配（5c1；纯函数 `packages/domain/src/employment/retirement-rules.ts`）

- 规则设置：`GET / POST / PUT / DELETE retirement-rules`、`POST retirement-rules/:id/copy`、`PUT retirement-rules/:id/enabled`（照 `auto-regularization-routes.ts:83～153`）；`?purpose=expected_date | flexible_range`。个人身份字典：`GET / POST retirement-identity-types`、`PUT retirement-identity-types/:id`。配置对象 `tenant.employment.configuration.write`（管理员 `other_settings`），读对持 EMPLOYMENT `object.view` 者开放；审计 `retirement_rule.save / delete / enabled`、`retirement_identity_type.save`。
- **条件字段白名单**（≤10 条，AND）：性别 `gender`、个人身份 `identityType`（取值只能是字典启用编码）、用工形式 `employType`。值取计算时点的人事最新版本与当前主职任职快照。其余候选字段（人员类别等）待 A-9。
- `matchRule(rules, person)`：只看 `enabled`、`purpose` 相同的规则；先按组织范围（含下级时展开，`org/hierarchy-reader.ts listOrgDescendantsInTransaction`，取员工当前主职部门）过滤，再按 `priority` 升序、`sequence_no` 升序逐条判条件，**命中第一条即停**（RT-R5，AC-RT-03）。
- `expectedDateOf(birthday, years, months)`：年月合并为总月数加到出生日期，截到目标月末（2-29 → 平年 2-28）；出生日期为空 → 空；无规则命中 → 空（A-4）。
- `flexibleRangeOf(expected, earlier, later)`：`expected` 为空 → 上下限都空（RT-R6、A-20）；否则 `[expected − earlier 月, expected + later 月]`（同样截月末）。

### 9.2 每日计算、立即执行与失败恢复（5c2）

- **调度入口**：挂在定时生效的进程内定时器（照 `auto-regularization-scheduler.ts`），每租户本地 03:00 之后的调度检查当天批次；`purpose` 两种各自一行 `retirement_rule_daily_runs`；对应开关关闭的日子不建行。
- **占用与续跑**（不靠“同值不写”代替恢复）：
  1. 认领：`INSERT … ON CONFLICT DO NOTHING` 建 `state = running`、`lease_until = now + 10 分钟`；已存在且 `state = running`、`lease_until < now` 的行用 CAS（`UPDATE … WHERE lease_until < now RETURNING`）接管并 `attempts + 1`；`done` 行跳过。认领在独立短事务。
  2. 分页：按员工 ID 升序、每页 200，从 `position_employee_id` 之后取候选；每名员工一个事务（`withTenant` + RLS），员工锁 `SKIP LOCKED`。
  3. 每页结束在**同一短事务**里：推进 `position_employee_id`、续租 `lease_until`、把本页锁忙跳过的员工写入 `retirement_rule_run_skips(state = pending)`。进程崩溃时下一次调度在租约过期后从该位置续跑；已处理员工的重复执行因“同值不写”为零写入；已提交页的锁忙清单在库里，不随进程丢失。
  4. **锁忙（第二遍）**：主扫描到末尾后，读本批次 `state = pending` 的跳过行逐个重试（同样 `SKIP LOCKED`）：成功则删除该行；仍锁忙则置 `given_up` 并 `skipped_count + 1`（同一短事务）。第二遍同样可被崩溃打断：接管者看到位置已到末尾、仍有 `pending` 行，即直接进入第二遍。`pending` 行清空后才置 `done`。`given_up` 的员工本日不再追，次日批次照常覆盖，HR 可“立即执行”。
  5. 单员工业务错误记入运行回执（员工 ID、原因）不中断；存储错误回滚该员工并结束本次调度（行仍 running，租约过期后续跑）。全部完成置 `done`。
- **立即执行** `POST retirement-rules/run?purpose=`：不占当天登记；一次最多处理一页，回执带 `next`（`retirement_rule_run_cursors.id`）；续跑请求带 `cursor`：按 `(tenant_id, id)` 查行，且 `user_id = 当前操作人`、`purpose` 相同、`business_date = 当前租户业务日`，任一不符 → 400 `RETIREMENT_RUN_CURSOR_INVALID`（跨租户因 RLS 查不到同样得此码，不泄露存在性）。
- **写入**：`expected_retirement_confirmed = true` 的不写 P（AC-RT-02）；`flexible_range_confirmed = true` 的不写上下限，**但 P 为空时按 A-20 清空上下限**；算出值与当前值相同不写；不同则 `appendEmployee(..., false)`（经 §2.3 同一 `normalizeRetirementRange`），审计 actor = 系统用户、`reason: 'retirement_rule'`、带规则 ID。
- **候选**：计算日当天在职（时间轴当天记录不是 leave / retirement、人员状态不是待入职）的员工；离职 / 退休人员不重算（A-4）。业务日按租户时区（DEC-056）。

## 10. 五视图口径（5d1；BE-12 依赖）

### 10.1 `asOf` 的语义：业务有效时点，按查询时已知的数据重建

`asOf` 表示**业务有效日**，回答“按现在掌握的数据，`asOf` 那天谁处于什么退休阶段”。状态、载荷、时间轴、撤销 / 墓碑全部取**查询时的当前数据**，不做“当时已知状态”的回放：

| 数据 | 取法 |
|---|---|
| 退休单状态 | 当前最新状态事件（被撤销的单当前是 `voided` / `deleted`，视为从未生效，任何时点都不进已完成 / 退休中） |
| 退休单日期 | 当前最新载荷的 L′ / E′（顺延后值） |
| 退休单“已提交” | 首个 `in_review`（申请）或 `approved`（直接）状态事件的 `created_at` 落在 `asOf` 当日结束（租户时区）之前——这是不可改写的事实，仅用作“这张单在 `asOf` 时是否已存在” |
| 在职与任职周期 | 当前时间轴在 `asOf` 当天的主职记录（撤销已生效退休后时间轴已恢复，自然在职），周期 = 该记录 `staff_id` |
| 人事字段 P / 上下限 | `personnel_employee_versions` 在 `asOf` 当日结束之前的最新一版（人事版本链只有记录时间，没有业务有效日，记录时间即其有效时间） |

由此，审查反例 1（10 日退休、20 日撤销、查 `asOf = 15`）：20 日之后查询，退休单当前 `deleted`、时间轴在职 → 只可能进“过期未退休”（若 P < 15）；20 日之前查询，退休单 `effective`、E′ = 10 ≤ 15、时间轴不在职 → 只进“已完成”。同一时刻的查询结果互斥。BE-12 时点花名册与本口径相同（撤销会改变历史报表，A-7 一并确认）。

### 10.2 谓词（`employment/retirement-views.ts` 的 `retirementViewSql(view, { tenantId, asOf, upcomingDays })` 与纯函数 `packages/domain/src/employment/retirement-views.ts` 的 `classifyRetirement`）

记号：S = `asOf` 当天主职记录的 `staff_id`（当前周期）；“本周期退休单”= `exit_requests.staff_id = S` 的 kind = retirement 业务；“流程中”= 当前最新状态 ∈ {in_review, approved} 且已提交（10.1）。

| 视图 | 谓词（全部在分页前叠加 `employmentVisibilitySql`，DEC-177） | 行 | 默认排序 |
|---|---|---|---|
| 即将退休（B16） | `asOf` 在职 ∧ P 非空 ∧ P ≥ 周期 S 入职日 ∧ `asOf ≤ P ≤ asOf + N` ∧ 本周期无“流程中”或 `effective` 退休单 | 员工 | P 升序 |
| 过期未退休（B17） | `asOf` 在职 ∧ P 非空 ∧ P ≥ 周期 S 入职日 ∧ `P < asOf` ∧ 本周期无“流程中”或 `effective` 退休单 | 员工 | P 升序 |
| 退休中（B18） | 退休单“流程中”（含 approved 未到期、生效失败 / 挂起仍为 approved 的单），或当前 `effective` 且 E′ > `asOf` 且已提交 | 退休单 | 最后工作日升序 |
| 已完成（B19） | 退休单当前 `effective` ∧ E′ ≤ `asOf` | 退休单 | 最后工作日降序 |
| 全部（B20） | 已存在（创建 ≤ `asOf`）的全部退休单，含草稿、驳回、disapproved / voided / deleted | 退休单 | 创建时间降序 |

- **周期限定**：前两视图只看当前周期 S 的退休单，旧周期已生效退休不排除返聘员工（审查反例 2）；“P ≥ 周期 S 入职日”排除返聘员工身上早于本周期的旧预计日期（否则返聘人员会永久出现在“过期未退休”），HR 为返聘员工维护新 P 后按新 P 进入视图。
- 草稿、已驳回只进“全部”（A-7 采用审查推荐）。
- `upcomingDays` 缺省读 `retirement.upcoming_days`，请求可传 1～365。员工行返回 P、退休到期天数 `P − asOf`、弹性上下限；单据行返回 L′ / E′、退休类型、是否同时返聘与返聘业务 ID、审批状态、发起方式、生效失败原因。
- “撤销的退休记录”沿用 #432 的撤销视图形态，`view=cancelled` 作为额外取值（5a′ 合入后可用，不计入五视图）。
- **测试要求**：SQL 与纯函数各自对固定夹具断言**具体期望行**（AC-RT-18 列出的每个边界都写死期望视图与行 ID），再加随机夹具的 SQL ≡ 纯函数对照；只断言两套实现相等不算覆盖。
