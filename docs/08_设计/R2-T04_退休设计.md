## 1. 总体思路与 main 现状

**退休 = 任职业务 `kind='retirement'` 的申请单层 + 离职扩展行 `exit_requests` + 退休薄扩展行 `retirement_requests`**。退休与离职共用离职全部机制，差异只在：按钮、表单字段、退休类型派生、实际退休日期回写、同时返聘、视图谓词、审计动作名。不新建第二套申请单，也不新建第二个编排器。

## 2. 数据模型与迁移清单

### 2.1 退休用 `exit_requests`（不加列）

退休创建时写一行 `exit_requests`（与离职同列，`R2-T03 §2.1`）：`staff_id`、`mode`、`initiator`、`initiator_user_id`、`process_code`、`handover_employee_id`、`add_to_blacklist`、`pending_transfer_ack`、`duty_transfer_timing`、`pre_release_date`、`batch_id` 照用。离职专用列对退休**必须为空**：`exit_type_code`、`reason_code`、`whereabouts_code`、Q-M0-85 结算字段、`actual_leave_date`（R2d 退休申请字段清单不含这些，服务层校验，§3.2）。这样编制预减、停用计数、§6B 投影、作废、合同、转交、#432 撤销全部按扩展行生效，无需按 kind 分叉。

### 2.2 新表 `retirement_requests`（5a，1:1 `exit_requests`）

| 列 | 类型 | 说明 | 批 |
|---|---|---|---|
| tenant_id, business_id | uuid, PK | 复合外键 → `exit_requests(tenant_id, business_id)` | 5a |
| employee_id | uuid | 冗余，范围谓词与审计 | 5a |
| expected_retirement_date | date, null | 创建时快照的人员“预计退休日期”P（派生依据，不随后续重算变化） | 5a |
| retire_type | text, null | `early` / `normal` / `delayed`，创建时由 L 与 P 派生（§3.5），CHECK 枚举；不可手改 | 5a |
| re_employed | boolean, default false | 是否同时返聘（规格 IsReEmployed） | 5a 建列，5b 开放为 true |
| rehire_plan | jsonb, null | 同时返聘的返聘任职 / 合同 / 试用期计划（§8.2）；`re_employed = true` 时非空（CHECK） | 5b |
| rehire_business_id | uuid, null | 生效时生成的 `retire_rehire` 业务（规格 LURetireReEmployedRecord），复合外键 → 业务头 | 5b |
| created_at | timestamptz | | 5a |

不设状态、revision（随业务头）。`rehire_plan` 用 jsonb 而非明细列的理由：它是**尚未落地的命令载荷**（落地后的规范对象是 `retire_rehire` 任职业务与合同），结构与 `POST employees/:id/businesses` 的入职请求体一致、按同一 zod schema 校验，不承载核心对象（AGENTS §7）；见 §15 A-14。

### 2.4 规则表（5c）

照 main 自动转正规则形态（`packages/db/src/schema/employment-probation.ts:125～158` `employment_auto_regularization_rules`：优先级 + 登记顺序号、`org_ids` + `include_subordinates`、单条启停、revision、整份保存、硬删除）：

- **`retirement_rules`**：`id, tenant_id, purpose`（`expected_date` / `flexible_range`，CHECK）`, rule_type`（首版只允许 `fixed_age`，CHECK；`formula` 留给 R3-T00 再放开）`, name, priority (0～9999), sequence_no, org_ids uuid[] (1～50), include_subordinates, retirement_age_years (30～80), retirement_age_months (0～11)`（purpose = expected_date 必填）`, earlier_months, later_months (0～120)`（purpose = flexible_range 必填）`, enabled, revision, created_at, updated_at`。唯一：`(tenant_id, purpose, sequence_no)`。
- **`retirement_rule_conditions`**：`tenant_id, rule_id, seq (1～10), field_code, operator`（`in` / `not_in` / `is_empty`）`, values text[]`；PK `(tenant_id, rule_id, seq)`；`field_code` 白名单见 §9.1。规格“最多 10 条条件字段”由 `seq` 范围与 CHECK 保证。
- **`retirement_rule_daily_runs`**：`(tenant_id, business_date)` PK + `command_id`（照 `employment_auto_regularization_daily_runs`，每租户每业务日一次）。
- 租户配置项（`system_settings` seed，两层配置 `tenant-settings/service.ts`）：`retirement.auto_expected_date`（默认 `false`）、`retirement.auto_flexible_range`（默认 `false`）、`retirement.upcoming_days`（默认 `30`，1～365，RT-R1“默认 30 天内”）。

### 2.5 意向退休申请表（5d）

- **`retirement_intentions`**：`id, tenant_id, employee_id, staff_id`（申请时所在任职周期）`, department_id`（申请时主职部门快照，范围与审批路由用）`, intended_date date, expected_date_snapshot date, earliest_snapshot date, latest_snapshot date, reason text (≤500), initiator ('hr'|'self'), initiator_user_id, state`（`draft / in_review / rejected / approved / disapproved / withdrawn`，CHECK）`, approval_instance_id, revision, command_id, created_at, updated_at`。同员工最多一张未办结（部分唯一索引 `state IN ('draft','in_review','rejected')`）。
- 状态单表 + revision，不做版本链：意向申请不是任职记录，不受硬规则“任职事件溯源”约束；审批意见与历史由审批实例承载。

## 8. 退休同时返聘（5b）

### 8.1 日期口径（DEC-296①）

- 退休记录生效日 E = L + 1；返聘任职 `retire_rehire` 生效日 **R = E + 1**；退休记录只覆盖 E 当天（时间轴 `[E, E+1)`），次日接返聘（新任职周期，`employment_cycles.entry_type = 'retire_rehire'`）。迟到顺延时以 E′ 计，R = E′ + 1。
- 与 AC-RT-01 字面“返聘日 = 最后工作日 + 1”冲突（那会让退休记录长度为 0）：本设计按已确认的 DEC-296① 与原站样本（规格第 228～230 行：失效日期 = 退休日期）取 E + 1，**须 00 拍板**（A-1）。实现上只有 `retireRehireStartDate(E′)` 一个函数决定 R，改口径只改一处。

### 8.2 一体化入口

- 同一 `POST retirements/employees/:id`（直接 / 申请均可）请求体带 `reEmployed: true` 与 `rehire` 区块：`{ fields, customFields, formId?, entry: { probation, probationMonths?, probationEndDate? }, contract? }`，结构与 `POST employees/:id/businesses kind=retire_rehire` 的请求体一致（`entry-options.ts` 的 `entryControls`，不允许 `pendingEntry`——返聘直接在任，不进待入职）；`contract` 用合同模块 `contracts/input.ts fieldsSchema`。不接受 `loginEmail`：沿用原账号。
- 创建时校验（门禁 `create` 之后、写入之前）：字段权限按 `Employment.Create`（返聘写的是新任职）+ 合同对象创建权与范围（照 `entry-contract.ts` 的重验口径）；返聘部门 / 职位在 R 日可用（`validatePreparedEmployment` 同一校验，干跑）；黑名单互斥（§4.4）。校验通过写 `retirement_requests.rehire_plan`。
- 判定复用：“前一条是退休才能返聘”只经 `write-service.ts:410` 顺序校验；Offer 同步的退休返聘仍由 `offer/sync.ts:101` 判定，不改；`rehire-match.ts` 不改（同时返聘不需要按证件匹配）。

### 8.3 生效时生成返聘（`runSteps` R-2，保存点内）

1. 版本链已写入退休记录 E′；合同已终止于 L′。
2. `createEmploymentBusiness(tx, trustedCtx, employeeId, { kind: 'retire_rehire', mode: 'direct', effectiveDate: R, fields, customFields }, { entry: { ...plan.entry, pendingEntry: false } })`：经 `assertBusinessSequence`（前一条 = 刚落地的退休，满足 `:410`）、`prepareInheritance`（新周期）、黑名单拦截（`write-service.ts:153`）；直接业务当场写入时间轴（R 在未来时为已落地的未来记录）。入职类型 = 退休返聘（`employment_cycles.entry_type`，AC-RT-01）。
3. `plan.contract` 存在时调 `generateContractForBusiness`（`contracts/ports.ts`，与 `entry-contract.ts` 同一端口）生成返聘合同，起始日 R。
4. 写 `retirement_requests.rehire_business_id`、`exit_effects(kind='rehire_created', target = 返聘业务)`，审计 `employment.retirement.rehired`。
5. 任一步失败（部门 R 日已停用、黑名单、合同冲突等）→ 整个退休生效失败（保存点回滚，记 failed，HR 待办、可重试），**不出现“已退休、未返聘”的半套**。

`trustedCtx` 只在编排器内部构造，不对外暴露；返聘业务不经离职门禁（它不是终止业务）。新增 `exit_effects.kind` 枚举值 `rehire_created`（5b 迁移改 CHECK）。

## 9. 预计退休日期规则与弹性范围（5c）

### 9.1 规则与匹配（纯函数 `packages/domain/src/employment/retirement-rules.ts`）

- 规则设置：`GET / POST / PUT / DELETE retirement-rules`、`POST retirement-rules/:id/copy`、`PUT retirement-rules/:id/enabled`（照自动转正规则路由 `auto-regularization-routes.ts:83～153`）；`?purpose=expected_date | flexible_range` 分两页。配置对象 `tenant.employment.configuration.write`（管理员 `other_settings`），读对持 EMPLOYMENT `object.view` 者开放；审计 `retirement_rule.save / delete / enabled`。
- **条件字段白名单**（≤10 条，AND）：性别 `gender`、个人身份 `identityType`、用工形式 `employType`、人员类别 `employeeCategory`（若人事 / 任职已有该字段则用，否则首版不提供，A-9）。值取员工计算时点的人事最新版本与当前主职任职快照。
- `matchRule(rules, person)`：只看 `enabled`、`purpose` 相同的规则；先按组织范围（`org_ids` 含下级时展开，`org/hierarchy-reader.ts listOrgDescendantsInTransaction`，取员工当前主职部门）过滤，再按 `priority` 升序、`sequence_no` 升序逐条判条件，**命中第一条即停**（RT-R5，AC-RT-03）。
- `expectedDateOf(birthday, years, months)`：出生日期 + 年龄（年 + 月），月末溢出按当月最后一天（2-29 → 平年 2-28）；出生日期为空 → 空。无规则命中 → **空**（与 RT-R7“女员工未维护个人身份被算为空”同一机理）。口径见 A-4。
- `flexibleRangeOf(expected, earlier, later)`：`expected` 为空 → 上下限都空（RT-R6）；否则 `[expected − earlier 月, expected + later 月]`。

### 9.2 每日计算与幂等

- 调度：挂在定时生效的进程内定时器（照 `auto-regularization-scheduler.ts`），每租户本地 03:00 之后第一次调度跑当天批次；`retirement_rule_daily_runs(tenant_id, business_date)` 只占一次；开关关闭的日子不占用。另有 `POST retirement-rules/run`（立即执行，`tenant.employment.configuration.write`，不占当天登记，续跑句柄照 `employment_auto_regularization_run_cursors`）。
- 候选：计算日 t 当天在职（时间轴当天记录不是 leave / retirement、人员状态不是待入职）的员工；离职 / 退休人员不重算（保留最后值）。
- 写入：逐员工切租户路径（`withTenant` + RLS），员工锁 `SKIP LOCKED`；`expected_retirement_confirmed = true` 的不写预计日期（AC-RT-02），`flexible_range_confirmed = true` 的不写上下限；**算出值与当前值相同则不写**（不产生人事版本、不审计）——这就是幂等键：同一员工同一天重复执行得到同一结果、零写入。不同才 `appendEmployee(..., false)`，审计 actor = 系统用户、`reason: 'retirement_rule'`、带规则 ID。
- 失败：单员工业务错误记入运行回执（员工 ID、原因），不影响其他人；存储错误整员工回滚、下次重试（DEC-052 同口径）。
- 时区：业务日按租户时区（DEC-056）。

## 10. 五视图口径（5d；BE-12 依赖）

### 10.1 可复用定义

导出 `retirementViewSql(view, { tenantId, asOf, upcomingDays })`（`employment/retirement-views.ts`）与等价纯函数 `classifyRetirement(person, businesses, asOf, upcomingDays)`（`packages/domain/src/employment/retirement-views.ts`）。**时点参数 `asOf`**（租户日）贯穿全部谓词：状态取 `employment_state_events.created_at` 落在 `asOf` 当日结束（租户时区）之前的最新一条；人事字段取 `personnel_employee_versions.created_at` 同界之前的最新一版；在职取 `asOf` 当天的时间轴记录。BE-12 时点花名册直接传历史日期；列表接口默认 `asOf = 今天`。

记号：P = 时点人事版本的预计退休日期；“退休单”= kind = retirement 的业务；“未完结退休单”= 时点最新状态 ∈ {draft, in_review, rejected, approved}。

| 视图 | 谓词（全部在分页前叠加 `employmentVisibilitySql`，DEC-177） | 默认排序 |
|---|---|---|
| 即将退休（B16） | 时点在职 ∧ P 非空 ∧ `asOf ≤ P ≤ asOf + upcomingDays` ∧ 无未完结退休单 ∧ 时点无已生效退休 | P 升序 |
| 过期未退休（B17） | 时点在职 ∧ P 非空 ∧ `P < asOf` ∧ 无未完结退休单 | P 升序 |
| 退休中（B18） | 存在未完结退休单（含 approved 未到期、生效失败 / 挂起仍为 approved 的单，行上带最近一次生效尝试） | 最后工作日升序 |
| 已完成（B19） | 退休单时点最新状态 = effective（未被撤销） | 最后工作日降序 |
| 全部（B20） | 全部退休单（含 disapproved / voided / deleted） | 创建时间降序 |

## 11. 意向退休日期申请（5d）

- **申请对象**：`retirement_intentions`（§2.5）。服务 `retirement-intention.ts` 按 `initiation = hr | self` 设计（同 R2-T03 §4B），5d 只开 HR 入口，自助入口随 F-020。
