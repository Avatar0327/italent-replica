**必需项显式表（第 4 轮，DEC-348②；`tests/acceptance/support/route-policy/required/`）**：撤掉第 3 轮按调用点区分准入 / 披露的启发式，改为逐端点人工审定的显式表（381 条，按模块分文件，只放字面量，不得从声明或探测结果生成）。每条义务 = 权限键（`obj:` / `btn:` / `rel:` / `guard:` / `admin:` / `own:` / `self` / `exception:`；范围、字段、逐行路径是元数据）+ 用途（缺省准入；`disclosure:<optional 名>`；`guard:<承载守卫 / 关系>` 守卫内部；`when:<具名条件守卫>` 条件准入）+ “或”组（`组:备选`，同一备选内全部义务 AND，备选之间 OR）+ 承接的探测事实 + 证据。校验器 `required.ts` 硬比对：R1 每个准入备选满足全部准入义务与每个“或”组；R2 准入义务出现在任何 optional 即报错；R3 披露义务必须由同名 optional 授予；R4 纯披露（本端点只有披露用途）不得进准入，同一权限另有准入 / 守卫内部 / 条件用途的复用不算冲突（按 权限 + 用途 + 承载者 区分义务，重复才是 TABLE_CONFLICT）；R5 / R6 承载者须是准入义务，条件权限不得写成无条件准入；R7 optional 分支或准入权限不在表里即报；R8 探测器的权限类原始事实没有义务承接 → REQUIRED_TABLE_GAP（探测器只给漏登线索，不决定用途），义务登记的事实探测器观测不到 → REQUIRED_STALE_FACT。**证据**（`evidence.ts`）：每条义务至少一个强制调用点（call），另按需登记授权实现（impl）与决定实参的常量（const）；单元 = `文件#函数 / 常量 / a>b / route:METHOD 路径`（路径按注册处求值，含模板常量与 for…of 字面量数组），锚点按 TS 词法记号比较（字符串 / 模板字面量内按空白折叠）；每个单元登记规范化摘要（`required/digests.ts`，按文件分组），单元一改即 EVIDENCE_STALE，复核引用它的义务后用 `ROUTE_POLICY_UPDATE_DIGESTS=1` 只重写摘要；证据不得指向登记表文件（`policy.ts` / `app-policy.ts`）。锚点存在不是语义证明：权限键与源码实参是否一致由人工审定（审定台账见 PR 评论）。审定中发现并补登的声明漏项（HTTP 授权本身正确）逐条列在 PR 描述；IDP 展示器按对象查看权省略嵌套内容（projectionOf）现状由投影器 `idp.*` 统一登记，未拆成逐对象披露分支，转 PR-B。

**在途 PR 如何补声明（PR-B1 起追加，设计 `F-039_PR-B_设计.md` §6）**：新路由除 PR-A 的声明、表与基准外，还要满足披露语义与范围绑定的新规则——① 可选分支（`optional`）只挂声明根节点、不嵌套、名字用驼峰字母数字（`^[A-Za-z][A-Za-z0-9]*$`，如 `nestedSubProcess`），对应表里的 `disclosure:<分支名>` 义务；披露权限要在该分支的**每个**析取备选里出现，且披露义务必须写 `need`（`DISCLOSURE_NEED_UNBOUND`）；准入权限与披露同权复用时，表里要有同权的 `disclosure:<分支名>`（否则 `REQUIRED_IN_OPTIONAL`）；② 某个准入备选含 ≥2 个承载节点（`object` / `admin`）时，由这些节点提供的每条 `obj:` / `admin:` 准入义务写 `need`（范围模式 + 定位器 / 谓词 / 守卫名，随主对象写 `none`，`NEED_UNBOUND`），`need.scope` 不是 `none` 的义务另登记 `role: 'scope'` 的强制范围判定处证据（构造器与已审定的证据见 `required/scopes.ts`，`NEED_EVIDENCE_MISSING`）；③ `purpose: 'guard:<承载者>'` 的守卫内部义务写 `inner`：`required` / `or`（内部“或”备选，要在 `required/guard-inner.ts` 的 `GUARD_INNER_ALTS` 登记备选与证据）/ `when`（条件名），缺了报 `GUARD_ROLE_UNBOUND`。

已知限制（写入 §10.6 第 6 轮小节）：删嵌套字段路径、拒绝码改宽、`ledger` perItem→single、N/A 依据这四类突变需要多维身份探测或 recorded 事实，静态基准测不到，PR-B 补。对象 × 操作事实只取常量实参的调用点（通用枢纽内部按变量判定的不记），选择器按路由绑定域、不区分同一路由里的选择器角色，也不核对“输入分支 → 对象 / 操作”的对应（实现审第 2 轮验证：人才表单六个键的对象映射全改成指标库，比较器仍零发现）；这几点由 PR-B 的多维身份探测补全。

## 0. 一页摘要

- **PR-A 范围（DEC-300，最后一版设计）**：只做三件事。① **声明登记**：227 条路由的类型与逐路由登记，按**现状契约**写（动态选择器、AND / OR、参与关系、`optional`、响应码、字段形状、`preconditions`、`ledger`）——批次 A 的 126 条写完整声明；批次 B 的 101 条进代码内冻结表 `PENDING_B`（只登记 method / path / module，FW-01 断言与冻结哈希逐条相等：不能增、改动必过评审），PR-B 再写成完整声明并清零。② **缺失声明即失败**：`verifyRouteDeclarations` 在 `createApp` 末尾枚举 `app.routes`，未声明且不在 `PENDING_B` → 抛错，**任何阶段都失败、没有告警路径**（含 HEAD、中间件、别名、晚注册反例）。③ **独立于声明的现状必测基准反向测试**：基准由探测现状行为生成并冻结在仓库里接受评审，FW 测试先拿候选声明与基准比较（声明比基准弱就失败），再按基准 ∪ 声明推导必测场景对现有 HTTP 行为断言，突变套件证明每一种声明弱化都会变红。可信基线、有限例外、retired / `OPEN_BATCHES`、初始化批准、CI 门禁协议**全部移到 PR-B**（§10.6，含第 5 轮 P2-② / P2-③ 与修复思路）；统一执行、QuerySpec、足迹守卫、统一出口投影仍在后续接管 PR（§10.1～10.5）。**PR-A 不改任何处理函数与响应。**
- **声明（§2）**：每条路由改用 `declare(router, method, path, policy, handler)` 注册。policy 十类：`public / platform / member / admin / self / own / relation / exception / button / object`，可用 `any`（OR）/ `all`（AND）组合；所有 policy 共用 `invalidId`、`guards`、`write`、`optional` 等基础字段。`object` 的对象、操作、按钮都可以是**选择器**，每个动态选择器与逐行关系都登记**有限分支清单**。范围外与标识非法都声明 **status + error.code**（DEC-291 Q1）。附录 A 对运行时枚举出的 **227 个端点**逐条给出确定映射，并与类型闭合。
- **PR-A 的执行点（§3）**：`declare` 包装只做两件事——注册身份核对（§2.3）和运行时自检（有效方法 HEAD → GET、`routePath` 与声明一致，否则 500 `ROUTE_POLICY_MISMATCH`），然后原样调用现有处理函数；不解析请求体、不鉴权、不改响应。`write.fields / footprint / result / preconditions / ledger` 与 `fields` 形状都是**登记项**，由 FW 测试按 HTTP 行为核对其真实性。
- **缺失即失败（§2.3）**：按注册实例绑定最终 method / path；中间件按 **Hono 规范化并挂载后的最终路径**登记；别名、`.all`、未登记中间件、多层 `onError`、晚注册都能检出；用 Hono "匹配器已构建"不变量封闭注册。**新增未声明路由在任何阶段都失败**（DEC-300）：PR-A 合并后，#106、#107、R3-T07、R3-T04、R3-T05 在各自下一轮补声明。
- **现状必测基准与反向测试（§4）**：基准 = `observed-contract.json`——探测器对每条路由用模板用户与对象目录维度逐项撤权、改范围、换参与关系、过期 revision、重放、跨租户后观察状态码、错误码与响应字段差异，得到"现状对哪些权限敏感"（`probed`），加上人工冻结、带证据用例的事实（`recorded`：审批前提、盲审 Outcome、台账计数、固定键、分支域 = 域常量）。FW-01 核对基准新鲜度（CI 重新探测必须逐字节相等）、声明不弱于基准、突变套件（把按钮 / 范围 / 字段 / 嵌套路径 / 前提 / 关系 / 守卫 / 组合分支任一项删掉或改成 `none`，比较必须变红）；FW-02～08 的必测场景由基准 ∪ 声明推导，`none / all`、N/A、删分支、删路径都要可执行证据；最小权限用户 M 证明声明足够。基准更新只能通过重新探测并把 diff 放进 PR 评审，顺手调低会因重新探测仍观察到敏感而变红。
- **告警边界（§8，DEC-300）**：身份不匹配、缺失声明、初始化不可信**始终失败**；允许告警的状态（PR-B 门禁期的未批准例外、退出到期、冻结表缩减待批等）必须跨提交持续报告，不进入可信基准，也不满足强制切换的激活条件；verify / FW-01 / 比较脚本的统一检查表见 §8。
- **交付（§9）**：PR-A → PR-B（101 条声明 + `PENDING_B` 清零 + 可信基线 / 例外 / retired / 初始化批准 / 门禁协议）→ 接管 PR 系列 T1～T4（§10.1～10.5）。

## 2. 设计一：路由权限声明 v5（PR-A：按现状契约登记）

### 2.1 类型（`apps/api/src/route-policy/types.ts`）

**PR-A 语义（DEC-297④）**：声明是对**现状契约**的登记——每个字段描述现有处理函数已经做的判定、响应与形状；PR-A 不据此拦截或改写请求（`declare` 包装只做注册身份核对与自检，§3.1）。类型注释里"框架评估 / 框架调用 / 框架组装"的描述是接管阶段（§10）的目标语义；在 PR-A，这些字段由 FW 测试按 HTTP 行为核对其真实性。`fields` 形状登记供 FW-04 定位字段，不等于已接管运行时投影。

```ts
/** 选择器：静态值，或由请求某处决定。取值只用步骤 0 的最小安全解析结果；取不到或不在映射表 / 分支清单 → 400 VALIDATION_FAILED，不进入鉴权。 */
type Selector<T> =
  | T
  | { from: 'param' | 'body' | 'query'; path: string; map: Readonly<Record<string, T>> } // 分支清单 = map 的键
  | { from: 'mapper'; mapper: MapperName; domain: readonly string[] } // 纯函数映射 + 有限输出域（P2-8）；域外输出 → 400
  | { from: 'record'; locator: LocatorName; attribute: string; domain: readonly string[] }; // 由已加载记录决定（审批快照 fieldObjectCode），域外 → 500 fail-closed

type ObjectSelector = Selector<ObjectCode>;
/** 'button' = 只校验按钮（按钮判定本身要求对象在身份清单内），不附加数据操作开关——审批管理员动作、流程仿真等现状。 */
type OperationSelector = Selector<'view' | 'create' | 'update' | 'delete' | 'button'>;
type ButtonPolicy = Selector<{ code: string; level: ButtonLevel }> | { none: true; reason: string };

/** 拒绝码：范围外 / 关系不成立 / 标识非法都声明 status 与 error.code（DEC-291 Q1），含 details.reason。 */
type Denial = { status: 400 | 403 | 404 | 409; code: ErrorCode; reason?: string };

/** 所有 policy 共用的基础字段（P2-1：invalidId / guards / write 推广到全部类型）。 */
interface PolicyBase {
  invalidId?: Denial; // 路径 / 查询标识非法时的现状码（org 400、permission idParam 404、job/context.uuidParam 400 …）
  guards?: readonly GuardName[]; // 附加具名守卫（grants 的 other_settings 附加能力、person-links 固定拒绝、经理身份 …）
  write?: WritePolicy; // 写路由必填（platform / admin / self / relation / object 都可能写）
  optional?: Readonly<Record<string, RoutePolicy>>; // 可选分支（P2-1）：不参与准入；框架评估后把 { granted, scope?, branch? } 放进 access.optional[name]，由处理函数 / 足迹 / 投影按分支取用，未通过不拒绝（交接的实例改派与披露）
}

export type RoutePolicy =
  | (PolicyBase & { kind: 'public'; reason: string; dec: string }) // 不要求成员身份；令牌 / 业务资格由 guards 强制（DEC-291 Q2）
  | (PolicyBase & { kind: 'platform'; fields: FieldsPolicy }) // 平台运营身份；write 为平台命令（Idempotency-Key + If-Match，platform.ledger）
  | (PolicyBase & { kind: 'member'; reason: string; fields: FieldsPolicy }) // 任一有效租户成员
  | (PolicyBase & { kind: 'admin'; capability: AdminCapability; alias?: string; scope?: ScopePolicy; fields: FieldsPolicy }) // alias = 现有 tenant.* 动作名；scope 供审计等能力级列表
  | (PolicyBase & { kind: 'self'; target?: Target; button?: ButtonPolicy; fields: FieldsPolicy }) // 绑定员工本人 + 叠加授权器 selfService
  | (PolicyBase & { kind: 'own'; predicate: PredicateName; target?: Target; locator?: LocatorName; denied?: Denial; fields: FieldsPolicy }) // 本人数据：列表用谓词；单条用 target + locator（序列同步任务）
  | (PolicyBase & { kind: 'relation'; relation: RelationName | Selector<RelationName>; target: Target; denied: Denial; rows?: RowsPolicy; fields: FieldsPolicy })
  | (PolicyBase & { kind: 'exception'; guard: GuardName; dec: string; fields: FieldsPolicy }) // 具名例外（DEC-135）
  | (PolicyBase & { kind: 'button'; object: ObjectSelector; button: Selector<{ code: string; level: ButtonLevel }>; denied: Denial }) // 独立按钮策略，供 any / all 组合（调动部门选择：任一发起按钮）
  | ObjectPolicy
  | (PolicyBase & { kind: 'any'; of: readonly RoutePolicy[] }) // OR：任一通过即通过；出口字段取通过分支的 fields；全失败按第一个分支的拒绝码
  | (PolicyBase & { kind: 'all'; of: readonly RoutePolicy[]; fields: FieldsPolicy }); // AND：全部通过；出口字段由组合层声明

interface ObjectPolicy extends PolicyBase {
  kind: 'object';
  object: ObjectSelector;
  operation: OperationSelector;
  button: ButtonPolicy;
  scope: ScopePolicy | { byObject: Readonly<Record<ObjectCode | '*', ScopePolicy>> };
  fields: FieldsPolicy;
  rows?: RowsPolicy;
  failureAudit?: FailureAuditPolicy; // 导入入口必填（§3.5）
}

export type ScopePolicy =
  | { mode: 'list'; predicate: PredicateName; view?: string } // 列表：谓词由框架注入 listQuery（§3.3）
  | { mode: 'point'; target: Target; locator: LocatorName; denied: Denial; view?: string }
  | { mode: 'see-all'; view?: string; creatorLocator?: LocatorName; denied: Denial | { status: 200; empty: true } } // 无归属对象（DEC-121）：看全部或创建人；view = 数据集（编制方案）；合同主数据列表无看全部时现状为 200 空列表
  | { mode: 'guard'; guard: GuardName; denied: Denial }
  | { mode: 'none'; reason: string };

export type Target =
  | { param: string } | { body: string } | { query: string }
  | { record: LocatorName; attribute: string }
  | { derived: GuardName };

export interface WritePolicy {
  fields: FieldsFrom;
  controls?: readonly string[];
  commandOnly?: boolean;
  footprint: GuardName | { none: true; reason: string }; // 提交前足迹守卫（§3.2 ②）；不再有裸 generic
  result: GuardName | { generic: { targets: string; locator: LocatorName } } | { none: true; reason: string }; // 返回后守卫（§3.2 ③）
  preconditions?: readonly PreconditionName[]; // ①b 动作前业务前提的名称登记（命令内执行，框架不调用；FW-06 核对工厂覆盖，§3.2）
  ledger?: 'single' | 'perItem'; // 命令台账策略（P2-7）：single = 整个请求一条命令（默认，含 job / org 导入、合同 batch）；perItem = 逐项 runCommand（合同待办批量 key:index）
}
type FieldsFrom =
  | 'body' | 'body.fields+customFields' | 'contracts.fields+customFields' /* 只取本次输入 body.fields，不含继承字段 */ | 'body+subdivisions'
  | { rows: string } | { guard: GuardName } | { none: true; reason: string };

export interface RowsPolicy {
  path: string; // 'rows[*]' | 'items[*]' | 'items[*].command'
  operation?: OperationSelector; // 逐行操作（含分支清单）
  button?: ButtonPolicy;
  relation?: Selector<RelationName>; // 逐行关系（合同待办批量：action → 当前审批人 / 发起人）
  fields: FieldsFrom;
  target?: Target;
  batch: 'atomic' | 'receipt';
}

export type FieldsPolicy =
  | { mode: 'shape'; shape: ShapeName }
  | { mode: 'projector'; projector: ProjectorName; shape: ShapeName; format?: 'text/csv' }
  | { mode: 'fixed'; keys: readonly string[]; dec: string; intersect?: ObjectCode } // 固定键；intersect = 再 ∩ 该对象字段权（经理员工列表）
  | { mode: 'all'; dec: string } // 整对象不裁剪（DEC-102 流程管理员分支）
  | { mode: 'none'; reason: string };

export interface FailureAuditPolicy {
  kind: 'import';
  rows: 'rows' | 'items';
  objectType: Selector<string>;
  anchors: MapperName;
  resolveAnchors?: GuardName;
  scopeEmployee?: Target;
}
```

### 2.3 缺失即失败 v3（P2-2 残留：中间件按最终路径登记；P2-10：HEAD）

**注册与绑定**

- `declare(router, method, path, policy, handler)`：为每次调用生成独立包装 `w`，登记 `Declaration = { method, localPath, policy, router, seen: false }`；同一 `(router 实例, method, localPath)` 重复声明抛错；多方法用 `declareEach`。
- `mount(router, prefix, module)`：调用 `router.route(prefix, module)` 前后对比 `router.routes`，把新增条目的**最终路径**（Hono `mergePath` 规范化后）回填到 `module` 上每条声明与中间件登记的 `expectedFullPath`；嵌套挂载逐层回填。不自行拼接字符串，只读 Hono 的结果。
- `useMiddleware(router, path, mw)`：调用 `router.use(path, mw)` 后读取 `router.routes.at(-1).path` 作为该中间件的登记路径（Hono 已规范化：`'*'` → `/*`），再登记进 `middlewareSet`；经 `mount` 时按上条回填最终路径。实测正例：顶层 `use('*')` → `ALL /*`；子路由器 `use('*')` 挂在 `/api` → `ALL /api/*`；两层嵌套 `inner.use('*')` 挂在 `/api` 下的 `/sub` → `ALL /api/sub/*`；`use('/api/tenant/*')` 不变。现有 7 条中间件改为经 `useMiddleware` 登记，三条源码里的 `'*'` 以 `/*` 入表。

**验证算法（`verifyRouteDeclarations(app, { pending: PENDING_B })`，`createApp` 末尾调用；PR-A 没有基线 / 例外输入，DEC-300）**

1. 遍历 `app.routes`；`fn = r.handler`，循环 `fn = fn['__COMPOSED_HANDLER']` 直到不存在。
2. `fn ∈ middlewareSet` → 要求 `r.method === 'ALL'` 且 `r.path === 登记的最终路径`；`fn ∈ declaredByHandler` → 要求 `r.method === d.method && r.path === d.expectedFullPath && !d.seen`，否则 `ROUTE_ALIAS`；其余 → 未声明：在 `PENDING_B`（§3.7，批次 B 的 101 条代码内冻结表）内 → 登记为 pending（不告警，也不放行其它任何路由），否则抛 `ROUTE_UNDECLARED`——**任何阶段都失败、没有告警路径**（DEC-300）（`.all()` 路由方法为 `ALL` 且不在 `middlewareSet` → 未声明）。
3. 收尾：每条声明都必须 `seen`；`PENDING_B` 每条都在运行时出现且未声明（已声明或路由已消失 → `PENDING_STALE`，抛错）。
4. **封闭**：`app.router.match('GET', '/__route_policy_seal__')` 预构建匹配器（此后 Hono 自身拒绝 `add`，实测），再 `Object.freeze(app.routes)`。
5. 返回运行时清单。

**包装的运行时自检（P2-10；PR-A 唯一的运行时动作）**：按**有效匹配方法**核对：`effective = c.req.method === 'HEAD' ? 'GET' : c.req.method`，要求 `effective === d.method && c.req.routePath === d.expectedFullPath`，否则 500 `ROUTE_POLICY_MISMATCH`（C8）。HEAD 请求走 GET 的同一处理函数（现状），响应体由 Hono 在 dispatch 层去除（实测 HEAD 命中 GET 路由返回 200、空体），涉及 107 条 GET 的隐式 HEAD；`/healthz` 的 HEAD 同样 200。FW-01 核对 HEAD 与 GET 的状态码一致（有权 200 / 无权 403，均空体）。

- 平台路由：`kind: 'platform'`，`fields: none`，写路由 `write.footprint: 'platform.ledger'`。

### 4.2 现状必测基准（独立于候选声明；第 5 轮 P2-①）

**定义**：`observed-contract.json` 每条路由一个条目，记录**现状**对哪些权限维度敏感、以什么状态码 / 错误码拒绝、响应里哪些路径的哪些字段随查看权消失、哪些前提 / 关系被触发时如何响应。它**不读声明**，由两类事实构成：

| 来源 | 内容 | 怎么得到 |
|---|---|---|
| `probed`（探测生成） | 按钮 / 数据操作 / 字段 / 范围 / 关系 / 本人绑定 / 过期 revision / 重放 / 跨租户 各维度的敏感性与观测码、观测形状（路径 × 消失的键） | 探测器 `probe.ts` 对每条路由：先用 H 的合法请求（`example` 或样本 GET）取基线响应；然后**每次只变更一个维度**再请求——撤 H 对该模块各对象的每个按钮、关每个数据操作开关、撤每个目录字段的查看权、把请求人换成 O / O_all / A（空范围）/ A− / N / P / S / S+ / S+∅ / S′、把参与关系换成非参与人 / 非当前审批人 / 非发起人、带过期 If-Match、同键同体重放、跨租户样本 id；记录 status + error.code（+ details.reason）与响应深扫差异。敏感 = 与基线响应不同。维度来自**对象目录与模板**，不来自声明 |
| `recorded`（人工冻结，带证据） | 探测不到或代价过高的事实：八个审批动作的命令内前提与盲审 Outcome、合同继承正例、台账计数（single / perItem、已提交 403）、失败导入日志、固定键集合、分支域（= 域常量 `JOB_KINDS` / `SUBSETS` / 合同 operation × mode / 导入 mode / 调动 initiator / 审批业务类型 / 经理 tab） | 写进同一文件，每条带 `evidence: 'AC-PRM-FW-0x/<it 名>'`；FW-01 要求证据用例存在且实际执行；分支域 recorded 值与域常量用测试断言相等（常量变了基准必须跟着变） |
| `inapplicable` | 某场景对该路由不适用的原因（无请求体、无路径参数、无按钮可撤 …） | 探测器给出；N/A 必须引用它 |

**生成与更新（可审查，防止顺手调低）**：
- `pnpm route-policy:probe` 重新探测，按 (method, path, 维度, 目标) 排序写回规范化 JSON（无时间戳、无随机 id：样本 id 用稳定别名）。
- FW-01 `baseline-fresh`：CI（PGlite job）重新探测并断言与冻结文件**逐字节相等**。基准只能通过"重新探测 + diff 进 PR 评审"变化：删一条敏感事实 → 重新探测仍观察到 → 红；现状行为变化（修了缺陷 / 改了规则）→ 红，直到重新生成并评审。recorded 事实的修改必须同时改证据用例，否则 `evidence` 检查红。
- 探测成本：模板用户共享一套夹具与 app；撤权经真实撤权入口或测试专用的缓存失效钩子（撤权后清缓存，AGENTS §10）；上限约 227 × 60 次请求，只在一条 job 执行一次；真 PG job 只做比较。
- **基准与矩阵**：§4.8 的"查看人 × 接口 × 字段"矩阵是 recorded 部分的人类可读视图，探测结果必须与之一致。

**现状缺陷的处理**：基准记录现状；声明按应有契约写并登记 `knownGap: { scenario, issue: '#n' }`；FW 对该场景断言"缺陷仍在"（修复后不删 `knownGap` → 红），统计单列、PR 描述列出。`knownGap` 不进入基准，也不改变"声明按现状契约"的口径（它是显式、可审查、带 issue 的差异登记）。

- **请求前断言有效范围与权限（P2-7 ②）**：每个派生用户建好后，用**真实范围解析器** `resolveModuleScope(deps, ctx(user), undefined, objectCode, pageCode, viewCode)`（按 object × view / 数据源 × asOf）断言 `all`、`orgIds` 集合、`hasDataPermission` 与模板设定一致——`GET /permission/scopes/:userId/:app` 只返回配置根（`getUserAppScope`），`me/objects` 不含数据范围，都不能作范围证据；字段与按钮用 `myObjectPermission`（`me/objects` 同一函数）断言 `viewableFields / editableFields / buttons`；无对象权限的用户（N、A−）预期它抛 **403 FORBIDDEN**，不是"空权限"。断言失败即夹具失败，不进入场景。
- **F 的写探针分两类**：(a) **请求字段探针**——探针字段为非必填字段 X，F 的 `example` 不带 X，写成功，响应与后续读取里 X 缺席（含服务端自动填充）；(b) **继承 / 派生输出字段探针**——探针字段为服务端写入的派生 / 继承字段 Y（组织 `fullName / level`、任职 `employeeStatus / entryStatus`、合同编号等），F 的 `example` 合法、写成功，响应里 Y 缺席、H 同一请求 Y 等于预期值。必填字段只在读路由上做探针（不可查看即不可编辑，`effective.ts`）。
- 样本：每个对象 `inOrg1 / inOrg2`；无归属对象按创建人（H 建 / A 建）。
- 模板用户与样本同时服务两件事：**探测器生成基准**（§4.2）与 **FW-02～08 的场景执行**；两边用同一套夹具，保证基准与测试观察到的是同一现状。

- **声明 vs 基准比较（FW-01 `declaration-not-weaker`，内存比较，不发请求）**：候选声明的每个维度必须覆盖基准观测到的敏感事实，否则按维度报错；反向（声明含基准没有的敏感项）不直接报错，而是让该项的反例必执行——现状不拒绝 → 红（过度声明，或现状缺陷 → `knownGap`）。

| 维度 | 基准事实（§4.2） | 声明必须 | 否则 |
|---|---|---|---|
| 按钮 | probed：撤按钮 X → 403 | `button` 为 X（选择器域覆盖所有观测到的 X） | `WEAKER:button` |
| 数据操作 | probed：关 operation 开关 → 403 | `operation` 对应 | `WEAKER:operation` |
| 范围 | probed：O / A（空范围）/ O_all 结果 ≠ H | `scope` 非 `none`，`denied` = 观测 status + code | `WEAKER:scope` / `MISMATCH:denial` |
| 字段 | probed：撤字段 f 查看 → 路径 p 上键 / 元素消失 | `fields` 形状含路径 p 且绑定对象含 f；`fixed` 键集合 ⊆ 观测键 | `WEAKER:fields@p` |
| 关系 | probed：非参与人 / 非当前审批人 / 非发起人 → 观测码 | `relation` 存在且 `denied` = 观测 | `WEAKER:relation` |
| 前提 | recorded：过期 revision 409、盲审 403 Outcome、`assertNotSelf` … | `preconditions` 含对应名称 | `WEAKER:precondition` |
| 守卫 | probed / recorded：缺某附加能力 → 403 | `guards` 含 | `WEAKER:guard` |
| 组合 | probed：only-branch-k 正例 / missing-branch-k 反例 | `any` / `all` 分支齐全 | `WEAKER:branch` |
| 分支域 | recorded：域常量（`JOB_KINDS`、`SUBSETS`、合同 operation × mode …） | `map` 键 / `domain` ⊇ 基准域 | `WEAKER:domain` |
| 台账 / Outcome | recorded：single / perItem、已提交 403 | `ledger` 对应 | `MISMATCH:ledger` |
| 本人 / 自助 | probed：未绑定 / 改绑 → 观测码 | `self` 且 `denied` = 观测 | `WEAKER:self` |

- **`none / all / N/A / 删分支 / 删路径` 的可执行依据**：`button: { none }` 要求基准对该路由全部按钮探测均不敏感；`scope: { mode: 'none' }` 要求全部范围变更均不敏感；`fields: { none }` 要求任何字段撤权都不改响应且响应不含目录字段；`fields: { all }` 要求 recorded 事实（DEC-102）且探测确认整对象可见；`notApplicable` 须引用 DEC / docs 且基准该场景标 `inapplicable`（探测器给出原因，如无请求体、无路径参数）；删分支 / 删路径须基准域 / 观测形状不含它。没有依据 → `EVIDENCE_MISSING`。
- **必测场景推导**：`requiredScenarios(baseline[route]) ∪ requiredScenarios(declaration)`——下表的"声明特征"首先来自**基准事实**（基准说有按钮敏感就要 `no-button`，不管声明怎么写），再并上声明自己的特征；删声明内容不会减少场景（v2 原表恢复并按 v3～v6 修正）：

| 声明特征 | 必测场景 |
|---|---|

| 声明突变 | 期望 |
|---|---|

| `denied` 码改宽（404 → 200、403 → 200）或改错 | `MISMATCH:denial` |
| `ledger: 'perItem'` → `'single'` | `MISMATCH:ledger` |
| 场景改 N/A 而无基准 `inapplicable` | `EVIDENCE_MISSING` |
| 删整条声明 | verify `ROUTE_UNDECLARED` |
| 把路由加进 `PENDING_B` | 冻结哈希不等 |

### 4.6 断言方式 v5（P2-7 ④⑤⑥：Outcome 分开、台账按实际新增并提交的命令数、平台失败通道）


- **校验和四组**：
  - 业务：全部带 `tenant_id` 的 RLS 表，**含 `permission_*`**（作为"权限管理业务"子组单独报告）；
  - 平台：`users / tenants / tenant_memberships / platform_command_ledger / platform_audit_events`（`platform_command_failures` 单列为"失败通道"，见下）；
  - 台账：`command_ledger` 的**内容哈希**（`command_id + request_hash + response_status + md5(response_body)`），不只比行数；
  - 审计与出站：`audit_events / audit_operation_logs / audit_command_failures / audit_object_creators` 与全部 `*_outbox*` 表。
- **回滚拒绝**（抛错 → 整体回滚、不入台账）：四组全部不变，只允许失败通道追加：租户 `audit_command_failures` ≤ 1、导入失败日志 ≤ 1；平台负例（幂等冲突、`PLATFORM_OPERATOR_REQUIRED` 之后的命令失败等）允许 `platform_command_failures` ≤ 1（`platform-command.ts` 记录后原错误照抛）。撤权在比对窗口之外。GET：四组全不变。
- **已提交的非 2xx Outcome**（盲审 403、合同待办回执里的 403 等：`execute` 正常返回 `{ status: 403 }` → `runCommand` 入台账并提交）：单独断言，不套"全不变"——台账 +1 且内容哈希含 `response_status = 403`；业务组按动作预期变化（原任务 `transferred`、异常管理员新任务、`approval.task.blind_review` 审计、通知与出站）；审计组追加对应事件。FW-06 逐动作给出预期增量（§3.2 表的"盲审"列）。
- 台账计数按声明 `write.ledger`、按**本次实际新增并提交的命令数**计（`runCommand` 在 `execute` 正常返回后才插入台账，`commands.ts`）：`single`（job / org 导入 `runWrite` / `write` 一条外层命令、合同 batch、任职导入）→ +1，与成功行数无关；`perItem`（合同待办批量，命令 ID `key:index`）→ + 实际新增并提交的项数：**计入**已提交的非 2xx Outcome（盲审 403），**不计**预检失败行（非合同待办 404、非当前审批人 403、重提权限）、进入命令后抛错回滚的行（过期 revision 409、业务校验失败——`todos.ts` 捕获为逐行失败回执）、重放（同键同体 → +0）。审查实测：三次进入 execute 分别 200 / 403 / 抛 409 → 台账只有两条 `[200, 403]`。`receipt`：范围外 / 不可编辑行与回滚行的对象快照前后一致。
- 状态码：断言 status 与 `error.code`（含 `details.reason`），与声明 `Denial` 逐项相等；未知字段预期 `403 FORBIDDEN`。

### 10.2 QuerySpec 查询改写与范围绑定（T2；第 3 轮 P2-3 残留未关闭）


**契约**：列表、计数与聚合一律通过 `access.listQuery(tx, spec)` / `access.count(tx, spec)` / `access.aggregate(tx, spec)` 由框架**组装并执行**；处理函数不再拿到谓词 SQL。

```ts
interface QuerySpec {
  columns: SQL;                                   // 列表达式；可含标量子查询（不改变行集合）
  from: { table: string; alias: string };         // 只能是表标识符
  joins?: readonly Join[];                        // INNER / LEFT JOIN 表标识符，ON 为谓词
  lookups?: readonly Lookup[];                    // LEFT JOIN LATERAL：模块给出子查询主体与 ORDER BY，框架追加 LIMIT 1（最新快照 / 最新版本一类）
  with?: readonly Cte[];                          // CTE：kind 'rows'（参与行集合，受关键字禁令）或 'lookup'（只能 LEFT JOIN 按键关联，允许 GROUP BY）
  where?: readonly SQL[];                         // 业务过滤谓词；可含 EXISTS / 标量子查询（含 LIMIT 1）
  scopeColumns: { org?: SQL; person?: SQL; creator?: SQL; employee?: SQL; department?: SQL }; // 供具名谓词绑定列
  orderBy: SQL;
  page?: { limit: number; offset: number };       // 只能由框架加 LIMIT / OFFSET
  groupBy?: SQL;                                  // 只能由框架放在 WHERE 之后（aggregate）
}
```

- **组装顺序固定**：`WITH … SELECT columns FROM from JOIN … LEFT JOIN LATERAL (… LIMIT 1) … WHERE <具名范围谓词> AND <where…> [GROUP BY] ORDER BY orderBy [LIMIT OFFSET]`，范围谓词永远在 WHERE 首项、LIMIT / OFFSET / GROUP BY 之前。
- **行集合部分的关键字禁令**：`from`、`joins`、`with(kind: 'rows')`、`lookups` 主体中出现 `LIMIT / OFFSET / FETCH / GROUP BY / HAVING / DISTINCT / UNION / INTERSECT / EXCEPT / OVER(` → 组装时抛 `ROUTE_POLICY_BAD_SOURCE`（扫描模块提供的 SQL 文本，字符串字面量除外）；`columns`、`where`、`with(kind: 'lookup')` 不受禁令（标量子查询与 EXISTS 不改变外层行集合；lookup CTE 只能 LEFT JOIN）。禁止模块传入已分页 / 已聚合的 source。
- **执行归框架**：`listQuery` 内部 `tx.execute(composed)`，并记录 `access.queriesExecuted += 1`。`scope.mode: 'list'` 与 `kind: 'own'` 的路由在处理函数返回时 `queriesExecuted === 0` → 500 `ROUTE_POLICY_UNSCOPED`（测试环境抛错）。谓词 SQL 不再暴露给处理函数，"取出即算消费"的假通过路径不存在。
- **lint 范围扩大**：`apps/api/src/modules/**/*.ts`、`apps/api/src/audit/**/*.ts`（含 `queries.ts`、`read-model.ts`、`lists.ts` 等查询辅助文件）禁止参数化分页 `LIMIT ${…}` / `OFFSET ${…}` 与 Drizzle `.limit(` / `.offset(`（常量 `LIMIT 1` 标量 / lateral 查找允许，由框架的 `lookups` 生成或在标量子查询内）；`route-policy/` 目录除外。
- **与现有查询的关系**：现有 `listOrgSnapshot / listJobObjects / listEmployees / listContracts / listTodos / auditViewer` 等改为返回 `QuerySpec`（或其 `from / joins / where / columns` 片段），分页参数由路由传给框架；`employmentVisibilitySql`、`instanceScopeSql`、`personScope`、`audit.visibility` 等成为具名谓词，由框架按 `scopeColumns` 绑定。审计五段逻辑的落点不变（下表为 v2 原表恢复，随 P2-3 冻结未改），但"分页前过滤"改为由组装顺序保证。

| 逻辑 | 现状 | 落点（v2 原文） |
|---|---|---|
| own 的 userId 过滤（待办 / 通知 / 我发起 / 经理待办 / 编制通知接收人 / 序列同步回执） | queries.ts 的 SQL | 具名谓词 `approval.recipient` 等，`listQuery` WHERE |

### 10.6 PR-B 待设计：可信基线、有限例外、retired / `OPEN_BATCHES`、初始化批准与门禁协议（DEC-300 移出；v5 §8 原文 + 第 5 轮 P2-② / P2-③）

**PR-B 的目标**：把 PR-A 的 `PENDING_B` 冻结表换成可机器治理的协议——缩减要可信、新增例外要批准、退出要登记、门禁先告警后强制——并声明完 101 条后清零。PR-A 期间没有例外机制（新增未声明路由始终失败，§8）。

**v5 §8 原文（设计起点，含已知漏洞，见后）**：


**文件与基准**

- `apps/api/src/route-policy/allowlist.baseline.json` = `{ "approval": "DEC-xxx", "entries": [ { method, path, module, batch: 'B' } × 101 ] }`；`allowlist.exceptions.json`：有限例外；`allowlist.retired.json`：**只增不减**的已退出条目（从基线 / 例外删除的每条都要追加，带删除它的 PR 号与日期）。
- 规范化哈希 `H(entries)` = 对 `entries` 按 (method, path) 排序、无空白、UTF-8 的 JSON 做 `sha256`；`approval` 字段不参与哈希。
- 可信基准 = `origin/main` 上这三个文件 + `origin/main:docs/00_状态/02_已确认决策.md` 里的 DEC 登记，且**基线的初始化批准追溯（第 1 条 b）通过**；追溯不通过时 main 的基线不是可信基准（见下）。比较脚本 `scripts/route-policy-allowlist.mjs` 在 CI 里 `git fetch origin main` 后读取基准；PR 自己的 JSON 只是候选。

**1. 初始化批准与自动校验（P2-9：首次引入即校验；激活时追溯引入提交及其父提交）**

- DEC「F-039 基线初始化批准」由总编排以纯文档 PR 登记到 main：内容 = `H(entries)`、条数 101、`OPEN_BATCHES = ['B']`，行内含 `approval` 编号。
- **(a) 引入时自动校验（PR-A 自己的 `pnpm test`，FW-01）**：读取**工作树** `docs/00_状态/02_已确认决策.md` 中 `approval` 指向的 DEC 行，核对 `H(entries)` 与条数相等；行不存在或不相等 → FW-01 失败，PR-A 合不进 main。这层在基线首次进入仓库的那次 CI 就生效，不依赖门禁 PR；它挡住"无 DEC"和"错误哈希"，但挡不住"DEC 与基线同一提交进 main"（晚补），所以还有 (b)。
- **(b) 历史追溯（脚本，任何模式下都是致命项）**：在 `origin/main` 历史上定位**批准绑定提交** C = 最后一次新增该文件或改变 `approval` 字段值的提交（`git log --diff-filter=A -- <file>` 与对 `approval` 字段的逐提交比较），取其第一父提交 P = `C^`；要求 `P:docs/00_状态/02_已确认决策.md` 含该 DEC 行，且行内哈希 / 条数等于 `H(entries@C)` / `|entries@C|`——证明**批准内容正确且批准早于引入**；再要求 `main.entries ⊆ entries@C` 且 `entries@C − main.entries ⊆ main.retired`（引入后只减、减项已登记退出）。任一不成立 → `BASELINE_BOOTSTRAP_UNAPPROVED`（exit 1，不分 warn / enforce），并把 main 的基线视为**不可信**：脚本不以它作基准，所有候选基线条目按"未批准"报告，直至修复。
- 三种建模情况在首次运行脚本（告警模式接入的第一次 main 运行）就得到 `BASELINE_BOOTSTRAP_UNAPPROVED`：无初始化 DEC → P 无行；晚补 DEC（与基线同一提交或之后才进 main）→ P 无行；错误哈希 DEC → 不相等。
- 修复路径：先以纯文档 PR 登记新的 DEC 行（内容 = 当前 `entries` 的哈希与条数）合入 main，**再**以单独提交把 `approval` 改为新编号（该提交的父提交已含该 DEC 行），追溯重新通过。
- CI 需要历史：门禁步骤的 `actions/checkout` 用 `fetch-depth: 0`（或 `git fetch --unshallow origin main`）；浅克隆下定位不到 C / P → `HISTORY_UNAVAILABLE`（致命，不降级为通过）。
- 之后每个 PR：`PR.entries ⊆ main.entries`（只删）；`main.entries − PR.entries ⊆ PR.retired`（删一条就要登记退出）；`PR.approval` 只能等于 `main.approval` 或指向 main 上已存在且哈希等于 `H(PR.entries)` 的新 DEC（重新批准路径）。

**2. 例外条目与批准记录（全要素绑定）**

- 条目：`{ method, path, pr, owner, dependsOn: ['#97'], approvedBy: 'DEC-xxx', exitBatch: 'B' | 'C', exitBy: 'YYYY-MM-DD' }`。
- 批准记录 = main 上的 DEC 行，必须包含该条目**全部要素**的规范化串 `METHOD /path | pr=#n | owner=xx | dependsOn=#a,#b | exitBatch=B | exitBy=日期`；脚本对每条 `PR.exceptions − main.exceptions` 做字符串相等比较，任一要素不同 → `EXCEPTION_UNAPPROVED`。即例外必须先由总编排以 DEC（纯文档 PR）登记到 main，再由开发 PR 引用。
- 退出：`exitBy` 到期或 `dependsOn` 的 PR 关闭 / 取消 → 责任人在下一次合并 main 的 PR 删除该条目并追加到 retired；脚本在 main 运行上对 `today > exitBy` 的条目报违规。基线条目对应路由消失 → FW-01 陈旧条目检查红，由 PR-B 删除并登记 retired。PR-B 前置 PR 任一关闭不影响 PR-B 派发。
- 防止重进：`PR.entries ∩ main.retired = ∅`、`PR.exceptions ∩ main.retired = ∅`（按 method + path）；`main.retired ⊆ PR.retired`（retired 只增）。已退出的路径只能靠补声明回来，不能再进基线或例外。

**3. 运行时集合、CI 顺序与两种模式**

- FW-01 在 `pnpm test` 内枚举运行时并写 `apps/api/.route-policy/runtime.json`（未声明端点集合、已声明端点集合、中间件登记），同时做自洽核对（未声明集合 = 基线 ∪ 例外）与第 1 条 (a)。
- 脚本步骤排在两个 job 的 `pnpm test` **之后**，读取该文件（缺失 → `RUNTIME_SET_MISSING`），断言：运行时未声明集合 `⊆ PR.entries ∪ PR.exceptions`，且基线 / 例外每条都在运行时出现并未声明（陈旧条目）。main 运行上同样执行，并与 `HEAD~1` 比较：基线只减、retired 只增、`OPEN_BATCHES` 按第 4 条。
- `--mode=warn`（告警模式，DEC-297④ 首先采用）：子集 / 陈旧条目 / retired / `OPEN_BATCHES` / `EXCEPTION_UNAPPROVED` / `exitBy` 过期 等**比较类违规**输出 `::warning::` 注解与汇总，exit 0；**信任链与契约类致命项不分模式**：`CONTRACT_MISSING`、`RUNTIME_SET_MISSING`、`HISTORY_UNAVAILABLE`、`BASELINE_BOOTSTRAP_UNAPPROVED` → exit 1。没有可信基准时告警没有意义，所以这四项先于一切。
- `--mode=enforce`（强制模式）：全部违规 exit 1。

**4. `OPEN_BATCHES`（"减少自由、增加须 DEC"）**

- 常量只允许两种变化：（a）**减少**——PR-B / PR-C 收尾提交删除已完成批次，任何 PR 都允许；（b）**增加 `'C'`**——退到 PR-C 的决定以 DEC 登记（DEC-291 Q6），DEC 行含 `OPEN_BATCHES += C`，脚本核对后才放行。其余变化 → `OPEN_BATCHES_UNAPPROVED`，与例外批准同一机制。

**5. 上线顺序（与 §0、§6、§9 一致：初始化 DEC → PR-A → CI 门禁 PR（告警）→ 激活 PR（强制））**

1. **初始化批准 DEC**（纯文档 PR，总编排）：在 PR-A 合并**之前**进 main；PR-A 描述附 `H(entries)` 与条数，PR-A 分支合并 main 后 FW-01 的 (a) 才能通过。
2. **PR-A（契约）**：脚本 `scripts/route-policy-allowlist.mjs`（两种模式）、三个 JSON（基线 101 条 + `approval`、例外空、retired 空）、FW-01（runtime.json + 自洽 + 引入时校验）。此时 `ci.yml` 还没有比较步骤，但 (a) 已在 `pnpm test` 内强制；脚本可在本地对 `origin/main` 手工运行。
3. **CI 门禁 PR**（只改 `ci.yml`，AGENTS §3.7，说明分钟消耗）：PR-A 合并**之后**开；两个 job 的 `pnpm test` 之后加步骤 `node scripts/route-policy-allowlist.mjs --mode=warn`，`actions/checkout` 加 `fetch-depth: 0`；脚本或 JSON 不存在 → `CONTRACT_MISSING` 失败，不做条件跳过。合并后第一次 main 运行即对 PR-A 合并后的 main 做第 1 条 (b) 追溯；三种建模情况都在这里红。
4. **激活 PR**（`--mode=enforce`）：条件 = 追溯通过 + 最近一次 main 运行 0 条比较类告警 + 在途声明补齐；合并后门禁为强制。
   顺序颠倒的情况都会红：CI PR 先合 → `CONTRACT_MISSING`；DEC 晚于 PR-A → PR-A 自己的 FW-01 (a) 红（无行），或追溯 (b) 红（晚补）。

**6. 清零与"声明强制"**：`entries ∪ exceptions` 为空 **且** `OPEN_BATCHES` 为空 **且** 门禁已是 enforce 且追溯通过 → `verifyRouteDeclarations` 进入 strict（缺声明 → `createApp` 抛错；`declare` 是唯一注册入口）；retired 保留作历史。退到 PR-C 时按第 4 条增加 `'C'`，强制切换推迟到 PR-C 合并。**声明强制不表示运行时接管完成**：查询、写入、投影三项各以模块验收为接管条件（§7 Q7、§10.5）。

**7. 冲突处理**：每次合并 main 后在 PR 描述逐项列出基线 / 例外减项与 retired 增项。

**第 5 轮审查未关闭的两类 P2 与修复思路（PR-B 设计必须先解决）**：

- **P2-② ① 同一 PR 内先提交 DEC、再提交基线，仍通过历史追溯**（v5 第 1 条 (b) 只在 main 全部祖先中找 C 与 `C^`；分支上先 D（新增 DEC）再 C（新增基线，`C^ = D`）整体合入 main 即可通过，批准从未经独立 PR 先进 main；仓库允许 merge / rebase / squash，不能靠合并方式隐式消除）。修复思路：批准与引入都以**进入 main 的集成事件**为准——沿 `main` 的 first-parent 链（`git log --first-parent origin/main`）定位 DEC 行首次出现的集成提交 M_dec 与基线 / `approval` 变更首次出现的集成提交 M_base，要求 M_dec 严格早于 M_base 且 M_dec 的变更不含基线文件；DEC 行内再登记"批准所在 main 提交 SHA"，脚本核对该 SHA 在 first-parent 链上且早于 M_base；候选校验只读 `origin/main`，任意祖先含 DEC 不作数。若 rebase-merge 会打散 first-parent 语义，PR-B 前以分支保护限定为 merge commit 或 squash。
- **P2-② ② 告警合入的未批准例外在后续比较中被当成可信数据**（v5 第 2 条只核 `PR.exceptions − main.exceptions`，第 3 条又让 `EXCEPTION_UNAPPROVED` 在 warn 模式 exit 0：未批准例外 e 告警合入 → 下次差集为空 → e 不再报错 → "零告警"满足激活）。修复思路：每次对**全部当前例外 / 冻结表 / retired / `OPEN_BATCHES`** 重算有效批准（不是差集）；维护独立的**可信快照** `trusted-snapshot.json`，只能在 enforce 模式全部校验通过时由脚本写入或由 DEC 批准生成，告警期合入的状态不进入快照；激活条件 = 当前集合与可信快照差异为零且连续 N 次 main 运行满足；历史违规（曾经告警过的条目）保留在报告里直到被批准或退出。与 §8 的边界一致：允许告警的状态持续报告、不进入可信基准、不满足激活。
- **P2-③ 初始化校验与正常缩减基线的规则冲突**（v5 第 1 条 (a) 让 FW-01 把当前 `entries` 哈希与初始化 DEC 比较，没有写"仅首次引入时执行"的判定：PR-B 合法迁移一条后 100 ≠ 101 → FW-01 红）。修复思路：明确两个分支——(1) **批准绑定校验**只对"`approval` 字段变化的那次提交"执行，比较对象是**该提交处的快照** `entries@C` 与 DEC 行；(2) **缩减校验**对其余提交执行：`current.entries ⊆ entries@C_latest` 且 `entries@C_latest − current.entries ⊆ retired`，不再要求哈希等值；重新批准只在重新引入（`approval` 变化）时需要，普通减项不需要。FW-01（工作树）只做 (2) 加"若本次改了 `approval` 则做 (1)"。
- PR-B 还要吸收 §8 表的后四行：致命项清单、告警项的持续报告格式（`::warning::` + 汇总文件 + PR 评论）、激活条件、`fetch-depth: 0`、`ci.yml` 单独 PR（AGENTS §3.7）。

#### 第 6 轮 P2-2 / P2-3（DEC-303 移入 PR-B）与 PR-A 基准的已知限制

**P2-2 探测器把多维身份变化误判成单维权限事实。** v6 §4.2 以 H 为对照、换成 A / O / P / S 等用户推导敏感维度，但这些用户同时改变了身份、能力、绑定与范围（反例：租户设置 H 403 / A 200，入口只查设置能力，会被误判为范围敏感）。修复思路：按路由与分支指定**成功对照身份**，先验证该身份请求成功，再克隆身份**只改目标维度**（撤一个按钮、关一个数据操作、改一个范围）；综合查看人矩阵只作阅读视图，不用于推导单维事实；写探针隔离业务状态、revision 与台账（每个探针独立样本或事务回滚）。

**P2-3 recorded 事实的防同步删减没有闭环。** 只检查“证据用例存在且执行”时，同时删掉 recorded 事实与声明里的同一前提仍全绿。修复思路：证据用例独立输出**规范化事实**（命令内前提名、Outcome 码、台账计数、固定键集合），FW 双向核对“证据实际输出集合 = recorded 集合”；人工评审 diff 作为补充，不替代自动失败条件。

**PR-A 限定版基准测不到、留给 PR-B 的突变**：删嵌套字段路径（需要字段探针观察响应路径）、拒绝码改宽 / 改错（需要范围外 / 关系不成立样本的实际状态码）、`ledger` perItem→single（需要台账计数观察）、场景改 N/A 无依据（需要场景执行集合）。PR-A 的静态基准对这些维度只登记“有无”，不登记“怎样拒绝”。另：过度声明对对象 / 范围 / 字段 / 关系 / 按钮只能单向检查（静态探测否定不了“现状没有”），PR-B 的单维探测补另一方向。

```ts
// tests/acceptance/_f039_enum.test.ts（临时，用后删除）；F039_OUT=… pnpm vitest run tests/acceptance/_f039_enum.test.ts
import { writeFileSync } from 'node:fs';
import { createApp } from '@italent/api';
import { it } from 'vitest';
const COMPOSED = '__COMPOSED_HANDLER';
function unwrap(handler: unknown) {
  let depth = 0; let fn = handler;
  while (fn && typeof fn === 'function' && (fn as Record<string, unknown>)[COMPOSED]) { fn = (fn as Record<string, unknown>)[COMPOSED]; depth += 1; }
  return { depth, fn };
}
it('enumerate routes', () => {
  // 任何数据库访问都抛错的 Proxy：注册阶段不得访问数据库
  const db = new Proxy({}, { get: (_t, p) => { if (typeof p === 'symbol' || p === 'then') return undefined; throw new Error(`db access: ${String(p)}`); } });
  const app = createApp({ db: db as never });
  const rows = app.routes.map((r) => ({ method: r.method, path: r.path, composedDepth: unwrap(r.handler).depth }));
  writeFileSync(process.env.F039_OUT!, JSON.stringify({ total: rows.length, endpoints: rows.filter((r) => r.method !== 'ALL').length, middleware: rows.filter((r) => r.method === 'ALL').length, rows }, null, 1));
});
```
