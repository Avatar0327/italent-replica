# F-481 调动电子签署 设计

> 状态：**第 2 版**（设计稿，只写文档；第 1 轮审查 P2-1～3、P3 1～4 已改，并写入 DEC-847 / DEC-848）。来源：DEC-799（电子签署不进 F-474，另立 F-481）、DEC-842①（照北森做流程、签署用模拟）、DEC-842②（02 补测写入两件）。
> 作用对象：本文全部结论都只作用于**复刻系统**。北森测试租户上的取证已由 02 完成（第 1 轮只读、第 2 轮按 DEC-842② 写入补测，§13），本版不再派取证动作；§14 列出的「可补取证」只供 00 决定，不是本设计的前提。
> 约束：DEC-402 不做存量 / 老租户兼容、不加开关、不回填；DEC-774 没有后端契约的标“未完成”，不做假保存；DEC-625 每片产品代码 ≤ 1500 行、手写 ≤ 3000 行；DEC-814 后端由 Claude Sonnet 实现，前端由 Claude Opus + fe_rules 实现。
> 底稿：调动表单按 [`13_调动配置_本租户实际取值.md` §7](../02_业务建模/13_调动配置_本租户实际取值.md)（HR 端「他人调动申请」表单结构），调动联动按 [`21_调动跨对象联动_对象规格.md`](../02_业务建模/21_调动跨对象联动_对象规格.md)（R1-T10）与现行 `apps/api/src/modules/transfer/linkage/`；本文**只写新增**，没有提到的调动、合同、审批条款继续按现行实现执行。

## 0. 写法选择与理由

- **签署做成独立模块 `esign`，调动只是第一个场景。** 北森的电子签是独立应用（企业认证 / 员工认证 / 我的签署 / 签署记录 / 印章管理 / 签署场景设置 / 设置），调动、Offer、入职共用同一个模板库和签署记录。复刻按同样的边界建：模板库、签署任务、签署记录、我的签署归 `esign`；调动只负责“要不要签、签哪些模板”和“什么时候发起”。Offer / 入职以后接入时只加场景，不改模型。
- **发起时点放在调动生效时，与合同联动同一处。** 北森字段说明原文是“系统将在此业务审批通过后、且在生效日期当天，自动发送签署通知”（§13 E1）。复刻的合同变更本来就在生效时执行（`applyTransferCrossLinkage`，REQ-LNK-001 R1），签署的文件内容（调动后部门、职位、新合同）也只有生效时才确定。所以签署发起挂在生效联动里，不另起时点。
- **模拟签署走与真实对接同一个状态机。** 复刻内“点确认”和将来电子签服务的回调，都翻译成同一组签署事件，交给同一个 `applySignEvent`。这样将来对接时只换“发起 / 撤销 / 提醒 / 取文件”的实现和回调入口，状态、通知、审计都不动（§5）。
- **失败不静默。** 北森补测里选了“是”的调动照样保存成功，签署记录为空，没有任何提示（§13 E6）；记录为空是因为未做企业认证被静默跳过，还是因为生效日在未来、尚未到发送时点，补测区分不了（U2，DEC-847 定为不补测）。复刻不论哪种原因都不静默：复刻没有认证概念，但仍有发起不成的情况（模板被停用、员工没有可登录账号等），一律落一条“发起失败”的签署任务并写原因，HR 在签署记录里能看到、能补发。这是 DEC-842①“失败原因字段复刻自定”的落点，记作差异 D2。

## 1. 结论摘要

1. 调动表单（HR「调动」与「他人调动申请」两种模式）在合同变更段新增「发起电子文件签署 是/否」，选“是”后出现必填多选「选择电子签署模板」（带全选）。只有“是否变更合同 = 是”时这两项才可填；否则后端 400。选择随调动联动版本保存，生效前可随联动一起修改（§3.1、§4.2）。
2. 调动**生效时**（直接调动当天生效即保存时；未来日期由定时生效落地；申请模式在审批通过且到生效日时），在生效联动的同一事务里发起一条签署任务。签署不阻塞调动生效；签署发起不成只记“发起失败”，不回滚调动（§6）。
3. 签署任务两节点：① 员工本人（签署人 = 被调动员工的账号）→ ② 企业确认（签署人 = 签署发起人）。复刻内“确认签署”即完成该节点，没有短信、人脸、实名、企业认证、印章（§5、D1）。
4. 有效期：场景设置默认 2 天、可设 2～30 天，发起时快照到任务；到期仍未完成的任务由定时任务置为“已过期”，不能再签，须重新发起。「到期前自动提醒」默认关，开启后只提醒员工节点，复刻定为到期前 24 小时提醒一次（§5.4、D9）。
5. 签署记录：页签“全部 / 签署中 / 签署完成”，列为发起人、业务所有者、所有者部门、签署场景、发起时间、签署完成时间、签署状态、电子文件；顶部按钮“提醒 / 撤销 / 下载文件”（§8.2）。员工与发起人在「我的签署」里看自己要签、签过的任务并确认签署（§8.3）。
6. 通知走现有站内通知表 `approval_notifications`（`businessType = 'esign_task'`），共 5 个模板：提醒（当前节点签署人）、撤销（发起人、员工各一）、完成（员工、发起人各一）。没有失败 / 过期通知，照北森。文案复刻自拟（§7、D4）。
7. 不做自动重试。撤销、过期、发起失败后，由 HR 在任职记录列表勾选调动记录点「调动发起电子签署」重新发起，新建一条任务，旧任务保留（§6.3、§8.1）。
8. 模板库是租户级，复刻新增最小的模板表与维护页（电子签 > 设置 > 签署模板），Offer / 入职以后共用；调动下拉列出全部启用模板，不按场景过滤。北森“场景自带的调动协议模板不在下拉里（入职登记模板可选）”这一现象复刻不复现：复刻没有场景级模板绑定，见 D3（§3.2）。
9. 合同副作用不在本单改：复刻**已经有**“新合同生效日晚于原合同时终止原合同并新建合同”的行为（`contracts/service.ts` `applyRequest`），但时点是调动生效日而不是北森的保存当时，且前端没有北森那个确认框。已定（DEC-847）：时点维持生效时写入；确认框另立 F-504 补；F-481 各片都不做（§9）。
10. 删除已生效的调动时，在途（签署中）的签署任务在同一事务里自动撤销并发撤销通知；已完成、已过期、发起失败的任务保留不动（§6.4）。
11. 拆 7 片：后端 5 片（Sonnet）、前端 2 片（Opus + fe_rules），每片在 DEC-625 上限内、可独立构建与验收（§11）；新增授权项编码按 DEC-439④ 处理（§10.2）。

## 3. 表单与模板库

### 3.1 调动表单的两个新字段

| 字段（复刻编码） | 北森编码 | 类型 | 何时可填 | 校验 |
|---|---|---|---|---|
| `electronicSignature` | ElectronicSignature | 是 / 否，无默认值（未填 = 否） | 只在“是否变更合同 = 是”时 | 联动请求里 `esign` 存在而 `contract` 为 null → 400 `VALIDATION_FAILED`，`reason: 'TRANSFER_ESIGN_REQUIRES_CONTRACT'` |
| `esignTemplateIds` | SelectMultiTemplate | 模板 ID 数组 | `electronicSignature = 是` 时必填 | 1～20 个、不重复；每个须是本租户**启用**的模板，否则 400 `reason: 'ESIGN_TEMPLATE_UNAVAILABLE'`（带不可用的 ID 列表） |

请求形状：在现有联动请求 `linkageSchema`（`transfer/linkage/input.ts`）上加一项，和 `contract` 并列：

```ts
esign: z.strictObject({ templateIds: z.array(uuid).min(1).max(20) }).nullable().optional(),
```

- `esign` 不存在或为 null 表示“否”；存在即“是”。前端的“是 / 否”单选只是这一项的展示（与“是否变更合同”以 `contract` 是否存在表示同一写法）。
- 两个字段编码加进 `TRANSFER_LINKAGE_FIELDS`（`packages/domain/src/approval/transfer-view.ts:82`），沿用联动字段的字段权限、审批披露与盲审口径；没有 `electronicSignature` 编辑权时带 `esign` → 现有字段权限拒绝。
- 适用范围：HR 的「调动」（direct）与「他人调动申请」（application）。员工本人、经理发起的调动表单本来就没有合同变更段，也不加这两项（U10）。
- 保存时只校验结构与模板可用，**不发起签署**。模板在保存后、生效前被停用，生效时按发起失败处理（§6.2）。

### 3.2 模板库（租户级，最小新增）

北森的模板库是租户级、与 Offer / 入职共用的一个列表。复刻没有，新增一张表和一个维护页：

| 列 | 说明 |
|---|---|
| `id`、`tenant_id` | 内部主键；全部按租户隔离（FORCE RLS） |
| `code` | 业务编码，租户内唯一（DEC-060 标识规则）；创建后不可改 |
| `name` | 模板名称，1～100 字，租户内唯一（下拉按名称显示，重名无法区分） |
| `body` | 正文纯文本，≤ 20000 字；可用 §3.3 的变量 |
| `status` | `enabled` / `disabled` |
| `sort_order` | 下拉顺序 |
| `revision`、`created_at`、`updated_at`、`updated_by` | 乐观锁与审计 |

- **维护入口**：电子签 > 设置 > 签署模板，列表 + 新建 / 编辑 / 启用 / 停用。**不提供删除**：签署任务快照了模板名称和正文（§4.4），但模板仍是签署记录追溯的来源，停用即可让它从下拉消失。
- **种子**：不预置任何模板，新租户和已有租户都一样（DEC-402，不回填）。北森租户里的 12 个模板是该租户自建或系统预置的，复刻不照抄名称。
- **不按场景过滤**：调动下拉 = 本租户全部 `enabled` 模板，按 `sort_order`、`name` 排序，与北森一致。表上**没有**“适用场景”列。
- **场景自带模板不在下拉里（D3）**：北森场景第 2 步「模板设置」绑了 2 个模板（调动协议电子签署模板、入职信息登记表电子签署模板）；调动表单下拉里**没有**场景自带的调动协议模板，入职登记模板可以选（§13 E5，以 02 第 2 轮补测为准）。原因原站没有说明，推测调动协议模板是只供场景内部使用的一类，与表单上手选的租户模板库分开管理。复刻的取舍：**不建场景级模板绑定**，也就不存在“场景模板”这一类对象，这一现象不复现。理由：①DEC-842① 只要求“必选签署模板（可多选，租户级模板库与 Offer / 入职共用）”，没有要求场景模板；②不知道场景模板在北森里何时被使用，照形状建一个不会被使用的绑定，就是一个死配置；③将来真要做“场景自动附带的协议”，可以在场景设置里加一列模板 ID，不影响本单的表结构。
- **权限**：模板维护挂在新的配置对象 `TenantBase.ESignSettings`（§10）；模板选项走两个只读入口，分别按“调动表单”和“批量补发”两种调用场景授权，都不要求模板维护权（§4.3、§10.2）。

### 3.3 模板变量与正文快照

正文里可以写下列变量，发起时替换并把结果快照到任务文件（§4.4）。保存模板时检查变量名，写了表外的变量 → 400 `reason: 'ESIGN_TEMPLATE_VARIABLE_UNKNOWN'`。

| 变量 | 取值（发起时，生效后的任职） |
|---|---|
| `{员工姓名}`、`{工号}` | 被调动员工；工号为空显示“--”（与 F-493 §3.5 同一口径） |
| `{调动生效日期}` | 调动生效日（迟到执行时为实际执行日，与联动同一口径） |
| `{调出部门}`、`{调出职位}`、`{调入部门}`、`{调入职位}` | 版本链上一条与本条（“变更前”从版本链取，硬规则） |

**批量补发的逐条判定**（按顺序，命中即停）：

| 条件 | 回执 code |
|---|---|
| 业务不存在、不是调动、已删除，或不在操作人写范围内 | `NOT_FOUND`（不区分，避免泄露范围外是否存在） |
| 调动未实际生效（判据见下表，**不看**联动执行行） | `ESIGN_TRANSFER_NOT_ACTIVE` |
| 已有签署中的任务 | `ESIGN_TASK_IN_PROGRESS` |
| 其余 | 按 §6.2 发起：成功为 `signing`；发起不成落 `failed` 任务，回执 `ok: true` 且带 `status: 'failed'`、`failureReason` |

**“调动已实际生效”的判据（P2-3）**：S2 在 `esign` 模块里写一个函数 `isTransferInForce(tx, ctx, businessId)`，只依据任职侧的生效事实，**不以 `transfer_linkage_runs` 是否存在为条件**——没有任何联动选项的调动，保存入口直接返回（`transfer/linkage/service.ts:36`），执行入口也不建执行行（`execute.ts:58`），用执行行判断会把这类已生效的调动误拒。判据：

1. 任职记录已落入版本链：`loadEmploymentRecord(tx, tenantId, businessId, 今天)` 返回 `kind = 'transfer'` 且生效日 ≤ 今天（租户时区）；
2. 业务不在待生效队列：复用 `employment/activation-store.ts` 的 `pendingActivationState`（同一条 SQL 谓词，不另写一套）为假——它覆盖“已审批待生效的申请”“已保存未到日的直接调动”“联动待执行（`employment.transfer.linkage.pending`）”，以及没有 `outcome = 'effective'` 生效尝试的情况；
3. 业务最近状态不是 `deleted`、`rejected`、`disapproved`、`voided`、`draft`、`in_review`。

| 情形 | 判定 | 回执 |
|---|---|---|
| 当天生效、没有任何联动选项的直接调动 | 1、2、3 都满足 → 已生效 | 按 §6.2 发起 |
| 当天生效、带联动且联动已执行 | 已生效 | 按 §6.2 发起 |
| 未来日期的直接调动（未到日） | 1 不满足（生效日 > 今天），2 也为真 | `ESIGN_TRANSFER_NOT_ACTIVE` |
| 未提交 / 审批中 / 被驳回 / 作废的申请 | 3 不满足 | `ESIGN_TRANSFER_NOT_ACTIVE` |
| 已审批但未到生效日的申请 | 2 为真 | `ESIGN_TRANSFER_NOT_ACTIVE` |
| 生效联动整单失败（定时任务记 failed，任职随之回滚） | 1 不满足或 2 为真（仍在待生效队列） | `ESIGN_TRANSFER_NOT_ACTIVE` |

S2 实现时以 `activation-store.ts` 现有谓词为准；若发现上表某一情形与现行谓词的结果不一致，按 AGENTS §4 开需取证 issue 并停下报 03，不自行改谓词。

补发不要求该调动当初变更过合同，补发时重新选模板（不沿用调动表单当初选的模板）——这两点都是**复刻取舍**（D16），不是已验证的北森行为：北森补测只看到补发入口和“请至少选择一条数据”提示（§13 E4），没有实际补发。`templateIds` 规则同 §3.1，整批共用一组模板；模板不可用时整批 400（不是逐条问题）。

### 4.4 失败原因（复刻自定，DEC-842①）

| `failure_reason` | 何时 | 显示文案（复刻自拟） |
|---|---|---|
| `TEMPLATE_UNAVAILABLE` | 生效时所选模板有任一被停用（保存后才停用的） | 所选签署模板已停用 |
| `EMPLOYEE_NO_ACCOUNT` | 员工没有绑定账号，或账号停用 / 不是本租户有效成员 | 员工没有可登录的账号，无法签署 |
| `INITIATOR_NO_ACCOUNT` | 发起人账号已停用或已不是本租户成员（只会在生效联动里出现，例如申请提交人离开后才到生效日） | 签署发起人账号不可用，无法完成企业确认 |
| `RENDER_FAILED` | 正文替换失败（保底项；变量已在保存模板时检查，正常不会出现） | 签署文件生成失败 |

`failure_detail` 只存不可用的模板 ID 等机器信息，不存姓名、证件号。“发起失败”是终态，不自动重试；补发即新建任务。

### 4.5 文件下载

- 下载按快照生成，不落文件存储：复用 `survey360/export-files.ts` 的 `renderPdf`（内置中文字体）生成每份文件的 PDF，多份时用 `qualification/chart-files.ts` 的 `zipFiles` 打包，响应头用现有 `fileResponse`；`attachmentName` 现在只接受 `png` / `pdf` 扩展名，S3b 给它加 `zip`（只增不改原有两种）。
- PDF 内容：模板名称作标题、正文快照，末尾两行签署信息——“员工本人：<姓名> 于 <时间> 确认（复刻模拟签署）”“企业确认：<企业名称> 由 <发起人显示名> 于 <时间> 确认（复刻模拟签署，无电子印章）”。明确写“模拟”，避免被当成有法律效力的电子签文件。
- **下载权限（P2-1）**：签署记录入口 `GET /esign/records/files` 每次请求都重新判断三件事，缺一不可：①`ESignRecord.Download` 按钮；②每条任务的业务所有者在操作人当前读范围内；③操作人对 `ESignRecord` 的**“电子文件”字段（`files`）有当前读权**。③不满足时整体 403 `FIELD_FORBIDDEN`，不生成 PDF / ZIP，响应和错误信封里不出现文件名、模板名、任务数。列表接口对 `files` 字段的裁剪与下载用同一个判断函数，避免两处口径不同；权限不缓存（撤权后下一次请求即拒绝，DEC-067 权限条）。
- **文件内其他内容的披露边界**：签署文件是两节点确认过的整份快照，不按字段删改（删改后就不是签署人确认过的文件）。因此“电子文件”读权的含义是“可看整份文件”，包括正文快照里替换进去的员工姓名、工号、调出 / 调入部门与职位、新合同日期，以及末尾两节点签署人的显示名与确认时间。这些内容不再逐项比对“业务所有者”“发起人”等列的字段读权；配置身份时应把“电子文件”视为包含上述信息的敏感字段（§10.1 写进字段说明）。文件**之外**由下载接口生成的部分照常按字段裁剪：zip 包内文件名用到业务所有者姓名时，须同时有“业务所有者”字段读权，否则改用 `<任务短号>_<模板名>.pdf`。
- 「我的签署」入口 `GET /esign/mine/:id/files` 只给该任务的签署人本人（员工或发起人），签署人是文件的一方，不再要求 `ESignRecord` 的按钮和字段权限。
- 只能下载 `completed` 的任务；其他状态逐条报 409 `ESIGN_NOT_COMPLETED`（单条时整体 409；多条里有未完成的整体 409 并列出 ID，不出半个包）。权限判断在状态判断之前：无“电子文件”读权的人拿不到 409 里的 ID 列表。
- 默认命名（**复刻取舍**：北森「签署文件名称」开关关时实际怎样命名未取证）：单份 `<模板名>.pdf`；多份 zip 名 `电子签署文件_<租户日期 yyyyMMdd>.zip`，包内 `<业务所有者姓名>_<模板名>.pdf`，同名加序号。不做自定义命名规则（D8）。
- 每次下载记一条操作日志 `behavior = export`（与现有导出口径一致）。

### 5.1 签署事件（模拟与真实共用）

type SignEvent =
  | { type: 'node_signed'; node: 'employee' | 'enterprise'; actorUserId: string | null; at: Date }

`applySignEvent(tx, ctx, task, event)` 是唯一改状态的函数：校验当前状态允许该事件（§6.3），写任务、写审计、发通知，全部在同一事务。终态吸收：对终态任务的任何事件都拒绝（模拟路径返回 409，回调路径按“已处理”丢弃，见 §5.3）。

### 5.2 模拟确认

- 员工在「我的签署」点「确认签署」→ `POST /esign/mine/:id/sign` → 校验当前用户 = 当前节点签署人、`revision` 一致、未过期 → `node_signed(employee)`，`current_node` 改为 `enterprise`。
- 发起人在「我的签署」（待我签署）里对企业节点点「确认签署」→ `node_signed(enterprise)` → `completed`，发两条完成通知。
- 过期判定以服务端时间为准：`now ≥ expires_at` 时即使定时任务还没跑，确认也返回 409 `ESIGN_TASK_EXPIRED`，并在同一事务里把任务置为 `expired`（与定时任务同一个函数，可重复执行）。
- 确认前不要求填写或核验任何身份信息；页面上写明“复刻模拟签署，不发送短信、不做实名认证”。

- `simulatedProvider` 的 `createEnvelope` / `revoke` / `remind` 都是空操作，`signedFiles` 返回 §4.5 生成的 PDF。

- **状态回调口径**：将来新增 `POST /esign/callbacks/:provider`（不登录、按服务签名验签，不进命令台账），把服务的事件按下表翻译成 `SignEvent`，以 `(provider, 服务事件 ID)` 去重：

| 服务侧事件 | 翻译为 | 说明 |
|---|---|---|
| 某签署人签完 | `node_signed(node)` | 按签署人顺序映射节点；乱序（企业先于员工）拒绝并记审计 |

| 已过期 | `expired` | 复刻自己的定时任务也会置过期，二者幂等 |
| 发起失败 / 签署人拒签 | `provider_failed(reason)` | 进入 `failed`，`failure_reason` 存服务原因码；本单的状态机已允许 `signing → failed` |

### 5.4 有效期与到期前提醒

- 发起时读场景设置（无行取默认 2 天、不提醒），把 `validity_days`、`remind_before_expiry` 快照到任务。之后改场景设置只影响新任务。
- 定时任务 `startESignScheduler`（照 `contracts/scheduler.ts` 的写法，接入现有调度启动处），每轮：
  1. **过期**：`status = 'signing' AND expires_at <= now` → `expired`（逐条 `applySignEvent`，可重复执行）；
  2. **到期前提醒**：`status = 'signing' AND remind_before_expiry AND current_node = 'employee' AND expiry_reminded_at IS NULL AND now >= expires_at - 24h` → 给员工签署人发提醒，写 `expiry_reminded_at`。幂等键 = 任务 + `'expiry_remind'` + 接收人（DEC-052）；员工节点已签则不再提醒企业节点（北森只提醒个人节点）。
- 有效期按小时数计算（发起时刻 + N × 24 小时），不按租户日历日；北森原文“须在 N 天内签完”没有写明口径，记作 D9。
- 失败处理：单条失败只记该条（审计 + 调度日志），下轮重试该条的过期 / 提醒动作；不重试“发起”。

## 6. 时序、状态与撤销

### 6.1 与调动审批、生效的先后

| 调动情形 | 签署何时发起 | 调动状态 |
|---|---|---|
| 直接调动，生效日 ≤ 今天 | 保存事务内（直接调动保存即生效、即执行联动） | 生效，不等签署 |
| 直接调动，生效日在未来 | 定时生效落地当天，随联动执行 | 到日生效，不等签署 |
| 他人调动申请 | 审批通过且到生效日、联动执行时 | 同上 |
| 申请被驳回、撤回、作废 | 不发起（联动没执行） | — |
| 生效联动整单失败（如合同变更被拒） | 不发起（随任职一起回滚，定时任务记 failed，HR 重试后再执行，DEC-052） | 未生效 |

- 发起点在 `applyTransferCrossLinkage` 整单部分的**合同变更之后**（新合同已建，模板变量可取），仍在同一事务。`linkageExecuted` 已保证可重复执行；部分唯一索引再挡一次重复任务。
- **签署失败不回滚调动**：§4.4 的情况写一条 `failed` 任务后正常返回，不抛错。只有数据库层错误才随事务回滚（结果未知，由调动的重试机制处理）。
- 发起成功的任务立即 `signing`、`current_node = 'employee'`。取证未见发起类消息配置（消息设置只有提醒 / 撤销 / 完成），北森实际是否发送待签通知未确认；复刻按 DEC-848 不发，员工在「我的签署」看到待签（已定，D13）。

### 6.2 发起函数

`initiateTransferSign(tx, ctx, { businessId, templateIds, initiatorUserId, origin })`，生效联动与补发共用：

1. 读调动生效后的任职、版本链上一条、联动生成的合同；
2. 检查模板全部启用，否则 `failed / TEMPLATE_UNAVAILABLE`；
3. 解析员工账号、发起人账号，不可用则 `failed / EMPLOYEE_NO_ACCOUNT`、`INITIATOR_NO_ACCOUNT`；
4. 替换变量生成文件快照，失败则 `failed / RENDER_FAILED`；
5. 写 `signing` 任务与文件，调 `provider.createEnvelope`（模拟为空操作），写审计。

### 6.3 状态迁移表（自查第 3 条）

| 当前状态 | 动作 | 结果 | 副作用 |
|---|---|---|---|
| — | 发起成功 | `signing`（员工节点） | 审计 `esign.task.initiated` |
| — | 发起不成 | `failed` | 审计 `esign.task.failed`；不发通知 |
| `signing`（员工节点） | 员工确认 | `signing`（企业节点） | 审计；不发通知 |
| `signing`（企业节点） | 发起人确认 | `completed` | 审计；完成通知 ×2 |
| `signing` | 提醒（手动） | 不变 | 提醒通知给当前节点签署人；审计 |
| `signing`（员工节点） | 到期前提醒（定时） | 不变，写 `expiry_reminded_at` | 提醒通知给员工；审计 |
| `signing` | 撤销（手动） | `revoked`（`manual`） | 撤销通知 ×2；审计 |
| `signing` | 删除该调动 | `revoked`（`business_deleted`） | 同上，在删除事务内 |
| `signing` | 到期（定时或确认时发现） | `expired` | 审计；不发通知 |
| `completed` / `revoked` / `expired` / `failed` | 任何动作 | 拒绝：`ESIGN_TASK_CLOSED`（409） | 无 |
| 任一终态 | 补发 | 新建一条任务 | 旧任务不变 |

撤销、提醒、确认都要求请求里的 `revision` 与当前一致，不一致 409 `REVISION_CONFLICT`，客户端刷新后显式重提（DEC-067）。

### 6.4 撤销调动对签署的影响

- 复刻删除已生效的调动走 `DELETE /businesses/:id`。联动生成的新合同仍有效且未被后续版本取代时，现有删除守卫拒绝删除（`transfer/linkage/deletion-probes.ts` 的 `contractProbe`，DEC-012）；这一点不改。
- 删除成功时（例如 HR 先调整过合同），在删除的同一事务里把该调动所有 `signing` 任务撤销，`revoke_cause = 'business_deleted'`，发撤销通知（员工不应再去签一份已撤销调动的协议）。做法：`esign` 模块给删除流程登记一个删除后钩子，照删除探针的登记方式（`registerDeletionLinkageProbe`），不改删除守卫的判定。
- 已完成的任务**不撤销、不删除**：签署记录是已发生事实的记录；签署记录里业务所有者、场景照旧显示，调动已删除这一点在签署记录里不另加标识（北森未取证，U8）。
- 未来直接调动在生效前删除、申请在审批中撤销 / 作废：还没有任务，无影响。
- 申请模式审批通过后、生效前改联动：沿用 `assertLinkageMutable`，不允许改，签署选择随之不可改。

## 9. 合同副作用（核对结论，不在本单改；DEC-847）

- 北森：保存调动时弹出“变更后合同的生效日期晚于原合同生效日期，继续保存将终止原合同。”确认后，原合同写入实际终止时间 = 调动日 − 1，并新建合同（§13 E5）。
- 复刻：`contracts/service.ts` 的 `applyRequest`（512～590 行）在 change 且新生效日晚于原生效日时，原合同置 `terminated`、`actualTerminationDate = 生效日 − 1`、原因 change，再新建合同（版本号 + 1、`previousContractId`）并写 `contract_changes`；否则原合同置 void。调动经 `changeContractOnActivation` → `changeContractForTransfer` 调用它。**结果与北森一致。**
- 两处差异：①时点：复刻在调动生效时写，北森在保存当时就写（未来日期的调动在北森保存后立刻能看到原合同的实际终止时间）；②复刻前端没有这个确认框（grep“继续保存将终止”无命中）。
- 判断：这两处都属于调动合同联动（F-474-3 / R1-T10 的范围），与电子签署无依赖——签署只读联动的结果。DEC-799 也把合同字段与电子签署分开。**已定（DEC-847，00 代决，待追认）**：时点维持复刻现行的生效时写入；只补保存时的确认框，另立 **F-504**（待派，后补-调动合同联动）。F-481 各片都不做确认框，也不改合同联动。

**独立构建与验收**：每片只调用已合入片的代码，不调用后续片的函数，也不需要后续片的路由来跑自己的 AC。具体来说：S2 发起与撤销用 S1 的 `simulatedProvider` 和通知模板目录，状态迁移在 S2 内闭合（AC-17 里“已完成的任务”用 `applySignEvent` 直接驱动两次确认得到，不经 S3a 的确认路由）；S3a 只调 S2 的 `initiateTransferSign`、`isTransferInForce`、`applySignEvent`；S3b 只调 S1、S2；S3c 只调 S2 的状态机与 S3a 的过期判定。S3a、S3b 互不依赖，可以并行开发。每片的 AC 只断言本片接口和已合入片接口，不跨到后续片。

衔接与风险：

- S1 带迁移和共享文件（schema 导出、`app.ts` 模块挂载、授权版本），按 AGENTS §3.3 作为契约片先合入。S1 合入后没有任何入口写签署任务，表为空，对现有功能无影响。
- S2 合入到 S3a～S3c 合入之间：调动生效会产生 `signing` 任务，也会写撤销 / 完成通知，但还没有员工签署入口；过期靠 S3c 的定时任务，S3c 合入前这些任务不会被定时置为过期（S3a 合入后员工确认时仍会即时判定过期）。窗口里的任务只是挂着，不影响调动本身。S2 的 PR 描述写明这一窗口，S3a～S3c 紧接着做。不用开关把接线推迟到后续片再开启，因为开关违反 DEC-402；只靠连续交付缩短窗口。S3c 合入后第一轮定时任务会把窗口内已超时的任务置为过期，HR 可补发。
- S2 前端还没有入口，后端字段可以先合；S4 依赖 S2 的请求形状与 S3a 的补发契约。
- 通知模板目录与文案放 S1 的 domain（S1 带单测），S2 / S3b / S3c 只接线并写集成用例。
- 信封「通知」页签依赖 F-493 S4b：S2 合入后通知已写入，但 F-493 S4b 合入前界面看不到；「我的签署」本身不依赖通知，员工仍可进入签署。
- 授权版本 S1、S2、S3a、S3b 各改一次，撞号交 `pnpm merge:main`。
