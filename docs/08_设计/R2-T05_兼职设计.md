## 0. 结论先行

1. **兼职记录进 `employment_records`，不进 `employment_timeline`**。解除 `employment_records_primary_only`，改为任职类型白名单 `primary / part_time / secondment / expatriate`（原站 ServiceType 主职 0 / 兼职 1 / 借调 4 / 外派 5，`31` 补充 Q-M0-121①）；时间轴继续只表达**主职**版本链，覆盖触发器只数主职记录。于是 main 上所有经时间轴读任职的位置（`read-model.ts recordsQuery` 及其上 40 余处）**自动只读主职**，不用逐处改。
2. **兼职的生效区间是一条独立的追加式期限链** `employment_part_time_terms`：新增 / 延长 / 结束 / 批量结束 / 调动结束 / 离职结束，每次在**同一条兼职记录**上追加一期（原站“不新增任职记录、同一条记录失效日改为结束日”，R2d / R2f1），不 UPDATE 任何业务值；“原结束日期”从上一期取（硬规则 3）。
3. **兼职申请是独立对象**（原站 `ParttimeJobApproval`，`31` §1.1、`21` §2），三类：新增 / 延长 / 结束；有自己的头、载荷版本、状态事件三张追加式表，接审批中心新业务类型 `part_time`。**不复用 `employment_business_objects` 承载申请**——否则向后更新、状态传播、序列同步、离职作废、生效队列等 10 余处“按员工扫全部任职业务”的查询都会吃进兼职申请（§3.4）。
4. **兼职不进生效队列**：兼职记录是带日期的区间，审批通过（或直接保存）时在同一事务落地；“未开始 / 兼职中 / 已结束”按租户今天从区间派生（原站“状态在保存时就按日期算好”，W-611～613）。状态机仍区分 approved 与 effective 两个事件（硬规则 4），只是落地不等到开始日，理由见 §2.4。
5. **向后更新**：兼职既不是来源（编辑兼职不触发，`07` #26 / AC-FWD-11），也不是目标（主职补录 / 编辑的向后更新不改兼职记录与兼职申请）。执行顺序、计划生效日、迟到重建、REBUILD 窗口一律不涉及兼职（§3）。
6. **离职 / 退休**：两道防线。① 落地时：经 main 既有的任职状态钩子 `onRecordMaterialized`（`status-hooks.ts`），在离职落地的同一事务里把该任职周期的兼职结束于 L′（= 离职实际生效日 − 1），并作废在途兼职申请（原站 R2f2 B63 实测“存在审批中的兼职流程，离职生效后会终止作废该流程”）。② 落地后：钩子不补发（`status-hooks.ts:6`），所以**所有**写兼职区间的人工入口（直接新增、申请提交与落地、编辑结束日、延长）都过同一个**主职周期边界校验**（§4.3A）：区间不得越过该周期已生效离职 / 退休的最后工作日；撤销离职后边界随之解除。**不改 R2-T03 任何已合并批次的语义**，只登记订阅方；撤销离职不自动恢复兼职（同 DEC-222 合同口径），HR 可编辑结束日恢复（§4.6、§12 U-2）。
7. **调动**：实装 `transfer/linkage/part-time.ts` 端口，勾选“结束兼职”= 调动实际生效日 − 1（#71、R2d、R2f 三次一致，AC-LNK-06）。

### 1.3 兼职记录的底层业务头（复用 `employment_business_objects` / `employment_payload_versions` / `employment_state_events`）

`employment_records_payload_fk` 要求每条记录有同 ID 的业务头与载荷版本，因此每条兼职记录配一个底层业务头：`kind = 'part_time'`、`mode = 'direct'`、`selected_staff_id` = 所属周期、`form_id = 'part_time'`；状态事件只有一条 `effective`（落地即写）。之后的**非日期字段编辑**按主职记录编辑同一机制追加 `is_record_snapshot = true` 的载荷版本（`forward-store.ts appendForwardPayload`，`forwardUpdate` 不调用）。底层业务头的 `revision` 是兼职记录的并发版本号（If-Match），期限链每追加一期也 +1。

这些底层业务头**不是申请**：最新状态恒为 `effective`、`mode = 'direct'`，因此不满足 `pendingActivationState`（`activation-store.ts:57`，只取 `approved ∧ application` 或已落地调动），不进生效队列、不进 HR 生效待办、不进调度器 `dueEmployees`（§3.6 逐处说明）。

### 1.4 兼职申请（原站 `ParttimeJobApproval`）：三张新表

**`part_time_requests`**（申请头，1 行 / 单）：`id`、`tenant_id`、`employee_id`、`request_type`（`add` / `extend` / `end`）、`record_id`（extend / end 的目标兼职记录；add 为 NULL，落地记录 ID 记在 effective 事件上）、`initiator`（`hr` / `self` / `manager`，self / manager 入口由 F-020 做，DEC-200 / 283 同构）、`initiator_user_id`、`process_code`（提交时绑定）、`revision`、`created_at`。头只允许改 `revision`（照 `protect_employment_head_metadata`）。

**`part_time_request_versions`**（载荷版本，追加式）：`id`、`request_id`、`version_no`、`previous_version_id`、`command_id`、`service_type`、预置字段（与 §1.1 同一组：部门、职位、职务、序列、职级、直线 / 虚线经理、用工形式、是否部门负责人、新增下属）、`start_date`、`end_date`（add：结束日期；extend：新结束日期；end：结束日期）、`original_end_date`（extend / end：**原定结束日期**，创建时取目标记录当前期；add 为 NULL）、`base_term_no`（extend / end：提交时目标记录的当前期号，落地前比对，§4.4）、`remark`（延长备注 / 结束备注；原站计数器 0/32766，复刻上限 32766 字符）、`custom_fields`、`created_at`。

**`part_time_request_events`**（状态事件，追加式）：`id`、`request_id`、`version_id`、`state`（`draft` / `in_review` / `approved` / `rejected` / `disapproved` / `voided` / `effective` / `deleted`，与任职业务同一集合）、`event_no`、`command_id`、`reason`（voided 时：`hr` / `exit` / `transfer` / `changed_since_submit` / `landing_rejected`）、`record_id`（effective 事件：落地或被改的兼职记录）、`event_seq`（identity，同员工内先后）、`created_at`。

三表都带 `tenant_id`、复合外键到员工 / 头、RLS、只追加触发器（头除外）。**原定结束日期不被实际失效日覆盖**：审批详情读申请版本里的 `original_end_date` 与 `end_date`，不读兼职记录的当前期（R2f1“原定结束日期仍是 10-31、结束日期 10-15”；#71“审批对象日期保持申请时的值、不回写”）。

### 1.6 “兼职是否占人头”与兼职薪资档案的取舍

| 项 | 原站 | 复刻 | 作用对象 |

## 2. 状态机与“审批通过 ≠ 生效”

### 2.1 兼职记录

没有状态列。存在即“已生效”；任职中 / 任职结束 / 未开始全部由期限链 + 今天派生（§1.2）。删除不在本设计（§12 U-5）。

### 2.2 兼职申请

```
draft ──submit──▶ in_review ──approve(末节点)──▶ approved ──落地成功──▶ effective
  ▲                 │  │  └─disagree──▶ disapproved（办结，不可重提，DEC-144）
  │                 │  └──reject──▶ rejected ──submit──▶ in_review
  └──withdraw───────┘
draft / rejected ──delete──▶ deleted
draft / in_review / rejected ──revoke(HR) / 离职 / 调动──▶ voided
approved ──落地前复核失败（§4.4）──▶ voided(reason = changed_since_submit / landing_rejected)
```

- 状态集合、迁移与任职业务一致（`transitions.ts assertTransition` 的同名动作），实现另写一份小状态表，不复用 `transitionEmployment`（后者只认 `employment_business_objects`）。
- approved 与 effective 是**两条事件**；末节点同意的同一事务里先写 approved，再执行落地（§4.4），落地成功写 effective（`record_id` = 兼职记录），落地复核失败写 voided。没有“approved 停留待调度”的中间态。

### 2.3 直接维护

新增兼职 / 编辑 / 批量结束是直接业务：保存即写记录或追加期限，不经申请对象（原站“新增兼职直接保存、不走审批”“批量结束直接生效”，R2d）。

### 2.4 为什么兼职“审批通过即落地”不违反硬规则 4

硬规则 4 要求“审批通过 ≠ 生效，状态机区分两态；未来生效日由定时任务落地”。它针对的是**改写当前值**的业务：主职链上一条未来记录一旦写入时间轴，读当前值的口径就会在未来日期切换，且要按落地时的前驱做继承、向后更新、联动，所以必须等到生效日由调度落地。兼职不同：

1. 兼职记录**不改写任何当前值**（不进时间轴、不继承、不触发向后更新，§3），它本身就是带起止日期的区间，“是否生效”是读取时按日期判断的事实，写入时刻不影响任何读口径。
2. 原站就是这样：未来开始的兼职保存后立即出现在“未开始”视图（W-612，R2d“未开始视图按开始日期在未来划分”）；审批通过前不生成兼职任职、通过后才生成（R2d）。若等到开始日才落地，“未开始”视图就永远为空，与原站不符。
3. 状态机仍然区分 approved 与 effective（两条事件、两个审计动作），满足“区分两态”的字面；“未来日期由定时任务落地”没有适用对象（没有未来才发生的写入）。PT-7 的“是否部门负责人”（开始日才改组织负责人）是唯一真正“到日执行”的效果，它走现有调度器（§4.8）。

此条作为**假设 A-1**提请设计审确认（§12）。

## 3. 主职 / 兼职对向后更新的影响（重点）

### 3.1 总原则

| 问题 | 结论 | 依据 |
|---|---|---|
| 兼职能否作为向后更新**来源** | 不能。编辑兼职只改本记录 | `07` §2 条件② 与表第 26 行；AC-FWD-11；main `forward-rules.ts:26`（`isForwardEditSupported` 的主职判定）已要求 `serviceType === 'primary'`，兼职编辑入口不调用 `forwardUpdateEmployment` |

### 4.3A 主职周期边界统一校验（第 1 轮 P2-01）

**问题**（v1.0）：离职钩子只在离职落地那一刻结束兼职、不补发（`status-hooks.ts:6`）；而 D-2 只看开始日、D-3 只看**未落地**离职，于是 ① 员工 10-16 离职已生效后，HR 补录 10-01 起、无结束日期的兼职能通过；② 钩子把兼职结束于 L′ 后，HR 再用编辑把结束日推到 L′ 之后也能通过。两种都会得到“已离职员工仍有进行中的兼职”。

**唯一函数**：`assertPartTimeWithinCycle(tx, ctx, { employeeId, staffId?, startDate, endDate, recordId? })`（`employment/part-time/boundary.ts`），在员工行锁内调用，纯判定部分在 `packages/domain/src/employment/part-time.ts` 的 `partTimeBoundaryViolation(input)`，SQL 只负责取三项事实：

| 事实 | 取法（全部读时间轴 / 业务头表，主职口径） |
|---|---|
| F1 开始日主职 | 时间轴在 `startDate` 的当前记录：所在周期 `staff_id`、`kind`、人员状态（`employment_record_status`）。新建时周期由它决定；已有兼职记录时须等于记录的 `staff_id` |
| F2 该周期已生效的终止 | 同员工时间轴上 `staff_id` = 该周期、`kind ∈ {leave, retirement}`、未删除的最早一条：其生效日 E，**L = E − 1**（离职 / 退休已落地；迟到顺延后即 L′） |
| F3 该周期未落地的终止 | 业务头表中 `kind ∈ {leave, retirement}`、`selected_staff_id` = 该周期、最新状态 ∈ {in_review, approved} 的业务：计划最后工作日 Lp = `plannedEffectiveDate` − 1（R2-T03 §5.0A 唯一来源）；多条取最早 |

**规则**（复刻系统；原站对“离职后补录 / 延长兼职”的行为未验证，B-4，取最保守）：

| # | 规则 | 错误 |
|---|---|---|
| B-1 | F1 存在、`kind ∉ {leave, retirement}`、人员状态 ∈ {试用 2, 正式 3, 非正式 12}（待入职 1、调出 4、待调入 5、离职 8、退休 6 拒绝） | 409 `PART_TIME_PRIMARY_NOT_ACTIVE` |
| B-2 | **F2 存在时**：`endDate` 必须非空且 ≤ L；`startDate` ≤ L 已由 B-1 保证（L 之后时间轴当前记录是离职） | 409 `PART_TIME_BEYOND_EXIT`，文案“兼职结束日期不能晚于主职最后工作日（L）”，`detail: { lastWorkDate: L }` |
| B-3 | F3 存在且 `startDate > Lp` | 409 `PART_TIME_AFTER_EXIT` |
| B-4 | F3 存在且区间跨过 Lp（`endDate` 为空或 > Lp） | 只提示 `warnings: PART_TIME_SPANS_PENDING_EXIT`，不拦（W-610；离职落地时钩子结束它） |

**调用点**（全部人工入口；系统入口只缩短区间，不调用）：

| 入口 | 何时调用 | 输入 |
|---|---|---|
| 直接新增（§4.2） | 保存 | 表单 `startDate` / `endDate` |
| 新增申请（§4.5） | 创建、修改、**提交**（含驳回后重提）、**审批编辑**（独立编辑与编辑并同意）、**审批落地** | 创建 / 修改 / 审批编辑：合入本次改动后的**待写版本**（校验通过才追加）；提交 / 落地：申请最新版本 |
| 编辑兼职改结束日（§4.4） | 保存 | 记录 `start_date` + 新 `endDate` |
| 延长申请（§4.4） | 创建、修改、提交、审批编辑、**审批落地** | 记录 `start_date` + 新结束日 |
| 结束申请 / 批量结束 / 调动结束 / 离职钩子 | 不调用（只会把结束日提前到当前结束日或之前；B-2 若已成立仍成立） | — |

**跨越已生效离职 / 退休的处理**：人工入口一律拒绝（B-2），不自动截断——截断会悄悄改写 HR 填的日期；HR 按提示把结束日改到 L 或之前再提交。**拒绝发生在本次写入之前**：创建不建申请头、修改与审批编辑不追加申请版本（草稿也不例外，A-16 无草稿豁免）。

**审批编辑的拒绝形态**（第 2 轮 P2-01 缺口 1）：审批引擎经 `approval/actions.ts:205 applyEdit` → 适配器 `edit` 保存业务新版本（独立编辑按钮走 `:684 editTask`，编辑并同意走 `:237 approveTask` 带 `fields`，编辑在关闭任务之前执行）。兼职适配器 `edit` 先把本次改动合入申请最新版本得到待写版本，对 add 重跑 D-1～D-10 与 `assertPartTimeWithinCycle`、对 extend 重跑 E-1～E-6、对 end 重跑 T-1～T-2，**通过才追加版本**；不通过即抛业务错误，事务整体回滚：独立编辑 → 申请版本、任务、实例都不变，不写 `approval.task.edit`；编辑并同意 → **整个同意动作失败**，任务不关闭、节点不推进、实例与申请状态不变（同 R2-T03 §7.2 #3 / #4 对离职日期的拒绝形态）。审批落地时命中 B-2（申请审批期间离职落地了）→ 申请按 §4.4 落地复核失败作废（`reason = landing_rejected`），不落地。

**撤销离职后允许恢复（正例）**：F2 只读未删除的时间轴记录。离职被撤销（R2-T03 B4 `exits/:id/cancel` → `deleteEmploymentBusiness` 写墓碑、移除时间轴行），或可信造数的离职经 R1-T11 删除，F2 随之消失，B-2 不再约束：HR 用“编辑兼职”把被钩子结束于 L′ 的兼职结束日改回截断前的值（期限链上一期，§1.2）或其他有限日期即可恢复；截断前没有结束日的，因结束日不可置空（A-9）须填一个有限日期。重聘（新周期）不会解除旧周期的边界：旧周期兼职仍受旧 L 约束，新兼职归新周期（F1）。

**并发**：离职落地与兼职写入都先持员工行锁（§7.1），串行；先写兼职后落地 → 钩子截断；先落地后写兼职 → B-2 拒绝。

用例：PB-58～PB-63（§9）。

**批量结束**（R2d；第 1 轮 P2-02 改为逐条 revision，照 `employment/batch-edit.ts` 先例）：
- 请求 `{ items: [{ recordId, revision }]（1～200 条）, endDate }`；**不使用 If-Match**（单个版本号无法对应多条记录），请求带 If-Match 时 400 `VALIDATION_FAILED`。
- 同一 `recordId`（不区分大小写）重复出现 → 400 `VALIDATION_FAILED` + `reason: 'DUPLICATE_RECORD'`，整批不执行。
- 取锁：先查各记录的员工（`employment_business_objects` 原始 owner 查询，不存在 / 不是兼职底层业务 → 整批 404），按员工 UUID 升序逐个 `lockEmploymentEmployee`，再按记录 ID 升序锁兼职底层业务头；**在锁内**逐条比对 `revision`，任一条不等 → 409 `REVISION_CONFLICT`，`detail.items` 逐条给出 `{ recordId, expected, actual }`（操作人不可见的只计 `hiddenCount`），整批回滚：不追加任何期限、不写任何审计 / outbox / 操作日志。
- revision 全部一致后逐条按 T-1 / T-2 / E-4 / E-5 校验，任一条失败同样整批回滚，逐条回执原因（不可见的只计件数）。
- 成功：每条追加期限 `source = batch_end`、`source_id = 批次 ID`，底层业务头 revision +1，逐条审计 `employment.part_time.batch_end`；对象操作日志一条（`recordOperationLog`，`behavior = 'batch_update'`，逐行 `employeeId` + `orgId` = 兼职部门，同 `batch-edit.ts:69～88`）。被结束的兼职进入“已结束”（结束日已过时）、任职状态“任职结束”（R2d）。

### 4.5A 审批适配器的资源锁计划（第 1 轮 P2-06）

全局锁序（`org/locks.ts`）：员工 / 业务 → 组织 → 编制 → 实例。审批引擎在锁实例之前先调适配器 `lock`（单实例命令）或 `lockMany`（批量交接 / 停用接管，`approval/handover.ts:516～540 lockHandoverParticipants` 先按 `subject_employee_id` 锁员工闭包，再按业务类型调 `lockMany`）。兼职申请的同意可能触发落地，落地要取组织锁（D-7 / E-3 部门可用性，`references.ts assertEmploymentDepartmentAvailableWithin`），因此组织锁必须在锁实例、**以及**批量交接登记替代人（对成员行取 KEY SHARE）之前取得，否则与“入职绑定账号：组织锁 → 成员行 FOR UPDATE”成环（F-065 的同一问题）。

| 方法 | 加锁顺序 | 组织锁 |
|---|---|---|
| `lock(tx, ctx, requestId)`（单实例：同意 / 驳回 / 不同意 / 撤回 / 审批编辑 / 加签激活等任一审批命令） | ① `lockEmploymentEmployee(申请员工)` → ② `part_time_requests` 头 FOR UPDATE → ③ extend / end：目标兼职记录的底层业务头 FOR UPDATE | `request_type ∈ {add, extend}` 时 ④ `lockOrganizationSettings`（与 employment 适配器对调动先取编制锁同理：落地需要的资源锁在实例锁之前取）；`end` 不取（结束只缩短区间，不查部门可用性） |
| `lockMany(tx, ctx, requestIds, { organization, reassignFrom })`（批量交接、全局停用接管） | 员工闭包已由 `lockHandoverParticipants` 取得；本方法 ① 申请头按 ID 升序 FOR UPDATE → ② 目标兼职记录底层业务头按 ID 升序 FOR UPDATE | `organization = true` 且批内有 `add` / `extend`，且（未给 `reassignFrom`，或 `mayMergeSeat(批, reassignFrom)` 为真——本批可能因会签合席推进业务）→ ③ `lockOrganizationSettings`；`organization = false`（撤销成员关系的接管，没有账号锁前缀）不预取，落地时由 `lock` 的 ④ 按既有顺序取得。与 employment 适配器 `lockMany`（`adapters.ts:317～330`）同一判定；`mayMergeSeat` 由 `adapters.ts` 导出共用 |

- 预锁后的落地只**重入**这些锁；落地内 `assertEmploymentDepartmentAvailableWithin` 再取组织锁是同事务重入，不产生新的等待。
- 停用接管（F-069 全局停用）在锁账号行之前以 `organization = true` 预取，路径与手动交接相同；撤销成员关系路径见上表。
- 真 PG 屏障用例 `AC-PT-approval-lock-pg`（PT-4a）：组织锁是租户级排他锁（`org/locks.ts:12`），双方不能同时越过它，屏障按“先 B 后 A”编排：① 事务 B（入职绑定账号路径）先取组织锁并停住（不提交）；② 启动事务 A：批量交接一批含兼职新增申请的实例；③ 轮询 `pg_locks` / `pg_stat_activity`，断言 A 正在 `lockMany` 的组织锁上等待（`wait_event_type = 'Lock'`），且**尚未**登记替代人（成员行上没有 A 的 KEY SHARE）；④ 放行 B（完成成员行 FOR UPDATE 并提交）；⑤ 断言 A 随后完成（登记替代人、会签合席推动落地），两者都成功、无 `40P01` 死锁、结果与串行执行一致。另一例：B 先持组织锁，A 对单个兼职新增申请执行同意，断言 A 在适配器 `lock` 的组织锁上等待（早于锁实例），放行 B 后 A 完成。

### 7.1 锁顺序（`org/locks.ts` 全局序之内）

**锁覆盖更正（第 1 轮 P3 / 表 B P-40）**：main `employment/transfer-locks.ts:79～83` 在多员工闭包（`planned.length > 1`）时对参与员工的**全部**业务头 `FOR UPDATE`，其中**包括兼职底层业务头**（它们就在 `employment_business_objects`）；R2-T03 离职经 `lockTransferParticipants`（§5.2 ①，participants 扩到 leave）同样会在组织锁之前锁到它们。v1.0 写“不含兼职底层业务头”有误。兼职申请头不在业务头表，任何既有路径都不会预锁它。

### 7.3A 命令重放与结果复核（第 1 轮 P2-03；表 B P-19）

**问题**：所有任职写入口经 `employment/context.ts:435 runWrite` 执行，提交前（`:463`）与重放时都调 `permission/employment-replay.ts authorizeEmploymentResult` 复核“本命令的足迹 + 响应里的对象”在当前权限下仍可写。main 上它只采 `employment-record` / `employment-business` 两类足迹（`:153 / :159`），目标只查业务头表（`:167～180`），创建人只认 `employment.business.create`（`:174`）。兼职申请 ID 不在业务头表 → 首次执行就 404；兼职审计对象足迹不被采集 → 撤权后重放拿得到原响应。

**方案：两层都做，缺一不可**

1. **专用命令 guard**（`employment/part-time/replay-guard.ts`，照 main `employment/replay-guard.ts` 的 `scopedGuard` 写法，如 BE-6a #386 的 `internRegularizationGuard`）：每个兼职写入口一个 guard，`before(tx)` 在 runCommand 的三个出口（首次执行、同键直接重放、失败后回查）都按**当前**授权重跑 §7.2 该入口整行（功能操作权、按钮、员工主职范围、兼职部门范围、字段权）；兼职部门取**当前值**（记录当前快照 / 申请最新版本 / extend、end 取目标记录当前部门），因此“改部门后”重放按新部门判。带 `scopedGuard` 标记，`runWrite` 让执行与结果复核都用事务内重新解析的范围（`context.ts:396～433` 既有机制）。
2. **扩展统一结果复核链**（`permission/employment-replay.ts`，PT-2）：
   - `footprints`：`object_type IN (…, 'employment-part-time', 'part-time-request')`，审计与 outbox 两个分支都加；兼职记录编辑写的快照载荷照常经 outbox 分支给出 `snapshotDepartment`。
   - `currentTargets`：在业务头查询后 `UNION ALL` 兼职申请：`SELECT r.id, r.employee_id, <部门>, r.initiator_user_id FROM part_time_requests r …`；`<部门>` = add 取最新版本 `department_id`，extend / end 取目标兼职记录当前部门（快照优先）。兼职底层业务头已在原查询内（部门取记录 / 快照，正是兼职部门）。
   - 创建人：兼职记录取 `partTimeRecordCreator`（第 1 期来自申请时取申请 `initiator_user_id`，否则 `audit_object_creators` 中 `action = 'employment.part_time.create'` 的创建人）；兼职申请取 `initiator_user_id`。`audit_object_creators` 由 0058 触发器对所有 `*.create` 动作自动写入，无需迁移。
   - `responseSnapshots`：兼职记录 / 申请的响应形状都带 `{ id, employeeId, fields: { departmentId } }`，现有解析即可识别；`linkedOnly`：`employment.part_time.ended_by_transfer` / `ended_by_exit` / `part_time.request.voided_by_*` 加入 `LINKED_ACTIONS`（联动改写，按 DEC-177 可见口径复核，同 DEC-178），其余兼职动作按写入口径复核。
   - 不涉及 `employment.forward-update` 字段复核（兼职不触发向后更新）。

### 7.5 幂等与并发

`Idempotency-Key` + If-Match：兼职记录用底层业务头 `revision`，申请用申请头 `revision`；不一致 409，客户端刷新后显式重提（AGENTS §10）。批量结束不用 If-Match，按 §4.4 逐条 `{ recordId, revision }`。真 PG 交错（`AC-PT-*-pg.test.ts`，CI 队首跑）：① 同员工并发新增两条外派恰一条成功（D-5）；② 结束申请审批落地 vs 调动联动结束同一兼职（恰一方改期限，另一方作废 / 幂等）；③ 离职落地 vs 新增兼职申请提交（员工行锁串行）；④ 组织停用 vs 新增兼职（组织锁串行，恰一方成功）；⑤ 批量交接兼职申请 vs 入职绑定账号（§4.5A 屏障，无死锁）；⑥ 批量结束 vs 单条编辑同一兼职（锁内 revision 比对，恰一方成功，失败方整批无写入）。

## 13. 分批实现计划（每批 ≤ 1500 行含测试；可独立合并、对外自洽）

原则同 R2-T03 §18：行数 = 产品代码 + 测试 + 测试 support + **手写 SQL**（迁移里的触发器 / 函数 / CHECK）；只排除生成物（F-039 冻结基准 / 摘要、迁移 `meta/` 快照与 `_journal`、Drizzle 生成的建表 DDL、标准授权指纹与 HISTORY 行）。PT-1 是契约 PR，先单独合并（AGENTS §3-3）。每批开工前 `pnpm merge:main`，推送前只跑 `pnpm lint && pnpm typecheck` 与本批测试文件（DEC-351）。

**v1.1 预先拆批**（第 1 轮 P2-07：v1.0 的 PT-3 / PT-4 都恰好 1500 行、没有文件级估算）：PT-3 拆为 3a / 3b / 3c，PT-4 拆为 4a / 4b / 4c；“写入底座”与“开闸入口”分开，底座批次**不注册任何公开写路由**，测试经内部服务调用。

**自洽边界**：系统里任一时刻都不能出现“兼职存在但离职不结束它 / 越过周期边界 / 组织能被停用 / 通用接口能改它”。所以离职钩子（结束兼职）、周期边界、停用计数、删除探针与**第一个能写出兼职的批次**（PT-3a 的内部服务；公开入口 PT-3b 才开）同时交付；作废兼职申请、在途申请停用计数、审批资源预锁与第一个能写出申请的批次（PT-4a）同时交付。
