## 0. 结论先行

1. **兼职记录进 `employment_records`，不进 `employment_timeline`**。解除 `employment_records_primary_only`，改为任职类型白名单 `primary / part_time / secondment / expatriate`（原站 ServiceType 主职 0 / 兼职 1 / 借调 4 / 外派 5，`31` 补充 Q-M0-121①）；时间轴继续只表达**主职**版本链，覆盖触发器只数主职记录。于是 main 上所有经时间轴读任职的位置（`read-model.ts recordsQuery` 及其上 40 余处）**自动只读主职**，不用逐处改。
2. **兼职的生效区间是一条独立的追加式期限链** `employment_part_time_terms`：新增 / 延长 / 结束 / 批量结束 / 调动结束 / 离职结束，每次在**同一条兼职记录**上追加一期（原站“不新增任职记录、同一条记录失效日改为结束日”，R2d / R2f1），不 UPDATE 任何业务值；“原结束日期”从上一期取（硬规则 3）。
3. **兼职申请是独立对象**（原站 `ParttimeJobApproval`，`31` §1.1、`21` §2），三类：新增 / 延长 / 结束；有自己的头、载荷版本、状态事件三张追加式表，接审批中心新业务类型 `part_time`。**不复用 `employment_business_objects` 承载申请**——否则向后更新、状态传播、序列同步、离职作废、生效队列等 10 余处“按员工扫全部任职业务”的查询都会吃进兼职申请（§3.4）。
4. **兼职不进生效队列**：兼职记录是带日期的区间，审批通过（或直接保存）时在同一事务落地；“未开始 / 兼职中 / 已结束”按租户今天从区间派生（原站“状态在保存时就按日期算好”，W-611～613）。状态机仍区分 approved 与 effective 两个事件（硬规则 4），只是落地不等到开始日，理由见 §2.4。
5. **向后更新**：兼职既不是来源（编辑兼职不触发，`07` #26 / AC-FWD-11），也不是目标（主职补录 / 编辑的向后更新不改兼职记录与兼职申请）。执行顺序、计划生效日、迟到重建、REBUILD 窗口一律不涉及兼职（§3）。
6. **离职 / 退休**：经 main 既有的任职状态钩子 `onRecordMaterialized`（`status-hooks.ts`），在离职落地的同一事务里把该任职周期的兼职结束于 L′（= 离职实际生效日 − 1），并作废在途兼职申请（原站 R2f2 B63 实测“存在审批中的兼职流程，离职生效后会终止作废该流程”）。**不改 R2-T03 任何已合并批次的语义**，只登记订阅方；撤销离职不自动恢复兼职（同 DEC-222 合同口径），列入撤销下游清单（§4.6、§12 U-2）。
7. **调动**：实装 `transfer/linkage/part-time.ts` 端口，勾选“结束兼职”= 调动实际生效日 − 1（#71、R2d、R2f 三次一致，AC-LNK-06）。

### 1.3 兼职记录的底层业务头（复用 `employment_business_objects` / `employment_payload_versions` / `employment_state_events`）

`employment_records_payload_fk` 要求每条记录有同 ID 的业务头与载荷版本，因此每条兼职记录配一个底层业务头：`kind = 'part_time'`、`mode = 'direct'`、`selected_staff_id` = 所属周期、`form_id = 'part_time'`；状态事件只有一条 `effective`（落地即写）。之后的**非日期字段编辑**按主职记录编辑同一机制追加 `is_record_snapshot = true` 的载荷版本（`forward-store.ts appendForwardPayload`，`forwardUpdate` 不调用）。底层业务头的 `revision` 是兼职记录的并发版本号（If-Match），期限链每追加一期也 +1。

这些底层业务头**不是申请**：最新状态恒为 `effective`、`mode = 'direct'`，因此不满足 `pendingActivationState`（`activation-store.ts:57`，只取 `approved ∧ application` 或已落地调动），不进生效队列、不进 HR 生效待办、不进调度器 `dueEmployees`（§3.6 逐处说明）。

### 1.4 兼职申请（原站 `ParttimeJobApproval`）：三张新表

**`part_time_requests`**（申请头，1 行 / 单）：`id`、`tenant_id`、`employee_id`、`request_type`（`add` / `extend` / `end`）、`record_id`（extend / end 的目标兼职记录；add 为 NULL，落地记录 ID 记在 effective 事件上）、`initiator`（`hr` / `self` / `manager`，self / manager 入口由 F-020 做，DEC-200 / 283 同构）、`initiator_user_id`、`process_code`（提交时绑定）、`revision`、`created_at`。头只允许改 `revision`（照 `protect_employment_head_metadata`）。

**`part_time_request_versions`**（载荷版本，追加式）：`id`、`request_id`、`version_no`、`previous_version_id`、`command_id`、`service_type`、预置字段（与 §1.1 同一组：部门、职位、职务、序列、职级、直线 / 虚线经理、用工形式、是否部门负责人、新增下属）、`start_date`、`end_date`（add：结束日期；extend：新结束日期；end：结束日期）、`original_end_date`（extend / end：**原定结束日期**，创建时取目标记录当前期；add 为 NULL）、`base_term_no`（extend / end：提交时目标记录的当前期号，落地前比对，§4.4）、`remark`（延长备注 / 结束备注；原站计数器 0/32766，复刻上限 32766 字符）、`custom_fields`、`created_at`。

**`part_time_request_events`**（状态事件，追加式）：`id`、`request_id`、`version_id`、`state`（`draft` / `in_review` / `approved` / `rejected` / `disapproved` / `voided` / `effective` / `deleted`，与任职业务同一集合）、`event_no`、`command_id`、`reason`（voided 时：`hr` / `exit` / `transfer` / `changed_since_submit` / `landing_rejected`）、`record_id`（effective 事件：落地或被改的兼职记录）、`event_seq`（identity，同员工内先后）、`created_at`。

三表都带 `tenant_id`、复合外键到员工 / 头、RLS、只追加触发器（头除外）。**原定结束日期不被实际失效日覆盖**：审批详情读申请版本里的 `original_end_date` 与 `end_date`，不读兼职记录的当前期（R2f1“原定结束日期仍是 10-31、结束日期 10-15”；#71“审批对象日期保持申请时的值、不回写”）。

## 2. 状态机与“审批通过 ≠ 生效”

### 2.1 兼职记录

没有状态列。存在即“已生效”；任职中 / 任职结束 / 未开始全部由期限链 + 今天派生（§1.2）。删除不在本设计（§12 U-5）。

### 2.2 兼职申请

```
draft ──submit──▶ in_review ──approve(末节点)──▶ approved ──落地成功──▶ effective
  ▲                 │  │  └─disagree──▶ disapproved（办结，不可重提，DEC-144）
  │                 │  └──reject──▶ rejected ──submit──▶ in_review
  └──withdraw───────┘
draft / rejected ──delete──▶ deleted
draft / in_review / rejected ──revoke(HR) / 离职 / 调动──▶ voided
approved ──落地前复核失败（§4.4）──▶ voided(reason = changed_since_submit / landing_rejected)
```

- 状态集合、迁移与任职业务一致（`transitions.ts assertTransition` 的同名动作），实现另写一份小状态表，不复用 `transitionEmployment`（后者只认 `employment_business_objects`）。
- approved 与 effective 是**两条事件**；末节点同意的同一事务里先写 approved，再执行落地（§4.4），落地成功写 effective（`record_id` = 兼职记录），落地复核失败写 voided。没有“approved 停留待调度”的中间态。

### 2.3 直接维护

新增兼职 / 编辑 / 批量结束是直接业务：保存即写记录或追加期限，不经申请对象（原站“新增兼职直接保存、不走审批”“批量结束直接生效”，R2d）。

### 2.4 为什么兼职“审批通过即落地”不违反硬规则 4

硬规则 4 要求“审批通过 ≠ 生效，状态机区分两态；未来生效日由定时任务落地”。它针对的是**改写当前值**的业务：主职链上一条未来记录一旦写入时间轴，读当前值的口径就会在未来日期切换，且要按落地时的前驱做继承、向后更新、联动，所以必须等到生效日由调度落地。兼职不同：

1. 兼职记录**不改写任何当前值**（不进时间轴、不继承、不触发向后更新，§3），它本身就是带起止日期的区间，“是否生效”是读取时按日期判断的事实，写入时刻不影响任何读口径。
2. 原站就是这样：未来开始的兼职保存后立即出现在“未开始”视图（W-612，R2d“未开始视图按开始日期在未来划分”）；审批通过前不生成兼职任职、通过后才生成（R2d）。若等到开始日才落地，“未开始”视图就永远为空，与原站不符。
3. 状态机仍然区分 approved 与 effective（两条事件、两个审计动作），满足“区分两态”的字面；“未来日期由定时任务落地”没有适用对象（没有未来才发生的写入）。PT-7 的“是否部门负责人”（开始日才改组织负责人）是唯一真正“到日执行”的效果，它走现有调度器（§4.8）。

此条作为**假设 A-1**提请设计审确认（§12）。

## 3. 主职 / 兼职对向后更新的影响（重点）

### 3.1 总原则

| 问题 | 结论 | 依据 |
|---|---|---|
| 兼职能否作为向后更新**来源** | 不能。编辑兼职只改本记录 | `07` §2 条件② 与表第 26 行；AC-FWD-11；main `forward-rules.ts:15 isForwardEditSupported` 已要求 `serviceType === 'primary'`，兼职编辑入口不调用 `forwardUpdateEmployment` |

**落地（审批末节点同意的同一事务）**：先写 approved，再锁员工 → 兼职记录 → 复核：① 目标记录当前期号 = 申请最新版本的 `base_term_no`（提交后有调动 / 离职 / 直接编辑改过它 → 不落地）；② 重跑 E-1～E-3 / T-1～T-2；③ 范围按**原发起人当前权限**不再复核（审批人代表业务批准，同任职申请审批落地口径）。通过 → 追加期限（`source = extend / end`、`source_id = 申请 ID`），写 effective 事件；任一不通过 → 写 voided（`reason = changed_since_submit / landing_rejected`），审计 + outbox `part_time.request.voided`，给发起人发站内消息（§4.6 同一通知）。审批动作本身成功、结论保留（与 F-007 §2-3“审批落地失败不影响审批结论”同一落点）。

结果对齐原站（R2f1）：同一条兼职记录失效日改为结束日（10-01～10-31 结束于 10-15 → 10-01～10-15）、任职状态“任职结束”（结束日已过时）、进“已结束”视图、**不新增任职记录**、**主职不变**；审批详情“原定结束日期”仍为 10-31（申请版本字段，不回写）。

**直接修改结束日期**（编辑兼职，`15` §1）：`PATCH part-times/:recordId` 带 `endDate` → 追加期限 `source = edit`；规则 = T-1 + D-7（推后时校验新增段）+ E-4（有未办结的延长 / 结束申请时拒绝改日期，409 `PART_TIME_REQUEST_IN_PROGRESS`）。原站编辑抽屉能否把结束日改成空（取消结束）未验证 → 不允许置空（400 `PART_TIME_END_DATE_REQUIRED`，仅当当前已有结束日时）。

## 7. 锁、权限、F-039、审计、幂等

### 7.1 锁顺序（`org/locks.ts` 全局序之内）

```
① lockEmploymentEmployee（批量：员工 UUID 升序逐个）
② 兼职记录的底层业务头 FOR UPDATE（按 ID 升序） → 兼职申请头 FOR UPDATE（按 ID 升序）
```

## 13. 分批实现计划（每批 ≤ 1500 行含测试；可独立合并、对外自洽）

原则同 R2-T03 §18：行数只排除生成物（F-039 基准 / 摘要、迁移 `meta/` 快照与 `_journal`、标准授权指纹与 HISTORY）；PT-1 是契约 PR，先单独合并（AGENTS §3-3）；按 DEC-249② 兼职流转同时只放 1 个 PR，批次串行；每批开工前 `pnpm merge:main`，推送前只跑 `pnpm lint && pnpm typecheck` 与本批测试文件（DEC-351）。**自洽边界**：任何批次合并后，系统里都不会出现“兼职存在但离职不结束它 / 组织能被停用 / 通用接口能改它”的状态——因此“离职结束兼职、停用计数、删除探针”与第一个能写出兼职的批次（PT-3）一起交付，“作废兼职申请、在途申请计数”与第一个能写出申请的批次（PT-4）一起交付。
