## 1. SP-01 身份（R4-01；A-12 / A-14；以 T05 为准）

| 身份 | 谁 | 职责 | 检查时点 | 失效时（码见 SP-14） |
|---|---|---|---|---|
| 源读取主体 | run 头 `principalUserId` = T04 显式授权的系统主体（T04 设计 §4.1） | 冻结源数据；每次执行、每页、每次重试前经 `authorizeSourceRead` 复核当前授权（SP-07） | T04 冻结时；T05 P0 与每页 | `PRINCIPAL_UNAVAILABLE { principal: 'source' }` |
| 项目所属人 | run 头 `ownerUserId` = `projects.owner_id`（**不是触发人**，A-14） | 前置条件：仍是有效成员、持 TalentReview 身份与本项目 `sync` 按钮 | T04 冻结时（失效 → 409 不建 run）；`authorizeSourceRead` 每次复核 | `OWNER_UNAVAILABLE` |
| 原触发人 | run 头 `actorUserId` | ① T04 入口：`sync` 按钮 + 所选对象在其管理范围（冻结时）；② **T05 第一次计划时**：本 run 的**完整实际目标集合**（提名目标 ∪ 范围内 `delete_only` 目标 ∪ `org_health` 目标）须 ⊆ 其当前继任写范围（继任记录新建 / 修改、健康度结果修改的数据范围，按对象所属应用解析） | ① 冻结时；② 第一次成功计划的事务内，**只做一次**；计划封存（SP-10）后不再复核 | ① 入口 403 / 404；② `ACTOR_SCOPE_EXCEEDED`（必须新建 run） |
| 目标写入主体 | T05 继任侧系统主体（`succession.system_principal_user_id`） | 执行全部目标写入 | T05 P0 与每页 | `PRINCIPAL_UNAVAILABLE { principal: 'write' }` |
| 显式重试 / `/sync` 调用人 | 调用 T05 `retry` 或 `POST /sync` 的用户 | 入口授权：本次将执行的目标（重试 = `pending ∪ (failed ∧ retry_same_run)`）须 ⊆ 其当前范围；不替代原触发人 | 每次调用 | 入口 403 `BATCH_SCOPE_EXCEEDS_REQUESTER`（不进批次、不写回执） |

- **触发人不是目标写入主体**。执行中撤销触发人的权限不影响已封存计划；撤销目标写入主体的权限 → 页回滚、保留计划可恢复（SP-14 A 类）。
- outbox 驱动没有调用人，只做原触发人的首次计划检查；`/sync` 与重试两项检查都要满足。
- T04 冻结时不预检目标（它不知道 `delete_only` / 健康度目标），由 T05 首次计划承担。

## 2. SP-02 run：触发、冻结、业务日期、事件（A-03 / A-04）

| 项 | 规则 |
|---|---|
| 触发 | **只有手动**：T04 项目页“同步数据 → 同步继任信息”勾选对象后 `POST /projects/:id/sync`，`trigger = 'sync_requested'`（事件枚举唯一值，DEC-306②）。项目进行中或已结束都可；项目结束、校准会结束**不**触发（🟡）。消费方收到其他枚举 → `UNSUPPORTED_TRIGGER`（必须新建 run），不预留自动分支 |
| `manualOverride` | 命令显式参数，缺省 false：false → `in_flow` 对象 `syncEligible = false`（SC-R15）；true → `in_flow` 对象 `syncEligible = true` 且只带已填提名行。消费方只看 `syncEligible / blockReason` |
| 冻结内容 | 对象结果（字段按源读取主体字段权）、逐提名行、健康度行、`excluded` 计数；`sourceSeq` 仅说明。冻结时 T04 为每个已登记消费方（当前 `succession`；T06 上线后加 `talent_pool`）的每个 `nomination / object / org_health` 行**预建 `pending` 回执** |
| `businessDate` | **非空**，冻结时固定 = 项目 `business_date ?? 冻结日租户本地日期`，跨日分页与重试不变。消费方不得再用计划日回退（T05 删 S:404 的 `?? 计划时租户本地日期`） |
| 事件 | outbox `{ runId, projectId, trigger, principalUserId, actorUserId, ownerUserId, scopeExplicit, businessDate }`，与 run 同事务。消费方以 `runId` 为唯一快照身份，不依赖 `snapshotId / resultVersion / snapshotVersion` |
| 分次 | 每次 ≤ 500 个对象，分次 = 多个独立 run；两次手动同步互不取代 |

## 3. SP-03 覆盖范围（A-05）

`scopeOrgIds` 来自命令参数并冻结；给出（含显式空数组）→ `scopeExplicit = true`；未给 → `[]`、`scopeExplicit = false`。显式空数组 = “范围内覆盖”的范围是空集，消费方按空集处理、不扩大。消费方策略为 `overwrite_in_scope` 且 `scopeExplicit = false` → `SCOPE_REQUIRED`（必须新建 run；DEC-306⑤ 保守口径）；T04 命令阶段按当时租户开关预检 400（同码）。判定只看 `scopeExplicit`。

## 4. SP-04 版本与取代（A-03）

run 冻结后不可变。项目重启（T04）在同一事务内：run → `superseded`；本项目每个未 `completed` 的消费记录（无记录的按已登记消费方补建）→ `superseded`；全部非终态回执行（`pending`、`failed ∧ retry_same_run`）→ `superseded`。手动 run 只被“项目重启”取代。消费方读到 `superseded` 按 SP-13 停止。

- **选择器** `resolveReviewSource(employeeId | orgId, context)`：tier 1 = `triggerMeetingId` 给定时只取该校准会的会中对象（员工不在会中 → tier 2；会议上下文**不降级**为项目），否则 `triggerProjectId` 的对象；tier 2 = 当前项目：`status = in_progress ∧ period_start_date ≤ asOf` 中按 `coalesce(business_date, period_start_date)` 最近者（并列 `code` 小者）；tier 3 = 最近一次盘点：`status = ended ∧ period_end_date ≤ asOf` 中 `period_end_date` 最近（并列 `period_start_date` 最近，再 `code`）。`terminated` 对象不计。
- **绿化率**按组织（行政子树内员工为对象）用同一选择器；分母 0 或缺参考九宫格 → `rate = null`（消费方显示“--”、条件行不满足，DEC-305④）。
- **继任读取**（A-19）：`module_absent`（对象所用模板版本都没有继任模块）与 `value + []`（有模块、零提名）分开；消费方对后者按人数 0 处理，不跳过等级。
- 健康度状态：`not_provided` = 盘点侧没有该组织的行（消费方不动旧值）；`empty` = 有行但等级为空（同步清空）；`manual` = 手动值。
- `direction = target` 行照常进 run；是否写正式继任记录 🟡（T04 Q-T04-10，保守：消费方回执 `skipped`）。
- 无 run 的读取按 `viewer` **当前**授权逐字段 / 逐来源 / 逐组织返回 `forbidden`。

## 7. SP-07 源读取授权（A-18）

- **只冻结数据，不冻结权限**。`authorizeSourceRead` 在每次执行开始、**每页事务内**、每次重试前调用，按 run 的 `principalUserId` 当前授权，对本页**实际使用的内容**逐项复核：对象（项目可见 ∧ 人员范围）、字段（每个将被消费的盘点字段的查看权）、外部来源（对象 `source_refs` 指向的子集对象 / 360 结果的查看权）、组织（健康度行的组织范围）。
- 逐项撤权 → `forbidden` 明细；消费方对相应行写 `failed`，码 `SOURCE_REVOKED`，`errorParams.scope ∈ {object, field, source, org}`、`ref` = 被撤权的对象 / 字段 / 来源 / 组织；**行级永久**（不是缺字段、不是空值、不继续消费冻结值）。v4 草案与 T05 的 `SOURCE_FORBIDDEN` 一律并入 `SOURCE_REVOKED { scope: 'field' }`，不再出现。
- 整 run 不可读（`ok = false`）→ 码取 `reason`，按 SP-14 处理（保留计划可恢复）。`runStatus = superseded` → 按 SP-13 停止。

## 8. SP-08 消费记录、执行序号与 T04 消费租约（A-10）

| 概念 | 规则 |
|---|---|
| 消费记录 | 唯一 (runId, consumer)；状态 `running → completed / aborted / superseded`；终态不可逆 |
| 执行序号 | `beginConsumption`：无记录 → 建 `executionNo = 1`、`running`、租约 `(leaseOwner, leaseUntil)`；有 `running` 且租约未过期 → 409 `CONSUMPTION_LEASED`；**租约已过期 → 接管**：`executionNo + 1`、新 `leaseOwner`、新租约；终态 → 返回终态（调用方按 SP-13 停止） |
| 续租 | `renewLease` 只对当前 `executionNo ∧ leaseOwner` 生效，否则 `EXECUTION_INACTIVE` |
| 旧执行失效 | 接管后旧执行的 `renewLease / assertExecutionActive / registerTargets / recordOutcome / completeConsumption / abortConsumption` 一律 `EXECUTION_INACTIVE`；旧 worker 停止，不写任何东西 |
| 职责边界 | T04 租约**只**决定“哪个执行可以对本 run 写回执、谁是旧 worker”；它按 (run, consumer) 计，**不**阻止另一个 run 的消费者同时运行，也不替代 SP-09 |

## 9. SP-09 T05 批次互斥（R4-04；两层职责并存；DEC-336）

| 层 | 键 | 管什么 | 不管什么 |
|---|---|---|---|
| T04 消费租约（SP-08） | (runId, consumer) | worker 存活、执行序号、旧 worker 失效、回执写入资格 | 跨 run 的先后 |
| T05 批次互斥（`succession_sync_mutex`，主键 `tenant_id`，列 `batch_id`、`acquired_at`） | tenant | 同一租户同一时刻**只有一个批次**处在“计划 → 执行 → 终态”之间；保证两个 run 不会为同一目标冻结相同 `old_record_ids` 并各自覆盖 | worker 存活与执行序号（全部交给 T04 消费租约；互斥行不设过期、不记执行号） |

T05 义务（DEC-336：采用 T05 的批次互斥模型）：
1. **计划事务取互斥在 `beginConsumption` 之前**：先 `SELECT … FOR UPDATE` 互斥行；被**另一个未到终态的批次**持有 → 本 run `BATCH_IN_PROGRESS`（A 类：整事务回滚，不调 `beginConsumption`、不写计划，T05 本地记 `waiting`）；空闲或持有者已终态 → 写入本批次再 `beginConsumption`。
2. **互斥由批次持有，不设过期**：worker 失效只影响 T04 消费租约；接管经 `beginConsumption`（`executionNo + 1`）完成，**不碰互斥行**；不得在原批次未到终态时把互斥给别的批次。
3. **释放时点**：只在批次的**终结事务**里释放——完成（`completeConsumption`）、终止 / 取代（SP-13）、拒绝（C 类）；计划前失败时计划事务整体回滚，互斥随之不持有。
4. **页事务不取互斥行**：执行页第一步是 `assertExecutionActive`；终结一定改变消费记录状态，断言已覆盖。
5. **锁序**（无环）：计划事务 = 互斥 X → 消费记录（`beginConsumption`，X）→ 目标锁；终结事务 = 互斥 X → 消费记录 X（`completeConsumption / abortConsumption`）→ 本地计划行；执行页 = 消费记录 S → 员工 S → 目标锁 → 记录行；T04 项目重启 = 消费记录 X（不取互斥）。**完成不在最后一个执行页内做**，而在其提交后的独立终结事务里做（零执行目标时可在计划事务末尾直接完成，锁序同样是互斥 → 消费记录）。
6. 原 `succession_sync_leases` 与“每页条件更新互斥行、`LEASE_LOST`”的写法删除；worker 失效一律表现为 `EXECUTION_INACTIVE`。

## 10. SP-10 目标登记与封存（A-20；R4-03）

- 消费方在**第一次成功计划**的事务内（取互斥 → `beginConsumption` → 目标锁 → 读 `old_record_ids` → 写本地计划之后、提交之前）调用一次 `registerTargets`，这一次调用就是**计划提交**，原子完成三件事：
  1. 登记并**封存**实际执行集合里的全部 `org / position` 目标（`append / overwrite / scope_overwrite / delete_only`，含无提名的 `delete_only`）：T04 为每个目标建 `target` 回执行（`rowId = targetKey`、`pending`），消费记录 `targetsSealed = true`、`targetCount = n`。健康度目标沿用冻结时已预建的 `org_health` 行，不重复登记。零执行目标登记空集。
  2. 写入 `planOutcomes`：计划阶段已经确定终态的行（可为空），包括计划校验失败或跳过的提名行、全部提名都已终态的对象行、**没有提名的对象行（`skipped`）**、**`not_provided` 的 `org_health` 行（`skipped`）**、计划阶段失败的健康度行。全部成功、只等执行的计划 `planOutcomes` 为空。
  3. 写一条 `PageCommit { kind: 'plan', pageNo: 0, pageCommandId: ${runId}:${consumer}:${executionNo}:0 }`，作为“计划已提交”的证明；它**不表示**任何业务目标已执行。
- **两种证明分开**：“计划已提交” = `targetsSealed` ∧ 存在 `kind = 'plan'` 的 `PageCommit`；“某目标已执行” = 该 `target`（或 `org_health`）行终态，且其 `pageCommandId` 对应一条 `kind = 'execute'` 的 `PageCommit`。
- 同一 `planCommandId` 且内容（目标与 `planOutcomes`）相同 → 幂等返回首次结果；已封存后内容不同或换 `planCommandId` → 409 `TARGETS_ALREADY_SEALED`。
- 重试、接管都**不重新登记**（计划不重建）；新执行看到的是同一封存集合。
- `targetKey` 稳定：`org:<orgId>` / `position:<positionId>`（规范化小写 UUID）；`nominationIds` 只作说明，提名行仍有各自的 `nomination` 回执。
- 未封存时，`recordOutcome`、`completeConsumption` → 409 `TARGETS_NOT_SEALED`；计划事务内调用 `assertExecutionActive` 时传 `requireSealed: false`，其余一律缺省 `true`。

## 11. SP-11 页事务与提交证明（A-15；R4-03）

- 页命令身份 `pageCommandId = ${runId}:${consumer}:${executionNo}:${pageNo}`；计划页 `pageNo = 0`（SP-10），执行页 `pageNo ≥ 1`。
- **三个事务边界**（R5-01 / 第 6 轮 P3）：
  1. **执行前续租**：每页开始前一个**独立短事务** `renewLease`（消费记录 `FOR UPDATE`，提交即放）；续租失败 → `EXECUTION_INACTIVE` / `RUN_SUPERSEDED`，不开执行页。续租时长须覆盖一页的执行时间。
  2. **执行页**：见下一条；页事务内不再续租。页执行中租约到期时，接管者的 `beginConsumption` 要取消费记录 X 锁，会等本页（持 S 锁）提交后才生效，所以已开始的页按自身提交顺序有效，之后旧执行的下一次续租或断言失败。
  3. **独立终结**：最后一个执行页提交后，另起事务：批次互斥 X → 消费记录 X → `completeConsumption`（或 SP-13 的终止）→ 本地清理 → 释放互斥。完成**不在执行页内做**；零执行目标的计划事务可在末尾直接完成（同一锁序）。
- **每个执行页**一个事务，顺序固定：`assertExecutionActive`（第一步；对消费记录取 `FOR SHARE`，断言 `running ∧ 本 executionNo ∧ 本 leaseOwner ∧ 租约未过期 ∧ run 未 superseded ∧ targetsSealed`）→ 业务写入 → `recordOutcome` → 提交。页事务不取 T05 互斥行（SP-09）。
- 执行页的 `recordOutcome.items` **不得为空**，且必须包含本页处理过的每个目标的 `target` 行终态（健康度目标为 `org_health` 行）；提名行与对象聚合行在其终态确定的那一页写入；T04 在同一事务写 `PageCommit { kind: 'execute' }`。所以“只做删除”的页也有本页的 `target` 行和 `PageCommit` 作为证明。
- **结果未知**（计划页或执行页）：一律调 `getPageCommit(pageCommandId)`。**存在且 `executionNo` 等于当前执行**才证明该页已提交；不存在 → 未提交，在当前执行内用同一 `pageCommandId` 重做；已被接管 → 由新执行以新页命令重做。旧执行留下的终态行或 `PageCommit` 都不能证明当前页。消费方不得另用“端口行回执 + 本地目标行”等第二套证明。

## 12. SP-12 行幂等键、回执状态、完成门槛（A-11 / A-20）

| 项 | 规则 |
|---|---|
| 行幂等键 | (runId, consumer, rowKind, rowId)；`rowKind ∈ {nomination, object, org_health, target}` |
| 允许的状态转换 | `pending → synced / failed / skipped`；`failed(retry_same_run) → synced / failed / skipped`（更新最新状态 + 追加历史，含旧 `pageCommandId`）；`synced / skipped / failed(none)` 为终态，同值重写幂等，异值 409 `ROW_FINAL`；`superseded / aborted` 只能由 T04 在 SP-04 / SP-13 写 |
| 完成门槛 | `completeConsumption` 要求：`targetsSealed` ∧ 四类行（含全部 `target` 行）都非 `pending` ∧ 没有 `failed ∧ retry_same_run` 行；否则 409 `TARGETS_NOT_SEALED` / `PENDING_ROWS_REMAIN` / `RETRYABLE_ROWS_REMAIN`。“已有回执” ≠ 完成 |
| 回执聚合 | 提名行：`created / updated / exists` ⇒ `synced`；计划或执行失败 ⇒ `failed`；`target` 方向、终止对象 ⇒ `skipped`。对象行：全部提名 `synced / skipped` ⇒ `synced`；任一失败 ⇒ `failed`，码 `NOMINATIONS_FAILED { codes, nominationIds }`（SP-14 R10）；全部 `skipped` ⇒ `skipped`；**没有提名行的对象**在计划提交（`planOutcomes`）里写 `skipped`。`target` 行：目标 `done` ⇒ `synced`；失败 ⇒ `failed` + 码 + `recovery`。`org_health` 行：写入 ⇒ `synced`；`not_provided` ⇒ 计划提交里写 `skipped`。消费方本地保存 `retryable` 布尔时，经端口适配为 `recovery`（`true → retry_same_run`，`false → none`） |
| 计数 | `ConsumptionState.counts` 含四类行；盘点侧页面按查看人范围逐行过滤后另计（T04 §6.6） |

## 13. SP-13 终止与取代（R4-02）

| 情形 | 谁调用 | 消费记录 | 剩余回执（非终态：`pending`、`failed ∧ retry_same_run`） | T05 计划与屏障、互斥 |
|---|---|---|---|---|
| 项目重启（取代） | T04（SP-04） | `superseded` | T04 全部改 `superseded` | T05 在下一次 `assertExecutionActive` / `authorizeSourceRead` 得知 → 未终态目标 `aborted`、屏障释放、互斥释放；**不调** `abortConsumption`（已终态，调用幂等返回终态） |
| 管理员终止（T05 `abort`） | T05：`abortConsumption(executionNo = 当前序号, code = 'ABORTED_BY_ADMIN', recovery = 'terminate')`，租约是否过期都允许 | `aborted` | T04 全部改 `aborted`，码同上 | 同一事务：未终态目标 `aborted`、屏障释放、互斥释放 |
| 计划前判定必须新建 run（SP-14 C 类） | T05：计划事务回滚后，新事务 `abortConsumption(executionNo = null, code, recovery = 'new_run')`；仅当该 run 尚无消费记录时允许 `null`。**不得先写失败回执**（此时未封存，`recordOutcome` → `TARGETS_NOT_SEALED`） | 建记录即 `aborted`（`terminalRecovery = new_run`） | T04 把四类预建行全部改 `aborted`，码同上 | 未建计划、无屏障；互斥随计划事务回滚而不持有 |

- 已提交页不回滚；终止后对本 run 的 `retry` → T05 入口 403 `RUN_NOT_RETRYABLE`。
- `abortConsumption` 对已终态记录幂等返回终态，不改码。

## 14. SP-14 公共错误码与三类恢复动作（A-17；R4-02）

**恢复动作**（取代单一 `retryable` 布尔）：

| 类 | 名称 | 消费记录 | 计划与屏障 | 怎么继续 |
|---|---|---|---|---|
| **A** | 保留计划、可恢复（`retry_same_run`） | 保持 `running`（计划前失败时整事务回滚，T04 侧无记录） | **计划前**：未建计划、未登记目标、无屏障。**计划后**：T05 `pending ∪ failed ∧ retry_same_run` 目标继续作为屏障；T04 `target / org_health` 等未终态行保持；批次互斥仍归本批次 | 同一执行：续租后下一页继续。worker 失效：等 T04 租约过期，由重试 / outbox 重投经 `beginConsumption` 接管（`executionNo + 1`），只跑未终态与 `failed ∧ retry_same_run` 目标；计划前失败的 run 重新走 P0 / P1（首次计划检查在那次成功计划时做） |
| **B** | 不可恢复终止（`terminate`） | `aborted` / `superseded` | 未终态目标 `aborted`，屏障与互斥在同一事务释放 | 本 run 不可再执行；已提交页保留。被取代时由用户在重启后的项目上重新同步（新 run） |
| **C** | 必须新建 run（`new_run`） | `aborted`（`terminalRecovery = new_run`） | 只可能发生在**首次计划成功之前**：无计划、无屏障 | 冻结内容或原触发人授权本身不合格，**不能修改旧 run 后重试**；修正配置 / 范围 / 授权后在盘点侧重新发起同步 |

另有两种行级结果：**行永久**（行 / 目标 `failed`、`recovery = none`，批次继续，计入 `partial`）与**行可重试**（行 / 目标 `failed`、`recovery = retry_same_run`，阻止完成，按 A 类在同一 run 重跑）。

**回执组合表**（穷举；R5-01）：回执行只能取下表列出的 (rowKind, 状态, 码, 阶段, recovery) 组合；“阶段”= 写入它的提交——计划 = `registerTargets.planOutcomes`（`PageCommit.kind = 'plan'`），执行 = `recordOutcome`（`kind = 'execute'`），终止 = T04 在 SP-04 / SP-13 收尾。`registerTargets` 与 `recordOutcome` 在写入前按本表校验，组合不在表内 → 409 `OUTCOME_NOT_ALLOWED`（协议违例，整调用不写）。**契约测试按组合逐条断言**（每个允许组合写入成功；同码换 rowKind / 阶段 / recovery 被拒），不只检查码字符串。

| # | 码（或状态） | 允许的 rowKind | 阶段 | recovery | 何时写、向谁传播（以 T05 逐行失败映射为准，S:480～487） |
|---|---|---|---|---|---|
| R1 | `SUBJECT_IN_PROCESS` | `nomination` | 计划 | `none` | 对象 `in_flow` 且未 `manualOverride` |
| R2 | `READINESS_UNKNOWN` | `nomination` | 计划 | `none` | 准备度映射不到 |
| R3 | `SUCCESSOR_NOT_ACTIVE`、`READINESS_DISABLED` | `nomination` | 计划 / 执行（锁内重验） | `none` | 坏提名自身；若它所在目标是 `overwrite / scope_overwrite`，同目标其余提名与目标行按 R5 写 |
| R4 | `TARGET_NOT_FOUND`、`TARGET_OUT_OF_SCOPE`；`TARGET_NOT_KEY_POSITION` **仅限 `position:` 目标** | `target`、`nomination` | 计划 / 执行 | `none` | **继任目标（`org:` / `position:`）的目标级原因**：目标行与它全部 `planned` 提名写同一码（执行期为整目标保存点回滚，回执写在保存点外） |
| R4a | `TARGET_OUT_OF_SCOPE` | `org_health` | 计划 / 执行（锁内重验） | `none` | **健康度目标的写入范围不足**：继任侧系统主体（目标写入主体）对该组织的健康度结果写入范围不覆盖或被收回，而源读取授权仍有效。该组织旧健康度不变、手动标记不变；同页其他目标照常写入。源读取授权也失效时按 R7 记 `SOURCE_REVOKED { scope: 'org' }`，不记本码（先判源授权，再判写范围） |
| R4b | `TARGET_NOT_FOUND` | `org_health` | 计划 / 执行（锁内重验） | `none` | **健康度目标的组织不存在**：组织在 `businessDate` 无有效版本（未生效、已撤销或已删除）；旧健康度不变 |
| R5 | `TARGET_PARTIAL_NOMINATIONS { causeNominationIds }` | `target`、`nomination` | 计划 / 执行 | `none` | 覆盖类目标中有坏提名（R3 / R6）：目标行与**其余合法提名**写本码，旧集合保持（Q-SC-15 暂按 B） |

## 16. SP-16 健康度回写凭据与逐组织 CAS（R4-05；DEC-311、DEC-305④）

| 凭据 | 服务端授权（回写事务内） | 版本 | 手动标记 |
|---|---|---|---|
| `compute` | 系统主体持 `TalentReview.OrgHealth` update 权 + 组织在其范围；项目 `ended` → 该行 `PROJECT_ENDED` | 每行 `expectedRevision` CAS | 当前 `manual = true` → `MANUAL_KEPT`（优先于版本判断）；否则写等级、`method = computed` |
| `assign` | 用户持 `OrgHealth.assign` 按钮 + `levelId` 字段编辑权 + 组织范围 + 项目未结束 | 每行 `expectedRevision` CAS | 写等级、`manual = true`、`method = manual` |
| `reset` | 用户持 `OrgHealth.reset` 按钮 + 组织范围 + 项目未结束 | 每行 `expectedRevision` CAS | **原子**：同一条写入写重算等级 + `method = computed` + `manual = false`（DEC-305④） |
| `import` | **延期（F-050，DEC-311②）** | — | — |

执行规则（三种凭据相同）：
1. `context = { projectId, meetingId }` 完整定位健康度行（唯一键 (tenant, project, coalesce(meeting, 空), org)）；`reset` 与 `assign` 同样必带 `meetingId`（项目级为 `null`）。
2. 按 `orgId` 升序对行 `FOR UPDATE`（无行时对 (project, meeting, org) 取咨询锁后插入）；**锁内 CAS**：当前 `revision ≠ expectedRevision` → 该行 `REVISION_CONFLICT`，**当前等级与手动标记保持不变**，回执带 `currentRevision / currentLevelId / currentManual`（前端提示“已被他人手工修改，刷新后重试”，DEC-311）；相等 → 写入、`revision + 1`、`written_by = { kind, user | principal, commandId }`。
3. 逐行回执（DEC-067 批量逐条）；`commandId` 进命令台账：同键同内容幂等返回首次回执，同键异内容 409。
4. **版本从哪里读**：调用方用本端口 `readOrgHealthRows({ context, orgIds, viewer })` 读取**目标项目 / 会议健康度行**的当前 `revision`（无行 `revision = 0`）；`viewer` 为用户时按其读权（项目可见 ∧ 组织在范围）返回；无权 → `status = 'forbidden'` 分支，类型上不带 `revision`、存在性与等级值；有权但无行 → `status = 'absent'`、`revision = 0`；计算凭据用 `{ kind: 'principal' }`。**不得**用 T05 本地 `succession_health_results.revision`、run 冻结的 `SyncOrgHealth` 或地图结果的版本代替。
5. 重置流程：调用方先读各行 `revision`，以 `compute` 端口算出新等级，再带这些 `expectedRevision` 调 `resetOrgHealth`；重算期间有人手工赋值 → 该行 `REVISION_CONFLICT`，手工值保留。与 T05 S:112 的逐对象 `expected_revision / revision_conflict` 同义。
6. “项目可见”只给读权，不给任何写权。
