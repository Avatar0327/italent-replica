# F-061 存量租户标准身份授权补装：方案

> 任务：F-061（DEC-340④；DEC-361 改为接入通用种子补装登记表）。本文只出方案，实现另派 Sonnet（DEC-338）。
> 依据：`DEC-361_种子补装登记表.md`；#160（a849083，`apps/api/src/seeds/registry.ts`）；
> `R3-T02_实现拆分方案.md` 第 8 节（#164 定稿的“授权补装台账”）；`apps/api/src/modules/permission/standard-profiles.ts`。
> 状态：方案稿 v2（按 #175 首轮审查修订，改动见第 11 节）。第 9 节 4 个产品决定未定；各 PR 等哪一项见第 7 节。

## 0. 一句话

把“标准身份”分两层登记进 #160 的登记表：**身份本身**（缺整个身份时补装，沿用 DEC-289③）和**身份上的每一项授权**
（应用、对象、数据操作、字段、按钮、预置看全部）。授权层配一张平台通用的**只追加台账**，记下平台装过的、回补时已存在的、租户保存时动过的、
因历史不明而保守不补的项；只补“当前没有、台账也没有”的项，所以租户撤销过的不会被补回来。
另记一个不随审计保留期消失的“对象被租户改过”标记，供首次接管判断。C1-2 的员工身份授权共用这张台账。

## 1. 现状

### 1.1 标准身份怎么装上去

| 环节 | 代码 | 行为 |
|---|---|---|
| 身份定义 | `packages/domain/src/platform/standard-presets.ts` 的 `STANDARD_PROFILES` | 12 个身份（组织员工 3 个 HR 身份、经理、人才标准、盘点、继任 3 个、360 3 个）。对象权限**从对象目录推导**：`full(def)` = 全部字段可见、非系统字段可编辑、全部按钮与数据操作；`readOnly(def)`；`partial(def, ops, buttons)`；360 身份显式排除部分按钮 |
| 开通安装 | `installStandardProfiles` → `installProfile` | 逐个身份写 `permission_profiles`（`source='standard'`）、`_apps`、`_objects`、`_fields`、`_buttons`；按 `hr` / `seeAll` 预置看全部（`presetSeeAll`：范围行、范围版本、审计）；每个身份一条 `permission_profile.provision` 审计 |
| 开通顺序 | `platform/provisioning.ts` | 先 `installStandardProfiles`（返回身份 id 给首位管理员授予），最后在同一开通命令里调 `installMissingSeeds`（#160） |
| 存量补整个身份 | `installMissingStandardProfiles`，`POST /api/platform/tenants/:tenantId/standard-profiles/backfill`（#117，DEC-289③） | 只补租户里**没有该编码**的身份；同编码已是标准身份 → `ALREADY_INSTALLED`；租户手工建过同编码 → `CODE_TAKEN`，不覆盖、不合并。**不补已装身份上缺的对象 / 字段 / 按钮** |
| 租户改对象权限 | `permission/profiles.ts#setObjectPermission`（`PUT /profiles/:id/objects/:objectCode`） | 身份行 `FOR UPDATE`、核 revision，按对象整体替换（删对象行，字段、按钮级联删，再重插），revision +1，写 `permission_profile.set_object` 审计。**全仓只有这一处推进身份 revision**；没有删除对象、改身份应用的路由，所以“对象行不存在”只会是“从未装过、从未保存过” |
| 租户改看全部 | `permission/scope-policy-service.ts#setIdentityScope` | 先取范围咨询锁 `identity-scope:<身份>:<应用>:<种类>:<目标>`，读身份**不加行锁**，再 upsert 范围行（revision 独立），写范围版本与审计 |
| 撤销的表达 | 同上 | 数据操作 = `can_*` 为 false；字段 = 行在但 `can_view` / `can_edit` 为 false，或行不在；按钮 = 行不在；看全部 = 范围行在但 `see_all=false` |
| 租户扩展字段 | `permission/tenant-catalog.ts#tenantObjectCatalog` | 任职、合同等对象在静态目录之外追加租户字段（`custom:<id>`、盘点 `field:<code>`），保存与鉴权都按扩展目录校验；超过 `TENANT_FIELD_LIMIT` 时一个都不追加 |

### 1.2 缺口

`STANDARD_PROFILES` 从目录推导，目录一加字段 / 按钮 / 对象，**新租户**开通就带上；**存量租户**的同一标准身份停在开通那天的目录，
#117 只补整个缺失的身份。存量租户的标准管理员看不到新字段、点不到新按钮，只能靠租户管理员逐个手工勾选（DEC-340④ 要求“不靠手动”）。

### 1.3 会给标准身份带来增量的来源（截至 2026-10-09）

| 来源 | 状态 | 影响的标准身份 | 增量 |

| R3-T04 B2～B7 | 未开工 | 同上 | 很可能继续加对象 / 按钮 |
| #173 R3-T02 P0 | open | 无（main 上没有标准身份引用评定对象） | 6 个流程对象与按钮；本身不装身份，**不产生存量缺口** |
| R3-T02 C1-2 | 未开工 | 新增 3 个标准身份；`employee_self_service` 追加发展通道授权 | 新身份走“补整个身份”；员工身份不在 `STANDARD_PROFILES`，走 C1-2 自己的登记项，**共用本方案的台账**（第 3.5 节） |

## 2. 总体结构

```
seeds/index.ts（import 顺序即执行顺序）
  └─ permission/standard-seeds.ts
       ├─ registerSeed permission/standard-profiles        codes = 身份编码；补整个缺失身份（#117 口径）
       └─ registerSeed permission/standard-profile-grants  codes = 授权项编码；只补缺失授权项
  └─ （C1-2）qualification/employee-profile-grants         共用同一台账表与登记函数
seeds/grant-ledger.ts      台账读写；租户补装锁 lockTenantSeeds（从 registry.ts 抽出，SQL 与锁键逐字不变）
permission/profiles.ts     setObjectPermission 保存登记（第 4.4 节）
permission/scope-policy-service.ts   setIdentityScope 锁序调整（第 4.1 节，PR-3）
packages/domain/src/platform/standard-grants.ts   授权项编码、解析、目录指纹（纯函数）
```

- **#160 通用接口不改**：`SeedEntry` 签名、`installMissingSeeds` 的流程与报告形状不动（#164 §8 约定）；只把锁语句抽成导出函数。
- 两个登记项同属模块 `permission`，按模块筛选时总是一起跑；`standard-profiles` 先登记，同一轮里先补整个身份、再补授权项。
- 旧路由 `standard-profiles/backfill` **保留**，响应不变（`AC-360-standard-profiles` 不改）；它只补整个身份，补授权项走 `seeds/backfill`。

## 3. 登记方式

### 3.1 授权项稳定编码

沿用 #164 §8 的格式，补上应用与看全部两类。编码只由身份编码与目录编码组成，不随租户改名变化。

| 种类 | 编码 | “当前已有”的判定 |
|---|---|---|
| 身份 × 应用 | `<身份>/app:<应用>` | `permission_profile_apps` 有行 |
| 对象 | `<身份>/<对象>/op:view` | `permission_profile_objects` 有行 |
| 数据操作 | `<身份>/<对象>/op:<create\|update\|delete>` | 对象行 `can_*` 为 true |
| 字段 | `<身份>/<对象>/field:<字段>:<view\|edit>` | 字段行在且 `can_view` / `can_edit` 为 true |
| 按钮 | `<身份>/<对象>/button:<按钮>@<层级>` | 按钮行在 |
| 预置看全部 | `<身份>/seeAll:<应用>:<entity\|datasource>:<目标>` | 范围行在且 `see_all=true`；**只有 D3 批准的目标进 codes**（PR-3） |

- 只有身份定义**授予**的项才进 `codes`：`readOnly` 不授予的按钮、`partial` 没列的数据操作、360 排除的按钮、系统字段的 `edit`、租户扩展字段，都不是编码，永远不补、也不动。
- 依赖关系：`app` → 该应用下对象的 `op:view` → 同对象的 `op:*`、`field:*:view`、`button:*`；`field:x:view` → `field:x:edit`。
- 台账另用两种**标记编码**（不在 `codes` 里，不会出现在报告的 `installed`）：
  - `<身份>/@ledger`：该身份已完成首次接管；
  - `<身份>/<对象>/@modified`：租户保存过该身份的该对象（第 4.4 节）。不随审计保留期（DEC-198）消失。
- `standard-grants.ts` 提供：`standardGrantItems(profiles)`（参数化，默认 `STANDARD_PROFILES`，供“旧版本升级”夹具注入旧定义）、`parseGrantCode`、
  `STANDARD_GRANT_CODES`、`STANDARD_GRANT_VERSION`、`STANDARD_GRANT_DIGEST`、`objectCatalogDigest(objectCode)`（PR-3 用）。

### 3.2 两个登记项

| 登记项 | `codes` | `existing` | `install(missing)` |
|---|---|---|---|
| `permission/standard-profiles` | 身份编码 | 租户里已有的身份编码（**不论 `source`**：手工同编码计入已有，即 `CODE_TAKEN` 不装） | 对每个缺失身份调 `installProfile`（装入即记账），再加入有效租户管理员的可授权身份；与旧路由同一实现 |
| `permission/standard-profile-grants` | `STANDARD_GRANT_CODES` | 第 4.2 节 | 第 4.3 节 |

### 3.3 授权补装台账（平台通用，取代 #164 §8 的 `qualification_seed_grant_installs`）

新表 `seed_grant_ledger`（新文件 `packages/db/src/schema/seeds.ts`，PR-1 契约落地）：

| 列 | 说明 |
|---|---|
| `tenant_id` | 租户；RLS 同其他租户表 |
| `entry` | 登记项 `module/key`，如 `permission/standard-profile-grants`、`qualification/employee-profile-grants` |
| `code` | 授权项编码或标记编码 |
| `source` | 见下表 |
| `command_id` | 平台命令或租户写命令 ID；`existing` 里的登记没有写上下文，留空 |
| `recorded_at` | UTC |

| `source` | 写入时机 | 含义 |
|---|---|---|
| `install` | 平台装入（开通、补整个身份、补授权项） | 平台装过；以后当前没有 = 租户撤销 |
| `adopted` | 每次回补的 `existing`：当前已有、台账没有 | 已存在的授权纳入管理；以后当前没有 = 租户撤销 |
| `tenant_saved` | 租户保存对象权限（第 4.4 节） | 租户动过：保存前或保存后授予过的项，及 `@modified` 标记；D2 = A 时还含面板上未勾的项 |
| `withheld` | 首次接管：历史不足以判断（第 5 节） | 平台不补；报告计入 `existing`；租户需要时手工勾 |

- 主键 `(tenant_id, entry, code)`；写入一律 `INSERT … ON CONFLICT DO NOTHING`，**第一次登记的来源为准**。
- 只追加：语句级触发器禁止 UPDATE / DELETE / TRUNCATE（同 `0003` / `0006` 的 `forbid_audit_mutation`，`--custom` 迁移）。
- 台账不参与鉴权；鉴权仍只读权限表。
- `seeds/grant-ledger.ts`：`readLedger(tx, entry)`、`recordLedger(tx, { entry, codes, source, commandId, now })`、`lockTenantSeeds(tx, tenantId)`。

**装入即记账**：`installProfile` 拆成 `installProfileRows`（只写权限行与审计）和 `installProfile`（行 + 全部授权项编码与 `@ledger` 以 `install` 记账）。
开通、旧路由、`standard-profiles` 登记项都调 `installProfile`；`installProfileRows` 只给“F-061 上线前租户”夹具用（第 7.1 节）。

### 3.4 version 与报告

- `version` 只用于报告，不参与缺失判断（#160 / #164 同口径）。目录增删授权项时 `STANDARD_GRANT_VERSION` +1。
- `STANDARD_GRANT_DIGEST` 记当前版本的编码指纹；守卫测试算出的指纹不一致即失败，提示“目录变了：version +1 并更新指纹”。
  任何改对象目录或 `STANDARD_PROFILES` 的 PR 都会撞到这条测试，审查方一眼看到“这个 PR 会给存量标准身份补授权”。
- 报告沿用 #160 形状：`installed` = 本次补装的编码；`existing` = 已有 + 台账已登记 + 不可装的个数，不细分原因，细节看审计与台账。

### 3.5 与 #164 §8（C1-2）统一口径

| #164 §8 原写法 | 本方案后的写法 |
|---|---|
| C1-2 自建 `qualification_seed_grant_installs` | 改用 `seed_grant_ledger`，`entry='qualification/employee-profile-grants'` |
| `source ∈ (install, adopted)` | 同一枚举，另有 `tenant_saved`、`withheld` |
| 三条登记路径（装入 / 开通 / 首次接管） | 不变，并改为**每次回补**都登记“当前已有、台账没有”（第 4.2 节）；由 `recordLedger` 统一实现 |
| `qualification/standard-profiles` 三个预置身份 | 直接加进 `STANDARD_PROFILES`，由本方案两个登记项覆盖，**不另起数据集** |
| 员工身份 `CODE_TAKEN` / 不存在 → 计入已有、不装 | 不变 |

**C1-2 依赖本方案 PR-2**（三个新身份要靠 `permission/standard-profiles` 给存量租户补，台账与保存登记也在 PR-1 / PR-2）。
拆分方案需要同步的内容见第 10 节，由总编排安排修订（本 PR 不改 `R3-T02_实现拆分方案.md`，避免与在途 #173 冲突）。

## 4. 回补流程

### 4.1 锁顺序（全部入口统一）

| 入口 | 顺序 |
|---|---|
| 开通、`seeds/backfill`、旧路由 | 租户补装锁（`lockTenantSeeds`）→ 标准身份行 `FOR UPDATE`（`existing` 第一步，按身份 id 排序）→ 补看全部时逐目标取范围锁 → 复读范围行 |
| 租户保存对象权限 `setObjectPermission` | 身份行 `FOR UPDATE`（现状） |
| 租户保存看全部 `setIdentityScope`（**PR-3 改**） | 身份行 `FOR UPDATE` → 范围锁 → 复读范围行 → 核范围 revision → upsert |

- 旧路由在 `installMissingStandardProfiles` 开头补调 `lockTenantSeeds`，消除它与 `seeds/backfill` 同时装同一身份撞唯一约束的 500。
- `setIdentityScope` 现状是先范围锁、读身份不加行锁；回补持身份行锁后插范围行时，与租户插同一范围行（外键检查要对身份行取共享锁）形成互等，
  真 PG 可复现 40P01。PR-3 把身份行锁提到最前，两条路径都按“身份 → 范围”加锁，不再有环；只加 `ON CONFLICT` 不能消除互等。
- 范围锁键：回补与 `setIdentityScope` 共用一个导出函数，租户 ID 按 `(tenantId::uuid)::text` 规范化（平台入口可能传大小写不同的同一 UUID，#160 同类问题）。
- 回补推进身份 revision：等待中的租户对象权限保存按 revision 不一致返回 409，客户端刷新后重提（AGENTS §10）。看全部有自己的 revision，回补只在改了同一范围行时让租户保存 409。

### 4.2 `existing`（授权层，每次回补都执行）

对 `STANDARD_PROFILES` 每个身份：

1. 租户里没有该编码，或该编码是手工身份（`source='custom'`）→ 该身份全部编码计入“不可装”。不读、不写手工身份的任何权限。
2. 读当前权限（应用、对象、字段、按钮；PR-3 起含看全部范围行）得到“当前已有”。
3. 没有 `@ledger` 标记 → 先做首次接管（第 5 节）。
4. **持续登记**：当前已有、台账没有的编码登记 `adopted`（不论是否首次）。以后租户撤销，这些项“台账有、当前无”，不补。
5. 返回 当前已有 ∪ 台账已登记 ∪ 不可装。“不可装”还包括：父项“台账有、当前无”（租户撤销过）的子项；范围行在但 `see_all=false` 的看全部。

不可装的子项**不记账**：将来租户自己恢复父项，那次保存会按第 4.4 节登记；未登记的才会被下一次回补当缺失补上。

### 4.3 `install(missing)`（授权层）

按身份分组，每个身份：

1. 记下受影响对象改动前的权限（`loadObjectPermissions`）；
2. 按依赖顺序写：插应用行 → 插对象行（数据操作取同批缺失的 `op:*`）→ 已有对象把缺失的 `can_*` 置 true → 字段行 upsert（只把缺失的标志置 true，另一标志不动）→ 插按钮行 → 看全部（PR-3）：取范围锁、复读，仍不存在才按 `presetSeeAll` 写范围行、范围版本、审计；
3. **只增不删**：原有行（含租户扩展字段 `custom:<id>` / `field:<code>` 的授权）一律不删不改；
4. 写完后对受影响对象按**租户扩展目录**重验：`tenantObjectCatalog(tx, objectCatalog, objectCode)` + `validateObjectPermission` + `isWithinProfileApps`，不合法即抛错、整笔回滚。
   扩展字段超过 `TENANT_FIELD_LIMIT` 时扩展目录不含租户字段：只校验本次新增项，原有扩展字段行原样保留、不参与校验（与鉴权“超限一个都不追加”同口径，不因此让整笔回补失败）；
5. 身份 revision +1（`UPDATE … WHERE revision = 读到的值`，0 行即抛错回滚）；
6. `recordLedger(source='install', commandId)`；
7. 每个身份一条租户审计 `permission_profile.backfill_grants`（`auditAs`，同事务写 outbox）：`before` / `after` = 受影响对象的权限与应用、新补的看全部键、revision。

持有该身份的用户下一次请求即获得新权限（服务端每次请求重新算权限，无需清缓存）。

### 4.4 租户保存登记（`setObjectPermission`，PR-2 起生效，不依赖 D2）

身份行 `FOR UPDATE` 之后、同一事务：若身份 `source='standard'` 且 `STANDARD_PROFILES` 里该身份含此对象，以 `tenant_saved`（`command_id` = 本次写命令）登记：

1. `<身份>/<对象>/@modified`；
2. 该对象的标准编码中，**保存前或保存后为已授予**的项（保存前 ∪ 保存后）。保证“租户授过、后来撤销”的项无论回补是否跑过都不会被补回；
3. **D2 = A 时（PR-3）**：面板上可见但未勾的项。只有请求携带的对象目录指纹 `catalogDigest`（GET 身份详情按对象返回 `objectCatalogDigest`）
   与服务端当前一致时才登记；不一致返回 409 `CATALOG_CHANGED`，要求刷新后重提；请求未带指纹（旧客户端）时只做第 1、2 步，不把未展示的新项当拒绝。

## 5. 首次接管（已上线租户）

F-061 上线前开通的租户台账为空。接管按身份进行（以 `@ledger` 判断，不按“台账是否为空”：旧路由新装的身份、租户保存登记都会让台账非空）。
目的只有一个：把“当前没有”的项分成“可以放心补”和“历史不足以判断、保守不补”。当前已有的项由第 4.2 节第 4 步登记 `adopted`。

**审计历史是否完整**：上线前只有 `setObjectPermission` 推进身份 revision，每次一条 `permission_profile.set_object` 审计。
`set_object` 审计条数 = revision − 1 → 完整；少于 → 有审计已过保留期（DEC-198 整条清理），历史不完整。
审计过期只会让结论从“完整”变成“不完整”，不会反过来，所以判断是单向保守的；不需要上线迁移回填。

对每个未接管的标准身份、身份定义里的每个对象：

| 情形 | 判定 | 当前没有的项 |
|---|---|---|
| 身份 revision = 1 | 确认从未改过 | 缺失，补 |
| 对象行不存在 | 确认未保存过（无删除对象路由） | 缺失，补（#148 的 4 个新对象属此类） |
| 有 `@modified` 标记，或有该对象的 `set_object` 审计 | 确认改过 | **D1**：A 登记 `withheld` 不补（推荐）；B 补 |
| 无标记、无审计、历史完整 | 确认未改过 | 缺失，补 |
| 无标记、无审计、历史不完整 | **历史不足以判断** | 登记 `withheld`，不补（固定保守，见 D1 说明） |

应用项：身份不能改应用，当前没有的应用项只可能是定义新增，补。看全部（PR-3）：范围行在且 `see_all=false` → 不可装；范围行不在 → 缺失（是否在 codes 里由 D3 定）。
最后写 `@ledger`（`adopted`）。接管只登记、不改权限、不写业务审计（#164 §8 同口径）；平台审计的回补汇总可见这次命令。
`withheld` 项进报告的 `existing`，可从台账查到；租户管理员在身份管理里手工勾选即可，勾选后按第 4.4 节登记。

运维建议：F-061 PR-2 上线后尽早对全部存量租户执行一次 `seeds/backfill`，减少因审计继续过期落入“历史不完整”的对象。
#160 只在持锁后调 `existing`，接管在锁内；若 #160 日后加只读预览，接管与持续登记要移到单独步骤，由改 #160 的 PR 处理。
