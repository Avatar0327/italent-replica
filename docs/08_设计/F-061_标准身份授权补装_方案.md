# F-061 存量租户标准身份授权补装：方案

> 任务：F-061（DEC-340④；DEC-361 改为接入通用种子补装登记表）。本文只出方案，实现另派 Sonnet（DEC-338）。
> 依据：`DEC-361_种子补装登记表.md`；#160（a849083，`apps/api/src/seeds/registry.ts`）；
> `R3-T02_实现拆分方案.md` 第 8 节（#164 定稿的“授权补装台账”）；`apps/api/src/modules/permission/standard-profiles.ts`。
> 状态：方案稿 v1。第 9 节列出的 4 个产品决定未定之前，涉及的 PR 不开工（见第 7 节依赖）。

## 0. 一句话

把“标准身份”拆成两层登记进 #160 的登记表：**身份本身**（缺整个身份时补装，沿用 DEC-289③ 口径）和**身份上的每一项授权**
（应用、对象、数据操作、字段、按钮、预置看全部）。授权层配一张平台通用的**只追加授权补装台账**：平台装过的、首次接管时已有的、
租户保存过的，一律记账；只补“当前没有、台账也没有”的项，所以租户撤销过的不会被补回来。C1-2 的员工身份发展通道授权也用这张台账，不另建表。

## 1. 现状

### 1.1 标准身份怎么装上去

| 环节 | 代码 | 行为 |
|---|---|---|
| 身份定义 | `packages/domain/src/platform/standard-presets.ts` 的 `STANDARD_PROFILES` | 12 个身份（组织员工 3 个 HR 身份 + 经理、人才标准、盘点、继任 3 个、360 3 个）。对象权限**从对象目录推导**：`full(def)` = 全部字段可见、非系统字段可编辑、全部按钮与数据操作；`readOnly(def)`；`partial(def, ops, buttons)`；360 身份按 `SURVEY360_PROFILES` 显式排除部分按钮 |
| 开通安装 | `installStandardProfiles` → `installProfile` | 逐个身份写 `permission_profiles`（`source='standard'`）、`permission_profile_apps`、`_objects`、`_fields`、`_buttons`；按 `hr` / `seeAll` 预置看全部（`presetSeeAll`，写范围行、范围版本、审计）；每个身份一条 `permission_profile.provision` 审计 |
| 开通顺序 | `platform/provisioning.ts` | 先 `installStandardProfiles`（返回身份 id 给首位管理员授予），最后在同一开通命令里调 `installMissingSeeds`（#160） |
| 存量补整个身份 | `installMissingStandardProfiles`，路由 `POST /api/platform/tenants/:tenantId/standard-profiles/backfill`（#117，DEC-289③） | 只补租户里**没有该编码**的身份；同编码已是标准身份 → `ALREADY_INSTALLED`；租户手工建过同编码 → `CODE_TAKEN`，不覆盖、不合并。新装身份加入有效租户管理员的可授权身份。**不补已装身份上缺的对象 / 字段 / 按钮** |
| 租户改权限 | `permission/profiles.ts#setObjectPermission`（`PUT /profiles/:id/objects/:objectCode`） | 按对象整体替换：删对象行（字段、按钮级联删），再按提交内容重插；身份 revision +1，写 `permission_profile.set_object` 审计。**没有删除对象、改身份应用的路由**，所以“对象行不存在”只会是“从未装过” |
| 撤销表达 | 同上 | 数据操作 = `can_*` 为 false；字段 = 行在但 `can_view` / `can_edit` 为 false，或行不在；按钮 = 行不在；看全部 = 范围行在但 `see_all=false` |

### 1.2 缺口

`STANDARD_PROFILES` 从目录推导，目录一加字段 / 按钮 / 对象，**新租户**开通就带上；**存量租户**的同一标准身份停在开通那天的目录，
平台回补（#117）只补整个缺失的身份。结果：存量租户的标准管理员看不到新字段、点不到新按钮，只能靠租户管理员逐个手工勾选（DEC-340④ 要求“不靠手动”）。

## 2. 总体结构

```
seeds/index.ts（import 顺序即执行顺序）
  └─ permission/standard-seeds.ts
       ├─ registerSeed permission/standard-profiles        codes = 身份编码；补整个缺失身份（原 #117 口径）
       └─ registerSeed permission/standard-profile-grants  codes = 全部授权项编码；只补缺失授权项
  └─ （C1-2）qualification/... registerSeed qualification/employee-profile-grants   共用同一台账表
seeds/grant-ledger.ts      台账读写 + 租户补装锁（从 registry.ts 抽出，行为不变）
packages/domain/src/platform/standard-grants.ts   授权项编码的构造、解析、目录指纹（纯函数）
```

- **#160 通用接口不改**：`SeedEntry` 签名、`installMissingSeeds` 的流程与报告形状都不动（#164 §8 的约定）。
  唯一的改动是把锁语句抽成 `lockTenantSeeds(tx, tenantId)` 导出，`installMissingSeeds` 改为调用它（SQL 与锁键逐字不变），供旧路由复用。
- 两个登记项同属模块 `permission`，平台回补按模块筛选时总是一起跑；`standard-profiles` 先登记，保证同一轮里先补整个身份、再补授权项。
- 旧路由 `standard-profiles/backfill` **保留**，响应形状不变（契约测试 `AC-360-standard-profiles` 不改）；它只补整个身份，
  补授权项要走 `seeds/backfill`（不带筛选或 `modules: ['permission']`）。

## 3. 登记方式

### 3.1 授权项稳定编码

沿用 #164 §8 的格式，补上应用与看全部两类。编码只由身份编码、对象 / 字段 / 按钮的目录编码组成，不随租户改名变化。

| 种类 | 编码 | “当前已有”的判定 |
|---|---|---|
| 身份 × 应用 | `<身份>/app:<应用>` | `permission_profile_apps` 有行 |
| 对象 | `<身份>/<对象>/op:view` | `permission_profile_objects` 有行 |
| 数据操作 | `<身份>/<对象>/op:<create\|update\|delete>` | 对象行 `can_*` 为 true |
| 字段查看 / 编辑 | `<身份>/<对象>/field:<字段>:<view\|edit>` | 字段行在且 `can_view` / `can_edit` 为 true |
| 按钮 | `<身份>/<对象>/button:<按钮>@<层级>` | 按钮行在 |
| 预置看全部 | `<身份>/seeAll:<应用>:<entity\|datasource>:<目标>` | 范围行在且 `see_all=true`（**第 9 节 D3 定了才进 codes**） |

- 只有身份定义**授予**的项才进 `codes`：`readOnly` 不授予的按钮、`partial` 没列的数据操作、360 `ADVANCED_WITHOUT` 排除的按钮、系统字段的 `edit`，都不是编码，永远不补。
- 依赖关系（安装顺序与“不可装”判定）：`app` → 该应用下对象的 `op:view` → 同对象的 `op:create/update/delete`、`field:*:view`、`button:*`；`field:x:view` → `field:x:edit`。
- `packages/domain/src/platform/standard-grants.ts`（纯函数，不引 IO）提供：
  - `standardGrantItems(profile)`：返回 `{ code, profileCode, kind, appCode?, objectCode?, fieldCode?, flag?, buttonCode?, level?, target? }[]`；
  - `parseGrantCode(code)`；
  - `STANDARD_GRANT_CODES`：对 `STANDARD_PROFILES` 展开去重；
  - `STANDARD_GRANT_VERSION` 与 `STANDARD_GRANT_DIGEST`（编码列表排序后的哈希，第 3.4 节）。
- 守卫测试：编码唯一、可解析回原项；每个身份展开后对 `objectCatalog` 校验通过（与 `installProfile` 同一个 `validateObjectPermission` + `isWithinProfileApps`）。

### 3.2 两个登记项

| 登记项 | `codes` | `existing` | `install(missing)` |
|---|---|---|---|
| `permission/standard-profiles` | `STANDARD_PROFILES` 的身份编码 | 租户里已有的身份编码（**不论 `source`**：手工同编码计入已有，即 `CODE_TAKEN` 不装） | 对每个缺失身份调 `installProfile`（第 3.3 节，装入即记账），再 `grantableToTenantAdmins`；与旧路由同一实现 |
| `permission/standard-profile-grants` | `STANDARD_GRANT_CODES` | 第 4.2 节（锁身份行 → 首次接管 → 当前 ∪ 台账 ∪ 不可装） | 第 4.3 节 |

### 3.3 授权补装台账（平台通用，取代 #164 §8 的 `qualification_seed_grant_installs`）

新表 `seed_grant_ledger`（新文件 `packages/db/src/schema/seeds.ts`，契约 PR 落地）：

| 列 | 说明 |
|---|---|
| `tenant_id` | 租户；RLS 同其他租户表 |
| `entry` | 登记项 `module/key`，如 `permission/standard-profile-grants`、`qualification/employee-profile-grants` |
| `code` | 授权项编码；另有每个身份一条接管标记 `<身份>/@ledger`（不在 `codes` 里，第 5 节） |
| `source` | `install`（平台装入）/ `adopted`（首次接管时登记）/ `tenant_saved`（租户保存对象权限时登记，D2） |
| `command_id` | 平台命令或租户写命令的 ID；`existing` 里的接管没有写上下文，留空 |
| `recorded_at` | UTC |

- 主键 `(tenant_id, entry, code)`；写入一律 `INSERT … ON CONFLICT DO NOTHING`，**第一次登记的来源为准**，之后不改。
- 只追加：语句级触发器禁止 UPDATE / DELETE / TRUNCATE（同 `0003` / `0006` 的 `forbid_audit_mutation`，`--custom` 迁移）。
- 台账只是“平台是否还该补这一项”的依据，**不参与鉴权**；鉴权仍只读权限表。
- `apps/api/src/seeds/grant-ledger.ts`：`readLedger(tx, entry)`、`recordLedger(tx, { entry, codes, source, commandId, now })`、`lockTenantSeeds(tx, tenantId)`。

**装入即记账**：`installProfile`（开通、旧路由、`standard-profiles` 登记项三处共用）写完一个身份后，把该身份全部授权项编码与接管标记以 `install` 记账。
所以开通后的新租户台账是满的，第一次回补就无缺失；以后目录新增的项才会成为缺失。

### 3.4 version 与报告

- `version`：只用于回补报告，不参与缺失判断（#160 / #164 同口径）。目录增删授权项时 `STANDARD_GRANT_VERSION` +1。
- 防止忘了 +1：`STANDARD_GRANT_DIGEST` 记录当前版本对应的编码指纹，守卫测试算出的指纹不一致即失败，提示“目录变了：version +1 并更新指纹”。
  任何改对象目录或 `STANDARD_PROFILES` 的 PR 都会撞到这条测试，作为提醒，也让审查方一眼看到“这个 PR 会给存量标准身份补授权”。
- 报告沿用 #160 形状 `{ module, key, version, installed, existing }`：
  - `installed` = 本次补装的编码；
  - `existing` = 已有 + 台账已登记 + 不可装（身份被租户占用编码、父项被租户撤销）的个数。报告不细分原因，细节看租户审计与台账。

### 3.5 与 #164 §8（C1-2）统一口径

| #164 §8 原写法 | 本方案后的写法 |
|---|---|
| C1-2 自建 `qualification_seed_grant_installs` | 改用 `seed_grant_ledger`，`entry='qualification/employee-profile-grants'`；C1 迁移恢复为 2 个 |
| `source ∈ (install, adopted)` | 同一枚举，另加 `tenant_saved`（D2 定为“是”时，C1-2 在员工身份的保存路径同样登记） |
| 三条登记路径（装入 / 开通 / 首次接管） | 不变，由 `recordLedger` 统一实现；接管标记按身份 |
| `qualification/standard-profiles` 三个预置身份 | 直接加进 `STANDARD_PROFILES`，由本方案两个登记项覆盖，**不另起数据集** |
| 员工身份 `CODE_TAKEN` / 不存在 → 计入已有、不装 | 不变 |

C1-2 依赖本方案 PR-1（第 7 节）。本 PR 合并后由总编排在 `R3-T02_实现拆分方案.md` §8 改一行指向本文（避免与在途的 #173 改同一文件）。

## 4. 回补流程

### 4.1 锁与事务

1. `installMissingSeeds` 开头取租户补装锁（#160，不变）；开通、`seeds/backfill`、旧路由三处都在这把锁上排队（旧路由在 `installMissingStandardProfiles` 开头补调 `lockTenantSeeds`，消除它与 `seeds/backfill` 同时装同一身份撞唯一约束的 500）。
2. `standard-profile-grants.existing` 第一步对租户的标准身份行 `SELECT … FROM permission_profiles WHERE code = ANY(标准编码) FOR UPDATE`：
   - 正在进行的租户保存（`setObjectPermission` 也是先 `FOR UPDATE` 身份行）要么已提交、被本次读到，要么等本次提交后再执行；
   - 本次补装推进了 revision，等待中的租户保存会按 revision 不一致返回 409，客户端刷新后重提（AGENTS §10 并发约定）。
   - 加锁顺序固定为“补装锁 → 身份行”，租户保存只取身份行，不会死锁。

### 4.2 `existing`（授权层）

对 `STANDARD_PROFILES` 每个身份：

1. 租户里没有该编码，或该编码是手工身份（`source='custom'`）→ 该身份全部编码计入“不可装”。不读、不写手工身份的任何权限。
2. 读当前权限（应用、对象、字段、按钮、看全部范围行）得到“当前已有”集合。
3. 该身份没有接管标记 → 执行首次接管（第 5 节）。
4. 返回 当前已有 ∪ 台账已登记 ∪ 不可装。其中“不可装”= 父项“台账有、当前无”（租户撤销过）的子项，例如租户关掉了字段查看，则该字段的编辑也不补；看全部范围行在但 `see_all=false` 的项也算已有（租户关过）。

不可装的子项**不记账**：将来租户自己恢复了父项，下一次回补会把子项当缺失补上；D2 定为“是”时，租户恢复父项那次保存会同时把子项登记为 `tenant_saved`，不会被补。

### 4.3 `install(missing)`（授权层）

按身份分组，每个身份：

1. 记下受影响对象改动前的权限（`loadObjectPermissions`）；
2. 按依赖顺序写：`app` 插应用行 → `op:view` 插对象行（数据操作取同批缺失的 `op:*`）→ 已有对象把缺失的 `can_*` 置 true → 字段行 upsert（只把缺失的标志置 true，另一标志保持）→ 按钮行插入 → 看全部复用 `presetSeeAll`（写范围行、范围版本、审计）；
3. 写完后对每个受影响对象按目录重新校验（`validateObjectPermission`、`isWithinProfileApps`），不合法即抛错，整笔命令回滚；
4. 身份 revision +1（`UPDATE … WHERE revision = 读到的值`，0 行即抛错回滚）；
5. `recordLedger(source='install', commandId)`；
6. 每个身份一条租户审计 `permission_profile.backfill_grants`（`auditAs`，同事务写 outbox）：`before` / `after` = 受影响对象的权限与应用、新补的看全部键、revision。

持有该身份的用户下一次请求即获得新权限（服务端每次请求重新算权限，无需清缓存）。不写平台以外的通知。

### 4.4 租户保存登记（D2 定为“是”时）

`setObjectPermission` 在身份行 `FOR UPDATE` 之后：若身份 `source='standard'` 且 `STANDARD_PROFILES` 里该身份含此对象，
把“该身份 × 该对象”此刻全部授权项编码以 `tenant_saved` 登记（同事务，`command_id` = 本次写命令 ID）。
含义：租户已经在完整的权限面板上看过这些项并保存，未勾选的就是租户的决定。之后目录**新增**的项不在这批登记里，仍会被补。

## 5. 首次接管（已上线租户）

F-061 上线前开通的租户台账为空。如果直接按“当前没有 = 缺失”补，会把租户上线前撤销过的项补回来。接管按身份进行，以接管标记 `<身份>/@ledger` 判断是否已接管
（不按“台账是否为空”判断：旧路由新装的身份或租户保存登记的零星行都会让台账非空，但别的身份还没接管）。

对每个未接管的标准身份，在锁内、同一事务里：

1. **当前已有的项**：全部登记 `adopted`。
2. **对象从未被租户改过**：身份 revision 为 1，或审计表 `audit_events` 里没有该身份、该对象的 `permission_profile.set_object` 记录 → 该对象下当前没有的项只可能是开通后目录才新增的，不登记，按缺失补。
3. **对象被租户改过**（有 `set_object` 审计）：当前没有的项分不清是“租户撤销 / 没勾”还是“目录后来新增”。按 **D1** 处理：
   - D1 = A（推荐，保守）：该对象下当前没有的项全部登记 `adopted`，不补；报告与审计可追溯，需要的项由租户管理员手工勾；
   - D1 = B：不登记，按缺失补。
4. 看全部：范围行在且 `see_all=false` → 登记 `adopted`（租户关过）；范围行不在 → 按缺失处理（D3 决定是否在 codes 里）。
5. 写接管标记（`adopted`）。

接管只登记、不改权限，不写业务审计（#164 §8 同口径）；平台审计的回补汇总里能看到这次命令。
#160 只在持锁后调 `existing`，所以接管在锁内；若 #160 日后加只读预览，接管要移到单独步骤，由改 #160 的 PR 处理（沿用 #164 §8）。

残余边界（写进实现 PR 描述）：上线前租户改权限只有 `setObjectPermission` 一条路径，必留 `set_object` 审计，所以“改过但无审计”的对象不存在；审计缺失（如人工改库）时按“未改过”处理，会补缺项，由回补审计追溯。

## 8. F-039 登记与零行为变化边界

- **不新增、不删除路由**，不改任何 `policy.ts` 声明、`required/*.ts` 义务、基准 `observed-contract.json`、`AC-PRM-FW-01/02*` 的端点总数与 `EXPECTED_BY_MODULE`。
- 改到的函数（`installMissingSeeds`、`installMissingStandardProfiles`、`installProfile`、`setObjectPermission`）若是证据锚点的调用链成员，摘要会变：在同一 PR 用 `ROUTE_POLICY_UPDATE_DIGESTS=1` 重生成 `required/digests.ts`，只提交摘要变化，PR 描述写明“仅实现变化、无授权口径变化”。
- 对外可见的变化只有：
  1. `seeds/backfill` 报告多两个 `permission` 条目，并真的补授权（这是本任务的目的）；
  2. 回补推进了被补身份的 revision（租户端旧页面保存会 409，刷新重提）。
- 不变的：开通响应（`ProvisionResult` 不含种子报告）、开通后新租户的权限内容、旧路由响应、租户保存接口的请求与响应、鉴权结果（台账不参与鉴权）。
- 新租户开通**零业务变化**：只多出台账行。用 T-01 加一条“开通后权限表内容与改动前快照一致”的断言守住。
