## 3. 状态机与视图口径（DEC-125 / 215、Q-M0-86；未来直接离职不提前落地）

### 3.1 状态机

申请单状态完全复用 `EmploymentState`。**直接离职也走 `approved → effective`**：保存即“已确认待生效”（approved），最后工作日已过则保存事务内立即生效；否则到期由定时任务原子生效（P2-04）。

```
[草稿 draft] ─提交→ [审批中 in_review] ─驳回→ [已驳回 rejected] ─修改重提→ in_review
                      │ 不同意办结 → [disapproved]        │ HR 撤销离职 → [voided]
                      ▼ 最后节点同意（confirmed 阶段：编制预减 R、approval_passed 转交、交接自动发起端口）
              [审批通过 approved] ──原生效日 E ≤ 今天→ 同事务 activateExit
                      ▲                 │ 未到 → 停在 approved，只有申请单
   [直接离职保存] ─────┘（confirmed 阶段：编制预减 R、approval_passed 转交；不自动发起交接 DM-R14）
                                        │ HR 撤销 → [voided]（无版本可删，DEC-215）；改期 → 新载荷版本仍 approved
                                        ▼ 到期（activateExit，一个保存点）
              [已生效 effective]  最终日期（契约 §DEC-272）→ 版本链新增离职记录（人员状态 8）→ 下游效果
                      │ 撤销 → [deleted]（墓碑 + 时间轴恢复；版本 / 事件 / 台账保留）
                      │ 改期到过去 → 同一业务重定位；改期到今天以后 → [deleted] + 后继单（§7.2）
```

**两条办理路径（B15，补证结论 R2c / W-831～837）**：① **离职申请**（HR 端或 F-020 的自助 / 代发入口）走审批（本租户流程 开始 → 直接上级 → HR 访谈 → 结束，即预置 `StandardDimission`），审批通过后出现在「离职中的员工」、审批状态“审批通过”，到期生效；② **员工档案 → 离职 → 保存**（直接离职）不产生审批，保存即 approved（L 已过则同事务生效）。两条路径生效结果相同：新增一条离职任职（开始日 = 最后工作日次日 E′，业务类型“离职”，人员状态 8 离职；详情“任职状态”对 kind ∈ {leave, retirement} 的记录由读模型显示“任职结束”，不加列），前一条任职区间截断到 L′；L′ 当天仍为原人员状态（如正式），E′ 起为离职；生效后进入「已完成的离职」与人员模块“离职人员”列表。R2c 观察到的“改到过去日期后进入已完成的离职”由 §7.2 approved 改期 → 新 E ≤ 今天 → 同事务生效覆盖。

**迟到生效**（契约 C-1 / C-2、F-007 §2）：实际执行日 a 晚于原生效日 E 才算迟到（`resolveLateLeave`）；a = E 当天执行属正常，不顺延。区间 [E, a) 的成员按 F-007 §2-2 的**位置规则**计算（与调动同一实现 `lateWindowBlockers`，§5.1-0）：离职按 `timelinePosition(E, 离职)` 得到插入位置，位置在其后且 `start_date < a` 的任职版本（不分 kind）∪ 原计划日 ∈ [E, a) 且按 C-3 同日规则排在离职之后的未落地申请（draft / in_review / approved / rejected 都算）。**区间为空**（简单迟到）：L′ = a − 1、E′ = a，离职记录当天落地。**区间非空**：fail-closed，不执行，记 `failed` 原因 `REBUILD_REQUIRED`“生效失败：需重建，待 HR 处理”（DEC-278③），重建属 F-036。

### 5.3 审批通过与直接离职保存时的立即生效

3. 取锁：合同侧 `lockEmployee` 对 `employment_employees` 取 FOR UPDATE，离职事务此前已持同一行 FOR NO KEY UPDATE（§5.2 ②），同事务升级，不引入新的锁序。
4. 范围：`checkScope` 用离职编排器构造的**系统合同上下文**（`scope` 为空，与调度器同一做法）——合同的终止 / 删除 / 撤回是离职生效的系统后果，授权已在离职门禁完成（§4A）；返回给 HR 的清单仍按查看人的合同 `object.view` 与字段权限裁剪（§7.4、§9.1）。
5. 时点：生效时调用（步骤 4，L′ 为最终最后工作日）；Q-M0-100（“审批通过即终止”还是“生效才终止”）仍未取证，若取证为前者再挪到 `confirmed` 阶段（§19）。
6. 撤销离职不自动恢复合同（DEC-222）：撤销清单列出被终止 / 删除的合同（§7.4）。**main 没有“恢复被离职终止的合同”的入口**：`service.ts:48 correctedState` 只允许到期终止（`terminationReason = 'expiry'`）延期恢复，离职终止的合同编辑即 `CONTRACT_TERMINATION_PROTECTED`；软删除的合同也没有恢复入口（F-128 / DEC-484 删去了手动删除，恢复更无入口）。因此撤销清单给出的“手工处理”是**重新签订合同**（新建 / 续签），恢复原合同的入口是否要做 → §19 待补证、§10.2 F-014 接口。
7. 保留的在途合同申请在离职后才落地：合同模块既有校验 `service.ts:370 validateReferences`（合同生效日的主职记录为离职 / 退休且类型不是离职后可签 → `VALIDATION_FAILED`“该合同类型不允许离职或退休后签订”）拒绝 → 合同侧按其生效失败处理（§5.9）。

### 5.6 继承矩阵、人员状态与“离职作为向后更新目标（不是重建目标）”（契约 §DEC-269）

**继承**（创建 / 落地时取值）：离职与其他业务同一套 `prepareInheritance / resolveEffectiveInheritance` 与 form 矩阵：INHERITED_FIELDS 预置字段有边；`isDepartmentHead` / `isStoreManager` / `addedSubordinateIds` 无边；employType / jobNumber / 人员状态 8 / 入职状态为系统派生；自定义字段 inherit:true 有边，inherit:false 在离职表单可编辑或未拖入为空、只读 / 隐藏继承（`07` §3.3）。`lastWorkDate` 与离职扩展字段是人工 intent；迟到顺延写入的 L' / E' 是**可信系统修订**（保留原意图版本，追加系统命令，契约 §DEC-272）。

**向后更新目标**：离职 / 退休版本永不作为传播来源（`forwardUpdate: false`、状态传播跳过；#83 合并后归一），但是合法的向后更新目标。按契约 §DEC-269（范围 C'）：迟到执行 = 补录一条更早生效的记录，[计划日, 实际执行日) 内的组织调整按 #83 重算，之后的独立业务**包括离职不重建**，走 AC-FWD 值匹配向后更新（只替换等于旧值的字段，“是否部门负责人”不动，职位与部门同时变化按原站规则②）；`lastWorkDate`、生效日、离职扩展字段、人员状态 8 不在匹配范围。**“编制不重算，超编只记警告。离职记录的部门被替换时，已在旧部门释放的编制也不重算、只记警告。”**（契约原话）有意设回旧值会被误替换（已接受局限）：写审计、测试固定（B-52a）；在途审批保留发起时审批人，新查询按替换后部门判范围（B-52b）；每条替换记录标明“迟到执行触发的向后更新”。F-021 序列同步同样以离职记录为目标。F-022 状态传播按契约 §F-022（完成入职必须传播；离职 8 ≠ 来源前值不被改）。

**撤销 / 改期与状态**：撤销已生效离职 = 时间轴恢复前一条开放区间，其版本状态自然成为当前；重定位追加快照版本，状态随快照为 8。

### 5.9 保留流程的离职后校验（DEC-267③）

被 DEC-267 默认政策**保留**的在途流程（载荷生效日 ≤ L′ 的审批中 / 已批准任职申请，终止日期 ≤ L′ 的在途合同申请；即 `exit_effects` 中 `transfer_retained` / `process_retained` 的目标）在离职**已生效**后才审批通过 / 定时生效 / 重试落地时，按 DEC-052 记生效失败交 HR，离职记录不变（B-56b 必测）：

| 流程 | 拒绝点（main 现有机制优先） | 失败原因 |
|---|---|---|
| 调动（迟到，a > 载荷日） | F-007 §2：区间 [载荷日, a) 含已落地离职 → 先命中 | `REBUILD_REQUIRED`（C-3 边界 3） |

## 6. 编制：批准即预减（DEC-266①）

原站：离职 / 退休的编制时机 = “审批通过-立即释放”，**审批通过即在当前及未来周期计为预减**，不等生效日。

**释放时点 R 与生效日 E' 分离**：R = 审批通过 / 直接离职确认的租户日，写入 `exit_requests.pre_release_date`；改期、迟到顺延、替代都**不改 R**（后继单的 R = 其确认日）。

1. **投影层**（`establishment/employment-check.ts` + `membership-windows.ts`，共享文件；main 的 `occupancyRows`（`:355`）只按时间轴主职记录、排除 kind ∈ {leave, retirement}，**没有** `pendingExits`，approved 未生效离职现在不释放占用）新增 `pendingExits(employeeIds)`，`occupancyRows` 与 `pendingTransfers`（`:383`）同处减去它；区间运算调用 §6B 的纯函数（P 投影），不另写 SQL 判定：对最新状态 ∈ {approved, effective} 且未被撤销的 kind ∈ {leave, retirement} 业务，读取 R 与**所属任职周期 `exit_requests.staff_id`**（§2.1）。**预减 = 同周期记录 ∩ 预减区间（v1.5，P2-01）**：预减区间 P = `[R, 后继周期入职日)`（后继周期 = `employment_cycles` 中 `entry_date > R` 的下一条，没有则开放）；对该员工 `r.staff_id = x.staff_id` 的**每条**主职记录区间 W，占编投影取 `W \ P`（即把落在 P 内的部分全部去掉）——**不用 L 过滤**：本周期内在 R 之后开始的记录（审批中途生成的组织调整、迟到批准后 DEC-278 拒绝生效而保留 approved 时的当前记录等）同样不占编（B-62b）；只有新周期（不同 staff_id）的记录不受影响。重聘（R2-T01：重聘开新 `employment_cycles` 行、新 staff_id，`inheritanceSourceId` 不跨周期）后的新周期记录不满足条件，**照常占编**，严格编制对调入新周期岗位的另一人照常拦截；第二次离职的 staff_id = 第二周期，只释放第二周期（B-62 / B-62a；B-62b 为同周期较晚记录）。从 R 起即不占编，与员工仍在岗到 L' 无关（原站口径）。已生效后时间轴截断在 E' ≥ R，不影响。
   staff_id 的取得：创建时的载荷 `selectedStaffId`（§2.1，`selectEmploymentCycle` 选定、改期与审批编辑以 `expectedStaffId` 锁定）；没有可选周期 → 既有 `EMPLOYMENT_CYCLE_MISMATCH` / 顺序校验 409（入口 §4A 已要求 L ≥ 当前周期入职日）。
2. **记账层** `establishment/exit-release.ts` 导出 `registerEstablishmentPreRelease(tx, ctx, business)`：在 `confirmed` 阶段写 `exit_effects(establishment_pre_released, detail: { departmentId, positionId, capacityId, releasedFrom: R, plannedEffectiveDate: E })`；生效时追加修正行记 E'（R 不变）。不追加编制版本、不改 `transfer_establishment_allocations`、不取编制锁。
3. **恢复占编**（撤销 approved、撤销已生效恢复在职、替代、后继单作废）：预减随业务作废 / 删除自动收回；需要重算的段**不再按入口写公式**，统一按 §6B（P 投影操作前后差集 ΔP 的每一段重算峰值）。超编 → DEC-258“一律只弹确认、不拦截”（严格控编同样只确认）：沿用 main 已有的确认形态 409 `CONFLICT` + `reason: 'CONFIRMATION_REQUIRED'` + `warnings[{ reason: 'ESTABLISHMENT_EXCEEDED', capacityId, departmentId, positionId, from, to, peak, limit }]`（`establishment/transfer-service.ts:324`、`org/write-service.ts:255` 同一形态；v1.5 的 `ESTABLISHMENT_EXCEEDED_CONFIRM_REQUIRED` 是新造码，main 没有，删去），明细按查看人可见范围裁剪；请求带 `confirmed: true` 重提后执行并记审计 `employment.exit.over_capacity_confirmed`。§6B 的组织停用交集（拒绝）排在本确认**之前**。改期（含改晚）不恢复占编（R 不变，ΔP = ∅）。
   **替代后的 R**（§7.2 已生效改到今天以后）：**同一业务内 R 永不变**；替代 = 前单删除 + 后继单，后继单 R₂ = 新确认日（今天）。前单的预减随前单删除消失，`[R₁, R₂)` 恢复占编（ΔP，§6B 表 #7），超编 → 确认协议，确认前**整个替代命令**（前单删除 + 后继单创建）不执行（B-21d）。
4. **与调动交叉**：审批通过未生效的调入申请（`pendingTransfers`）与预减同时存在：调动生效日 < R 的在新部门占编到 R；≥ R 的不占编（员工已预减）；> L' 的按政策作废或保留（§5.1-1）。
5. **迟到执行触发的向后更新替换离职记录部门**：契约原话——编制不重算，只记警告 `employment.forward-update.capacity_warning`（契约 C-7，F-036 实现，recordKind = leave）；`exit_effects` 不追加修正行。
6. 撤销 / 挂回未来调动（§5.8）时，T 的区间重新进入 P 投影，自然出现在 ΔP 里（§6B 表 #1 / #4）。
7. 停用校验侧的离职排除（§6A.1，O 投影）同样限定 `r.staff_id = 该离职 staff_id`，与本节口径一致；两个投影由同一纯函数给出（§6B.1）。

## 6A. 组织停用校验与离职（DEC-275②，照原站 W-499～502）

### 6A.1 停用侧：离职计数

**main 现状**：`org/deactivation.ts:41 planDeactivation` → `assertSubtreeVacant`（`:112`）合计三项占用——在职人员 `employment/org-people.ts:100 countDepartmentStaff`（时间轴主职记录与 `[停用日 D, ∞)` 相交、kind ∉ {leave, retirement}，**按员工去重计人数**）、在途调入申请 `countPendingTransfers`（`:154`，按申请单条数，无日期过滤，DEC-196）、启用职位；任一非零 → 409 `ORG_SUBTREE_NOT_EMPTY`。已生效离职截断时间轴，自然不计；**approved 未生效离职不被考虑**（员工照常计入）。main 上没有 `TODO(Q-M0-92)` 标记（v1.5 的“替换 TODO”说法删去），DEC-275② 由本设计落实：

| 离职状态 | 停用日 D 的计数规则（DEC-275②：按**任职记录条数**计，不按员工去重） |
|---|---|
| 审批通过、尚未生效（approved，申请或直接，含生效失败仍为 approved；生效日 E 取最新载荷） | 该员工同 staff_id 的在职任职记录**从 E 起不计入占用**：D ≥ E → 不计；D < E → 照常计入 |
| 审批中（in_review）/ 草稿 / 已驳回 | **照常计入**（离职未定） |
| 已生效 | 时间轴已截断到 L′，D ≥ E′ 自然不计（现有逻辑） |
| 作废 / 已删除的离职 | 不影响计数 |

实现：`countDepartmentStaff` 改为按 §6B.1 的 O 投影计数——SQL 只取“子树内与 `[D, ∞)` 相交的时间轴主职记录 + 这些员工的 approved 离职（E、staff_id）”，是否计入由 §6B 纯函数判定，计数单位改为记录条数（DEC-275②；main 只有主职记录，兼职上线后（BE-7）按条计入同一投影）；文案条数随之变化；不改在途调入的计数口径。迟到顺延只在生效时发生，停用校验用申请当前载荷的 E（生效时若顺延跨过停用日由 §5.1-0c 拦下）。测试计划 B-61：D 在 E 前后各一例、审批中离职一例、作废离职一例、同员工同组织两条主职记录（E 前一条、组织调整后一条）按条数计一例、跨周期（旧周期 approved 离职不影响新周期记录）一例。

### 6A.2 反向：扩大在职区间的离职操作（v1.6 并入 §6B）

## 6B. 区间变化统一规则（v1.6，DEC-431①；关闭 v1.5 复审 P2-01，取代 v1.5 §6A.2 逐入口公式与 §6-3 恢复区间公式）

v1.5 对每个入口各写一个“恢复区间 I”公式（`[E, 同周期下一条起始)`、`[E', E₂)`、`[R, min(…))` 等），复审 P2-01 证明这种写法会漏段：撤销 approved 离职撤掉的是**整个同周期**的停用计数豁免与编制预减，而公式只截到同周期下一条起始。v1.6 不再按入口写公式，统一为**同一投影函数 + 操作前后差集**：

### 6B.1 两个占用投影（纯函数，`packages/domain/src/employment/exit-occupancy.ts`）

| 投影 | 含义 | 用于 | 离职的作用 |
|---|---|---|---|
| **O（在职占用）** | 员工在某组织“在职”的日期段：时间轴上每条在职任职记录（main 只有主职；兼职上线后同口径按条计入）的区间，扣掉同 staff_id 的 approved 离职从 E 起的部分（§6A.1）；被摘下、待挂回的未来调动（§5.8）不在时间轴上，不计 | 组织停用校验（§6A.1 计数、本节反向校验） | approved：同周期记录在 `[E, ∞)` 不计；effective：时间轴已截断到 L′ |
| **P（编制占用）** | 员工在某部门 / 职位 / 编制上占编的日期段：主职记录区间扣掉同 staff_id 离职的预减区间 `[R, 后继周期入职日)`（§6-1） | 编制峰值与 DEC-258 确认 | approved / effective：同周期记录在 `[R, 后继周期入职日)` 不计 |

两个投影都由同一个纯函数按“时间轴记录 + 离职状态（state、E、L′、R、staff_id）+ 被摘下的未来调动窗口”计算，`planDeactivation` 的停用计数（§6A.1）、`pendingExits`（§6-1）与本节反向校验**读同一实现**，不各写 SQL 条件（SQL 侧只负责取数，判定在纯函数）。

### 6B.2 唯一规则

对**任何**会改变离职状态或日期的操作 op（下表全部入口），在同一事务、按 §5.2 全局锁序取到 ④ `lockOrganizationSettings` 之后：

1. 计算 op 之前的投影 `O₀ / P₀` 与 op 之后（模拟）的投影 `O₁ / P₁`（同一纯函数，输入只差离职状态 / 日期 / 时间轴挂回与否）；
2. **新增段** `ΔO = O₁ \ O₀`、`ΔP = P₁ \ P₀`（按记录、组织 / 编制对象逐段求差，按 staff_id 不跨周期）；
3. `ΔO` 的每一段 `(record, departmentId, [from, to))` 调 `assertEmploymentDepartmentAvailableWithin(departmentId, from, to)`（`employment/references.ts` 新增的有终点变体：已持 ④ 锁 → `org/employment-validity.ts:14 employmentDepartmentDisable(dept, from)` → 返回的 `disabledOn < to`（to 开放则任一）才拒绝；既有无终点 `assertEmploymentDepartmentAvailable`（`:28`）不改）：段内任一天组织不可用 → **拒绝**（命令入口 409 `EMPLOYMENT_DEPARTMENT_DISABLED`，main 现为 `VALIDATION_FAILED` + reason，沿用；系统执行入口记生效失败，见下）；
4. `ΔP` 的每一段按编制峰值重算：超编 → DEC-258 确认协议（§6-3：409 `CONFIRMATION_REQUIRED` + `warnings[ESTABLISHMENT_EXCEEDED]`，`confirmed: true` 重提执行并记审计 `employment.exit.over_capacity_confirmed`）；系统执行入口（调度、重试、审批落地）不弹确认——它们只会出现 `ΔP = ∅`（R 不变，见下表 #8～#10），实现上断言为空，非空即视为实现错误 503 而不是静默放行；
5. 3 在 4 之前；任一步拒绝 → 整个命令不执行（前后读取相等）。被缩小的段（`O₀ \ O₁`、`P₀ \ P₁`）不需要校验。

不支持（§4）：已删除 / 作废的离职不能恢复为申请或记录；需要时另发新离职单。对 kind ∈ {leave, retirement} 的任何恢复端口：**授权先于不支持**（§9.1）——无功能权 / 按钮 / 范围者 403 / 404；授权通过者 409 `EXIT_RESTORE_NOT_SUPPORTED`（B-57 两例：无权限 403 / 404、有权限 409）。

### 7.4 改期与撤销的下游数据检查（DEC-275①，照原站；DM-R5 / R7）

**适用状态**（§7.2 / §15 同此）：仅 **approved**（未生效改期）与 **effective**（已生效改期两种）；draft / rejected / in_review 的改期不触发。

**改期**：保存成功后按改期方向检查**原最后工作日 L₀**上的下游数据，返回**不阻断**的清单 `downstreamHints`（保存已完成，清单只提示）：

| 方向 | 检查项（端口） |
|---|---|
| 改早（新 L < L₀） | 薪资档案、社保档案 |
| 改晚但仍早于今天（L₀ < 新 L < 今天） | 薪资、社保 + 假期余额、调休假、育儿假 |
| 改到今天之后（新 L ≥ 今天） | 以上 + 职责转交（`exit_effects(duty_transferred)` 与 linkage 子项，本设计真实实现） |

实现：`employment/exit-downstream.ts` 导出 `probeDownstream(tx, ctx, { employeeId, originalLastWorkDate, direction })`，按注册的探针端口逐项查询：薪资 / 社保 / 假期余额 / 调休假 / 育儿假 在复刻中尚无模块，**只留端口**；职责转交与合同由本设计实现。**内部端口返回值与用户清单分开**：每个探针 `DownstreamProbe.probe()` 返回 `{ kind, status: 'found' | 'none' | 'not_connected', targets[], hiddenCount }`（未接入模块的默认实现返回 `not_connected`）；响应 `probes[]` 原样保留每个探针的 status；用户看到的改期清单 `downstreamHints` **只含 `found` 项**（`none` / `not_connected` 不出现在清单里，前端据 `probes[]` 灰显“模块未接入”）。`targets` 按查看人 DEC-177 可见范围裁剪，不可见的只计件数；文案走资源文件（Q-M0-94 原文待取证时替换）。

### 10.1 迟到调动与离职交错（v1.6 重写 v1.5 §10-A，关闭复审 P2-02）

**规则 T（终止依赖，v1.6 新增，`linkage-dependency.ts` 扩一种依赖）**：离职 / 退休与同一员工排在它之前、尚未解决的任何前序业务**一律视为有依赖**——`linkageDependent(前序, 离职)` 对 kind ∈ {leave, retirement} 的后序恒为真，因此 §2.5 的 blocker 豁免对离职不成立，离职按 DEC-112 挂起 `PREDECESSOR_FAILED`。理由：离职若先落地，前序只能在“同日、原计划日更早”时插到离职之前（C-3 边界 2），否则因区间含离职记 `REBUILD_REQUIRED`——结果取决于 HR 哪天重试、调度是否同一轮，无法保证两种执行顺序一致；挂起后两笔都停在 HR 待办，由 HR 先处理前序（删除 / 作废 / 改期），结果与顺序无关。离职自己作为前序时不受影响（前序是离职、后序是调动的情形由 C-3 处理：排在离职之后的任职不能生效）。

**失败例 A（有 blocker）**：已批准待落地的调动申请 T（载荷 10-10）迟到；离职 L = 10-15 / E = 10-16 已批准；10-18 一起到期。
- T：区间 [10-10, 10-18) 内有未落地的离职申请（原计划 10-16，排在 T 之后）→ `REBUILD_REQUIRED`，blockers = [离职]（F-007 §2-2 / §2-3，main 现行）。
- 离职：前序 T 失败未解决；离职是 T 的 blocker，但按规则 T 恒有依赖 → 不豁免 → 挂起 `PREDECESSOR_FAILED`（blockedBy = T）；离职自身不做步骤 0 的顺延，不写任何任职数据。
- HR 先单独重试 T：T 仍 `REBUILD_REQUIRED`（离职申请仍在区间内）；main 的“HR 重试目标的 blockers 同轮再试一次”会再试离职 → 仍按规则 T 挂起 → T 不再试。HR 先单独重试离职：`assertPredecessorsSettled` → 409 `ACTIVATION_PREDECESSOR_PENDING`（blockedByBusinessId = T）。三种顺序结果一致：两笔都不落地、HR 待办各一条。
- HR 处理：作废 / 撤回 T（或撤销离职）后重试另一笔：只剩离职时，离职区间 [10-16, a) 为空 → 简单迟到 L′ = a − 1、E′ = a，正常生效；只剩 T 时 T 简单迟到落地。
- 测试 B-11（重写）：上述三种执行顺序 × 断言（两笔生效尝试原因、blockedBy、时间轴 / 载荷版本数 / 调动状态 / 合同前后相等）；HR 作废 T 后离职重试成功。
- 对照 B-11a（规则 T 的必要性）：同一场景若离职按 §2.5 豁免先落地，HR 于 10-18 当轮重试 T 会插到离职之前成功，10-19 重试则 `REBUILD_REQUIRED`——测试固定规则 T 下这两种重试日结果相同（都不落地）。

**正例 A′（真正空区间的排序）**：离职 L = 10-09 / E = 10-10 已批准；调动申请 T 原计划 10-05，10-10 当天先于离职到期执行前被批准。
- T 批准落地：区间 [10-05, 10-10) 内无其他记录或申请（离职申请原计划 10-10 不 < 10-10）→ 简单迟到，生效日 10-10（DEC-195②）。
- 10-10 离职到期：a = E，不迟到；`timelinePosition` 同日按原计划日 10-05 < 10-10 → T 在前、离职在后（C-3 边界 2），离职“变更前”读 T，不作废 T。
- 交换顺序（离职先于 T 批准在 10-10 落地，T 当日稍后批准）：T 区间 [10-05, 10-10) 内离职记录起始 10-10 不 < 10-10 → 空；T 按 C-3 插到离职之前，离职记录按 R1 值匹配向后更新（离职记录是合法目标，§5.6）。两种顺序最终时间轴相同（测试 B-11b 断言两种顺序下时间轴、离职记录字段、编制投影逐项相等）。
- 注意：A′ 中 T 若在 10-11 及之后才批准，区间 [10-05, a) 含已落地离职 → `REBUILD_REQUIRED`（C-3 边界 3），不是正例。

**A″（区间非空的迟到离职，原 v1.5 A′，口径不变）**：离职 E = 10-16 于 10-18 执行，另有 10-17 如期生效的直接调动 / 组织调整，或载荷 10-17 的 draft / in_review / approved / rejected 调动申请 → 离职 `REBUILD_REQUIRED`（DEC-278，区间按 F-007 §2-2 的位置规则，见 §5.1-0）。

**B（F-036 归属，不变）**：调动计划 10-05 迟到至 10-12 执行，组织调整 10-08 在区间内，离职 10-16 已生效：F-036 落地前该调动按 F-007 §2 记 `REBUILD_REQUIRED`；F-036 落地后离职记录按值匹配替换部门，状态 8 不变，旧部门已释放编制不重算、记警告（契约 C-6）。

**C（离职已生效后 HR 补录更早的直接调动）**：补录的直接调动生效日 ≤ L′、插在离职之前：按 main 既有顺序校验（`assertBusinessSequence` / `assertSuccessorSequence`）；离职记录作为 R1 值匹配向后更新目标（状态 8 不变，§5.6）；它不是 DEC-267 保留的流程，§5.9 的检查不命中。

### 10.2 F-014③（未来生效离职与合同恢复有效；已并入 F-016，DEC-179）

F-014③ 的两条路径在 main 上的现状与本设计的接口：
- **拦截路径（已在 main）**：`contracts/service.ts:75 assertRestorationAllowed`（“DEC-167④ / F-014”）在把到期终止的合同延期恢复为有效时，查两类离职：已生效（时间轴上 kind ∈ {leave, retirement} 的主职记录）与**最新状态 approved 且载荷生效日 > 今天**的离职业务（`employment_business_objects` + 最新载荷），最后工作日落在 `[合同生效日, 新终止日)` → 409 `CONTRACT_EMPLOYEE_DEPARTED`。本设计的离职单正是这两种形态（approved 业务头 + 载荷；生效后时间轴记录），**查询不用改就能识别本设计的离职**。唯一缺口：生效失败（`REBUILD_REQUIRED` / 挂起 / `EMPLOYMENT_DEPARTMENT_DISABLED`）而仍为 approved、载荷生效日已过去的离职不满足“> 今天”，会被漏掉 → 批 B3 把该条件改为“最新状态 = approved（不论日期）”，配测试 AC-CT-11 补例（B-74）。
- **端口路径（本设计）**：离职生效时 `handleContractsOnExit` 终止 / 删除合同、撤回在途申请（§5.4），即 F-014③“把离职生效时终止合同的端口接进离职流程”。
- 撤销离职后合同的“手工恢复”：main 没有恢复被离职终止 / 删除合同的入口（§5.4-6），撤销清单给“重新签订”；是否补恢复入口是合同侧口径，§19 待补证 / 待决，不在本设计实现。

### 10.3 F-096（离职改期对已结束继任记录的处理；口径待用户，DEC-440）

本设计**只预留入口与事件，不定口径**：
- 入口：已生效离职重定位（§7.2，新 L ≤ 今天 − 1）在同一事务调用任职状态钩子 `onRecordRescheduled(before, after)`——`status-hooks.ts` 已声明该钩子但 `employeeStatusHooks` 调度对象只有 `recordMaterialized` / `recordDeleted`，本设计补 `recordRescheduled` 调度（按订阅方名称顺序，与另两个同一锁序约定：调用时已持员工行锁）。事件 `before` / `after` 均为 `EmploymentRecordEvent`（`effectiveDate` = 旧 / 新离职生效日，`lastWorkDate` 旧 / 新）。
- 继任订阅方现为空实现（`succession/exit-store.ts:164`，注释引用 DEC-440 / F-096），本设计不改；F-096 定口径后只改订阅方。
- 替代（改到今天以后）不是“改期事件”：前单走 `onRecordDeleted`（继任侧把申请标 `delete_revert`，不恢复已结束记录），后继单到期走 `onRecordMaterialized`——这与 F-096 待定的“结束日是否跟随”相互独立，F-096 定口径时如需把替代也视为改期，在 `exit_requests.supersedes_business_id` 上即可识别（本设计在两个事件的 meta 里带 `supersedesBusinessId`）。
- 未生效（approved）改期不触发任何钩子：下游都只认已落地记录（§10.6），到期按新日期自然处理（DEC-440 原文）。

## 17. 风险与遗留

- 契约以 main 上 F-007 设计 §2 / §3 为准（#83 已合并）；F-036 接管重建后，§10.1 规则 T 与 §5.9 的保留流程检查需随 F-036 设计复核。

- 直接离职“保存即 approved、到期原子生效”与直接调动不同，随 B2 在规格 `30` §1.4 补说明。
- §6-1 预减绑定周期依赖“重聘开新 `employment_cycles` 行”；若 R2-T01 改为复用旧周期，须同步改 `pendingExits` 的截止条件。
