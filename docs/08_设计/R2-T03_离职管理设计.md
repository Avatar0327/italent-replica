## 3. 状态机与视图口径（DEC-125 / 215、Q-M0-86；未来直接离职不提前落地）

申请单状态完全复用 `EmploymentState`。**直接离职也走 `approved → effective`**：保存即“已确认待生效”（approved），最后工作日已过则保存事务内立即生效；否则到期由定时任务原子生效（P2-04）。

```
[草稿 draft] ─提交→ [审批中 in_review] ─驳回→ [已驳回 rejected] ─修改重提→ in_review
                      │ 不同意办结 → [disapproved]        │ HR 撤销离职 → [voided]
                      ▼ 最后节点同意（confirmed 阶段：编制预减 R、approval_passed 转交、交接自动发起端口）
              [审批通过 approved] ──原生效日 E ≤ 今天→ 同事务 activateExit
                      ▲                 │ 未到 → 停在 approved，只有申请单
   [直接离职保存] ─────┘（confirmed 阶段：编制预减 R、approval_passed 转交；不自动发起交接 DM-R14）
                                        │ HR 撤销 → [voided]（无版本可删，DEC-215）；改期 → 新载荷版本仍 approved
                                        ▼ 到期（activateExit，一个保存点）
              [已生效 effective]  最终日期（契约 §DEC-272）→ 版本链新增离职记录（人员状态 8）→ 下游效果
                      │ 撤销 → [deleted]（墓碑 + 时间轴恢复；版本 / 事件 / 台账保留）
                      │ 改期到过去 → 同一业务重定位；改期到今天以后 → [deleted] + 后继单（§7.2）
```

**迟到生效**（契约 §DEC-272 / 278）：实际执行日 a 晚于原生效日 E 才算迟到；a = E 当天执行属正常，不顺延。**简单迟到**（[E, a) 内同一员工没有其他任职版本或业务）：最后工作日 L' = a − 1、生效日 E' = a，离职记录当天落地起始当天。**非简单迟到**（区间内另有调动、组织调整等记录或业务）：fail-closed，不执行，记“生效失败：需重建，待 HR 处理”（DEC-278），重建本身属 F-036。

| 视图 | 谓词（读申请单 / 状态事件 / 扩展行，不读版本链） |
|---|---|
| 离职中的员工 | kind=leave 最新状态 ∈ {draft, in_review, approved, rejected}（含 mode=direct 的 approved）；默认最后工作日近 30 天 |
| 已完成的离职 | 最新状态 = effective |
| 撤销的离职记录 | `exit_cancellations` 有行 |
| 全部离职记录 | 以上 ∪ disapproved / voided / deleted |

`assertTransition` 放行（`transitions.ts`，仅 kind ∈ {leave, retirement}）：`activate` 允许 mode=direct；`revoke` 允许 approved → voided（经 §4A 门禁的撤销入口）；由离职编排器以 `byExit` 作废 draft / rejected / in_review / approved 的调动申请。

## 5. 生效事务编排

### 5.1 单一编排器 `activateExit`（唯一的 approved → effective 路径）

调用点：① `transitionEmployment(approve)`：写 approved 事件 → `confirmed` 阶段（§6 预减、`approval_passed` 转交、交接自动发起端口）→ E ≤ 今天且无前序 → `activateExit`；② `createEmploymentBusiness`（direct）：同上，但不调用交接自动发起（DM-R14）；③ `activateDueBusinesses → activateWithJudgement → transitionEmployment(activate)`：保存点内调用，失败整体回滚、`recordActivationAttempt(failed)`、HR 重试。

| 序 | 步骤 | 实现 | 失败处理 |

### 5.3 审批通过与直接离职保存时的立即生效

approve 事务内 `approveEmploymentBusiness` 判定 E ≤ 今天且无前序 → `activateExit` 全部步骤在审批事务内一次完成；a = E 当天不算迟到（契约 §DEC-272）；a > E（迟到审批，DEC-195② 同口径）→ 步骤 0：窗口内无其他记录则顺延为 L' = a − 1、E' = a 后立即执行；有则审批通过停在 approved 并记 failed 需重建（审批结论不受影响，HR 处理后重试）。直接离职 L 已过：保存事务内同样一次完成（输入 L 已过 → E ≤ a；a > E 时同样顺延，并在 0b 重验）。

### 5.6 继承矩阵、人员状态与“离职作为向后更新目标（不是重建目标）”（契约 §DEC-269）

**继承**（创建 / 落地时取值）：离职与其他业务同一套 `prepareInheritance / resolveEffectiveInheritance` 与 form 矩阵：INHERITED_FIELDS 预置字段有边；`isDepartmentHead` / `isStoreManager` / `addedSubordinateIds` 无边；employType / jobNumber / 人员状态 8 / 入职状态为系统派生；自定义字段 inherit:true 有边，inherit:false 在离职表单可编辑或未拖入为空、只读 / 隐藏继承（`07` §3.3）。`lastWorkDate` 与离职扩展字段是人工 intent；迟到顺延写入的 L' / E' 是**可信系统修订**（保留原意图版本，追加系统命令，契约 §DEC-272）。

**向后更新目标**：离职 / 退休版本永不作为传播来源（`forwardUpdate: false`、状态传播跳过；#83 合并后归一），但是合法的向后更新目标。按契约 §DEC-269（范围 C'）：迟到执行 = 补录一条更早生效的记录，[计划日, 实际执行日) 内的组织调整按 #83 重算，之后的独立业务**包括离职不重建**，走 AC-FWD 值匹配向后更新（只替换等于旧值的字段，“是否部门负责人”不动，职位与部门同时变化按原站规则②）；`lastWorkDate`、生效日、离职扩展字段、人员状态 8 不在匹配范围。**“编制不重算，超编只记警告。离职记录的部门被替换时，已在旧部门释放的编制也不重算、只记警告。”**（契约原话）有意设回旧值会被误替换（已接受局限）：写审计、测试固定（B-52a）；在途审批保留发起时审批人，新查询按替换后部门判范围（B-52b）；每条替换记录标明“迟到执行触发的向后更新”。F-021 序列同步同样以离职记录为目标。F-022 状态传播按契约 §F-022（完成入职必须传播；离职 8 ≠ 来源前值不被改）。

**撤销 / 改期与状态**：撤销已生效离职 = 时间轴恢复前一条开放区间，其版本状态自然成为当前；重定位追加快照版本，状态随快照为 8。

- 时机映射：

| 配置 | 离职申请 | 直接离职（立即） | 直接离职（未来） |
|---|---|---|---|
| `business_effective` | `activateExit` 步骤 6 | 保存事务内步骤 6 | 到期步骤 6 |
| `approval_passed` | approve 事务内 `confirmed`，生效日 = 批准当天 | 保存事务内 `confirmed`（写 approved 事件后、`activateExit` 前） | 保存事务内 `confirmed`，生效日 = 保存当天 |

### 5.8 DEC-263②：离职与已落地未来直接调动的共存规则（P2-01）

条件：员工有已落地（effective）、起始日 S > L' 的直接调动记录 T。契约 §DEC-263②：只提示、不拦截、不自动删除，离职照常生效，T 到期执行时记失败交 HR。

| 时点 | 规则 |
|---|---|
| 预览 / 保存 / 提交 / 改期 | `warnings` 列出 T（可见者给调动与起始日；不可见者只给“存在未来生效的调动，需由有权限的人员处理”与件数）；不进确认令牌、不阻塞 |
| 离职落地（步骤 2） | `assertSuccessorSequence` 对 kind=leave 的这一种后继**放行**；`insertEmploymentTimeline` 写入离职后，把 T 的 `employment_timeline` 行**摘下**（删除该行，T 的 `employment_records`、载荷版本、状态事件、生效尝试、命令台账全部保留），离职记录区间开放到无穷；写 `exit_effects(future_transfer_detached, target = T, detail: { window: T 原区间 })` 与审计 `employment.exit.future_transfer_detached`。**员工从 E' 起即为离职，不会在 S 重新读为在职**（时间轴只剩离职为末尾）；T 在调动管理中仍显示为“已落地、待执行”并带警告 |
| T 到期执行（待复查队列 `activateMaterializedLinkage` / 待联动） | 检查 T 当前是否在时间轴上且前驱非离职：已被摘下 → 按 DEC-052 记 failed `EMPLOYEE_DEPARTED_BEFORE_TRANSFER`、HR 待办，不执行联动、不复查编制 |
| HR 处理 | ① 删除 T（R1-T11 `delete`：删除路径容忍“无时间轴行”，墓碑照写）；或 ② 撤销离职（§7.1）→ 恢复在职时按 `exit_effects.detail.window` 把 T 的时间轴行**挂回**原位置（重新计算区间，经 `assertRestoredPredecessor` 与 §6 确认协议），T 的待办随之清除 |
| 改期离职到 S 之后 | 等同撤销 + 后继单（§7.2）：挂回 T 后后继单到期再次按本节处理 |
| 查询 | 列表 / 详情 / 占编 / 在岗统计全部按时间轴，T 被摘下期间不计入；审计与台账可查 |

删除 v1.2 的 `EXIT_FUTURE_EMPLOYMENT_EXISTS` 失败路径。

### 5.9 保留流程的离职后校验（DEC-267③）

被 DEC-267 默认政策**保留**的在途流程（生效日 ≤ L' 的审批中调动 / 转正，终止日期 ≤ L' 的在途合同申请）在离职生效后才审批通过 / 定时生效 / 重试落地时：任职类经 `assertBusinessSequence`（前驱为离职 → `ACTIVE_EMPLOYMENT_REQUIRED`）及 `activation-checks.ts precheck` 新增“执行当日员工已离职”检查（`EMPLOYEE_DEPARTED`），合同类经合同模块在职校验；均按 DEC-052 记 failed、HR 待办，离职记录不变（B-56b 必测）。判定日期 = 执行当日的租户日与该员工时间轴。

## 6. 编制：批准即预减（DEC-266①；P2-02）

原站：离职 / 退休的编制时机 = “审批通过-立即释放”，**审批通过即在当前及未来周期计为预减**，不等生效日。

**释放时点 R 与生效日 E' 分离**：R = 审批通过 / 直接离职确认的租户日，写入 `exit_requests.pre_release_date`；改期、迟到顺延、替代都**不改 R**（后继单的 R = 其确认日）。

1. **投影层**（`establishment/employment-check.ts` + `membership-windows.ts`，共享文件）新增 `pendingExits(employeeIds)`：对最新状态 ∈ {approved, effective} 且未被撤销的 kind ∈ {leave, retirement} 业务，读取 R，把该员工当前及未来主职区间的上界裁到 `min(原上界, R)`——**从 R 起即不占编**，与员工仍在岗到 L' 无关（原站口径）。已生效后时间轴截断在 E' ≥ R，不影响。
2. **记账层** `establishment/exit-release.ts` 导出 `registerEstablishmentPreRelease(tx, ctx, business)`：在 `confirmed` 阶段写 `exit_effects(establishment_pre_released, detail: { departmentId, positionId, capacityId, releasedFrom: R, plannedEffectiveDate: E })`；生效时追加修正行记 E'（R 不变）。不追加编制版本、不改 `transfer_establishment_allocations`、不取编制锁。
3. **恢复占编**（撤销 approved、撤销已生效恢复在职、后继单作废使前单消失）：预减随业务作废 / 删除自动收回；对**整个恢复区间 `[R, 下一条起始或开放)`** 用同一投影重算峰值；超编 → DEC-258 只弹确认：409 `ESTABLISHMENT_EXCEEDED_CONFIRM_REQUIRED` + 明细（按可见范围裁剪），`confirmed: true` 重提后执行并记审计 `employment.exit.over_capacity_confirmed`。改期（含改晚）**不恢复占编**（R 不变）。
4. **与调动交叉**：审批通过未生效的调入申请（`pendingTransfers`）与预减同时存在：调动生效日 < R 的在新部门占编到 R；≥ R 的不占编（员工已预减）；> L' 的按政策作废或保留（§5.1-1）。
5. **迟到执行触发的向后更新替换离职记录部门**：契约原话——编制不重算，只记警告 `employment.exit.capacity_warning`；`exit_effects` 不追加修正行。
6. 撤销 / 挂回未来调动（§5.8）时，T 的区间重新进入投影，恢复区间校验含它。

| 离职状态 | 停用日 D 的计数规则（按**任职记录条数**，不按员工去重） |
|---|---|
| 审批通过、尚未生效（approved，申请或直接；最后工作日 L，生效日 E = L + 1） | 该员工在本组织的在职任职记录**从 E 起不计入占用**：D ≥ E → 不计；D < E → 照常计入 |
| 审批中（in_review）/ 草稿 / 已驳回 | **照常计入**（离职未定） |
| 已生效 | 时间轴已截断到 L，D ≥ E 自然不计（现有逻辑） |
| 作废 / 已删除的离职 | 不影响计数 |

实现：`planDeactivation` 的在职任职统计 SQL 增加一段 `NOT EXISTS (approved 离职 且 effective_date ≤ D)` 的排除条件（读取最新载荷与状态，与 §6 `pendingExits` 共用“approved 离职及其 E”的子查询）；提示文案条数随之变化；不改 F-019 对在途调入的计数口径。迟到顺延只在生效时发生，停用校验用的是申请当前载荷的 E。测试计划 B-61：D 在 E 前后各一例、审批中离职一例、作废离职一例、同员工两条记录（主职 + 兼职）按条数计一例。

## 7. 撤销离职（DM-R5 / R6、DEC-222）与改期（DM-R7）

### 7.1 撤销：`POST exits/:id/cancel`

| 当前状态 | case | 动作 | 下游清单（按 `exit_effects` 真实历史 + 前单链） |
|---|---|---|---|
| draft | process_voided | `delete` | 无 |
| in_review / rejected | process_voided | `revoke` → voided；cancel 实例 | 无 |
| approved 未生效 | approved_voided | `revoke(byExit)` → voided；预减收回，恢复区间 `[R, …)` 按 §6 确认 | `confirmed` 阶段已执行的转交与已自动发起的交接（PR-B 自动置终止） |
| effective 且今天 ≤ L'（重定位后或当天生效后立即撤销） | record_deleted | `delete`：墓碑、时间轴移除、前一条区间恢复；挂回被摘下的未来调动（§5.8） | 台账全部已执行效果 |
| effective 且今天 > L' | record_deleted_reinstated | 同上 + 恢复在职；恢复区间按 §6 确认；`personnelHooks.sync` | 合同（不自动恢复）、作废的调动申请（需重新发起）、保留流程的失败待办（恢复后可重试）、挂回的未来调动、终止的流程、职责转交、编制（已自动重占）；PR-B 交接 / 黑名单 / 账号 |

“不删历史”：版本、状态事件、`exit_requests`、`exit_effects`、命令台账全部保留，只追加 deleted 事件 + 墓碑 + 撤销记录，重建时间轴投影。**“没有任职时间轴记录”≠“没有历史”**：未生效撤销的申请没有任职记录与时间轴行，但其载荷版本、状态事件、确认令牌、效果台账仍在，可查可审计。

### 7.2 改期：`PATCH exits/:id { lastWorkDate }`

| 状态 | 处理 | 提示 |
|---|---|---|
| draft / rejected | 改载荷（E 重推） | 无 |
| in_review | 审批编辑端口 | 无 |
| approved | 新载荷版本仍 approved；R 不变；新 E ≤ 今天 → 同事务 `activateExit`；否则队列按新 E | §7.4 按方向检查 |
| effective，新 L ≤ 今天 − 1 | 同一业务重定位（`repositionEffectiveRecord`，抽自 `late-transfer.ts`）：追加快照版本、时间轴重插、顺序校验；已执行效果不改；R 不变 | §7.4 按方向检查；合同已按旧 L 终止 → 另列“合同实际终止日需手工更正” |
| effective，新 L ≥ 今天 | **替代**：前单 `record_deleted_reinstated`（§7.1，含挂回未来调动、§6 确认），同事务新建后继单（复制元数据，`supersedes_business_id`，approved，R = 今天，职责计划按 §5.7 过滤）；后继单到期 `activateExit`，按**当时**在途数据处理合同 / 流程 / 调动，恢复在职期间新增的流程自然纳入 | §7.4 “改到今天之后”方向（含职责转交）；并列出前单已执行、不自动恢复的效果 |

### 7.3 restore（恢复已删除离职）

不支持（§4）：已删除 / 作废的离职不能恢复为申请或记录；需要时另发新离职单。对 kind ∈ {leave, retirement} 的任何恢复端口返回 409 `EXIT_RESTORE_NOT_SUPPORTED`，有权限与无权限各一例（B-57）。

### 7.4 改期与撤销的下游数据检查（DEC-275①，照原站；DM-R5 / R7）

**改期**：保存成功后按改期方向检查**原最后工作日 L₀**上的下游数据，返回**不阻断**的清单 `downstreamHints`（保存已完成，清单只提示）：

| 方向 | 检查项（端口） |
|---|---|
| 改早（新 L < L₀） | 薪资档案、社保档案 |
| 改晚但仍早于今天（L₀ < 新 L < 今天） | 薪资、社保 + 假期余额、调休假、育儿假 |
| 改到今天之后（新 L ≥ 今天） | 以上 + 职责转交（`exit_effects(duty_transferred)` 与 linkage 子项，本 PR 真实实现） |

实现：`employment/exit-downstream.ts` 导出 `probeDownstream(tx, ctx, { employeeId, originalLastWorkDate, direction })`，按注册的探针端口逐项查询：薪资 / 社保 / 假期余额 / 调休假 / 育儿假 在复刻中尚无模块，**只留端口**（`DownstreamProbe` 接口，默认实现返回“模块未接入”且不列入清单）；职责转交与合同由本 PR 实现。清单每项 `{ kind, label, targets[], hiddenCount }`，`targets` 按查看人 DEC-177 可见范围裁剪，不可见的只计件数；文案走资源文件（Q-M0-94 原文待取证时替换）。

**撤销离职**：`POST exits/:id/cancel` 响应与 `exit_cancellations.downstream` 固定提示四类：**合同、职责转交、离职交接、薪资档案**（DM-R5 / 原站 W-517），其中合同与职责转交按 `exit_effects` 真实历史填充，离职交接由 PR-B 端口填充（PR-A 返回空列表但保留类目），薪资档案走探针端口（未接入时标“模块未接入”）；其他台账效果（作废 / 保留的调动、终止流程、挂回的未来调动、编制）作为附加项列在四类之后。全部按查看人裁剪。

测试计划：B-60 三个方向各一例（断言清单类目、职责转交目标、未接入端口的占位、范围外裁剪）；B-60a 撤销清单四类固定顺序与真实填充。

## 8. 在途调动确认（DEC-154 / 166 / 220；确认令牌）

- 发起 / 保存 / 提交不拦截在途调动。确认清单 = in_review 的调动申请（DEC-166）∪ approved 未生效且 `greatest(effective_date, 今天)` > L 的调动申请（DEC-220）；按 DEC-267 默认政策其中生效日 ≤ L 的 in_review 项在生效时**保留**而非作废，确认框文案区分“将作废”与“将保留，若在离职后才通过将生效失败”。
- 令牌：`ackToken = HMAC(tenantId, employeeId, L, sorted(S))`，只回传可见项 + `hiddenCount` + token；保存 / 提交 / 改期重算，不一致 409 `EXIT_PENDING_TRANSFER_ACK_REQUIRED`；完整集合与哈希写 `pending_transfer_ack`，不回传。
- `warnings`（不进令牌）：已落地未来直接调动（§5.8）、draft / rejected 调动申请（DEC-263③ 一律作废）、DEC-267 将保留的流程。

## 8A. 逾期迟到调动拦截（DEC-252①）

定义：`pendingActivations` 中 `kind='transfer' AND effectiveDate < 今天` 的项，三类：A `materialized = false` → 拦截；B `materialized && !reminderOnly`（已落地联动未完成）→ 拦截；C `reminderOnly` → 不拦截、warnings。判定函数 `findOverdueTransfers`（与 #83 合一）。拦截点经 §4A：create / submit / reschedule / 批量逐人 → 409 `EXIT_LATE_TRANSFER_PENDING`，错误体含可见项与 `hiddenCount`。approve / activate / cancel / delete 不拦截，由 §5.1-0a 兜底。边界 B-36～B-45（§12）。

## 8B. 劳务转正式 / 实习转正在途流程拦截（DEC-266④）

定义：kind ∈ {`intern_regularization`, `labor_regularization`（R2-T07 编码常量）} 的任职申请，最新状态 = in_review，载荷生效日 ≤ L。入口（create / submit / reschedule）命中 → 409 `EXIT_REGULARIZATION_IN_FLIGHT`（按可见范围裁剪）；**迟到顺延后在 §5.1-0b 用 L' 重验**，命中 → 生效失败交 HR（B-55d：输入 L = 10-10、实际执行 10-16 → L' = 10-15，存在 10-15 实习转正在途 → 离职 failed、待办，离职记录不变）。生效日 > L' 的同类流程按 §5.1-5 政策处理；approved 未生效且 ≤ L' 的不拦截（排在离职前落地）。

## 10. 与 #83 F-007、#96 F-026、F-022 的衔接

- **#83（契约）**：本设计凡涉及 DEC-263①②③ / 267 / 269 / 272、离职与调动先后顺序、F-022 状态传播、`employment.leave.rescheduled` 均引用 #83 v4“共享契约：离职与迟到重建”；`resolveLateExecution` 与 `findOverdueTransfers` 两边共用同一实现（谁先合并谁实现）。三组边界测试（生效日当天执行、晚 1 天、跨月）由实现方写、另一方复用。#83 合并后补跑交错用例：
  - A. 调动计划 10-10 迟到，离职 L = 10-15 / E = 10-16，10-18 一起到期：窗口 [10-16, 10-18) 内没有**已落地**记录（迟到调动尚未执行，属 0a）→ 简单迟到，步骤 0 → L' = 10-17、E' = 10-18；调动顺延到 10-18 = E' → 同日调动在前（契约顺序）→ 调动 10-18 生效，离职 10-18 紧随其后生效，不作废。HR 10-18 先单独重试调动再跑离职：调动落地于 10-18，不在窗口 [10-16, 10-18) 内 → 仍为简单迟到，结果相同。
  - A'. 同上，但另有一条 10-17 如期生效的直接调动（或组织调整）：窗口 [10-16, 10-18) 内有已落地记录 → 离职 fail-closed `EXIT_LATE_REBUILD_REQUIRED`、HR 待办；HR 删除 / 处理后重试。
  - B. 调动计划 10-05 迟到至 10-12 执行，组织调整 10-08 在重算窗口内，离职 10-16 已生效（部门旧值）：组织调整重算；离职记录按值匹配替换部门，状态 8 不变，旧部门已释放编制不重算、记警告。
  - C. 离职已生效后补录更早的直接调动并向后更新：离职记录按 forward 矩阵更新，状态 8 不变。
- **#96 / DEC-258**：§6 恢复区间与确认协议；合并后核对 `clipMembership` 能否承接 `pendingExits`。
- **F-022**：§5.6；不新建字段；状态传播按契约。
