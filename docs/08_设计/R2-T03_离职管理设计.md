## 1. 总体思路：离职 = 任职业务 `kind='leave'` 的申请单层 + 离职扩展行

与调动同构（DEC-125 / 215）。调动已经把“申请单层”做成了通用任职业务：`employment_business_objects`（业务头 + revision）、`employment_payload_versions`（载荷版本链）、`employment_state_events`（状态事件）、生效时才写 `employment_records` + `employment_timeline`；调动特有元数据放在薄扩展表 `transfer_requests`。

## 2. 数据模型

### 2.1 新表（批 B1a 一个迁移，`pnpm db:generate` 基于最新 main 生成，当前 main 到 0129）

**`exit_requests`**（离职扩展行，1:1 任职业务，照 `transfer_requests`）

| 列 | 类型 | 说明 |
|---|---|---|
| tenant_id, business_id | uuid, PK | 复合外键 → `employment_business_objects(tenant_id, employee_id, id)` |
| employee_id | uuid | 冗余便于范围谓词与审计归属 |
| **staff_id** | uuid | **离职所属任职周期**（`employment_cycles.id`，即任职记录的 `staff_id`）：创建时等于载荷 `selectedStaffId`（`write-service.ts:434 selectEmploymentCycle` 按生效日选定，`updateEmploymentBusiness` 以 `expectedStaffId` 锁定不变）；落地时 `cycleForMaterialization` 用同一值，前驱周期已不同 → `EMPLOYMENT_CYCLE_MISMATCH`（§5.1-2）。离职只结束这一周期；编制预减（§6-1）、停用计数（§6A）、§6B 投影都绑定它 |
| mode | text | `application` / `direct`（历史导入的 `import` 随 F-139 再加） |
| initiator | text | 发起方式 `hr` / `self`（员工本人）/ `manager`（经理代发，DEC-283）；入口由 F-020 做，服务层由本设计（批 B2a）实现（§4B） |
| initiator_user_id | uuid | 发起人账号，与被离职人 `employee_id` 分开记录（DEC-283） |
| attachment_refs | jsonb, null | 本人申请的“手写离职申请”附件元数据 ID（AGENTS §10 附件约定：先登记元数据再上传）；本设计只存引用，上传与下载验权随 F-020 |
| process_code | text, null | 申请单发起时绑定的流程编码；直接离职为空 |
| exit_type_code | text, null | 离职类型（`exit_types` 字典，不混用 `transfer_types`）；self / manager 发起时可空，confirmed 前必须补齐（§4B） |
| reason_code, whereabouts_code | text, null | 离职原因、离职后去向（DM-R1，只能选启用项） |
| handover_employee_id | uuid, null | 交接人（只存值，交接流程归 BE-8） |
| add_to_blacklist | boolean, default false | 只存值（DM-R2，黑名单归 BE-8） |
| compensation_amount, non_compete_amount, last_pay_date, social_insurance_end_month, annual_leave_settled, tax_period, tax_year, employer_name | 按类型 | Q-M0-85 表单字段，只存值 |
| actual_leave_date | date, null | 实际离岗日（≤ 最后工作日；只存值，账号停用 DM-R9 另行任务） |
| pending_transfer_ack | jsonb | 确认过的在途调动完整集合与令牌哈希（§8，不回传） |
| batch_id | uuid, null | 批量申请批次号 |
| duty_transfer_timing | text | 转交时机快照（`business_effective` / `approval_passed`，DEC-213） |
| **pre_release_date** | date, null | **编制预减时点 R**（DEC-266①）：审批通过 / 直接离职确认的租户日；与生效日分离，迟到顺延不改它（§6） |
| created_at | timestamptz | |

不设状态列、不设 revision 列。

**`exit_types` / `exit_reasons` / `exit_whereabouts`**（B60～62 三个字典）：`id, tenant_id, code, name, enabled, display_order, revision, created_at, updated_at`，`(tenant_id, lower(code))` 唯一，`id` 主键（照合同主数据 `contract_types` 的 `master()` 形态，`packages/db/src/schema/contracts.ts:33`，不照 `transfer_types` 的“出厂默认 + 覆盖”形态：离职字典要支持新增、停用与改名）。按租户的**配置对象**：写入走 `tenant.employment.configuration.write`（管理员 `other_settings`，与 `PUT transfers/settings` 同一授权，不产生标准授权码），读取对持 EMPLOYMENT `object.view` 者开放（表单下拉、列表显示名称）。停用：只有启用项可选（DM-R1）；已保存单据引用停用项仍按编码显示名称；**删除不提供**（照合同主数据，被引用的编码不能消失）。字典表单字段原站 60 / 62 截图只在本机：本设计取“名称（必填）、编码（必填、租户内唯一、保存后不可改）、启用、显示顺序”，是否另有“说明”“离职类型分类（主动 / 被动）”**待补证**（§19，若有由 BE-8 自动加黑一并补列）。迁移 seed 预置：`exit_reasons` 的 `personal`（个人原因）/ `family`（家庭原因）；`exit_whereabouts` 的 `other_industry`（离职去其他行业）/ `same_industry`（离职去同行业）/ `startup`（自主创业），自助子集依赖这些编码（§4B）；`exit_types` 的 `voluntary`（主动离职，R1d W-845 原站可见）/ `involuntary`（被动离职，AC-DM-06 用语），使 confirmed 前“离职类型必填”（§4B）开箱可用。

**`exit_effects`**（离职在确认 / 生效时对下游产生的效果台账，只追加）

| 列 | 说明 |
|---|---|
| id, tenant_id, business_id, employee_id | FK 业务头 |
| phase | `confirmed`（审批通过 / 直接离职保存）/ `effective` |
| kind | `establishment_pre_released` / `contract_terminated` / `contract_deleted` / `contract_request_withdrawn` / `application_voided`（被离职作废的任职申请，`detail.kind` 记调动 / 转正等，DEC-496①）/ `future_transfer_detached` / `duty_transferred` / `duty_failed`（v1.6 的 `transfer_retained` / `process_retained` / `process_terminated` 删除：本设计不再保留在途申请，F-138 再议） |
| target_type, target_id | 合同 ID、调动业务 ID、审批实例 ID、联动子项 ID 等 |
| detail jsonb | 合同终止日、调动原生效日 / 被摘下的时间轴窗口、流程类型、转交接收人等 |
| command_id, created_at | |

用途：① 生效重试的幂等判断（同 business_id + phase + kind + target 已有行则跳过）；② 撤销的“需手工处理的下游数据”清单——**只按台账真实历史生成**；③ 作废申请的通知与撤销离职清单里的“已作废、需重新发起”项；④ 撤销离职时把被摘下的未来调动时间轴行按 `detail.window` 重新挂回（§5.8）。

**`exit_cancellations`**（撤销的离职记录，一次撤销一行、不删除）：`id`、`business_id`、`employee_id`、`state_before`、`case`（process_voided / approved_voided / record_deleted / record_deleted_reinstated）、`reason`（必填；DM-R5 允许事后在「撤销的离职记录」视图修改，故另设 `revision`，修改写审计 before / after，其余列不可改）、`downstream jsonb`、`command_id`、`actor_user_id`、`created_at`。

## 3. 状态机与视图口径（DEC-125 / 215、Q-M0-86；未来直接离职不提前落地）

### 3.1 状态机

申请单状态完全复用 `EmploymentState`。**直接离职也走 `approved → effective`**：保存即“已确认待生效”（approved），最后工作日已过则保存事务内立即生效；否则到期由定时任务原子生效（P2-04）。

```
[草稿 draft] ─提交→ [审批中 in_review] ─驳回→ [已驳回 rejected] ─修改重提→ in_review
                      │ 不同意办结 → [disapproved]        │ HR 撤销离职 → [voided]
                      ▼ 最后节点同意（confirmed 阶段：编制预减 R、approval_passed 转交、交接自动发起端口）
              [审批通过 approved] ──原生效日 E ≤ 今天→ 同事务 activateExit
                      ▲                 │ 未到 → 停在 approved，只有申请单
   [直接离职保存] ─────┘（confirmed 阶段：编制预减 R、approval_passed 转交；不自动发起交接 DM-R14）
                                        │ HR 撤销 → [voided]（无版本可删，DEC-215）；最后工作日创建后不可改（§7.2）
                                        ▼ 到期（activateExit，一个保存点）
              [已生效 effective]  最终日期（契约 §DEC-272）→ 版本链新增离职记录（人员状态 8）→ 下游效果
                      │ 撤销 → [deleted]（墓碑 + 时间轴恢复；版本 / 事件 / 台账保留）
```

**两条办理路径（B15，补证结论 R2c / W-831～837）**：① **离职申请**（HR 端或 F-020 的自助 / 代发入口）走审批（本租户流程 开始 → 直接上级 → HR 访谈 → 结束，即预置 `StandardDimission`），审批通过后出现在「离职中的员工」、审批状态“审批通过”，到期生效；② **员工档案 → 离职 → 保存**（直接离职）不产生审批，保存即 approved（L 已过则同事务生效）。两条路径生效结果相同：新增一条离职任职（开始日 = 最后工作日次日 E′，业务类型“离职”，人员状态 8 离职；详情“任职状态”对 kind ∈ {leave, retirement} 的记录由读模型显示“任职结束”，不加列），前一条任职区间截断到 L′；L′ 当天仍为原人员状态（如正式），E′ 起为离职；生效后进入「已完成的离职」与人员模块“离职人员”列表。R2c 观察到的“改到过去日期后进入已完成的离职”属人工改期，转 F-140（DEC-499）；本设计中最后工作日已过的离职只经两条路径进入「已完成的离职」：直接离职保存时 L 已过（同事务生效），或申请审批通过时 E ≤ 今天（§5.3）。

**迟到生效**（契约 C-1 / C-2、F-007 §2）：实际执行日 a 晚于计划生效日 E（§5.0A `plannedEffectiveDate`：首次系统顺延前的日期；离职日期创建后不可人工修改，未顺延时即创建时的 L + 1）才算迟到（`resolveLateLeave`）；a = E 当天执行属正常，不顺延。区间 [E, a) 的成员按 F-007 §2-2 的**位置规则**计算（与调动同一实现 `lateWindowBlockers`，§5.1-0）：离职按 `timelinePosition(E, 离职)` 得到插入位置，位置在其后且 `start_date < a` 的任职版本（不分 kind）∪ 原计划日 ∈ [E, a) 且按 C-3 同日规则排在离职之后的未落地申请（draft / in_review / approved / rejected 都算）。**区间为空**（简单迟到）：L′ = a − 1、E′ = a，离职记录当天落地。**区间非空**：fail-closed，不执行，记 `failed` 原因 `REBUILD_REQUIRED`“生效失败：需重建，待 HR 处理”（DEC-278③），重建属 F-036。

### 5.0 执行顺序单一入口（DEC-496④；关闭第 5 轮 P2-01）

**问题**（第 5 轮 P2-01）：main `pendingActivations`（`activation-store.ts:58`）的排序只对调动用 `greatest(effective_date, 今天)`，其他 kind 用原生效日。迟到调动 T（原计划 10-10）与离职（E = 10-16）在 10-18 同时执行时，T 排在 10-18、离职排在 10-16，队列是“离职 → T”，`activationPredecessors(离职)` 为空，v1.6 的规则 T 拿不到 T；离职自己的区间 [10-16, 10-18) 也不含原计划 10-10 的 T，于是离职先落地。根因是**排序与“迟到后实际写入哪一天”用了两套日期**。

**唯一规则**：同一员工的全部待生效业务（`pendingActivationState` 定义的集合：已批准未落地申请、本设计纳入的 approved 直接离职、待复查 / 待联动的已落地调动）按**最终执行日期**排成一条队列，前序集合**只从这条队列截取**，任何入口（审批通过落地、调度到期、HR 重试、`activate` 端口）都不另算先后。

### 5.0A 计划生效日的唯一来源（v1.9 按 DEC-499 收窄；DEC-431①）

**背景**：第 6 轮 P2-01 是“排序与迟到窗口各读一种计划日”；v1.8 把两处统一到一个函数，但函数要从事件流里区分“人工改期”（意图）与“迟到顺延”（实际），第 7 轮 P2-01 证明同一事务写出的两类事件共用 `created_at`、靠随机 UUID 排序，计划日不可靠。DEC-499 把人工改期整体转 F-140（§21）：本设计中离职日期创建后不可人工修改（§7.2，后台统一拒绝），于是事件流里只剩系统顺延，计划日的定义随之收窄。

**唯一规则**：全系统只有一个“计划生效日”函数，所有需要“原计划日 / 计划日期”的地方（排序、时间轴同日位置、迟到窗口的起点与成员、前序判断、确认清单、逾期判定、展示）都只调用它；不再有任何直接读顺延事件或直接读载荷日期来充当计划日的写法。

| 项 | 定义 |
|---|---|
| 名称与签名（SQL，保留 main 名称与签名，改函数体） | `apps/api/src/modules/employment/timeline.ts`：`plannedEffectiveDate(tenantId: string, businessId: SQL, fallback: SQL): SQL` |
| 名称与签名（纯函数镜像，供单测与 domain 推演） | `packages/domain/src/employment/execution-order.ts`：`resolvePlannedEffectiveDate(input: { latestPayloadEffectiveDate: string \| null; lateExecutions: readonly { originalEffectiveDate: string }[]; fallback: string }): string` |
| 输入 | ① 该业务在 `employment_outbox` 中的**系统迟到顺延事件**：`employment.transfer.rescheduled`（main 只由 `late-transfer.ts:135 postponeLateTransfer` 写出，载荷 `originalEffectiveDate = 顺延前的业务日期`）与 `employment.leave.rescheduled`（契约 C-2 动作名，只由本设计 §5.1-0 `postponeLateExit` 写出，`reason: 'late-execution'`）。本设计**没有**任何写入口产生人工改期事件（§7.2 拒绝），因此不需要、也不再有区分事件原因的分支；② 该业务最新载荷版本（`employment_payload_versions` 按 `version_no` 最大）的 `effective_date` |
| 计算 | 1. 有顺延事件 → 计划生效日 = 全部顺延事件 `originalEffectiveDate` 的**最小值**（= 首次系统迟到顺延之前的日期，理由见下）；2. 没有顺延事件 → 最新载荷生效日；3. 没有载荷 → `fallback` |
| SQL 写法 | `COALESCE((SELECT min((e.payload->'after'->>'originalEffectiveDate')::date) FROM employment_outbox e WHERE e.tenant_id = … AND e.business_id = … AND e.event_type IN ('employment.transfer.rescheduled', 'employment.leave.rescheduled')), (SELECT p.effective_date … ORDER BY p.version_no DESC LIMIT 1), fallback)`；与 main 现行写法只差两处：事件类型加入离职顺延事件；`ORDER BY e.created_at, e.id LIMIT 1` 改为 `min(…)` |
| 与 main 的兼容 | 对 main 可达数据，`min` 与“按 `(created_at, id)` 取第一条”结果相同（下条“单调”）；调动、组织调整、序列同步、编制投影的计划日与排序不变（B-81 回归：main 现有 AC-TRF-F017-* 等用例原样通过） |

**为什么不受同事务事件先后影响**：

1. **没有人工事件**：创建后的人工日期变更在所有入口都被拒绝且无写入（§7.2）；v1.8 中“最后一条人工事件 M 之后的第一条顺延事件”的解析分支连同它依赖的事件先后一并删除。调动在 main 上本来就满足这一点：人工改日期只发生在 draft / in_review / rejected（`updateEmploymentBusiness`，含审批编辑），都在批准之前，即在任何顺延之前；approved 调动不能改载荷（`PAYLOAD_IMMUTABLE`）。审批编辑与同意在同一事务时，编辑先写载荷，随后顺延事件的原日期取的就是编辑后的载荷日期，仍是“首次顺延前的日期”。
2. **只剩系统顺延，且只追加、只往后**：每次顺延写入的 `originalEffectiveDate` 是顺延前的业务日期——创建 / 审批前编辑时的日期，或上一次顺延写入的执行日；顺延只把日期改到执行日 a ≥ 原日期。所以同一业务的顺延事件原日期单调不减，“首次顺延前的日期”恰是全部原日期的最小值。
3. **最小值与读取顺序无关**：同一事务写出的多条顺延事件（例如审批落地顺延后又在同一轮被重试）共用 `created_at = ctx.now`、`id` 为随机 UUID，按任何顺序读取，最小值都相同；最新载荷只在没有顺延事件时使用，此时按单调的 `version_no` 取，不依赖时间戳。
4. **离职的顺延事件只随落地持久化**：`postponeLateExit` 与落地同一保存点，落地失败整体回滚（§5.1），未落地的 approved 离职没有顺延事件，计划日 = 创建时的 L + 1。

**三种情况各取哪个日期**：

| 情况 | 取值 | 理由 |
|---|---|---|
| **人工修改日期** | 不存在：离职创建后任何入口改日期都拒绝（§7.2，`EXIT_DATE_IMMUTABLE` / `RECORD_DATE_IMMUTABLE`，无写入）；调动的人工修改都在顺延之前，计划日 = 当时的最新载荷 | 人工改期（意图与实际分字段存储、改期后重新入队）整体转 F-140（§21） |
| **迟到执行**（系统顺延：调动 `employment.transfer.rescheduled`；离职 `employment.leave.rescheduled`） | **首次顺延前的日期**（全部顺延事件原日期的最小值）；同一申请多次顺延仍保留同一原计划日 | 顺延只改“实际写入日”，不改计划（DEC-195①“改到同日后仍按原计划日排序”、契约 C-2“审批单上的原定日期不改”）；与 F-007 §2-2“首次改期事件”同义 |
| **撤销后重排** | 被撤销的离职（approved_voided → voided；record_deleted / record_deleted_reinstated → deleted）**离开队列与时间轴**，任何读取点都不再读它的计划日；其余业务各自按本函数取自己的计划日，不因离职撤销而改变；撤销已生效离职时挂回的 T 仍按 T 自己的事件取计划日；撤销后重新办理离职是新业务，计划日 = 其载荷生效日 | 撤销不写顺延事件；队列与区间只由“仍在队列 / 时间轴上”的业务组成，撤销后的重排只需重新读队列（`activateDueBusinesses` 每次落地后重读，`retryActivation` 每次重读） |

**最终执行日期也只经它**：§5.0 的 `finalExecutionDate({ kind, plannedEffectiveDate, … executionDate })` 的 `plannedEffectiveDate` 参数一律传本函数的结果（调动 / 离职：max(本函数, a)；其他 kind：本函数）。对可达状态它与“max(最新载荷日, a)”恒等（顺延写入的载荷日都是某个已过的执行日，≤ 今天），因此 main 的 `greatest(p.effective_date, today)` 写法结果不变；但设计与实现统一写成“max(计划日, a)”，不再出现第二种日期来源。

approve 事务内（`approveEmploymentBusiness`）E ≤ 今天 → 调用 `activateExit`，按 §5.1 同一顺序：0a 前序（§5.0 队列；有未执行的前序则停在 approved、不记尝试，交调度按队列推进；有失败 / 挂起的前序则记 `suspended`，`trigger = approval`）→ 0 迟到判定（a = E 当天不算迟到；a > E 时区间为空则顺延为 L′ = a − 1、E′ = a 并落地，区间非空则审批通过停在 approved 并记 failed `REBUILD_REQUIRED`）→ 后续步骤在审批事务内一次完成。审批结论不受落地失败影响（审批动作本身成功，与 F-007 §2-3 审批落地失败同一落点）。直接离职 L 已过：保存事务内同样调用 `activateExit`（输入 L 已过 → E ≤ a；a > E 时同样顺延，并在 0b 重验）。E > 今天：停在 approved，到期由调度按 §5.0 队列执行。

**main 现状**（`ports.ts:8`，已导出、无调用方）：`handleContractsOnExit(tx, ctx, { employeeId, lastWorkDate })` → `lockEmployee` → `checkScope` → 读合同设置 → 私有 `cancelExitRequests`（撤回状态 ∈ {approved, in_review, returned}、类型不在“离职后可签类型”`postExitTypeIds`、且 **`request.effectiveDate > lastWorkDate`** 的在途合同申请：有运行中实例则 `approval/actions.ts cancel`，申请置 `withdrawn`，审计 `contract.request.exit_delete`）→ 逐份合同：`postExitTypeIds` 类型与作废合同跳过；**起始日晚于最后工作日的合同软删除**（`deleteContract`，即 DEC-484 / CT-R14 的“系统自动删除留给离职”）；有效且终止日为空或晚于最后工作日的合同**原地终止**（`setContractState(…, 'terminated', lastWorkDate, 'exit')`，实际终止日 = 最后工作日、终止原因 exit）。合同侧写 `contract.*` 审计与 `contract_outbox`。

**本设计的改动（批 B3-2，合同模块共享文件，改动随离职 PR 提交、合同模块方审一并核对）**：

1. 签名不加政策参数；返回 `{ terminated[], deleted[], withdrawnRequests[] }`（合同 / 申请 ID、类型、日期、申请的审批实例 ID），离职侧据此写 `exit_effects`（`contract_terminated` / `contract_deleted` / `contract_request_withdrawn`）。
2. `cancelExitRequests` **去掉日期过滤**（DEC-496①：在途合同申请默认作废，回到 DEC-222 原文“在途合同流程全部终止，`cancelExitRequests` 不再按日期过滤”；DEC-267 的“按终止日期保留”转 F-138）：状态 ∈ {approved, in_review, returned} 的在途合同申请全部撤回（有运行中 / 退回中的审批实例则 `cancel`，申请置 `withdrawn`，审计 `contract.request.exit_delete`，均为 main 现有动作），只保留既有“离职后可签类型”`postExitTypeIds` 豁免——这些类型由合同设置明确允许在离职后签订，合同模块 `service.ts:370 validateReferences` 对它们放行，不属于“被离职保留、此后需要拒绝”的流程，因此不需要 F-138 的拒绝机制（第 5 轮 P2-04 的反例针对的是按日期保留的普通类型，已不存在）。
3. 取锁：合同侧 `lockEmployee` 对 `employment_employees` 取 FOR UPDATE，离职事务此前已持同一行 FOR NO KEY UPDATE（§5.2 ②），同事务升级，不引入新的锁序。
4. 范围：`checkScope` 用离职编排器构造的**系统合同上下文**（`scope` 为空，与调度器同一做法）——合同的终止 / 删除 / 撤回是离职生效的系统后果，授权已在离职门禁完成（§4A）；返回给 HR 的清单仍按查看人的合同 `object.view` 与字段权限裁剪（§7.4、§9.1）。
5. 时点：生效时调用（步骤 4，L′ 为最终最后工作日）；Q-M0-100（“审批通过即终止”还是“生效才终止”）仍未取证，若取证为前者再挪到 `confirmed` 阶段（§19）。
6. 撤销离职不自动恢复合同（DEC-222）：撤销清单列出被终止 / 删除的合同（§7.4）。**main 没有“恢复被离职终止的合同”的入口**：`service.ts:48 correctedState` 只允许到期终止（`terminationReason = 'expiry'`）延期恢复，离职终止的合同编辑即 `CONTRACT_TERMINATION_PROTECTED`；软删除的合同也没有恢复入口（F-128 / DEC-484 删去了手动删除，恢复更无入口）。因此撤销清单给出的“手工处理”是**重新签订合同**（新建 / 续签），恢复原合同的入口是否要做 → §19 待补证、§10.2 F-014 接口。
7. 通知：被撤回申请的申请人按 §5.5 收到站内消息（main 的 `cancelExitRequests` 不通知，本设计在端口返回清单后由离职侧统一发）。

### 5.6 继承矩阵、人员状态与“离职作为向后更新目标（不是重建目标）”（契约 §DEC-269）

**向后更新目标**：离职 / 退休版本永不作为传播来源（`forwardUpdate: false`、状态传播跳过；#83 合并后归一），但是合法的向后更新目标。按契约 §DEC-269（范围 C'）：迟到执行 = 补录一条更早生效的记录，[计划日, 实际执行日) 内的组织调整按 #83 重算，之后的独立业务**包括离职不重建**，走 AC-FWD 值匹配向后更新（只替换等于旧值的字段，“是否部门负责人”不动，职位与部门同时变化按原站规则②）；`lastWorkDate`、生效日、离职扩展字段、人员状态 8 不在匹配范围。**“编制不重算，超编只记警告。离职记录的部门被替换时，已在旧部门释放的编制也不重算、只记警告。”**（契约原话）有意设回旧值会被误替换（已接受局限）：写审计、测试固定（B-52a）；在途审批保留发起时审批人，新查询按替换后部门判范围（B-52b）；每条替换记录标明“迟到执行触发的向后更新”。F-021 序列同步同样以离职记录为目标。F-022 状态传播按契约 §F-022（完成入职必须传播；离职 8 ≠ 来源前值不被改）。

**撤销与状态**：撤销已生效离职 = 时间轴恢复前一条开放区间，其版本状态自然成为当前。

## 6. 编制：批准即预减（DEC-266①）

原站：离职 / 退休的编制时机 = “审批通过-立即释放”，**审批通过即在当前及未来周期计为预减**，不等生效日。

**释放时点 R 与生效日 E' 分离**：R = 审批通过 / 直接离职确认的租户日，写入 `exit_requests.pre_release_date`；迟到顺延**不改 R**，同一业务内 R 永不变。

1. **投影层**（`establishment/employment-check.ts` + `membership-windows.ts`，共享文件）。main 的占编投影 `projectedMembers`（`:175`）由两类输入组成：**时间轴主职记录**（`occupancyRows`，`:355`，排除 kind ∈ {leave, retirement}）与**按控编时机解析出的申请预占段**（`pendingTransfers`，`:383`：该员工 kind=transfer 的 in_review / approved 申请及待复查的已落地调动，起点 `greatest(载荷生效日, 今天)`；租户控编时机 `establishment/settings.ts` 的 `transferIn` / `transferOut` ∈ {`submitted`, `approved`} 决定审批中的申请是否已在目标岗位预占、是否已从原岗位扣出，`:223～:250`）。main **没有** `pendingExits`，approved 未生效离职现在不释放任何占用。本设计新增 `pendingExits(employeeIds)`：对最新状态 ∈ {approved, effective} 且未被撤销的 kind ∈ {leave, retirement} 业务读取 R 与所属任职周期 `exit_requests.staff_id`（§2.1），**对上述两类输入一并**扣掉预减区间——不论该段来自时间轴记录还是申请预占（DEC-496⑤，关第 5 轮 P2-03：v1.6 只写了时间轴记录，漏了申请预占段）。区间运算只调用 §6B.1 的纯函数（P 投影），`projectedMembers` 在合并成员区间后、`clipMembership` 之前调用它，不另写 SQL 判定。**预减 = 同周期段 ∩ 预减区间**：预减区间 = `[R, 下一周期入职日)`（下一周期 = `employment_cycles` 中 `entry_date > R` 的下一条，没有则开放）；对该员工属于 `x.staff_id` 周期的**每一段**（时间轴记录段 W，或申请预占段——申请没有 staff_id，按其载荷 `selectedStaffId`，未选定时按申请生效日所在周期）取 `段 \ [R, 下一周期入职日)`——**不用 L 过滤**：本周期内 R 之后开始的记录或预占（审批中途生成的组织调整、迟到批准后 DEC-278 拒绝生效而保留 approved 时的当前记录、审批中的未来调入申请）同样不占编（B-62b、B-77）；只有新周期（不同 staff_id）的段不受影响。重聘（R2-T01：开新 `employment_cycles` 行、新 staff_id，`inheritanceSourceId` 不跨周期）后的新周期记录照常占编，严格编制对调入新周期岗位的另一人照常拦截；第二次离职只释放第二周期（B-62 / B-62a）。从 R 起即不占编，与员工仍在岗到 L′ 无关（原站口径）。已生效后时间轴截断在 E′ ≥ R，且在途申请已在落地时作废（DEC-496①），不再有预占段。
   staff_id 的取得：创建时的载荷 `selectedStaffId`（§2.1，`selectEmploymentCycle` 选定、审批编辑以 `expectedStaffId` 锁定；日期创建后不可改，周期不会因改日期变化）；没有可选周期 → 既有 `EMPLOYMENT_CYCLE_MISMATCH` / 顺序校验 409（入口 §4A 已要求 L ≥ 当前周期入职日）。
2. **记账层** `establishment/exit-release.ts` 导出 `registerEstablishmentPreRelease(tx, ctx, business)`：在 `confirmed` 阶段写 `exit_effects(establishment_pre_released, detail: { departmentId, positionId, capacityId, releasedFrom: R, plannedEffectiveDate: E })`；生效时追加修正行记 E'（R 不变）。不追加编制版本、不改 `transfer_establishment_allocations`、不取编制锁。
3. **恢复占编**（撤销 approved、撤销已生效恢复在职）：预减随业务作废 / 删除自动收回；需要重算的段**不再按入口写公式**，统一按 §6B（P 投影操作前后差集 ΔP 的每一段重算峰值）。超编 → DEC-258“一律只弹确认、不拦截”（严格控编同样只确认）：沿用 main 已有的确认形态 409 `CONFLICT` + `reason: 'CONFIRMATION_REQUIRED'` + `warnings[{ reason: 'ESTABLISHMENT_EXCEEDED', capacityId, departmentId, positionId, from, to, peak, limit }]`（`establishment/transfer-service.ts:324`、`org/write-service.ts:255` 同一形态；v1.5 的 `ESTABLISHMENT_EXCEEDED_CONFIRM_REQUIRED` 是新造码，main 没有，删去），明细按查看人可见范围裁剪；请求带 `confirmed: true` 重提后执行并记审计 `employment.exit.over_capacity_confirmed`。§6B 的组织停用交集（拒绝）排在本确认**之前**。
4. **与调动交叉**：该员工审批中 / 已批准未落地的调入申请（预占段）与预减同时存在：预占起点 < R 的在目标岗位占编到 R；≥ R 的整段不占编（员工已预减）；离职落地时这些申请一律作废（DEC-496①，§5.1-1），预占随之消失；**撤销 approved 离职**时申请尚未被作废，其预占段从 R 起恢复，按 §6B ΔP 对目标岗位重新做 DEC-258 超编确认（§6B.3 推演 B）；**撤销已生效离职**时被作废的申请保持作废、不复活，没有预占要恢复（§7.5）。
5. **迟到执行触发的向后更新替换离职记录部门**：契约原话——编制不重算，只记警告 `employment.forward-update.capacity_warning`（契约 C-7，F-036 实现，recordKind = leave）；`exit_effects` 不追加修正行。
6. 撤销 / 挂回未来调动（§5.8）时，T 的区间重新进入 P 投影，自然出现在 ΔP 里（§6B 表 #1 / #2）。
7. 停用校验侧的离职排除（§6A.1，O 投影）同样限定 `r.staff_id = 该离职 staff_id`，与本节口径一致；两个投影由同一纯函数给出（§6B.1）。

## 6A. 组织停用校验与离职（DEC-275②，照原站 W-499～502）

### 6A.1 停用侧：离职计数

**main 现状**：`org/deactivation.ts:41 planDeactivation` → `assertSubtreeVacant`（`:112`）合计三项占用——在职人员 `employment/org-people.ts:100 countDepartmentStaff`（时间轴主职记录与 `[停用日 D, ∞)` 相交、kind ∉ {leave, retirement}，**按员工去重计人数**）、在途调入申请 `countPendingTransfers`（`:154`，按申请单条数，无日期过滤，DEC-196）、启用职位；任一非零 → 409 `ORG_SUBTREE_NOT_EMPTY`。已生效离职截断时间轴，自然不计；**approved 未生效离职不被考虑**（员工照常计入）。main 上没有 `TODO(Q-M0-92)` 标记（v1.5 的“替换 TODO”说法删去），DEC-275② 由本设计落实：

| 离职状态 | 停用日 D 的计数规则（DEC-275②：按**任职记录条数**计，不按员工去重） |
|---|---|
| 审批通过、尚未生效（approved，申请或直接，含生效失败仍为 approved；生效日 E 取 §5.0A 计划生效日（D-16）） | 该员工同 staff_id 的在职任职记录**从 E 起不计入占用**：D ≥ E → 不计；D < E → 照常计入 |
| 审批中（in_review）/ 草稿 / 已驳回 | **照常计入**（离职未定） |
| 已生效 | 时间轴已截断到 L′，D ≥ E′ 自然不计（现有逻辑） |
| 作废 / 已删除的离职 | 不影响计数 |

实现：`countDepartmentStaff` 改为按 §6B.1 的 O 投影计数——SQL 只取“子树内与 `[D, ∞)` 相交的时间轴主职记录 + 这些员工的 approved 离职（E、staff_id）”，是否计入由 §6B 纯函数判定，计数单位改为记录条数（DEC-275②；main 只有主职记录，兼职上线后（BE-7）按条计入同一投影）；文案条数随之变化；不改在途调入的计数口径。迟到顺延只在生效时发生，停用校验用申请当前载荷的 E（生效时若顺延跨过停用日由 §5.1-0c 拦下）。测试计划 B-61：D 在 E 前后各一例、审批中离职一例、作废离职一例、同员工同组织两条主职记录（E 前一条、组织调整后一条）按条数计一例、跨周期（旧周期 approved 离职不影响新周期记录）一例。

## 6B. 区间变化统一规则（v1.6 起，DEC-431①；v1.7 按 DEC-496⑤ 把申请预占段纳入 P）

v1.5 对每个入口各写一个“恢复区间 I”公式（`[E, 同周期下一条起始)`、`[E', E₂)`、`[R, min(…))` 等），复审 P2-01 证明这种写法会漏段：撤销 approved 离职撤掉的是**整个同周期**的停用计数豁免与编制预减，而公式只截到同周期下一条起始。v1.6 不再按入口写公式，统一为**同一投影函数 + 操作前后差集**：

### 6B.1 两个占用投影（纯函数，`packages/domain/src/employment/exit-occupancy.ts`）

| 投影 | 含义 | 用于 | 离职的作用 |
|---|---|---|---|
| **O（在职占用）** | 员工在某组织“在职”的日期段：时间轴上每条在职任职记录（main 只有主职；兼职上线后同口径按条计入）的区间，扣掉同 staff_id 的 approved 离职从 E 起的部分（§6A.1）；被摘下、待挂回的未来调动（§5.8）不在时间轴上，不计 | 组织停用校验（§6A.1 计数、本节反向校验） | approved：同周期记录在 `[E, ∞)` 不计；effective：时间轴已截断到 L′ |
| **P（编制占用）** | 员工在某部门 / 职位 / 编制上占编的日期段，两类输入：① 时间轴主职记录区间；② **按控编时机解析出的申请预占段**——该员工审批中 / 已批准未落地的调动申请（及待复查的已落地调动）在目标岗位的预占段与在原岗位的提前扣出，按 `transferIn` / `transferOut`（`submitted` / `approved`）决定审批中的申请是否已计入（main `projectedMembers` 现有口径，§6-1）。两类都扣掉同周期离职的预减区间 `[R, 下一周期入职日)` | 编制峰值与 DEC-258 确认 | approved / effective：同周期记录与同周期申请预占在 `[R, 下一周期入职日)` 不计；离职落地后在途申请已作废（DEC-496①），预占段消失 |

两个投影由同一个纯函数计算：`exitOccupancy(input: { records: TimelineSegment[]; applications: PreOccupancySegment[]; exits: ExitState[]; detachedTransfers: DetachedWindow[]; timings: { transferIn; transferOut } }): { o: OccupancySegment[]; p: OccupancySegment[] }`，差集 `newlyOccupied(before, after): OccupancySegment[]`。`TimelineSegment` = 时间轴记录（员工、staff_id、部门、职位、编制、区间）；`PreOccupancySegment` = 申请预占（员工、selectedStaffId、申请状态、目标 / 原部门与岗位、预占起点 `greatest(载荷日, 今天)`、终点 = 插入窗口结束）；`ExitState` = 离职（state、E、L′、R、staff_id）。O 只用 records（申请对 O 的影响是 `countPendingTransfers` 按申请条数的计数，DEC-196，不随离职状态变化，见 §6B.4 R-O2），P 用 records + applications。`planDeactivation` 的停用计数（§6A.1）、`projectedMembers` 的 `pendingExits`（§6-1）与本节反向校验**读同一实现**，SQL 侧只负责取数，判定在纯函数。

### 6B.2 唯一规则

对**任何**会改变离职状态或日期的操作 op（下表全部入口），在同一事务、按 §5.2 全局锁序取到 ④ `lockOrganizationSettings` 之后：

1. 计算 op 之前的投影 `O₀ / P₀` 与 op 之后（模拟）的投影 `O₁ / P₁`（同一纯函数，输入只差离职状态 / 日期 / 时间轴挂回与否）；
2. **新增段** `ΔO = O₁ \ O₀`、`ΔP = P₁ \ P₀`（按记录、组织 / 编制对象逐段求差，按 staff_id 不跨周期）；
3. `ΔO` 的每一段 `(record, departmentId, [from, to))` 调 `assertEmploymentDepartmentAvailableWithin(departmentId, from, to)`（`employment/references.ts` 新增的有终点变体：已持 ④ 锁 → `org/employment-validity.ts:14 employmentDepartmentDisable(dept, from)` → 返回的 `disabledOn < to`（to 开放则任一）才拒绝；既有无终点 `assertEmploymentDepartmentAvailable`（`:28`）不改）：段内任一天组织不可用 → **拒绝**（命令入口 409 `EMPLOYMENT_DEPARTMENT_DISABLED`，main 现为 `VALIDATION_FAILED` + reason，沿用；系统执行入口记生效失败，见下）；
4. `ΔP` 的每一段按编制峰值重算：超编 → DEC-258 确认协议（§6-3：409 `CONFIRMATION_REQUIRED` + `warnings[ESTABLISHMENT_EXCEEDED]`，`confirmed: true` 重提执行并记审计 `employment.exit.over_capacity_confirmed`）；系统执行入口（调度、重试、审批落地）不弹确认——它们只会出现 `ΔP = ∅`（R 不变，见下表 #3～#5），实现上断言为空，非空即视为实现错误 503 而不是静默放行；
5. 3 在 4 之前；任一步拒绝 → 整个命令不执行（前后读取相等）。被缩小的段（`O₀ \ O₁`、`P₀ \ P₁`）不需要校验。

## 8. 在途调动确认（DEC-154 / 166 / 220 / 496①；确认令牌）

- 发起 / 保存 / 提交不拦截在途调动。确认清单 S = 该员工 in_review 的调动申请（DEC-166，**不论生效日**，DEC-496①）∪ approved 未生效且**计划生效日** > L 的调动申请（DEC-220，契约 C-5：按载荷日期比较，不投影到今天；T 的计划生效日与离职的 L 都只取 §5.0A，L = 离职计划生效日 − 1，D-17）。确认框统一文案“离职生效时将作废以下调动申请（审批中的申请若在离职生效前已通过并生效则不受影响）”，原站 DEC-220 文案保留其“离职生效后会自动终止作废该任职”。approved 且计划生效日 ≤ L 的调动不进 S：两笔的计划日都取 §5.0A，T 的计划日 ≤ L < 离职计划日 E，所以无论是否迟到（最终执行日期相同时比计划日），它在 §5.0 队列中都排在离职之前，先于离职落地；若它失败，离职按 0a 挂起（不会被作废，B-85a）。
- 令牌：`ackToken = HMAC(tenantId, employeeId, L, sorted(S))`，只回传可见项 + `hiddenCount` + token；保存 / 提交重算（L 创建后不变，重算只反映在途调动集合的变化），不一致 409 `EXIT_PENDING_TRANSFER_ACK_REQUIRED`；完整集合与哈希写 `pending_transfer_ack`，不回传。

| **② 迟到重试 · HR 先重试 T**（10-18，`retryActivation(T)`） | 前提：T 最近一次是 failed（若调度还没跑过，main 返回 409 `NOT_FAILED`“等待定时生效”，结果同①）。T 之前没有前序 → `activateDueBusinesses(retry, T)`：T 再判区间仍含离职申请 → `REBUILD_REQUIRED`（重试目标因 REBUILD 失败，按 main 允许同轮再试其 blockers）；离职按终止依赖仍不豁免 → 已是同一 blockedBy 的 suspended，不重复记录；本轮没有任何项落地，不重读队列，T 不再试 | 同①（T failed、离职 suspended） |
| **② 迟到重试 · HR 先重试离职**（10-18，`retryActivation(离职)`） | 离职最近一次是 suspended（满足重试前提）；`before = [T]`，`blockingPredecessors` 因终止依赖不豁免 T，`unresolvedPredecessor` = T → **409 `PREDECESSOR_FAILED`（blockedByBusinessId = T）**，不写任何业务数据 | 同① |
| **③ 审批通过 · 离职 10-18 才批准**（T 已批准未落地） | 审批事务 → `confirmed` 阶段（R = 10-18 预减、`approval_passed` 转交）→ `activateExit` 步骤 0a：`activationPredecessors(离职) = [T]`；T 尚未执行 → 离职停在 approved、不记尝试（§5.3）；T 已失败 → 记 `suspended`（trigger = approval）。之后调度按①执行 | 同① |
| **③ 审批通过 · T 10-18 才批准**（离职已批准未落地） | main `approveEmploymentBusiness(T)`：`postponeLateTransfer` 先判区间 → 含未落地离职申请 → T `REBUILD_REQUIRED`（trigger = approval，审批动作本身成功，T 停在 approved）。之后调度：T 已失败（调度不自动重试）→ `unresolved = [T]`；离职按终止依赖挂起 | 同① |

**收敛状态**：T `REBUILD_REQUIRED`（blockers 含离职），离职 `PREDECESSOR_FAILED`（blockedBy = T）；两笔都不落地；时间轴、载荷版本数、调动状态、合同、`exit_effects`（除审批时已写的 `confirmed` 阶段预减行）逐项与执行前相等；HR 待办（`/activation-todos`）各一条。**HR 处理**（两条路径结果都确定）：
- 删除 T（approved 申请可 `delete`，`assertTransition`）→ 重试离职：0a 无前序 → 步骤 0 区间 [10-16, a) 为空 → 简单迟到 L′ = a − 1、E′ = a 落地；
- 或撤销离职（approved_voided，§7.1，经 §6B）→ 重试 T：区间 [10-10, a) 为空 → T 落地于 a。

**为什么必须有终止依赖**（B-11a 固定）：若按 §2.5 豁免离职，①中离职会先简单顺延落地（E′ = 10-18），并在步骤 1 把 T 作废（DEC-496①）——一笔原定先于离职生效的已批准调动被静默作废；而同一场景下 HR 若先撤销离职再重试，T 会成功。结果取决于哪笔先被处理，违反 DEC-278“需重建，待 HR 处理”的 fail-closed 口径。终止依赖让三类入口全部收敛到“两笔交 HR”。

**正例 A′（真正空区间的排序）**：离职 L = 10-09 / E = 10-10 已批准；调动申请 T 原计划 10-05，在 10-10 离职到期**之前**被批准（审批时 T 的区间 [10-05, 10-10) 内只有未落地离职申请，其原计划 10-10 不 < 10-10 → 区间空）→ T 简单迟到落地于 10-10。10-10 调度：f(T) 已落地不在队列；离职 a = E 不迟到、0a 无未解决前序 → 落地，“变更前”读 T（契约 C-3 边界 2）。**若离职先于 T 的批准落地**：T 仍是审批中，被离职步骤 1 作废（DEC-496①），之后无法再批准——这是 DEC-496① 的有意结果，v1.6 的“两种顺序结果相同”说法删去（它依赖已删除的保留政策）。B-11b 分别固定这两种顺序各自的结果。

**A″（区间非空的迟到离职）**：离职 E = 10-16 于 10-18 执行，另有 10-17 如期生效的直接调动 / 组织调整，或载荷 10-17 的 draft / in_review / approved / rejected 调动申请 → 离职 `REBUILD_REQUIRED`（DEC-278，区间按 F-007 §2-2 位置规则，§5.1-0）。其中 approved、载荷 10-17 的调动：f = 10-18，原计划 10-17 > 10-16 → 在队列中排在离职**之后**，不是离职的前序；离职先失败，该调动作为后序按终止依赖挂起，两笔交 HR（B-05b ⑤）。

**B（F-036 归属，不变）**：调动计划 10-05 迟到至 10-12 执行，组织调整 10-08 在区间内，离职 10-16 已生效：F-036 落地前该调动按 F-007 §2 记 `REBUILD_REQUIRED`；F-036 落地后离职记录按值匹配替换部门，状态 8 不变，旧部门已释放编制不重算、记警告（契约 C-6）。

**C（离职已生效后 HR 补录更早的直接调动）**：补录的直接调动生效日 ≤ L′、插在离职之前：按 main 既有顺序校验（`assertBusinessSequence` / `assertSuccessorSequence`）；离职记录作为 R1 值匹配向后更新目标（状态 8 不变，§5.6）。

### 10.2 F-014③（未来生效离职与合同恢复有效；已并入 F-016，DEC-179）

F-014③ 的两条路径在 main 上的现状与本设计的接口：
- **拦截路径（已在 main）**：`contracts/service.ts:75 assertRestorationAllowed`（“DEC-167④ / F-014”）在把到期终止的合同延期恢复为有效时，查两类离职：已生效（时间轴上 kind ∈ {leave, retirement} 的主职记录）与**最新状态 approved 且载荷生效日 > 今天**的离职业务（`employment_business_objects` + 最新载荷），最后工作日落在 `[合同生效日, 新终止日)` → 409 `CONTRACT_EMPLOYEE_DEPARTED`。本设计的离职单正是这两种形态（approved 业务头 + 载荷；生效后时间轴记录），**查询不用改就能识别本设计的离职**。唯一缺口：生效失败（`REBUILD_REQUIRED` / 挂起 / `EMPLOYMENT_DEPARTMENT_DISABLED`）而仍为 approved、载荷生效日已过去的离职不满足“> 今天”，会被漏掉 → 批 B3-2 把该条件改为“最新状态 = approved（不论日期）”，配测试 AC-CT-11 补例（B-74）。
- **端口路径（本设计）**：离职生效时 `handleContractsOnExit` 终止 / 删除合同、撤回在途申请（§5.4），即 F-014③“把离职生效时终止合同的端口接进离职流程”。

## 17. 风险与遗留

- 契约以 main 上 F-007 设计 §2 / §3 为准（#83 已合并）；F-036 接管重建后，§5.0 终止依赖是否放宽由 F-036 设计重新判定。
- §5.0A 改 `plannedEffectiveDate` 函数体（加离职顺延事件、取原日期最小值）：对 main 可达数据与“按 `created_at, id` 取首条”结果相同（B-81 回归）。§5.0 改动 `pendingActivations` 的排序第一键（离职与调动同式），会改变“迟到离职与其他业务同日”的队列顺序；main 上现有调动 / 组织调整用例不涉及离职，不受影响，B3 补等价测试与队列断言（B-11）。
- 规格 `30` DM-R8 中“不走审批的待办”（新员工融入、入职准备、信息采集）依赖 R2-T01 对象，本设计只留端口（BE-8 / R2-T01）。
- Q-M0-100（合同终止时点）、Q-M0-94（清单原文）仍按暂定口径集中实现。
- 直接离职“保存即 approved、到期原子生效”与直接调动不同，随 B2a 在规格 `30` §1.4 补说明。
- §6-1 预减绑定周期依赖“重聘开新 `employment_cycles` 行”；若 R2-T01 改为复用旧周期，须同步改 `pendingExits` 的截止条件。
- `countDepartmentStaff` 计数单位由人数改为记录条数（DEC-275②），会改变组织停用 409 详情里的数字；main 上依赖该数字的测试随 B3 一并更新（DEC-402：不考虑存量兼容）。
- 生效时 `precheck` / 落地引用校验对离职跳过部门可用性；实现时须确认没有其他依赖“离职记录部门必须可用”的路径（如人员投影）。
- 人工改期转 F-140 后（DEC-499），HR 要改最后工作日只能撤销重建：approved 单撤销会收回预减并经 §6B 校验，已生效单撤销恢复在职并留下撤销记录；原站可直接改期（R2c W-832），这是有意接受的能力缺口，由 F-140 补（§21）。F-140 合并前，前端编辑表单把最后工作日显示为只读。
- DEC-496① 作废范围比原站默认（DEC-267 按日期终止）宽：原站会保留的“生效日不晚于最后工作日的审批中申请”在复刻中被作废、需重新发起；按日期保留的可选政策随 F-138 再评估。

### 21.2 两次 P2 的根因

| 轮次 | 现象 | 根因 |
|---|---|---|
| 第 6 轮 P2-01：计划日来源分歧 | 离职 10-16 人工改到 10-30、调动 T 10-20、调度停到 11-01：排序第二键取“首次改期事件原日期”（含人工改期，得 10-16），迟到窗口只认迟到事件、没有就取最新载荷（得 10-30）→ 队列 [离职, T]、窗口不含 T → 离职落地并作废本应先处理的 T | 同一业务有两个“计划日”，各读取点自行解释事件 |
| 第 7 轮 P2-01：同事务事件无可靠先后 | approved 离职 E = 11-10，11-01 人工改到 10-20 并同事务立即生效、顺延到 11-01：人工事件 M（11-10 → 10-20）与顺延事件 X（10-20 → 11-01）共用 `created_at = ctx.now`（`employment/context.ts` 写 outbox），`id` 为 `gen_random_uuid()`；v1.8 规则“最后一条人工事件之后的第一条顺延事件”按 `(created_at, id)` 排序，计划日随机为 10-20 或 11-01，进而改变时间轴同日位置、前驱与继承来源（审查自构①②） | 人工计划与系统顺延写在同一种事件流、同一个载荷日期字段，靠事件先后区分“意图”与“实际” |

共同根因：**“计划日”是从事件流推断出来的，而不是独立存储的**。只要人工计划和系统顺延共用存储并依赖事件先后，计划日就会因读取方式或写入顺序而变。v1.9 去掉人工事件后，事件流里只剩系统顺延，计划日可以用与顺序无关的最小值得到（§5.0A）。

### 21.3 F-140 必须满足的约束

1. **事件要有单调序号或版本号**：凡需要区分先后的写入（人工改期、系统顺延、立即生效）都带业务内单调递增的序号（如载荷版本 `version_no`、状态事件 `event_seq` 同类列，在同一业务行锁下分配），读取一律按该序号；**不得**用 `created_at` + UUID 排序（同一事务共用 `ctx.now`、UUID 随机）。
2. **人工计划和系统顺延分字段存储**：人工计划日（意图，只有人工改期改它）与系统实际执行日（只有顺延与落地写它）分成两个字段或两类记录；§5.0A 的 `plannedEffectiveDate` 改为直接读人工计划字段（签名不变，D-1～D-18 自动跟随），不再从事件流推断。系统顺延不得改人工计划字段；人工改期不得写系统顺延事件类型（`employment.transfer.rescheduled` / `employment.leave.rescheduled`），本设计 §5.0A 的“取原日期最小值”只对系统顺延成立。
3. **改期后重新入队规则**：改期命令在同一事务内 ① 让该业务既有的生效失败 / 挂起记录按新计划重新判定（不沿用旧日期的失败原因），② 按新计划日重算 §5.0 队列位置与前序（`activationPredecessors`），③ 新 E ≤ 今天时是否同事务立即执行、立即执行又遇顺延时人工计划字段保持不变，④ 被它挂起的后序业务重新判定；approved 与 effective 两种状态、审批 / 调度 / 重试三类入口逐一推演。
4. **沿用本设计的统一规则**：改晚 / 重定位 / 替代各自经 §6B 求 ΔO / ΔP（停用交集拒绝、超编 DEC-258 确认）；§8 确认令牌与 §8A / §8B 门禁按新 L 重算；同一业务内 R 不变，替代的新单 R 另定；F-096 钩子调度（口径待用户）；改期下游清单（DEC-275①）；B-86 的拒绝点改为“放行并按上述规则处理”时，未放开的入口仍须保持拒绝且无写入。
5. **验收至少覆盖**第 6、7 轮的全部反例：10-16 → 10-30 与 T 10-20、停到 11-01；改早跨过 T 后共同迟到；两次改期；11-10 → 10-20 同事务立即顺延；同日已完成迟到调动的插入位置与继承来源。
