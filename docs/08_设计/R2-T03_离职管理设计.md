## 1. 总体思路：离职 = 任职业务 `kind='leave'` 的申请单层 + 离职扩展行

与调动同构（DEC-125 / 215）。调动已经把“申请单层”做成了通用任职业务：`employment_business_objects`（业务头 + revision）、`employment_payload_versions`（载荷版本链）、`employment_state_events`（状态事件：draft / in_review / approved / rejected / disapproved / voided / effective / deleted）、生效时才写 `employment_records` + `employment_timeline`；调动特有元数据放在薄扩展表 `transfer_requests`（tenant_id, business_id 为键）。

现有代码已经为离职铺好了底层：

| 现有能力 | 位置 | 离职直接复用 |
|---|---|---|
| 业务类型 `leave` 与最后工作日 | `employment/types.ts` BUSINESS_KINDS；`fields.ts:105` 离职必填最后工作日、生效日 = 最后工作日 + 1；`employment_payload_versions.last_work_date` / `employment_records.last_work_date` | 生效日推导、校验 |
| 顺序校验 | `write-service.ts:338 sequenceViolation`：离职后同周期不能再接业务，只能 rehire；`assertSuccessorSequence` 拒绝“离职 → 同周期调动” | 不改 |
| 人员状态 = 离职 | 迁移 0062 `employment_kind_status('leave') = 8`，插入触发器自动写；`employee-status.ts` STATUS_SETTING_KINDS 含 leave | 不传 status 即得 8 并继承入职状态 |
| 审批类型 | `packages/domain/src/approval/types.ts:344` `leave: employmentType('leave','离职','DimissionProcessNew')`；预置流程 `standard_leave`（直接上级 → HR 访谈，`presets.ts:96/135`）；`approvalTypeOfBusiness('leave')='leave'` | 流程匹配、发起、驳回重提、盲审沿用 employment 适配器 |
| 定时生效 | `activation-store.ts` 队列（最新状态 approved 的申请）、`activation-service.ts` 按序落地、`employment_activation_attempts` 失败 / 挂起记录（DEC-052 / 112）、HR 重试接口 | 到期生效、失败待办、重试 |
| 合同端口 | `contracts/ports.ts:8 handleContractsOnExit` | 生效事务内调用（需按 DEC-222 调整，见 §5.4） |
| 下属 / 组织角色转交 | `transfer/linkage/items.ts executeItem`（未导出）+ `transfer_linkage_versions / duties / runs / items`（FK 指向通用业务头，不限调动） | 抽成共享函数后复用（§5.7） |
| 可见与范围 | `employment/visibility.ts`（DEC-177）、`context.ts requireScopedEmploymentObject`（DEC-193） | HR 列表、详情、写入 |
| 审计 | `auditEmployment`（审计 + employment_outbox 同事务）、`audit/visibility.ts` RULES | 所有新写入口 |

因此 R2-T03 **不新建第二套申请单**，只增加：离职扩展行、撤销记录、下游效果台账、去向字典、两个租户配置项，以及“离职生效效果编排器”。

## 3. 状态机与视图口径（DEC-125 / 215、Q-M0-86）

申请单状态完全复用 `EmploymentState`，不新增状态值：

```
[草稿 draft] ─提交→ [审批中 in_review] ─驳回→ [已驳回 rejected] ─修改重提→ in_review
                      │ 不同意办结 → [disapproved]（办结不生效）
                      │ HR 撤销离职 → [voided]
                      ▼ 最后节点同意
              [审批通过 approved] ──生效日（最后工作日+1）已到→ 立即生效（同事务）
                      │ 未到 → 停在 approved，只有申请单，不进版本链
                      │ HR 撤销离职 → [voided]（无版本可删，DEC-215；#83 设计 v2 §8.1 同口径：无版本、无台账）
                      ▼ 定时任务到期
              [已生效 effective]  版本链新增离职记录（人员状态 8），前一条止于最后工作日
                      │ 撤销离职 → [deleted]（删除离职版本：墓碑 + 时间轴恢复；版本与事件不物理删除；#83 v2 §8.1 / §5）
[直接离职 direct] 保存即写入离职记录（最后工作日可为未来，记录先存在、未来起始）；下游效果到生效日执行
```

| 视图 | 谓词（全部读申请单 / 状态事件，不读版本链） |
|---|---|
| 离职中的员工 | 存在 kind=leave 业务，最新状态 ∈ {draft, in_review, approved, rejected}；默认最后工作日近 30 天（Q-M0-85 ③）。在岗统计不排除这些人（与原站一致，`30` §1.4） |
| 已完成的离职 | 最新状态 = effective |
| 撤销的离职记录 | `exit_cancellations` 有行 |
| 全部离职记录 | 以上 ∪ disapproved / voided / deleted |

`approved` 状态离职的 revoke：现有 `assertTransition` 只允许 in_review / rejected 撤销。按规格 30 §1.4“审批通过未生效 → 申请单作废”，`transitions.ts` 增加一条**仅限 kind ∈ {leave, retirement} 且由离职撤销入口调用**的放行（`approved → voided`），调动口径不变（`08` §6 审批通过只能删除任职）。共享文件改动，PR 描述列出。

## 5. 生效事务编排（DM-R4，DEC-052 / 056 / 166 / 186 / 195 / 213 / 220 / 222）

### 5.1 触发点与幂等

新增 `employment/exit-effects.ts`（归属 employment 车道）导出 `applyExitEffects(tx, ctx, business, phase)`，在以下三处调用，均在任职落地的同一事务 / 同一保存点内：

1. `materializeEmploymentRecord` 末尾：`payload.kind ∈ {leave, retirement}` 且 `effectiveDate ≤ 租户今天` → `applyExitEffects(..., 'effective')`（照 `queueTransferLinkage` 的挂接方式；退休 R2-T04 后续复用，本 PR 只对 leave 启用）。
2. 直接离职最后工作日在未来：记录已落地但 `effectiveDate > 今天`，写 outbox 事件 `employment.exit.effects.pending`，由 `pendingActivationState` 纳入复查队列（照已落地未来直接调动 `employment.transfer.recheck.pending` 的做法），到期由定时任务经 `activate` 路径的已落地分支调用 `applyExitEffects`。
3. `approve` 动作：转交时机为 `approval_passed` 时调用 `applyExitEffects(..., 'approval_passed')`（只执行职责转交；合同、作废调动、终止流程一律在生效时，DEC-222 / 166 / 220）。

幂等：每一步先查 `exit_effects` 同 business_id + phase + kind + target 是否已有行，有则跳过；整单重试（DEC-052）不会重复终止合同或重复作废调动。

### 5.2 锁顺序（org/locks.ts 全局序，不反向）

```
① lockTransferParticipants(employee, extra = 本单职责转交的下属 ∪ 该员工在途调动的参与人闭包)
   —— participants() 的闭包计算把 kind IN ('transfer') 扩为 ('transfer','leave')，使离职单上的下属转交进入闭包（共享文件 transfer-locks.ts）
② lockEmploymentEmployee → lockEmploymentBusiness(离职业务头)
③ 该员工其他在途任职业务头：按 id 升序 FOR UPDATE（将被作废的调动申请）
④ lockOrganizationSettings（仅当有组织角色转交需要写组织人员，或编制释放需要读写编制设置时）
⑤ 编制锁（仅编制释放一步需要；见 §6）
⑥ 审批实例：activeInstanceOf(FOR UPDATE) 逐个取锁后 cancel（最后一步，与 employmentApprovalHooks.deleted 的顺序一致）
```

定时任务路径由 `sweepTenant` 先 `lockTransferParticipants(..., skipLocked)`，再进入 `activateDueBusinesses`，锁序不变；审批路径由 employment 适配器 `lock` 先锁业务再锁实例，`applyExitEffects` 在实例锁之后只重入已持有的员工 / 业务锁，对其他在途调动的实例取锁属于“审批实例”层，不违反“持资源锁后不扩充员工集合”（员工集合在 ① 已含在途调动的参与人）。

## 8. 在途调动确认（DEC-154 / 166 / 220、Q-M0-64 / 87）

## 8A. 逾期迟到调动拦截（DEC-252①，新增校验；引擎层兜底仍按 DEC-052）

**定义**：员工存在“已过计划生效日、尚未执行的迟到调动” ⇔ 该员工有 kind=transfer 的任职业务，最新状态 = approved（含生效失败 failed、因前序挂起 suspended），且载荷 `effective_date` < 租户今天（DEC-056），且没有 outcome=effective 的生效尝试。即 `pendingActivations` 中 `kind='transfer' AND effectiveDate < today` 的项。审批中（in_review）的调动不算迟到调动（尚未批准，归 DEC-166 的确认框）；已落地的未来直接调动不算（归 §8 / §13-2）。

**判定接口**：只读函数 `findOverdueTransfers(tx, ctx, employeeId): Promise<OverdueTransfer[]>`（`employment/activation-store.ts`，返回业务 ID、计划生效日、最近尝试结果、调入部门 ID）。#83 设计 v2 §8.3 承诺导出同一判定；两边谁先合并谁实现，后合并方复用，不留两份。退休（R2-T04）复用同一函数。

**拦截点**（以下入口命中即 409，不写任何数据；范围内可见的调动给明细，范围外只给件数，DEC-126 / 177）：

| 审批通过（approve）、定时生效（activate）、撤销、删除 | **不拦截**：审批通过是审批人的动作，不因 HR 侧数据阻断；生效由引擎兜底（§5.3 步骤 0a：前序调动失败 → 离职挂起 PREDECESSOR_FAILED；调动顺延到离职之后 → 作废） |
| 通用入口 `POST employment/employees/:id/businesses` kind ∈ {leave, retirement} | 同样拦截（校验放在 `createEmploymentBusiness` 的 kind 分支，造数测试需先处理迟到调动或用 `trusted` 选项绕过，绕过只允许可信端口，不开放给请求体） |

**错误体**：`{ error: 'CONFLICT', reason: 'EXIT_LATE_TRANSFER_PENDING', message: '该员工存在已过计划生效日、尚未执行的调动（计划生效日：2026-10-10），请先处理该调动后再办理离职', transfers: [{ businessId, plannedEffectiveDate, lastOutcome, departmentId? }], hiddenCount }`。文案走资源文件（DEC-045），日期按租户时区。“处理”= HR 对该调动重试生效（`POST businesses/:id/activation/retry`）、或删除 / 撤销该调动申请。

**为什么入口拦截而不只靠引擎**：迟到调动一旦补执行会按 DEC-186 改到实际执行日；若那天已晚于最后工作日，调动会排到离职之后而被作废，HR 在办理离职时看不到这个后果；拦截让 HR 先决定调动的去留。引擎兜底保留：拦截后仍可能出现的逾期（§5.3 步骤 0a），以及 #83 v2 §8.3 的重建侧兜底（迟到调动排在已生效离职之后 → `assertBusinessSequence` 拒绝 → 记生效失败，离职记录不变）。

## 9. 权限、盲审、审计、幂等

- **范围**：所有写入口 `requireScopedEmploymentObject`（DEC-193）；列表 / 详情 / 下游清单 / 候选 `employmentVisibilitySql` / `visibleEmploymentRecords`（DEC-177）；幂等重放路径重新校验当前范围（`runWrite` 既有）。范围外 404，不泄露存在性。

## 13. 需要产品决策的问题（不自行定口径，等总编排转达）

1. **迟到离职是否顺延最后工作日**：DEC-186 / 195 针对调动“生效日改为实际执行日、不倒签”。离职的生效日 = 最后工作日 + 1（`fields.ts` 强制），顺延生效日就要顺延最后工作日，进而改变合同实际终止日与薪资口径；原站最后工作日是事实日期（W-513 样本审批 10-06、最后工作日 10-05 已过仍按 10-05）。选项：A 照 DEC-186 顺延两者（与调动一致）；B 离职不顺延，生效日仍 = 最后工作日 + 1，允许倒签，原计划日与实际执行日都记审计（**推荐 B**，更接近原站且不改合同终止日）。只影响复刻系统。
2. **已落地的未来直接调动晚于最后工作日**：DEC-220 只写了“审批通过未生效”的调动申请。选项：A 保存离职时 409，要求先删除该未来任职（**推荐**，fail-closed）；B 与申请同口径，生效时删除该记录并通知。只影响复刻系统，建议顺带登记需取证（原站对此场景的行为）。
3. **审批中 HR 编辑离职**（Q-M0-85 ③）：A PR-A 经审批编辑端口实现（**推荐**，表单字段改动走盲审复核）；B 放到 PR-B。
4. **草稿 / 已驳回且生效日晚于最后工作日的调动申请**：DEC-166 只覆盖审批中。选项：A 离职生效时一并作废（**推荐**，否则残留永远不能提交的单）；B 不动，提交时按顺序校验拒绝。
5. **PR-A 核心流程的 AC 编号**：规格 30 §5 的 AC-DM-01～11 只覆盖撤销 / 改期 / 账号 / 黑名单 / 重聘 / 交接 / 融入；PR-A 的申请、直接离职、生效、合同、在途调动、终止流程、转交、去向、批量、逾期迟到调动拦截没有编号。建议新增 AC-DM-12～21（见 §14）并写入规格 30 §5 与追溯表；是否同意编号。

已由 DEC-252① 定、无需再决策：逾期未执行迟到调动时离职 / 退休入口拦截，引擎兜底记生效失败（§8A）。
