## 1. 总体思路：离职 = 任职业务 `kind='leave'` 的申请单层 + 离职扩展行

与调动同构（DEC-125 / 215）。调动已经把“申请单层”做成了通用任职业务：`employment_business_objects`（业务头 + revision）、`employment_payload_versions`（载荷版本链）、`employment_state_events`（状态事件：draft / in_review / approved / rejected / disapproved / voided / effective / deleted）、生效时才写 `employment_records` + `employment_timeline`；调动特有元数据放在薄扩展表 `transfer_requests`（tenant_id, business_id 为键）。

现有代码已经为离职铺好了底层：

## 3. 状态机与视图口径（DEC-125 / 215、Q-M0-86；v1.2：未来直接离职不提前落地）

申请单状态完全复用 `EmploymentState`，不新增状态值。**直接离职（mode=direct）也走 `approved → effective`**：保存即“已确认待生效”（approved），最后工作日已过则在保存事务内立即生效；最后工作日在今天或未来则停在 approved，到期由定时任务原子生效。这样未来直接离职不会提前提交时间轴截断，到期任一步失败整单不落地（P2-04）。与直接调动“保存即落地”不同，原因是离职的下游效果（合同、流程、调动）必须与版本链截断同一事务。

```
[草稿 draft] ─提交→ [审批中 in_review] ─驳回→ [已驳回 rejected] ─修改重提→ in_review
                      │ 不同意办结 → [disapproved]（办结不生效）
                      │ HR 撤销离职 → [voided]
                      ▼ 最后节点同意
              [审批通过 approved] ──生效日（最后工作日+1）≤ 今天→ 同事务立即生效
                      ▲                 │ 未到 → 停在 approved，只有申请单，不进版本链
   [直接离职保存] ─────┘                 │ HR 撤销离职 → [voided]（无版本可删，DEC-215；#83 v2 §8.1）
   （mode=direct，保存即 approved）       │ 改期 → 追加载荷版本，仍 approved，重排队列
                                        ▼ 定时任务到期（activateExit，一个保存点）
              [已生效 effective]  版本链新增离职记录（人员状态 8），前一条止于最后工作日，下游效果同事务
                      │ 撤销离职 → [deleted]（删除离职版本：墓碑 + 时间轴恢复；版本与事件不物理删除；#83 v2 §8.1 / §5）
                      │ 改期到今天以前 → 同一业务重定位（§7.2）
                      │ 改期到今天以后 → [deleted] + 新建后继单（approved，supersedes 前单，§7.2）
```

| 视图 | 谓词（读申请单 / 状态事件 / 扩展行，不读版本链） |
|---|---|
| 离职中的员工 | 存在 kind=leave 业务，最新状态 ∈ {draft, in_review, approved, rejected}（含 mode=direct 的 approved）；默认最后工作日近 30 天（Q-M0-85 ③）。在岗统计不排除这些人（`30` §1.4） |
| 已完成的离职 | 最新状态 = effective |
| 撤销的离职记录 | `exit_cancellations` 有行 |
| 全部离职记录 | 以上 ∪ disapproved / voided / deleted（含被后继单替代的前单） |

`assertTransition` 需放行（共享文件 `transitions.ts`，仅 kind ∈ {leave, retirement}）：`activate` 允许 mode=direct；`revoke` 允许 approved → voided（仅经 §4A 门禁的撤销入口），以及由离职生效编排器以 `byExit` 作废 draft / rejected / approved 的调动申请（DEC-263③）。调动口径不变。

迟到生效（DEC-263①）：到期执行日 T 晚于原生效日时，最后工作日改为 T、生效日 = T + 1，离职记录当天落地、起始于次日（与已落地的未来直接调动同形），员工当天仍在职、次日起为离职；下游效果在 T 当天同事务执行，合同实际终止日 = T。

## 4. 写入口（HTTP）

统一前缀 `/api/tenant/employment/exits`（路径参数 `uuidParam` 规范化，请求体 UUID 经 zod 小写化，DEC-194）。**所有入口（含通用任职入口）都经 §4A 的公共门禁。**

| 方法 / 路径 | 作用 | 门禁操作（§4A） | 范围与裁剪 |
|---|---|---|---|
| POST `exits/employees/:id/preview` | 发起前预览：逾期迟到调动拦截项（`blockers` / `warnings`）、在途调动确认清单与确认令牌（§8）、合同影响、将终止的在途流程计数、职责转交候选 | `preview`（持 Dimission 或 DimissionApproval 任一） | 员工 `requireScopedEmploymentObject`；清单每项 `visibleEmploymentRecords`，不可见的只给件数 |
| POST `exits/employees/:id` | 离职申请（mode=application，`submit` 可选）/ 直接离职（mode=direct，立即或未来） | `create`（direct → `Employment.Dimission`；application → `Employment.DimissionApproval`） | 同上；令牌校验 |
| POST `exits/batch` | 批量离职申请：≤ 100 人，整体成功或失败；每人一条业务 + 一条流程，`batch_id` 相同 | `create` 逐人 | 逐人范围与门禁；任一人失败整批 409，逐条原因 |

## 5. 生效事务编排（DM-R4，DEC-052 / 056 / 166 / 186 / 195 / 213 / 220 / 222）

### 5.1 单一编排器 `activateExit`（P2-04）

新增 `employment/exit-activation.ts` 导出 `activateExit(tx, ctx, business)`，是离职从 approved → effective 的**唯一**路径，替代 v1.1 的“materialize 末尾挂接 + 先作废再 materialize”两处表述。调用点：

1. `transitionEmployment(approve)`：写 approved 事件后先执行 `confirmed` 阶段（编制预释放 §6、`approval_passed` 转交 §5.7、PR-B 交接自动发起端口）；审批通过且生效日 ≤ 今天、无前序待生效业务 → 同事务接着调用 `activateExit`。
2. `createEmploymentBusiness`（mode=direct，kind=leave）：写 approved 状态事件后同样先执行 `confirmed` 阶段，生效日 ≤ 今天 → 同事务调用 `activateExit`。
3. `activateDueBusinesses` → `activateWithJudgement` → `transitionEmployment(activate)`（kind=leave，mode 不限）：在保存点内调用；失败整体回滚到保存点，`recordActivationAttempt(failed, reason)` + HR 待办；HR 修正后 `retryActivation`。

`activateExit` 内部顺序（全部同一事务 / 保存点；任一步 AppError → 整体不落地）：

| 序 | 步骤 | 实现 | 失败处理 |
|---|---|---|---|
| 0 | 迟到对齐（DEC-263①） | 今天 T > 原生效日时 `postponeLateExit`（照 `postponeLateTransfer`）：追加载荷版本，最后工作日 := T、生效日 := T + 1；审计 `employment.exit.rescheduled` 记 `{ originalLastWorkDate, originalEffectiveDate, lastWorkDate, effectiveDate, executedAt(UTC) }`；后续步骤全部用顺延后的日期（合同终止日 = T、编制释放自 T + 1、队列先后按 T + 1）。审批通过时已逾期（DEC-195② 同口径）同样在 approve 事务内顺延并立即执行 | — |
| 0a | 逾期迟到调动兜底（DEC-252①） | `activationPredecessors` 已把生效日更早且未完成的调动（approved 未落地、已落地待联动、待复查）排在前面：未完成 → 离职挂起 `PREDECESSOR_FAILED`（DEC-112，`reminderOnly` 的复查项不阻塞）；调动按 DEC-186 顺延到今天而排到离职之后 → 进入步骤 1 的作废候选 | 挂起，不落地 |

| 2 | 版本链落地 | `materializeEmploymentRecord(business, { forwardUpdate: false })`：触发器写人员状态 8、继承入职状态；`insertEmploymentTimeline` 截断前一条到最后工作日；`assertBusinessSequence / assertSuccessorSequence` 拒绝“离职 → 同周期已生效业务”：已落地、起始晚于最后工作日的未来直接调动按 DEC-263② **不自动删除**，离职记 failed `EXIT_FUTURE_EMPLOYMENT_EXISTS`（DEC-252① 兜底口径）并生成 HR 待办，由有权限的人删除该调动或改期离职后重试。离职不作为传播来源（§5.6），故 `forwardUpdate: false` 且跳过状态传播 | 顺序 / 周期 / 范围校验失败即 failed |

### 5.2 锁顺序与预锁计划（org/locks.ts 全局序；P3 补）

审批适配器 `lock`（approve 路径）与定时 / 重试路径在取**审批实例锁之前**都按下列顺序预锁；`activateExit` 只重入已持有的锁，不反向首次取锁：

```
① lockTransferParticipants(employee, extra = 本单职责转交下属 ∪ 该员工在途调动申请的参与人闭包)
   —— participants() 的闭包计算把 kind IN ('transfer') 扩为 ('transfer','leave')（共享文件 transfer-locks.ts）
② lockEmploymentEmployee → lockEmploymentBusiness(离职业务头)
③ 该员工其他未办结任职业务头（将被作废的调动申请、待复查的已落地调动）：按 id 升序 FOR UPDATE
④ lockOrganizationSettings（仅当有组织角色转交或需读写编制设置）
⑤ 编制锁（仅编制释放需要；§6 释放不追加版本故通常不取；DEC-258 确认路径只读）
⑥ 审批实例：本单实例由引擎 openRun 取；DM-R8 / 作废调动的其他实例在 ⑥ 内按实例 id 升序逐个 activeInstanceOf(FOR UPDATE) 后 cancel
```

多实例顺序：同一事务内所有被终止 / 作废的实例按 `approval_instances.id` 升序取锁；两个并发离职（不同员工）彼此不共享实例，共享的只有组织设置 / 编制锁，仍按全局序。定时任务 `sweepTenant` 先 `lockTransferParticipants(..., skipLocked)` 跳过被占用员工。

### 5.3 审批通过与直接离职保存时的立即生效

审批通过时最后工作日已过（规格 30 §1.5 样本）：approve 事务内 `approveEmploymentBusiness` 判定生效日 ≤ 今天且无前序 → `activateExit` 全部步骤在审批事务内一次完成（与原站“通过即生效、合同同一时刻终止”一致）。直接离职最后工作日已过：保存事务内同样一次完成。两者都要求门禁（§4A）在落地前通过。

### 5.4 DEC-222 对合同端口的改动（共享文件 `contracts/ports.ts`，归属 R2-T06 车道，契约 PR 或 PR-A 内单独提交）

- `cancelExitRequests(tx, ctx, input, allowedTypes, { terminateAll })`（DEC-267 修订 DEC-222）：`terminateAll=false`（默认）保留现有“只撤回终止日期晚于最后工作日的在途合同申请”的过滤（现有代码按 `request.effectiveDate`，改为按合同终止日期比较，照原站 SwitchTypes=41 文案）；`terminateAll=true` 撤回全部在途合同申请。保留“离职后可签类型”豁免。有效合同的原地终止 / 删除与“撤销离职不自动恢复”不变。

- 未被撤回、继续流转的在途合同申请在离职后生效：合同模块现有在职 / 已离职校验（`CONTRACT_EMPLOYEE_DEPARTED` 口径）拒绝落地 → 记生效失败交 HR（DEC-267③，B-56b）。

### 5.6 继承矩阵、人员状态与“离职作为传播 / 重建目标”（P2-03；对齐 #83 v2 §4、§8.2、T-33）

**继承（创建 / 落地时取值）**：离职与其他任职业务使用同一套 `prepareInheritance / resolveEffectiveInheritance` 与 form 矩阵，**不是“任职字段全部继承”**：

| 字段 | 离职表单（form 矩阵） |
|---|---|
| INHERITED_FIELDS 预置字段（部门、职位、职务、职级、职等、地点、经理、序列、人员类别等） | 有继承边，取插入点前驱 |
| `isDepartmentHead` / `isStoreManager` / `addedSubordinateIds` | 无边（默认空 / false） |
| `employType` / `jobNumber` / 人员状态 / 入职状态 | 系统派生：employType 取同周期前驱，jobNumber 取员工主档，人员状态 = 8（自带类，`employment_kind_status`），入职状态继承前一条 |
| 自定义字段 inherit:true | 有边 |
| 自定义字段 inherit:false，离职表单**可编辑** | 无边，值为空（HR 可填） |
| 自定义字段 inherit:false，离职表单**只读 / 隐藏** | 有边（`07` §3.3 例外） |
| 自定义字段 inherit:false，**未拖入**离职表单 | 无边，值为空 |

`lastWorkDate` 与离职扩展字段是人工 intent，不参与矩阵。

**传播 / 重建目标**：离职 / 退休版本**永不作为传播来源**（`forwardUpdateEmployment` 与 `propagateEmployeeStatus` 不以它为源；#83 合并前守卫放在 `activateExit` 的 `forwardUpdate: false` 与状态传播跳过，合并后归一到 #83 的空计划），但**是合法的传播与重建目标**，不冻结离职记录的业务字段：

- 向后更新：补录 10-12 的 A→B 直接调动并开启向后更新 → 10-16 的离职记录按 `forward` 矩阵值匹配，部门 A→B，人员状态仍为 8、入职状态不变（F-022 的 `propagateEmployeeStatus` 对不同值“不动”，离职 8 ≠ 来源前值）。测试同时断言业务字段与两个状态列。
- F-021 序列同步、#83 迟到重建：离职记录作为目标按同一 fold / 矩阵处理，`lastWorkDate`、生效日、离职扩展字段是 intent 不被改写；重建不会把离职记录移出时间轴末尾。
- 删除来源（#83 v2 §5）：离职记录可以是依赖 S 的目标（如部门来自 S 的传播），删除 S 时按 §5 写 retain；离职自身被删除时 retain 集合为空（它不是来源）。

**撤销 / 改期与状态**：撤销已生效离职 = 时间轴恢复前一条的开放区间，前一条版本上的状态自然成为当前状态；改期重定位（§7.2）追加记录快照版本，状态列随快照复制为 8。

| `business_effective` | `activateExit` 步骤 6 | 保存事务内 `activateExit` 步骤 6 | 到期 `activateExit` 步骤 6 |
| `approval_passed`（“单据确认时”） | approve 事务内，`phase = confirmed`，生效日取批准当天（DT-R7） | 保存事务内，在写 approved 事件后、`activateExit` 之前执行，`phase = confirmed` | 保存事务内执行，`phase = confirmed`，生效日 = 保存当天（转交先于离职生效，与审批流“通过即转交”语义一致） |

  直接离职的 `confirmed` = 保存动作，是 `approval_passed` 在无审批业务上的唯一可达对应点；测试覆盖立即 / 未来两种直接离职各一例（B-48 / B-49）。撤销离职时已执行的转交不自动恢复，列入手工清单。

- 不做 DT-R4 强校验、DT-R5 未转交清空（R2-T09）。

## 6. 编制：审批通过即预释放（DEC-266①，取代 Q-M0-93 暂定）与 #96 / DEC-258 对接

原站：离职 / 退休的编制时机 = “审批通过-立即释放”，审批通过即在当前及未来周期计为预减，不等生效日（`30` 文末 Q-M0-93）。

**现状**：占编由 `employment_timeline.valid_during` 实时投影（`employment-check.ts occupancyRows` 排除 `kind IN ('leave','retirement')`），在途调动由 `pendingTransfers` 投影为未来区间。离职申请在 approved 期间没有版本，投影里员工仍占编到无穷——与原站不符。

**设计**：

1. **投影层**（`establishment/employment-check.ts` + `membership-windows.ts`，共享文件）新增 `pendingExits(employeeIds)`：读取最新状态 = approved 的 kind ∈ {leave, retirement} 业务（申请与直接离职都在此）的载荷生效日 E，把该员工当前及未来主职区间的上界裁到 `min(原上界, E)`；已生效离职由时间轴截断自然表达，不重复裁。这样“审批通过即预减”在严格 / 非严格控编判定、超编提示、F-026 占编区间里一处生效。
2. **记账层** `establishment/exit-release.ts` 导出 `registerEstablishmentPreRelease(tx, ctx, business, phase)`：在 `confirmed` 阶段（审批通过 / 直接离职保存）写 `exit_effects(establishment_pre_released, detail: {departmentId, positionId, capacityId, releasedFrom: E})`；改期（§7.2）与迟到顺延（§5.1-0）各追加一条修正行（`releasedFrom` 变化）；不追加编制版本、不改 `transfer_establishment_allocations`、不取编制锁（只读投影）。它是离职编制释放的**唯一**入口。
3. **恢复占编**（撤销 approved 为 voided、撤销已生效恢复在职、改期把最后工作日改晚、后继单作废使前单区间重开）：预释放随 approved 状态消失或 E 后移而自动收回，占编回升。对**整个恢复区间** `[原 E, 新 E 或下一条起始或开放)` 用同一投影重算编制峰值：不超编 → 直接执行；超编（严格或非严格控编）→ 按 DEC-258“一律只弹确认、不拦截”：409 `ESTABLISHMENT_EXCEEDED_CONFIRM_REQUIRED` + 超编明细（按可见范围裁剪），客户端 `confirmed: true` 重提后执行并记审计 `employment.exit.over_capacity_confirmed`。协议与 #96 的 `confirmed` 透传一致；#96 合并后核对 `clipMembership` 能否直接承接 `pendingExits`。
4. **与调动的交叉**：审批通过未生效的调入申请（`pendingTransfers`）与同员工的预释放同时存在时，按日期各自裁区间：调动生效日 ≤ E 的在新部门占编到 E，> E 的按 DEC-220 会被作废，投影先按 greatest(effective, today) > E 排除。

## 8. 在途调动确认（DEC-154 / 166 / 220、Q-M0-64 / 87；P3 确认令牌）

- 发起 / 保存 / 提交离职不拦截在途调动（DEC-154 只拦直接调动）。
- 需确认清单 = kind=transfer 且 ① 最新状态 in_review（DEC-166）或 ② approved 未生效且 `greatest(effective_date, 今天)` > 最后工作日（DEC-220）。
- 文案照搬原站两种确认框。
- **确认令牌**：预览计算完整候选集合 S（含操作人不可见的）→ `ackToken = HMAC(tenantId, employeeId, lastWorkDate, sorted(S))`（服务端密钥，不含明文 ID）；响应只给可见项 + `hiddenCount` + `ackToken`。保存 / 提交 / 改期带 `pendingTransferAck: { token }`，服务端重算 S 与令牌：不一致 → 409 `EXIT_PENDING_TRANSFER_ACK_REQUIRED`（返回新的可见项 / hiddenCount / token）。完整集合与令牌哈希写入 `exit_requests.pending_transfer_ack`，不回传。隐藏项不按 DEC-178 拒绝整单：作废发生在生效时，对操作人不可见的调动申请由系统作废并通知其发起人，操作人只知件数。
- 已落地的未来直接调动（start_date > 最后工作日，DEC-263②）：**只提示、不拦截、不进令牌**。预览与保存响应的 `warnings` 列出：对操作人可见的给出调动与生效日；不可见的只给“存在未来生效的调动，需由有权限的人员处理”与件数。系统不自动删除该调动；离职到期执行时按 §5.1-2 记生效失败交 HR 处理。
- 草稿 / 已驳回且生效日晚于最后工作日的调动申请（DEC-263③）：预览 `warnings` 提示“离职生效时将作废”，不进令牌；生效时作废并站内通知申请人。

## 8A. 逾期迟到调动拦截（DEC-252①；P2-02 按完整执行状态判定）

**定义**：对员工调用 `pendingActivations`（与定时任务同一谓词 `pendingActivationState`，不另写状态筛选），取 `kind='transfer' AND effectiveDate < 租户今天` 的项，按执行状态分三类：

| 类 | 判定（`PendingActivation` 字段） | 含义 | 处理 |
|---|---|---|---|
| A 未落地 | `materialized = false`（最新状态 approved，任意 `lastOutcome`：null / failed / suspended） | 审批通过但到期未执行或执行失败 | **拦截** |
| B 已落地、联动未完成 | `materialized = true AND reminderOnly = false`（直接调动已有记录，职责联动 / 负责人 / 新增下属尚未执行或失败，无 `employment.transfer.linked`） | 任职已变、联动悬空 | **拦截** |
| C 已落地、仅待复查 | `materialized = true AND reminderOnly = true`（DEC-173 到期复查，不阻塞后序业务） | 只剩编制 / 组织复查提醒 | 不拦截，预览列为 `warnings` |

审批中（in_review）的调动不是迟到调动（归 §8 确认框）；已落地的**未来**直接调动不在此列（归 §8，DEC-263② 只提示不拦截）。

**判定接口**：`findOverdueTransfers(tx, ctx, employeeId): Promise<OverdueTransfer[]>`（`employment/activation-store.ts`；返回 businessId、plannedEffectiveDate、materialized、reminderOnly、lastOutcome、linkagePending、departmentId），`blocking = !reminderOnly`。#83 v2 §8.3 承诺导出同一判定，两边谁先合并谁实现、后者复用。退休复用。

**拦截点**：全部经 §4A 门禁 → 命中 blocking 项即 409 `EXIT_LATE_TRANSFER_PENDING`，不写数据：`create`（专用与通用）、`submit`、`reschedule`、批量逐人。approve / activate / cancel / delete 不拦截，由 §5.1 步骤 0a 兜底。

**错误体**：`{ error: 'CONFLICT', reason: 'EXIT_LATE_TRANSFER_PENDING', message: '该员工存在已过计划生效日、尚未执行完成的调动（计划生效日：2026-10-10），请先处理该调动后再办理离职', transfers: [{ businessId, plannedEffectiveDate, materialized, lastOutcome }], hiddenCount }`（可见项按 DEC-177 裁剪）。“处理” = 重试生效 / 重试联动子项（`POST businesses/:id/activation/retry`、`POST transfers/linkage-items/:id/retry`）、或删除 / 撤销该调动。

**为什么入口拦截而不只靠引擎**：迟到调动补执行会按 DEC-186 改到实际执行日；若已晚于最后工作日，调动会被作废或与离职冲突，HR 办理离职时看不到后果。引擎兜底保留（§5.1-0a；#83 v2 §8.3 的重建侧兜底：迟到调动排在已生效离职之后 → 记生效失败、离职不变）。

**边界用例**（并入 §12）：

| # | 场景 | 预期 |
|---|---|---|
| B-36 | approved、计划日昨天、未执行的调动；HR 直接离职 | 409，前后读取相等 |
| B-37 | 同上但调动生效失败（控编）；发起离职申请并提交 | 保存与提交都 409；重试调动成功后 → 200 |

| B-39 | 离职已提交（审批中，最后工作日 L），之后一条计划日已过的调动审批通过，按 DEC-195 落到今天 T 并立即生效（已 effective，不在作废候选） | T ≤ L：调动已生效，离职到期正常生效。T > L：离职审批通过 / 到期执行时已逾期 → DEC-263① 顺延，最后工作日 = 执行日 ≥ T、生效日次日 → 排在该调动之后正常生效；若离职在 T 之前就已生效（不可能同时满足 T > L 且离职未逾期）则不适用。**不承诺该调动作废** |

| B-43 | 退休 kind=retirement | 本 PR 只做判定复用点，断言不启用（R2-T04） |
| B-44 | 直接调动 10-01 保存计划 10-10、带职责联动；10-12 联动未执行或失败；HR 办理最后工作日 10-20 的离职 | **B 类拦截** 409；重试联动子项成功后放行 |
| B-45 | 同 B-44 但调动无联动、只剩 DEC-173 复查（reminderOnly） | 不拦截，预览 `warnings` 含该项；离职生效队列不被它阻塞 |

## 8B. 劳务转正式 / 实习转正在途流程拦截（DEC-266④，照原站）

**定义**：员工存在 kind ∈ {`intern_regularization`（实习转正）, `labor_regularization`（劳务转正式，R2-T07 的业务类型，PR-A 先登记编码常量、无数据则不命中）} 的任职申请，最新状态 = in_review（流程中），且载荷生效日 ≤ 本次离职的最后工作日。
**行为**：经 §4A 门禁，在 `create`（专用与通用）、`submit`、`reschedule`（按新最后工作日重算）命中即 409 `EXIT_REGULARIZATION_IN_FLIGHT`，不写数据；错误体 `{ reason, message: '该员工存在生效日不晚于最后工作日的劳务转正式 / 实习转正审批流程，请先完成或撤销该流程', requests: [{ businessId, kind, effectiveDate }], hiddenCount }`（按 DEC-177 裁剪）。生效日 > 最后工作日的同类流程不拦截，按 §5.1-5 的终止口径处理（默认终止）。approved 未生效且生效日 ≤ 最后工作日的转正不拦截：它排在离职之前，由队列先落地（失败则离职挂起，DEC-112）。
**边界**：B-55 实习转正审批中、生效日 = 最后工作日 → 409；B-55a 同一流程审批通过后再发起 → 200，队列先转正后离职；B-55b 生效日 = 最后工作日 + 1 → 不拦截，生效时按默认口径终止；B-55c 范围外 → 409 且 `requests` 空、`hiddenCount` = 1。
