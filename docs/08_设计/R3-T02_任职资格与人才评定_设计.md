### 1.2 合并顺序与并行

```
设计 PR（A）→ PR-0（C 小）→ PR-A（C）─┬→ C1 → C2
                         └→ PR-B（C）─┘
```
- PR-0 是 AGENTS §3.3 的“契约 PR”，先单独合并；PR-A / PR-B 只消费契约，不再改共享权限文件。
- **PR-A 与 PR-B 并行**（DEC-320①、DEC-322③）：**并行审只适用于两边不重叠的提交范围**，不能因为业务目录不同就当作两个 PR 文件完全不重叠。
  - 可并行的部分：PR-A 只动 `apps/api/src/modules/qualification/**`、`packages/db/src/schema/qualification.ts`、`packages/domain/src/qualification/**`；PR-B 只动 `apps/api/src/modules/evaluation/**`、`packages/db/src/schema/evaluation.ts`、`packages/domain/src/evaluation/**`。
  - PR-B 依赖 PR-A 的 `ql_*` 表、`qlReadable` 与 `assertQualificationRefs`：PR-A 的第一个提交只含这三样并冻结签名，PR-B 以该提交为基开发（叠在 PR-A 分支上）。

  - **B 在 A 合并后的最终 head 上复核**：PR-A 合并后，PR-B 合并 main，本地重跑 `pnpm lint && pnpm typecheck && pnpm test`，审查对合并后的最终 head 做一轮复核，再合并 PR-B。

**通用指标的能力标准：照原站“覆盖写入”（DEC-334①，Q-T02-14 🟢 规格 23 §12）**：
- **非通用 → 通用**：保存前确认框照抄原文“保存指标将同步更新关联数据，是否确认保存？ / …为通用指标，保存后会将指标说明更新到使用该指标的任职资格标准中”。确认后，在同一事务里把指标说明写进**所有**引用该指标的标准：该格原有能力标准全部删除，写入一条 `content = 指标说明` 的能力标准，并打来源标记 `source = 'common_overwrite'`、`source_target_id`。通用期间该格不可编辑（409 `ABILITY_LOCKED_BY_COMMON`）；通用期间再改指标说明，同样覆盖写一遍。
- **通用 → 非通用**：不再改写各标准，保留被覆盖后的值（原来的自定义内容不恢复），该格恢复可编辑；被手工改过的行清除来源标记。
- **跨范围写入**：覆盖会写到操作人数据范围以外的标准（原站行为，DEC-334 定），不另做范围校验；每个受影响的标准各写一条审计（action `qualification.standard.common-overwrite`，同事务），审计可见性按标准的所属组织（§8）。
- **锁序**：覆盖时先查出引用该指标的标准 ID，按 id 升序 `FOR UPDATE` 标准行，再 `FOR UPDATE` 指标行，然后复核引用集合（有新增引用则重来，有界重试 3 次后 409）。这样全局都是“标准 → 指标”，与冻结锁（§3.4）和标准编辑入口一致。
- **带出值权限（DEC-309）**：带 `common_overwrite` 标记的能力标准，读取时仍按查看人当前对 `Qualification.Target.description` 的字段查看权判断，看不到就省略并带 `projectionHidden: true`（§5.2 #2）；被手工改过、清掉标记后按普通能力标准处理。

**指标等级描述：投影 + 手改，不跨对象批量写**（避免改等级明细时改到操作人范围外的指标）：
- 未手改的描述 = 等级明细 description 的投影；手改才落 `ql_target_grade_descriptions`。新增明细 → 所有评级指标读到多一条（AC-QL-04）；编辑明细 → 未手改的随之变化；删除明细 → 软删，手改行保留不显示。改等级方案不写任何指标行。
- 投影的源字段权限见 §5.2 带出值入口清单。

**导入（QL-R11 / AC-QL-05）**：一行 = 类别编码 × 级别编码 × 指标编码；请求体逐标准带预期 revision（DEC-067，不用 If-Match），锁住后不符整批 409；编辑导入对每格先删全部能力标准再按文件重建；整批一个事务，上限 2000 行，失败逐行回执、整体回滚；任务日志按 DEC-199。编码解析只在导入人的 `qlReadable`（§5.1）内进行，范围外与不存在同一回执“编码不存在”。

**申请目标的修改（R2-P2-03）**：申请类别、申请级别、标准引用三者合称申请目标，带 `target_version`（首次申报为 1）。
- 只在 `apply_status = draft` 且**没有任何下游数据**时可改：没有材料环节评分项上的分数、没有场次时段、没有评委记录、没有校准结果（提前转入过的评定在驳回后就有下游数据）；有下游数据时改目标 → 409 `TARGET_LOCKED`，需要换目标只能撤销后按 Q-T02-19 处理。
- **不重置**申报基准（DEC-320⑨，Q-T02-21 ①）。修改成功时只把 `target_version + 1`；**首次申报时固定的申报基准**（原类别 / 原级别、上次通过情况、历练时长、`cycle_id`）**保持不变、不重新取数**，在同一事务里以这份基准重新校验参评条件与跨级（R3-P2-01）。反例：原级别 P3、最多跨 1 级，驳回期间员工经另一项评定得到 P4，此时把目标改为 P6 → 仍按 P3 计算（跨 2 级）拒绝。
- 下游写入（评分项分数、评委记录、校准结果）都记录写入时的 `target_version`；**发布守卫**（§3.5）校验参与计算的全部评委记录、冻结评分项、校准结果的 `target_version` 都等于评定当前的 `target_version`，否则 409 `PUBLISH_PRECONDITION`（`reason: TARGET_VERSION_MISMATCH`）。按上一条规则这种不一致不应出现，守卫是第二道保险。

**冻结锁**：冻结事务锁序 = `ev_staff_evaluations FOR UPDATE` → `ql_standards`（该评定引用的标准行）`FOR SHARE` → 该级别引用的 `ql_targets` 按 id 升序 `FOR SHARE` → 答辩环节 `ev_forms` 行 `FOR SHARE` → 读明细、能力标准、通用评分项后写快照。对应修改入口：标准的明细 / 能力标准 / 级别描述 / 发展通道一律先 `FOR UPDATE` 标准行（聚合根锁）再写子行；指标改说明 / 通用标记先 `FOR UPDATE` 指标行（会触发覆盖写入时，先按 id 升序 `FOR UPDATE` 受影响的标准行、再锁指标行，§3.1）；评价表改评分项先 `FOR UPDATE` 表单行。三类修改入口都不锁评定数据，冻结方不反向锁更上层对象，因此无环。真实 PG 交错测试见 §7.4。

| defense `scheduled` | 场次“确定并发送通知” | 开始 / 结束答辩；评委保存 / 提交 / 弃权；移出场次（有在途审批须先撤销，EV-R37） | 跟场人 / 评委 / 管理员 |
| defense `reviewed` | 所有在职评委都已提交或弃权（DEC-044） | 评委改分重提；确认校准（全员弃权时见 Q-T02-18） | 评委 / 跟场人 |
| defense `calibrated` | 确认校准 | 评委提交 / 弃权一律 409 `CALIBRATION_LOCKED`（DEC-046）；重新校准；手动转入结果发布 | 跟场人 / 管理员 |
| result `pending` | 手动转入（有答辩：须 `calibrated`；无答辩：Q-T02-15） | 提前通知；发布（守卫见下） | 活动管理员 |
| result `published` | 发布 | 只读 | — |
| 任一**进行中** → 终止 | 撤销 / 完成活动 / 离职 | 只读；在途审批实例立即作废（Q-T02-12，DEC-365④ 🟡：引擎 cancel，实例“已终止”、审批人清空、待办收回；评定保留，申请类别 / 级别不变） | 撤销：见上；完成活动：能管理该活动的管理员，活动内全部进行中评定一并终止，含其人员范围外的（§5.1，DEC-320② 🟡）；离职：系统（§4.4） |

**进行中与终态（R2-P2-02）**：
- **终态**（不再流转、不被任何终止入口改动，历史保留）：① `terminated_at` 非空；② `apply_status = failed`（资格未通过）；③ `result_status = published`（结果已发布）。
- **进行中** = 不是终态的全部评定（含 apply `draft` 待申报、material `failed` 尚未转入或放弃的）。代码只用一个谓词 `inProgressSql(alias)` / `isInProgress(row)` 表达，离职终止（§4.4）、完成活动、撤销申报、活动“已有进行中评定”判断、写守卫都调用它，不各写一份。
- 已发布的评定在离职、完成活动后保持 `published`，`TalentReviewPort`（§6.2 (2)）与人员档案照常可读（DEC-032 只终止进行中的评定）。

**发布守卫（P2-05）**：发布事务在评定数据行锁内检查，任一不满足即 409 `PUBLISH_PRECONDITION`：进行中；`apply_status = passed`（资格审批**已通过**结束）；有答辩环节时 `defense_status = calibrated`，无答辩环节时按 Q-T02-15 选定的结果来源已就绪；`result_status = pending`；参与计算的数据 `target_version` 一致（见 §3.4“申请目标的修改”）。资格审批的结束回调同样先锁评定数据行，二者串行：发布先拿锁时资格必已通过（不可能再被否决）；否决先拿锁时评定已回到 apply `failed`、答辩时段删除，发布因 `apply_status ≠ passed` 被拒。不做发布后的补偿。转入结果发布同样要求 `apply_status = passed`。

**提前转入后资格不通过（AC-EV-11 🟡）**：`apply_status = failed`、`current_stage = apply`，从场次删除时段（已有评委记录一并删除，审计保留）；材料审批不通过不影响答辩（EV-R29）。

### 4.2 唯一映射（QL-R15 🟢 G-047）

任职记录 → 类别：按 **职位 > 职务序列 > 职级类别** 依次查关联，第一个恰好命中 1 个启用类别的类型胜出；同类型内一个岗职务只关联一个类别（DEC-331④），所以同类型不会多命中；“职务”排在职位之后、职务序列之前（职位 > 职务 > 职务序列 > 职级类别，按手册与设计推荐 🟡，DEC-335②）；组织调整不触发同步，撤销 / 删除任职时不删已生成的子集（同样 🟡，以后补测）。级别：职级 → 职等，须恰好 1 个启用级别。不唯一 → 不生成，回执 `skipped: AMBIGUOUS_MAPPING`（原站无提示 🟢）。

### 4.3 任职事件订阅（P2-03：入队触发器 + 状态重试，不用时间游标）

- **入队**：C1 迁移在 `employment_outbox` 上加 `AFTER INSERT … WHEN (NEW.event_type = 'employment.record.create')` 触发器，按处理器各插一行 `(tenant_id, outbox_id, handler, employee_id, created_at)` 到本任务的 `ev_sync_queue(state = 'pending', attempts = 0)`；C1 只有 `qualification_sync`，C2 迁移改触发器函数追加 `evaluation_leave`（只对离职 / 退休记录）；C2 上线时的补入见下方“C1 → C2 窗口”。触发器在写任职的同一事务内执行，事件与队列行同时提交或同时回滚——不论 `created_at` 与提交顺序如何错位，都不会漏。不改任职模块代码（DEC-249），只在迁移里加触发器。
- **消费**：调度器（同 `job/sequence-worker.ts` 的平台遍历租户 + 逐租户 `withTenant` + `runPlatformCommand` 幂等）每轮按 `state IN ('pending','failed') AND next_attempt_at <= now()` 取一批，`FOR UPDATE SKIP LOCKED`，按 (employee_id, created_at) 处理；成功 `done`，业务跳过 `skipped`（附原因），异常 `failed` + attempts + reason + 退避的 next_attempt_at（DEC-052）。没有高水位：每轮都从“未完成”状态取，迟提交的事件下一轮自然被取到。判重键 `UNIQUE(tenant_id, handler, dedupe_key)`：`qualification_sync` 的 dedupe_key = `outbox_id`；`evaluation_leave` 的 dedupe_key = 离职 / 退休**业务单 ID**（`employment_outbox.business_id`，同一笔离职无论来自触发器还是补入只占一行）；重复入队 `ON CONFLICT DO NOTHING`，各处理器的回执互不影响。
- **C1 → C2 窗口（R3-P2-02）**：C1 上线后、离职捕获上线前登记的离职 / 退休（尤其是尚未生效的未来离职），触发器当时只为 `qualification_sync` 入队。拆分后离职捕获在 C2-1b，先于第一个能产生评定数据的 C2-2（拆分方案第 6 节）；C2-1b 的迁移在**同一事务**内按顺序：
  1. `LOCK TABLE employment_outbox IN SHARE ROW EXCLUSIVE MODE`：等已插入 outbox 的在途写事务提交，并在本迁移提交前阻止新的插入，避免“旧触发器函数入队、又不在补入快照里”的缝隙；
  2. `CREATE OR REPLACE` 触发器函数，追加 `evaluation_leave`；
  3. **补入**：来源为 `employment_records` 中 `kind IN ('leave','retirement')` 且（`start_date >= CURRENT_DATE - 1`（迁移不知道各租户时区，多留一天）**或**其 `staff_id` 出现在任一 `ev_staff_evaluations.cycle_id`（覆盖拆分上线期间已有评定的周期））、并且仍在 `employment_timeline` 上（排除逻辑删除后只保留历史的行）的记录；任职记录 ID 与业务单 ID 相同（`read-model.ts` 的 `recordsQuery` 以 `b.id = r.id` 关联），按上述判重键 `INSERT … ON CONFLICT DO NOTHING`，`next_attempt_at` = 记录 `start_date`。
  - 幂等：迁移重跑或与触发器同时产生同一业务单的行，都只保留一行；补入不依赖 C1 的队列，C1 之前登记的未来离职同样覆盖。
  - 也可以选择 C1 预先为离职 / 退休入队一个“待启用”的 `evaluation_leave` 行（C1 不消费）；v4 取“C2 补入”，因为它同时覆盖 C1 之前的数据，且 C1 不用为尚不存在的处理器建行。
- **处理时按有效任职读模型复核**：处理器（含补入的行）不直接信任队列里的数据，按同租户、业务单 ID 经 `employment/read-model.ts` 的 `loadEmploymentRecord`（走 `employment_timeline` 时间轴，逻辑删除后只留历史的行读不到）重新读取有效任职：读不到（已删除、已撤销）→ `skipped`（`reason: RECORD_NOT_EFFECTIVE`），不生成子集、不终止评定；`start_date` 晚于今天（租户时区；源头问题“未来生效记录提前发事件”由 F-055 修复，C2 在其后开工，这里仍保留复核作第二道保险）→ 本行改回 `pending`、`next_attempt_at` = 生效日当天；到期后再读一次，届时被删除同样 `skipped`。
- **上线基线**：触发器只覆盖上线后的事件；历史数据由初始化命令处理（同 DEC-188 思路）。
- **触发业务**（QL-R15②）：入职（含重聘、退休返聘）、转正（含实习转正）、调动、新增员工；离职 / 退休走终止；其他业务 Q-T02-05。

### 4.4 离职终止（DEC-032；P2-04：按任职周期界定）

- 任职周期用现有稳定标识：任职记录的 `staff_id`（外键指向 `employment_cycles.id`，`employment/cycles.ts` 以它作周期 ID）。评定申报时把员工当前有效任职记录的 `staff_id` 固定为 `cycle_id`。
- 消费 `leave` / `retirement` 落地事件时，只终止 `cycle_id = 该离职记录的 staff_id` 且**进行中**（§3.5 `inProgressSql`）的评定（原因“离职”，终止时间 = 离职记录生效日），在途审批按 Q-T02-12；已发布等终态的历史不动。重聘后新周期的评定 `cycle_id` 不同，不受旧事件影响。（C2）
- **写守卫**：评定的每个写命令在评定数据行锁内检查 `cycle_id` 对应周期内是否已有 `start_date ≤ 今天（租户时区）` 的离职 / 退休记录；有则 409 `EMPLOYEE_LEFT`。检查的是评定自己的周期，不是“员工当前是否在职”，所以旧周期的评定在重聘后同样被拒，且在消费者落地终止之前就已不能再写。

### 4.5 结果发布 → 子集（DEC-025 / AC-EV-09 / AC-QL-07）

发布事务：锁评定数据 → §3.5 发布守卫 → `result_status = published` → 通过者写子集一行 → 审计 → 通知登记。**不生成调动任职**；AC-QL-07 按 DEC-025 改写为“发布后子集只多 1 行、任职记录不变”。HR 另发调动时**不去重**（P-2 ①，DEC-320③）：照原站，由 HR 关闭 SW73 避免评定后调动重复生成子集；关闭 SW73 会停止所有任职变更的资格同步，设置页给出提示（§1.3）。

- **publicDownSql 抽取保留的语义**（PR-0）：范围内组织为空 → `false`；只看管理 / 组织维度的组织；按租户时区当天的组织版本；行政维度 `org_hierarchy_links.dimension = 'admin'`；向上递归深度 ≤ 64；起点含本组织。`scope.all` 时 `readableSql` 为 `true`。
- **owner-units 抽取保留的语义**（PR-0）：只取 `kind <> 'default'` 的应用范围、启用的具名管理单元、当天有效且启用的组织；`MAX_UNITS = 200`；`nameable` 谓词只决定 `named`（组织名称 / 编码按查看人组织员工应用的当前范围与字段权带出，DEC-316②），不影响候选本身；`chooseUnit`：无 → 403 `NO_MANAGEMENT_UNIT`、一个 → 自动、多个未选 → 400 `MANAGEMENT_UNIT_REQUIRED`、选了不属于本人的 → 404（存在与否同一响应）；之后按 DEC-082 复核新建范围；编辑时不提供改所属单元，创建 / 编辑候选行为与 #106 相同。
- **整体操作的授权（DEC-320② 🟡，取证 Q-M0-136 后再确认）**：分两类。
  1. **活动级整体操作**（命令对象是活动本身，不点名人员）：完成活动、发布 / 取消发布活动。授权以活动为界：操作人有对应功能权限、且活动在其 `scopeSql(owner)` 内（能管理这个活动）即可执行，**不要求活动内全部人员都在操作人人员范围内**。完成活动照常终止活动内全部进行中评定，包括操作人人员范围外的人员。
     - **响应**：只返回操作人人员范围内被终止评定的明细与计数（`terminated`、`terminatedCount` 都只算范围内）；范围外人员不出现，也不给总数或差额。
     - **审计**：活动对象只写一条状态变化审计，不含人数与名单；每条被终止的评定各写一条评定审计（同事务），查看时按 `activityPersonRule` 以查看人当前权限裁剪（§8），范围外的行不出现、不计数。
     - 人员范围在同一事务内只读一次，响应明细以它为准。通知按评定逐条登记，接收人是员工本人 / 在途审批人，与操作人范围无关。
     - 取证 Q-M0-136 若显示原站拦截或跳过范围外人员，按 DEC-320② 保留的收紧备选（全覆盖才可执行）另行修订本条；实现里不预埋开关。
  2. **点名的批量命令**（请求里列出评定或员工）：批量提名、批量转入、批量发布结果、安排场次、子集初始化。逐条在事务内检查人员范围：范围外与不存在同一回执（`NOT_FOUND` / `EMPLOYEE_NOT_FOUND`），不透露是否存在；其余条目逐条回执（DEC-067）。前端“全选”只选列表里看得到的行；服务端不提供“活动内全部人员”模式（完成活动除外）。
- 引用校验统一一处：活动 / 评价表 / 发展通道引用类别、级别、标准、指标时，被引用对象须对操作人可见（类别、级别、指标、标准有对象查看权即可见，DEC-352，`qlViewable`）且启用（只拦新引用；已引用后停用照常显示，同 DEC-281⑧）；不存在 404、无对象查看权 403。
- **人员引用的出口（DEC-331① / DEC-339② 修订 DEC-322②；DEC-325③ 上级同口径）**：配置对象里引用的员工，按查看人当前的人员范围（`personnel/access.ts` 的 `personScope`）裁剪。
  - **范围内**：返回 ID 与姓名等展示字段（字段仍按字段查看权裁剪）。
  - **评审组成员**（含组长，及活动、场次里嵌套引用的评审组成员）范围外时：**照原站显示姓名、计入人数**（DEC-331①），返回员工 ID 与姓名，**不带**工号、邮箱、手机、部门、职位等其他字段；用这个 ID 查人员详情（`GET /people/:id` 等）仍与“不存在”一样返回 404。评审组列表本身按“所属组织”裁剪（§5.1 表）。
  - **其他人员引用**（活动负责人 `manager_employee_id`、场次评委 `judge_employee_ids`、跟场人 `follower_employee_id`）范围外时：**与评审组成员相同（DEC-339②）**，返回员工 ID 与姓名，不带其他字段；用这个 ID 查人员详情与“不存在”一样 404。
  - **覆盖的出口**（同一 helper、同一种呈现，不各写一份；评审组成员另计入人数）：评审组列表 / 详情的成员与组长（PR-B）；活动详情的负责人 `manager_employee_id`（PR-B）；嵌套引用，即活动、场次里引用的评审组成员，以及场次的评委 `judge_employee_ids`、跟场人 `follower_employee_id`（C2 管理入口）；审计记录中这些字段的前后值（按查看人当前范围裁剪，§8）；导出（本任务的导出目前只有 C1 图谱导出，不含人员引用；今后任何导出带人员引用都按本条）。评委、跟场人经关系入口看到的场次信息按 §5.3 与 Q-T02-13，不走本条。
  - **写入**：前端按完整 ID 集合保存（两种呈现都返回了全部 ID，不做“保留看不到的成员”的写时合并）。服务端只对**新增**的 ID 校验在操作人人员范围内（范围外与不存在同一 404）；集合里原有的范围外 ID 原样提交视为保留，不重新校验可见性（同 DEC-319①“未改动不重校”）；删除成员不要求该成员在范围内（操作人能管理该评审组 / 活动）。组长恰好 1 个的校验对完整集合做。
- 所有候选 / 列表 / 详情 / 导出用同一谓词在分页前过滤（DEC-317②）；F-039 PR-B 的绕开检查落地后自动覆盖。

- C1 合并后、C2 合并前不登记，引擎按未接入 `DATA_UNAVAILABLE`。

**(3) 通用当前资格** `currentQualification(tx, tenantId, employeeId, asOf)`：发展通道与端口 (1) 用。判定照原站（DEC-335①，规格 23 §13）：每人的任职资格是一条不分类型、不重叠、无断档的单一时间轴，自动同步与手工录入混排；当前资格 = 覆盖 `asOf`（开始日 ≤ asOf 且结束日为空或 ≥ asOf）、开始日最晚的那一条，每人最多一条；记录都已结束的人没有当前资格。

**(4) 评定专用的上一条资格**（P2-07）`priorQualificationForApply(tx, tenantId, employeeId, activityTypeId, asOf)`：申报专用，按 EV-R18“先子集、取不到再评定记录”。子集部分按上面同一条单一时间轴取（DEC-335① 选项 c：不分来源、不分活动类型，即申报时点的当前资格）；子集取不到时，回退到该员工同活动类型最近一条已发布评定（通过取申请类别级别、未通过取原类别级别，设计推荐 🟡）。申报场景原站未实测，整条标 🟡。返回 `{ categoryId, levelId, lastResult, obtainedDate, source: 'subset' | 'evaluation' } | null`。

## 7. 规则实现要点

### 7.1 申报校验（EV-R19～R22，AC-EV-01～04；C2，跨级纯函数在 PR-B）

按顺序，第一条不满足即拒绝（400 `APPLY_REJECTED`，`details.reason`）：
1. 在职（§4.4 周期守卫）、任职部门在活动适用范围、申请类别 / 级别在活动范围（`OUT_OF_ACTIVITY_RANGE`）；
2. 活动已发布且在起止内（`ACTIVITY_NOT_STARTED`）、未完成（`ACTIVITY_COMPLETED`，在活动行锁内判断）；资格申报强控截止且已过（`APPLY_DEADLINE_PASSED`）；
3. 申请人方式（`SELF_APPLY_NOT_ALLOWED` / `NOMINATION_NOT_ALLOWED`）；
4. **跨级（P2-06）**：`跨过的级数 = rank(申请级别) − rank(原级别) − 1`，`跨过的级数 > max_level_jump` 拒绝（`LEVEL_JUMP_EXCEEDED`）。`rank` 是级别在**有序级别序列中的位置**（按顺序号升序后编号 1、2、3…），不直接用顺序号相减，所以顺序号不连续（如 10、20、40）时结果不变。AC-EV-01：原 P3、最多跨 1 级 → P4 跨 0 级、P5 跨 1 级允许，P6 跨 2 级拒绝；默认申请 = 原级别的下一级。“有序级别序列”取哪个集合（申请类别标准的级别范围 / 全部启用级别）、原级别不在该序列或为空时怎么办、申请级别不高于原级别时：Q-T02-06。
5. 同一活动重复（`DUPLICATE_APPLICATION`，AC-EV-04）：唯一性口径 Q-T02-19；
6. 参评条件：通用 + 匹配申请类别 / 级别的附加条件，按申请人类型取对应一套；不达标且不能破格 → 400，`details.failedConditions = [{seq, text}]`，提示“{姓名} 以下参评条件不达标：{序号}）{条件文本}”（🟢）；可破格时：勾选须填原因；未勾选也自动标记破格（EV-R21 🟡，AC-EV-03）。
- 批量提名 ≤ 500 行：保存待申报时校验 1～5，提交时逐条校验 6，逐条回执；每行逐条检查人员范围，范围外与不存在同一回执（§5.1 点名的批量命令）。

### 7.2 计分（EV-R38～R41，DEC-044；AC-EV-06 / 07 / 12）

- 分 ∈ [0, 满分]；按指标评分每项一个分，评总分一个总分。
- 权重（PR-B 纯函数）：`average` = 100% / 参与项数（剔除不显示、能力标准为空的指标）；`weighted`：指标 = 标准整体权重 × 明细权重%（空按 0%），通用项 = 自身权重；`sum` 不加权。AC-EV-07：32% / 48% / 20%。按 `chain_id` 各用本环节评价表计算，材料与答辩互不影响。
- 单评委总分：`average` = Σ分 / 项数；`weighted` = Σ(分 × 权重%)；`sum` = Σ分。**提交时评分项全部必填**（全空或部分留空都提示“存在未填写的必填项”，已填自动暂存，DEC-370② Q-T02-07）。
- 最终得分 = Σ已提交评委总分 / 已提交评委数（DEC-044；弃权不计；EV-R41 固定）；所有在职评委都已提交或弃权才进入 `reviewed`（AC-EV-12）；离职评委不计入“在职评委”。**已提交数为 0（全员弃权）**：Q-T02-18。
- 精度与通过判定（DEC-370② Q-T02-07）：numeric 精确计算；单评委总分四舍五入到 2 位；答辩得分（舍入后总分的平均）同样四舍五入到 2 位（DEC-370② 未单列 🟡）；通过判定用舍入后的值；显示两位 🟢 W-320。评委提交后、校准前可以改分重提，重提后重算答辩得分。评委打分不需要先“开始答辩”（Q-T02-08）；评委只看自己的记录，提交前后都看不到其他评委的分数和姓名（Q-T02-13 评委部分）。
- 弃权（EV-R31 🟢）：评委本人或跟场人，原因必填，不可撤销，清空该评委评价，提示原文照抄；按钮权限 `TEvaluation.EvaluationRecord / Abstain` 与关系入口的组合：Q-T02-13。
- 校准（EV-R36 / DEC-046）：最终得分 / 结果为空时默认取答辩得分 / 结果；优势、建议为空时按评委顺序拼接已提交评委内容；通过率 = 通过 / (通过 + 未通过)；确认后锁定评委评价，可重新校准。

### 7.3 场次（EV-R33～R35、R37）

开始时间 + 每人时长排时段；插入 / 拖拽后续顺延；评委冲突只查本系统 30 天内场次（第三方 ⏸），返回 `warnings` 不阻断；暂存不发通知，“确定并发送通知”登记待办；`reviewed` / `calibrated` 的人不能再调整；同一场次同时只有一人 `in_progress`，结束后不能再开始；打分是否须先开始答辩：Q-T02-08；有已评审 / 已校准人员的场次不能删。

### 7.4 并发与锁

- 锁序：员工 → 活动（计数）→ 评定数据 → 场次 → 评委记录 → 审批实例；Qualification 配置侧：类别 → 标准（聚合根）→ 指标 → 评价表（§3.4 冻结锁）。
- 真实 PostgreSQL 交错测试：① 同一员工并发两次申报同一活动只成功一次；② 校准与评委提交交错（校准后提交 409）；③ 离职落地与评分交错（§4.4 守卫）；④ 冻结评分项与修改标准 / 指标 / 评价表交错（快照只含一方完整版本）；⑤ **迟提交事件**：事务 T1 先写 outbox 后迟提交、T2 后写先提交并被消费，T1 提交后下一轮仍被处理（§4.3）；⑥ **离职后重聘**：旧离职事件晚于重聘与新申报被消费，新评定不受影响、旧评定写入 409（§4.4）；⑦ **资格否决与结果发布交错**：两种先后顺序下都不会出现“资格未通过却已写子集”（§3.5 发布守卫）；⑧ **完成活动**：(a) 与并发申报交错，申报先拿活动锁则其评定随后被一并终止，完成先拿锁则申报被拒（`ACTIVITY_COMPLETED`），两种顺序都不留下进行中评定；(b) 与操作人人员范围变更交错，响应明细只按事务内读到的一次范围生成，不出现范围外人员（§5.1）；⑨ 驳回后改申请目标与下游写入（评委保存、提前转入）交错：只会出现“改目标 409”或“下游写入 409”之一（§3.4）；⑩ **C1 → C2 迁移窗口**：C1 期间登记未来离职 → C2 迁移（补入）与一笔并发的离职写入交错 → 两笔都各有且只有一行 `evaluation_leave`；迁移重跑无新增；生效日到达后终止该周期进行中评定（§4.3）。
