## 1. 表结构（迁移 0002、0004 由 Drizzle 生成，0003 手写）

| 表 | 层级 | 关键列 | 说明 |
|---|---|---|---|
| `tenants` | 平台，无 RLS | `code` 全局唯一、`timezone`（IANA，默认 `Asia/Shanghai`，CHECK `is_valid_iana_timezone`）、`status` active/suspended/restoring、`revision` | restoring = 按租户恢复后的隔离期（DEC-061） |
| `users` | 平台，无 RLS | `email` 唯一且必须小写、`status` active/disabled | 全局身份；一人可属多租户 |
| `system_settings` | 平台，无 RLS | `key`、`value jsonb`、`overridable`、`version` | 系统预置；`overridable=false` 即“预置只读”（`11` §13.1） |
| `tenant_memberships` | 租户，RLS | 唯一 `(tenant_id, user_id)`、`status` active/revoked、`revision` | 撤销只改状态、保留行 |
| `tenant_setting_overrides` | 租户，RLS | 主键 `(tenant_id, key)`、`value`、`active`（迁移 0004）、`revision`、`updated_by` | 有效值 = 激活的覆盖 ?? 系统值；恢复 = 置 `active=false`，不删行 |
| `audit_events` | 租户，RLS | `actor_user_id`、`action`、`object_type/id`、`before/after jsonb`、`occurred_at`（UTC）、`command_id` | 最小结构，只追加；R1-T16 扩展为字段级变更日志（DEC-019） |
| `command_ledger` | 租户，RLS | 主键 `(tenant_id, command_id)`、`request_hash`、`response_status/body` | 命令幂等台账（DEC-067） |

- 时间列一律 `timestamptz`：库内存 UTC 瞬时，显示时按租户时区换算（DEC-056）。
- 预置数据：`audit.retention = {queryMonths: 3, retainMonths: 6}`，可覆盖（`20` §5 第 4 条）。
- M0 示例表 `m0_demo_validity` 也带 `tenant_id`，一并纳入 RLS（守卫要求）。
- 测试夹具 `tenant_probe` 只由 `packages/testkit` 建，不进产品迁移；R1-T03 落地组织表后 AC-TEN-01 改用组织表补测。

## 2. RLS 方案

- 每张带 `tenant_id` 的表：`ENABLE` + `FORCE ROW LEVEL SECURITY`，策略 `tenant_isolation`，`USING` 与 `WITH CHECK` 都是 `tenant_id = current_tenant_id()`。
- `current_tenant_id()` = `NULLIF(current_setting('app.tenant_id', true), '')::uuid`：未设置或为空 → NULL → 比较结果非真 → 读不到、写不进。
- 新表统一调用 `SELECT enable_tenant_isolation('表名')`（迁移 0003 提供，已对 PUBLIC 撤销执行权），再单独 `GRANT` 给 `app_user`。
- 角色：`app_user`（租户路径）、`app_platform`（平台路径），均 `NOLOGIN NOSUPERUSER NOBYPASSRLS`。权限最小化：
  - `app_user`：租户表按需 SELECT/INSERT/UPDATE/DELETE；`audit_events`、`command_ledger` 只有 SELECT/INSERT；`system_settings` 只读；平台表 `tenants`、`users` 无权限。
  - `app_platform`：只有平台表 SELECT/INSERT/UPDATE，对任何租户表**无权限**。
- 审计只追加：语句级触发器对 UPDATE / DELETE / TRUNCATE 一律报 `55000`，对表属主和超级用户同样生效。
- **CI 守卫** `tests/guard-rls.test.ts`：扫描 `pg_catalog`，public 中凡含 `tenant_id` 列的表必须 `relrowsecurity`、`relforcerowsecurity` 为真且至少一条策略；另验证两个角色不是超级用户、无 BYPASSRLS；并用一张漏配的临时表证明守卫本身有效。

## 3. 两条访问路径（`packages/db/src/tenant-context.ts`）

| 路径 | 函数 | 事务内动作 | 能碰什么 |
|---|---|---|---|
| 租户 | `withTenant(db, tenantId, fn)` | 校验 UUID → `set_config('app.tenant_id', id, true)` → `SET LOCAL ROLE app_user` | 本租户的 RLS 表 + 只读系统预置 |
| 平台 | `withPlatform(db, fn)` | 清空 `app.tenant_id` → `SET LOCAL ROLE app_platform` | 仅平台表 |

- 都是事务级设置，事务结束即还原，连接池复用安全。
- 平台操作集中在 `packages/db/src/platform-ops.ts`（开租户、改租户状态、建用户、授予/撤销成员关系、下发预置）。平台方需要写租户数据（如成员关系）时，**显式**切到 `withTenant`，没有“绕过 RLS”的第三条路。
- 业务代码不得用连接角色直接读写业务表；连接角色可能是表属主或超级用户（测试中即如此）。

## 4. 请求链路（`apps/api`）

`requireJson` → `limitBody` → `/api/tenant/*` 租户上下文中间件（每次请求都执行）→ 路由（授权钩子 → `withTenant` / `runCommand`）。

中间件校验顺序与对外结果：
1. `IdentityResolver` 得不到用户、或用户不存在 / 非 active → **401 UNAUTHENTICATED**；
2. 缺少或非法 `X-Tenant-Id` → **400 TENANT_CONTEXT_REQUIRED**；
3. 在该租户下没有 active 成员关系（**含租户不存在**）→ **403 TENANT_NOT_MEMBER**，不泄露租户是否存在；
4. 租户非 active（suspended / restoring）→ **403 TENANT_UNAVAILABLE**，只有成员才可能看到这一码。

- **租户放请求头而非路径**：租户是会话上下文而非资源属性；资源路径保持稳定；中间件是唯一解析点，路由无从绕过。`tenantOf(c)` 在未经中间件时直接抛错。
- **他租户对象 ID 统一 404**：RLS 下他租户对象与不存在的对象在查询结果上无法区分，接口也不做区分，不泄露存在性。
- 撤销成员关系、停用租户或用户后，下一次请求立即生效（无会话缓存；日后加缓存须在撤权时清除，AGENTS.md §10「权限」）。
- 身份：`IdentityResolver` 可插拔。本任务只有开发/测试实现（HMAC 签名头，仅 `NODE_ENV=test|development`，密钥 ≥32 字符）；`server.ts` 在其他环境调用 `identityResolverFromEnv()` 直接抛错阻止启动。
- 授权：`Authorizer` 钩子（代码注释“R1-T01 接入”）。缺省**一律拒绝（含读）**→ 403 FORBIDDEN；测试通过 `AppDeps.authorize` 注入放行。生产入口 `server.ts` 不注入授权，即使用拒绝实现（选“拒绝”而非“启动报错”：健康检查仍可用，租户接口在 R1-T01 前全部 403）。

## 5. 配置接口与平台约定

| 接口 | 行为 |
|---|---|
| `GET /api/tenant/settings/:key` | 返回 `{key, value, source: system/tenant, revision, systemVersion, overridable}`，`ETag` = revision |
| `PUT /api/tenant/settings/:key` | 覆盖；必须 `If-Match`（缺 → 400 REVISION_REQUIRED，不一致 → 409 REVISION_CONFLICT）；只读预置 → 403 SETTING_READ_ONLY |
| `DELETE /api/tenant/settings/:key/override` | 恢复系统值（覆盖行置非激活）；必须 `If-Match`；本就取系统值时为空操作、不写审计 |

- revision：每个（租户, 配置）一行，从未覆盖过时为 0；覆盖、恢复各 +1，**单调递增**，取系统值状态下 ETag 也返回该行 revision，因此恢复后持旧 ETag 的写入必得 409（无 ABA）。读取覆盖行时 `FOR UPDATE`，并发首次覆盖的主键冲突映射为 409。
- 业务写、审计、命令台账在**同一租户事务**内完成（`apps/api/src/commands.ts`）。带 `Idempotency-Key` 时：同键同内容返回首次结果、不再执行；同键异内容 409 IDEMPOTENCY_CONFLICT；并发同键由台账主键冲突兜底后重放。失败命令整体回滚、不入台账。
- 审计 `occurred_at` 取注入时钟（UTC 瞬时），与数据库会话时区无关。

## 6. fail-closed 清单

| 位置 | 失败时的行为 |
|---|---|
| RLS 策略 | 未设 / 空 `app.tenant_id` → 0 行、写入 42501；非法 UUID → 转换报错 |
| `withTenant` | 租户 ID 非 UUID → 抛错，不退化为不过滤 |
| 平台角色 | 对租户表无任何权限 → 42501 |
| 中间件 | 任一校验不过即拒绝；`tenantOf` 缺上下文即抛错 |
| 身份 | 缺省 `denyAllIdentity`；生产未接入真实登录 → 拒绝启动 |
| 授权 | 缺省拒绝一切操作（含读） |
| 时区 | 领域层与数据库 CHECK 两层只接受 IANA 名（拒绝 `+08:00` 之类偏移） |
| 审计 | 触发器拒绝改删与清空，属主与超级用户也不例外 |

部署要求：连接数据库的登录角色须被 `GRANT app_user, app_platform`，否则 `SET ROLE` 失败（即请求失败，而不是放行）。非超级用户的迁移角色无权建角色时，由 DBA 预建（`scripts/dev-db.sh` 已为云端容器做好）。
