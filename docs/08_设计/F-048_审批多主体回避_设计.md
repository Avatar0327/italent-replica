## 0. 一页摘要

- **问题**：审批实例现在只有一个主体（`approval_instances.subject_employee_id`）。自审（DEC-058 / 068）、异常管理员回避（DEC-091）、管理员不得干预本人单据（DEC-092）都按“发起人 ∪ 这一个主体”判断，散在 8 个文件。R3-T04 的结果审批是**集合审批**，一个实例涵盖多名被盘点人，DEC-309③ 定为保留。
- **契约（DEC-329）**：
  1. **冻结两个集合**：主体员工集合 `S` 和主体账号集合 `U(S)`，都在**实例创建**和**重提**时写入新表 `approval_instance_subjects`，按轮次插入、只增不减、行不可改。之后判定一律读冻结值，不再实时查绑定（⑤）。
  2. **节点级**：
     - 新增开关 `avoidSubjects`，新建节点默认关。命中时**照原站按节点配置自动执行**（①），取证前只有“跳过”一种动作（🟡 Q-M0-138）。
     - 现有开关 `avoidSelf` 保持 DEC-068 处理（改派直线经理 / 异常管理员），新建节点默认值改为**关**（④）。
  3. **实例级**：{发起人} ∪ 全部主体，不受开关影响（②）。适用于异常管理员、管理员干预、交接、接管和提交预检。
  4. **抄送**：节点开启 `avoidSubjects` 时，不能抄送给主体，返回 409（③）。
  5. **入口**：33 个入口都改调同一组判定函数（§6）。
- **新建节点默认关（R1-01）**：`avoid_self` 列默认值改为 `false`，只影响新建节点。存量已发布版本和在途实例保持冻结值。读取回显两个开关一律显式输出。补其他审批类型的回归测试（§3.2、§10 T11）。
- **v2 中删除的部分**：绑定锁协议、触达改派、补偿扫描、待办实时过滤。原因：账号集合冻结后，审批途中的首次绑定按 DEC-329⑤ 不追溯，判定结果在一轮内不会变（§7）。
- **第 2 轮审查（v2）的 4 项 P2 在 v3 的处理**：
  - R2-01：绑定锁删除；冻结行 `user_id` 不建外键；外键隐式锁逐项核对（§5.4）。
  - R2-02：候选按员工来源 / 账号来源分开，账号来源只按冻结的 `U(S)` 判断（§2.3）。
  - R2-03：没有前置自动改派，救援动作不走自动路由（§7.1）。
  - R2-04：自动跳过使用专用 origin `subject_skip`，记为系统处理（§7.2）。
- **适配器**：业务域只实现 `BusinessAdapter.subjects?()`，即“对象 → 员工 ID”映射。
- **迁移**：1 个。
- **拆分**（DEC-317③）：PR-1 存储与定义，PR-2 判定接入（§14）。PR-1 的定义校验**拒绝** `avoidSubjects=true`，到 PR-2 与运行判定同时放开，任何中间版本上线都不会出现“开关已开、判定未接”的窗口（R3-01）。

## 1. 问题与范围

### 1.1 场景
项目管理员 P 对盘点项目 X 发起结果审批，一个实例涵盖被盘点人 A1～A10。可能出现：
- A3 是部门负责人节点解析出的审批人；
- A5 持有干预按钮，且实例在其范围内；
- A7 是异常管理员或替代人；
- A2 被转交、加签或管理员改派为审批人；
- P 本人也在 A1～A10 中；
- A9 在实例创建时没有账号，审批途中首次绑定了账号 U。按 DEC-329⑤，U 不追溯回避，到下次重提重新冻结时才回避。

### 1.2 范围
- 做：
  - 主体员工集合与账号集合的冻结存储；
  - 节点开关 `avoidSubjects` 及其自动动作（取证前只有“跳过”）；
  - 新建节点默认关；
  - 统一回避判定，§6 全部入口改调；
  - 抄送排除主体；
  - 仿真支持；
  - 适配器接口与契约测试套件。
- 不做（§11）：
  - 新的审批类型 / 业务类型（由 T04 C-08 负责）；
  - 集合实例的数据范围谓词；
  - 依赖单主体的表达式和消息；
  - 前端；
  - 追溯已完成的决定，或冻结后才发生的绑定。

## 2. 术语、生命周期与回避集合

### 2.1 术语

| 名称 | 定义 |
|---|---|
| 发起人 `initiator` | `approval_instances.initiator_user_id`（不可改，0029 触发器） |
| 单主体 `primary` | `approval_instances.subject_employee_id`（可空） |
| 主体集合 `S` | 本实例**全部轮次**冻结行中的 `employee_id` 并集（只增不减，DEC-329⑤）；新实例的冻结行一定包含单主体 |
| 账号集合 `U(S)` | 本实例全部轮次冻结行中的 `user_id`（非空者）并集。冻结时取当时的绑定（`permission_user_person_links`），**不看账号 / 成员状态**（Q05） |
| 单主体账号 `U(primary)` | 冻结行中 `employee_id = primary` 的 `user_id`（`avoidSelf` 口径用） |
| 存量实例 | F-048 上线前已创建、没有冻结行的实例：`S = {primary}`，`U(primary)` 沿用现状的实时 `userOfPerson(primary)`。行为与上线前完全一致，作为存量冻结口径 |

### 2.2 生命周期（R1-02 → DEC-329⑤）

| 对象 | 冻结时点 | 存储 | 重提时 | 冻结后的变化 |
|---|---|---|---|---|
| `S` | 实例创建（`insertInstance` 之后、提交预检与路由之前）；重提（`resume`，写新一轮） | `approval_instance_subjects.employee_id` | 新一轮 = 上一轮员工 ∪ 适配器当前返回的员工（只增不减） | 无（行不可改） |
| `U(S)` | 同上，与 `S` 同一语句写入（`LEFT JOIN permission_user_person_links`） | 同表 `user_id` 列 | 新一轮对本轮全部员工**重新取当时的绑定**；历史轮次的账号行保留，判定取并集 | 首次绑定发生在冻结之后：**按冻结值，不追溯**，直到下一次重提重新冻结 |
| 发起人、节点开关 | 实例创建、版本发布 | 实例行、冻结版本 | 不变 | 无 |

两个集合只在发起和重提时写入，这两个时点都持有实例锁，且实例上没有在办任务。所以**一轮之内判定结果不变**：任务派出时判过一次，之后不会出现新的命中者。办理时再查一次只是防御。

### 2.3 命中规则

被判定的人按**来源**分两类（R2-02），判定只和冻结值比较，所有入口都**不再实时**查“账号 → 人员”：

| 来源 | 哪些 | 命中 `S` / `U(S)` | 说明 |
|---|---|---|---|
| **员工来源** | 从员工解析出的表达式候选：部门负责人 / HRBP / 一级组织负责人、直接上级、`idp_employee`、`idp_tutor`、自审改派的直线经理 | `personId ∈ S` **或** `userId ∈ U(S)` | `personId` 是表达式的解析结果（组织角色、任职记录上的人员），不是从账号反查的 |
| **账号来源** | `owner`（发起人账号）、办理人、转交 / 加签 / 改派 / 抄送目标、异常管理员、交接替代人、租户管理员 | **只看 `userId ∈ U(S)`**（单主体口径为 `userId = U(primary)`）；忽略 `personId` | `owner` 候选现状经 `personOfUser(initiator)` 得到 `personId`，可能为空并被缓存（`resolver.ts:241`）。判定不依赖它，避免空值漏判 |

- **缓存**：`resolveCandidate` 的推进内缓存（X-20）只保存候选本身（来源、`userId`、`personId`）。回避结论不进缓存，每次由 `nodeRecusal(候选, recusalFacts)` 在冻结值上现算。`recusalFacts` 本身就是冻结值，可以在 Run 内缓存，冻结写入后刷新。
- **对 R2-02 场景的结论**：发起人账号 U 在冻结时已属于 `U(S)` → `owner` 节点命中（`userId ∈ U(S)`），按节点开关回避，不会进入相同 / 历史同人自动同意（回避先判，§2.4）。U 在冻结时还不属于 `U(S)`（冻结后才首次绑定）→ 本轮不命中，这是 DEC-329⑤“冻结后不追溯”的约定结果，不是漏判；重提后命中。

### 2.4 两层回避集合

| 层 | 命中条件 | 处理 | 用途 | 受开关影响 |
|---|---|---|---|---|
| 节点级·自审 | `avoidSelf(node)` ∧ (`userId = initiator` ∨ 命中 primary) | DEC-068：回避跳过（不计同意），转直线经理 → 异常管理员（不变） | 路由；办理人；目标；详情办理类动作 | 是 |
| 节点级·多主体 | `avoidSubjects(node)` ∧ 命中 `S` / `U(S)` | 路由时**按节点配置自动执行**：只有“跳过”（DEC-329①，🟡 Q-M0-138）；办理人 / 目标 / 抄送：409 | 同上 + 抄送 | 是 |
| 实例级 `I` | `userId = initiator` ∨ 命中 `S` / `U(S)` | DEC-091 / 092 处理（扩到全部主体，DEC-329②） | 异常管理员、管理员操作人、交接操作人与替代人、停用接管、提交预检 | 否 |
| 实例级 `I′` | 命中 `S` / `U(S)` | 同上 | IDP 计划所有者干预（DEC-321①） | 否 |

**两个开关同时命中时的先后**：`avoidSelf` 先判（DEC-068 要求改派给真人审批，比自动跳过更严）。之后才判 `avoidSubjects`，再判相同 / 历史相同审批人自动处理（DEC-106）。

## 3. 节点开关

### 3.1 `avoidSubjects` 与命中动作

| 项 | 内容 |
|---|---|
| 字段 | `NodeActions.avoidSubjects: boolean`（缺省 `false`）；`ApprovalNode.avoidSubjectsResult`（命中动作，对应原站 `isSameExpressionSkip` 的 `…SkipOutcome`） |
| 取值（DEC-331⑤） | 契约类型预留原站全部取值：`'skip'`（跳过）\| `'approve'`（同意）\| `'disagree'`（不同意）\| `` `exit:${code}` ``（自定义出口动作）（规格 14 §11.6）。**本任务只启用 `'skip'`**（DEC-329①）：输入枚举与列 check 都只接受 `'skip'`，其余取值返回 400 `APPROVAL_AVOID_SUBJECTS_RESULT_UNSUPPORTED`。X 的可选范围仍为 🟡 Q-M0-138 |
| 其余取值的启用条件 | 每项都需要 Q-M0-138 取证确认适用节点后，另开任务放宽枚举与 check（只增约束值，不改数据）：① `'approve'`：记为被回避者本人同意，**须做盲审**（同 DEC-106 自动同意与清单 5），盲审不过按 DEC-069 转异常管理员；会签节点计入流转规则；② `'disagree'`：节点须有「不同意」出口，按 DEC-144 计数，并行中间节点不可选（`14` §11.6）；③ 自定义出口：复刻首版没有自定义出口线（`types.ts` NODE_EXITS 只有同意 / 不同意），待自定义出口落地后才可选 |
| “跳过”语义 | 同 DEC-106：沿「同意」路径流转，处理人记为“系统”，任务 `origin='subject_skip'`、`status='skipped'`、`assignee=null`、`candidate=被回避者`；日志 `skip`，`detail.mechanism='subject'`。不计任何人的同意，不触发“同意”消息 |
| 盲审 | **不做**。跳过没有审批人作判断（不同于“相同审批人自动同意”需要该审批人看得到变化字段） |
| 适用节点 | 与 DEC-106 的“跳过”相同：只有单人审批节点、且有「同意」出口时可开启。会签节点开启时返回 400 `APPROVAL_AVOID_SUBJECTS_UNSUPPORTED`（🟡 原站会签节点可选哪些动作待 Q-M0-138） |
| 存储 | `approval_process_nodes.avoid_subjects boolean NOT NULL DEFAULT false`、`avoid_subjects_result text NOT NULL DEFAULT 'skip' CHECK (avoid_subjects_result IN ('skip'))`；随版本冻结（DEC-097） |
| 预置 | 现有全部预置显式 `avoidSubjects: false`；T04 结果审批预置由 T04 设为 `true` |

### 5.4 锁（R2-01）
- 冻结行与实例在同一事务、同一实例锁下写入。读取不加锁。
- **v2 的绑定锁全部删除**：
  - 审批侧不再取 `personLink` 共享锁，绑定端（`user-provisioning.ts`）不改。
  - 理由：冻结后审批命令不再实时读取绑定，与首次绑定之间没有需要串行化的读写。冻结语句（`INSERT … SELECT … LEFT JOIN permission_user_person_links`）读到语句开始时已提交的绑定；并发提交的绑定按 DEC-329⑤ 归入“冻结之后”，不追溯。
  - 因此 R2-01 的锁环（交接持成员行 `KEY SHARE` → 绑定持排他锁并等成员行 → 交接等绑定锁）的第三条边不再存在。
- **外键隐式锁核对**（冻结写入新增的行锁）：

  | 外键 | 隐式锁 | 可能冲突的写锁 | 结论 |
  |---|---|---|---|
  | `employee_id`（**不建外键**，P3 更正 v3） | 无 | v3 曾写“员工行只被 `FOR NO KEY UPDATE`”，不准确：人员模块 `lockPerson`（`personnel/store.ts:50`）与合同模块 `lockEmployee`（`contracts/context.ts:23`）都对员工行用 `FOR UPDATE`，与外键的 `KEY SHARE` 冲突。集合实例冻结时要对成百上千个员工行取 `KEY SHARE`，会与持有其中若干员工 `FOR UPDATE` 的命令互等（多员工加锁顺序不一致时成环）。因此不建外键，存在性用不加锁查询校验（§5.1） | 不涉及 |
  | `instance_id → approval_instances` | 实例行 `KEY SHARE` | 本事务已持有该实例锁 | 不等待 |
  | `user_id`（不建外键） | 无 | 绑定端对成员行 `FOR UPDATE` | 不涉及 |
  | 读 `permission_user_person_links`（普通 SELECT） | 无行锁 | — | 不等待 |

  | 实例行既有外键 `subject_employee_id → employment_employees`（现状） | 单主体员工行 `KEY SHARE` | 单主体业务的适配器在同一事务里已先锁住该员工（员工 → 实例，与全局顺序一致）；集合实例的单主体为空，不取 | 现状不变 |

  结论：冻结写入只对本事务已持有的实例行取 `KEY SHARE`，不新增任何会等待的锁边，现有取锁顺序不变（员工闭包 → 业务 → 组织 → 编制 → 审批实例）。
- **T13 用真 PG 证实**：① 交接事务持成员行 `KEY SHARE` 时并发首次绑定，再并发重提冻结，三者都能完成、无死锁，冻结结果要么含新绑定、要么不含；② 人员模块（`lockPerson`）与合同模块（`lockEmployee`）分别持主体员工行 `FOR UPDATE` 未提交时，集合实例发起 / 重提冻结不等待，可先于它们提交。

## 7. 冻结后的不变式（取代 v2 的 §7）

- **一轮之内判定结果不变**：`S`、`U(S)`、发起人、节点开关都已冻结。
  - 任务派出时（路由、转交、加签、改派、激活）判过的结果，到办理时不会变。
  - 已有的 pending / queued / add_signed 任务不需要事后改派；待办列表不需要实时过滤。
- **冻结之后发生首次绑定**（场景 A9 → U）：本轮按冻结值，U 不回避（DEC-329⑤）。若 U 已是本单审批人，可以继续办理本轮任务；重提后新一轮冻结到 U，U 从此回避。审查若认为本轮也要拦，需另行决策，本设计不自造。
- **因此删除**：
  - 绑定共享锁（不再实时读绑定）；
  - 触达改派与补偿扫描（不会出现事后命中）；
  - 待办实时过滤；
  - 对权限模块与 `server.ts` 的改动。
- **保留的防御**：办理时（#10）与激活时（#13～#16）仍按冻结值再判一次。两处都是纯内存比较，不取锁；若出现命中，说明数据异常，按 409 / F8 处理，不静默放行。

### 7.1 自动跳过之后，以及救援动作（R2-03）

| 情形 | 处理 |
|---|---|
| 节点命中 `avoidSubjects` | 自动“跳过”总能完成：只允许在有「同意」出口的单人节点上开启（§3.1），跳过不需要接手人、不调 `exceptionAdminFor`，节点直接沿同意线流转到下一节点，下一节点照常路由 |
| 跳过后到了最后一个节点之后 | 实例按现状结束为“通过”（`complete`），业务照常落地。**注意**：若一条流程的每个审批节点都被跳过，实例会在没有任何人工同意的情况下通过。这是 DEC-329①“照原站自动执行”的直接后果，原站同样如此。T04 预置流程应保留至少一个不由被盘点人担任的节点（如 HR / 项目管理员节点），已写入 §13 交 T04 |
| 下一节点审批人为空或自审改派后无人（DEC-054 / 068） | 按现状转异常管理员。异常管理员按实例级 I 判定，命中则转其直线经理；仍不可用则抛 409 `APPROVAL_EXCEPTION_ADMIN_SELF`，触发推进的那条命令整体回滚、不留半截写入（现状）。冻结后这种情况在一轮内基本不会出现：提交 / 重提预检（#2）已按同一份冻结值确认异常管理员可用，剩余可能只来自直线经理或在职资格的实时变化（现状边角，F-048 不新增） |
| **救援动作不被前置自动处理挡住** | v3 **没有**任何“写命令前置的自动改派”（v2 §7.1 已删除），下列动作都不先跑自动路由或 `exceptionAdminFor`：① 发起人撤回 `withdraw`：只取消在办任务、改实例状态；② 管理员转交 / 改派给显式指定的 W（`admin-transfer`，或 `admin-intervene` 的 `reassign`）：只校验 W（资格 + 节点级回避）与操作人（实例级）；③ 异常管理员交接：显式替代人按实例级判定，不可用时**只跳过该单**并在回执中列出，不影响同批其他单；④ 业务删除作废 `cancel`。以上动作都**没有前置的自动改派**，不会因为“先要自动找到接手人”而被挡住；它们仍保留各自既有的校验与失败边界（revision 冲突、权限、范围、显式目标不合格等，失败时整单回滚）。只有 `admin-intervene` 的 `jump`（要从目标节点重新路由）和人工同意（推进到下一节点）会走路由，失败时整单回滚并返回明确错误码，此时上面四种救援动作仍然可用 |

### 7.2 自动处理留痕与撤回 / 历史算法（R2-04）

- 自动跳过的任务使用**专用 origin `subject_skip`**，并加入 `rules.ts:7` 的 `AUTO_ORIGINS`（与 `same_skip / history_skip / self_skip` 同类）。因此：
  - `untouchedStatus` 把它当作系统处理，不阻断前一节点的审批人撤回（`retrievableTask`）；
  - 它自身不会被当成“本人已同意”的可撤回任务（`assignee = null`、被 `!AUTO_ORIGINS.has` 排除）；
  - 有效历史（DEC-124）、`chainUserIds`、参与人判定（`disclosure.ts:110 / 132`、`queries.ts:66`）都不把它算作任何人的处理或参与。
- 会签节点的 `countersignRetrievable` 只看本次流转产生的下游任务；`subject_skip` 不会出现在会签节点上（§3.1），对下游的判断同上。
- v3 不再有 v2 的“关闭为 skipped 但保留原 origin”的改派留痕，R2-04 所指的误判来源已不存在。
- 测试 T14：前一节点开启撤回，A 同意 → 下一节点命中 `avoidSubjects` 被自动跳过 → 再下一节点待办 → A 仍可撤回；撤回后流程回到 A 的节点，被跳过节点在重新推进时重新判定。
