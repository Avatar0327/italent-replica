## 0. 一页摘要

- **问题**：审批实例现在只有一个主体（`approval_instances.subject_employee_id`）。自审 DEC-058 / 068、异常管理员回避 DEC-091、管理员不得干预本人单据 DEC-092 都按“发起人 ∪ 这一个主体”判断，散在 8 个文件（routing / rules / actions / handover / disclosure / engine / resolver / simulation）。R3-T04 的结果审批是**集合审批**：一个实例涵盖多名被盘点人。只把字段换成数组会漏掉其中部分入口（R3-08）。另外，“谁是主体本人”依赖人员与账号的绑定，而首次绑定可能在审批途中发生（R1-02）。DEC-309③ 已定保留集合审批。
- **契约**：
  1. **主体集合 `S`（员工）**：新表 `approval_instance_subjects`，按轮次插入、不可改；读取时并入单主体列（单主体归一化）。按当前轮还是历史全部轮判定，待定（Q04）。
  2. **主体本人（账号）**：不预先物化账号集合，**每次判定时按“账号 → 人员”现查**，查之前对该账号取共享的绑定锁，与首次绑定的排他锁同键（§5.5）。绑定只增不改，所以一个账号只会从“不回避”变成“回避”，不会反过来。
  3. **判定函数**：纯函数模块 `domain/approval/recusal.ts` 提供两层：
     - 节点级 `nodeRecusal`：节点开关 `avoidSelf` 管发起人与单主体；新增 `avoidSubjects` 管全部主体，照原站缺省关。
     - 实例级 `instanceRecusal`：发起人 ∪ 全部主体，不受开关影响（Q02）。
  4. **当前回避检查（R1-02）**：每个“以某人身份办理”或“把任务交给某人”的入口，都在当时重新判定，共 34 个入口（§6）。身份变化后，已有的待办 / 排队任务按 §7 处置：触达时改派，加上补偿扫描。待办列表按当前身份过滤。
- **新建节点 `avoidSelf` 的缺省值**：与 §46“照原站默认关闭”冲突，待定（R1-01 → **Q10**）。两个选项分别写清缺省值、输入、存储、回显（§3.2）。存量版本和在途实例一律保持冻结值。
- **适配器**：业务域只实现 `BusinessAdapter.subjects?(tx, ctx, businessId)`，即“对象 → 员工 ID”映射，不写回避。不实现的业务仍是单主体。
- **迁移**：1 个（节点列 `avoid_subjects`、可能调整 `avoid_self` 列缺省值、主体表、RLS、不可变触发器），编号不写死。
- **拆分**（DEC-317③）：PR-1 契约与同步判定；PR-2 身份变化（绑定锁、触达改派、补偿扫描、待办过滤）（§14）。

## 1. 问题与范围

### 1.1 场景
项目管理员 P 对盘点项目 X 发起结果审批，一个实例涵盖 10 名被盘点人 A1～A10（主体集合）。可能出现：
- A3 是“部门负责人”节点解析出的审批人；
- A5 持有审批中心转交 / 干预按钮，且实例在其范围内；
- A7 是该流程的异常管理员或替代人；
- A2 被转交 / 加签 / 管理员改派为审批人；
- P 本人也在 A1～A10 中；
- **A9 还没有账号，外部账号 U 被派为审批人。审批途中 HR 给 A9 办入职，用 U 的邮箱首次绑定 A9 → U（DEC-128 / DEC-158 外部用户转内部员工）。此后 U 即主体本人**（R1-02）。

### 1.2 范围
- 做：主体集合的持久化与读取；节点开关 `avoidSubjects`；新建节点开关缺省值（按 Q10）；统一回避判定；§6 全部入口改调统一判定；身份变化的锁协议与已有任务处置；仿真支持虚拟主体集合；适配器接口与契约测试套件。
- 不做（边界，见 §11）：
  - 新的审批类型 / 业务类型，由 T04 PR-A（C-08）登记；
  - 集合实例的数据范围谓词；
  - 集合实例的“异动员工本人”消息接收人；
  - 依赖单主体的审批人表达式；
  - 前端；
  - 已经完成的决定（同意 / 驳回等）不因事后身份变化而追溯作废（Q11，设计自定）。

### 1.3 集合审批
DEC-309③ 已定保留，本设计不改变审批单粒度、批量失败与撤回 / 部分通过的行为。

## 2. 术语、生命周期与回避集合

### 2.1 术语

| 名称 | 定义 |
|---|---|
| 发起人 `initiator` | `approval_instances.initiator_user_id`（账号，不可改，0029 触发器） |
| 单主体 `primary` | `approval_instances.subject_employee_id`（员工，可空） |
| 主体集合 `S` | 用于判定的员工集合 = 主体表中判定轮次的员工 ∪ {`primary`}（非空时）。判定轮次：Q04-A 为全部轮次的并集；Q04-B 为实例当前轮次。没有集合行的实例归一化为 `{primary}` 或 `∅` |
| 账号的人员 `person(u)` | `permission_user_person_links` 中账号 u 绑定的员工；不看账号 / 成员状态（Q05）；判定前取共享绑定锁（§5.5） |
| 命中主体 | 候选 `{personId, userId}`：`personId ∈ S`，或 `person(userId) ∈ S` |

### 2.2 生命周期（R1-02）

| 对象 | 何时写 | 能否变化 | 变化方向 | 判定时怎么读 |
|---|---|---|---|---|
| `S`（员工） | 发起写第 1 轮；每次重提写新一轮完整集合 | 一轮之内不变（只在持有实例锁、且无在办任务时写入） | 按轮次追加，行不可改（Q04 决定是“并集”还是“当前轮”） | 命令内读一次，Run 内缓存；**本命令写入新一轮后立即刷新缓存**（T9c） |
| `person(u)`（绑定） | 只由建档 / 入职的首次绑定写入（`user-provisioning.ts:34`，DEC-128）；没有改绑或删除入口（迁移 0033 收回 UPDATE） | 可以在审批途中出现 | 只会从“无绑定”变成“有绑定”，即“不回避 → 回避”单向 | **每次判定现查**，查前取共享绑定锁；不缓存跨命令结果 |
| 发起人 | 实例创建时 | 不变 | — | 实例行 |
| 节点开关 | 版本发布时冻结（DEC-097） | 不变 | — | 实例冻结版本 |

结论：一轮之内，回避判定结果只会因首次绑定从“不回避”变为“回避”。§6 的“当前检查”和 §7 的“已有任务处置”针对的就是这一变化。

### 2.3 两层回避集合

| 层 | 命中条件 | 用途 | 受节点开关影响 |
|---|---|---|---|
| **节点级** `N(node)` | (`avoidSelf(node)` ∧ (是发起人 ∨ 命中 `primary`)) ∨ (`avoidSubjects(node)` ∧ 命中 `S`) | 节点路由；以办理人身份做的全部任务动作（§6 #10）；转交 / 加签 / 改派的目标；排队激活与回到原审批人；详情页办理类动作；待办列表 | 是 |
| **实例级** `I` | 是发起人 ∨ 命中 `S` | 异常管理员（DEC-091）、管理员操作人（DEC-092）、交接操作人与替代人、停用接管、提交预检、异常管理员任务的待办与改派 | 否（Q02） |
| 实例级 `I′` | 命中 `S` | IDP 计划所有者干预（DEC-321①） | 否 |

## 3. 节点开关

### 3.1 `avoidSubjects`（新增）

| 项 | 内容 |
|---|---|
| 字段 | `NodeActions.avoidSubjects?: boolean`；判定 `avoidsSubjects(node)` = `=== true`（缺省关） |
| 依据 | §46 / DEC-318：多主体回避是节点开关，照原站默认关。原站最接近的是节点级“审批人与 X 相同时”（`isSameExpressionSkip`），默认关 |
| 存储 | `approval_process_nodes.avoid_subjects boolean NOT NULL DEFAULT false`；随版本冻结（DEC-097） |
| 预置 | 现有全部预置（调动、离职、员工子集、合同、IDP 三类）显式 `false`；T04 结果审批预置由 T04 设为 `true` |

### 3.2 `avoidSelf` 新建节点的缺省值（R1-01，**待定 Q10**）

两个选项共用的部分：
- **存量已发布版本、在途实例**：一律用版本中冻结的列值（现有行都是 `true`，IDP 预置为 `false`），迁移不改存量行。
- **新版本 `POST /processes/:id/versions`**：逐节点复制上一版本的值。
- **回显**：`GET /processes`、`GET /processes/:id`、发布 / 新版本 / 草稿保存的响应，节点 `actions` **始终显式给出** `avoidSelf` 与 `avoidSubjects` 的布尔值。现状只在 `avoidSelf=false` 时回显（`definitions.ts:177`），改为两者都显式输出。只增字段，旧客户端不受影响。
- **草稿整份替换 `PUT /processes/:id/draft`**：请求里没写这两个开关时，节点键已存在的沿用该节点当前草稿值；新节点键用“新建缺省值”；显式值优先。这样旧客户端保存草稿时，不会因漏传字段而悄悄翻转已有节点的开关。
- **预置安装**：一律显式写值，不依赖缺省。

| | **选项 A：照 §46 / 原站，新建节点缺省关** | **选项 B：维持基线，新建节点缺省开（DEC-058 有意差异 D-016）** |
|---|---|---|
| 作用对象 | 复刻系统 | 复刻系统 |
| 新建节点（`POST /processes`、草稿新增节点）未传 | `avoidSelf = false` | `avoidSelf = true` |
| 列缺省 | 迁移改 `avoid_self` 列 `DEFAULT false`（只影响新行） | 不变（`DEFAULT true`） |
| 领域判定 `avoidsSelf(node)` | 改为 `=== true`；输入边界、加载、预置都显式给值，内存里不再有“未给出”的节点 | 维持 `!== false` |
| 现有非 IDP 预置 | 显式写 `true`，保持 DEC-058 / 068 在标准流程上的落点；需确认是否改为 `false` 照原站（子选项 A1 保持 `true` / A2 改为 `false`） | 显式写 `true` |
| 影响 | 管理员新建流程不勾选时，发起人 / 单主体可以审批自己的单据（照原站）；DEC-058“禁止自审”只在勾选的节点生效，需要总编排确认这是对 DEC-058 的修订 | 与 §46 注记冲突，需要总编排修订 §46 |
| 测试 | 新建流程未传开关 → 发起人收到待办；旧版本实例仍回避（冻结值） | 现状测试不变 |

“现有测试不改全部通过”只能证明存量冻结值不变，不能证明新建节点缺省值符合要求。新建缺省值另有专门用例（§10 T11）。

## 5. 持久化、适配器与锁

### 5.1 表 `approval_instance_subjects`

| 列 | 类型 | 说明 |
|---|---|---|
| tenant_id | uuid NOT NULL | RLS `enable_tenant_isolation` |
| instance_id | uuid NOT NULL | FK (tenant_id, instance_id) → approval_instances |
| round | integer NOT NULL | 实例轮次（发起 = 1；每次重提写新一轮完整集合） |
| employee_id | uuid NOT NULL | FK (tenant_id, employee_id) → employment_employees |
| created_at | timestamptz NOT NULL | UTC |

- 主键 (tenant_id, instance_id, round, employee_id)；索引 (tenant_id, employee_id)。
- 不可变：触发器禁止 UPDATE / DELETE（借鉴不可变审计表思路）。按轮次存完整集合，Q04 两个选项都只改读取口径，不改表结构。
- 不回填：没有集合行的实例归一化为 `{primary}`。

### 5.2 读写

| 函数 | 作用 |
|---|---|
| `loadSubjects(tx, tenantId, instance, mode)` | `mode = 'all_rounds' \| 'current_round'`（由 Q04 定，常量收在一处），∪ primary |
| `appendSubjects(tx, ctx, run, employeeIds)` | 去重、`canonicalId`、上限 10,000（Q06，超出 400 `APPROVAL_SUBJECTS_TOO_MANY`）、写本轮完整集合、刷新 `run` 缓存 |

### 5.3 适配器接口

```ts

   * F-048：集合审批的“对象 → 主体”映射，返回本单涵盖的全部对象对应的员工 ID。不实现即单主体业务。
   * 只在发起与重提时调用；不得写入、不得自行判断回避。
   */
  subjects?(tx: Tx, ctx: ApprovalContext, businessId: string): Promise<readonly string[]>;
}
```

- 适配器返回本单快照涵盖的全部对象主体（含已终止对象，回避多算一人不会放过越权）。
- 契约测试套件 `runSubjectAdapterContract(factory)`：返回规范 UUID、覆盖全部对象、无写入、重复调用结果一致。
- 与 #113 v4 的差异：不用 `BusinessSnapshot.subjectEmployeeIds`（理由见附录 A）。

### 5.5 首次绑定与审批命令的锁协议（R1-02）

- **共用一个锁键**：现有绑定端口对账号取排他锁 `hashtextextended('<tenant>:person-link:<userId>', 0)`（`user-provisioning.ts:58`）。抽出 `permission/person-link-lock.ts` 的 `personLinkLock(tx, tenantId, userId, 'exclusive' | 'shared')`：两个 ID 都先经 `::uuid::text` 规范化（同 R6-1 派单闸做法），绑定端改用它。这是本任务唯一改到权限模块的地方。
- **审批侧**：`whoOf(userId)` 先 `pg_advisory_xact_lock_shared(同键)`，再读 `permission_user_person_links`（READ COMMITTED，加锁之后的语句能看到已提交的绑定）。锁持有到事务结束。
- **结果**：
  - 绑定先拿到排他锁：审批命令在共享锁上等它提交，之后读到新绑定，判为回避。
  - 审批命令先拿到共享锁：绑定等到审批事务提交后才写入。等价于“审批先、绑定后”，审批时 U 确实还不是主体本人。
- **锁序**：共享绑定锁在审批命令已持有业务 / 实例锁之后取，位于锁序末端。绑定端（`employment/routes.ts:183 → 188`）先锁员工、再取排他绑定锁，之后只锁成员行，不等审批侧持有的任何锁，所以不会成环。死锁检测命中时，现有 `LOCK_CONFLICTS` 返回 409 `APPROVAL_CONCURRENT_CONFLICT`。
- **路由候选**由表达式从员工解析而来，自带 `personId`，不需要绑定锁；只有按账号判定的写入口需要取锁：办理人、目标、异常管理员、替代人、租户管理员、加签激活人与返回的原审批人；待办、详情动作等读侧不取锁（§7.3）。

## 7. 身份变化后已有任务的处置（R1-02）

### 7.1 触达改派 `reconcileRecusal(tx, run)`
- **时点**：任何以 `openRun` / `openTask` 打开实例的写命令，取锁后、执行业务前调用（办理、转交、加签、抄送、编辑、撤回、管理员操作、交接、接管、补偿扫描）。
- **动作**：逐个检查本实例的在办 / 排队 / 挂起任务（`pending / queued / add_signed`），对办理人做当前判定（取共享绑定锁）。普通任务按节点级判定，异常管理员任务按实例级判定。
- **命中的处置**：

  | 任务状态 | 处置 |
  |---|---|
  | `pending` | 关闭为 `skipped`（`origin` 保留，日志 `recusal_reroute`，不计同意）。新任务挂在原任务下（沿用其 activation，会签一人一席与 `mergeSeat` 规则不变）：普通任务按 Q01-A 链路（直线经理 → 异常管理员）；异常管理员任务走 `exceptionAdminFor` |
  | `queued` | 关闭为 `cancelled`。轮到它时按 #13 走 `canTake`。为不留死链，这里直接在链上用接手人替换：新建同序 `queued` 任务，`parentTaskId` 不变 |
  | `add_signed`（前加签挂起的原审批人） | 不改；加签链结束回到他时按 #14 / #15 由 `canTake` 处理 |

- **写入**：任务、日志、审计（`approval.task.recusal_reroute`，before / after 含原 / 新办理人）、outbox `approval.task.reassigned`，与本命令同事务。实例 `revision` 随本命令加一。
- **命令本身**：办理人就是被改派者时，返回 409 `APPROVAL_SELF_REVIEW`（`rerouted: true`），事务**提交**（同 DEC-069 盲审）；其他人的命令照常继续。

### 7.2 补偿扫描（新定时任务）
- 只靠“触达”的话，没人碰的实例会一直挂着已回避的待办。
- 新增 `startApprovalRecusalScheduler`（`server.ts` 登记，环境变量 `APPROVAL_RECUSAL_SCHEDULER=off` 可关，缺省 5 分钟一轮）。按租户分页找“办理人当前命中回避”的在办 / 排队任务（§7.3 的同一谓词），逐实例在独立事务内以系统主体执行 `openRun → reconcileRecusal → persistRun`。
- 按 AGENTS §10 / DEC-052：幂等键 =（实例, 任务, 办理人）；失败记 failed、次数、原因，可重试；按租户时区运行（不涉及业务日期）；每轮有上限（200 实例），并带游标。
- 绑定发生后到被扫描到的这段时间里，该任务不会出现在待办列表（§7.3），U 也无法办理（#10），所以不会产生越权，只会有不超过一个扫描周期的停顿。

### 7.3 读侧当前过滤（不取锁）
- 待办 / 经理工作台 / 详情动作只读，不取绑定锁，按读取时已提交的绑定判断。
- 谓词（对 `approval_tasks t` / `approval_instances i` / 节点 `n`）：存在 `l = link(t.assignee)`，且满足以下任一：
  - 节点级：(`n.avoid_self` ∧ (`t.assignee = i.initiator` ∨ `l.employee = i.subject_employee_id`)) ∨ (`n.avoid_subjects` ∧ `l.employee ∈ S(i)`)；
  - 异常管理员任务：`t.assignee = i.initiator` ∨ `l.employee ∈ S(i)`。
- 读与写的结果允许短暂不一致（读先于绑定提交），写命令总会再按锁判定一次。

- 普通命令（`routes.command → runCommand`）：同键同内容**不重复执行**，台账回放首次的状态码与响应体。

- 合同批量：逐条独立命令 ID，逐条回放。

## 附录 A：为什么用适配器方法而不是快照字段
审批快照在每次 `openRun` 与每次详情读取时都会经 `adapter.snapshot` 重算。集合大时成本高，而且会出现“实时快照 vs 冻结集合”两个来源。主体集合只在发起和重提时取，持久化后判定只认持久化集合。
