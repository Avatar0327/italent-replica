## 0. 一页摘要

- **问题**：审批实例现在只有一个主体（`approval_instances.subject_employee_id`）。回避规则（自审 DEC-058 / 068、异常管理员回避 DEC-091、管理员不得干预本人单据 DEC-092）都按“发起人 ∪ 这一个主体”判断，散在 8 个文件、十余处调用点（routing / rules / actions / handover / disclosure / engine / resolver / simulation）。R3-T04 的盘点结果审批是**集合审批**：一个实例涵盖一个项目里的多名被盘点人。只把单主体换成数组，会漏掉其中某些入口（R3-08）。DEC-309③ 已定保留集合审批，不改成“每个对象一个实例”。
- **契约**：
  1. 实例持久化一份**主体集合**：新表 `approval_instance_subjects`，只增不减；读取时并入单主体列，做单主体归一化。
  2. 回避判定收在一个纯函数模块 `domain/approval/recusal.ts`，分两层：
     - **节点级**：节点开关 `avoidSelf`（现有，缺省开）决定发起人与单主体是否回避；新增节点开关 `avoidSubjects`（缺省**关**，照原站，DEC-318）决定全部主体是否回避。用于路由、办理、转交 / 加签目标，以及详情页能否显示同意 / 驳回等动作。
     - **实例级**：发起人 ∪ 全部主体，不受节点开关影响，与现行 DEC-091 / 092 同口径。用于异常管理员、管理员干预 / 转交、交接 / 接管。
  3. 所有入口只调这两个函数（§6 列出 28 个入口，逐项对应）。
- **输出**：命中节点级回避时，照 DEC-068 处理：回避跳过，不计同意，转该人直线经理；直线经理不可用时转异常管理员；异常管理员自己也回避时，转其直线经理，再不行就 409。办理时命中返回 409 `APPROVAL_SELF_REVIEW`，管理员命中返回 403 `APPROVAL_ADMIN_SELF`，交接时命中则跳过该单。
- **适配器**：业务域只实现 `BusinessAdapter.subjects?(tx, ctx, businessId)`，即“对象 → 主体（员工 ID）”映射，不写回避逻辑。不实现的业务（任职、员工子集、合同、IDP）仍是单主体，行为不变。
- **迁移**：1 个（`approval_process_nodes.avoid_subjects` 列 + `approval_instance_subjects` 表 + RLS + 不可变触发器），编号不写死。
- **对现有业务零行为变化**：现有业务的主体集合就是 `{subject_employee_id}`，`avoidSubjects` 缺省关，实例级集合等于现行的“发起人 ∪ 单主体”。现有 AC-APV 测试应不改即通过，作为回归证据。

## 1. 问题与范围

### 1.1 场景（集合审批）
项目管理员 P 对盘点项目 X 发起结果审批，一个实例涵盖 10 名被盘点人 A1～A10（主体集合）。可能出现：
- A3 是“部门负责人”节点解析出的审批人（审批自己的盘点结果）；
- A5 持有审批中心“实例转交 / 干预”按钮，且该实例在其范围内（干预自己的结果）；
- A7 是该流程的异常管理员，或是异常管理员停用时指定的替代人；
- A2 被转交 / 加签 / 管理员改派为审批人；
- P 本人也在 A1～A10 中（发起人兼主体）。

现在的单主体判断只认 `subject_employee_id`。集合审批的这一列为空，或只是其中一人，以上 5 种情况都拦不住。

### 1.2 范围
- 做：主体集合的持久化与读取；节点开关 `avoidSubjects`；统一回避判定；§6 全部入口改调统一判定；仿真支持虚拟主体集合；适配器接口；契约测试套件，供业务域复用。
- 不做（边界，见 §11）：
  - 新的审批类型或业务类型。`talent_review_result` 等由 R3-T04 PR-A（C-08）登记。
  - 集合实例的数据范围谓词，由各业务登记（C-08）。
  - 集合实例的“异动员工本人”消息接收人。
  - 依赖单主体的审批人表达式（直接上级等）在集合实例上的含义。
  - 前端。

### 1.3 与“每对象一个实例”的关系
DEC-309③ 已定保留集合审批。本设计不改变审批单粒度、批量失败与撤回 / 部分通过的行为。

## 2. 术语与回避集合

| 名称 | 定义 | 来源 |
|---|---|---|
| 发起人 `initiator` | `approval_instances.initiator_user_id`（不可改，0029 触发器） | 现有 |
| 单主体 `primary` | `approval_instances.subject_employee_id`（员工 ID，可空）及其绑定账号 | 现有 |
| 主体集合 `S` | `approval_instance_subjects` 中本实例的全部员工 ID ∪ {`primary`}（非空时）；**单主体归一化**：没有集合行的实例，`S = {primary}` 或 `∅` | 新增 |
| 主体账号 `U(S)` | `permission_user_person_links` 中绑定到 `S` 任一员工的账号，**不看账号 / 成员状态**（fail-closed，F048-Q05） | 新增 |
| 命中 | 候选 `{personId, userId}`：`personId ∈ S` 或 `userId ∈ U(S)`；比较一律用规范 UUID（DB 侧 `::uuid`，内存侧 `canonicalId`，DEC-194 / F-017） | 新增 |

两层回避集合：

| 层 | 集合 | 用途 | 受节点开关影响 |
|---|---|---|---|
| **节点级** `N(node)` | (`avoidSelf(node)` ? {initiator, primary} : ∅) ∪ (`avoidSubjects(node)` ? S : ∅) | 节点路由、办理（同意 / 不同意 / 驳回 / 驳回到上一步 / 跳转 / 后加签）、转交 / 加签 / 管理员改派的**目标**、详情页的办理类动作 | 是 |
| **实例级** `I` | {initiator} ∪ S | 异常管理员（DEC-091）、管理员干预 / 转交的**操作人**（DEC-092）、交接操作人与替代人、停用接管的替代人与租户管理员、提交预检 | 否（F048-Q02） |
| 实例级（所有者干预） | S（不含 initiator） | IDP 计划所有者干预 `ownerIntervention`（DEC-321①：发起人就是所有者本人，不回避） | 否 |

`avoidSelf` 的口径（initiator ∪ primary）原样保留。对现有单主体业务：`S = {primary}`，`N`、`I` 与现状逐格相同（§9 表）。

## 3. 节点开关 `avoidSubjects`

| 项 | 内容 |
|---|---|
| 字段 | `NodeActions.avoidSubjects?: boolean`；判定函数 `avoidsSubjects(node)` = `node.actions?.avoidSubjects === true`（**缺省关**） |
| 依据 | DEC-318 补充 / 派发注记：多主体回避做成节点级开关，照原站默认关闭。原站最接近的是节点级“审批人与 X 相同时”（`isSameExpressionSkip`，`14` §11.6、`28` K-37），默认关 |
| 存储 | `approval_process_nodes.avoid_subjects boolean NOT NULL DEFAULT false`；随版本冻结（DEC-097）；新版本从上一版本继承 |
| 输入 / 输出 | `definition-input.ts` 节点 `actions.avoidSubjects: z.boolean().optional()`；`definitions.ts` 读写同 `avoid_self`（只在为 true 时回显，与 `avoidSelf` 只在 false 时回显对称） |
| 预置 | 现有全部预置流程（调动、离职、员工子集、合同、IDP 三类）显式 `false`；R3-T04 结果审批预置在 T04 PR 中设 `true`（不在本任务） |
| 校验 | 不限审批类型。单主体业务开启后 `S = {primary}`，效果等于只回避单主体（不含发起人） |
| 与 `avoidSelf` 分立的理由 | `avoidSelf` 缺省**开**（DEC-058 有意差异 D-016，已在全部预置与在途版本上生效）；`avoidSubjects` 按 DEC-318 缺省**关**。合成一个开关，必然改变其中一方的缺省值 |

## 4. 契约：输入与输出

### 4.1 领域模块 `packages/domain/src/approval/recusal.ts`（纯函数，禁止 IO）

```ts
/** 实例的主体集合（已含单主体；员工 ID 与绑定账号均为规范 UUID）。 */
export interface SubjectSet {
  readonly employeeIds: readonly string[];
  readonly userIds: readonly string[];
}

/** 回避判定的实例事实：发起人、单主体（avoidSelf 口径）、全部主体（avoidSubjects 与实例级口径）。 */
export interface RecusalFacts {
  readonly initiatorUserId: string;
  readonly subjectEmployeeId: string | null; // 单主体
  readonly subjectUserId: string | null; // 单主体账号（现有 userOfPerson 口径）
  readonly subjects: SubjectSet;
}

export type RecusalReason = 'initiator' | 'subject';

/** 节点级（§2 N(node)）：路由、办理、转交 / 加签 / 改派目标、详情办理类动作。 */
export function nodeRecusal(
  node: { readonly actions?: Pick<NodeActions, 'avoidSelf' | 'avoidSubjects'> },
  who: Candidate,
  facts: RecusalFacts,
): RecusalReason | null;

/** 实例级（§2 I）：异常管理员、管理员操作人、交接 / 接管。ownerIntervention 时发起人不回避（DEC-321①）。 */
export function instanceRecusal(
  who: Candidate,
  facts: RecusalFacts,
  options?: { readonly exemptInitiator?: boolean },
): RecusalReason | null;
```

现有函数的改法（签名对旧调用方兼容）：

| 现有 | 改为 |

| `RoutingFacts`（`routing.ts:15`） | `extends RecusalFacts`；`subjectEmployeeId / subjectUserId` 字段保留（即单主体），新增 `subjects` |

| `avoidSelfExceptionAdmin`（`routing.ts:142`） | 管理员和直线经理都改用 `instanceRecusal`；签名入参 `facts` 改为 `RecusalFacts & Pick<RoutingFacts,'chainUserIds'>` |

### 4.3 判定输出（按入口类型）

| 入口类型 | 命中层 | 输出 | 错误码 / 留痕 |
|---|---|---|---|
| 节点路由（单人 / 会签逐席） | 节点级 | **回避跳过，不计同意**，转候选人直线经理。直线经理为空、自身命中节点级回避、或已在本单审批链上时，转异常管理员（DEC-068，F048-Q01） | 任务 `origin='self_skip'`（只留痕）+ 接手任务 `self_skip_manager` / `exception_admin`；日志 `self_skip.detail.recusal = 'initiator' \| 'subject'` |
| 异常管理员落定（含盲审转异常、会签重结算、加签回退） | 实例级 | 异常管理员命中，转其直线经理；直线经理也命中或已在链上，则不可用（DEC-091） | 409 `APPROVAL_EXCEPTION_ADMIN_SELF`（提交预检同码，整单不建） |
| 人工办理（同意 / 不同意 / 驳回 / 驳回到上一步 / 跳转 / 后加签） | 节点级 | 拒绝，任务不动（防御：按 §4.4 不变式不应出现） | 409 `APPROVAL_SELF_REVIEW` |
| 转交 / 加签 / 管理员改派的目标 | 节点级（目标任务所在节点） | 拒绝 | 409 `APPROVAL_SELF_REVIEW` |
| 管理员干预 / 转交的操作人（DEC-092） | 实例级（所有者干预：不含 initiator） | 拒绝 | 403 `APPROVAL_ADMIN_SELF` |
| 异常管理员交接：操作人 | 实例级 | 本单跳过，其余照常 | `skipped[].reason = 'APPROVAL_ADMIN_SELF'` |
| 异常管理员交接：替代人 | 实例级 | 转替代人直线经理；不可用则本单跳过 | `'APPROVAL_EXCEPTION_ADMIN_SELF'` |
| 停用接管：替代人 / 租户管理员 | 实例级 | 替代人命中，回退租户管理员；租户管理员逐个按 DEC-091 判断；都不可用则拒绝停用 | 409 `APPROVAL_EXCEPTION_ADMIN_UNAVAILABLE`（现有） |
| 详情动作 | 办理类按节点级，管理员类按实例级 | 命中则不公布对应动作，与命令共用同一函数 | — |

`APPROVAL_SELF_REVIEW` 的错误消息改为“发起人或被审批对象本人不能审批自己的单据”，`details.recusal` 给出 `initiator | subject`。错误码不变，现有客户端不受影响。

### 4.4 不变式
1. **主体集合在一轮审批内不变**：只在发起（insertInstance）和重提（resume）时写入。这两处都持有实例锁，且此时实例上没有在办任务（重提前已退回或撤回，任务均已取消）。
2. 因此一轮内，节点级回避在派单时判过一次即可。加签排队激活、回到原审批人、会签重结算都不会产生新的命中者；办理时再查是防御性检查，有测试覆盖。
3. 回避判定只读，不取新锁；主体行与实例同事务写入。取锁顺序不变（员工闭包 → 业务 → 组织 → 编制 → 审批实例，`org/locks.ts`）。

### 4.5 与现有规则的先后与关系

| 规则 | 关系 |
|---|---|
| DEC-054 / 098 / K-38 审批人为空 | 先判。候选为空（无账号、停用、未激活、已离职）按现状处理，不进入回避判定 |
| DEC-058 / 068 自审 | `avoidSelf` 口径不变；`avoidSubjects` 命中的处理方式与之相同（F048-Q01 推荐 A） |
| DEC-106 相同 / 历史相同审批人自动处理 | 回避优先（与 DEC-068 优先级一致）；回避跳过的候选人仍按 DEC-114 留作下一节点“与上一节点相同”的比较对象（现状） |
| DEC-069 盲审转异常管理员 | 异常管理员落定按实例级回避（现状经 `exceptionAdminFor`，自动覆盖） |
| DEC-070 管理员转交给自己 | 操作人先过 DEC-092 实例级；目标（本人）再过节点级 |
| DEC-091 异常管理员回避 / DEC-123 停用接管 | 集合由 initiator ∪ primary 扩为 I |
| DEC-092 管理员不得干预本人单据 | 集合由 initiator ∪ primary 扩为 I；DEC-321① 所有者干预不含 initiator |
| DEC-115 记录隐藏 / C-非3 | 回避跳过的留痕任务（`origin='self_skip'`）不算参与，现状不变 |
| DEC-318 K-37 | IDP 预置 `avoidSelf=false`、`avoidSubjects=false`，员工本人节点不回避 |

## 5. 持久化与适配器

### 5.1 表 `approval_instance_subjects`（迁移随本任务）

| 列 | 类型 | 说明 |
|---|---|---|
| tenant_id | uuid NOT NULL | 租户维度（RLS `enable_tenant_isolation`） |
| instance_id | uuid NOT NULL | FK (tenant_id, instance_id) → approval_instances |
| employee_id | uuid NOT NULL | FK (tenant_id, employee_id) → employment_employees |
| added_round | integer NOT NULL | 写入时的实例轮次（发起 = 1；重提追加 = 新轮次） |
| created_at | timestamptz NOT NULL | UTC |

- 主键 (tenant_id, instance_id, employee_id)；索引 (tenant_id, employee_id)。
- **不可变**：触发器禁止 UPDATE / DELETE（借鉴 `reference/gpt-legacy` 不可变审计表思路），只增不减（F048-Q04）。
- **不回填**：现有实例没有集合行，读取时由单主体归一化补齐。迁移不触碰存量数据。

### 5.2 读取 `apps/api/src/modules/approval/subjects.ts`

```ts
/** 实例的主体集合：集合行 ∪ 单主体；账号映射不看状态（fail-closed）。一次查询，Run 内缓存。 */
export async function loadSubjects(tx: Tx, tenantId: string, instance: Pick<InstanceRow, 'id' | 'subjectEmployeeId'>): Promise<SubjectSet>;
/** 发起 / 重提时写入适配器给出的主体（去重、规范化、上限校验），只追加。 */
export async function appendSubjects(tx: Tx, ctx: ApprovalContext, instance: InstanceRow, employeeIds: readonly string[]): Promise<number>;
```

`RecusalFacts` 由 `recusalFacts(tx, run)` 组装（initiator、单主体及其 `userOfPerson`、`loadSubjects`）。`engine.routingFacts / currentRouting / advanceFrom`、`actions`、`handover`、`disclosure`、`resolver.tenantAdminTakeover`、`simulation` 统一从这里取，不再各自调用 `userOfPerson(subjectEmployeeId)`。

### 5.3 适配器接口（业务域只提供映射）

```ts
export interface BusinessAdapter {
  // …现有方法不变
  /**
   * F-048：集合审批的“对象 → 主体”映射——本单涵盖的全部对象对应的员工 ID（可重复、可含单主体）。
   * 不实现即单主体业务（只有 snapshot.subjectEmployeeId）。只在发起与重提时调用；不得写入、不得自行判断回避。
   */
  subjects?(tx: Tx, ctx: ApprovalContext, businessId: string): Promise<readonly string[]>;
}
```

- 引擎负责：去重、`canonicalId`、校验员工存在于本租户（外键兜底）、上限（每实例 10,000，超出返回 400 `APPROVAL_SUBJECTS_TOO_MANY`，F048-Q06）、写表、审计计数。
- 适配器负责：返回本单快照涵盖的**全部**对象主体，包括后来被终止的对象，F-048 不过滤（回避多算一人不会放过越权）。
- 契约测试套件 `apps/api/src/modules/approval/subjects.contract.ts` 导出 `runSubjectAdapterContract(factory)`，业务域（T04 PR-D）用自己的适配器跑：返回值为规范 UUID 的员工、覆盖快照全部对象、无写入、同一业务单多次调用结果一致。
- **与 #113 v4 §3.3 的差异**（T04 侧应改）：T04 原提 `BusinessSnapshot.subjectEmployeeIds?`。快照在每次 `openRun` 与每次详情读取时都会重算；集合大时成本高，而且会出现“实时快照 vs 冻结集合”两个来源。本设计改为适配器方法 + 持久化集合，回避只认持久化集合。

### 5.4 写入时点
