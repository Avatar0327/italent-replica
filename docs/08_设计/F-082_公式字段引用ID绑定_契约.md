# F-082 计算公式字段引用按 ID 绑定：契约

> 依据：DEC-373②（字段引用内部按字段 ID 绑定，界面与公式文本仍显示名称，改名自动跟随，被引用字段禁止删除；在 T04 PR-C 之前做完）、D-067（偏离原站“按名称存储”）、DEC-374⑥（#184 其余口径）、DEC-274、DEC-287、DEC-314②、DEC-260、DEC-194、AGENTS §10；规格 `26` §8；设计 `R3-T04_人才盘点_设计.md` §2.2、§4.3、§4.5、§7；B5 路由声明 `R3-T04_PR-B5_路由声明.md`（下称“B5 声明”）。
> 作用对象：**复刻系统**，不涉及北森测试租户。
> 基线：main `2f8d7973`（#182 九宫格、#184 计算规则均已合并；迁移已用到 0085）。
> 角色：本文是契约（Opus）；实现按 §9 拆成 3 个 PR（F082-1～3，与 T04 的 PR-C 无关） 由 Sonnet 完成，须全部在 T04 PR-C（计算执行）之前合并。

## 0. 结论速览

| 问题 | 契约 |
|---|---|
| 存储形态 | **规范文本（字段引用换成 ID 句柄）+ 派生引用表**。`formula` 列存规范文本，`盘点对象.<名>` 在库里是 `@{tr-field:<uuid>}`；新表 `talent_review_calc_item_refs` 存每个计算项目引用的字段 ID（外键 restrict） |
| 用户看到什么 | 仍是名称：读取时把句柄渲染成 `盘点对象.<当前名称>`；保存时把名称解析成 ID。与 `26` §8 原站写法一致，用户不接触句柄 |
| 改名 | 公式自动跟随（存的是 ID）。被引用字段改名须仍是公式可用的写法，且不让任何引用它的公式超长 |
| 删除 | 被引用字段删除 409 `FIELD_IN_USE`，判定只查引用表；库外键 restrict 兜底。取代 #184 的“文本粗筛 + 解析判定” |
| 重名 | 新引用遇重名 400 `CALC_FIELD_NAME_AMBIGUOUS`；本项目已绑定的引用重提时保持原绑定；目标字段重名不再拒绝 |
| 停用 | “新引用停用字段 400”保持，“是否新引用”改按字段 ID 判断（改名后不再误判） |
| 裸词 | `A`、`默认盘点方案` 这类不带引号、不是变量的词一律 400 `FORMULA_BARE_WORD`，提示加英文双引号；与可见字段短名同名时同时提示 `盘点对象.<名>` 写法（DEC-374⑥） |
| 存量公式 | 迁移只加表与状态列，存量行标 `legacy`；平台命令按租户逐项改绑（幂等、带报告、写审计）；改绑不了的标 `unresolved`、保留原文、不猜 |
| 锁 | 不新增锁种类：仍是“规则行 → 字段行 FOR SHARE（排序后一次取）”；与 #182 不成环 |

## 1. 存储形态

### 1.1 选型

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 名称文本 + 引用表，改名时改写全部公式 | 公式仍存名称；字段改名事务里找出引用它的项目并重写文本 | 不采用：改名要锁并改写别的配置对象（规则 revision、审计都要动），与 #182 / #184 的锁协议叠加；仍要靠文本处理 |
| **B. 规范文本（内嵌 ID 句柄）+ 派生引用表** | 公式存句柄，读取时渲染当前名称；引用表由规范文本派生，同事务写入 | **采用**：改名零写入；删除守卫、锁集合、T04 PR-C 的依赖闭包都直接用 ID；外键在库层兜底 |
| C. 只存引用表 + 位置槽 | 公式文本存 `{{0}}` 槽位，引用表按序号存 ID | 不采用：槽位与表序号要额外保持一致，收益不比 B 多 |

### 1.2 句柄语法（只在库里出现）

- 句柄 `@{tr-field:<uuid>}` 代表一个**完整的盘点字段引用**（即原来的 `盘点对象.<名>` 整段），UUID 按 DEC-194 小写。`tr-field` 是命名空间，留给以后别的对象按 ID 绑定时扩展。
- 词法器加一个**存储模式**：`tokenize(source, { handles: true })` 才识别 `@{tr-field:…}` 为句柄词；输入模式下 `@` 仍是无法识别的字符（现状即 400 `FORMULA_INVALID` / `SYNTAX_ERROR`），**用户无法提交句柄**（AC-TR-F082-08）。
- 字符串字面量里的 `@{…}` 是普通文本：渲染与改绑都在**词法单元**上操作，禁止对公式整段做正则 / 子串替换（#184 P2-08a 的教训）。
- 解析结果：句柄解析成 `FieldNode`，额外带 `fieldId`；`text` = 句柄原文，作为依赖排序、诊断、类型目录的字段键。
- 存储模式不做 4000 字符上限（句柄比名称长），仍受 800 个词的上限约束。

### 1.3 表结构变化（F082-1 迁移，序号按 DEC-221 合并时定）

```
talent_review_calc_rule_items
  + unique (tenant_id, id)                                   -- 供引用表复合外键
  + formula_binding text not null default 'legacy'
      check in ('bound', 'legacy', 'unresolved')             -- 存量行迁移后为 legacy，新写入为 bound
  + binding_issue text null                                  -- unresolved 的原因码（§4.3），其他状态为空
  + check (priority between 0 and 1000000)                   -- 替换原 priority >= 0（DEC-374⑥，🟡）

talent_review_calc_item_refs                                  -- 新表，由规范文本派生
  tenant_id uuid not null, item_id uuid not null, field_id uuid not null
  primary key (tenant_id, item_id, field_id)
  foreign key (tenant_id, item_id)  -> talent_review_calc_rule_items (tenant_id, id) on delete cascade
  foreign key (tenant_id, field_id) -> talent_review_fields (tenant_id, id)         on delete restrict
  index (tenant_id, field_id)                                 -- 删除守卫与改名守卫
  RLS / 租户策略同其他 talent_review_* 表
```

- `formula` 列语义：`bound` 行存规范文本；`legacy` / `unresolved` 行存原来的名称文本（不改写）。
- 不变式：`bound` 行的引用表 = 其规范文本中句柄 ID 的集合（去重）；目标字段不进引用表（已有 `target_field_id` 外键）。项目字段 `盘点活动.项目名称 / 盘点活动.盘点年度 / 盘点对象.盘点方案` 和取数记录字段（`考核结果.年度`、`360结果.…`）不是盘点字段目录里的字段，保持文本、不进引用表。
- 写入时机：创建 / 整组替换计算项目时，在同一事务里先写项目行，再按 item_id 删除旧引用、插入新引用。

### 1.4 保存：名称 → ID（领域函数 `bindFormula`）

输入是用户提交的名称文本，按 B5 现状先做语法、函数、参数个数检查，然后对每个 `FieldNode`：

| 引用形态 | 处理 |
|---|---|
| 项目字段（`FORMULA_CONTEXT_FIELDS`） | 保持文本，不绑定。字段目录里有字段名叫 `盘点方案` 时，`盘点对象.盘点方案` 仍指项目字段（🟡 C-F082-3） |
| 取数记录字段（函数参数里的 `考核结果.…` 等） | 保持文本，不绑定（DEC-287） |
| `盘点对象.<名>`，在**查看人可见**字段里恰有 1 个同名 | 绑定该字段 |
| 同名的可见字段有多个，其中恰有 1 个是**本项目原有绑定**（同一目标字段的已存项目） | 保持原有绑定（重提不受后来出现的重名影响） |
| 同名的可见字段有多个，且不满足上一行 | 400 `CALC_FIELD_NAME_AMBIGUOUS`（带 `item`、`fields: [文本路径]`），提示先改名 |
| 可见字段里没有同名（含不存在、范围外、缺列权限） | 400 `FORMULA_INVALID`，issue `UNKNOWN_FIELD`（与 B5 C-B5-2 相同，不区分“不存在”和“看不到”） |
| 渲染出来的不可见占位符（§1.5） | 400 `FORMULA_INVALID`，issue `HIDDEN_FIELD`（“公式含当前不可见的字段，无法修改该计算项目”） |
| 单段标识符，既不是 `Def` / 赋值定义的变量，也不是函数名 | 400 `FORMULA_INVALID`，issue `BARE_WORD`（§1.6） |

- 绑定只做一次，类型检查、多选判定（`MULTI_OPTION_IN_FORMULA`）、停用判定、依赖排序、`uses_ranking` 都基于这一个结果（沿用 B5 原则）。
- 产出：规范文本（把每个绑定的 `FieldNode` 源码区间换成句柄，其余字符原样保留）+ 引用字段 ID 集合。解析器需要给 `FieldNode` 补源码结束位置（`end` 偏移），区间从 `盘点对象` 首字到字段名末字，中间的空白与换行一并替换（`盘点对象 . 来源` 读回为 `盘点对象.来源`）。
- 目标字段已按 ID 提交，不再要求目标字段名唯一：B5 的“目标字段与其他字段重名 400”取消（C-B5-1 的这部分作废）。依赖排序以句柄为键，重名不影响排序。

### 1.5 读取：ID → 名称（领域函数 `renderFormula`）

- `bound` 行：逐个句柄换成 `盘点对象.<当前名称>`。只有**当前查看人可见**的字段（字段目录范围内且 name / kind / enabled / systemWritten 四列可见，与保存口径一致）才显示名称；其余换成固定占位符 `盘点对象.〔不可见字段〕`。占位符不是合法写法，重提时得到 `HIDDEN_FIELD`（见上表），不会被误绑。
- `legacy` / `unresolved` 行：按存储前的名称文本词法解析，`盘点对象.<名>` 只有在查看人可见字段里存在同名字段时原样显示，否则同样换成占位符；整段无法解析时，只有“全部字段都可见”的查看人看原文，其他人只看到 `〔公式待修复，无法显示〕`。
- 渲染发生在**响应时**：GET、写响应、幂等重放都按当前数据与当前查看人渲染。命令台账只缓存规范文本（与 B5 对 `hints` 的处理一样，不缓存渲染结果，避免撤权后重放泄露名称）。
- 审计快照：`formula` 记**写入时刻**按全部字段渲染的名称文本（历史记录，后来改名不回写），另加 `refFieldIds`（排序后的 ID 列表）——只改绑定、文本不变时，审计仍能看出差异。审计的查看口径同 B5（日志入口权 + 对象查看权 + 看全部），本任务不改（🟡 C-F082-4）。

### 1.6 裸词（DEC-374⑥）

- `26` §8.6 样本里的 `A`、`B`、`默认盘点方案` 等在原站按字面文本处理；复刻**要求加英文双引号**，不做隐式转换。
- 判定：单段标识符，不是 `Def` / 赋值定义的变量，也不是函数调用名 → `BARE_WORD`。消息：`“A”不是字段也不是变量；作文本请写成 "A"`；当该词恰好是查看人可见字段的名称（计算目标短名）时追加 `；引用盘点字段请写 盘点对象.A`（只提示可见字段，不泄露看不到的名称）。
- 只在盘点计算规则（以及 B6 的结果设置公式，见 §6）的分析层把 `UNKNOWN_FIELD` 中的单段引用改判为 `BARE_WORD`；表达式引擎公共行为不变（其他模块不受影响）。
- 存量：B5 已经把裸词判为 `UNKNOWN_FIELD` 拒绝，库里不应有裸词；迁移遇到也按 `unresolved` 处理。

## 2. 改名跟随、删除守卫、停用与锁

### 2.1 改名

- 公式存的是 ID，改名不写任何计算规则数据，规则 revision 不变；下次读取即显示新名称。
- **被引用字段改名守卫**（`updateField` 已持该字段行 `FOR UPDATE`，在写入之前判断；只在 `name` 变化且引用表或目标字段里有该字段时执行）：
  1. 新名称须是公式可用写法：`盘点对象.<新名称>` 按输入模式解析后**恰为一个** `FieldNode`，其文本等于该串（排除关键字、空格、括号、`/` 等），且不等于项目字段路径（`盘点对象.盘点方案`）→ 否则 400 `FIELD_NAME_NOT_FORMULA_SAFE`；
  2. 用新名称重新渲染每个引用它的 `bound` 项目，长度不得超过输入上限 4000 → 否则 409 `FIELD_NAME_FORMULA_TOO_LONG`（保证改名后公式仍可原样重提）。
- 改成与其他字段同名**不拒绝**（字段名本无唯一约束）；已有绑定不受影响，新引用遇重名按 §1.4 处理。
- 不变式“每个被引用字段的名称都可原样写进公式”由两处共同保证：引用只在名称可解析时写入（保存持字段 `FOR SHARE`），改名在持 `FOR UPDATE` 时检查引用。并发交错见 §2.4。

### 2.2 删除守卫（取代 #184 文本粗筛）

- `registerConfigReferenceGuard('field')`（`calc-rule-service.ts`）改为：目标字段命中 **或** 引用表命中 → `CALC_RULE`（409 `FIELD_IN_USE`）。删掉 `strpos` 粗筛与 `formulaReferences` 判定。
- 兜底：仍有 `legacy` / `unresolved` 行的租户，对这些行保留原来的“文本粗筛 + 解析判定”（只查这些状态的行），直到该租户改绑完成；全量改绑完成后由后续任务删除兜底（§4.5）。
- 库层：引用表外键 restrict。守卫 + 锁保证正常路径不会撞外键（不会 500）；外键只是最后一道防线。

### 2.3 停用

- “公式**新增**引用的字段须已启用，保留已有引用不受影响”（设计 §7，400 `CALC_FORMULA_FIELD_DISABLED`）保持。
- “已有引用”改为：同一目标字段的已存项目的**引用表 ID 集合**（`legacy` 行用其文本按当前名称解析出的 ID）。B5 按文本路径比较，字段改名后会把保留的引用误判为新增，此处修正（AC-TR-F082-05）。
- 目标字段的 `CALC_TARGET_DISABLED` 不变。

### 2.4 锁协议

| 入口 | 取锁顺序（F-082 后） | 变化 |
|---|---|---|
| 计算规则新建 / 修改（含项目） | 规则行 `FOR UPDATE`（新建无）→ 第一遍绑定得到字段 ID 集合 → 排序后**一次性** `FOR SHARE` → 锁内第二遍绑定 → 集合超出已锁集合 409 `CALC_FIELD_CHANGED` → 写项目行与引用表 | 只把“分析”换成“绑定”；锁集合 = 目标 + 绑定出的字段 ID（与 #184 同） |
| 字段改名 / 停用 / 删除 | 字段行 `FOR UPDATE`（`lockConfigRow`）→ 读引用表 / 项目目标（不加锁）→ 写 | 新增“读引用表”，不新增锁 |
| 九宫格写入（#182） | 九宫格行（≤1）→ 位置字段 advisory 锁（排序一次）→ 字段 `FOR KEY SHARE` | 不变 |
| 平台改绑（§4） | 每个租户一个事务：待改绑规则行 `FOR UPDATE`（按 id 排序）→ 该租户全部字段行 `FOR SHARE`（按 id 排序一次）→ 改绑写入 | 新增；顺序与计算规则保存一致（规则 → 字段） |

- 所有入口都是“配置对象行 → 字段行”或“只取字段行”，没有“先字段后规则 / 九宫格”的路径，因此不成环；`FOR SHARE` 与 `FOR KEY SHARE` 互相兼容，与 #182 无等待关系。
- 交错结果：改名先提交 → 保存的锁内第二遍按新名称解析，提交文本里的旧名称成 `UNKNOWN_FIELD`（400）或指向别的字段（409 `CALC_FIELD_CHANGED`）；保存先提交 → 改名看到引用，按 §2.1 检查。删除同理（409 `FIELD_IN_USE` 或保存 404 / 400）。真 PG 交错测试沿用 #184 的 `AC-TR-calc-rule-pg` 写法改成按 ID 断言（AC-TR-F082-10）。
- 租户 UUID 规范化按 F-078 处理，本任务不新增 advisory 锁键。

## 3. 计算执行（T04 PR-C）的接口约定

T04 PR-C 只读规范文本，不再按名称找字段：

- `parseStoredFormula(text)`（存储模式）得到带 `fieldId` 的 AST；求值时字段读取器按 `fieldId` 取值；依赖排序、触发矩阵的“引用字段集合”（设计 §4.4）直接用引用表或句柄 ID。
- 规则里有 `legacy` / `unresolved` 项目时**拒绝计算**（run 登记失败，原因 `CALC_RULE_NEEDS_REBIND`，提示管理员改绑或重新保存），不按名称兜底猜测。
- 本契约提供的领域函数（F082-1）：`bindFormula`、`renderFormula`、`parseStoredFormula`、`formulaFieldIds(stored)`（与字段目录无关）；`orderComputationItems` 增加可选 `display(key)` 回调，诊断文案用显示名称生成，结构化 `fields` 仍是字段键（句柄）。

## 4. 存量公式迁移

### 4.1 步骤

1. **结构迁移（F082-1，SQL）**：建引用表；项目表加 `formula_binding`（默认 `legacy`，存量行即为 `legacy`）、`binding_issue`、复合唯一键、优先级上限检查。存量数据若有优先级 > 1000000 的行，迁移先失败报告（输入层自 #184 起已限制 0～1000000，预期没有）。
2. **改绑（F082-3，平台命令）**：`POST /api/platform/tenants/:tenantId/talent-review/calc-formulas/rebind`，只认平台运营身份、显式指定租户、命令台账幂等（同 DEC-361 回补）。对该租户全部 `legacy` 与 `unresolved` 项目：
   - 按 §2.4 加锁；字段目录用**全部字段**（系统执行，不按查看人）；
   - 逐项按 §1.4 绑定（没有“本项目原有绑定”可用，重名一律不猜）；
   - 成功 → 写规范文本、引用表，`formula_binding = 'bound'`，`binding_issue = null`；
   - 失败 → `formula_binding = 'unresolved'`，`binding_issue` = 原因码，**原文不动**。
3. **运维**：部署 F082-2 之后对每个租户执行一次改绑（平台批量脚本逐租户调用命令）；报告里 `unresolved > 0` 的租户通知其管理员修公式（修的方法就是在页面上改正后重新保存，保存即 `bound`）。

### 4.2 幂等与审计

- 只处理 `legacy` / `unresolved` 行；`bound` 行不读不写。重复执行不产生新行、不改已绑定结果；`unresolved` 的行在租户改名后重跑可能变成 `bound`（这是期望的）。
- 不改规则 `revision`：渲染出的公式与改绑前逐字相同（只有空白被规范化），客户端手里的 revision 继续有效（🟡 C-F082-5）。
- 审计：每条有变化的规则写一条 `talent-review.calc-rule.rebind`（同事务；before / after 为项目的 `formulaBinding`、`bindingIssue`、`refFieldIds`；actor = 平台命令的运营身份）；平台审计留一条汇总（同 DEC-361）。
- 返回报告：`{ rules: n, bound: n, unresolved: [{ ruleId, targetFieldId, reason }] }`，不含公式原文与字段名称。

### 4.3 失败原因码（`binding_issue`）

| 码 | 情形 |
|---|---|
| `UNKNOWN_FIELD` | 公式里的 `盘点对象.<名>` 在租户字段里找不到（被改名或删除——删除在 #184 守卫下不应发生） |
| `AMBIGUOUS_FIELD` | 同名字段不止一个 |
| `NOT_FORMULA_SAFE` / `BARE_WORD` / `INVALID` | 名称已不是合法写法 / 有裸词 / 整段解析失败 |
| `MULTI_OPTION` | 引用了多选字段（B5 已拒绝，理论上不会出现） |

`unresolved` 项目：读取时带保存提示“部分公式当前无法完整校验…”（沿用 B5 `UNVERIFIABLE`）；删除守卫走文本兜底；T04 PR-C 拒绝计算。

### 4.4 失败处理

- 单个租户一个事务：锁等待超时或其他异常 → 整个租户回滚，命令失败可重试（台账记失败；重试用新的命令 ID）；已经 `bound` 的行在下次执行时被跳过。
- 单个项目绑定失败不让整租户失败（记 `unresolved` 继续）。

### 4.5 收尾（后续 F 任务，不在本任务）

全部租户报告 `legacy = 0` 后：删除删除守卫里的文本兜底与 `legacy` 状态的读取分支（`unresolved` 保留）。由总编排在改绑执行完后开 F 任务。
