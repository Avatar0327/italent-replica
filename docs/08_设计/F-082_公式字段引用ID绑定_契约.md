## 0. 结论速览

| 问题 | 契约 |
|---|---|
| 存储形态 | **规范文本 + 派生引用表**。`formula` 列存规范文本，其中每个 `盘点对象.<名>` 换成 ID 句柄 `@{tr-field:<uuid>}`；新表 `talent_review_calc_item_refs` 存每个计算项目引用的字段 ID（外键 restrict） |
| 用户看到什么 | 仍是名称：读取时把句柄渲染成 `盘点对象.<当前名称>`，看不到的字段显示占位符（DEC-376①）。与 `26` §8 原站写法一致，用户不接触句柄 |
| 编辑协议 | 读取时每个计算项目附带**逐引用绑定** `formulaBindings`（第 k 处引用 → 字段 ID）。提交时原样带回；名称与 ID 对不上返回 409 并要求刷新（DEC-376②）。新输入的引用（绑定为空）按名称解析，同时核对字段目录版本 |
| 重名 | 允许字段重名，不收紧改名（DEC-376②）。带 ID 的引用不受重名影响；新输入遇到重名返回 400 |
| 盘点方案 | 新输入的 `盘点对象.盘点方案` 指项目上下文；如果查看人能看到同名的自定义字段，要求显式选择（返回 400，带选项）。存量公式按迁移时的解析结果固定绑定（DEC-376③） |
| 改名 | 公式自动跟随，不改规则 revision（DEC-376⑤）。对每个引用它的公式做完整往返校验（长度、词数、语法、逐引用映射）。全租户的改名在目录版本行上串行，不新增反向锁序 |
| 删除 | 引用表（含 `unresolved` 的候选引用）命中，或 `unresolved` 公式文本兜底命中 → 409 `FIELD_IN_USE`；库外键 restrict 兜底。文本兜底**长期保留**，不以 `legacy = 0` 为删除条件（DEC-376⑥） |
| 诊断与审计 | GET、写响应、重放、审计共用一个“计算规则投影”。所有诊断服从 `items` 查看权（DEC-376⑥）；看不到的只给匿名计数。审计读取时按来源字段的当前权限裁剪（DEC-376④、DEC-197） |
| 存量迁移 | SQL 迁移只加表和状态列；平台命令按租户改绑，幂等、带报告、写审计、不改 revision；解析不了的标 `unresolved`，保留原文和删除保护 |
| 锁 | 统一顺序：**配置对象行 → 字段行（排序后一次取）→ 字段目录版本行**；所有入口都遵守，无反向路径 |

## 1. 存储与编辑协议

### 1.1 选型

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 名称文本 + 引用表，改名时改写全部公式 | 改名事务里改写引用它的公式 | 不采用：改名要写别的配置对象（规则 revision、审计都要动），锁序变成“字段 → 规则”，与保存的“规则 → 字段”相反 |
| **B. 规范文本（内嵌 ID 句柄）+ 派生引用表** | 公式存句柄，读取时渲染当前名称；引用表由规范文本派生，同事务写入 | **采用**：改名零写入；删除守卫、锁集合、T04 PR-C 的冻结都直接用 ID；外键在库层兜底 |
| C. 槽位文本 + 序号表 | 公式存 `{{0}}`，表里按序号存 ID | 不采用：槽位与序号要额外维护一致，收益不比 B 多 |

### 1.2 句柄与占位符的词法（领域层 `expression/`）

- **句柄** `@{tr-field:<uuid>}`：表示一个完整的盘点字段引用（即原来的 `盘点对象.<名>` 整段）；UUID 按 DEC-194 小写；`tr-field` 是命名空间，留给以后扩展。只在**存储模式** `tokenize(source, { handles: true })` 下识别。输入模式下 `@` 仍是非法字符，用户无法提交句柄。
- **占位符** `〔不可见字段〕`：渲染时用 `盘点对象.〔不可见字段〕` 代替看不到的引用。**输入模式**的词法器把 `〔不可见字段〕` 识别为专用词（不报非法字符），解析器只接受它出现在 `盘点对象.` 之后。见 §1.6 的识别顺序。
- 字符串字面量里的 `@{…}`、`〔不可见字段〕` 都是普通文本。渲染与绑定都在**词法单元**上进行，禁止对公式整段做正则或子串替换（#184 P2-08a 的教训）。
- 解析结果：句柄解析成带 `fieldId` 的 `FieldNode`，其 `text` 等于句柄原文，用作依赖排序、诊断和类型目录里的字段键。解析器给 `FieldNode` 补上源码结束位置（`end` 偏移）。
- 存储模式不做 4000 字符上限（句柄比名称长），只保留 800 个词的上限。输入限制统一由 `checkInputLimits(text)` 校验（4000 字、800 词，与 `parseFormula` 同源），§3.1 的改名往返复用它。

### 1.3 表结构（F082-1 迁移，序号按 DEC-221 合并时定）

```
talent_review_calc_rule_items
  + unique (tenant_id, id)                                   -- 供引用表复合外键
  + formula_binding text not null default 'legacy'
      check in ('bound', 'legacy', 'unresolved')             -- 存量行迁移后为 legacy；F082-2 起新写入为 bound
  + binding_issue text null                                  -- unresolved 的原因码（§6.3）；其他状态为空
  + check (priority between 0 and 1000000)                   -- 替换原 priority >= 0（DEC-374⑥，🟡）

talent_review_calc_item_refs                                  -- 新表，由规范文本或迁移派生
  tenant_id uuid not null, item_id uuid not null, field_id uuid not null
  kind text not null check in ('bound', 'candidate')
  primary key (tenant_id, item_id, field_id)
  foreign key (tenant_id, item_id)  -> talent_review_calc_rule_items (tenant_id, id) on delete cascade
  foreign key (tenant_id, field_id) -> talent_review_fields (tenant_id, id)         on delete restrict
  index (tenant_id, field_id)
  RLS / 租户策略同其他 talent_review_* 表

talent_review_field_catalog_versions                          -- 新表：字段“名称 → ID”映射的版本
  tenant_id uuid primary key, version bigint not null default 0
  RLS / 租户策略同上；迁移为已有字段的租户插入一行
```

- `formula` 列：`bound` 行存规范文本；`legacy` / `unresolved` 行存原来的名称文本，不改写。
- 不变式：
  - `bound` 行的引用表全部是 `kind = 'bound'`，且等于规范文本中句柄 ID 的集合；
  - `unresolved` 行只有 `kind = 'candidate'`（§6.2）；`legacy` 行没有引用表记录；
  - 目标字段不进引用表（已有 `target_field_id` 外键）；
  - 项目上下文字段与取数记录字段（`考核结果.年度` 等）保持文本，不进引用表。
- **字段目录版本**：字段的新建、改名、删除都在同一事务里把版本 +1（停用不改变名称映射，不 +1）。版本行不存在时先 `INSERT … ON CONFLICT DO NOTHING` 再加锁，避免首次写入竞态。

### 1.4 读取：ID → 名称（`renderFormula`），以及逐引用绑定

计算项目的视图新增两个只读系统值：

| 键 | 含义 |
|---|---|
| `formula` | 渲染文本：句柄 → `盘点对象.<当前名称>`；查看人看不到的字段 → `盘点对象.〔不可见字段〕`；项目上下文路径原样 |
| `formulaBindings` | 渲染文本中**每一处** `盘点对象.*` 引用的绑定，按出现顺序排列：可见字段为其 ID；项目上下文 `盘点对象.盘点方案` 为 `"context"`；占位符为 `null` |

规则视图还新增 `fieldCatalogVersion`：读取时字段目录版本的值，只读。

- “可见”的口径与保存相同：字段在查看人的字段目录范围内，且 name / kind / enabled / systemWritten 四列都可见。
- `legacy` / `unresolved` 行：按存储前的名称文本做词法解析。`盘点对象.<名>` 只有在查看人可见字段里存在同名字段时才原样显示，否则换成占位符。这类行的 `formulaBindings` 一律为 `null`：它们没有确定绑定，不能作为绑定证明。整段无法解析时，只有“全部字段都可见”的查看人看原文，其他人只看到 `〔公式待修复，无法显示〕`。
- 渲染在**响应时**进行：GET、写响应、幂等重放都按当前数据和当前查看人渲染。命令台账只缓存规范文本（§5.4 讲旧台账兼容）。

### 1.5 保存：名称 → ID（`bindFormula`），绑定证明

提交的计算项目可带 `formulaBindings`（数组，元素为字段 ID / `"context"` / `null`）；规则级可带 `fieldCatalogVersion`。服务端先按输入模式解析，并检查语法、函数、参数个数，再按出现顺序逐处处理 `盘点对象.*` 引用（第 k 处对应 `formulaBindings[k]`）：

| 第 k 处 | 绑定证明 | 处理 |
|---|---|---|
| `盘点对象.<名>` | 字段 ID，该字段对提交人可见，且**当前名称等于 `<名>`** | 绑定该 ID（不看重名） |
| 同上 | 字段 ID，该字段可见但当前名称不等于 `<名>` | 409 `CALC_BINDING_STALE`（“公式里的字段已改名或已变化，请刷新后重新编辑”） |
| 同上 | 字段 ID 不存在、跨租户或对提交人不可见 | 400 `FORMULA_INVALID`，issue `UNKNOWN_FIELD`（与不存在同一个结果，不泄露） |
| 同上 | `null` 或未提供（新输入） | 要求 `fieldCatalogVersion` 等于当前版本，否则 409 `FIELD_CATALOG_CHANGED`。然后按名称解析：可见字段中**恰有 1 个**同名 → 绑定；多个 → 400 `CALC_FIELD_NAME_AMBIGUOUS`（带 `item`、`occurrence`）；没有 → `UNKNOWN_FIELD` |
| `盘点对象.盘点方案` | `"context"` | 绑定项目上下文（固定路径） |
| 同上 | 字段 ID（名称为“盘点方案”的自定义字段） | 按第 1 行，绑定该自定义字段（显式选择） |
| 同上 | `null`，查看人**没有**可见的同名自定义字段 | 项目上下文 |
| 同上 | `null`，查看人有可见的同名自定义字段 | 400 `FORMULA_INVALID`，issue `RESERVED_PATH_AMBIGUOUS`，附 `item`、`occurrence`、`choices: ["context", <各同名可见字段 ID>]`。前端据此弹出选择（“项目上下文：盘点方案”或“自定义字段：盘点方案（编码 xxx）”），把选择写入该处绑定后重提（DEC-376③） |
| `盘点对象.〔不可见字段〕` | — | 见 §1.6 |
| 其他 | `formulaBindings` 的长度不等于引用处数 | 400 `FORMULA_INVALID`，issue `BINDING_MISMATCH` |

- **向后兼容**：不带 `formulaBindings` 等同于全部为 `null`（新输入），此时必须带 `fieldCatalogVersion`。B5 时代的客户端只要补上版本即可工作，但 B5 已存项目里的重名引用无法这样重提（会 400），需要按新协议带 ID。
- 绑定只做一次。类型检查、多选判定（`MULTI_OPTION_IN_FORMULA`）、停用判定、依赖排序、`uses_ranking` 都基于这同一个结果。
- 产出：规范文本（把每个绑定的 `FieldNode` 源码区间换成句柄，其余字符原样保留，`盘点对象 . 来源` 读回为 `盘点对象.来源`）、逐引用映射 `M = [k → ID | context]`、引用 ID 集合。
- 目标字段按 ID 提交，不再要求目标字段名唯一：B5 的“目标字段与其他字段重名 400”取消（C-B5-1 的这部分作废）。依赖排序以句柄为键，不受重名影响。

### 1.6 不可见引用（DEC-376①）

- 查看人对含不可见引用的计算项目**只能整组替换公式**，不能逐处修改不可见引用：
  - **原样保留**：提交的 `formula` 与该查看人当前的渲染文本逐字相同，且 `formulaBindings` 与当前绑定相同 → 视为未修改，保留已存规范文本与引用（含不可见字段），不重新绑定；
  - **整段重写**：提交的公式不含占位符 → 按 §1.5 正常绑定（原来的不可见引用随之移除）；
  - 其他情况（含占位符但与当前渲染不同，包括旧页面）→ 400 `FORMULA_INVALID`，issue `HIDDEN_FIELD`（“公式里有你看不到的字段，只能原样保留或整段重写；如页面已过期请刷新”）。
- **识别顺序**：词法识别出占位符词，不报非法字符 → 语法错误照常最先报告 → 语法正确时，先判断“原样保留”。不是原样保留时，`HIDDEN_FIELD` 优先于同一公式里的其他语义问题（`UNKNOWN_FIELD`、`BARE_WORD` 等）。
- 原样保留不改变引用，因此不触发停用判定，也不重新校验对不可见字段的访问。整组替换 `items` 时，未触碰的项目按原样保留提交即可。

### 1.7 裸词（DEC-374⑥）

- `26` §8.6 样本里的 `A`、`B`、`默认盘点方案` 等在原站按字面文本处理；复刻要求加英文双引号，不做隐式转换。
- 判定：单段标识符，既不是 `Def` / 赋值定义的变量，也不是函数调用名 → 400 `FORMULA_INVALID`，issue `BARE_WORD`（**错误码统一为 `FORMULA_INVALID` + issue code**，与 `UNKNOWN_FIELD` 等同级；不存在独立的 `FORMULA_BARE_WORD`）。
- 消息：`“A”不是字段也不是变量；作文本请写成 "A"`。当该词恰好是查看人可见字段的名称时，追加 `；引用盘点字段请写 盘点对象.A`；看不到的字段不提示。
- 只在盘点计算规则（以及 B6 的结果设置公式，见 §8）的分析层把单段引用改判为 `BARE_WORD`；表达式引擎的公共行为不变。

### 1.8 披露边界（DEC-376①）

“完全不透露隐藏项的存在”与“占位符 + 匿名计数”不能同时成立，本契约采用后者。查看人**可以**知道：

- 某计算项目某处引用了自己看不到的字段（占位符的位置）；
- 被隐藏的提示条数、被隐藏的排序 / 阻断项目个数（`others` 匿名计数，DEC-374⑥）；
- 在 `items` 可见的前提下，“存在涉及不可见字段的循环依赖”这一类别（DEC-274 要求不能静默省略循环）；
- `fieldCatalogVersion` 的数值（只反映名称映射的变化次数）。

查看人**不能**知道：不可见字段的名称、ID、类型、启停状态，以及与其他项目的依赖关系。`items` 不可见时，连诊断类别也不给（§5.2）。

## 2. 锁内复核（P2-1）

保存（新建 / 修改带 `items`）的顺序：

1. 规则行 `FOR UPDATE`（新建时没有这一步）；
2. 第一遍绑定（读已提交数据）→ 得到逐引用映射 `M1`、目标集合 `T` 与引用集合；
3. 对 `T ∪ refs(M1)` 排序后**一次性** `FOR SHARE`；“原样保留”的项目（§1.6）把其已存引用一并计入锁集合，第二遍重新核对“逐字等于当前渲染”；
4. 字段目录版本行 `FOR SHARE`，核对 `fieldCatalogVersion`（有新输入引用时）；
5. 锁内第二遍绑定 → `M2`；**要求 `M2` 与 `M1` 逐处相同**（同一处同一 ID / context）、目标集合不变，否则 409 `CALC_FIELD_CHANGED`（客户端刷新后显式重提）；
6. 写项目行、引用表（删旧插新），同事务写审计与命令台账。

这样能拦下审查给出的三类情况：

- 旧页面换绑：带 ID 的引用名称对不上 → 409 `CALC_BINDING_STALE`；新输入引用遇到目录版本已变 → 409 `FIELD_CATALOG_CHANGED`；
- 改名后 `B+B` 原样重提：两处各带原 ID，都能通过；
- 锁前后名称互换导致来源变自引用：`M1 ≠ M2` → 409。

## 3. 改名、删除、停用

### 3.1 改名（DEC-376②⑤）

- 公式存的是 ID，改名不写计算规则数据，规则 revision 不变（DEC-376⑤）；下次读取即显示新名称。允许改成与其他字段同名。
- **被引用字段的改名守卫**（`updateField`，只在 `name` 变化时执行）：
  1. 字段行 `FOR UPDATE`（已有）；
  2. 字段目录版本行 `FOR UPDATE`（版本 +1 的同一行）——**全租户的新建、改名、删除在这一行上串行**；
  3. 在持有版本行之后读取：引用该字段的全部 `bound` 项目（引用表 `kind = 'bound'`）与其余字段的当前名称；
  4. 对每个项目做**完整往返**：用改名后的名称渲染出全文与 `formulaBindings`，再按输入管道（`checkInputLimits` + `bindFormula`，全字段可见、带全部绑定证明）重新绑定，结果必须**逐字等于**原规范文本。任何失败（超 4000 字、超 800 词、`A.B` 之类导致词数或结构变化、关键字等）→ 409 `FIELD_NAME_BREAKS_FORMULA`（带 `ruleId`、`targetFieldId`、`reason`：`TOO_LONG` / `TOO_MANY_TOKENS` / `NOT_PARSEABLE`）；
  5. 写名称，版本 +1。
- 并发：两个改名分别持有各自的字段行，但都要拿版本行 `FOR UPDATE`，后到者在前者提交后才读名称并校验（READ COMMITTED 下后续语句能看到前者的提交），所以“各自通过、合计超限”不会发生。
- 不变式“每个 `bound` 公式按当前名称渲染后都可原样重提”由两处保证：
  - 保存时：持被引用字段的 `FOR SHARE` 与版本行 `FOR SHARE`，名称不会变化，`checkInputLimits` 校验的是渲染文本；
  - 改名时：持版本行 `FOR UPDATE` 做往返校验。
- 未被任何 `bound` 公式引用的字段改名不做往返检查，只 +1 版本。

### 3.2 删除守卫（DEC-376⑥）

`registerConfigReferenceGuard('field')`（`calc-rule-service.ts`）的判定，任一命中即为 `CALC_RULE`（409 `FIELD_IN_USE`）：

1. 作为某计算项目的目标字段；
2. 引用表里有该字段（`bound` 或 `candidate`）；
3. **文本兜底**：`formula_binding in ('legacy','unresolved')` 的行里，公式按 #184 的“文本粗筛 + 解析判定”引用了该字段的当前名称；对解析失败的行，**只要粗筛命中名称就算引用**（不能解析时宁可多保护）。

- 文本兜底**长期保留**，只作用于非 `bound` 行。`legacy = 0` 不是删除兜底的条件：`unresolved` 行一直需要它（DEC-376⑥）。
- 库层：引用表外键 restrict。守卫 + 锁保证正常路径不会撞外键；外键是最后一道防线。
- 删除 +1 字段目录版本（§1.3）。

### 3.3 停用

- “公式**新增**引用的字段须已启用；保留已有引用不受影响”（设计 §7，400 `CALC_FORMULA_FIELD_DISABLED`）保持。
- “已有引用”按 ID 判断，取同一目标字段的已存项目：
  - `bound` 行：引用表 `bound` 集合；
  - `unresolved` 行（用户修复时）：`candidate` 集合——迁移时认定的可能引用，含停用字段；
  - `legacy` 行：按当前名称解析出的 ID（过渡期）。
- B5 按文本路径比较，字段改名后会把保留的引用误判为新增；本契约修正。
- 目标字段的 `CALC_TARGET_DISABLED` 不变。

### 3.4 锁协议总表

| 入口 | 取锁顺序 |
|---|---|
| 计算规则保存（含项目） | 规则行（新建无）→ 字段行 `FOR SHARE`（排序一次）→ 版本行 `FOR SHARE` |
| 字段新建 | （新行）→ 版本行 `FOR UPDATE` |
| 字段改名 / 删除 | 字段行 `FOR UPDATE` → 版本行 `FOR UPDATE` → 读引用（不加锁）→ 写 |
| 字段停用 / 其他修改 | 字段行 `FOR UPDATE`（不动版本行） |
| 九宫格写入（#182） | 九宫格行（≤1）→ 位置字段 advisory 锁（排序一次）→ 字段 `FOR KEY SHARE`（不变） |
| 平台改绑（§6） | 待改绑规则行 `FOR UPDATE`（按 id 排序）→ 该租户全部字段行 `FOR SHARE`（排序一次）→ 版本行 `FOR SHARE` |

- 所有入口都按“配置对象行 → 字段行 → 版本行”的顺序取锁，没有“先版本后字段”或“先字段后规则”的路径，因此不成环。改名不补锁计算规则行，不引入反向锁序。`FOR SHARE` 与 `FOR KEY SHARE` 互相兼容，与 #182 无等待关系。
- 租户 UUID 规范化按 F-078 处理；本任务不新增 advisory 锁键。

## 4. 计算执行（T04 PR-C）的接口约定（DEC-376⑤）

- T04 PR-C 只读规范文本，不再按名称找字段。`parseStoredFormula(text)` 得到带 `fieldId` 的 AST；求值时按 `fieldId` 取值；依赖排序与触发矩阵的“引用字段集合”（设计 §4.4）直接用引用表。
- **冻结**：calc run 冻结时，每个计算项目存档 `{ itemId, targetFieldId, formula（规范文本）, refFieldIds（排序）, ruleRevision }`；求值只用存档，不再读当前项目。改名不改 revision，也不影响存档（存的是 ID）。
- 规则里有 `legacy` / `unresolved` 项目时**拒绝计算**：run 登记失败，原因 `CALC_RULE_NEEDS_REBIND`，提示管理员改绑或重新保存；不按名称兜底猜测。平台改绑只把非 `bound` 行变成 `bound`，而这类行不可能出现在已冻结的 run 里，所以改绑不改 revision 不会让 run 漏检“规则已改”。
- 本契约提供的领域函数（F082-1）：`bindFormula`、`renderFormula`、`parseStoredFormula`、`formulaFieldIds(stored)`（与字段目录无关）、`checkInputLimits`；`orderComputationItems` 增加可选的 `display(key)` 回调，诊断文案用显示名称生成，结构化 `fields` 仍是字段键（句柄）。

## 5. 计算规则投影（GET / 写响应 / 重放 / 审计共用）

### 5.1 统一投影

新增 `projectCalcRule(view, viewer)`。输入是规则聚合（项目为规范文本）和查看人（规则字段查看权 + 字段目录可见集合），输出就是对外的规则表示。四个出口都调用它：

| 出口 | 名称来源 |
|---|---|
| `GET /calc-rules`、`GET /calc-rules/:id` | 当前名称 |
| 写响应、幂等重放 | 当前名称；台账只存规范文本 |
| 审计 before / after / snapshot / changes | 写入时刻的名称（快照里存，§5.3） |

### 5.2 hints 投影（DEC-376⑥、DEC-374⑥）

- `hints` 在 GET（详情与列表）、写响应、重放中都返回（B5 C-B5-4“GET 不带”作废），并经 `hints` 列查看权裁剪。
- 检测在全部字段上做（与 B5 一样），输出按下面规则投影：

| 查看人 | `order` / `blocked` | `cycles` | `warnings` | `others` |
|---|---|---|---|---|
| 没有 `items` 列查看权 | `[]` | `[]` | 只有一句固定文案：“计算项目对你不可见，N 条提示未显示” | `{ order: 全部个数, blocked: 全部个数, warnings: 条数 }` |
| 有 `items` 列查看权 | 只列目标字段对其可见的项目 ID | 只列**全部**成员目标可见、且环上**全部**引用可见的环（元素为目标字段 ID） | 只保留 `fields` 全部可见的诊断（文案用当前名称）；被裁掉的循环类诊断汇总为不含名称的循环提示（B5 `CYCLE_HIDDEN`），其余汇总为“另有 N 条提示涉及不可见的字段，未显示” | 被裁掉的个数；都为 0 时省略 |

- “可见”一律按 ID 判断（句柄 / 目标字段 ID），不按名称，也不做子串匹配。
- `cycles` 从字段路径改为目标字段 ID 数组：客户端直接对应到项目，名称由客户端从 `items` 取。这是对 B5 的表示变更，在 F082-3 的 PR 描述中列出。

### 5.3 审计（DEC-376④、DEC-197）

- **写入**（同事务）：审计快照的每个计算项目存 `{ targetFieldId, priority, description, formula（规范文本）, formulaBinding, fieldNames: { <id>: <写入时刻名称> }, refFieldIds }`。删除快照、`changes` 中的 `items` 前后值同此结构。
- **读取**：新增 `calcRuleSources(deps, ctx)`，结构同 `audit/qualification-sources.ts` 的 `SourceRedactor`，在 `visibleValue` / `visibleChanges` 之前对计算规则行执行：
  1. 按审计查看人**当前**的字段目录范围与四列查看权得到可见字段集合；
  2. 每个项目：可见引用按 `fieldNames` 的历史名称渲染，不可见的换成占位符；`refFieldIds`、`fieldNames` 去掉不可见的 ID；
  3. 再按 §5.2 的规则裁剪审计里可能出现的 `hints`（B5 起审计就不含 hints，这里只作防御）；
  4. 查看人没有 `items` 字段权限时，整个 `items` 由原有字段级裁剪去掉（不变）。
- B5 时代的旧审计行（`formula` 是名称文本，没有 `formulaBinding`）：按 §1.4 的 legacy 规则渲染，只显示查看人可见字段中存在的同名引用。
- F-082 不重写历史审计，只在读取时裁剪。DEC-376④ 不豁免任何出口。

### 5.4 命令台账兼容

- F082-2 起，台账结果体里的项目存规范文本与 `formulaBinding`；响应时经 §5.1 投影。
- **旧台账**（B5 时代，`formula` 是名称文本、没有 `formulaBinding`）：重放时按 `legacy` 处理（§1.4 的 legacy 渲染，`formulaBindings` 全为 `null`）；`hints` 缓存一律丢弃（B5 已如此），按当前数据重算。
- 改名后用原命令 ID 重放：不重新执行；返回体按当前名称渲染（与 GET 一致），不带出旧名称。

## 6. 存量公式迁移（DEC-376③）

### 6.1 步骤

1. **结构迁移（F082-1，SQL）**：建引用表与目录版本表；项目表加 `formula_binding`（默认 `legacy`，存量行即为 `legacy`）、`binding_issue`、复合唯一键、优先级上限检查。存量里如有优先级 > 1000000 的行，迁移直接失败并报告（输入层自 #184 起已限制在 0～1000000，预期没有）。
2. **改绑（F082-4，平台命令）**：`POST /api/platform/tenants/:tenantId/talent-review/calc-formulas/rebind`。只认平台运营身份、显式指定租户、命令台账幂等（同 DEC-361 回补）。对该租户全部 `legacy` 项目，以及可选的 `retryUnresolved: true` 时的 `unresolved` 项目：
   - 按 §3.4 加锁；
   - **按迁移时 B5 的解析规则固定绑定，不按新规则重新解释**：字段目录用全部字段（系统执行，不按查看人）；`盘点对象.<名>` 恰有 1 个同名字段 → 绑定；`盘点对象.盘点方案` 有 1 个名为“盘点方案”的自定义字段 → 绑定该字段（B5 中自定义字段优先），没有 → 项目上下文，多于 1 个 → `unresolved`（`RESERVED_PATH_CONFLICT`，B5 此时退到上下文，但这里视为冲突、不猜）；
   - 成功：写规范文本、`kind = 'bound'` 的引用，`formula_binding = 'bound'`，`binding_issue = null`；
   - 失败：`formula_binding = 'unresolved'`，`binding_issue` 写原因码，**原文不动**；同时写入候选引用（§6.2）。
3. **运维**：部署 F082-2 后，对每个租户执行一次改绑（运维脚本逐租户调用命令）。报告里 `unresolved > 0` 的租户，通知其管理员修公式：在页面上改正后重新保存，保存后即为 `bound`。

### 6.2 unresolved 的保护（DEC-376⑥）

- **候选引用**：改绑失败的项目，把公式里每处 `盘点对象.<名>` 在当时全部同名字段的 ID 都写成 `kind = 'candidate'` 的引用（歧义时全部写入；`RESERVED_PATH_CONFLICT` 写入全部名为“盘点方案”的字段）。即使这些字段后来改名，候选引用也由外键与删除守卫第 2 条按 ID 保护。整段解析失败的项目写不出候选，由文本兜底保护。
- **文本兜底**（§3.2 第 3 条）长期保留，覆盖迁移后才出现的同名字段。
- `unresolved` 项目被用户重新保存成功 → 变为 `bound`，候选引用被 `bound` 引用替换；停用字段是否算“保留”，按 §3.3 的候选集合认定。

### 6.3 原因码（`binding_issue`）

| 码 | 情形 |
|---|---|
| `UNKNOWN_FIELD` | `盘点对象.<名>` 在租户字段里找不到 |
| `AMBIGUOUS_FIELD` | 同名字段不止一个 |
| `RESERVED_PATH_CONFLICT` | `盘点对象.盘点方案` 有多个同名自定义字段 |
| `BARE_WORD` / `INVALID` | 有裸词 / 整段解析失败 |
| `MULTI_OPTION` | 引用了多选字段（B5 已拒绝，理论上不会出现） |
| `INPUT_LIMIT` | 改绑后的渲染文本无法通过输入限制（理论上不会出现，作防御） |

`unresolved` 项目在读取时带提示“部分公式当前无法完整校验…”（沿用 B5 的 `UNVERIFIABLE`，经 §5.2 投影）；删除守卫走候选引用与文本兜底；T04 PR-C 拒绝计算。

### 6.4 幂等、revision 与审计

- 只处理 `legacy` 行（以及显式重试时的 `unresolved` 行）；`bound` 行不读不写。重复执行不产生新行、不改已绑定的结果。
- **不改规则 revision**（DEC-376⑤）：渲染后的公式与改绑前逐字相同（只有空白被规范化），客户端手里的 revision 继续有效。与计算冻结的关系见 §4。
- 审计：每条有变化的规则写一条 `talent-review.calc-rule.rebind`（同事务；before / after 为项目的 `formulaBinding`、`bindingIssue`、`refFieldIds`、`fieldNames`，读取时经 §5.3 裁剪；actor 为平台命令的运营身份）；平台审计另留一条汇总（同 DEC-361）。
- 返回报告：`{ rules, bound, unresolved: [{ ruleId, targetFieldId, reason }] }`，不含公式原文与字段名称。

### 6.5 失败与回退

- 单个租户一个事务：锁等待超时或其他异常 → 整个租户回滚（不留规范文本、引用、审计），命令记失败，可用新的命令 ID 重试；已经 `bound` 的行下次会被跳过。
- 单个项目绑定失败不会让整个租户失败（记 `unresolved`，继续处理其他项目）。
- **部署回退**：F082-2 及以后不提供把 `bound` 转回名称文本的反向迁移。回退到 F082-1 的代码时：
  - `bound` 行的公式会显示句柄原文；
  - 被引用字段的删除由引用表外键拒绝（不会静默丢失保护）；
  - 新保存写回名称文本，并按默认值成为 `legacy` 行。
  回退只作为事故处置，之后须前滚，并对受影响的租户再执行一次改绑。
