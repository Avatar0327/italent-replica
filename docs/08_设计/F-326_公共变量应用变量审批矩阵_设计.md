### 0.2 目标与非目标

- 目标：复刻系统具备公共变量、应用变量、审批矩阵三类业务对象，有管理页、权限、审计与“查看引用”；流程设计器可以把三者选作审批人来源（含“审批人为空时→指定人员”的候选），取消灰显，服务端不再拒存；运行时与模拟都能解析。
- 非目标：旧版矩阵（30 槽位）；业务规则、消息模板对变量的实际引用；矩阵导入 / 导出；变量引用表达式语言（变量参与条件表达式、公式）。理由见 §1.2。

### 1.3 与 F-318、设计器“指定人员”的关系

- F-318a 已建统一来源模型 `{type, value}`，`APPROVER_SOURCE_TYPES` 已含 `public_variable` / `application_variable` / `matrix`。F-326 不改模型，只把这三类的 `value` 语义定下来（§3.1），并把 `sourceViolation` 里的“暂不支持，后补 F-326”换成真实校验。
- F-318b 设计器级联已把三类放在 `unsupported` 集合里灰显。F-326 取消灰显，接候选接口（§5）。
- 原站在设计器选“指定人员”时会自动生成一条公共变量（编码 `Global.B.<流程编码><时间戳>`，名称“流程名-节点名”，描述“通过指定人员自动生成的公共变量”，适用范围“流程”，规格 F-326 节公共变量条）。
  - 结论（DEC-858）：复刻照原站做。设计器里“指定人员”的选法不变，保存流程时服务端把指定人员落成公共变量，节点存 `{type:'public_variable', value:<变量 id>}`。设计见 §5.5，拆分为 S7a / S7b（§8）。
  - DEC-686③ 其余内容不变：“审批人为空时→指定人员”与审批人共用级联选择器、单独保存；它同样落成变量，但单独一条（§5.5 ⑥）。
  - 存量：已发布版本里的 `specified` 不迁移（DEC-402），`specified` 解析器保留给这些旧版本用。
  - U-14～U-16 已定（DEC-859，U-14 / U-16 按 DEC-860 修订）：编码照北森；未选人也生成；自动变量租户级、跨流程可选，共享同一条。拆为 S7a / S7b（§8）。
  - 已定（DEC-861）：草稿期变量只给本节点用（①）、编码数字开头补 P（③）、草稿空变量豁免（④-1）、未选人不能发布（④-2）、保存时显示引用流程数（⑥）、重新启用的无引用变量下次保存再停用（⑧），落点见 §5.5。
  - 已由 F-326-L 定稿（`docs/08_设计/F-326-L_自动变量生命周期_设计.md`）：U-17 旧版本在途清零自动停用、DEC-862（取代 DEC-861②）、DEC-861 ⑤⑦ 与第 6 轮 P2-1。⑤（来源流程发布时才生效）并入 S7a；其余落在 S7e1 / S7e2，另加契约片 C2（§5.5 ⑨、§8）。

## 2. 数据模型

### 2.1 表

五张新表，都在 `packages/db/src/schema/approval.ts` 旁新建 `approval-variables.ts`（S1 契约片定），全部带 `tenant_id`，迁移里对每张表调 `enable_tenant_isolation('<表名>')`（FORCE RLS，和现有租户表同一做法）。

**`approval_variables`**：公共变量和应用变量共表，用 `scope` 区分。

| 列 | 类型 | 约束 / 说明 |
| --- | --- | --- |
| `id` | uuid | 主键（内部标识，与编码分离，平台约定“标识”） |
| `tenant_id` | uuid | 非空；RLS |
| `scope` | text | `public` / `application`，创建后不可改 |
| `app_id` | text | `scope='application'` 时非空且须在 `APP_IDS` 内；`public` 时须为空（CHECK） |
| `code` | text | 完整编码，含前缀；创建后不可改 |
| `name` | text | 非空，≤100 字（原站长度未测，取保守值，§9 U-8）；单行文本，按下文“文本字段统一校验” |
| `data_type` | text | `string` / `integer` / `decimal` / `datetime` / `boolean` / `person` / `persons`，创建后不可改 |
| `default_value` | jsonb | 可空；按 `data_type` 校验（§2.3） |
| `usage_scopes` | text[] | 只用于 `public`：`{process, business_rule, message_template}` 的非空子集；“全部”存三项全集。`application` 时须为空 |
| `description` | text | 只用于 `public`，≤32766 字（按 JS 字符串长度，即 UTF-16 码元计）；多行文本，按下文“文本字段统一校验”（只收良构 Unicode，除 `\t` `\n` `\r` 外禁止控制字符，§4.2 的字节计算以此为前提）；`application` 时须为空，非空即 400 |
| `status` | text | `draft` / `enabled` / `disabled` |
| `revision` | integer | 乐观锁，每次写 +1 |
| `created_by` / `created_at` | uuid / timestamptz | 服务端写 |
| `updated_by` / `updated_at` | uuid / timestamptz | “最近修改人 / 最近修改时间”，服务端写 |
| `origin` 及 4 个来源列 | — | **S1 补充**（DEC-858）：自动生成变量的来源标记与来源流程 / 版本 / 节点 / 位置，列定义与约束见 §5.5 ⑤ |

唯一约束：`(tenant_id, code)`。公共变量与应用变量前缀不同（§2.2），同表唯一不会误伤；同一应用前缀相同，跨应用同码也会冲突，这是有意为之（编码在租户内唯一，平台约定“业务编码按租户唯一”）。

**`approval_matrices`**：矩阵头。

| 列 | 说明 |
| --- | --- |
| `id`、`tenant_id`、`revision`、四个审计列 | 同上 |

| `description` | 可空，≤255 字（规格原文） |

**`approval_matrix_columns`**：列定义。

| 列 | 说明 |
| --- | --- |
| `id`、`tenant_id`、`matrix_id` | `matrix_id` 外键到矩阵头，同租户 |

**`approval_matrix_rows`** 与 **`approval_matrix_cells`**：数据行与单元格。

| 表 | 列 | 说明 |
| --- | --- | --- |
| rows | `id`、`tenant_id`、`matrix_id`、`seq` | `seq` 即页面“顺序”，同矩阵内唯一；调序整体重写 |

单元格不用 JSON 实体表承载：条件和角色都是 id 列表，落成 `uuid[]` 是明确的列（AGENTS.md §7）。

规模上限（与 §4.2 请求体上限一起成立，计算依据见 §4.2）：

| 项 | 上限 |
| --- | --- |
| 条件列 | ≤5 |
| 角色列 | ≤10 |
| 列名 | ≤50 字 |
| 数据行 | ≤500 |
| 单个条件格 | ≤50 个 id |
| 单个角色格 | ≤100 人（与会签上限一致） |
| 整个矩阵全部单元格的 id 总数 | ≤20000 |

超过任一项返回 400 `VALIDATION_FAILED`，`reason` 指明哪一项；一次保存整体成功或整体失败（平台约定“批量”），不部分写入。

**文本字段统一校验**（结论：本设计所有带长度上限的自由文本字段只收良构 Unicode，S1 在 `packages/domain/src/approval/variables.ts` 用一个纯函数 `textViolation(value, {max, multiline})` 统一实现，接口层不各写一份）：

| 字段 | 上限（UTF-16 码元） | 单行 / 多行 |
| --- | --- | --- |
| 变量名称、矩阵名称 | 100 | 单行 |
| 矩阵列名 | 50 | 单行 |
| 矩阵描述 | 255 | 多行 |
| 公共变量描述 | 32766 | 多行 |
| `string` 类型变量默认值（§2.3） | 1000 | 多行 |

规则依次判定，任一不满足即 400 `VALIDATION_FAILED`，`reason` 分别给出：

1. 良构：不得含未配对的 UTF-16 代理码元，即高代理 `U+D800`～`U+DBFF` 后面不是低代理，或低代理 `U+DC00`～`U+DFFF` 前面不是高代理。用带 `u` 标志的正则 `/[\uD800-\uDFFF]/u` 判定：`u` 模式按码点匹配，配对代理被视为一个增补平面码点，不会命中，命中的只有未配对代理码元。不用 `String.prototype.isWellFormed()`，因为仓库 `tsconfig.base.json` 的 `lib` 是 ES2023，没有它的类型，不为此改共享配置。`reason` = `TEXT_MALFORMED`。
2. 控制字符：单行字段禁止全部 C0 控制字符（`U+0000`～`U+001F`）与 `U+007F`；多行字段只放行 `\t` `\n` `\r`。`reason` = `TEXT_CONTROL_CHAR`。
3. 长度：按 `value.length`（UTF-16 码元）计，配对的代理对算 2；超过上限，`reason` = `TEXT_TOO_LONG`。名称类先去首尾空白再判非空。

为什么必须拒绝未配对代理码元：

- 它不是合法字符，存进 PostgreSQL `text` 前驱动也要替换或报错，入库结果与提交内容不一致。
- 它会让字节计算失效：`JSON.stringify` 把每个未配对代理码元写成 6 字节的 `\uD800` 转义。只按长度和控制字符约束时，32766 个这样的码元仍算“合法”，但请求体有 196,614 字节，会被 128 KiB 中间件拒为 413，违背“字段合法则不被 413 拒绝”的承诺（§4.2）。
- 矩阵单元格只存 uuid，不是自由文本，按 uuid 格式校验即可，不受本规则影响；编码后缀已由 §2.2 正则限定为 ASCII，同样不受影响。

### 2.2 编码前缀（系统固定）

| 对象 | 前缀 | 用户输入 | 存储 |
| --- | --- | --- | --- |
| 公共变量 | `Global.B.` | 后缀，`^[A-Za-z][A-Za-z0-9_]{0,63}$`（字母开头） | 前缀 + 后缀 |
| 应用变量 | `B.` | 后缀，`^[A-Za-z0-9_]{1,64}$`（可数字开头、可纯数字） | 前缀 + 后缀 |
| 审批矩阵 | 无（规格只写“编码必填，编辑时只读”） | `^[A-Za-z0-9_]{1,64}$` | 原样 |

- 两类变量的规则分开写、分开校验，不共用一个正则。
- 应用变量：规格第 543 行实测编码 `B.2`、`B.19`、`B.ee`，后缀可以是纯数字或纯字母，所以允许数字开头。
- 公共变量：实测样例 `Global.B.HTCtoTind0` 与自动生成的 `Global.B.<流程编码><时间戳>` 都以字母开头，没有数字开头的反例，保持字母开头。
- 其余字符（如 `-`、`.`）原站未测，取保守集合（§9 U-8）；有反例再放宽。
- 前缀拼接与校验放在 `packages/domain/src/approval/variables.ts`，前后端共用。

### 2.3 数据类型与默认值

| data_type | 页面名 | 默认值形态 | 作审批来源 |
| --- | --- | --- | --- |
| `string` | 字符串 | ≤1000 字，多行文本，按 §2.1“文本字段统一校验” | 否 |
| `integer` | 整数 | 安全整数 | 否 |
| `decimal` | 小数 | 十进制字符串，≤18 位有效数字 | 否 |
| `datetime` | 时间 | ISO 日期时间（租户时区录入，存 UTC） | 否 |
| `boolean` | Boolean | true / false | 否 |
| `person` | 人员 | 1 个用户 id | 是，单人 |
| `persons` | 多人 | 1～100 个用户 id，去重 | 是，多人 |

- 人员类默认值的候选与设计器选人同口径：`eligibleDesignerPeople`（DEC-135 / DEC-686①：全租户在职内部员工、有活跃账号）。保存时服务端复核，外部成员、离职员工报 400 `VALIDATION_FAILED`。
- “默认值”就是变量的取值。复刻没有按上下文赋值的机制，变量值即默认值。
- 启用条件：人员类变量启用时默认值不得为空，否则 409 `APPROVAL_VARIABLE_EMPTY`。非人员类允许空。系统生成的自动变量（§5.5 ②“未选人”，U-15）不受此限（已定（DEC-861④-1）：草稿中的空变量豁免），但来源流程不能带着未选人的位置发布（已定（DEC-861④-2），§5.5 ②“发布检查”）；默认值为空的变量被解析时按 `[nobody]` 走空人策略；管理员手工编辑自动变量仍受此限。

### 2.4 应用变量的应用归属

- 应用变量属于一个应用（`app_id`）。流程能用哪个应用的应用变量，由流程的审批类型决定。
- 新增领域常量 `APPROVAL_TYPE_APPS: Record<ApprovalTypeCode, AppId>`，放在 `packages/domain/src/approval/types.ts` 旁。守卫测试核对：每个审批类型都有映射，且该类型的 `objectCode` 在 `APP_OBJECT_DIRECTORY[app]` 中。不从目录反推，因为同一对象（如任职记录）可能出现在多个应用的目录里。
- 本期管理页入口只开审批流程用得到的应用：映射值去重后的集合。其他应用不出现应用变量入口。

### 2.5 状态机（三类对象相同，无删除）

```
新建 ──► 草稿 ──启用──► 启用 ──停用──► 停用
                         ▲               │
                         └─────启用──────┘
```

- 新建时可选“保存为草稿”或“保存并启用”；后者等于新建后立即启用，审计记两条。
- 草稿不能直接停用；停用不能回草稿。
- 编辑：三种状态都可编辑；编码、数据类型、`scope`、`app_id` 不可改，改了报 400。
- 原站页签提示“当前页面展示草稿状态、启用状态的……”，所以“启用的”页签显示草稿 + 启用，“停用的”页签显示停用。照原站。
- 删除：变量无删除（规格原文）。矩阵原站有删除按钮，但复刻也只做停用，不做删除（§9 U-2，推荐）。理由：已发布流程可能引用矩阵，删除会破坏引用；停用已经足够把它移出候选。矩阵的数据行可以删。

### 2.6 并发、幂等、审计列

- 每个写请求带 `revision`，不一致返回 409 `REVISION_CONFLICT`（沿用 `assertRevision`）。
- 每个写命令走 `runCommand`（命令台账，同键同内容幂等，同键异内容冲突），和流程定义写入同一套。
- 矩阵的列、行、单元格都挂在矩阵头的 `revision` 上：任何子项改动都使矩阵头 `revision +1`，客户端只需持有一个版本号。
- `updated_by` / `updated_at` 由服务端在同一事务内写，不接受客户端传值。

## 3. 解析语义

### 3.1 来源 value 约定

| type | value | 说明 |
| --- | --- | --- |
| `public_variable` | 变量 `id`（UUID） | 存 id 不存编码：编码不可改，但存 id 与 `specified` 一致，回查和引用扫描更直接 |
| `application_variable` | 变量 `id`（UUID） | 同上 |
| `matrix` | `<matrixId>:<roleColumnId>` | 两段 UUID，冒号分隔；长度 73，在 `sourceSchema` 的 200 上限内 |

`sourceViolation`（纯函数）只查格式：UUID 或两段 UUID。存在性、状态、类型、适用范围、应用归属要读库，放在保存校验（§5.2）。

### 3.2 变量取值

- `person` 变量取 1 人，`persons` 变量取 N 人（≤100）。
- 解析时对每个用户 id 走现有 `resolveFallbackCandidates`（与 `specified` 同一路径）：账号停用、人员离职的被滤掉。全部滤掉即 `[nobody]`，走节点空人策略。
- 单人节点（非会签 / 或签）配 `persons` 变量：保存即拒，422 `APPROVAL_SOURCE_INVALID`，文案“多人变量只能用于会签或或签节点”。配 `person` 变量不会出现多人。
- 节点的 `emptyApproverSources`（“审批人为空时→指定人员”）也能选这三类来源，规则同上。

### 3.3 矩阵：条件维度与求值

矩阵条件列不做“逐节点映射到表单字段”，而用固定的条件维度目录，统一从申请对象解析。理由：原站条件列是“部门”等业务维度；复刻各审批类型的条件字段各不相同，逐节点映射会把矩阵配置和流程配置耦合在一起。

| dimension | 申请对象的取值 | 匹配规则 |
| --- | --- | --- |
| `department` | `recordDepartmentId ?? latestDepartmentId`（与现有 `record_department_*` 来源一致） | 单元格任一 id 等于取值即命中；列勾“包含下级”时，取值的行政祖先链（按申请业务日，含自身）与单元格任一 id 相交即命中 |
| `position` | 申请对象在申请业务日的**主职**职位 | 单元格任一 id 相等即命中（主职口径同 DEC-691 D3） |
| `job` | 申请对象在申请业务日主职的职务 | 同上 |

- 空格表示该列不限。
- 行命中 = 该行所有非空条件格都命中。
- **按 `seq` 升序，取第一条命中行**（原站“顺序”列即为此）。不存在“多匹配”歧义，第二条及以后的命中行不参与。
- 命中行中，取来源 `value` 指定的角色列的单元格人员，再走 `resolveFallbackCandidates` 过滤。
- 条件维度取值为空（如申请对象没有主职职位）时，非空的该列条件格视为不命中。

### 3.4 矩阵的适用审批类型

- 条件求值需要单一申请对象和申请业务日。沿 DEC-691 D7：无任职申请业务日的审批类型（`definition.ts` 中 `relationSource` 的同一判断：adapter 不在 `employment` / `part_time` / `exit_handover`）配置矩阵来源，保存报 422，文案“该审批类型没有任职申请业务日”。**例外（DEC-902，与 AC-APV-F326-18 一致）**：个人信息变更（`personnel_change`）可配矩阵来源，其业务日取每次推进到新节点当天，按当天的任职求值；其余任职类审批仍按上述原口径。
- 多主体审批（`MULTI_SUBJECT_ADAPTERS`）同样拒存。这两条都在纯函数 `approverSourceViolations` 里加，前后端共用。
- 这会让 Offer、组织调整、人才盘点等类型暂时用不了矩阵。是保守取舍，§9 U-3 写明，推荐保持。

### 3.5 异常情形

| 情形 | 保存流程时 | 已发布流程运行时 |
| --- | --- | --- |
| 变量 / 矩阵不存在（他租户 id、伪造 id） | 422 `APPROVAL_SOURCE_INVALID` | 不会出现（保存已拦）；防御上按 `[nobody]` |
| 变量 / 矩阵处于草稿 | 422（只有启用的可配，原站提示“可使用列表展示的启用状态……”） | — |
| 变量 / 矩阵已停用 | 422 | `[nobody]`，走空人策略（类比 DEC-691 D8） |
| 公共变量适用范围不含“流程” | 422 | 改适用范围后变量仍被流程引用：运行时按 `[nobody]`；编辑适用范围时若有引用，给出影响清单（§6） |
| 应用变量不属于本流程审批类型的应用 | 422 | 不会出现（应用不可改） |
| 变量不是人员 / 多人类型 | 422 | 不会出现（类型不可改） |
| 角色列不存在 / 已被删 | 422 | `[nobody]` |
| 矩阵无命中行 / 命中行角色格为空 | — | `[nobody]` |
| 单人节点解析出多人（矩阵角色格多人） | 角色列 `allow_multiple=true` 且节点为单人：422 | 沿用 `APPROVAL_SINGLE_SOURCE_MULTIPLE`（engine.decide，422）。只有角色列在流程发布后才改成允许多人时会走到这里 |

“删角色列”：已被流程引用的角色列不允许删除，409 `APPROVAL_MATRIX_COLUMN_REFERENCED`（§6）。“被引用”含仍有可推进实例的旧发布版本，口径见 §6.1。条件列可删。

### 3.6 已发起实例是否冻结来源取值

- **结论：不在实例发起时冻结，节点激活时实时读取变量 / 矩阵的当前值；任务一经派出即固定。**
- 理由：
  1. 和现有全部来源一致。组织负责人、职务、身份都在节点激活时解析（DEC-691 D7：授权按派单时实时状态）；变量单独冻结会让同一流程内的来源语义不一。
  2. 变量和矩阵的用途就是“改一处、所有在途审批跟着走”（例如替换财务审批人）。发起时冻结会让管理员改了矩阵、在途单仍派给旧人。
  3. 已派出的任务不受影响：任务表记的是具体处理人，后续改变量不回溯改派，和改组织负责人一样。
- 已办内容冻结（F-476）只针对单据内容，不涉及审批人来源，二者不冲突。

### 3.7 模拟（simulation）

现有模拟只收虚拟输入（`simulation.ts` 文件头注释、`policy.ts` 第 428 行“仿真只收虚拟数据（清单 7）”），只有流程对象查看权的账号也能调（`access.ts` `requireProcessView`）。读取真实变量 / 矩阵会把真实人员披露给这类账号，所以分两条路径：

| 路径 | 谁能用 | 三类来源怎么取人 |
| --- | --- | --- |
| 虚拟路径（默认） | 现有全部可模拟者：流程管理员，或有流程对象查看权者 | 按 `sourceKey(source)` 从 `data.sourceRelations` 取虚拟人员；没给就是空，走空人策略。**不读变量表、矩阵表**，现有 `virtualSources` 的兜底分支已覆盖，不加新分支 |
| 当前值路径 | 只有 `admin.process_matrix` | 请求显式带 `resolveCurrentSources: true`。没给虚拟值的三类来源按变量当前值、当前矩阵求值；矩阵条件的部门 / 职位 / 职务仍取 `data.values`，“包含下级”仍取 `data.orgAncestors`（虚拟），不读真实组织 / 任职 |

- 结论：省略虚拟值本身**不会**触发读真实值，只有显式标志才会；标志由服务端单独校验管理员能力，不靠前端隐藏按钮。
  - 非管理员带 `resolveCurrentSources: true`：403 `FORBIDDEN`，`reason=APPROVAL_SIMULATION_CURRENT_ADMIN_ONLY`，不返回部分结果。
  - 非管理员不带标志、也不给虚拟值：三类来源节点显示审批人为空，不出现任何真实用户 id。
- 管理员走当前值路径能看到的人，管理员在变量 / 矩阵管理页本来就能看到（§4.3），不扩大披露面。
- 当前值路径对变量 / 矩阵里的用户同样走 `resolveFallbackCandidates` 过滤（停用账号、离职人员滤掉），和运行时一致。
- 两条路径都只读，不落库、不进台账（沿用 `simulationWrite`）。
- 当前值路径只是模拟的取值方式，不影响 §3.6 的运行时结论。
- 实现：`simulateProcess` / `simulateByObject` 增加 `currentSources: boolean` 参数，由路由层在通过 `isProcessAdmin` 之后才置为 true；`virtualSources` 在三类来源、无虚拟值、`currentSources=true` 时转调 §3.2 / §3.3 的解析器。权限声明改动见 §4.3。

## 4. 接口与权限

### 4.1 接口（审批模块路由，均为管理员接口）

| 方法与路径 | 作用 |
| --- | --- |
| `GET /variables?scope=public\|application&appId=&status=active\|disabled&q=&offset=&limit=` | 列表；`active` = 草稿 + 启用；分页上限 200 |
| `GET /variables/:id` | 详情 |
| `POST /variables` | 新建（`enable: boolean` 决定草稿还是直接启用） |
| `PATCH /variables/:id` | 编辑（带 `revision`） |
| `POST /variables/:id/enable` / `POST /variables/:id/disable` | 启用 / 停用（带 `revision`） |
| `GET /variables/:id/references` | 查看引用流程（§6） |
| `GET /matrices?status=&q=&offset=&limit=` / `GET /matrices/:id` | 列表 / 详情（详情含列、行、单元格及名称回显） |
| `POST /matrices` / `PATCH /matrices/:id` | 新建 / 编辑头部 |
| `PUT /matrices/:id/structure` | 整体保存列定义 + 数据行 + 单元格（一次提交整体成功或失败，带 `revision`） |
| `POST /matrices/:id/enable` / `POST /matrices/:id/disable` | 启用 / 停用 |

- 全部只接受 JSON、同源校验，错误码走 `approvalError`。请求体上限见 §4.2。

### 4.2 请求体上限与结构上限

结论：两个接口放宽，其余仍为默认 32KB；放宽值按字段上限的最坏情况算出，保证“字段合法的请求一定不被 413 拒绝”。

- “字段合法”指满足 §2.1 结构上限与“文本字段统一校验”（含良构 Unicode）。
- 字节数按标准序列化计：`JSON.stringify` 不加缩进。前端与测试都这样提交。客户端若把普通字符也写成 `\uXXXX` 转义，或加入大量空白，体积可能超限并得到 413。这不属于“合法请求被拒”，复刻不为非标准编码放宽。

| 接口 | 请求体上限 | 依据（最坏情况字节数） |
| --- | --- | --- |
| `PUT /matrices/:id/structure` | **1 MiB**（1,048,576） | 见下方计算，最坏约 0.89 MB |
| `POST /variables`、`PATCH /variables/:id`（仅 `scope=public` 会用到） | **128 KiB**（131,072） | 描述最坏 98,300 + 其余字段约 5,000，约 103 KB |
| 应用变量的新建 / 编辑 | 默认 32KB | 无描述；名称 300 + 默认值最坏 3,900（100 个 UUID）+ 其余约 300，约 4.5 KB |
| 矩阵头新建 / 编辑、启停、`references` 等 | 默认 32KB | 描述 ≤255 字 = 765 字节 |

- 公共变量与应用变量共用 `/variables` 路径，`limitBody` 只能按方法 + 路径匹配，所以 128 KiB 对两者的新建 / 编辑都生效；应用变量请求实际不会超过 32KB，放宽对它无害。
- 放宽登记在 `apps/api/src/app.ts` 的 `limitBody` 覆盖表（与 DEC-422 继任规则 64KB、合同批量 1MB 同一机制），每条一行注释写依据。S2 登记 `/variables` 两条，S3 登记 `structure` 一条。

**矩阵 `structure` 请求的序列化形状**（S3 按此实现，前端同形状提交）：

```json
{ "revision": 3,
  "columns": [{ "id": "<uuid|省略>", "key": "c1", "kind": "condition", "dimension": "department",
                "includeChildren": true, "name": "部门", "allowMultiple": false }],
  "rows": [{ "id": "<uuid|省略>", "cells": { "c1": ["<uuid>"], "r1": ["<uuid>", "<uuid>"] } }] }
```

- 行顺序即数组顺序，不另传 `seq`；`key` 是本次请求内的列短键（`^[a-z][a-z0-9]{0,3}$`），单元格按 `key` 引用列，避免每格重复 36 字节的列 id。

**最坏情况计算**（UTF-8；中文 3 字节；UUID 带引号与逗号 39 字节）：

| 部分 | 计算 | 字节 |
| --- | --- | --- |
| 全部单元格 id | 20,000（总数上限）× 39 | 780,000 |
| 行骨架 | 500 行 ×（`{"id":"<uuid>","cells":{}},` 约 58 + 15 格 × `"c123":[],` 10 = 150）= 500 × 208 | 104,000 |
| 列定义 | 15 列 ×（固定键与值约 160 + 列名 50 字 × 3 = 150）= 15 × 310 | 4,650 |
| 外层与 revision | — | 约 100 |
| **合计** | | **约 888,750 < 1,048,576** |

- 余量约 15%，用来吸收 JSON 空白与键顺序差异；前端提交时不加缩进。
- 单格上限（条件 50、角色 100）只约束单格，总字节由“id 总数 ≤20000”约束；两者同时成立。
- 公共变量描述：32,766 码元 × 最多 3 字节 = 98,298，加引号为 98,300。“每码元最多 3 字节”只在良构文本下成立，所以以 §2.1 的良构校验为前提。逐类说明如下：
  - BMP 非代理字符（含中文）：1 码元，UTF-8 最多 3 字节；
  - 配对代理（如表情）：2 码元，4 字节，平均每码元 2 字节；
  - `"`、`\`、`\t`、`\n`、`\r`：转义后 2 字节；
  - 其余控制字符已禁止，不会出现 6 字节的 `\u00XX`；
  - 未配对代理码元已拒绝，不会出现 6 字节的 `\uD8XX`。
- 同一前提适用于其他文本字段：名称 100 × 3 = 300、列名 50 × 3 = 150（已计入上表列定义）、矩阵描述 255 × 3 = 765、`string` 默认值 1000 × 3 = 3,000。都落在各自接口的上限内。

**失败语义**：

- 超过请求体上限：中间件直接 413 `PAYLOAD_TOO_LARGE`，不进入处理器，数据库无变化。
- 字节数合规但超过结构上限，或文本不良构（如 501 行、id 总数 20,001、描述 32,767 字、名称或描述含未配对代理码元）：400 `VALIDATION_FAILED`。在命令事务内先校验后写入，任何一项不合规整个事务都不写，`revision` 不变。

**矩阵结构的持久审计**（结论：持久层存可还原的完整差异和删除快照，界面另做摘要）：

1. 一次 `PUT structure` 在同一事务里写：
   - 一条 `approval.matrix.structure`，`objectId` = 矩阵 id；
   - 每删除一行，另写一条 `approval.matrix.row.delete`，`objectId` = 行 id。
2. `approval.matrix.structure` 的 `before` / `after` 按条目展开成顶层键，`auditApproval` 的 `changed()` 只留有变化的键：
   - `column:<columnId>`：该列完整定义 `{kind, dimension, includeChildren, name, seq, allowMultiple}`。新增列 `before` 为空，删除列 `after` 为空。
   - `row:<rowId>`：该行完整内容 `{seq, cells: {<columnId>: [ids]}}`，含该行全部单元格，不是只含变化的格。改一个格、调一次序，都记整行前后。新增行 `before` 为空。
   - 被删除的行在这里也有 `before`（`after` 为空），删除内容可从这一条还原。
   - 因此“把角色格从 A 改成 B”“改某行的部门条件”都能从 `row:<rowId>` 的前后值直接看出原条件和原审批人。
3. `approval.matrix.row.delete`：`before` 为删除前该行完整快照 `{matrixId, matrixCode, seq, cells}`，并带当时列名 `{<columnId>: {name, kind}}`（列之后可能改名或被删）；`after` 为空。审计视图把它当删除操作，详情显示快照（`apps/api/src/audit/routes.ts` 删除时返回 `snapshot`，S1 登记时核对动作到“删除”操作的映射）。
4. 界面摘要（审计详情的展示层，不影响存储）：变更行数、新增 / 删除行数、变更列名。点开再看逐行前后。
5. 体量：单次保存的审计正文上界约为请求体的两倍（前后各一份），即 ≤2 MB，与合同批量（1MB 请求体）同一量级，可接受；不为审计单独截断，截断会破坏可还原性。
6. 用户 id 原样存；展示时按当前权限回显姓名（读取历史仍按当前权限裁剪）。条件格里的组织 / 职位 / 职务 id 同理，回显名称时按当前组织披露口径。
- 原站有无后台审计日志未测（§9 U-5）。复刻照常记审计，属于复刻的平台约定。

### 5.2 保存校验（`assertSourceReferences` 扩展）

对节点 `approver` / `approvers` / `emptyApproverSources` 中的三类来源，按 id 批量读库（一个节点一次查询），逐条检查：

1. 存在且同租户（RLS 已保证，查不到即不存在）；
2. 状态为 `enabled`；
3. 变量：`data_type` 为 `person` / `persons`；公共变量 `usage_scopes` 含 `process`；应用变量 `app_id = APPROVAL_TYPE_APPS[流程审批类型]`；
4. 矩阵：角色列存在且 `kind='role'`；
5. 单人节点：`persons` 变量或 `allow_multiple=true` 的角色列，拒；
6. 自动变量（S7a，§5.5 ③“草稿期限制”）：来源版本仍为草稿时，只能出现在它自己的来源位置，否则拒，`reason` 为 `APPROVAL_SOURCE_AUTO_VARIABLE_UNPUBLISHED`。来源版本已发布的自动变量与人工变量同样校验，不看 `origin`（DEC-860）；

### 5.5 指定人员落成公共变量（S7，DEC-858）

总体口径：设计器的“指定人员”仍是一个选人控件，接口入参仍可写 `{type:'specified', value:<用户 id>}`；服务端在流程版本落库时把它换成自动生成的公共变量，节点里只存变量来源。以下 ①～⑨ 每项给结论；⑨ 指向 F-326-L 定稿的生命周期设计。

**术语**：

- **自动变量**：`origin='auto'` 的公共变量。
- **位置（slot）**：一个节点里指定人员出现的两个地方，`approver`（审批人）和 `empty_approver`（审批人为空时→指定人员）。
- **归属版本**：生成该自动变量的流程版本（`origin_version_id`）。

**① 生成时机与事务**

- 结论：在流程版本内容落库时生成，即 `definitions.ts` 的 `writeVersionContent`，在节点 `INSERT` 之前调新函数 `materializeSpecified`。不在选人时生成。
- 顺序：先照旧校验指定人员（`assertFallbackUsers`，人员须为本租户有效成员，失败 422 `APPROVAL_SOURCE_USER_INVALID`；未选人的输入占位跳过，见 ②“未选人”），再落成变量并把来源换成 `public_variable`，然后用守卫确认已无 `specified` 与占位，再对合并后的会签节点查重（见 ②“未选人”前置校验第 4 项），最后走 `assertSourceReferences` 与 §5.2 校验。自动变量启用、人员类型、范围为流程，必然通过 §5.2。
- 理由：
  - 选人时生成需要单独的建变量接口，用户取消编辑会留下孤儿变量。
  - 落库时生成与流程保存同一事务：任一节点校验失败（422 / 400），整个事务回滚，变量一条也不写。
- 覆盖的入口：`writeVersionContent` 是所有版本落库的唯一入口，下列入口都经过它：
  - 新建流程 `createProcess`；
  - 保存草稿 `replaceDraft`；
  - 编辑最新版本 `newVersion`；

**③ 去重与复用（类型感知；跨流程共享按 DEC-860）**

- 结论：
  - 自动变量按“流程 × 节点 × 位置”生成。人员相同、类型相同就复用。
  - 人员变化时改这一条，所有引用方共用这一条（DEC-860）。占位变量在保存时原地更新；继承变量推迟到来源流程发布时写入（DEC-861⑤，F-326-L §5）。
  - 目标数据类型（`person` / `persons`）不同时，新建变量，不原地改类型。
- “本位置自动变量”：`origin='auto'`，且来源流程、`origin_node_key`、`origin_slot` 与当前节点位置一致的自动变量。只有它在设计器里显示为“指定人员”。别处对它的引用，包括其他流程，都是普通的公共变量来源，设计器显示为“公共变量”，保存时不改它。
- 判定方法：保存时，对每个节点的每个位置，先确定三样东西：
  - P：本次提交的人员集合，可以为空集，即 U-15 的未选人。
  - T：目标类型，按 ② 的“数据类型”。
  - V：按顺序取第一个存在的：
    1. **占位变量**：`origin_version_id` 为本次写入的版本、节点与位置相同、状态不是停用的自动变量。S1 唯一索引保证至多一条。它是本版本早先保存时生成的，也可能是管理员重新启用的遗留变量。
    2. **继承变量**：保存前内容在该位置引用的本位置自动变量。V 来自替换前的草稿内容；`newVersion` 时来自被复制的版本，此时 V 的来源版本是更早的版本。
    3. 无。

| 情形 | 处理 |
| --- | --- |
| 没有 V | 新建自动变量，来源版本为本版本 |
| V 已停用（只可能是继承变量） | 不复用；新建，V 保持停用作历史 |
| V 的类型 ≠ T | 新建，类型为 T。V 若是占位变量，先停用它（`auto_disable`，腾出位置）再新建。这样不撞 S1 唯一索引；草稿期 V 只可能被本草稿引用，见下文“草稿期限制”。V 若是继承变量，不动：它占的是旧版本的位置，旧发布版本照旧用它 |
| V 类型 = T，默认值 = P（按集合比较，顺序不同也算相同；空集 = 空集） | 复用 V，不写变量，不写审计；继承变量上已有的待生效值一并去掉（F-326-L §5.3） |
| V 类型 = T，默认值 ≠ P，V 是占位变量 | 保存时原地更新 V 的默认值（`auto_update`）。V 只被本草稿引用（“草稿期限制”），不影响在用派单 |
| V 类型 = T，默认值 ≠ P，V 是继承变量 | 保存时不写变量：草稿节点来源仍引用 V，另记 `pendingUserIds`（即 P）与 `pendingRevision`（待生效值新出现那次保存时 V 的 `revision`）；发布时按 F-326-L §5.4 写入（`auto_update`，操作者为发布人）。草稿期间 V 被手工改过时，发布提示冲突、由发布人选，不默认覆盖（DEC-864①，见 ④“并发”）。影响面见 ④ |

- 生效时点（DEC-861⑤“来源流程发布时才生效，存草稿不改在用流程的路由”，F-326-L §5 定稿）：新建、占位变量的原地更新、类型不同时停用占位变量腾位，都在保存时写入，只影响本草稿；继承变量改人推迟到发布，发布事务里以 `P = pendingUserIds` 再跑一次上表（同一函数 `materializeSpecified`）写入，与切换当前版本同一事务，提交时对所有引用方一起生效（F-326-L §5.4）。

- 解除引用后的收尾：节点写完后，取三类变量的并集，去掉新内容仍引用的，逐条做租户内引用扫描（`retireUnreferencedAutoVariables`）。扫描口径与 §6.1 三类在用版本相同，用 `source-usages.ts` 同一函数。没有任何引用的才 `auto_disable`；仍被别的流程、发布版本、草稿或在途单引用的不停用，只解除本节点的引用。三类变量是：
  - 保存前内容引用过的自动变量，含本位置与公共变量来源两种引用；
  - 来源版本为本版本、状态不是停用的自动变量，即占位变量；
  - 管理员手工重新启用过的本流程自动变量（DEC-861⑧，按原文收窄）：来源流程为本流程、状态为启用，且有过 `approval.public_variable.enable` 审计。这类变量来源版本可能更早，前两类取不到（④“手工重新启用”）。
    - 判据用审计：自动变量生成时即为启用，只记 `auto_create`，不会有 `.enable`；有 `.enable` 记录就说明管理员手工重新启用过。S1 没有专门的列，S7 不带迁移，所以不加列。
    - 查询：先用 S1 的 `approval_variables_origin_process` 索引取本流程启用的自动变量 id，再按 `object_type` + `action` + `object_id = ANY(ids)` 查审计（走 `audit_operation_logs_tenant_object_type` 前缀），一个流程的自动变量只有几条。
    - 不扫描：本流程更早版本里其他启用的自动变量（从未被手工重新启用过的），即使已无引用，本设计也不停用；旧版本自动变量的停用由 F-326-L 的系统停用负责（F-326-L §2、§8）。
- 写入顺序：
  1. 停用（类型不同时腾位）；
  2. 原地更新（只限占位变量）；
  3. 新建；
  4. 写节点（继承变量改人在此带 `pendingUserIds` / `pendingRevision`，不写变量）；
  5. 收尾停用。
  - 涉及的变量行（`FOR UPDATE`）与 `assertSourceReferences` 引用的变量行（`FOR SHARE`）合成一批，按 id 升序一次取，见 ④“并发”。
  - 例外：`republishWithExceptionAdmin`（交接与 `restore.ts`）在 S7e1 合入后，第 5 步不在此执行，登记到提交前任务（见 ①“覆盖的入口”，F-326-L §3.4）。
- 草稿期限制：来源版本仍是草稿的自动变量，只能被它自己的位置引用。
  - 不进其他流程的候选（§5.3）。
  - 其他节点、其他流程引用它时，保存返回 422 `APPROVAL_SOURCE_INVALID`，`reason` 为 `APPROVAL_SOURCE_AUTO_VARIABLE_UNPUBLISHED`。
  - 来源版本发布后，限制自动解除。
  - 理由：草稿里改类型时要停用占位变量来腾位。若这时它已被别处引用，按 DEC-860 不得停用，新变量就会撞 S1 唯一索引。这条限制让 S1 索引可以照原样成立。
  - 已定（DEC-861①）：草稿期的变量只给本节点用，发布后其他流程才能选。
- 各场景：
  - 同一节点重复保存：人员、类型都不变即复用，不会越存越多。
  - 未选人保存（U-15）：生成一条默认值为空的变量。之后选人，类型不变时原地更新这一条；节点类型改了就新建。
  - 会签 ↔ 单人（同节点 key、同人员）：类型变化，新建一条；旧变量按上表处理，已发布的旧版本不变。
  - 同一流程多个节点选同一批人：每个节点各一条。名称“流程名-节点名”本身就区分节点。
  - 会签节点审批人里有多个 `specified` 来源：合并为一条 `persons` 变量，放在第一个 `specified` 的位置，其余 `specified` 移除，`value:null` 的占位一并忽略，其他来源顺序不变。会签各审批人并行、无先后（`types.ts` 会签节点注释），合并不改变派单结果。
  - 编辑最新版本（`newVersion`）：复制出的草稿直接引用原版本的自动变量。草稿里改人不写变量，在草稿节点记待生效值（`pendingUserIds`），发布时才写入；改类型才新建（F-326-L §5.2、§5.3）。
  - 发布：先做 ②“发布检查”（DEC-861④-2，按有效值），再应用待生效值（`applyPendingAutoVariables`），然后切换当前版本，提交时对所有引用方生效（F-326-L §5.4）。被替换的旧版本在途为 0 时，其已无引用的自动变量由系统停用（F-326-L §2）。
  - 复制流程：复刻目前没有“复制流程”接口。将来加时，按“没有 V”处理。
- 跨流程选用（DEC-860 U-16，照北森，规格 30 第 426、552 行已取证）：
  - 自动变量是租户级公共变量。来源版本已发布的，进 `public_variable` 候选，并按 §5.2 校验。
  - 其他流程引用它时，与引用人工公共变量完全相同，不加 `origin` 判断。

**④ 生命周期**

本节“共享同一条、改动一起生效”是 00 定的口径（未取证假设，DEC-860），规格第 552 行“最近修改人为在设计器里操作的人”可作旁证。不做写时复制。

| 操作 | 自动变量怎么处理 |
| --- | --- |
| 来源节点改选人员（类型不变） | 改这一条（`auto_update`），所有引用它的流程、版本共用这一条，包括当前已发布版本与其他流程。占位变量保存时原地更新；继承变量在来源流程发布时写入并生效，存草稿不改在用流程的路由（DEC-861⑤，F-326-L §5.4） |
| 来源节点类型变化（会签 ↔ 单人） | 新建一条，不原地改类型（P2-3）。旧变量：占位变量先停用腾位，继承变量不动；已发布的旧版本照旧用旧变量 |
| 删除节点、把指定人员改成其他来源 | 只解除本节点的引用。收尾时做租户内引用扫描（③）：仍被其他流程、发布版本、草稿或在途单引用就不停用；没有任何引用才 `auto_disable` |
| 发布新版本 | 应用草稿上的待生效值（F-326-L §5.4）。替换当前版本后，旧版本在途为 0 即由系统停用其已无引用的自动变量；仍有在途的，最后一单离开在途（含撤回，DEC-862）时停用（U-17，F-326-L §2） |
| 流程作废（`discardProcess`；复刻没有流程删除，也没有单独的草稿删除） | 作废时，无在途单的版本中已无其他引用的自动变量由系统停用；有在途的，作废后最后一单结束时停用（DEC-861⑦，F-326-L §7）。草稿上的待生效值不生效 |

- 影响面：
  - 不能再凭“变量归属本草稿”推断改动没有影响。原地更新会改变：其他流程的解析结果；已发布版本的解析结果；在途实例**之后**激活的节点（运行时实时读取，§3.6；已派出的任务不变，同 AC-13）。继承变量改人在来源流程发布提交后生效（F-326-L §5.4）。
  - 引用流程数（已定（DEC-861⑥），S7d 后端 / S7b 前端）：设计器保存时显示“该变量被 N 个流程引用”。
    - 计数口径：与 §6.1 扫描同一组在用版本（草稿、当前已发布版本、仍有可推进实例的旧发布版本），任一版本的任一节点、任一位置以 `public_variable` 引用该变量，该流程计 1；按流程去重，一个流程的多个版本、多个节点只计一次；**含本流程**，所以本流程在用时 N ≥ 1。作废流程仍随 §6.1 现状（作废流程有在用版本时计入）；F-326-L 只改系统停用口径，不改本计数（F-326-L §1）。
    - 实现：`source-usages.ts` 新增 `referencingProcessCounts(tx, tenantId, variableIds)`，复用 §6.1 的在用版本常量，一次 `COUNT(DISTINCT process_id) ... GROUP BY` 查询，返回 `Map<变量 id, number>`。
    - 返回形状：读视图的 `autoVariable` 增加 `referencingProcessCount: number`（见下文“设计器回显”）。`GET /processes/:id` 与新建、保存草稿、编辑最新版本的响应都返回读视图，所以保存后即拿到新值，不额外请求；`trimProcess` 的字段投影放行该字段。只给数，不给流程名，不扩大披露面；要看是哪些流程，仍走 `GET /variables/:id/references`（S4，需 `admin.process_matrix`）。
    - 前端（S7b）：保存成功后，以及打开设计器时，在节点“指定人员”下方、变量编码旁显示“该变量被 N 个流程引用”。N ≥ 2 时用提示色，提醒改人会影响其他流程。
- 只停用不删除：自动变量与人工变量同受 §2.5 约束，没有删除。
- 停用记录是历史，不占位：S1 唯一索引条件为 `origin='auto' AND status <> 'disabled'`，所以停用后同一位置可以再生成。
- 管理员在变量页手改自动变量：
  - 可改：名称、默认值（人员）、描述。改默认值对所有引用方一起生效（§3.6），与设计器改人同一效果；两条路径改的是同一条变量，各自记审计。变量页的修改立即生效，不受 DEC-861⑤ 约束；它与草稿待生效值的冲突在发布时提示、由发布人选（DEC-864①，F-326-L §5.4）。
  - 不可改：适用范围固定为“流程”；编码、数据类型、`origin` 及来源列只读。编辑接口收到这些字段的改动，返回 400 `VALIDATION_FAILED`，`reason` 为 `APPROVAL_AUTO_VARIABLE_FIELD_LOCKED`。
  - 列表多一列“来源”：人工 / 自动（流程名 · 节点名）。
- 手工停用：照常走 §6.2 的引用检查与影响确认。停用后，引用它的节点运行时按 `[nobody]` 走空人策略（§3.5）。
- 手工重新启用（P2-1）：
  - 若该变量的位置，即“来源版本 × 节点 × 位置”，已有另一条状态不是停用的自动变量，返回 409 `CONFLICT`，`reason` 为 `APPROVAL_AUTO_VARIABLE_SLOT_TAKEN`，`details` 带占位变量的 `id` / `code`。
  - 前端提示：“该位置已有自动变量〈编码〉，请改用它，或在流程设计器里重新选择人员”。
  - 写入时撞唯一索引，同样映射为这个错误码。
  - 位置空闲时照常启用。已定（DEC-861⑧）：重新启用的变量若已无任何引用，下次该流程保存时由 ③ 的收尾再次停用（③ 第三类候选），操作人为保存人；若管理员要长期用它，改由人工变量承载。前端在重新启用成功后提示这一行为（S7b）。
- 设计器回显：
  - `GET /processes/:id` 返回的节点来源中，凡是本位置自动变量，附带 `autoVariable: {id, code, status, userIds, referencingProcessCount}`（`referencingProcessCount` 由 S7d 加）。设计器显示为“指定人员：〈当前默认值的人员〉”，并以小字标出变量编码。
  - 草稿有待生效值时（F-326-L §5.5，S7a）：`autoVariable` 另给 `pendingUserIds`、`revision`（V 当前值），以及按发布时同一判定得出的 `pendingConflict: true`（无冲突时不出现）；`userIds` 仍为变量当前值，节点来源对象本身不返回 `pendingUserIds` / `pendingRevision`。设计器显示待生效人员并标“发布后生效”（S7b）。
  - 默认值为空时，显示“指定人员：未选择”。
  - 变量已停用时标“已停用”，提示“保存后将按所列人员重新生成”；保存时按 ③“V 已停用”新建。
  - 其他流程的自动变量与人工变量一样，显示为公共变量（名称与编码）。
- 并发（锁顺序按 F-326-L §3.1 的全局顺序：业务锁 → 流程头 → 实例行 → 变量行；不锁版本行，变量一个事务至多一批、按 id 升序；各条路径只取其中一段，不逆序）：
  - 同一草稿并发保存：已有流程头锁（`lockedForChange`）与草稿 `revision`。后到者 409 `REVISION_CONFLICT`，不写任何变量；刷新后重提成功。
  - 两个流程争同一生成编码：靠 ② 的 `ON CONFLICT DO NOTHING` 加 +1 毫秒，两边都能提交。
  - 管理员编辑与设计器保存同一变量：
    - 设计器在 ③ 写入前对 V 取 `FOR UPDATE`，管理员编辑也取 `FOR UPDATE`。设计器保存时，本流程涉及的变量 `FOR UPDATE` 与 `assertSourceReferences` 对引用变量的 `FOR SHARE` 合成一批按 id 升序取，避免两个流程互相引用对方自动变量时并发保存成环（F-326-L §3.2 R2）；S7e1 再把这些调用点改经 `lockVariableBatch`（F-326-L §3.3）。
    - 设计器先提交：`auto_update` / `auto_disable` 都使变量 `revision` +1，管理员的旧 `revision` 返回 409，刷新后重提成功。
    - 管理员先提交，V 是占位变量（只被本草稿引用）：设计器拿到锁后重新读 V，按最新默认值与类型重新判定（与 P 相同就复用，不同就再更新）。
    - 管理员先提交，V 是继承变量：设计器保存时不写 V（③），草稿随待生效值记下 V 的 `revision`（`pendingRevision`）。发布时 V 的 `revision` 已变（草稿期间被手工改过）→ 整笔 409 `CONFLICT`，`reason` 为 `APPROVAL_PENDING_VARIABLE_CONFLICT`，`details.conflicts` 附“设计器值 / 变量页当前值”两边人员；发布人选“用设计器值”或“保留变量页值”后，带选择与 `revision`（发布请求体 `pendingResolutions`）以新命令 ID 再发布，服务端再次核对，仍不一致再 409。不默认覆盖（DEC-864①，F-326-L §5.4）。V 已停用（按“V 已停用”新建）、V 的默认值已等于 P（不写）两种情形照旧，不要求选择。
    - 两次写各有审计。
  - 其他流程引用与停用竞争：沿用 §6.2，引用方对变量取 `FOR SHARE`。停用方取 `FOR UPDATE` 后，在新语句里重做引用扫描。
    - 停用先提交：引用方读到“已停用”，返回 422。
    - 引用方先提交：停用方扫描到这条新引用，不停用。
  - 交接 / 恢复重发（`republishWithExceptionAdmin`）例外（S7e1 合入后，F-326-L §3.4）：引用校验不对已有变量加锁；存量 `specified` 照旧落成新变量；收尾停用登记到提交前任务，在同一批锁之后以原操作者与 §6.1 口径执行。S7a 照本节实现，由 S7e1 改。

**⑤ 数据模型影响（S1 补充）**

S1（PR #646，审查已通过）已按下表实现，本轮照 S1 实际定义写，未发现站不住之处（理由见“索引”一条）：

  - `origin='manual'` 时 4 个来源列全为空；
  - `origin='auto'` 时 4 列全非空，且 `scope='public'`、`data_type IN ('person','persons')`、`usage_scopes = '{process}'`。
- 索引：
  - 部分唯一索引 `approval_variables_origin_slot`：`(tenant_id, origin_version_id, origin_node_key, origin_slot) WHERE origin='auto' AND status <> 'disabled'`。草稿与启用都占位，停用作历史、不占位（P2-1），所以停用后同一位置可以再生成；它也兜住并发重复生成。

  - 部分索引 `approval_variables_origin_process`：`(tenant_id, origin_process_id) WHERE origin='auto'`，供模拟与回显使用。
- 来源版本与来源流程的一致性（版本属于该流程）由 `materializeSpecified` 写入时保证，S7a 用测试覆盖，不另加触发器。
- 人工新建 / 编辑接口不接受这 5 列：入参 schema 里没有这些字段，严格模式下多余字段返回 400。
- S1（PR #646）已一并加上，S7a / S7b / S7d 都不带迁移；默认 `'manual'` 让 S2 / S3 无需任何改动。第 4 轮的“S1 已先合入则由 S7a 带迁移”备选不再需要。

**⑥ 解析与模拟**

- 运行时：节点引用自动变量后就是普通的 `public_variable` 来源，走 §3.2 变量取值路径（实时读取、停用即 `[nobody]`、人员过 `resolveFallbackCandidates`）。不加分支，`origin` 不参与解析。
- 审批人为空时→指定人员（`emptyApproverSources`）：
  - 同样落成自动变量，`origin_slot='empty_approver'`，一个节点一条 `persons` 变量，与审批人位置分开。
  - 理由：两处共用同一个级联选择器（DEC-686③），用户看到的“指定人员”应是同一语义。
  - 原站空人位置是否也生成变量未取证，§9 U-15。
  - F-316 空人策略校验 `node.emptyApproverPolicy === 'specified'` 时才允许配 `emptyApproverSources`（`definition.ts` 第 87 行）。这里的 `specified` 是策略名，不是来源类型，不受影响。
- 模拟：

## 6. 查看引用与停用前影响检查

### 6.1 引用扫描

**扫描范围（结论）**：一个流程版本只要还可能派单，就算“在用”，引用都要列出。具体是三类版本：

| 版本 | 为什么在用 |
| --- | --- |
| 草稿版本 | 发布后即生效 |
| 当前已发布版本（`approval_processes.current_version_id`） | 新发起的单据绑定它 |
| 仍有**可推进实例**绑定的旧发布版本 | 引擎按实例自身的 `versionId` 加载定义（`engine.ts` `openRun` 第 122 行 `loadVersion(tx, ctx.tenantId, instance.versionId)`），发布新版本不会把在途实例迁过去 |

- “可推进实例”与 `store.ts` `resumableInstanceOf`（第 183 行）同一集合：`status IN ('running','returned','withdrawn')`。被驳回、已撤回的实例重新提交时沿用原实例与原版本（DEC-103），所以也算。终态（`approved` / `disapproved` / `cancelled`）不算。
- 这一集合由 `source-usages.ts` 里一个常量统一给出，引用扫描、停用影响清单、删角色列阻止三处共用，不各写一份。F-326-L 的系统停用另用生命周期口径（`running` / `returned`，F-326-L §1，DEC-865），同在 `source-usages.ts`，以参数区分；本节三处与 §5.5 ③ 的保存收尾停用仍用本口径。
- 不在上述三类里的历史版本不再派单，不列入。

**查询与返回**：

- 来源：`approval_process_nodes` 的 `approver_expression` / `approver_expressions` / `empty_approver_sources` 三列（jsonb），连版本表与流程头；第三类版本用 `EXISTS (SELECT 1 FROM approval_instances WHERE version_id = v.id AND status IN (...))` 判定。
- 匹配：`type` 与 `value` 相等；矩阵按 `value` 前缀 `<matrixId>:` 匹配，并给出引用的是哪个角色列。
- 返回：流程编码、流程名称、审批类型、版本（草稿 / 当前已发布 / 在途旧版本 + 版本号）、节点名称、引用位置（审批人 / 审批人为空时）；在途旧版本另给可推进实例数。分页上限 200。
- 实现：在 `source-reference.ts` 旁新增 `source-usages.ts`，用 jsonb 包含查询（`@>`）。三列都不大，租户内流程数在百级，本期不建 GIN 索引；如审查认为需要，S1 迁移顺手加（§9 U-9）。

### 6.2 停用前影响检查

- 停用接口不阻止停用。前端点“停用”时先调 `references`，有引用则弹窗列出影响清单（口径同 §6.1，含在途旧版本），文案“以下流程引用了该变量，停用后这些节点将视为审批人为空，按节点空人策略处理”，用户确认后再调停用。
- 服务端停用接口接受 `acknowledgedReferenceCount`（S4 加入；S4 之前流程无法引用三类对象，停用无影响面）：与当前引用数不一致时返回 409 `APPROVAL_REFERENCES_CHANGED`，防止确认后又新增了引用。
- 编辑会改变运行结果的字段时，做同样的检查：公共变量把“流程”移出适用范围；人员类默认值清空（启用中不允许清空，§2.3）。
- 删除矩阵角色列：只要 §6.1 三类版本中任何一个引用该列，即 409 `APPROVAL_MATRIX_COLUMN_REFERENCED`，清单同上。这是唯一硬阻止的情形，因为角色列删除后来源 `value` 永久失效，无法恢复。在途实例全部结束后，旧版本不再算在用，角色列才可删。

**并发**：

- `PUT structure` 和启停先对矩阵头 / 变量行 `SELECT ... FOR UPDATE`，再做引用检查，再写入。
- 流程保存（`writeVersionContent` → `assertSourceReferences`）对引用到的矩阵头 / 变量行取 `FOR SHARE`。两者互斥，避免“检查时无引用、同时另一事务保存了引用”。
- 新实例只绑定当前已发布版本，而当前已发布版本本来就在扫描范围内，所以对本设计的停用（管理员停用、设计器收尾），发起新单不需要额外加锁。发起与发布、系统停用之间的竞争（第 6 轮 P2-1）：发起在插入实例前对流程头取 `FOR SHARE` 并重验，见 F-326-L §4（§5.5 ⑨②）。
