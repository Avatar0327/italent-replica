## 0. 结论摘要

### 0.1 一句话

新增一个按租户隔离、按“用途”配置限制的附件模块：文件**先登记元数据再上传**，字节存在 PostgreSQL 的独立 blob 表（本地、CI、PGlite 都能跑，不需要云凭据）；上传后的文件是**本人临时文件**，只能被本人读、删；写进本人离职草稿的 `attachmentRefs` 时由同一个**绑定函数**校验并绑定到该申请；提交后附件随申请**封存**，之后只能经三个**载体**（本人申请、审批实例、HR 离职详情）读取，载体打不开或附件字段不可见一律 404；未绑定的临时文件 24 小时后转待清理，清理任务按租户、可重复执行。

## 1. 存储

### 1.1 存储端口与实现

```
AttachmentBlobStore（apps/api/src/modules/attachments/blob-store.ts）
  put(tx, tenantId, fileId, bytes): Promise<void>      // 与元数据同事务
  read(tx, tenantId, fileId): Promise<Uint8Array | null>
  remove(tx, tenantId, fileId): Promise<void>          // 只由清理任务调用
```

- **唯一实现 `PgBlobStore`**：字节写入独立表 `attachment_blobs`（`bytea`），与元数据同库同事务。本地 `pnpm test`（PGlite）、`pnpm test:pg`（PG16，含 `app_owner` 普通角色分片）与 CI 不需要任何外部凭据。
- 不复用头像 / 模型图的 `content_base64 text` 存法：10MB 图片的 base64 文本约 13.4MB，元数据行与字节同行会让列表、清理扫描都拖着大字段；拆表后元数据查询不触碰字节。
- 选 PG 而不是本地磁盘：AGENTS §10“恢复”要求恢复单元 = 数据库一致快照 + 附件清单与哈希。字节在库内时，一致快照天然包含字节，附件清单即 `attachment_files` 行（含 `sha256`），恢复后的隔离校验逐行重算哈希比对即可（§2.6）；磁盘实现会引入“快照与文件不同时刻”的问题。
- 端口留给以后换对象存储：换实现时 `put` 改为“先写对象、元数据同事务登记、失败进待清理队列”，属另一任务，不在本期。

### 1.2 表结构（S1 片一个迁移，编号以合并顺序为准，`pnpm merge:main` 顺延）

**`attachment_files`**（元数据，一文件一行，不物理删除）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | 内部主键，对外即附件 ID |
| `tenant_id` | uuid not null | RLS 维度；所有索引以它开头 |
| `purpose` | text not null | 用途编码，CHECK ∈ 已登记用途（本期只有 `exit.handwritten_application`） |
| `owner_user_id` | uuid not null | 上传人账号；临时阶段的唯一读者 |
| `owner_employee_id` | uuid null | 上传人当时对应的员工（本人离职用途必填，由用途校验写入） |
| `status` | text not null | `registered` / `uploaded` / `bound` / `detached` / `pending_cleanup` / `purged`（§2.1） |
| `business_type` | text null | 绑定载体类型，本期 `employment`（离职业务单） |
| `business_id` | uuid null | 绑定载体 ID（离职业务 ID）；`status ∈ {bound, detached}` 时必填（CHECK） |
| `sealed_at` | timestamptz null | 首次随申请提交的时间；非空后永不物理清理（§2.3） |
| `filename` | text not null | 清洗后的文件名（§1.4），1～255 字符 |
| `declared_type` | text not null | 客户端声明的 MIME，仅记录 |
| `content_type` | text null | 上传时**按内容判定**的 MIME，CHECK ∈ {image/jpeg, image/png, image/gif, image/bmp}；下载只用此列 |
| `byte_size` | integer not null | 登记大小，CHECK 1～`maxBytes`（用途上限，见 §1.3） |
| `sha256` | char(64) not null | 登记哈希，上传时比对 |
| `expires_at` | timestamptz null | 临时文件转待清理的时刻；绑定时置空 |
| `revision` | integer not null | 乐观锁 |
| `created_at` / `updated_at` / `uploaded_at` / `cleanup_at` / `purged_at` | timestamptz | `cleanup_at` = 进入待清理时刻，`purged_at` = 字节删除时刻 |

索引：`(tenant_id, owner_user_id, purpose, status)`（配额与本人列表）、`(tenant_id, business_type, business_id)`（载体读取）、`(tenant_id, status, expires_at)` 与 `(tenant_id, status, cleanup_at)`（清理扫描，有界分页）。

**`attachment_blobs`**：`tenant_id, file_id (PK, FK → attachment_files.id), bytes bytea not null, created_at`；CHECK `octet_length(bytes) <= 10485760`。

**`attachment_cleanup_attempts`**（清理尝试记录，照 `contract_job_attempts` 形态）：`tenant_id, file_id, kind (expire|purge), period, status (succeeded|failed), attempts, reason, updated_at`，唯一键 `(tenant_id, file_id, kind)`（AGENTS §10 定时任务：按“对象 + 周期”幂等，失败记次数与原因、可重试）。

三张表都 `ENABLE` + `FORCE ROW LEVEL SECURITY`，策略与既有租户表一致（`tenant_id = current_setting('app.tenant_id')`）；`attachment_files` 加不可改列触发器：`tenant_id, purpose, owner_user_id, sha256, byte_size, content_type（非空后）, sealed_at（非空后）` 不可更新，防止事后改写哈希或解封。

### 1.4 文件名与类型校验

登记时（`POST /attachments`，JSON，≤32KB）：

1. `purpose` 必须是已登记用途，否则 400 `VALIDATION_FAILED`。
2. **文件名清洗**：取最后一个 `/` 或 `\` 之后的部分；去掉控制字符（U+0000～U+001F、U+007F）与 Unicode 双向控制符（U+202A～U+202E、U+2066～U+2069）；去首尾空白；清洗后为空或超过 255 字符 → 400。清洗后的名字只用于展示与下载头，不参与任何路径拼接。
3. **扩展名**取最后一个 `.` 之后、小写，必须在用途的 `extensions` 中，且与声明 MIME 一致（`jpg` 与 `jpeg` 都对应 `image/jpeg`）；否则 415 `UNSUPPORTED_MEDIA_TYPE`。
4. `byteSize` 为正整数且 ≤ `maxBytes`，否则 413 `PAYLOAD_TOO_LARGE`；`sha256` 为 64 位十六进制。
5. 本人未绑定临时文件（`registered` / `uploaded` 且未过期）数 ≥ `maxTemporaryPerOwner` → 409 `ATTACHMENT_TEMP_LIMIT`。

上传时（`POST /attachments/:id/upload`，JSON `{ base64 }`）：

1. 严格 base64 解码（复用 `talent/model-image-format.ts` 的 `decodeImage`，参数化上限）；解码后长度与 `byte_size` 不一致、`sha256` 不一致 → 400 `VALIDATION_FAILED`（不落任何字节）。
2. **内容嗅探**：按文件头判定真实类型（JPEG `FF D8 FF`、PNG `89 50 4E 47 0D 0A 1A 0A`、GIF `GIF87a` / `GIF89a`、BMP `BM`）；判定结果必须 ∈ 用途 `types`，且与登记扩展名对应的 MIME 一致——扩展名是 `.png`、内容是 JPEG 也拒绝（415），不做“按内容纠正”。
3. 再调用 `validateImageContent(bytes, sniffedType)` 做结构与完整解码校验（静态 PNG、单帧 GIF、JPEG / BMP 结构合法，像素可完整解码）；失败 415。
4. 通过后同一事务：写 `attachment_blobs`、`status = uploaded`、`content_type = 嗅探结果`、`uploaded_at`、`expires_at = now + tempTtlHours`、审计（§4.4）。

**复用改造（S1 片）**：`model-image-format.ts` 的 `validateImageMetadata` / `decodeImage` 增加 `maxBytes` 参数与中性措辞参数（默认值保持 5MiB 与“模型图”措辞，头像与模型图行为不变）；新增 `sniffImageType(bytes)` 纯函数（放在同文件或抽到 `apps/api/src/image-format.ts`，二者择一由实现定，不影响契约）。

请求体上限：`apps/api/src/app.ts` 的 `limitBody` 例外表新增一行 `POST ^/api/tenant/attachments/[^/]+/upload$`，`maxSize = 4 * ceil(10 MiB / 3) + 1024`（约 13.4MB）。仍只接受 JSON（AGENTS §10“请求”），不开 multipart。

## 2. 生命周期

### 2.1 状态机

```
registered ──上传成功──▶ uploaded ──写入本人草稿 attachmentRefs──▶ bound ──随申请提交──▶ bound + sealed_at
    │                      │  ▲                                     │
    │ 超时 / 本人删除        │  └──从 draft / rejected 草稿中移除（从未提交过）──┘
    ▼                      ▼
 pending_cleanup ◀─────────┘                      已封存的从可编辑草稿中移除 ──▶ detached（保留，不清理）
    │
    └──清理任务删除字节──▶ purged（元数据行保留作快照）
```

| 状态 | 谁能读 | 能否删 | 进入方式 |
|---|---|---|---|
| `registered` | 本人（只读元数据，无内容） | 本人 | 登记 |
| `uploaded`（临时） | 本人（元数据 + 内容预览） | 本人 | 上传成功 |
| `bound`，`sealed_at` 空 | 本人；该申请对 HR 可见时 HR | 只能经 PATCH 申请移除 | 草稿创建 / 修改时写入 |
| `bound`，`sealed_at` 非空 | 本人；审批载体；HR 载体（§3） | 不能 | 提交 |
| `detached` | 仅经审批载体读取它出现过的那一份表单（§3.2），以及本人在审批详情中 | 不能 | 已封存附件在驳回 / 撤回后的草稿里被本人移除 |
| `pending_cleanup` | 无人（孤儿对象不可读，AGENTS §10） | — | 临时文件过期、本人删除、未封存的绑定被移除 |
| `purged` | 无人 | — | 清理任务 |

### 2.2 与离职申请状态的对应（自查 3：每条迁移的附件副作用）

离职单状态见 R2-T03 §3（`draft → in_review → rejected → in_review …`；`transitions.ts:72` 撤回回到 `draft`）。

| 申请迁移 | 入口 | 附件副作用（与业务写入同一事务） |
|---|---|---|
| 新建草稿 | `POST /self-service/exit-requests`（带 `attachmentRefs`） | 绑定函数：每个引用 `uploaded → bound`，`business_id` = 新业务 ID，`expires_at` 置空 |
| 修改草稿 / 已驳回单 | `PATCH /self-service/exit-requests/:id`（只允许 draft / rejected，既有规则） | 新列表与旧列表求差：新增的走绑定；移除的按 `sealed_at` 分流——空 → `pending_cleanup`，非空 → `detached`；顺序变化只改列表 |
| 提交 / 驳回后重提 | `POST /self-service/exit-requests/:id/submit` | 列表内全部附件 `sealed_at` 为空的写为提交时刻；提交前复核每个引用仍是 `bound` 且 `business_id` = 本单、字节存在（`purged` 或缺字节 → 409 `ATTACHMENT_MISSING`，不提交） |
| 审批驳回 / 退回发起人 | 审批引擎 | 无附件变化（单据回到 rejected，本人可再编辑） |
| 本人撤回 | 审批中心 `withdraw`（→ draft） | 无附件变化；已封存的附件仍封存，之后在草稿中移除即 `detached` |
| 审批不同意 / HR 撤销 / 删除（`DELETE businesses/:id` 对离职映射为撤销，`exit-routes.ts:378`） / 离职生效 | 既有入口 | **无附件变化**：附件随申请保留只读（终态单据仍可被 HR 查看，与“删除时保留快照”一致）；未封存的（草稿被 HR 撤销）同样保留，不清理（U-4） |
| 本人删除草稿 | **不存在**：B6c 自助没有删除草稿入口 | 若以后增加，未封存附件转 `pending_cleanup`，由该任务实现 |

### 2.3 封存的含义

- `sealed_at` 非空的文件**永不进入待清理**：它出现在某次提交的表单里，审批人可能已经办理过（F-476 冻结快照：已办人读冻结份），删掉会让历史审批表单引用失效。
- 封存后元数据与字节都不可改（§1.2 触发器）。

### 2.4 绑定函数（唯一出口，自查 1）

`bindAttachmentRefs(tx, ctx, { carrier, businessId, previous, next, actor })`，放在 `apps/api/src/modules/attachments/binding.ts`，在 `FOR UPDATE` 锁住涉及的 `attachment_files` 行后逐条校验：

1. `next` 是 UUID 数组，去重前后长度一致（重复 → 400），长度 ≤ 用途 `maxFiles`（超出 → 400 `ATTACHMENT_LIMIT`，文案“最多上传 5 张”）。
2. 新增的每个 ID：同租户（RLS 已保证，查不到即视为不存在）、`purpose` 与载体用途一致、`owner_user_id` = 当前操作人、`status = uploaded`、未过期。任一不满足 → 400 `ATTACHMENT_INVALID`，**错误体只回显请求里的下标，不回显该 ID 的任何元数据**（自查 9：不泄露别人文件是否存在）。
3. 保留的 ID 必须仍是 `bound` 且 `business_id` = 本单。
4. 移除的按 §2.2 分流。
5. 返回规范化后的列表写入 `exit_requests.attachment_refs`（列表即顺序的唯一来源；`attachment_files.business_id` 是归属校验，两者同事务写）。

调用方（S2 片 grep 全部 `attachmentRefs` 写出口逐个接上）：

| 出口 | 处理 |
|---|---|
| 自助新建 / 修改（`application-service.ts` `exitFields` / `exitCreate`） | 调绑定函数 |
| 自助提交（`checkApplication` 构造提交载荷处） | 调 `sealAttachments`（同文件，§2.2 提交行） |
| HR 发起 `POST exits/employees/:id` 与批量、经理代发、HR `PATCH exits/:id`、审批编辑 `applyEdit`、编辑并同意 | 只读校验 `assertRefsUnchanged(previous, next)`：不带或相同放行；不同 → 400 `ATTACHMENT_REFS_READONLY`（R-2）。新建时 `previous = []`，即 HR 发起只能带空数组或不带 |

### 2.5 过期清理（原站未测，按复刻口径实现，U-3）

- **临时文件 TTL 24 小时**：`registered` / `uploaded` 且 `expires_at < now` → `pending_cleanup`（`kind = expire`）。依据：复刻口径；用户在同一次填写中完成上传与保存草稿，24 小时足够覆盖“上传后隔天再保存”，又能限制未保存文件占库时长。原站是否有临时文件、多久清理未取证。
- **待清理宽限 1 小时后删字节**：`pending_cleanup` 且 `cleanup_at < now − 1h` → 删除 `attachment_blobs` 行，元数据 `status = purged`、`purged_at`（`kind = purge`）。宽限期只为让并发中的读取请求自然失败而非读到半删状态；进入 `pending_cleanup` 时已不可读。
- **执行方式**：新调度器 `startAttachmentCleanupScheduler`（照 `contracts/scheduler.ts` 形态）在 `server.ts` 启动；每 15 分钟一轮，`withPlatform` 列租户，逐租户 `withTenant`，每租户每轮最多处理 500 条（有界），按 `(status, expires_at / cleanup_at, id)` 游标分页；每条一个小事务，`attachment_cleanup_attempts` 记成功 / 失败（次数、原因），失败下轮重试，同一文件同一 `kind` 成功后再跑是空操作（可重复执行）。
- 测试入口：导出 `runAttachmentCleanup({ db, clock, tenantId? })`，验收测试注入时钟直接调用，不依赖真实定时器。
- 审计：系统身份 `SYSTEM_USER_ID` 写 `attachment.file.expired` / `attachment.file.purged`（与状态变更同事务）。

### 2.6 恢复（AGENTS §10）

- 附件清单 = `attachment_files` 中 `status ∈ {uploaded, bound, detached}` 的行（ID、租户、`sha256`、`byte_size`）。
- 恢复后的隔离校验增加一项：逐行重算 `attachment_blobs.bytes` 的 sha256 与 `byte_size` 比对，不一致的文件列入恢复报告并置为不可读（不自动修复）。本期只提供校验函数 `verifyAttachmentManifest(tx, tenantId)` 与单测；接入恢复演练脚本属既有恢复任务。

## 3. 读取与下载

### 3.1 原则

- **没有“按附件 ID 直接下载”的公共入口**。临时阶段只认上传人本人；绑定后只经“载体”读取：调用方先证明自己能打开某个载体、并能看到载体上的附件字段，再按“该附件属于这个载体”放行。权限每次请求重新计算（AGENTS §10“下载前再次验权”），不签发下载令牌、不缓存。
- 越权一律不可读，错误形态沿用各载体现状（见 §3.3）：载体打不开 → 载体既有的 404；载体能打开但附件字段不可见、附件不属于该载体、附件不可读状态 → 404 `NOT_FOUND`“附件不存在”。不返回 403 以免暴露附件存在（与头像内容接口“头像不存在”、审批“审批实例不存在”一致）。只有路由级按钮 / 菜单缺失沿用 F-039 声明的既有 403。

### 3.2 读取入口

| 入口 | 读者 | 判定（全部满足才返回） |
|---|---|---|
| `GET /api/tenant/attachments/:id`、`GET /api/tenant/attachments/:id/content` | 上传人本人（临时文件预览） | 登录成员；`owner_user_id` = 本人；`status = uploaded`（`registered` 只给元数据，无内容 404）。已绑定的文件不再经此入口读（404），避免绕过载体 |
| `GET /api/tenant/self-service/exit-requests/:id/attachments/:fileId/content` | 员工本人 | `ownRequest`（既有：员工、发起人、发起方式 self，否则 404“申请不存在”）；本人对 `TenantBase.SelfExit.attachmentRefs` 有查看权；`fileId ∈ 当前 attachment_refs` 且 `business_id` = 本单、`status = bound` |
| `GET /api/tenant/approval/instances/:id/attachments/:fileId/content` | 发起人、待办 / 已办审批人、转交接收人、会签与加签人、抄送人、有转交 / 干预范围的审批管理员——即 `assertCanOpen` 放行的人 | ① `assertCanOpen`（`approval/disclosure.ts`，`self_skip` / `subject_skip` 来源的任务不算）；② `disclosedFields(data, userId, viewable)` 含 `attachmentRefs`（节点表单 ∩ 查看人字段权，DEC-057 / DEC-119）；③ `fileId ∈ 该查看人被服务的那份表单值的 attachmentRefs`（已办人读 F-476 冻结份、在办人读现值，与详情接口同一取值函数）；④ 文件 `business_id` = 实例业务 ID、`status ∈ {bound, detached}` |
| `GET /api/tenant/employment/exits/:id/attachments/:fileId/content` | HR（离职详情可见者） | 与 `GET exits/:id` 同一路由声明与范围判定（员工数据范围 fail-closed）；查看人对 EMPLOYMENT 对象 `attachmentRefs` 字段有查看权（`exit-queries.ts:572` 既有依赖登记）；`fileId ∈ 当前 attachment_refs`、`business_id` = 本单、`status = bound` |

- 盲审：节点表单含 `attachmentRefs` 但查看人无字段权时，详情按既有盲审规则不出现该字段，下载入口同样 404。
- 元数据随载体详情一起返回：三个载体的详情 / 表单接口把 `attachmentRefs` 展开为 `attachments: [{ id, filename, contentType, byteSize, uploadedAt }]`（仍按同一字段权裁剪，无权时整键不出现，与 `AC-DM-19` 现有“三类形状一致”口径相同）；`attachmentRefs` 原值保留（审批 `changedFields` 与编辑基线仍用 ID 列表）。审批详情在 `namedForm` 阶段展开，不改快照结构。
- 被清理或缺字节的引用（理论上不会出现在封存附件上）在展开时标 `missing: true`，下载 404，不报 500。

### 3.3 与现有 403 / 404 行为对齐

| 情形 | 返回 | 依据 |
|---|---|---|
| 未登录 | 401 | 既有中间件 |
| 跨租户 / 别人的申请 / 打不开的实例 / 范围外员工 | 404，沿用载体原文案（“申请不存在”“审批实例不存在”、离职详情既有 404） | `ownRequest`、`assertCanOpen`、离职详情范围判定 |
| HR 无离职详情路由所需按钮 | 403（F-039 声明既有行为） | `GET exits/:id` 现状 |
| 载体可打开，字段不可见 / 附件不属于该载体 / 已 `pending_cleanup` / `purged` / 别人的临时文件 | 404“附件不存在” | 不暴露存在性 |
| 写入口越权（删除、绑定别人的文件） | 绑定 400 `ATTACHMENT_INVALID`（只回显下标）；删除别人的临时文件 404 | §2.4 |

### 3.4 下载响应头（防内联执行）

```
Content-Type: <attachment_files.content_type>        // 嗅探结果，不用客户端声明
Content-Disposition: attachment; filename="<ASCII 回退名>"; filename*=UTF-8''<RFC 5987 编码的清洗后文件名>
X-Content-Type-Options: nosniff
Content-Security-Policy: default-src 'none'; sandbox
Cross-Origin-Resource-Policy: same-origin
Cache-Control: private, no-store
Content-Length: <byte_size>
```

- **不照抄头像内容接口的 `Content-Disposition: inline`**：附件即使被直接在地址栏打开也只触发下载；CSP `sandbox` 兜底，万一类型判定出错也不会以同源身份执行脚本。
- ASCII 回退名：非 ASCII、引号、反斜杠替换为 `_`，防头部注入；`filename*` 使用 `encodeURIComponent` 并额外编码 `'()*`。
- 前端预览走 `<img src>`（同源、带会话 Cookie）：`Content-Disposition: attachment` 不影响 `<img>` 渲染；`CORP same-origin` 阻止第三方页面嵌入。
- 只支持 GET，不支持 Range（10MB 以内无需分段）；`ETag` 用 `sha256`，但仍 `no-store`（每次都重新验权）。
