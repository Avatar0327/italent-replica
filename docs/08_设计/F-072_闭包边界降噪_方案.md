## 2. 边界加入清单与替代保障（①）

### 2.1 单元级边界

- 仍禁止 `apps/api/src/modules/<x>/` 下的条目（`permission/` 除外），也禁止覆盖业务目录的目录条目。`packages/domain/` 下**只允许单列文件**（本期仅 `tenant-time.ts`），不允许目录。

### 2.3 核心摘要门禁（独立于义务摘要）

新增手写登记 `support/route-policy/evidence-core.ts` 与生成文件 `required/core-digests.ts`：

```ts
// evidence-core.ts（手写，审查对象）
interface CoreEntry {
  readonly id: 'tenant-time' | 'require-permission' | 'system-actor';
  readonly boundary: string;                 // 对应的 EVIDENCE_BOUNDARY 条目
  readonly units: readonly string[];         // 核心单元：边界覆盖的全部顶层声明（含私有辅助与常量）
  readonly contract: readonly string[];      // 契约单元：投影规则见 §2.4
  readonly deps: readonly CoreDep[];         // 依赖白名单：核心闭包里允许出现的边界外单元（§2.3.1）

  readonly mutants: readonly Mutant[];       // 变异体（§2.5）
  readonly supporting: readonly CoreTest[];  // 已有的外部测试（只跟踪摘要，不承担杀变异）
  readonly reason: string;

  readonly closure: Readonly<Record<string, string>>; // 核心闭包：依赖单元（解析后的目标）→ 摘要

  readonly local: string;                            // 局部标识符（命名空间成员写 `ns.member`）
```

#### 2.3.1 核心的传递依赖由谁跟踪（审查补定的技术点一）

**结论：核心门禁独占跟踪核心实现的完整依赖闭包；普通依赖图在核心处截断，不再展开。**

1. 核心闭包的算法与 B-02 相同：从 `units` 出发求闭包，**只把本核心自己的条目从边界里拿掉**。闭包走到其他边界条目时停下：原有 4 条，以及其他核心（各核心由各自的门禁负责）。
2. 闭包结果按依赖单元的**解析后目标**登记（`文件#名字`）。这只能发现“引入了新目标”的重绑定；目标 B 已经在闭包里时，重绑定可以让 `closure` 的键和值全不变，交换两个别名绑定甚至让直接邻接集合也不变（#176 第 2 轮 R2-1）。所以另登记**绑定指纹**（§2.3.2），重绑定靠它发现。
3. **白名单，失败关闭**：核心闭包里出现 `deps` 白名单之外的单元，就报 `EVIDENCE_CORE_DEPENDENCY`。核心闭包里出现**任何** unresolved，不论位于哪个目录，也报 `EVIDENCE_CORE_DEPENDENCY`。存在这两类发现时，`ROUTE_POLICY_UPDATE_CORE` 拒写；只能手改 `evidence-core.ts` 把依赖登记进白名单，这个改动本身是审查对象。现状 3 个核心的白名单都是空的：它们只依赖本文件声明，以及边界内的 `errors.ts#AppError`。
4. 白名单依赖的摘要任何变化（辅助函数改了），都报 `EVIDENCE_CORE_STALE`，并点名变化的依赖与链。普通刷新不写 `core-digests.ts`，所以消不掉它。
5. 同一个辅助函数也可能经别的非核心路径被证据单元引用。这时它同时出现在普通图（只算那些路径上的根）和核心闭包里，两边各报各的、各消各的：普通刷新只能消普通那条。
6. 普通图只把核心记成**终端节点**：保留入边、不展开、不登记摘要。终端节点只用于 `EVIDENCE_CORE_CONTRACT` 的反向展开（§4.1）。
7. 核心单元或任一闭包依赖的绑定变化 → `EVIDENCE_CORE_STALE`（明细写“绑定变化”，列出变化的引用位置、旧目标、新目标）。普通刷新同样消不掉。核心的绑定量很小，`core-digests.ts` 直接存**完整绑定清单**（`BindingEntry[]`），旧目标从登记里取，新目标从当前源码算，逐项比较即可得出明细。

#### 2.3.2 绑定指纹（修 R2-1）

对每个声明（核心单元、核心闭包里的每个依赖；普通图里的每个节点与根同样计算，见 §4.1），按 `collectRefs` 的遍历顺序列出全部**引用位置**，每个位置记三项：

| 项 | 内容 |
|---|---|
| 序号 | 该声明内第 k 个引用（按遍历顺序计数，不用字节偏移，空白与注释不影响） |
| 局部标识符 | 源码里写的名字（`fmt`、`ns.member` 记作 `ns` + `member`） |
| 解析结果 | `decl:文件#名字`（同文件顶层声明）；`import:说明符 → 转导出跳 1 → … → 文件#名字`（**每一跳都记**，`export … from`、`export *`、`export * as` 都算一跳）；`boundary:<条目>`；`external:<包>#<导入名>`；`global:<名字>`（`Intl`、`Date` 等未声明的全局）；`dynamic:<说明符>#<成员>` |

绑定指纹 = 这张列表规范化后的摘要。两种审查反例都会改变它：

- 目标已在白名单与闭包中：`import { a as fmt }` 改成 `import { b as fmt }`（`b` 本来就被别处引用）→ 第 k 个位置 `fmt` 的解析结果从 `…#a` 变 `…#b`；
- 交换两个别名：`import { a as fmt, b as tz }` 改成 `import { b as fmt, a as tz }` → 邻接集合仍是 `{a, b}`，但 `fmt`、`tz` 两个位置的解析结果互换；
- 中间文件改转导出（`index.ts` 的 `export { a as fmt } from './x'` 改指 `./y`）→ 解析链里那一跳变；
- 局部新增同名 import 遮蔽全局（`Intl` 从 `global:Intl` 变成 `import:…`）→ 解析结果变。

#### 2.3.3 登记范围也是契约（P3「白名单审定」）

`evidence-core.ts` 里本核心的登记本身（`boundary`、`units`、`contract`、`deps` 白名单及其理由）规范化后并入 `contract` 摘要。因此：

- 扩大或缩小白名单、调整核心单元或契约单元的范围 → `EVIDENCE_CORE_CONTRACT`，必须按契约级审定（§2.7），`ROUTE_POLICY_CORE_CONTRACT=changed`；
- 删减 `mutants` 或把某个变异体的 `kill` 从 `required` 改成 `not-required` → `tests` 摘要变，同样按契约级审定（§2.7 第 3 点）。

审查给的两步反例（第 2 步只改辅助文件），在本设计下的走法：

| 步骤 | 改动 | 门禁输出 | 普通刷新后 |
|---|---|---|---|

### 2.4 契约投影：签名 + 出口点（修 P2-2）

契约单元逐个投影，再走 `normalize()` 求摘要。投影内容只有下表几类，函数体里的其他内容一律算“实现”：

| 契约单元种类 | 投影内容 |
|---|---|
| 函数 | 名字、参数列表（含类型）、返回类型；加上**全部出口点** |
| 常量 | 名字 + 初始化文本 |
| 类型 / 接口 | 全文（字段增减即契约变化） |

**出口点**是函数体里每一个 `throw`、`return`，以及函数末尾的隐式返回。每个出口点记录：

- `kind`：`throw` / `return` / `fallthrough`。
- `path`：从函数入口到该出口的条件链，每段是“条件表达式的规范化文本 + 分支”。分支取 `then` / `else`、`catch`、`case <值>`；`return a ? b : c` 拆成两个出口点，分别带 `a/then`、`a/else`。
- 抛错的出口点：构造器名（`AppError` / `RangeError` / …）和错误码。错误码的提取规则：
  - `new AppError(<码>, …)` 的第一个实参是字符串字面量 → 取字面量；
  - 是同文件顶层 `const` 字符串常量的标识符 → 取常量值；
  - 其他形式（形参、模板字符串、函数调用、属性访问）属动态错误码 → 报 `EVIDENCE_CORE_CONTRACT_DYNAMIC`，失败关闭，不能登记；
  - `throw error` 这类重抛记为 `rethrow`；
  - 消息实参（中文文案）**不进**契约：错误码是机器可读的契约，文案不是（AGENTS.md §10「错误」）。
- 返回的出口点：返回值是 `true` / `false` / `null` / `undefined` 字面量时记下字面量，其他表达式只记“非字面量”。

由此，三类变化都进入契约级复核：错误码替换（码变了）、删除拒绝分支（`throw` 出口点消失）、加旁路返回（多出一个 `return` 出口点）。纯计算细节，例如日期格式化、正则内容、文案，归实现。

**投影是下限，不穷举授权语义。** 出口点和错误码都不变、只改了传给授权器的实参（例如调用前把 `object.update` 改写成 `object.view`）时，投影不变，只报 `EVIDENCE_CORE_STALE`。这类变化靠 suite 的“实参原样传递”断言杀死（§2.5），不靠投影。

### 2.5 专项检查由门禁亲自执行，并杀死变异体（修 P3「必做反例要实际运行」）

- 每个核心的 `suite` 是测试目录内的函数，例如 `tests/acceptance/support/route-policy/core-suites.ts#requirePermissionSuite`。它接收被测实现（核心入口模块的导出），返回失败的断言列表，不依赖 vitest 的 `it`。
- 门禁测试调用 `checkCore()`，也就是现有 `AC-PRM-FW-02-evidence` 全表“零发现”那条用例：
  1. 对真实实现跑 `suite`，必须零失败；
  2. 对每个 `mutant` 跑变异运行器（见下），`kill: 'required'` 却全部通过 → `EVIDENCE_CORE_TESTS`（变异体存活）；`kill: 'not-required'` 必须带非空 `equivalence`，否则 `EVIDENCE_CORE_TESTS`；
  3. 对每个 `mutant` 再用补丁读取器跑一次门禁分类，结果必须与 `expect` 一致。

**变异运行器：保证核心实际加载变异后的依赖。**

1. 求**模块集合**：从核心入口文件出发，沿全部静态 / 字面量动态 import 与转导出，收集仓库内的文件。白名单依赖所在文件、转导出的中间文件、边界内被核心引用的文件（如 `errors.ts`）都在集合里。第三方包不在集合里。
2. 新建临时目录（`fs.mkdtempSync(os.tmpdir())`），把集合里的每个文件按仓库相对路径原样布局；只对 `mutant.file` 应用 `find → replace`，`find` 必须恰好匹配一次，否则 `EVIDENCE_CORE_TESTS`。
3. 用 `ts.transpileModule` 把每个文件编译成 `.mjs`，改写导入说明符：
   - 集合内的相对导入与 `@italent/*` 工作区导入 → 临时目录里对应的 `.mjs`；
   - 第三方包 → 以仓库根为基准 `createRequire` 解析出的绝对路径。
   这样整套变异模块图与 vite / tsx 的转换无关，核心入口只能加载临时目录里的副本。
4. **加载哨兵**：在被变异的文件末尾注入 `globalThis.__f072Loaded?.add('<mutant.id>')`。导入核心入口后，若哨兵集合里没有这个 id，就报 `EVIDENCE_CORE_TESTS`（“变异未被核心加载”），不把这次运行算作“已杀死”或“存活”。
5. 每个变异体用独立的临时目录与独立的模块 URL（带 `?mutant=<id>` 查询串），避免模块缓存串用；运行结束删除临时目录。
6. **未变异控制组**（#176 第 3 轮 P3）：每个核心先用同一套流程复制、编译出一份**不做任何替换**的模块图（哨兵 id 为 `control`），对它跑 suite，必须零失败。控制组失败就报 `EVIDENCE_CORE_TESTS`（“复制环境与真实环境不一致”），该核心本轮的变异结果一律不计。这能挡住“复制环境本身导致的假杀死”。例如复制后的 `AppError` 与真实模块里的 `AppError` 是两个不同的构造器：suite 若拿真实模块的类做 `instanceof`，正确的 `FORBIDDEN` 也会判失败，看起来像“变异被杀死”。
7. **suite 不得引用真实模块里的类**：suite 签名为 `suite(impl, ctx)`，`ctx` 由运行器从**同一份模块图**取出被测实现依赖的类与常量（如 `ctx.AppError`）；判错误优先比 `code` / `name`，必须用 `instanceof` 时只用 `ctx` 里的类。对真实实现跑时，`ctx` 取自真实模块。suite 的测试闭包里出现从真实 `errors.ts` 等文件直接导入的类，报 `EVIDENCE_CORE_TESTS`。
8. 需要数据库的检查不进变异运行，只放在 `supporting`。
- **跳不过**：专项检查不是单独的 `it`，而是在门禁用例里执行，跳过它就等于跳过整个证据门禁，这本身违反 AGENTS.md §3.6，审查可见。suite 文本及其描述链出现 `.skip`、`.todo`、`.only`、`skipIf`、`runIf`、`fails`，或提前 `return`，都报 `EVIDENCE_CORE_TESTS`。
- **helper / setup 变化可见**：`tests` 摘要覆盖以下内容，任一项变化都报 `EVIDENCE_CORE_TESTS`，只能经 §2.7 审定：
  - 用 B-02 闭包算法求出的 suite 测试闭包（含绑定指纹），包含它导入的 helper，覆盖到测试目录；变异运行器自身的模块（`core-mutants.ts`）及其闭包也在内；
  - `vitest.config.ts` 全文：新增 `setupFiles` / `globalSetup`、改 `include` 都会变；
  - 配置里实际登记的每个 `setupFiles` / `globalSetup` 文件：整文件文本（含顶层副作用语句），加上从它出发的 import 闭包（同样按模块集合收集，含绑定指纹）。现状两者都没有配置；一旦配置，其内容变化同样可见；
  - `mutants` 清单（含 `kill` 与 `equivalence`）；
  - `supporting` 各 `it` 块。
- `supporting` 是已有的外部测试，只跟踪摘要，不承担杀变异：
  - `tenant-time`：`packages/domain/src/tenant-time.test.ts`、`AC-TEN-05`、`AC-TRF-32-AC-TEN-05-timezone`、`AC-R1-E2E-01-transfer-closure`（生效日落地）；

suite 内容（PR-3b）：

- `requirePermissionSuite`：

## 3. 集中报告：数据结构与 `EVIDENCE_STALE` 输出形态（②）

本节建在 PR-1 已落地的**登记直接图**上（§4、§6）。旧的传递闭包恢复不出直接边：导入从同一辅助函数 A 重绑定到另一个 B（`R→A` 变为 `R→A,B`，两边都有 `A→B`）时，根摘要、依赖摘要和闭包完全不变，直接边却变了。

### 3.1 记号

| 记号 | 含义 |
|---|---|
| `G_reg` / `G_cur` | 登记的直接图 / 由当前源码算出的直接图（节点 → 直接依赖集合；根也是节点） |
| `D_reg` / `D_cur` | 登记的 / 当前的节点摘要（证据单元自身的摘要另记为 `U_reg` / `U_cur`，即 `units.ts`） |
| `B_reg` / `B_cur` | 登记的 / 当前的绑定指纹（§2.3.2，普通图的每个节点与根都有） |
| `Cl_G(r)` | 在图 `G` 上从根 `r` 做广度优先（同一 `MAX_DEPTH`）得到的闭包节点集；节点集合与遍历顺序无关 |
| `R_G(x)` | `{ r : x ∈ Cl_G(r) 或 x = r }`，在**单个快照**上求 |

### 3.2 变更识别与分组

变更节点集合 `C = Δd ∪ Δe ∪ Δb ∪ Δr`，其中：

- `Δd`：两边都有、但 `D_reg[x] ≠ D_cur[x]` 的节点；
- `Δe`：`G_reg(x) ≠ G_cur(x)` 的节点（按集合比较；只在一边存在的节点，另一边的邻接视为空集）；
- `Δb`：两边都有、但 `B_reg[x] ≠ B_cur[x]` 的节点（别名交换、重绑定到已有目标、转导出改指：邻接集合可能不变）；
- `Δr`：证据单元自身摘要变化或未登记，即 `U_reg[r] ≠ U_cur[r]`（沿用现有逐单元报告）。362 个只作根、不作依赖的单元（如 `route:` 处理函数）只会落在这里。

每个 `x ∈ C` 出**一条** `EVIDENCE_STALE`。影响集合为 **`impacts(x) = R_reg(x) ∪ R_cur(x)`：两个快照各自求可达，再取并**。不在并图 `G_reg ∪ G_cur` 上求可达，因为并图会拼出两个快照里都不存在的路径。例：旧图 `R→A→Y`，新图 `R→B→Y` 且新增 `A→X`；并图会误判 R 能到 X，而分快照求，R 在两边都到不了 X。

链怎么选：

- 根 `r` 在当前图里仍能到 `x`，就用 `G_cur` 上的最短链；
- 否则用 `G_reg` 上的最短链。

判断依据是“该根是否仍可达”，不是“节点是否已删除”。

```ts
interface StaleGroup {
  readonly node: string;                                   // 变更节点
  readonly kinds: readonly ('digest' | 'edge' | 'binding' | 'root')[];
  readonly added?: readonly string[];                      // G_cur(x) \ G_reg(x)
  readonly removed?: readonly string[];                    // G_reg(x) \ G_cur(x)
  readonly impacts: readonly Impact[];                     // 完整，不截断，按 route、label 排序
}
interface Impact {
  readonly root: string;
  readonly snapshot: 'cur' | 'reg';                        // 链取自哪个快照
  readonly chain: readonly string[];
  readonly uses: readonly Use[];                           // 该证据单元的全部义务 / 登记项
  readonly self: boolean;                                  // root = node 且 node ∈ Δr：证据单元自身变化
  readonly closureChanged: boolean;                        // 见 §3.4 归因；只是标注，不是分组存在的条件
}
// compare.ts 的 Finding 新增可选字段：readonly group?: StaleGroup
```

输出形态（`route: '*'`，与 `EVIDENCE_UNUSED` 一致；文本明细 + 结构化 `group`）：

```
EVIDENCE_STALE *  依赖 packages/domain/src/qualification/catalog.ts#levelRank 已变化（摘要）。
  受影响 341 个证据单元 / 612 条义务，逐条复核：
  - POST /api/tenant/qualification/... #1 obj:qualification:update  链(cur)：route:POST … → assess → levelRank
  - …（全部列出，不截断）
EVIDENCE_STALE *  依赖 apps/api/src/modules/x/helpers.ts#pick 的直接依赖变化：+ helpers.ts#pickB。
  受影响 12 个证据单元 / 15 条义务（其中 0 个闭包集合变化：仅绑定 / 路径变化）……
EVIDENCE_STALE *  证据单元 apps/api/src/modules/tenant-settings/routes.ts#route:GET /api/tenant/settings/:key 自身已变化。
  受影响 1 个证据单元 / 1 条义务（证据单元自身变化，依赖闭包未变）：
  - GET /api/tenant/settings/:key #1 admin:other_settings
```

规则：

1. **一个节点一条**。一次改动涉及 N 个节点就出 N 条；同一证据单元出现在多条里是正确的。
2. `Δr` 的节点若同时在 `Δd ∪ Δe ∪ Δb`（证据单元也是别人的依赖），合并成一条，`kinds` 同时含 `root`。只在 `Δr` 的节点（纯根变化）单独成组：`kinds = ['root']`，`impacts` 只有它自己（`self = true`，`closureChanged = false`），文本写“证据单元自身变化”。
7. 组内所有 impact 的 `closureChanged` 都是 `false` 时，文本按种类说明原因：`root` 组写“证据单元自身变化”；`edge` / `binding` 组写“仅绑定 / 路径变化”；`digest` 组写“该节点只在一侧快照可达，闭包变化见对应的边变化组”。
3. 不截断。旧实现“前 5 处 + 共 N 处”删掉；完整清单放在 `group.impacts`，文本明细同样全列。
4. 核心节点（终端节点）在普通图里不展开，所以不会出普通的 `EVIDENCE_STALE`；它们的变化只由 §2.7 的门禁码报告。核心单元若同时是证据单元（如 `requirePermission`），根自身的 `root` 报告照出，两者各自消除。
5. `EVIDENCE_CLOSURE_UNRESOLVED`、`EVIDENCE_UNIT`、`EVIDENCE_ANCHOR`、`EVIDENCE_MISSING`、`TABLE_CONFLICT`、`EVIDENCE_UNUSED` 不变。
6. “依赖牵连的义务数分布”改为从 `R_cur` 计算，顺带消除 #165 指出的统计去重问题。

### 3.3 旧逐根算法（oracle）

`legacyStaleOf(G_reg, G_cur, D_reg, D_cur)` 只在测试里使用，产出三元组集合 `L`：

- `(r, y, added)`：`y ∈ Cl_cur(r) \ Cl_reg(r)`；
- `(r, y, removed)`：`y ∈ Cl_reg(r) \ Cl_cur(r)`；
- `(r, y, changed)`：`y ∈ Cl_reg(r) ∩ Cl_cur(r)`，且 `D_reg[y] ≠ D_cur[y]`。

另有根自身变化集合 `L_root = { r : U_reg[r] ≠ U_cur[r] 或 r 未登记 }`，对应现行逐单元报告的“X 已变化 / 未登记摘要”（#176 第 2 轮 R2-2：v2 的 oracle 漏了这一类）。

PR-1 已证明：由 `G_reg` 推出的 `Cl_reg(r)` 与旧 `DEPENDENCIES[r]` 的键集合**逐根相等**，摘要也相等（686 个根）。所以 `L` 就是 main 上现行算法会报的全部“根 × 依赖”变化，只是不截断。

### 3.4 精确等价关系（审查补定的技术点二）

**归因**：三元组 `(r, y, k)` 归因到变更节点 `x`，当且仅当满足下面之一：

- `k = changed`，且 `x = y`；
- `k = added`，`x ∈ Δe`，`r ∈ R_cur(x)`，且存在 `t ∈ added(x)`，使 `y = t` 或 `y ∈ Cl_cur(t)`。`r → … → x` 在 `G_cur` 上的最短链必须在 `MAX_DEPTH` 内，按 `snapshot: 'cur'` 的链长判定；
- `k = removed`：与上一条对称，用 `removed(x)`、`R_reg`、`Cl_reg`。

**oracle 断言**（PR-2 合并门槛），对夹具与真实表上的每一次变异都成立：

| 断言 | 内容 |
|---|---|
| A1 完整 | `L` 中每个三元组都至少归因到一个 group，且该 group 的 `impacts` 里有这个 `r`，`closureChanged = true`；`L_root` 中每个 `r` 都恰有一个 `node = r`、`kinds ∋ root` 的 group，其中 `r` 的 impact `self = true` |
| A2 逐条可靠 | 每个 group 的**每一条** impact 都满足 `r ∈ R_reg(x) ∪ R_cur(x)`。用独立实现的朴素深度优先搜索分别在两个快照上复算，不复用被测代码 |
| A3 标注正确 | `impact.closureChanged = true`，当且仅当 `L` 中存在归因到 `(x, r)` 的三元组；`impact.self = true`，当且仅当 `r = x` 且 `x ∈ L_root` |
| A4 无凭空分组 | 每个 group 的 `node ∈ C`，且 `kinds` 与 `node` 所属集合一一对应（`digest ⇔ Δd`、`edge ⇔ Δe`、`binding ⇔ Δb`、`root ⇔ Δr`）。**不要求**组内至少一条 `closureChanged = true`：纯根变化、仅绑定 / 路径变化、只在一侧可达的摘要变化都是合法分组，按 §3.2 规则 7 写明原因 |
| A5 其他发现 | 除 `depth-limit` 外的 `unresolved` 集合与旧算法相等；`depth-limit` 按 §8 D-8 的选择：选①时满足 §4.1 的“新集合 ⊆ 旧集合，差集每一项都满足 `G(x) ⊆ V(r)`（`V(r) = {r} ∪ Cl(r)`，含根自身）”，选②时与旧算法相等 |

A1 的依据：`y` 新进入 `Cl(r)` 时，`G_cur` 上从 `r` 到 `y` 的最短路径中，至少有一条边不在 `G_reg` 里（否则 `y ∈ Cl_reg(r)`）。取这条路径上第一条新边，它的起点就是 `x`。删除的情形对称。深度上限的边界情况（路径缩短后才进入上限内）用 §6 测试 9 的 40 / 41 层夹具覆盖。`L_root` 与 `Δr` 由同一个“证据单元摘要比较”产生，A1 的根部分按定义成立；测试 12b 用纯根变化验证。

## 4. `digests.ts` 的存储拆分（③）

### 4.1 新结构

```
required/digests/
  units.ts        // DIGESTS：证据单元（根）→ 摘要；686 行，与现在同形
  nodes.ts        // NODE_DIGESTS：依赖节点 → 摘要；每个节点一行（3,411 行）

  index.ts        // 汇总导出（手写，固定）
required/core-digests.ts   // §2.3，独立生成命令（PR-3a 起）
```

- 区域划分：`domain-<子目录>`、`api-modules-<模块>`、`api-root`（`apps/api/src/*.ts`）、`tests`（选择器绑定表的证据单元若在测试目录）。模块内的改动只碰本模块的 graph 文件；共享依赖改实现只改 `nodes.ts` 1 行。
- 闭包在校验时由 `GRAPH` 推出，**不再存平铺闭包**。
- **`depth-limit` 与遍历顺序**（#176 第 2 轮 R2-3、第 3 轮 R3-1）：现行 `closureOf` 在第 `MAX_DEPTH` 层处理节点 `x` 时，只要 `x` 有“当时还没访问过”的依赖就报 `depth-limit`。同层里先处理谁，结果就可能不同。审查反例：`R → n01 → … → n39 → {z40, a40}`，`z40 → a40`。按源码顺序先处理 `z40`，此时 `a40` 尚未访问，报 `z40`；按字典序先处理 `a40`，`z40` 就不报。而 `a40` 本来就在闭包里，`z40` 后面其实没有漏掉任何东西，旧报告是**顺序相关的误报**。按 §8 D-8 二选一：
  - **① 建议：改成与顺序无关的定义**。记**实际访问集合** `V(r) = {r} ∪ Cl(r)`：B-02 从 `visited = {r}` 开始，根自己不属于 `Cl(r)`，但从一开始就算“已访问”（#176 第 3 轮 R3-1：只看 `Cl(r)` 会把回指根的边误判为越界）。定义 `depth-limit(r) = { x : x 在第 MAX_DEPTH 层，且 G(x) 中有节点 ∉ V(r) }`，即 `x` 确有依赖落在上限之外。登记图与遍历都按字典序。
    - **新 ⊆ 旧**：设 `y ∈ G(x)` 且 `y ∉ V(r)`。`y` 自始至终没被访问过，旧算法处理 `x` 时 `y` 必然是“当时还没访问过”的依赖，所以旧算法也报 `x`。
    - **差集确属误报**：旧算法报了而新定义不报的 `x`，满足 `G(x) ⊆ V(r)`。旧算法在处理节点时才标记已访问，第 `MAX_DEPTH − 1` 层及以上的节点在处理第 `MAX_DEPTH` 层之前都已标记，根一开始就标记。所以处理 `x` 时仍未访问、最终却在 `V(r)` 里的依赖，只能是同在第 `MAX_DEPTH` 层、排在 `x` 后面的节点。`x` 后面并没有漏掉任何东西。
    - 等价门槛 A5 写成这个包含关系，并逐根、逐项校验差集确属误报（`G(x) ⊆ V(r)`）。
    - 闭包节点集合与最大深度不受影响；等长最短链的取舍会与现在不同，链只是说明信息。现状真实表最大深度 27，两种定义下 `depth-limit` 都是空集；
  - **② 保留旧诊断**：登记图按引擎的源码遍历顺序存邻接（不排序），遍历按登记顺序走，`depth-limit` 与链都与现在逐位相同。`Δe` 仍按集合比较；只改顺序的变化不报发现，但重算后文件会有顺序 diff。
  - 两种做法都不再声称“只改说明链且 `depth-limit` 恒等”。测试 5c 与 9 增加审查反例这类“上限层同层交叉边”夹具，按所选口径断言。
- 核心门禁节点在图里记为**终端节点**：保留入边、不展开、不登记摘要（§2.3.1 第 6 点）。原有 4 条非门禁边界照旧不记入边；D-2 选“统一门禁”后一并记。
- **绑定指纹**：`nodes.ts` 每个节点存两列，`digest`（与旧 `DEPENDENCIES` 同算法，供等价测试）和 `bindings`（§2.3.2 清单的摘要）；根的绑定指纹存在 `units.ts` 第二列。别名交换这类“邻接集合与文本都不变”的重绑定，**在 main 的普通闭包里同样发现不了**；F-072 用同一套指纹一并补上（`Δb`），检测只增不减。
- **普通图绑定变化的旧明细从哪来**：普通图只存指纹摘要，不存完整清单（全量清单会把登记体积再翻一倍左右，抵消 §4.2 的收益）。摘要恢复不出旧清单，所以分两处给明细：
  - 测试里的 `EVIDENCE_STALE`（`Δb`）列出**当前**的完整绑定清单，并写明“旧清单用 `explain-graph-diff` 查看”；
