### 2.3 核心摘要门禁（独立于义务摘要）

新增手写登记 `support/route-policy/evidence-core.ts` 与生成文件 `required/core-digests.ts`：

```ts
// evidence-core.ts（手写，审查对象）
interface CoreEntry {
  readonly id: 'tenant-time' | 'require-permission' | 'system-actor';
  readonly boundary: string;               // 对应的 EVIDENCE_BOUNDARY 条目
  readonly units: readonly string[];       // 实现单元：边界覆盖范围内的全部顶层声明（含私有辅助与常量）
  readonly contract: readonly string[];    // 契约单元：导出签名、导出常量值、入参类型（见下）
  readonly tests: readonly CoreTest[];     // 专项测试：文件 + it 标题（锚点）
  readonly reason: string;
}
interface CoreTest { readonly file: string; readonly title: string }

// required/core-digests.ts（生成，但不由 ROUTE_POLICY_UPDATE_DIGESTS 写）
interface CoreDigest {
  readonly implementation: string;  // units 规范化文本的摘要
  readonly contract: string;        // contract 规范化文本的摘要
  readonly tests: string;           // tests 各 it 块规范化文本的摘要
  readonly review: string;          // 最近一次审定说明（非空），随 diff 进 PR 评审
}
```

契约的定义（逐项，§8 D-4 确认）：

| 核心 | 契约（变了 = 展开全部义务） | 实现（变了 = 集中审定一次） |
|---|---|---|
| `tenant-time` | 4 个导出函数的签名（名字、参数类型、返回类型）、`DEFAULT_TENANT_TIMEZONE` 的值、`IsoDate` 类型 | 整文件：`IANA_NAME`、`ISO_DATE`、各函数体、`assertIsoDate` |
| `require-permission` | `requirePermission` 签名、`Authorizer` 与 `AuthorizationRequest` 类型声明（字段增减即契约变化）、抛出的错误码 `FORBIDDEN` | `requirePermission` 函数体 |
| `system-actor` | `SYSTEM_USER_ID` 的值、`auditActor` 签名 | `auditActor` 函数体 |

签名取法：对契约单元做 TS AST 投影——函数只取 `名字 + 参数列表 + 返回类型`（丢函数体），常量取 `名字 + 初始化文本`，类型声明取全文；再走 `normalize()` 求摘要。契约摘要是**下限**：签名不变但语义变了（如 `requirePermission` 不再抛错）仍是“实现变化”，靠集中审定与专项测试兜住，不会被放过。

门禁的输出与处置：

| 发现码 | 触发 | 输出 | 怎么消 |
|---|---|---|---|
| `EVIDENCE_CORE_STALE` | 实现摘要变、契约摘要没变 | **一条**：核心 id、变化的实现单元、专项测试清单、受影响证据单元 / 义务**计数**（完整清单附在 `impacts` 字段，见 §3.2） | 跑并审专项测试 → `ROUTE_POLICY_UPDATE_CORE=<id> ROUTE_POLICY_CORE_REVIEW='<审定说明>'` 只重写该核心的 `implementation` 与 `review` |
| `EVIDENCE_CORE_CONTRACT` | 契约摘要变 | **一条**，`impacts` 展开全部受影响义务（与 §3 同构，不截断），明细写“契约变化：逐条复核” | 逐条复核义务 → 同上命令另加 `ROUTE_POLICY_CORE_CONTRACT=changed`，否则拒写 |
| `EVIDENCE_CORE_TESTS` | 专项测试的文件 / `it` 标题找不到，或测试块摘要变化（测试被删弱） | 一条，点名测试 | 恢复测试，或审定后 `ROUTE_POLICY_UPDATE_CORE=<id>` 重写 `tests`（同样要说明） |
| `BOUNDARY_CORE_MISSING` | 边界条目没有核心登记（§2.1） | 一条 | 补登记或移出边界 |

“不能静默刷新”的保证（实现时逐条有测试，§6）：

1. `ROUTE_POLICY_UPDATE_DIGESTS=1` **不写** `core-digests.ts`；执行后核心发现仍在，测试仍红。
2. `ROUTE_POLICY_UPDATE_CORE` 必须同时给出非空 `ROUTE_POLICY_CORE_REVIEW`；契约变化还必须 `ROUTE_POLICY_CORE_CONTRACT=changed`；不满足即抛错、不写文件。
3. 一次只能更新一个核心 id；`review` 文本写进生成文件，评审在 diff 里看得到“谁以什么理由审定”。
4. PR 描述模板加一行“核心门禁变化：无 / `<id>`：实现 | 契约 | 测试，审定说明……”；审查清单（AGENTS.md §9）由总编排决定是否加一条（§8 D-5）。

## 3. 集中报告：数据结构与 `EVIDENCE_STALE` 输出形态（②）

### 3.1 计算

校验时建两张反向索引（与旧算法同一份闭包计算，不新增解析）：

- `rootsOf(node)`：依赖节点 → 能走到它的证据单元（在**当前图 ∪ 登记图**上求，删掉的边也能找到受影响者）；
- `usesOf(root)`：证据单元 → 引用它的义务 / 选择器登记（已有）。

变更以**节点**为单位识别（不再以“根 × 依赖”为单位）：

| 变更种类 | 判定 |
|---|---|
| `digest` | 节点在登记与当前都存在，摘要不同 |
| `edge+` / `edge-` | 节点的直接依赖集合增 / 减（明细列出增减的目标） |
| `node+` | 当前图有、登记图没有的节点（由某个 `edge+` 引入，归并到引入它的那条） |
| `node-` | 登记图有、当前图没有（归并到删掉它的 `edge-`） |
| `root` | 证据单元本身摘要变化 / 未登记（保持现有逐单元报告） |

### 3.2 输出

`Finding` 增加可选的结构化字段（`compare.ts`，只在测试框架内）：

```ts
interface StaleGroup {
  readonly node: string;                         // 变更的依赖节点（或核心 id）
  readonly kinds: readonly ('digest' | 'edge+' | 'edge-' | 'root')[];
  readonly added?: readonly string[];            // edge+ 的目标
  readonly removed?: readonly string[];          // edge- 的目标
  readonly impacts: readonly Impact[];           // 完整反向影响清单，不截断，按 route、label 排序
}
interface Impact {
  readonly root: string;                         // 受影响的证据单元
  readonly chain: readonly string[];             // root → … → node 的最短链（当前图；节点已删则用登记图）
  readonly uses: readonly Use[];                 // 该证据单元的全部义务 / 登记项
  readonly closureChanged: boolean;              // 该根的闭包集合是否真的变了（区分“只是路径变”）
}
// Finding 新增：readonly group?: StaleGroup
```

一条 `EVIDENCE_STALE` 的形态（`route: '*'`，与 `EVIDENCE_UNUSED` 一致；文本明细 + 结构化 `group`）：

```
EVIDENCE_STALE *  依赖 packages/domain/src/qualification/catalog.ts#levelRank 已变化（摘要）。
  受影响 341 个证据单元 / 612 条义务，逐条复核：
  - POST /api/tenant/qualification/... #1 obj:qualification:update  链：route:POST … → assess → levelRank
  - …（全部列出，不截断）
```

规则：

1. **一个节点一条**。一个提交改了 N 个节点就出 N 条；同一证据单元出现在多条里是正确的（它确实被多个变化牵连）。
2. 根自身变化（`root`）与它作为别人依赖的变化合并成一条（同一节点只出一条，`kinds` 同时含 `root` 与 `digest`）。
3. 不截断：旧实现“前 5 处 + 共 N 处”删掉；完整清单放 `group.impacts`，文本明细同样全列（测试失败输出会长，这是代价，换来不漏）。
4. 核心门禁的发现（§2.3）与依赖发现分开出，核心节点不会再以 `EVIDENCE_STALE` 重复报。
5. `EVIDENCE_CLOSURE_UNRESOLVED`、`EVIDENCE_UNIT`、`EVIDENCE_ANCHOR`、`EVIDENCE_MISSING`、`TABLE_CONFLICT`、`EVIDENCE_UNUSED` 不变。
6. 现有“依赖牵连的义务数分布”输出（`AC-PRM-FW-02-evidence` 全表用例）改为从 `rootsOf` 计算，顺带消除 #165 指出的统计去重问题。

### 3.3 不减少检测范围：等价 oracle

保留旧的逐根比较作为测试内 oracle（`legacyStaleOf(table, registered, current)`，只在测试里用），断言：

- **覆盖**：旧算法报出的每一个（根, 依赖, 变化）三元组，都落在新输出某条 `group` 的 `impacts` 里（`root` 相同，且该 group 的 `node` 是该依赖或其在链上的直接改动处）；
- **不多余**：新输出每条 `group` 至少对应一个旧三元组，或是 `closureChanged=false` 的“只是路径变”（显式标出，不当作新问题）；
- 夹具：B-02 已有的 7 个闭包反例（`levelOf` 恒返 detail、依赖增 / 减、多余登记……）全部过一遍；真实表上用补丁读取器随机改 30 个节点（固定种子）跑一遍。

## 4. `digests.ts` 的存储拆分（③）

### 4.1 新结构

```
required/digests/
  units.ts       // DIGESTS：证据单元（根）→ 摘要；686 行，与现在同形
  nodes.ts       // NODE_DIGESTS：依赖节点 → 摘要；每个节点一行（约 3,411 行）
  graph/<区域>.ts // GRAPH：节点（含根）→ 直接依赖列表；按节点所在区域分文件
  index.ts       // 汇总导出（手写，固定）
required/core-digests.ts  // §2.3，独立生成命令
```

- 区域划分：`domain-<子目录>`、`api-modules-<模块>`、`api-root`（`apps/api/src/*.ts`）。模块内的改动只碰本模块的 graph 文件；共享依赖改实现只改 `nodes.ts` 1 行。
- 闭包在校验时由 `GRAPH` 推出（与 `closureOf` 同一 BFS、同一 `MAX_DEPTH`），**不再存平铺闭包**。
- 核心门禁节点在图里记为**终端节点**（有入边、不展开、不登记摘要），用于 `EVIDENCE_CORE_CONTRACT` 的反向展开；旧的 4 条非门禁边界照旧不记入边（D-2 选“统一门禁”则一并记）。
- 键排序固定（节点按字典序、邻接按字典序），生成后跑 prettier；行宽仍由 `eslint-disable max-len` 豁免（生成文件）。

### 4.2 改善预估

| 指标 | 现在 | 拆分后（估算） |
|---|---|---|
| 依赖登记体积 | 6.9 MB（单文件） | `nodes.ts` 约 0.28 MB + `graph/*` 约 0.5～0.8 MB，合计约 1.1 MB（−84%） |
| 依赖登记行数 | 约 8.5 万行 | 约 1.5 万行 |
| 改一个被 380 个单元引用的共享函数的实现 | 约 380 行散落在 380 个块里 | 1 行（`nodes.ts`） |
| 共享函数新增一个直接依赖 | 约 380 个块各加 1 行 | 该节点邻接 1 处 + 新节点 1 行 |
| 两个不同模块的补表 PR 并行 | 同一文件大面积交错，几乎必冲突 | 各碰各的 `graph/api-modules-<模块>.ts` 与 `units.ts` 的不同行；`nodes.ts` 只在新增节点时冲突（按字典序插行，冲突面小） |

冲突处理规则不变：生成文件冲突一律“取任一侧 → `ROUTE_POLICY_UPDATE_DIGESTS=1` 重算 → prettier”，并核对**摘要值**没有意外变化（只应有新增）。`core-digests.ts` 冲突不得重算了事，须按 §2.3 重新审定。
