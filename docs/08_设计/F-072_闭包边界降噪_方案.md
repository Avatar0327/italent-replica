#### 2.3.1 核心的传递依赖由谁跟踪（审查补定的技术点一）

**结论：核心门禁独占跟踪核心实现的完整依赖闭包；普通依赖图在核心处截断，不再展开。**

1. 核心闭包的算法与 B-02 相同：从 `units` 出发求闭包，**只把本核心自己的条目从边界里拿掉**。闭包走到其他边界条目时停下：原有 4 条，以及其他核心（各核心由各自的门禁负责）。
2. 闭包结果按依赖单元的**解析后目标**登记（`文件#名字`）。导入绑定从 A 改指向 B 时，`closure` 的键集合会变，所以导入重绑定一定会被发现。
3. **白名单，失败关闭**：核心闭包里出现 `deps` 白名单之外的单元，就报 `EVIDENCE_CORE_DEPENDENCY`。核心闭包里出现**任何** unresolved，不论位于哪个目录，也报 `EVIDENCE_CORE_DEPENDENCY`。存在这两类发现时，`ROUTE_POLICY_UPDATE_CORE` 拒写；只能手改 `evidence-core.ts` 把依赖登记进白名单，这个改动本身是审查对象。现状 3 个核心的白名单都是空的：它们只依赖本文件声明，以及边界内的 `errors.ts#AppError`。
4. 白名单依赖的摘要任何变化（辅助函数改了），都报 `EVIDENCE_CORE_STALE`，并点名变化的依赖与链。普通刷新不写 `core-digests.ts`，所以消不掉它。
5. 同一个辅助函数也可能经别的非核心路径被证据单元引用。这时它同时出现在普通图（只算那些路径上的根）和核心闭包里，两边各报各的、各消各的：普通刷新只能消普通那条。
6. 普通图只把核心记成**终端节点**：保留入边、不展开、不登记摘要。终端节点只用于 `EVIDENCE_CORE_CONTRACT` 的反向展开（§4.1）。

审查给的两步反例（第 2 步只改辅助文件），在本设计下的走法：

| 步骤 | 改动 | 门禁输出 | 普通刷新后 |
|---|---|---|---|
| 1 | `tenantLocalDate` 的格式化逻辑提取到 `packages/domain/src/tz-format.ts#formatLocalDate` | `EVIDENCE_CORE_DEPENDENCY`（新依赖不在白名单）+ `EVIDENCE_CORE_STALE`（`units` 文本变） | 仍在。须把依赖登记进白名单，再按 §2.7 审定 |
| 2 | 只改 `tz-format.ts`：把 `Pacific/Honolulu` 按 UTC 算（`2026-10-09T05:00Z` 本地日期从 10 月 8 日错成 10 月 9 日） | `EVIDENCE_CORE_STALE`，点名 `tz-format.ts#formatLocalDate` 已变化，链为 `tenantLocalDate → formatLocalDate` | 仍在；同时 suite 对该变异实现失败（§2.5），门禁测试红 |

### 2.4 契约投影：签名 + 出口点（修 P2-2）

契约单元逐个投影，再走 `normalize()` 求摘要。投影内容只有下表几类，函数体里的其他内容一律算“实现”：

| 契约单元种类 | 投影内容 |
|---|---|
| 函数 | 名字、参数列表（含类型）、返回类型；加上**全部出口点** |
| 常量 | 名字 + 初始化文本 |
| 类型 / 接口 | 全文（字段增减即契约变化） |

**出口点**是函数体里每一个 `throw`、`return`，以及函数末尾的隐式返回。每个出口点记录：

- `kind`：`throw` / `return` / `fallthrough`。
- `path`：从函数入口到该出口的条件链，每段是“条件表达式的规范化文本 + 分支”。分支取 `then` / `else`、`catch`、`case <值>`；`return a ? b : c` 拆成两个出口点，分别带 `a/then`、`a/else`。
- 抛错的出口点：构造器名（`AppError` / `RangeError` / …）和错误码。错误码的提取规则：
  - `new AppError(<码>, …)` 的第一个实参是字符串字面量 → 取字面量；
  - 是同文件顶层 `const` 字符串常量的标识符 → 取常量值；
  - 其他形式（形参、模板字符串、函数调用、属性访问）属动态错误码 → 报 `EVIDENCE_CORE_CONTRACT_DYNAMIC`，失败关闭，不能登记；
  - `throw error` 这类重抛记为 `rethrow`；
  - 消息实参（中文文案）**不进**契约：错误码是机器可读的契约，文案不是（AGENTS.md §10「错误」）。
- 返回的出口点：返回值是 `true` / `false` / `null` / `undefined` 字面量时记下字面量，其他表达式只记“非字面量”。

由此，三类变化都进入契约级复核：错误码替换（码变了）、删除拒绝分支（`throw` 出口点消失）、加旁路返回（多出一个 `return` 出口点）。纯计算细节，例如日期格式化、正则内容、文案，归实现。

统一后的分类（取代 v1 测试 12～15；每一行都是 §6 PR-3b 的必做反例，用补丁读取器做门禁分类，同时用变异体实际运行 suite）：

| 变异 | 门禁分类 | suite 必须杀死 |
|---|---|---|
| `requirePermission`：`throw` 改成 `return`（不再抛） | `EVIDENCE_CORE_CONTRACT`（`throw` 出口点消失） | 是 |
| `requirePermission`：`FORBIDDEN` 改成 `NOT_FOUND` | `EVIDENCE_CORE_CONTRACT`（错误码变） | 是 |
| `requirePermission`：入口加 `if (request.action === 'x') return;` | `EVIDENCE_CORE_CONTRACT`（新增出口点） | 是 |
| `requirePermission`：去掉 `await`（Promise 恒为真值） | `EVIDENCE_CORE_CONTRACT`（条件文本变） | 是 |
| `requirePermission`：错误码改成取自变量 | `EVIDENCE_CORE_CONTRACT_DYNAMIC` | —（不能登记） |
| `requirePermission`：只改中文文案 | `EVIDENCE_CORE_STALE` | 否（等价变异，登记为 `expect: 'stale'` 并注明不要求杀死） |
| `tenant-time`：`IANA_NAME` 放宽为接受 `+08:00` | `EVIDENCE_CORE_STALE` | 是（偏移写法必须被拒） |
| `tenant-time`：`isValidTimeZone` 的 `catch` 分支 `return false` 改 `true` | `EVIDENCE_CORE_CONTRACT`（字面量返回变） | 是 |
| `tenant-time`：`DEFAULT_TENANT_TIMEZONE` 改值 | `EVIDENCE_CORE_CONTRACT` | 是 |
| `tenant-time`：§2.3.1 两步反例的第 2 步 | `EVIDENCE_CORE_STALE`（白名单依赖变化） | 是（Honolulu 用例） |

### 2.5 专项检查由门禁亲自执行，并杀死变异体（修 P3「必做反例要实际运行」）

- 每个核心的 `suite` 是测试目录内的函数，例如 `tests/acceptance/support/route-policy/core-suites.ts#requirePermissionSuite`。它接收被测实现，返回失败的断言列表，不依赖 vitest 的 `it`。
- 门禁测试调用 `checkCore()`，也就是现有 `AC-PRM-FW-02-evidence` 全表“零发现”那条用例：
  1. 对真实实现跑 `suite`，必须零失败；
  2. 对每个 `mutant`：把 `find → replace` 应用到文件文本（片段必须恰好匹配一次，否则 `EVIDENCE_CORE_TESTS`，防止变异体过期失效），用 `ts.transpileModule` 编译后写到临时目录，相对导入改写为真实文件的绝对路径，再动态 `import`，然后跑 `suite`；`expect` 要求杀死却全部通过 → `EVIDENCE_CORE_TESTS`（变异体存活）；
  3. 对每个 `mutant` 再用补丁读取器跑一次门禁分类，结果必须与 `expect` 一致。

## 3. 集中报告：数据结构与 `EVIDENCE_STALE` 输出形态（②）

本节建在 PR-1 已落地的**登记直接图**上（§4、§6）。旧的传递闭包恢复不出直接边：导入从同一辅助函数 A 重绑定到另一个 B（`R→A` 变为 `R→A,B`，两边都有 `A→B`）时，根摘要、依赖摘要和闭包完全不变，直接边却变了。

### 3.1 记号

| 记号 | 含义 |
|---|---|
| `G_reg` / `G_cur` | 登记的直接图 / 由当前源码算出的直接图（节点 → 直接依赖集合；根也是节点） |
| `D_reg` / `D_cur` | 登记的 / 当前的节点摘要 |
| `Cl_G(r)` | 在图 `G` 上从根 `r` 做广度优先（字典序、同一 `MAX_DEPTH`）得到的闭包节点集 |
| `R_G(x)` | `{ r : x ∈ Cl_G(r) 或 x = r }`，在**单个快照**上求 |

### 3.2 变更识别与分组

变更节点集合 `C = Δd ∪ Δe ∪ Δr`，其中：

- `Δd`：两边都有、但 `D_reg[x] ≠ D_cur[x]` 的节点；
- `Δe`：`G_reg(x) ≠ G_cur(x)` 的节点（按集合比较；只在一边存在的节点，另一边的邻接视为空集）；
- `Δr`：证据单元自身摘要变化或未登记（沿用现有逐单元报告）。

每个 `x ∈ C` 出**一条** `EVIDENCE_STALE`。影响集合为 **`impacts(x) = R_reg(x) ∪ R_cur(x)`：两个快照各自求可达，再取并**。不在并图 `G_reg ∪ G_cur` 上求可达，因为并图会拼出两个快照里都不存在的路径。例：旧图 `R→A→Y`，新图 `R→B→Y` 且新增 `A→X`；并图会误判 R 能到 X，而分快照求，R 在两边都到不了 X。

链怎么选：

- 根 `r` 在当前图里仍能到 `x`，就用 `G_cur` 上的最短链；
- 否则用 `G_reg` 上的最短链。

判断依据是“该根是否仍可达”，不是“节点是否已删除”。

```ts
interface StaleGroup {
  readonly node: string;                                   // 变更节点
  readonly kinds: readonly ('digest' | 'edge' | 'root')[];
  readonly added?: readonly string[];                      // G_cur(x) \ G_reg(x)
  readonly removed?: readonly string[];                    // G_reg(x) \ G_cur(x)
  readonly impacts: readonly Impact[];                     // 完整，不截断，按 route、label 排序
}
interface Impact {
  readonly root: string;
  readonly snapshot: 'cur' | 'reg';                        // 链取自哪个快照
  readonly chain: readonly string[];
  readonly uses: readonly Use[];                           // 该证据单元的全部义务 / 登记项
  readonly closureChanged: boolean;                        // 见 §3.4 归因
}
// compare.ts 的 Finding 新增可选字段：readonly group?: StaleGroup
```

输出形态（`route: '*'`，与 `EVIDENCE_UNUSED` 一致；文本明细 + 结构化 `group`）：

```
EVIDENCE_STALE *  依赖 packages/domain/src/qualification/catalog.ts#levelRank 已变化（摘要）。
  受影响 341 个证据单元 / 612 条义务，逐条复核：
  - POST /api/tenant/qualification/... #1 obj:qualification:update  链(cur)：route:POST … → assess → levelRank
  - …（全部列出，不截断）
EVIDENCE_STALE *  依赖 apps/api/src/modules/x/helpers.ts#pick 的直接依赖变化：+ helpers.ts#pickB。
  受影响 12 个证据单元 / 15 条义务（其中 0 个闭包集合变化：仅绑定 / 路径变化）……
```

规则：

1. **一个节点一条**。一次改动涉及 N 个节点就出 N 条；同一证据单元出现在多条里是正确的。
2. `Δr` 的节点若同时在 `Δd ∪ Δe`（证据单元也是别人的依赖），合并成一条，`kinds` 同时含 `root`。
3. 不截断。旧实现“前 5 处 + 共 N 处”删掉；完整清单放在 `group.impacts`，文本明细同样全列。
4. 核心节点（终端节点）在普通图里不展开，所以不会出普通的 `EVIDENCE_STALE`；它们的变化只由 §2.7 的门禁码报告。核心单元若同时是证据单元（如 `requirePermission`），根自身的 `root` 报告照出，两者各自消除。
5. `EVIDENCE_CLOSURE_UNRESOLVED`、`EVIDENCE_UNIT`、`EVIDENCE_ANCHOR`、`EVIDENCE_MISSING`、`TABLE_CONFLICT`、`EVIDENCE_UNUSED` 不变。
6. “依赖牵连的义务数分布”改为从 `R_cur` 计算，顺带消除 #165 指出的统计去重问题。

### 3.3 旧逐根算法（oracle）

`legacyStaleOf(G_reg, G_cur, D_reg, D_cur)` 只在测试里使用，产出三元组集合 `L`：

- `(r, y, added)`：`y ∈ Cl_cur(r) \ Cl_reg(r)`；
- `(r, y, removed)`：`y ∈ Cl_reg(r) \ Cl_cur(r)`；
- `(r, y, changed)`：`y ∈ Cl_reg(r) ∩ Cl_cur(r)`，且 `D_reg[y] ≠ D_cur[y]`。

PR-1 已证明：由 `G_reg` 推出的 `Cl_reg(r)` 与旧 `DEPENDENCIES[r]` 的键集合**逐根相等**，摘要也相等（686 个根）。所以 `L` 就是 main 上现行算法会报的全部“根 × 依赖”变化，只是不截断。

### 3.4 精确等价关系（审查补定的技术点二）

**归因**：三元组 `(r, y, k)` 归因到变更节点 `x`，当且仅当满足下面之一：

- `k = changed`，且 `x = y`；
- `k = added`，`x ∈ Δe`，`r ∈ R_cur(x)`，且存在 `t ∈ added(x)`，使 `y = t` 或 `y ∈ Cl_cur(t)`。`r → … → x` 在 `G_cur` 上的最短链必须在 `MAX_DEPTH` 内，按 `snapshot: 'cur'` 的链长判定；
- `k = removed`：与上一条对称，用 `removed(x)`、`R_reg`、`Cl_reg`。

**oracle 断言**（PR-2 合并门槛），对夹具与真实表上的每一次变异都成立：

| 断言 | 内容 |
|---|---|
| A1 完整 | `L` 中每个三元组都至少归因到一个 group，且该 group 的 `impacts` 里有这个 `r`，`closureChanged = true` |
| A2 逐条可靠 | 每个 group 的**每一条** impact 都满足 `r ∈ R_reg(x) ∪ R_cur(x)`。用独立实现的朴素深度优先搜索分别在两个快照上复算，不复用被测代码 |
| A3 标注正确 | `impact.closureChanged = true`，当且仅当 `L` 中存在归因到 `(x, r)` 的三元组 |
| A4 无凭空分组 | 每个 group 都有 `x ∈ Δd ∪ Δe ∪ Δr`。某组所有 impact 的 `closureChanged` 都是 `false` 时，只允许是 `Δe` 组，文本标“仅绑定 / 路径变化” |
| A5 其他发现不变 | `unresolved`（含 `depth-limit`）的集合与旧算法一致 |

A1 的依据：`y` 新进入 `Cl(r)` 时，`G_cur` 上从 `r` 到 `y` 的最短路径中，至少有一条边不在 `G_reg` 里（否则 `y ∈ Cl_reg(r)`）。取这条路径上第一条新边，它的起点就是 `x`。删除的情形对称。深度上限的边界情况（路径缩短后才进入上限内）用 §6 测试 9 的 40 / 41 层夹具覆盖。
