## 0. 结论先行

1. **只做新版一体化组织调整**（DEC-029）。旧版 B44 / B45 不做、连只读也不做；原站灰度的“组织调整”直接生效按钮**不做**（DEC-644 A-1）；架构图首版做**预览树 + 增减标记**，**并做导出**（DEC-644 范围）：入口、PNG / SVG、调整前 / 后开关与文件规格按 F273A §3 / §6 设计（§10A）；**不单设权限，能查看该申请详情的人都能导出**（DEC-650①）；编制变化标记是否进导出待 F273C（DEC-650②）。
2. 申请单是独立业务对象（新模块 `apps/api/src/modules/org-adjustment/`），**不再挂在任职适配器上**：审批类型 `org_adjustment` 改用新适配器与新 business_type `org_adjustment`、流程编码 `OrganizationProcess`、预置“HRBPLeader 审批 → HR 负责人审批”两节点，取审批主体组织的 HRBP / 负责人，做成可改草稿（DEC-526②、DEC-644 A-2，取人口径是推断、非原站事实，§4）。权限对象按 F273A §2 取原站编码：申请单 `TenantBase.OrganizationApproval`（13 个功能权限）、明细 `TenantBase.OrganizationApprovalDetail`（9 个）；原站另有的 `TenantBase.OrgAdjustment`（组织架构调整）不复用（§9.2）。
3. 审批快照把**明细的实际变更字段**放进 `changedFields`，与任职审批同一套披露 / 盲审 / 自动跳过判定，**不改审批模块**：本对象字段用静态命名空间编码（权限编码 = 披露编码），合同等外部字段的编码带明细身份（逐行判可见）；`values` / `originals` 含全部变化编码；详情、明细、预览按同一可见集裁剪（§4.5）。
4. 每条明细保存**目标稳定 ID + 基线版本**；提交、审批同意、执行各自按基线判冲突，冲突即显式刷新或该组失败，不静默覆盖（§2.5）。同单新建对象之间用“明细引用”，执行后把“明细 → 正式对象 ID”映射与业务写入同事务落库（§2.6）。
5. 跨对象写授权（调动补齐项的合同、职责转交，组织角色、职位、编制、兼职）在保存 / 审批编辑 / 提交 / 重提 / 幂等重放五处共用 `transfer/linkage/access.ts` 的 `LinkageAccess / authorizeLinkageWrite` 与各对象既有判定；数据权限取严：**审批主体组织 + 明细组织 + 员工三层**都须在范围内，**执行时复核申请人三层范围**，已不在范围的组失败（DEC-644 A-3，§6.3 授权矩阵）。
6. 状态分两列：审批状态 0～6，列表下拉 8 项（DEC-526④）；执行状态 1～3。审批通过只排期；数据量 ≤ 5000 在下一个调度刻（≤ 5 分钟）执行，> 5000 在租户时区次日 03:00 执行（DEC-526③）。**5000 只是调度阈值**，不是任何组的硬上限；单个组织 6000 人的改名照常处理（§7.1 / §7.5）。
7. 执行器：租户级执行权（租约 + fencing 号）、同租户一次只执行一张单、重叠组织的单据按审批先后、业务写入与明细结果同事务提交，崩溃后按租约接管续跑（§7.2～§7.4）。执行期间按 OA-R9 暂停相关部门员工的写入，拦截覆盖全部写入口（§7.6 矩阵）。
8. 部分失败：审批状态、执行状态不变（“审批通过 / 已执行”），失败只写明细结果与执行备注“成功执行N个调整，失败M个调整”，**不做重新执行入口**（DEC-526⑤；与规格 `33` OA-R10、§4“失败重跑”、旧 AC-OA-07 冲突处以 DEC-526⑤ 为准，§7.8）。
9. 联动一律复用 main 端口，不另写生效链（DEC-029 / DEC-431①）；调动明细走**完整调动编排**（抽出受信入口，含 `saveNewTransferLinkage`），未来生效与跨对象子项的时机逐对象写明（§8）。
10. 分 **13 批**（BE-10a / 10a2 / 10b～10e、BE-11a / 11b / 11c / 11c2 / 11d / 11e / 11f），每批给文件级行数，产品代码 ≤ 1500、手写合计 ≤ 3000（DEC-625，§14）。F273A 已完成（v1.6 合入）：**10a2 可派**（对象与 22 个功能权限映射见 §9.2），其后 10b～10d、11b～11e 按前序链依次派；11a 只依赖 10a 与 BE-7 全部（A-17）。A-4 同步调整编制按已证部分开放，落新批 **11f**；A-9 调整范围改为组织多选，随 10b；导出（10e）按 DEC-650 随详情可见开放，只等 10d（§13.2）。

## 2. 数据模型与迁移清单

新模块 schema 文件 `packages/db/src/schema/org-adjustment.ts`；所有表带 `tenant_id`、FORCE RLS（F-212）；主键 UUID，单据编码按租户唯一（AGENTS §10 标识）。“变更前”值不建列（硬规则 3 同口径）：明细只存**目标 ID + 基线版本 ID**（§2.5），“原上级 / 原名称 / 原负责人”一律从基线版本读。

### 2.6 同单新建对象的引用与正式 ID（第 1 轮 P2-02）

main 的创建端口在函数内生成 ID（`org/write-service.ts:107`、`job/write-service.ts:34`），不接受外部 ID；本设计**不改这两个端口的 ID 生成**，改为：

- 明细之间引用同单新建对象一律用**明细 ID**（`parent_item_id`、`transfer_to_item_id`、调动 / 职位 / 编制 / 兼职行的 `department_item_id` / `position_item_id`），不引用尚不存在的组织 / 职位 ID。
- 执行新增类明细时，端口返回的正式 ID 写进本行 `created_org_id` / `created_position_id`，与端口写入**同一事务**；后续引用该明细的组在执行时把明细引用解析为正式 ID（`resolveItemRef`），被引用行失败或尚无结果 → 引用方失败 `DEPENDENCY_FAILED`。
- 崩溃重入：本行已有 `created_*_id` 即视为已执行（事务已提交），不重复创建；没有则整组事务未提交，重做安全。
- 预览与详情用明细 ID 作为虚拟节点 ID。

## 3. 状态机（审批状态 × 执行状态）

| 动作 | 前置（审批 / 执行） | 结果 | 谁能做 |
|---|---|---|---|
| 新建（弹窗保存） | — | 0 已暂存 / 1 | 有对象新建按钮、审批主体组织在范围内 |
| 编辑头 / 明细 / 刷新基线 | 0、6 | 不变，revision + 1 | 申请人（创建人）且仍有编辑权与范围 |
| 审批中编辑 | 1 | 不变，revision + 1，实例 businessVersion 同步 | **只有当前节点在办审批人**（OA-R7，§4.4） |
| 提交 | 0、6（6 走同实例重提，DEC-099） | 1 审批中 | 申请人 |
| 撤回 | 1 | 0 已暂存（实例 withdrawn） | 申请人 |
| 驳回到发起人 | 1 | 6 已驳回，可改后重提 | 审批人 |
| 不同意 | 1 | 3 审批未通过（终态，DEC-144） | 审批人 |
| 作废 | 0、6 | 5 作废（终态，不物理删除） | 申请人 |
| 最后一节点同意 | 1 / 1 | 2 审批通过 / 1 未执行，并写执行队列（BE-11b 起；BE-10c～11a 不写队列，§14.1） | 审批人 |
| 执行开始 | 2 / 1 | 2 / 3 执行中，写暂停行 | 执行器 |
| 执行完成 | 2 / 3 | 2 / 2 已执行，写备注与计数，删暂停行，通知申请人 | 执行器 |

- **审批状态 4“生效”复刻不写入**，只在下拉与枚举中保留（原站新版审批通过且执行后仍显示“审批通过 / 已执行”，A-7）。审批状态（是否同意）、执行状态（是否已落库）、版本的“当前生效”（按日期读取）三种含义分开。
- **列表下拉 8 项**（DEC-526④）：草稿、已暂存、审批中、审批通过、审批未通过、生效、作废、已驳回。“草稿”“已暂存”都筛 `approval_status = 0`；“生效”筛 4，复刻恒为空（A-8a）。枚举、文案放 `packages/domain/src/org-adjustment/status.ts`（DEC-045）。
- **暂存明细**（DEC-644 A-8：暂存明细不参加执行；v1.3 的“含暂存行不能提交 / 同意”取消）：只有组织明细有 `is_staged` 列；连带行与生成行（`cascaded_from_item_id` / `generated_by_item_id` 指向的发起行）跟随发起行的暂存状态，不另存。

| 时点 | 暂存行怎么处理 |
|---|---|
| 保存 / 审批编辑 | 照常写入；§6.3 授权照判（暂存行也是单据内容，审批人可见）；计入 §5.3 数量上限 |
| 提交 / 重提 | **不拒绝提交**。暂存行只做 §6.3 授权与字段格式校验，跳过 §5.2 业务校验与 §2.5 基线；非暂存行引用暂存行（`parent_item_id`、`transfer_to_item_id`、各分区 `*_item_id`）→ 400 `ORG_ADJUSTMENT_STAGED_REFERENCE`（列出行），不让执行依赖不会落地的对象 |
| 审批同意 | `beforeApprove` 只对非暂存行判基线；快照照常含暂存行（静态编码 `orgItems.isStaged` 标明），盲审 / 披露口径不变（§4.5） |
| 执行 | 不进数据量（§7.1）、涉及组织集合 S / S′（§7.6、§7.6A）、执行组与暂停；执行结果三列保持空；不计入 N / M（§7.8）；详情标“暂存（未执行）”（§10） |

- **为何审批通过 + 执行后写未来版本不违反硬规则 4**：审批通过与执行是两个状态；未来生效日的单据执行时写入**生效日为未来**的组织 / 职位 / 编制版本与任职记录，按日期读取才成为当前生效，与直接改组织写未来版本（`org/write-service.ts:150 rejectEarlierThanFutureVersion` 所在的同一写入路径）同一机制；需要到期才执行的跨对象动作仍由既有定时生效执行（§8.6 逐对象表）。

### 5.3 数量上限（OA-R16）

**照搬**：组织明细 ≤ 100（连带停用的下级计入）；职位 ≤ 500；调动 ≤ 500（换负责人、停用转移生成的计入）；兼职 ≤ 500。超限 413 `ORG_ADJUSTMENT_LIMIT_EXCEEDED`（带 `section`、`limit`、`count`）。DEC-029“实现时按性能评估”的结论：**保留**——上限让同步校验与执行组事务（§7.4）都有界。**改名 / 改上级带出的任职人数不受这四个上限约束，也不受 5000 约束**：它只计入数据量决定排期（§7.1），执行时分批（§7.5）。

### 5.4 编制明细规则（OA-R14 与 DEC-029 的关系，BE-11e）

- **新建编制**（`createCapacity`，`establishment/capacity-service.ts:156`）：只能给本单新增的组织（OA-R14 照搬）。
- **调整已有组织编制**（`updateCapacity`，`:222`，DEC-029 补齐）：只能调整该组织已有的编制（增 / 减），不能借“调整”给已有组织新建编制。已有组织没有编制 → 400 `ORG_ADJUSTMENT_ESTABLISHMENT_NEW_ORG_ONLY`。
- **停用编制部分转移**（DEC-029 补齐）：只在“同步调整编制 + 有转移目标 + 方式 2”时可填 `establishment_transfer_amount`（可小于 N），剩余随组织停用一并结束；同步调整编制与停用方式的语义见 §5.5（F273A §1，v1.6 起开放，随 BE-11f）。

### 5.5 同步调整编制与停用方式（A-4，F273A §1；BE-11f）

**单一计算点**：纯函数 `planEstablishmentSync`（`packages/domain/src/org-adjustment/establishment-sync.ts`）。输入为明细类型、被调整组织在 E 的编制快照、上下级链与各级编制、转移目标及其上级链、方式、转移数量；输出编制生成行（`org_adjustment_establishment_items`，`generated_by_item_id` = 该明细，operation 调整 2 / 转移 3）。N 的口径（`syncAmount`，DEC-649）与“调哪个上级”（`syncAncestor`）只在此函数内，后续复核结论回来单点改。

- 11f 之前：`sync_establishment = 是`、停用方式、`sync_parent = 是` 一律 400 `ORG_ADJUSTMENT_ESTABLISHMENT_SYNC_NOT_AVAILABLE`（批次关口）。

### 5.6 调整范围约束（A-9，F273A §4；BE-10b 起）

- **单一判定** `assertInAdjustmentRange(tx, ctx, adjustmentId, orgRefs)`：范围 = 所选组织在 E 的行政维度子树，叠加本单新增组织（上级在范围内的新增组织也在范围内）。
- **必须落在范围内的引用**：
  - 组织明细的目标组织、新上级、转移目标（10b）；
  - 调动行的源部门与目标部门（11c）；
  - 职位行所在组织（11d）；
  - 编制行与兼职行的组织（11e / 11f）。
  - 连带下级天然在范围内。超出 → 400 `ORG_ADJUSTMENT_OUT_OF_RANGE`（列出 `{section, itemId, orgId}`）。
- **判定时点**：保存、提交 / 重提、审批编辑（与 §5 同处）；执行时不另判（范围是表单约束，明细目标的变化由 §2.5 基线兜住）。
- 改调整范围（改头）使已有明细超出范围 → 改头 400 同码，不自动删明细。
- 预览树只展示范围内组织及其下级（F273A §4“审批时根据选择的范围显示组织架构”）。
- **授权**：所选组织并入 §6.3 ② 组织范围判定（矩阵“调整范围”行）。

## 7. 生效执行（BE-11a 底座；各明细执行器随 11b～11e 接入）

### 7.1 数据量与排期（DEC-526③）

审批通过事务（适配器 `approved`）内：

1. `data_volume`（只计非暂存行，§3）= 组织明细行数（含连带）+ 职位行 + 任职人数 + 编制行 + 兼职行；任职人数 = 调动行数 + 改名 / 改上级选“是”的整支在职主职人数。后者用**新的无截断计数** `countOrgEmploymentTargets`（与 `orgEmploymentTargets`，`employment-linkage.ts:49`，同一选人 SQL 的 `count(*)` 形态，不带 `LIMIT`），不调用有界的 `orgEmploymentTargets`。
2. ≤ 5000：`run_on_date = 审批当天`、`run_from_hour = 0`，在下一个调度刻执行（定时器间隔默认 5 分钟，`activation-scheduler.ts:217`；服务时限 = 一个间隔，A-15）；> 5000：`run_on_date = 审批当天 + 1`、`run_from_hour = 3`（租户时区，DEC-056，判定同 `auto-regularization-scheduler.ts localHour`）。
3. 写执行队列行、涉及组织集合（`org_adjustment_scope_orgs`，§7.6 的范围）；审计 `org-adjustment.execution.scheduled`。审批事务不写暂停、不改组织与任职（§4.1 锁环论证）。

### 7.2 执行权（租约 + fencing，第 1 轮 P2-07）

- 执行器 `org-adjustment/execution-runner.ts` 挂在任职定时生效的同一进程定时器上（`activation-scheduler.ts:259 / :261` 挂每日批次的同一位置），每刻遍历活跃租户。
- **领取**（独立短事务）：`UPDATE org_adjustment_tenant_runners SET holder_token = 本进程令牌, fencing_no = fencing_no + 1, lease_until = now() + 5 分钟 WHERE tenant_id = … AND (lease_until < now() OR holder_token = 本进程令牌) RETURNING fencing_no`；行不存在先 `INSERT … ON CONFLICT DO NOTHING`。领不到即本刻跳过该租户。**同一租户任一时刻只有一个持有者**，SKIP LOCKED 只用于队列行，不再承担串行。
- **fencing**：此后每个执行组事务的第一句 `SELECT fencing_no, holder_token FROM org_adjustment_tenant_runners WHERE tenant_id = … FOR UPDATE`，与领取时的值不同即回滚放弃（租约已被接管）；相同则顺延 `lease_until`。业务写入、明细结果、进度游标与这句在同一事务提交，所以被接管的旧进程不可能再提交任何业务写入。
- **接管**：进程崩溃或卡住超过租约，下一个领取者 `fencing_no + 1` 接管，从未出结果的组继续（§7.4 幂等）。
- **释放**：本租户没有可执行的单据时，`lease_until = now()`。

### 7.3 选单规则（最早单据与重叠）

持有执行权后，在本租户 `state ∈ {pending, running}` 的队列行中：

1. 有 `running` 的单 → 继续它（崩溃接管）。
2. 否则按 `(approved_at, id)` 升序找第一张**已到期**（`run_on_date` / `run_from_hour` 已到）且**不存在更早审批、尚未完成、涉及组织集合与它相交**的单；有更早的相交单未到期（如其 > 5000 等 03:00）→ 本单也等，不越过它。涉及组织不相交的单可以先执行。相交判定用审批时按组写入的集合 S；执行开始时实际集合 S′ 只允许 ⊆ S，扩大的组直接失败（§7.6A），所以用 S 判定不会越过与实际执行范围相交的更早单据。
3. 同一租户一次只执行一张单（执行权保证），因此任一时刻暂停行只属于一张单，**不存在两张单的暂停互相阻挡**；执行器豁免的是“本单的暂停行”，暂停表 `(tenant_id, org_id)` 主键保证一组织只被一张单暂停。

### 7.4 执行组、顺序与原子性

- 暂存行及其连带 / 生成行不组成执行组（§3 暂存明细）。
- 一个**执行组** = 一条用户明细 + 它的生成行（连带停用下级、停用转移生成的人员 / 职位 / 编制 / 兼职、换负责人生成的调动）。组内**一个事务**：fencing 校验 → 组锁（§9.1）→ 申请人范围复核（§6.3 授权矩阵“执行”列，DEC-644 A-3）→ 基线（§2.5）与依赖解析（§2.6）→ 端口写入 → 本组全部行的执行结果 → 提交。全成或全败；组之间互不回滚（部分失败的前提）。例外只有改名 / 改上级的任职联动，按 §7.5 分批。
- 单内顺序（依赖图）：新增组织（按树深度）→ 变更组织（按新树拓扑序）→ 新增 / 复制职位 → 编制 → 调动（含换负责人生成行）→ 兼职 → 独立的职位变更 / 停用 → 停用组织组（自下而上；组内依赖图见 §8.4）。引用失败行的组记 `DEPENDENCY_FAILED`，不执行。
- 幂等（按组状态判定）：全部行有执行结果（`exec_phase = 2`）→ 跳过；改名 / 改上级组 `exec_phase = 1` → 只续任职分页，不重做组织写入（§7.5 恢复阶段）；其余情况整组未提交过，重做安全。执行器串行推进组，前一组到 `exec_phase = 2` 才进入下一组。
- 执行身份为系统用户（`SYSTEM_USER_ID`），审计带 `trigger = org-adjustment:<单据 ID>`。

### 7.5 改名 / 改上级的任职联动：计数、分页、分批（第 1 轮 P2-01）

- **总量计数**：§7.1 的无截断计数，只用于排期与进度展示。
- **目标分页**：按员工 ID 键集分页（`WHERE e.id > 游标 ORDER BY e.id LIMIT 500`），选人 SQL 与 `orgEmploymentTargets` 同一子树与条件（`employment-linkage.ts:49～64`，只选主职、排除离职 / 退休），抽成共享的 `orgEmploymentTargetsPage(tx, ctx, orgId, date, after, size)`；`orgEmploymentTargets` 改为调用它并保留 `ORG_EMPLOYMENT_LIMIT = 1000` 与 :66～69 的 413（**直接路径上限不变**）。
- **执行批量与恢复阶段**（第 2 轮 P2-R2-02）：改名 / 改上级选“是”的组织组按 `exec_phase` 推进，三类事务各自原子提交：

| 事务 | 前置 | 同一事务内 | 之后 |
|---|---|---|---|
| T1 组织写入 | `exec_phase = 0` | fencing → 组锁 → 申请人范围复核（组织层）→ 基线（§2.5）→ `updateOrganization` → 写 `executed_version_id`、`exec_phase = 1`、游标 = 空 | T2 |
| T2 第 k 页 | `exec_phase = 1` | fencing → 核对 `executed_version_id` 仍是该组织在 E 的现行版本（暂停期间组织写入被拦，正常必然一致；不一致 → 本行记失败 `EXECUTION_STATE_DIVERGED`、`exec_phase = 2`）→ 游标后一页（≤ 500）→ `lockOrgEmploymentEmployees`（:79）→ 申请人任职范围外的员工记逐员工失败 `APPLICANT_OUT_OF_SCOPE`（DEC-644 A-3）→ 其余逐人 `appendOrgAdjustment`（`employment/org-adjustment.ts:15`，`changeType` 参数化，审批路径传 `'org_adjustment'`，:58 缺省 null 保持直接路径）→ 游标、计数、逐员工失败 | 页为空 → T3 |
| T3 收尾 | `exec_phase = 1` 且下一页为空 | fencing → 写本行执行结果（成功 / `EMPLOYMENT_PARTIAL`）、`exec_phase = 2` | 下一组 |

  接管时：`exec_phase = 0` → 从 T1 重做（T1 未提交过，基线仍是原基线）；`exec_phase = 1` → **不做基线校验、不再写组织**，按游标续 T2（本单自己的写入以 `executed_version_id` 识别，不会被当成“基线已变”）；`exec_phase = 2` → 跳过。选“否”或整支无人时，T1 内直接写结果并置 `exec_phase = 2`。其他组类型只有 0 / 2 两态（单事务）。
- **重入去重**：员工若已有本明细触发的组织调整记录（载荷版本的触发业务 = 本明细，或审计 `trigger` 命中）即跳过；游标保证续跑从下一页开始。
- **逐员工业务失败**（如其主职已变化、DEC-178 不可见、不在申请人任职范围）：该员工记进 `org_adjustment_employment_failures`，本批其余员工照常；明细最终结果：全部成功 = 成功，有失败 = 失败（原因 `EMPLOYMENT_PARTIAL`，消息“组织已调整，N 名员工任职追加失败”）。组织版本此时已落库——与 DEC-137“保存后（可异步）为员工追加任职”同一语义：组织调整与任职追加本就允许分开完成；失败员工在详情逐人列出，由 HR 走既有任职入口补录（不是重新执行入口）。
- `org-adjustment-projection.ts:38～40` 的 1000 上限是调动落地时的只读投影、`authorizeOrgEmploymentReplay`（`employment-linkage.ts:157～165`）只服务直接路径重放，均不改。
- 回归（AC-OA-31）：**单个组织 6000 名主职员工**改名选“是”→ 排到次日 03:00；分别在 T1 提交后首页前、第一页后、最后一页后 T3 前杀进程，接管后组织只有本单一版（`executed_version_id` 不变）、6000 人各一条、无重复，执行结果、备注与暂停解除都正确。

### 7.6 执行期间暂停（OA-R9，第 1 轮 P2-06）

- **范围**：本单涉及组织（只计非暂存行，§3）= 明细组织 ∪ 连带下级 ∪ 改名 / 改上级选“是”的整支 ∪ 调动 / 兼职的源与目标部门 ∪ 转移目标 ∪ 职位明细所在组织。

### 7.6A 执行开始时复核涉及集合（第 2 轮 P2-R2-03）

审批时按组写入的集合 S 可能过期：例如 A 改名选“是”的单审批后、执行前，有人把 X 部门直接移到 A 下——推进的是 X 的版本，A 的明细基线仍匹配，但执行时分页会按新树选中 X 的员工。处理：

1. **执行开始事务**（⓪ fencing → ③ 本单行 → ④ `lockOrganizationSettings`）内，按当前组织树在 E 的状态为每个执行组重算实际集合 S′（§7.6 同一范围规则）。
2. S′ ⊆ S → 正常。S′ ⊄ S（扩大）→ 该组在本事务内直接记失败 `SCOPE_CHANGED`（业务失败、终态，计入 M），不执行、不暂停扩出的组织——**不静默扩大执行范围**；需要处理 X 的员工须另起单据。
3. 暂停行 = 未失败各组 S′ 之并，与第 1、2 步同一事务写入；此后组织新建 / 变更按“目标组织 + 新旧上级”、设立日期更正按“目标组织 + 首版上级”命中暂停（§7.6 表与“更正入口”），所有改组织树或组织生效区间的写入都在同一组织设置锁后判定，任何组织都无法再被移入暂停子树，员工也无法调入，执行期间 S′ 不会再扩大，分页选人稳定。
4. 选单（§7.3）始终用 S 判相交；保留执行的组 S′ ⊆ S，因此不会越过与实际执行范围相交的更早单据。上例中若另有更早、涉及 X 的未完成单 Y：本单 A 组因 S′ ⊄ S 失败、不触碰 X，本单其余组与 Y 的先后已在选单时按 S 判定。
5. 集合缩小（如员工、下级已移出）不算变化，按 S′ 执行与暂停。

回归（AC-OA-36）：审批后把 X 移到 A 下再执行 → A 组 `SCOPE_CHANGED`、X 员工无组织调整记录、X 不被暂停（其员工调动照常）、其余组正常；同时放一张更早、涉及 X、尚未执行的单 → 不越序、两单结果与串行一致；集合缩小的单正常执行且暂停只覆盖 S′；**设立日期更正两种先后**：X 首版自 E + 1 起、上级为 A——暂停先建立时更正 X 到 E → 409，X 版本日期与 revision 不变，执行结果不含 X；更正先于执行开始提交 → 开始时 S′ 含 X、A 组 `SCOPE_CHANGED`。

### 7.7 基础设施失败与崩溃恢复（第 1 轮 P2-07 / A-16）

| 类别 | 判定 | 处理 |
|---|---|---|
| 业务失败 | 端口抛出的业务错误码（`VALIDATION_FAILED`、`CONFLICT`、`NOT_FOUND`、`LINKED_RECORD_OUT_OF_SCOPE`、`PAYLOAD_TOO_LARGE`、基线 / 依赖失败、申请人范围复核失败 `APPLICANT_OUT_OF_SCOPE` 等） | 组事务回滚后，**另起本组事务**只写本组各行“失败 + 原因”（同 fencing 校验）；终态 |
| 可恢复的基础设施失败 | 连接中断、`40001` 序列化失败、`40P01` 死锁、语句超时、存储不可写 | 回滚；`org_adjustment_group_attempts` +1（独立短事务）；下一刻重试本组，不改任何结果 |
| 崩溃 | 进程退出 / 失联 | 无需记录：租约到期后接管，从未出结果的组续跑（§7.2） |
| 同一组连续 5 次可恢复失败 | — | 记该组失败 `EXECUTION_ERROR` 并继续后续组，保证暂停能解除（DEC-644 A-16 已定，采纳原写法；业务失败只记结果、不重执行，DEC-526⑤） |

回归（AC-OA-29）：双进程同租户同时领取（只有一个执行）；组提交后、下一组前杀进程（接管后不重复）；收尾事务前杀进程（接管后补收尾、暂停解除）；被接管的旧进程迟到提交被 fencing 拒绝。

### 7.8 结果、备注与通知（DEC-526⑤）

全部组都有结果后，收尾事务：fencing → 头 `execution_status = 2`、`success_count / failure_count`、`execution_note = "成功执行{N}个调整，失败{M}个调整"` → 删暂停行 → 队列 done → 审计 `org-adjustment.execution.completed` → `approval/notifications.ts:52 notifyMessage` 发站内消息给申请人（模板编码 `OrgAdjustmentExecuted`，文案“组织调整【主题】已执行：成功N个，失败M个”）。

- **计数口径**（A-10，固定）：N / M 按非暂存明细**行**计（暂存行不计，§3），生成行与连带行计入并跟随其所在组的结果；失败组的每一行都计入 M；改名 / 改上级明细只算一行（逐员工失败在明细内列出，不进 N / M）。
- **审批状态保持 2、执行状态为 2，不因失败改变**；没有重新执行接口（路由不存在，404），失败明细需新建一张单处理。规格 `33` OA-R10“修正后可重新执行”、§4“失败重跑”、差距表 BE-11 行“失败重执行”、旧 AC-OA-07 与此冲突，**以 DEC-526⑤ 为准**（AC-OA-07 按 §12 改写）。R1-T10 职责转交子项自身的“HR 单独重试”（`linkage/items.ts:154 retryLinkageItem`）是调动联动既有能力，不是组织调整的重新执行入口（§8.6）。

## 8. 联动（BE-11b～11e）

### 8.1 组织新增 / 变更 / 空部门停用（BE-11b）

- 新增：`createOrganization`（`org/write-service.ts:94`），上级由 §2.6 解析；结果 ID 写回本行。
- 变更：`updateOrganization`（`:124`），`OrgUpdateOptions`（`:115～122`）加 `employmentLinkage?: { changeType: 'org_adjustment' }`；审批路径**不在组织写入事务内**调 `applyOrgEmploymentLinkage`（:104），改走 §7.5 分批；直接路径不变（仍在同一事务、1000 上限）。
- 停用（空部门）：对根调 `updateOrganization(enabled = false)`，级联停用下级由其内部 `disableDescendants` 完成；**根与全部连带下级一个组**，连带行结果跟随根，不对下级重复写入。
- 选“否”：任职不动，组织路径读时解析（DEC-137“否”分支，A-5）。
- 兼职与职位：不生成记录，兼职部门 ID 不变（R2-T05 S10 / T-32 / P-12，R2e2 / R2f3）。
- 负责人变化带“原下属转交 / 新负责人经理调整”= 是：BE-11c2 前 400 `ORG_ADJUSTMENT_HEAD_LINKAGE_NOT_AVAILABLE`。

### 8.2 换负责人（BE-11c2；A-12 校验在 BE-10b）

- “原负责人直属下级转交给新负责人 = 是”→ 写明细时为每名直属下级生成调动行（改直线经理），计入 500；“新负责人的直线经理调整 = 是”→ 为新负责人生成调动行（默认上级组织负责人，OA-R4）。生成行按 §6.3 授权。
- 新负责人不在本组织：原站自动“调入或新增兼职并结束原负责人兼职”（OA-R11）。复刻**首版拒绝提交并提示**（DEC-644 A-12）：提交 400 `ORG_ADJUSTMENT_HEAD_NOT_IN_ORG`，提示在本单手动加调动或兼职明细（判定口径见 §5.2，校验随 BE-10b，单内调动 / 兼职明细自 11c / 11e 起计入）；自动生成调入 / 兼职待 PT-7 合入后再议，不在本设计范围。

### 8.3 调动明细：完整调动编排（BE-11c，第 1 轮 P2-03）

- **受信入口**：把 `transfer/service.ts:137 createTransfer` 拆成两层——外层保留人工入口检查（发起人类型、草稿位、`requireDirectTransfer` 的租户开关与按钮，:193）；内层 `createTransferCore`（锁调动人与转交下属 :142～146、规范化与继承 :147～151、`createEmploymentBusiness` :159、`transfer_requests` 写入 :170、`saveNewTransferLinkage` :177）供人工入口与组织调整执行器**共用**（DEC-431①）。执行器以 `mode = direct`、`initiator = 'hr'`、生效日 = 单据生效日、`change_type = 'org_adjustment'`（标来源，A-11）调用内层；不经租户“须走审批”开关（本单已审批）。

  - **跨日**：一律按上两条新建调动业务与任职记录。
  - **同日**：员工在生效日的现行主职恰好起于生效日且 kind ∈ {hire, rehire, retire_rehire} 时，照原站**不新增任职、就地改部门**：不新建调动业务，对该入职记录追加一条记录快照载荷版本（`is_record_snapshot`，与 `record-edit.ts:54 editEmploymentRecord` 同一追加机制，不 UPDATE 原值，硬规则 2；“变更前”从上一载荷版本取，硬规则 3），部门 / 职位 / 经理取本明细行目标值。

### 8.4 非空部门停用转移（BE-11d / 11e，第 1 轮 P2-05）

写明细时（填了“人员转移到”）对整支（根 + 连带下级）生成：

- 人员：整支在生效日的在职主职各一条调动行（目标 = 转移目标；`batch_transfer = 是` 时允许逐行改目标组织 / 直线经理 / 虚线经理，OA-R5 分批转移）；
- 职位：每个启用职位一条“复制”行（目标组织下有同名职位则改为“匹配”，不复制）和一条“停用源职位”行；人员行的目标职位引用对应的复制 / 匹配行；
- 编制：被停用整支的编制行一律结束（BE-11e）；勾选同步调整编制时按 §5.5 生成上级 / 目标组织的编制调整行（BE-11f）；
- 兼职（BE-11e）：整支内的兼职记录各一条结束行（结束日 = 生效日 − 1，`part-time/transfer-port.ts:82 end`，OA-R13）；选择转移时另加一条新增行（`part-time/service.ts:155 createPartTime`，开始日 = 生效日）——transfer port 只有查询与结束，没有新增；
- BE-11e 合并前：整支内有兼职或编制 → 提交 409 `ORG_ADJUSTMENT_TRANSFER_NOT_AVAILABLE`（不留半套）；BE-11f 合并前勾选同步调整编制 → 400（§5.5 批次关口）。

**组内依赖图**（根与全部连带下级、全部生成行同一组、同一事务）：

```
① 创建 / 匹配目标职位
② 转人（调动行，经 §8.3 受信入口；目标职位取 ①）
③ 停用源职位（此时已无在岗，job/personnel.ts:35 不再拒绝）
④ 编制：结束整支编制行（BE-11e）+ 同步调整生成行（BE-11f，§5.5）    ⑤ 兼职结束 / 新增（BE-11e）
⑥ 停用组织：updateOrganization(enabled=false)，内部 planDeactivation → assertSubtreeVacant 应通过
```

任一步业务失败 → 整组回滚，组内全部行记失败；⑥ 的占用检查不过（期间又有在途申请等）同样整组失败。直接停用路径（DEC-129 / DEC-016 “不做自动转移”）不变。回归（AC-OA-33 / 34）：带子部门、人员、职位、兼职与部分编制的完整转移；③ 前人为制造失败验证整组回滚。

## 10A. 架构图导出（BE-10e；F273A §3 / §6；DEC-644 范围、DEC-650）

- **入口**（已证）：详情 › 调整预览 › 切到“架构图”视图 › “导出”下拉；“树状图”视图没有导出（F273A §3，3_01）。复刻的“架构图”视图首版就是预览树的图形化渲染（前端），后端出导出文件。
- **格式**（已证）：PNG、SVG 两项（3_02、6_01～6_04）。接口 `GET /adjustments/:id/preview/export?after=true|false`（§9.3 #28）返回 SVG 与文件名；“PNG图片下载”由前端把同一 SVG 栅格化后下载，同一受权限保护的接口供两种格式，服务端不引入图像渲染依赖。
- **权限**（DEC-650①）：不单设权限、不注册按钮，**能查看该申请详情的人都能导出**：与 `GET /adjustments/:id` 同一判定（申请单对象 read + 范围，或审批 `canOpen`）；导出内容 = 当前预览，不超出该查看人的详情可见范围（§4.5 披露集）。DEC-648④ 的“期间关闭”已解除。
- **文件规格**（F273A §6，已证；照搬）：
  - 跟随“展示调整后架构”开关（`after`）：关 = 调整前，节点上标出本次要调整的组织（如“停用”标签、灰色顶边）；开 = 调整后，被停用组织不出现、不带标记。导出的就是当前预览。
  - 只含调整范围子树：根节点是调整范围所选组织（§5.6），范围外组织不出现。多个所选组织时并列多棵树（原站样本只有一个，多棵的排布未证，取所选顺序 `seq`）。
  - 节点字段固定为 **名称 / 负责人 / 分管领导 / 编制**，**不含人数**（预览里的在岗 / 兼岗数不进导出）；无值显示“--”；名称过长截断为“…”，SVG 文字即截断后文字；没有标题、日期等页眉，没有图例。
    - 分管领导：复刻组织对象没有该字段（原站人员角色 `LeaderWithSpecificDuty`，见 `docs/02_业务建模/10_组织对象_实测规格.md` 人员角色行，原站“仅作为信息记录”），本设计不新增字段，导出恒显示“--”，补字段另立任务。
    - 编制：取预览节点的编制数（10d 预览补“编制原值”，口径与组织详情的编制展示一致；无编制“--”）。
