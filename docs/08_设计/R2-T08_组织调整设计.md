## 0. 结论先行

1. **只做新版一体化组织调整**（DEC-029）：一张申请单含组织（新增 / 变更 / 停用）、职位、编制、调动、兼职五类明细，经审批后由执行器按明细逐组落地。旧版 B44 / B45 **不做，连只读也不做**（§1.2）。原站“组织调整”直接生效按钮**不做**（假设 A-1）。
2. 申请单是独立业务对象（新模块 `apps/api/src/modules/org-adjustment/`），**不再挂在任职适配器上**：审批类型 `org_adjustment` 改用新适配器 `org_adjustment`、新 business_type `org_adjustment`、流程编码 `OrganizationProcess`、预置“HRBPLeader 审批 → HR 负责人审批”两节点（DEC-526②，§4）。
3. 状态分两列：审批状态 0～6 照原站枚举，列表下拉照原站 8 项（DEC-526④）；执行状态 1～3。**审批通过 ≠ 已执行**：审批通过写“审批通过 + 执行中”并入执行队列，执行器跑完写“已执行”（§3）。
4. 执行（BE-11）：数据量 ≤ 5000 审批通过后即排队执行，> 5000 排到次日 03:00（租户时区，DEC-526③）；未来生效日的单据同样在审批通过时执行，落成未来版本（R2f3）。执行期间对涉及部门的员工暂停入职 / 编辑任职 / 调动 / 转正 / 实习转正 / 任职导入（OA-R9，§7.3）。
5. 部分失败：审批状态、执行状态不变（“审批通过 / 已执行”），失败只写明细执行结果和执行备注“成功执行N个调整，失败M个调整”，**不做重新执行入口**（DEC-526⑤；与规格 `33` OA-R10、§4“失败重跑”、AC-OA-07 冲突处以 DEC-526⑤ 为准，§7.5）。
6. 联动一律复用 main 已有端口，不另写生效链（DEC-029 / DEC-431①）：组织写入走 `org/write-service.ts createOrganization / updateOrganization`，改名 / 改上级的任职联动走 `org/employment-linkage.ts` 同一入口，只多一个“变动类型”参数（DEC-526①：审批路径写“组织调整”，直接路径仍为空，DEC-137 不变）；调动走直接调动 + R1-T10 跨对象联动；兼职走 `part-time/transfer-port.ts`；编制走 `establishment/capacity-service.ts`。
7. 分 6 批：BE-10a 契约 / BE-10b 申请单与组织明细 / BE-10c 审批适配器 / BE-10d 列表详情预览 / BE-11a 执行底座与组织明细执行 / BE-11b 职位与调动明细 / BE-11c 停用转移、编制与兼职；每批产品代码 ≤ 1500 行（DEC-625，§14）。

## 2. 数据模型与迁移清单

新模块 schema 文件 `packages/db/src/schema/org-adjustment.ts`；所有表带 `tenant_id`，FORCE RLS（F-212，与既有租户表同模板）；主键 UUID，单据编码按租户唯一（AGENTS §10 标识）。“变更前”值不建列：组织明细的“原上级 / 原名称 / 原负责人”在执行前读该组织在生效日的现行版本，执行后读本明细落下版本的 `previous_version_id`（`org_versions.previousVersionId`，`packages/db/src/schema/org.ts:60`），与硬规则 3 同口径。

## 3. 状态机（审批状态 × 执行状态）

| 动作 | 前置（审批 / 执行） | 结果 | 谁能做 |
|---|---|---|---|
| 新建（弹窗保存） | — | 0 已暂存 / 1 | 有对象新建按钮、审批主体组织在范围内 |
| 编辑头 / 明细 | 0、6 | 不变，revision + 1 | 申请人（创建人）且仍有编辑权与范围 |
| 审批中编辑 | 1 | 不变，revision + 1，审批实例 businessVersion 同步 | **只有当前节点在办审批人**（OA-R7，§4.4） |
| 提交 | 0、6（6 走同实例重提，DEC-099） | 1 审批中 | 申请人 |
| 撤回 | 1 | 0 已暂存（实例 withdrawn） | 申请人 |
| 驳回到发起人 | 1 | 6 已驳回，可改后重提 | 审批人 |
| 不同意 | 1 | 3 审批未通过（终态，DEC-144） | 审批人 |
| 作废 | 0、6 | 5 作废（终态，不物理删除，保留快照） | 申请人 |
| 最后一节点同意 | 1 / 1 | 2 审批通过 / 3 执行中（BE-11a 起；BE-10c～11a 之间为 2 / 1，§14.1） | 审批人 |
| 执行完成 | 2 / 3 | 2 / 2 已执行，写备注与计数，通知申请人 | 系统 |

- **审批状态 4“生效”复刻不写入**：原站新版审批通过且执行后仍显示“审批通过 / 已执行”（规格 `33` 补充节），4 只在下拉与枚举中保留（假设 A-7）。
- **列表下拉 8 项**（DEC-526④）：草稿、已暂存、审批中、审批通过、审批未通过、生效、作废、已驳回。“草稿”“已暂存”两项都筛 `approval_status = 0`（原站草稿 = 0 即显示“已暂存”，两者并存只是下拉口径；假设 A-8）；“生效”筛 4，复刻恒为空。枚举、文案放 `packages/domain/src/org-adjustment/status.ts`（DEC-045 文案走资源文件，前端 `messages.ts` 引同一份编码）。
- **为何“审批通过即执行”不违反硬规则 4**：审批通过与执行是两个状态（审批状态 2 + 执行状态 3 → 2）；未来生效日的单据执行时写入的是**生效日为未来**的组织版本与任职记录，按日期读取才成为“当前生效”，与直接改组织写未来版本（`org/write-service.ts:150 rejectEarlierThanFutureVersion`）同一机制，不需要另一个到期任务（规格 `33` OA-R8 + 补充节 + R2f3）。

## 5. 提交校验（BE-10b 实现，提交 / 重提 / 审批编辑 / `check` 共用一个 `validateAdjustment`）

### 5.1 同步还是异步（OA-R17）

**全部同步**：原站分“组织类立即返回 + 其余异步 + 进度条”是因为单据可达数千行。复刻单据受 §5.3 上限约束（组织 100、职位 / 调动 / 兼职各 500），全部校验是有界查询，一次请求内可完成；不建异步校验任务、进度条与“查看详情”页，错误以 `{ items: [{ section, itemId, reason, message }] }` 一次返回（最多 200 条，超出标 `truncated`）。`POST …/check` 只校验不写入，供编辑器“提交前检查”。

### 5.3 数量上限（OA-R16）

**照搬**：组织明细 ≤ 100（连带停用的下级计入）；职位 ≤ 500；调动 ≤ 500（换负责人、停用转移生成的计入）；兼职 ≤ 500。超限 413 `ORG_ADJUSTMENT_LIMIT_EXCEEDED`（带 `section`、`limit`、`count`）。DEC-029 要求“实现时按性能评估”的结论：**保留**——上限让同步校验（§5.1）与单组事务（§7.4）都有界；复刻每个执行组一个事务，100 个组织 × 单组 ≤ 5000 人的最坏情况已由 5000 阈值改到次日 03:00 执行，放宽上限没有收益只增加锁时长。生成行在**提交时**按当时数据计数并落成明细行，执行时再按实际重算，超限则该组失败（§7.4）。

### 5.4 编制明细规则（OA-R14 与 DEC-029 的关系，BE-11c 实现）

- **新建编制**（`createCapacity`，`establishment/capacity-service.ts:156`）：只能给本单新增的组织（OA-R14 照搬）。
- **调整已有组织编制**（`updateCapacity`，`:222`，DEC-029 补齐）：只能调整该组织已有的编制（增 / 减），不能借“调整”给已有组织新建编制——两条合起来：已有组织没有编制 → 400 `ORG_ADJUSTMENT_ESTABLISHMENT_NEW_ORG_ONLY`。
- **停用编制部分转移**（DEC-029 补齐，原站只支持全部）：`deactivation_establishment_mode = 2` 时 `establishment_transfer_amount` 可小于全部，剩余随组织停用一并结束。

## 7. 生效执行（BE-11a；明细类型随 11b / 11c 接入）

### 7.1 数据量与排期（DEC-526③，按规格 `33` OA-R8 实现，不等补证）

审批通过事务（适配器 `approved`）内：

1. 计算 `data_volume` = 组织明细行数（含连带）+ 职位明细与生成行 + 任职人数（改名 / 改上级选“是”的整支在职主职人数，按 `orgEmploymentTargets` 同一选人 SQL 计数 + 调动行 + 兼职行）+ 编制明细行。
2. ≤ 5000：`run_on_date = 审批当天`、`run_from_hour = 0`（下一个调度刻即执行；原站约 1 分钟，复刻取定时器间隔，默认 5 分钟，`employment/activation-scheduler.ts:217`）；> 5000：`run_on_date = 审批当天 + 1`、`run_from_hour = 3`（租户时区，DEC-056，判定同 `auto-regularization-scheduler.ts localHour`）。
3. 写 2 / 3、写暂停行（§7.3）、写执行队列行；审计 `org-adjustment.execution.scheduled`。

### 7.2 执行器

`org-adjustment/execution-runner.ts`：挂在任职定时生效的同一进程定时器上（`activation-scheduler.ts:259 / :261` 挂每日批次的同一位置），每刻遍历活跃租户，`FOR UPDATE SKIP LOCKED` 取到期队列行；**同租户串行**（按 `approved_at`、id 升序一张一张执行），保证两张单涉及同一组织时先批先执行。执行身份为系统用户（`SYSTEM_USER_ID`），审计带 `trigger = org-adjustment:<id>`；DEC-178 联动可见性取**申请人在执行时点**的任职范围（假设 A-3）。

执行顺序（同一张单内）：新增组织（按树深度自上而下）→ 变更组织（按新树拓扑序）→ 职位 → 编制 → 调动（含换负责人生成行）→ 兼职 → 停用组织组（自下而上；每组内先做本组生成的转移，再停用）。引用了失败明细（如上级是失败的新增组织）的行直接记失败 `DEPENDENCY_FAILED`，不执行。

### 7.3 执行期间暂停（OA-R9）

- **范围**：本单涉及的组织 = 明细组织 ∪ 连带下级 ∪ 改名 / 改上级选“是”的整支 ∪ 调动 / 兼职的源与目标部门 ∪ 转移目标。审批通过时写 `org_adjustment_pauses`，**最后一组执行完的同一事务**删除（含 > 5000 等到次日 03:00 的整段，假设 A-6）。
- **拦截点（单一入口，DEC-431①）**：`employment/references.ts:71 assertEmploymentDepartmentAvailable` 已在全部入职 / 调动 / 转正 / 实习转正 / 编辑任职 / 任职导入路径上、且在 `lockOrganizationSettings` 之后执行（调用方：`write-service.ts:900`（新建业务，含导入 `forward-import.ts:101`）、`:295`（更新业务）、`:684`（落地）、`transitions.ts:160`（提交 / 审批）、`record-edit.ts:84`（编辑任职）、以及经 `createEmploymentBusiness` 进入的 `regularization.ts:63`、`intern-regularization.ts:56`、`entry-actions.ts:188`）。BE-11a 给它加可选参数 `{ employeeId, kind }`，在取锁后调新函数 `assertNotPausedByOrgAdjustment(tx, ctx, departmentIds)`：目标部门，以及（传了员工时）员工在该日的现行主职部门，命中暂停行即 409 `ORG_ADJUSTMENT_EXECUTING`（带单据编号，不带明细）。kind 为 leave / retirement 与兼职不暂停（OA-R9 未列；冲突由执行时的组失败兜住）。
- **组织直接写入**：`updateOrganization` / `createOrganization`（上级命中）/ 组织导入对暂停组织 409 同一码（数据正确性，原站未列，假设 A-6）。
- **执行器自身豁免**：执行上下文带 `orgAdjustmentId`，暂停判定忽略本单的暂停行。
- **串行化**：暂停行在审批事务里持组织设置锁写入；拦截点在组织设置锁之后读；两者经同一把租户级锁串行（`org/locks.ts:4～10` 全局序），不存在“检查通过后暂停行才出现”的窗口。

### 7.4 执行组与事务

- 一个**执行组** = 一条用户明细 + 它的生成行（连带停用下级、停用转移的人员 / 职位 / 编制 / 兼职、换负责人生成的调动），组内**一个事务**全成或全败；组之间互不回滚（部分失败的前提）。
- 组织组调用 `createOrganization`（`org/write-service.ts:94`）/ `updateOrganization`（`:124`），**不另写组织版本逻辑**；`OrgUpdateOptions`（`:115～122`）加 `employmentLinkage?: { changeType: 'org_adjustment'; limit: number }`，经 `applyOrgEmploymentLinkage`（`employment-linkage.ts:104`）传到 `appendOrgAdjustment`（`employment/org-adjustment.ts:15`），后者把 `:58` 的 `changeType: null` 改为参数（缺省 null = 直接路径，DEC-137 不变）。
- **与直接路径上限的关系**：直接路径 `ORG_EMPLOYMENT_LIMIT = 1000`（`employment-linkage.ts:16`，`:66～69` 超限 413）保持不变；审批路径单组上限传 5000（`orgEmploymentTargets` 加 `limit` 参数，默认仍 1000；`authorizeOrgEmploymentReplay` 的 `:157～165` 只服务直接路径重放，不改）。单组超过 5000 人 → 该组失败 `PAYLOAD_TOO_LARGE`。`org-adjustment-projection.ts:38～40` 的 1000 上限是调动落地时的只读投影，与本路径无关，不改。
- 每组开始前重新读取并校验（§5 的组织类校验 + 计划人员集合），数据在提交后变了（人员已离开、组织已有未来版本、编码被占）→ 该组失败，原因写明细。
- 非业务错误（存储不可用、序列化失败等）：该组事务回滚、不写结果，队列 `attempts + 1` 写 `last_error`，下一刻重试未出结果的组（已出结果的组不重做，幂等）；连续 5 次仍失败则剩余组记失败 `EXECUTION_ERROR` 并收尾，保证暂停能解除（DEC-052）。这是**基础设施重试**，不是 DEC-526⑤ 不做的“业务失败重新执行”。

### 7.5 结果、备注与通知（DEC-526⑤）

全部组都有结果后，一个收尾事务：头 `execution_status = 2`、`success_count / failure_count`、`execution_note = "成功执行{N}个调整，失败{M}个调整"`（N / M 按明细行计，含生成行，假设 A-10）、删暂停行、队列 done、审计 `org-adjustment.execution.completed`；`approval/notifications.ts:52 notifyMessage` 发站内消息给申请人（模板编码 `OrgAdjustmentExecuted`，文案“组织调整【主题】已执行：成功N个，失败M个”）。**审批状态保持 2，执行状态为 2，不因失败改变**；没有重新执行接口（路由不存在，404），失败明细需新建一张单处理。规格 `33` OA-R10“修正后可重新执行”、§4“失败重跑”、差距表 BE-11 行“失败重执行”、AC-OA-07 原文与此冲突，**以 DEC-526⑤ 为准**（AC-OA-07 按 §12 改写）。

### 8.2 换负责人与调动明细（BE-11b）

### 8.3 停用转移（BE-11c）

非空部门停用且填了“人员转移到”：提交时生成——人员：整支在生效日的在职主职各一条调动行（目标组织 = 转移目标，`batch_transfer = 是` 时允许用户逐行改目标的组织 / 直线经理 / 虚线经理，OA-R5 分批转移）；职位：在目标组织下按同名复制、原职位停用（OA-R5）；编制：按 `deactivation_establishment_mode`（1 / 2，2 可部分，§5.4）生成编制行；兼职：结束（`part-time/transfer-port.ts:82 end`，结束日 = 生效日 − 1，OA-R13）或转移（= 结束 + 在目标组织新增，两步都走既有端口，不原地改部门）。执行时组内先落调动 / 职位 / 编制 / 兼职，再调 `updateOrganization(enabled=false)`，此时 `assertSubtreeVacant` 应通过；不通过（期间又有人员 / 在途申请）→ 组失败。直接停用路径（DEC-129 / DEC-016 “不做自动转移”）不变。

### 8.4 同日与跨日（R2f3）

R2f3 已证“**同日入职同日转移**”不新增任职、原入职任职原地改部门。复刻口径：员工在生效日的现行主职记录**恰好起于生效日且 kind ∈ {hire, rehire, retire_rehire}** 时，调动行不新建调动业务，改为给该记录**追加一条记录快照载荷版本**（版本链追加，不 UPDATE，硬规则 2；同 F-021 / 向后更新的“追加载荷版本、原业务 ID 与时间线不变”口径）；改名 / 改上级选“是”遇同日入职者同样不追加组织调整（该员工已在新组织路径下）。其他情形（跨日、同日的非入职记录）一律新建记录排在当日最后（跨日原站未证，保守按“新建”，假设 A-13，数据正确性类）。
