## 0. 一页结论

1. **阶段 ①（可单独派开发）**：新增一张只追加的“字段来源台账”表 `employment_field_origins`。每次追加任职载荷版本时，在同一事务里为**本次实际写入的字段**各记一行：谁写的、是哪一类来源、写入的值、从哪条记录或哪次传播来的。只沿用旧值的字段不记行。
2. 每个字段的来源状态分两层：**策略层**（创建时继承 / 延迟继承 / 不继承 / 整记录复制）和**覆盖层**（员工输入、HR 保存、审批节点编辑、HR 补录、向后更新、派生、序列同步、状态传播）。覆盖值不适用时（例如职位不属于新部门）不销毁，只记一行“回落”，字段退回策略层；条件恢复时再记一行“恢复”。这样“延迟继承”的策略不会因为被传播值盖过一次就丢失，#99 四轮同类问题的根因在这里。
3. 现有两列 `explicit_field_codes`、`deferred_field_codes` 保留，改为由来源状态经**一个投影函数**算出，不再由各写入口各自拼。判断“员工本次是否输入了某字段”改看请求体，判断“已保存的值是否可信”改看该字段最后一次实际写入的来源，逐字段判断，不再整单豁免。
4. **阶段 ②**：迟到执行不再遇到区间内有记录就交 HR，而是在同一事务里重建。改期和重建只由**一个落地模块**做（`beginLanding` / `finishLanding`，§6.1）；前序判断留在各路径基线原来的位置，调动审批、调动定时 / 重试、离职 / 退休各自的先后在 §6.1 逐条写明，前序未解决时不写任何目标和台账。真正落地时，在内存里按最终时间轴的先后次序依次算出每条记录的结果（前一条用的是刚算出的值，不是库里的旧值），全部算完再一次写入（§6.3）。迟到传播命令调动恰好一条，离职 / 退休不发。区间内的组织调整重新折叠；独立业务按 DEC-269 做值匹配替换（U1 已定）；历史上的传播命令按各自的候选、跳过、匹配规则重放，并照样执行目标级的拒绝规则（引用可用性、经理成环，§6.5.2）。最终值由“最终时间轴 + 两张台账”决定；多笔迟到按如期视图定先后，与谁先执行无关（DEC-945 U9；承诺范围见 §6.8）。有一处要另看：派生字段第一次遇到没有锚点的新引用时，按重建当刻的配置取值并永久记下（DEC-945 U8，§6.5.3），这个值取决于那一次重建发生在哪一天。
5. 阶段 ② 新增第二张只追加表 `employment_propagation_commands`（传播命令台账），记录每次向后更新 / 状态传播的来源、前后值与当时的配置，命中零条也记。
6. 阶段 ① 新增一个**只读**接口 `GET /api/tenant/employment/businesses/:id/field-origins`（DEC-943 U6 选乙，§4.9）。它返回的字段与值不超过同一操作人此刻在详情接口看到的内容：已办审批人只看到办理当时冻结并披露的字段，不附来源；看不到的业务一律是同一个 404。两个阶段都不新增写接口，HR 重试沿用已有的 `POST /api/tenant/employment/businesses/:id/activation/retry`。前端展示见 F-531，本文不写。
7. 审批触发的重建单独带上审批人的数据范围和字段写权（事务内解析）。碰到范围外的后续记录、或审批人对要写的字段没有写权时，重建整单回滚，审批动作成功、申请停在“审批通过”并记生效失败；这个转换只发生在重建写目标的三项检查处，审批自己的 403 照旧让审批失败（§6.4）。
8. U1～U6 已由 DEC-943 定，U7～U9 已由 DEC-945 定：已保存的员工本人职位可信，只有本次请求又带职位才拒（U7 甲）；派生字段首次遇到新引用时取重建当刻的配置（U8 甲，不是原推荐项）；多笔迟到按如期视图的唯一顺序（U9 甲）。本文没有剩余的待决项。

## 2. 现状与问题（main `b0e4dad2f`）

### 2.1 现在来源信息存在哪

任职载荷版本表 `employment_payload_versions`（`packages/db/src/schema/employment.ts`）是只追加的版本链。与来源有关的只有四处：

| 位置 | 现在的含义 |
| --- | --- |
| `explicit_field_codes text[]` | 名义上是“人工填写的字段”，实际是“任何写入口写过的字段” |
| `deferred_field_codes text[]` | 延迟继承、值待定的字段 |
| `form_snapshot.fieldDerivations` | 派生规则（`post-sequence` / `department-manager` / `position-manager`）与当时的引用 ID |
| `trigger_business_id`、审计 meta 的 `sourceVersionNo` | 这一版是哪笔业务的传播触发的（整版一个值，不分字段） |

字段编码是 `preset:<字段名>` 与 `custom:<自定义字段 ID>`（`apps/api/src/modules/employment/inheritance.ts:102-103`）。main 上没有任何字段来源台账类的表。

约束与索引：

- 迁移里照 `0013_employment_rls_timeline.sql` 的现行写法：`SELECT enable_tenant_isolation('employment_field_origins');`、`GRANT SELECT, INSERT ON employment_field_origins TO app_user;`、只追加触发器 `employment_field_origins_append_only BEFORE UPDATE OR DELETE OR TRUNCATE … EXECUTE FUNCTION forbid_audit_mutation();`。序列 `employment_origin_seq` 在同一迁移里创建，并 `GRANT USAGE, SELECT ON SEQUENCE employment_origin_seq TO app_user;`（先例：`0097_r3t02_c1_4_sync_queue.sql:35`）。
- 索引 `(tenant_id, business_id, field_code, seq DESC)`：按业务读每个字段最近的几行。索引 `(tenant_id, employee_id, source_business_id)`：删除来源时找依赖它的字段（阶段 ② 用）。
- 部分索引 `(tenant_id, business_id, field_code, derivation_rule, reference_id, seq DESC) WHERE derivation_rule IS NOT NULL`：按 `(规则, 引用)` 定点读最近一条派生锚点（§4.6 `loadDerivationAnchor`）。一个字段可以经历很多次换职务、换职位，锚点不随折叠一起全部载入。三个索引都随 S1 的迁移建。
- 值的权威来源仍是载荷版本的字段列。台账里的 `value` 是为了两件事：覆盖值被回落后还能恢复；重建时不必回读每一版载荷。写入函数保证“最新一版载荷里每个非空字段的值 = 该字段最后一条实际写入行的 `value`”，并有守卫测试。
- 这张表不存“变更前”，不替代 DEC-019 的字段级变更日志，审计照旧另写。

### 4.2 来源种类

`origin_kind` 取值，分三组：

**策略层**（这个字段在没有覆盖值时该怎么取值）

| 值 | 含义 | 派单要求的来源种类 |
| --- | --- | --- |
| `inherit` | 创建或重新处理时从前驱继承，值已取到，带 `source_record_id` | 继承 |
| `deferred` | 延迟继承：现在不取值，落地时才从实际前驱取 | 延迟继承 |
| `resolved` | 落地时延迟字段解析出的值，带 `source_record_id` | 延迟继承（落地） |
| `none` | 按继承设置不继承，也没有输入 | — |
| `copy` | 组织调整整记录复制前驱，带 `source_record_id` | HR / 系统保存 |

延迟继承的三种形态不单设种类，由逐字段的策略组合表达：

| 形态 | 部门 `preset:departmentId` | 职位 `preset:positionId` |
| --- | --- | --- |
| 部门延迟 | `deferred` | 非 `deferred` |
| 职位单独延迟 | 非 `deferred`（有覆盖值或已继承） | `deferred` |
| 两者都延迟 | `deferred` | `deferred` |

判定函数 `deferralShape` 见 §4.6。

**覆盖层**（有人或系统明确写了一个值）

| 值 | 含义 | 派单要求的来源种类 |
| --- | --- | --- |
| `employee-input` | 员工本人在自助单据上本次填写 | 员工本次输入 |
| `hr-input` | HR 在业务表单上新建 / 修改时填写（含导入新建） | HR / 系统保存 |
| `system-input` | 系统建单或系统改写：Offer 同步、实习生建单、岗位端口、调动联动、再入职工龄、迟到顺延改最后工作日等 | HR / 系统保存 |
| `approval-edit` | 审批节点编辑 | 审批节点编辑 |
| `hr-record` | HR 对已生效任职记录的补录 / 编辑（页面、导入编辑、批量编辑）。请求点名的字段即使值没变也记一行（DEC-252③，§4.4.4） | HR 补录 |
| `forward-update` | 值匹配向后更新写入，带来源业务、版本号和 `match_before` | 向后更新 |
| `derive` | **建单或修改申请时**随输入自动带出的派生值（职务带序列、部门 / 职位带直线经理），带规则、引用和结果。不算人工填写，不进 explicit | 向后更新（引用派生） |
| `derive-edit` | **记录编辑或传播实际写入**的派生值：HR 编辑已生效记录的职务时服务端带出的新序列（`record-edit.ts:48`），以及这次变更传播到后续记录时连带写入的派生值，带规则、引用、结果和来源业务。基线把它们算进本次变更（`forward-store.ts:18`、`:29`），所以进 explicit | 向后更新（引用派生） |
| `sequence-sync` | F-021 序列同步写入，带**实际命中的引用**：按职务命中记 `post-sequence` + 职务 ID，按职位命中记 `position-sequence` + 职位 ID | 序列同步 |

`derive`、`derive-edit`、`sequence-sync` 三种都登记派生锚点。

覆盖行的 `value` 为 JSON `null` 表示“有人明确把这个字段清空了”。这与“这个字段从来没有任何来源行”是两回事：前者是一次写入，参与 §4.6 的只读字段复验；后者没有写入，不复验（没有来源行的旧载荷按 §4.8 处理）。

**判定行**（不带新值，只改变状态）

| 值 | 含义 |
| --- | --- |
| `fallback` | 某一条带值的行不再适用（例如职位不属于新的有效部门），把它挂起；`ref_seq` 指向被挂起的那一行。被挂起的可以是覆盖行，也可以是 `inherit` / `copy` 策略行或 `resolved` 行；几层的值都不适用时各记一行 |
| `restore` | 被挂起的行重新适用；`ref_seq` 指向它 |

### 4.3 折叠规则

一个字段的状态 `FieldOriginState`：

```ts
interface FieldOriginState {
  policy: 'inherit' | 'deferred' | 'none' | 'copy' | null; // 最近一条策略行
  policyRow: OriginRow | null;
  resolved: OriginRow | null; // 最近一条 resolved（落地后才有）
  override: OriginRow | null; // 最近一条覆盖行（含创建版的人工输入、retain）
  suspended: ReadonlySet<bigint>; // 当前被挂起的行的 seq（覆盖行、inherit / copy、resolved 都可能在里面）
  retained: boolean; // 当前覆盖行是不是 retain
  lastWriter: OriginRow | null; // 有效值取自哪一行；有效值为空时是 null
}
```

派生锚点不放进折叠状态，按需定点读取（§4.6 `loadDerivationAnchor`）。

按 `seq` 从小到大处理该字段的行：

| 读到的行 | 状态变化 |
| --- | --- |
| `inherit` / `none` / `copy` | `policy`、`policyRow` 更新 |
| `deferred` | `policy = 'deferred'`，`policyRow` 更新 |
| `resolved` | `resolved` 更新 |
| 任一覆盖行（含 `retain`） | `override` 更新；`retained` 记这一行是不是 `retain` |
| `fallback` | 把 `ref_seq` 加进 `suspended` |
| `restore` | 把 `ref_seq` 从 `suspended` 里拿掉 |

折叠只记“有哪些行、哪些被挂起”。`lastWriter` 不在读行时逐步改写，而是折叠结束后由下面的取值规则一次算出。

**取值规则（唯一一份）**：`effectiveOrigin(state)` 从高到低看四个位置，取第一条**存在且没被挂起**的行，它的 `value` 就是字段的有效值，它本身就是 `lastWriter`。

| 优先级 | 位置 | 说明 |
| --- | --- | --- |
| 1 | 覆盖行 `override` | 包括创建版里的人工输入（`hr-input` / `employee-input` / `system-input`）、之后的任何覆盖行，以及 `retain`。值为 JSON `null`（显式清空）也算取到，有效值就是空 |
| 2 | 落地解析值 `resolved` | 落地后才有 |
| 3 | 策略行里已取到的值：`inherit` / `copy` | `deferred`、`none` 不带值，跳过 |
| 4 | 都没有 | 有效值为空，`lastWriter = null`。策略是 `deferred` 且尚未落地时，这表示“待定” |

三点说明：

- **被挂起就整行跳过，不回落到同一行的值。** 第 1 轮的写法是“覆盖值挂起后从策略层取值”，没有判断策略层的值自己适不适用，草稿只有 `inherit(P)`、员工改到别的部门时仍然取到 P。现在覆盖值、普通继承值、落地解析值三处**各自**判适用性（§4.6 `settleFieldValues`），各自挂起、各自恢复。
- **创建版的人工输入就是覆盖行**，与之后的人工输入同一位置、同一优先级。重建不单独读“创建版”，而是折叠该业务的全部来源行再调 `effectiveOrigin`（§6.5）。
- **`retain` 是一条覆盖行**，取值优先级与其它覆盖行相同；它与普通覆盖行的差别只在重建时按人工值对待。之后新的覆盖行照常替换它。

通用读取（§4.6 J4）、两列投影（§4.5）、可信判定（J2）、重建规划（§6.5）都只调这一个函数，没有第二套取值规则。

折叠与取值都是纯函数，放在 `packages/domain/src/employment/field-origins.ts`（新增），没有 IO。

| 条件（从上到下，先命中先用） | 种类 |

#### 4.4.4 稀疏 PATCH 点名同值（DEC-252③）

HR 对已生效记录点名保存一个字段，即使值没变，也表示“我确认过这个值”，重建后要保持。基线 `editEmploymentRecord` 在 `record-edit.ts:98-102` 逐字段比出 `changes`，`:103` 发现没有变化就直接返回，到不了第 5 行的写点。阶段 ① 在 `:103` 的早返回**之前**加一步：

1. `named` = 请求体 `fields` / `customFields` 里出现了键的字段（`requestInputFields`）；`same` = `named` 里不在 `changes` 中的字段。
2. 对 `same` 里的每个字段：如果它的 `lastWriter` 已经是人工种类（`hr-record`、`hr-input`、`approval-edit`、`employee-input`、`retain`）而且值相同，不写；否则写一行 `hr-record`，`value` 为当前值。
3. 这一行关联哪版载荷：本次还有别的字段变了（`changes` 非空）→ 随本次新追加的那一版；全部同值（走早返回）→ **不追加载荷版本**，挂在这条记录当前最新的一版载荷上，并带 `record_id`。
4. 全部同值时：不动任职字段、不推进 revision、不触发向后更新（没有值变化可传播）；同一事务写一条审计 `employment.record.intent_confirmed`（对象是这条任职记录，meta 列出被确认的字段编码，不含字段值）。
5. 幂等：同一命令 ID 重放由命令台账返回首次结果，不再执行；换一个命令再点名同值时，第 2 步发现 `lastWriter` 已是人工种类，不再写行。所以重复保存不会让来源行数增长。

对照口径：整版表单重提里“随表单带上但没变”的字段不记行（§4.4.1 表第一行），重建后仍随来源变化。两条口径各配一条成对的验收（AC-EMP-28）。

### 4.5 现有两列怎么办

`explicit_field_codes`、`deferred_field_codes` 保留为**投影列**，由 `projectOriginMarkers(states)`（新增，纯函数）算出，写点不再自己拼：

| 列 | 投影规则 |
| --- | --- |
| `explicit_field_codes` | `effectiveOrigin` 取到的是覆盖行，且种类不是 `derive` 的字段（`status:*` 字段本来就不在这两列里）。`derive-edit`、`retain` 都算。含义收敛为“这个字段的值不由继承策略决定” |
| `deferred_field_codes` | 策略是 `deferred`，且 `effectiveOrigin` 没取到值（没有未挂起的覆盖行，也还没有 `resolved`）的字段 |

- 投影以“与基线各写点写出的列值一致”为准，S3 用对拍测试固定（同一组操作序列，新旧实现写出的两列逐版相等）。
- 派生字段进不进 explicit，基线分两种，投影照做：建单或修改申请时自动带出的（`derive`）不进；记录编辑带出、以及随这次变更写进后续记录的（`derive-edit`、目标上的 `forward-update`）进，因为基线 `appendForwardPayload` 把本次变更的全部字段并入 explicit（`forward-store.ts:18`、`:29`）。第 1 轮写的“`derive` 一律不进 explicit”只对前一种成立，已更正。草稿之后只改日期时，沿用哪些保存值由这个区别决定（AC-EMP-26）。
- 有意的差异只有一处：带值的行被回落后该字段从 explicit 移出、策略为 `deferred` 时回到 deferred（基线做不到，属于修复）。
- 两列是载荷版本的列，只在追加载荷版本时写。§4.4.2 第 16 行与 §4.4.4 这两处不追加版本的写入不会改已有版本的列，变化在下一版追加时体现。产品代码在阶段 ① 之后不再读这两列做判断（读取方全部改读字段状态，§4.6），所以这段滞后不影响结果；两列只为与基线对拍和排查保留。
- “人工意图”“员工本次输入”“保存值是否可信”三件事不再从 explicit 推断，改用 §4.6 的函数。

### 4.7 只追加怎么守

- 两类写入都只有 INSERT：来源表有 `forbid_audit_mutation` 触发器；`app_user` 只被授予 `SELECT, INSERT`。
- “撤回一个值”不是删行，是追加 `fallback`；“恢复”是追加 `restore`；“删除来源后保留”是追加 `retain`。
- 载荷版本链照旧只追加；回落导致载荷列被清空时，照常追加一版新载荷，“变更前”从上一版取。
- 来源行与载荷版本、审计在同一事务；事务回滚时一起回滚，不会出现有载荷无来源或反过来。

### 4.8 没有来源行的值（DEC-943 U5，已定）

DEC-402 下不回填。阶段 ① 合并前产生的载荷没有来源行。已定口径：**没有任何来源行的字段，按基线两列的口径判**——不在该版 `explicit_field_codes` 里的视为继承值（可信，与基线放行一致），在里面的视为不可信（与基线的 403 一致）。这样不回填也不改变旧数据上的结果，DEC-913 的升级用例不受影响。一旦该字段有了任何一条来源行，就只按来源行判。

### 4.9 只读接口：查一笔任职业务的字段来源（DEC-943 U6，已定）

`GET /api/tenant/employment/businesses/:id/field-origins`

供 HR 在任职业务详情里看“这个值是怎么来的”。只读，不带命令 ID，不写审计。前端见 F-531（后补），本设计不写前端。

**权限对象与披露上限：沿用该业务既有的读权，不新增授权对象、不新增授权项编码，授权版本不变。** 一条总规则（第 2 轮审查 P1）：**本接口返回的字段集合与值，不超过同一操作人此刻调详情接口 `GET /businesses/:id` 得到的内容**；来源只是附在详情内容上的说明，不是另一条读数据的通道。所以新路由不自己取值，而是与详情路由（`routes.ts:437–449`）逐步调用同一批既有函数，拿到详情会返回的那份内容之后再附来源。

**两条分支怎么出数**

| 分支 | 字段集合 | `value` | 来源 |
| --- | --- | --- | --- |
| 现值（`read.frozen` 为空） | `shown.fields` 的键（记 `preset:<名>`）、`shown.customFields` 的键（记 `custom:<ID>`），以及 `shown` 里出现的 `employeeStatus` / `entryStatus`（记 `status:…`） | 取 `shown` 里的值，不另从台账取值 | 读来源台账折叠后的当前状态（§4.3）：`origin`、`policy`、`pending`、`suspended` |
| 冻结（`read.frozen` 非空，已办审批人） | 同上，但 `shown` 已是“冻结内容 ∩ 披露集合 ∩ 当前字段权” | 冻结值 | **不读来源台账**：`origin = null`、`policy = null`、`pending = false`、`suspended = false` |

冻结分支不给来源的理由：来源台账记的是**现在**的状态。办理之后 HR 改过工作地，台账里最新一行就是这次修改（种类、时间、来源业务）；把它附在冻结值旁边，等于告诉已办审批人“这个值后来被改过、是谁的哪类操作改的”，这是详情接口不披露的现值信息。披露集合之外的字段在 `shown` 里本来就没有，所以整行不出现——不给值、不给来源、不给占位或计数。字段读权的裁剪由第 7 步的 `trimEmploymentResponse` 完成（预置字段按字段名、自定义字段按 `custom:<字段 ID>` 判），本接口不再另做一遍，避免两套口径。

现值分支的 `value` 也只取 `shown`：未落地的延迟继承字段，详情里是什么值这里就是什么值，“落地时还会再解析”由 `pending = true` 表达。

**统一 404（第 2 轮审查 P2-5）。** 第 4～6 步是“定位这笔业务并确认操作人能看它”。这三步抛出的 `AppError`，错误码是 `NOT_FOUND` 或 `FORBIDDEN` 的，新路由一律改抛同一个错误：`404 / NOT_FOUND / 任职业务不存在`，不带 `details`。实现是包住这三步的一处 `try / catch`，不逐点改文案。其它错误码原样抛出。

- 为什么 403 也归一：随机 UUID 没有调动行，第 4 步直接放行，在第 5 步得到 404；真实存在的调动单才可能在第 4 步得到 `404 / 员工不存在` 或资源级 403。不归一的话，文案和状态码都能用来区分“存在但不可见”与“不存在”。
- 第 6 步的权限点与第 2 步是同一个对象查看权（`tenant.employment.read` 是任职对象 `object.view` 的别名，`packages/domain/src/permission/module-actions.ts:652–680`），只是绑定了员工资源；它在业务已取到之后才判，按资源级拒绝处理，同样归一。
- 跨租户不需要单独判断：取数都在 `withTenant` 内按 `tenant_id` 进行，别的租户的业务就是“取不到”。
- 入口级的 401 / 403（第 2 步）、400（第 1 步）、503（第 3 步）不归一：它们与这笔业务是否存在无关（503 只在操作人本人办理过该审批实例时才会出现）。
- **与详情接口的差别**：详情接口不改，现状仍会返回 `404 / 员工不存在` 与资源级 403。这个差别是有意的，写进 AC-EMP-31 的对拍口径；详情接口自身是否也要归一不在本单范围，记入结果文件“未决 / 假设”。

**出参**（200）：

```ts
{
  businessId: string;
  contentView: { mode: string; instanceId: string | null }; // 与详情接口同一字段、同一取值
  fields: Array<{
    fieldCode: string; // 'preset:positionId' | 'custom:<id>' | 'status:employeeStatus' …

      kind: string; // 取到值的那一行的 origin_kind

```

- 只返回折叠后的当前状态，不返回历史来源行，不分页；行数上限 = 详情内容里的字段数。
- `sourceBusinessId` 指向另一笔任职业务。返回前用 `visibleEmploymentRecords`（`visibility.ts:61`）对这些来源业务批量判一次可见，对操作人不可见的置 `null`，种类与展示名照常返回。这样不会借来源接口探到范围外业务的 ID。
- 不返回操作人 ID、命令 ID、`match_before`、被挂起行的值。被挂起的值可能是操作人现在不该看到的旧值（例如 #99 要求员工预览不泄漏原职位），所以只给布尔。

### 4.10 阶段 ① 的权限、幂等与规模

- 新增一条只读路由（§4.9），没有新的写路由；不新增权限点，授权版本不变。
- 来源行随所属写命令的命令 ID 幂等：命令台账命中缓存时不重复写；`requireEmployeeTransferBusiness` 在返回缓存前仍会重跑（撤权后重放不放行）。

关于已保存的 `employee-input` 职位（已定，DEC-945 U7 甲）：这里说的是**有来源行、且来源是员工输入**的职位，即阶段 ① 上线之后、DEC-232 的只读限制对该员工生效之前，员工自己在草稿里填过的职位。它与 §4.8（U5）的“没有来源行”是两回事。这个保存值算可信：员工之后只改生效日或提交都放行；被拒的只有“换岗位”，即本次请求体里又出现了职位字段，由 J1 拦下（403）。J1 只看请求体里有没有这个字段，带同值、带 `null` 也算（§5.4 R1-P2-1e），这是 §9 U7 选项甲的原文。职位不属于有效部门时照常回落清空。这与 #99 的 AC-TRF-59 口径一致。职务、职级、序列三个字段不适用这一条，因为基线上员工从来不能写它们。

状态传播只写 `status:*` 行，所以它**不可能**成为这四个字段的最后写入来源；序列同步只写序列一行，所以不可能为职务、职级背书。这两条不需要专门的判断，是“逐字段记行”的直接结果。

## 6. 阶段 ②：迟到后重建

### 6.1 要替换什么：一个落地模块，四条路径各按基线位置接入

现状见 §2.3：`postponeLateTransfer`（`late-transfer.ts:136`）与 `postponeLateExit`（`exit-activation.ts:99`）在写入前调用 `assertNoRebuildRequired`（`late-transfer.ts:112`），区间 `[p, a)` 内只要有别的任职版本或在途申请，就抛 `REBUILD_REQUIRED`、记生效失败、交 HR。

第 1 轮的写法是“把这一步换成重建”，但基线上“改期”“前序判断”“落地”“向后更新”散在多个位置，各有各的先后。只换其中一步会留下三个结构问题：前驱还没重算就被后一条记录读走（P2-5）；审批路径在前序判断之前就重建，挂起后已经改了目标，解挂时又发一次传播（P2-8）；多笔迟到的结果取决于谁先批准（P2-9）。

### 6.3 总规则：先在内存里按次序算完，再一次写入

**重建结果 = f（最终时间轴，字段来源台账，传播命令台账）**。规划不读“上一次重建的输出”当输入，也不读库里尚未重算的后续记录的值。只有一个地方会读配置：某个派生没有任何历史锚点时（§6.5.3）。这一处按重建当刻的配置取值（DEC-945 U8），所以上面的等式有一个限定：首次解析出的派生值还取决于那一次重建发生在哪一天；一经记成锚点，之后的重建只读锚点，不再随配置变化。

`planLateRebuild`（纯函数，`packages/domain/src/employment/late-rebuild-plan.ts`，新增）的主要输入由 API 侧一次读齐：员工本任职周期在 `p` 之后的全部时间轴记录与在途申请、这些业务的来源行（§4.10 的行数上限）、该员工的传播命令。另有三类事实要算到某条记录才知道该查什么，按本节后文“事实补读”取。规划对“`p` 之后的记录”**按最终时间轴次序单遍处理**（`(start_date, sort_order)`；在途申请按 DEC-195 投影到生效日，只作目标，不作别人的前驱）。每条记录按种类算：

| 记录 | 怎么算 | 小节 |
| --- | --- | --- |
| 本次落地的 L | 覆盖层不动；策略层按最终位置的前驱重新继承 | §6.5.1 |
| 组织调整（集合 W） | 重新折叠：起点取前驱，再按 `seq` 重放事件 | §6.5.2 |
| 独立业务（含已落地的其它迟到业务、在途申请） | 不重新折叠，只做迟到命令的值匹配 | §6.6、§6.8 |

**前驱一律取本轮规划结果**。处理到某条记录时，排在它前面的记录都已经算完；它读前驱的值，读的是内存里刚算出的结果，库里的旧值只在“前驱不在重建范围内”（排在 `p` 之前）时才用。这是 P2-5 的修法，例子：

> 入职 H（工作地甲）；迟到调动 L 不改工作地（继承）；组织调整 O 复制前驱（甲）。HR 把历史记录 H 的工作地改成乙——历史记录的编辑不向后传播（`forward-rules.ts:16` `isForwardEditSupported`），O 仍是甲。L 迟到落地，最终次序 H → O → L。
> 规划先算 O：复制 H 的当前值，得乙。再算 L：继承前驱 O 的**规划结果**，得乙。第 1 轮的写法先算 L（读到库里 O 的旧值甲）再算 O，要跑第二次 L 才变成乙。AC-ORG-38 断言首轮 O、L 都是乙，第二轮值、版本数、来源行数都不变。

一遍够用的理由：组织调整只依赖排在它前面的记录；独立业务只依赖迟到命令的 `before` / `after`，`after` 是迟到业务自己的覆盖层内容（与位置无关），`before` 取自排在候选下界之前的记录（§6.6）；L 的策略层只依赖它的前驱。没有反向依赖。

写入（`applyRebuildPlan`）把规划结果与库中当前值逐字段比较，只写有差别的（§6.5.2 末尾的三种结果），所以**同一输入再跑一次不产生任何新行**。

**事实补读。** 三类判断要读库，规划自己不读（它是纯函数，`packages/domain` 禁止 IO）：

| 事实 | 键 | API 侧怎么读 |
| --- | --- | --- |
| 引用在某天是否可用 | `(字段, 引用值, 目标生效日)`，与基线缓存键相同 | 基线 `availableForwardChanges` 里的可用性查询（`forward-references.ts:68`） |
| 换成某位经理是否成环 | `(目标业务, 经理, 目标在最终时间轴上的有效区间)` | `findReportingCycle`（`reporting-cycle.ts:64`），区间由规划给出，不读库里的旧区间 |
| 派生锚点与配置 | `(业务, 字段, 规则, ref)` | `loadDerivationAnchors`（§4.6）；没有锚点时按 §6.5.3 第 3 步读配置，日期取本次落地的实际执行日 `a` |

规划的入参带一张事实表 `facts`。处理到某条记录时缺事实，规划就停在这条记录，返回它需要的全部键；这时排在它前面的记录都已算完，它要查哪些键是确定的。API 侧（`late-rebuild.ts`）一次查询补齐，并入 `facts` 后再调规划。规划对相同入参的结果确定，所以“再调一次”与“从这条记录接着算”等价。补读次数不超过需要判这三类事实的记录数（上限见 §6.9），与基线逐目标判的查询次数同量级；键相同的不重复读。这三类事实都不依赖本次规划写出的值：引用可用性只看引用对象自己的启停，成环只看别的员工的汇报链，锚点是历史行，配置按 `a` 读（同一次重建里各条记录读的是同一天，`(规则, ref)` 相同的只读一次）。

**锁序**不变：员工闭包 → 业务头（ID 升序）→ 组织 → 编制（只读），与 DEC-269 写的顺序一致，在段 ① 之前取齐。

### 6.4 操作人范围与失败时的状态（P1-1）

基线上审批中心以可信身份推进任职状态，不带数据范围（`approval/adapters.ts:204` `employmentTransition` 的注释；`requireEmploymentWrite` `context.ts:276` 在没有 `ctx.authorize` 时直接返回，`employmentVisibilitySql` `visibility.ts:40` 在没有 `ctx.scope` 时用真谓词）。迟到重建要改写**别的业务**的记录，如果沿用这个上下文，审批人就能借一次同意改到自己范围外的记录。

所以 `beginLanding` 的 `actor` 是**必填入参**，重建对目标的可见性判断（DEC-177 / DEC-178）与字段写权只用它，不读 `ctx.scope` / `ctx.authorize`：

```ts
type RebuildActor =
  | { kind: 'system' } // 只允许定时入口构造
  | { kind: 'operator'; scope: ModuleScope; authorize: Authorizer };
```

| 触发 | `actor` 从哪来 |
| --- | --- |
| 定时生效 | `{ kind: 'system' }`。只有 `activateDueBusinesses` 能构造，守卫测试检查没有第二个构造点 |
| HR 重试 | `scopedGuard`（`context.ts:575`）已解析的 `ctx.scope` 与 `ctx.authorize` |
| 审批通过即落地（普通同意、编辑并同意） | 审批路由的写上下文（`approval/routes.ts:155–162`）新注入 `lateRebuildAuthorize: deps.authorize`，写法照同一处已有的 `exitEditAuthorize`、`handlingAuthorize`。适配器在**审批命令的事务内**用 `resolveModuleScopeInTransaction({ authorize, clock }, ctx, tx, 任职对象)`（`permission/module-access.ts:80`）解析审批人的任职模块范围，用 `authorizeInTransaction(authorize, tx)`（`:36`）得到字段写权判断，**只传给 `beginLanding` 的 `actor`** |
| 没有注入（含系统自动完成的审批） | 按空范围 `EMPTY_SCOPE`（fail-closed）：只要重建需要改写别的业务就失败 |

故意不叫 `authorize`、不放进 `ctx.scope`：那样会让普通审批的全部任职写入都改按审批人的范围判，改变既有语义（审批不授予范围，DEC-057；审批人只看本单字段）。范围只在“迟到重建改写别的业务”这一处生效。**不迟到的审批、迟到但没有别的记录要改的审批，行为与基线完全相同**：前者 `finishLanding` 只执行基线的落地语句，后者不会走到下面的任何一处检查。

**写目标的检查处**（同类位置清单，DEC-431①）。重建写任何一条 L 以外的记录之前，都经模块里同一个函数（暂名 `requireRebuildTarget(actor, 目标, 要写的字段)`）。它只做下面三项，和基线向后更新写目标时的三项一一对应：

| # | 检查 | 基线对应位置 | 重建里怎么判 | 被拒时 `detail.code` |
| --- | --- | --- | --- | --- |
| 1 | 目标可见（写前） | `forward-update.ts:166` `linked(目标当前部门)` → `requireLinkedEmploymentRecord`（`context.ts:265`） | 用 `actor.scope` 判目标当前部门 | `LINKED_RECORD_OUT_OF_SCOPE` |
| 2 | 目标可见（写后） | `forward-update.ts:185` `linked(替换后的部门)` | 用 `actor.scope` 判替换后的部门 | `LINKED_RECORD_OUT_OF_SCOPE` |
| 3 | 字段写权 | `forward-update.ts:187` `requireEmploymentWrite` → `permission/object-write.ts:21` → `authorization.ts:27`，抛 `FORBIDDEN` | 用 `actor.authorize` 调 `requireObjectWrite`，字段取本次要写的非系统字段 | `REBUILD_FIELD_WRITE_DENIED`（暂名） |

三项的范围：

- `{ kind: 'system' }` 三项都跳过。L 自己的记录不判：那是这笔业务自己的内容，由审批或定时落地授权，基线也不判。
- 字段写权只判**非系统字段**：值匹配替换的字段、重新折叠后变了的字段、连带的派生字段（序列、直线经理）。`employType`、人员状态这类系统派生不送字段写权——授权器要求“每个字段都是已登记的非系统字段”（`object-write.ts:4`），基线的状态传播也只判可见（`employee-status.ts:338` `propagateEmployeeStatus`）。
- 四类写点都经这个函数：组织调整重新折叠（§6.5.2）、迟到命令的值匹配（§6.6）、撤回重放（§6.8）、状态传播重放（§6.5.2，只判第 1 项）。S2b' 的守卫测试检查 `applyRebuildPlan` 写目标的语句前都有它。

**拒绝怎么变成“生效失败”**（第 2 轮审查 P2-1）。基线审批路径只认 `activationFailureOf`（`transitions.ts:285`；定义在 `activation-checks.ts:205`，读错误 `details.activationFailure`）。字段写权被拒时，基线抛的是 `FORBIDDEN`，它既不带 `activationFailure`，也不在 `RULE_REJECTIONS`（`activation-checks.ts:103`）里；直接让它抛出，审批事务就整体回滚，任务也不完成。

本单的做法是**只在上表三项检查处**转换，别处不动：

- `requireRebuildTarget` 自己判出不可见时，以及它调 `requireObjectWrite` 的**那一次调用**抛出 `FORBIDDEN` 时，改抛 `new AppError('CONFLICT', …, { activationFailure: { reason: 'RULE_REJECTED', detail: { code, affected } } })`。`affected` 是被拒的记录数。
- 审批路径的识别式不改，仍是 `activationFailureOf`；不接 `ruleRejection`，不把 `FORBIDDEN` 加进 `RULE_REJECTIONS`。
- 所以审批自己的 403（审批人不是该任务的办理人、没有审批入口权限、节点编辑越权）、节点编辑的校验错误、落地时其它不带 `activationFailure` 的错误，都照基线原样抛出：审批不完成、整笔回滚、可以重提。

失败时各项的状态（审批路径；回归 AC-TRF-73）：

| 项 | 结果 |
| --- | --- |
| 目标记录、字段来源台账、传播命令台账 | 保存点整体回滚，**零写入**；L 自己的改期版本、任职记录也一起撤销（§6.1 I2） |
| 节点编辑（编辑并同意） | **保留**。它在审批命令里先于落地保存（`approval/actions.ts:344–349` `applyEdit`），不在重建的保存点内 |
| 审批动作 | **成功**。任务完成、实例照常流转，申请状态停在“审批通过”（`approved`），不变成“已生效” |
| 生效 | 同一事务记一条生效失败：`trigger: 'approval'`，原因 `RULE_REJECTED`，`detail.code` 取上表 |
| 返回给审批人 | 审批成功的正常响应；失败明细只给原因码与受影响记录数，不带目标记录的字段值、部门、业务 ID |
| 之后 | 按 DEC-052，定时任务不自动重试失败项；由范围和字段写权都覆盖这些记录的 HR 用 `POST …/activation/retry` 重试 |

定时与 HR 重试路径、离职路径的外层本来就接 `activationFailureOf ?? ruleRejection`（`activation-checks.ts:198`、`exit-activation.ts:589`），同一个带 `activationFailure` 的错误在那里记成同样的失败记录；HR 重试的响应沿用现有的失败回执。

审批路径只是多了一种“审批通过但未生效”的原因，状态机不变（硬规则“审批通过 ≠ 生效”）。

### 6.5 规划：每条记录怎么算

#### 6.5.1 L 自身

| 字段状态（§5.3 的记号） | 重建时 |
| --- | --- |
| 覆盖适用（Z3、Z4） | 值不动。这是这笔业务自己的内容 |
| 策略:继承，无适用覆盖（Z1、Z5） | 从最终位置的前驱（规划结果）重新取值，追加新的 `inherit` 行（带新的 `source_record_id`） |
| 策略:延迟（Z2、Z6） | 未落地：保持待定，落地时按最终前驱解析。已落地：按最终前驱重新解析，追加新的 `resolved` 行 |
| 策略:无 | 保持空，不从前驱补回（R6-P2-03） |
| 派生字段 | 按 §6.5.3 的锚点规则 |
| `employType` 等系统派生、人员状态 | 按最终前驱 / 任职周期重算（现有 `rederiveRepositionedStatus` `employee-status.ts:243`；R7-P2-02、R8-P2-04），不走继承矩阵 |

DEC-232 的职位规则（#99 重做后）在这一步经 `settleFieldValues`（§4.6）复判：L 重新继承后部门变了，职位按 J3 重新判保留 / 清空。

#### 6.5.2 组织调整记录的重新折叠

**重算集合 W**：同一员工、同一任职周期（StaffID 相同）、`kind = 'org_adjustment'`、最终位置在 `p` 之后的全部记录。不只取窗口 `[p, a)` 内的：窗口外的组织调整若复制自窗口内的记录，也要跟着变（R8V3-P2-01）。上限见 §6.9。

W 里每条记录 O 的每个字段这样算：

1. **起点**。折叠 O 的**全部**来源行，调 `effectiveOrigin`（§4.3），不单独读“创建版”：
   - 取到覆盖行（创建版的 `hr-input` / `system-input`、之后的人工编辑、`retain`）→ 这是 O 自己的内容，值就取这一行，重建不改写（DEC-255①）。例如 F-006 调整后的经理、首版就人工填了的工作地。
   - 没有适用的覆盖行，策略是 `copy`（纯联动复制，F-007）或 `inherit`（F-006 这类按表单继承矩阵生成的组织调整）→ 值取 O 在**最终时间轴上的直接前驱的规划结果**，不取策略行里存的旧值（R8V3-P2-01 期望“O2 读到 O1 的当前结果甲”）。取到的值若与 O 库中的当前值不同，先过目标级拒绝规则（本节后文）；被拒的字段，规划结果就是 O 的当前值。
   - 策略是 `none` → 保持空（R6-P2-03 十二例、R8-P2-03）。用哪套矩阵由创建时的策略行决定，重建不重新读继承开关（DEC-244③）。
2. **按 `seq` 依次重放 O 创建之后的传播命令**（两张台账合并排序，人工覆盖行已在第 1 步的折叠里按 `seq` 体现：一条命令只能作用于 `seq` 比它小的人工值）：

| 事件 | 处理 |
| --- | --- |
| `forward-update`，`trigger` 不是 `late-execution` | 先判来源：来源没有被删除、来源在最终时间轴上仍排在 O 之前、且命令记下的来源位置（`source_point`）等于来源的最终位置；不满足就整条不重放（来源被改期的旧命令作废，由迟到命令取代）。再按该命令的 `before′` / `after′` **先判整条跳过**（`skipsWholeRecord`，`forward-rules.ts:39`：部门、职位同时变化而 O 的部门、职位不全等于变动前值，整条不更新，DEC-120），通过后才逐字段匹配：字段在该命令 `config` 的允许集合内，且 O 此刻的值等于 `before′`，成为候选替换。候选替换再过**目标级拒绝规则**（本节后文）：被拒的字段不替换，其余字段照常替换成 `after′`。当时零命中的命令也照此重新判断 |
| `forward-update`，`trigger = 'late-execution'` | 不重放。组织调整不是迟到命令的候选（DEC-943 U2），它们通过“复制 / 继承前驱”拿到结果 |
| `status-propagate` | 候选条件与 `propagationTargets`（`employee-status.ts:375`）相同，单独判，不套值匹配的规则：来源没有被删除；O 与来源同一任职周期、不是兼职；O 的最终位置在命令记下的来源位置之后；有 `until` 时 O 的最终位置在 `until` 之前；O 此刻的人员状态等于 `from`。成立则状态改成 `to`，**O 的 `entryStatus` 保留自身值**（F-007 设计 C-4） |
| `fallback` / `restore` | 按 §4.3 |

`before′` / `after′` 按命令的 `source_version_no` 还原，**不是统一取来源的最终值**（P2-6）：

- 来源不在重建范围内（排在 `p` 之前，或是不被重新折叠的独立业务）：就是命令 `changes` 里记下的前后值。同一来源先后把工作地由甲改乙、再由乙改丙，是两条命令，分别用 甲→乙、乙→丙 重放。
- 来源在 W 内：规划折叠来源时，在它每个“发过命令的版本”处各记一份该版写入前、写入后的整版值，重放时取对应版本的那一份。`trigger = 'materialize'` 的命令（来源落地时发），写入前的值取来源最终前驱的规划结果。

3. **派生字段**（序列、直线经理）最后算，见 §6.5.3。
4. **系统派生**（`employType`、人员状态）按最终前驱重算；被 `retain` 固定的除外（R8-P2-04）。

**目标级拒绝规则**（第 2 轮审查 P2-4）。基线的普通传播在值匹配之后，还要按目标再判两项（`forward-update.ts:167–183`，`forward-references.ts:68` `availableForwardChanges`）；只读的控编推演用的也是这一组规则（`org-adjustment-projection.ts:49`）。重建里凡是要给目标的引用字段写一个**与库中当前值不同**的值，都照做，否则会补写原命令当时拒绝的值：

- **引用可用性。** 引用字段指部门、职位、职务、职级、职等、序列、专业条线、直线经理、虚线经理。按**目标记录自己的生效日**判这个值那天是否可用（`forward-references.ts:43` `referenceCheckDate`，DEC-079 / DEC-110），与重建哪天执行无关。不可用只排除这个字段。
- **经理成环。** 直线经理换成新值后，如果在目标的有效区间内形成循环汇报（`forward-references.ts:57` `formsCycle`；区间按目标的最终位置取），只排除这个字段。
- **被排除的字段**值保持目标的库中当前值：不追加载荷版本、不记来源行，排在它后面的记录读到的也是这个值。同一次写入里通过的字段照常写。排除的字段记进重建审计的 `skipped`（原因 `REFERENCE_UNAVAILABLE` / `REPORTING_CYCLE`，与基线向后更新的回执同名）。

例子：HR 在记录 S 上同时把直线经理改成丙、把工作地改成乙。组织调整 O 排在 S 之后，丙在 O 的有效区间内向该员工汇报。当时的传播命令只改了 O 的工作地，经理因成环被跳过。之后一次迟到重建重新折叠 O：起点从前驱取到经理丙，重放那条命令时丙又一次成为候选，两处都被本规则拒绝。结果 O 的工作地是乙，经理仍是原值，没有新的经理来源行（AC-ORG-39）。

算出的结果与 O 当前值逐字段比较：

- 值不同 → 追加一版记录快照载荷（`is_record_snapshot = true`），并为变了的字段记来源行。
- 值相同但依据变了（例如前驱换了一条）→ 不追加载荷版本，只追加来源行（新的 `copy` / `inherit`，带新的 `source_record_id`）。之后删除来源时要靠它找“实际依赖”（R8V2-P2-01）。
- 值和依据都没变 → 什么都不写。

#### 6.5.3 派生锚点规则

（R6-P2-02、R8-P2-02、R8V2-P2-02、R8V4-P2-02。）派生字段没有适用的人工覆盖时：

1. 算出本次折叠里**实际起作用的引用** `ref` 及其规则。序列有两种来源，分开算、分开存：按职务带出是 `(post-sequence, 职务 ID)`，按职位同步是 `(position-sequence, 职位 ID)`；直线经理是 `(department-manager, 部门 ID)` 或 `(position-manager, 职位 ID)`。哪一种起作用，看该字段最近一条派生类来源行（`derive`、`derive-edit`、`sequence-sync`）的 `derivation_rule`。
2. 用 `loadDerivationAnchors(tx, ctx, businessId, keys)`（§4.6）按 `(字段, 规则, ref)` **定点**读这条记录最近的一条锚点（走 §4.1 的部分索引，不把全部锚点载入）。**找到就用锚点的值**，不读配置。规划是纯函数，锚点和第 3 步的配置都经 §6.3 的“事实补读”取得：规划算到这条记录时报出缺的键，API 侧定点读回后再继续。
3. 找不到 → 按**重建当刻**的配置读一次（已定，DEC-945 U8 甲），并追加一条 `derive` 锚点行（规则、`ref`、结果）。“重建当刻”指本次落地事务执行的那一天，也就是本次 L 的实际执行日 `a`（租户时区，DEC-056）：基线的三条规则调 `resolveDerivation`，日期参数传 `a`，不传这条记录自己的生效日；`position-sequence` 不在这个函数里，按同一天读该职位当天版本上的序列（`loadJobObject`，`job/read-model.ts:97`）。之后再遇到同一个 `(规则, ref)` 就用这次的结果。解析出的值与库中当前值不同时，再过目标级拒绝规则（§6.5.2）；被拒时字段保持当前值，这一次不记锚点。

三点说明：

- `derive`（建单 / 修改申请时带出）、`derive-edit`（记录编辑或传播实际写入）、`sequence-sync` 三种行都是锚点（§4.2）。“职务不变、职位变了”时，`(post-sequence, 职务)` 的锚点仍在，但起作用的是 `(position-sequence, 新职位)`；两者不互相顶替（P2-4）。
- 合法传播把引用换成了新值时，派生跟着新引用走（R8V4-P2-02）：第 1、2 步用的是折叠后的 `ref`，自然覆盖这种情况。
- 第 3 步取重建当刻，只管重建这一步。建单、修改申请、记录编辑带出派生值仍是基线口径，本单不改：`resolveDerivation(tx, tenantId, employeeId, date, origin)`（`field-derivations.ts:40`）按传入日期读职务、职位、部门负责人与在岗人，建单时传的是记录生效日（`:100`）。重建调的是同一个函数，只是日期换成 `a`。返回值照基线处理（`:101`）：`undefined` 表示这条规则没有产出，字段保持当前值、不记锚点；`null` 是明确的空值，照常写入并记锚点。

**U8 选甲后的核对与口径交界**（DEC-945 要求；U1、DEC-269 都不改）。先逐条核对第 3 步会不会碰到 DEC-269 的例子和 U1：

| 对象 | 走不走第 3 步 | 结论 |
| --- | --- | --- |
| L 自己（例①：调入市场部、经理老李） | 经理是手填的：覆盖层，不走。是建单时带出的：L 上已有 `derive` 锚点，第 2 步命中，不读配置；建单之后市场部换了负责人，L 仍是老李。落地时才第一次解析的（延迟继承，引用到落地才确定）走第 3 步，但 L 的生效日就是 `a`，“重建当刻”与“记录生效日”是同一天 | 与原推荐项没有差别 |
| 区间内的独立业务（例③：10-11 只改职级的调动，销售部、老王） | 不走。独立业务不重新折叠、不做派生解析，只按值匹配（§6.6）：等于 `before` 的换成 `after`，`after` 是 L 的最终值（市场部、老李） | 例③ 的结果不变 |
| 已是别的值的独立业务（例④：研发部、老赵） | 不走。不等于 `before`，不命中、不动，也不重新带出 | 例④ 的结果不变 |
| U1 A（候选下界取原计划位置、按值替换） | U1 定的是候选范围与 `before` / `after` 的取法；第 3 步不改这三样 | 不冲突 |
| W 里的组织调整 O（生效日 `d`，通常 `d ≠ a`） | 走。O 的引用在本次重建里第一次变成一个没有锚点的值时，按 `a` 的配置取，不按 `d` | 甲与原推荐项真正不同的地方 |

结论：U8 甲与 U1 A、DEC-269 例③ **没有冲突**。值匹配只作用于独立业务，第 3 步只作用于 L 与组织调整（组织调整不参加值匹配，DEC-943 U2 甲），两者不落在同一条记录的同一个字段上。但选甲带来四处口径交界，本文按下面的取舍写死：

1. **同一区间里，两类记录上同一个部门的经理可以不同。** 独立业务拿到的是 L 的值；组织调整第一次带出时拿到的是重建当天的配置。例：L 调入市场部（老李），区间内的独立业务 B 被换成市场部、老李；排在 B 之后的组织调整 O 复制 B，部门第一次变成市场部，它的经理是按部门带出的；重建之前市场部的负责人已换成老赵 → O 的经理是老赵，B 仍是老李。两条规则各自照做，不互相对齐：不把例③ 的“老李”推广到组织调整（那是按值匹配，U2 已定不用），也不让 B 重新带出。AC-TRF-67 与 AC-ORG-41 各自固定。
2. **“与落地先后无关”的承诺要加前提（U9）。** 首次解析的值取决于“第一次需要它的那次重建”读到的配置。两笔迟到的落地之间相关配置改了，交换先后就可能在不同的时点第一次解析，得到不同的锚点；这个值还会经复制、继承、迟到命令的 `after` 传给别的记录。取舍：§6.8 的承诺保留，前提加上“两次落地之间相关的派生配置没有改动”；改动了的，以首次解析那一次读到的为准，不要求两种先后相同（已知行为，AC-ORG-41）。
3. **目标级拒绝规则不放宽（DEC-079 / 110）。** 按 `a` 读到的经理、序列，仍按目标自己的生效日判引用可用性、按目标的最终区间判成环（§6.5.2）。重建当天的负责人在目标生效日那天还不可用，是选甲之后多出来的被拒情形：字段保持当前值、不记锚点，下一次重建按那时的配置再读。
4. **结果取决于哪天重建。** 这是选项甲原文写明的后果，用户知情选择（§9 U8）：HR 改部门负责人时选的“不调整员工的直线经理”，对之后才第一次解析的记录不起作用；生效日在过去的记录上可能出现之后才上任的经理。落地失败回滚后改天重试，按重试那天的配置取（锚点与重建同事务，回滚时一起撤销）；成功之后再跑命中锚点，不再变。

### 6.7 删除来源后保留（DEC-244②）

基线上删除入口是 `deleteEmploymentBusiness`（`transitions.ts:404`）：不级联、不重算。阶段 ② 之前，后续记录的值没人去动，自然保留；有了重建之后，必须显式记下来，否则下一次无关的迟到重建会把它们撤回（R7-P2-03、R8V2-P2-01）。

- 删除来源 S 时，在同一事务里找出**当前实际依赖 S** 的字段：同一员工后续记录上，`lastWriter`（§4.3 的取值规则算出的那一行）的 `source_business_id = S` 或 `source_record_id` 属于 S 的字段（用 §4.1 的第二个索引）。包括历次重建追加的依据行，所以“重建后才开始依赖 S”的也能找到（R8V2-P2-01）；系统派生字段（`employType`、人员状态）同样按依据行找（R8-P2-04）。
- 为每个这样的字段追加一条 `retain` 行，`value` = **删除时的当前值**（含之前重建的结果），`reason = 'source-deleted'`。不追加载荷版本，值没有变。
- `retain` 是覆盖行，重建时**按人工值对待**（§6.5.2 第 1 步）：之后前驱怎么变，这个字段都不跟着变；只有新的人工覆盖或新的合法传播命令能改它。排在它后面、复制它的组织调整照常读到这个保留值（AC-ORG-47）。
- `retain` 只在删除来源时写。来源只是改期（迟到）时不写，改期后按 §6.5.2 的规则重新判断（R8V4-P2-03：不能把“删除后保留”推广成“改期时一律保留”）。
- 撤销离职、作废申请不是“删除来源”：已批准未生效的离职撤销是作废申请，没有版本可删（DEC-215，R8-P2-06）；已生效离职的撤销走既有恢复逻辑（`deletion-guards.ts` 的 `employment.record.restore`），离职本来就不是传播来源，不产生 `retain`。

### 6.8 多笔迟到与离职

**多笔迟到的唯一次序（P2-9；已定，DEC-945 U9 甲）。** 同一员工两笔迟到 L1、L2 都改同一个字段时，第 1 轮的写法是“各自匹配一次”，结果取决于谁先落地：未来草稿 X 的工作地是甲，L1 改乙、L2 改丙，先落地 L1 则 X 停在乙（L2 找不到甲），先落地 L2 则 X 停在丙。同一份最终数据出现两种结果，不能作为契约。

本设计给出唯一规则，叫**如期视图**（DEC-945 的写法是“按生效日排定视图”，生效日指各笔迟到的原计划生效日）：把本周期内每笔已落地的迟到业务（含本次的 L）放回各自的原计划位置，其它记录位置不变，同一位置按原计划日 → 操作序号排（与 C-3 `timelinePosition` 同一规则）。迟到命令的三件事都在这个视图里定：

| 项 | 规则 |
| --- | --- |
| 先后 | 各条迟到命令按如期视图里来源的先后依次生效。与真实批准、落地的先后无关 |
| `before` | 如期视图里来源的直接前驱的值。前驱若也是迟到业务：该字段是它的覆盖层内容就取它的值，只是继承来的就继续向前找（如期执行时它只是把前一条的值传下来） |
| 候选 | 如期视图里排在来源之后的独立业务。排在它前面的迟到业务不是它的候选，即使最终生效日更晚 |

落地一笔新的 L 时，若已有落地的迟到业务在如期视图里排在 L **之后**（记为集合 Q），规划对每个候选字段做“撤回再重放”：

1. **撤回**：该字段的 `lastWriter` 若是 Q 中某条迟到命令写的 `forward-update` 行，沿 `match_before` 退回到这串迟到写入之前的值。`lastWriter` 是人工写入或别的来源时不撤回，人工值保持。
2. **重放**：先应用 L 的命令，再按如期视图的先后应用 Q 中各条命令。Q 中的命令只在两种情况下重新匹配某个字段：它的 `before` 因 L 的插入而变了；或该字段在本次规划里已经被撤回 / 被前面的命令替换。其余字段保持现值。
3. Q 为空（L 在如期视图里排最后）时不需要撤回，直接应用 L 的命令。

Q 中命令重新写入的行仍记在原来的来源业务名下（`source_business_id`、`source_version_no` 不变），不新增传播命令；本次落地只新增 L 的那一条。

上面的例子按此规则：L1 原计划日早于 L2。先落地 L1 再落地 L2——L2 的 `before` 是 L1 的值乙，X 由乙改丙。先落地 L2 再落地 L1——X 先被改成丙；L1 落地时 Q = {L2}，X 撤回到甲，L1 改成乙，L2 的 `before` 变成乙、再改成丙。两种先后都是丙，也等于两笔都如期执行时的结果。

**承诺的范围**（AC-TRF-70）：最终时间轴相同、人工写入相同的两份数据，只交换迟到业务的落地先后，重建后每个字段的值、每个字段的来源折叠状态（`lastWriter` 的种类、来源业务、值）相同；只追加的行数可以不同。人工写入夹在两次落地之间时，按“人工值不撤回、之后生效的命令照常按值匹配”处理，这是不同的输入，不在“交换先后”的范围内；它的行为单独用 AC-TRF-75 固定（其中一例两种先后的结果确实不同）。组织调整每次都从“最终时间轴 + 台账”重新折叠，除下面说的派生首次解析之外与先后无关。

派生字段另有一个前提（DEC-945 U8，§6.5.3 交界 2）：没有锚点的引用第一次解析时取重建当刻的配置。所以承诺只在“两次落地之间相关的派生配置没有改动”时覆盖派生字段；改动了的，派生字段以及由它传下去的值（复制、继承、迟到命令的 `after`）以首次解析那一次读到的为准，两种先后可以不同。AC-TRF-70 的夹具用工作地，不是派生字段，不受这个前提影响；派生字段的行为由 AC-ORG-41 固定。

### U1 迟到区间内的独立业务，要不要按值匹配替换——已定（DEC-943）：选 A

- **作用对象**：复刻系统（迟到执行后的任职记录内容）。
- **背景**：DEC-269 的例③写的是替换；#83 设计 v4 改成了不替换（审查称为 A′），审查 R8V4-P2-03 指出这没有经过批准。
- **选项 A（已选）**：照 DEC-269 字面。迟到业务按“补录一条更早生效的记录”处理，原计划日到实际执行日之间的独立业务也参加值匹配。迟到业务自己的生效日仍是实际执行日。
- **选项 B（未选）**：只有排在实际执行日之后的独立业务参加值匹配；区间内的不动。
- **白话例子**：老张 10-05 调入市场部（经理老李），这笔调动拖到 10-12 才执行。10-11 有一笔只改职级的调动按期生效了，上面写着“销售部、经理老王”。按 A：10-11 那条改成“市场部、老李”。结果是 10-11 的记录已经显示市场部，而调入市场部这笔调动本身 10-12 才生效。
- **正文落点**：§6.6 的候选下界写成常量（`candidateFloor = 'planned'`），不留开关；AC-TRF-67 例③的期望是“被替换”。
- **与 U9 的区别**：U1 定的是“哪些记录算候选”（下界在哪）；U9 定的是“两笔迟到都把同一条记录当候选时，谁先谁后”。U1 选 A 之后候选范围变大，U9 的情形更容易出现，所以必须有唯一顺序。

### U2 选 A 时，区间内的组织调整记录是否也按值匹配替换——已定（DEC-943）：选甲

- **作用对象**：复刻系统。

- **选项乙（未选）**：和独立业务一样，等于旧值就替换成迟到业务的新值。

### U7 已保存的员工本人职位是否可信——已定（DEC-945）：选甲

- **选项丙（未选）**：读迟到业务原计划日那天的配置。
- **白话例子**：市场部原来的负责人是老李。10-20，HR 把市场部的上级改成了老赵，并选择“不调整员工的直线经理”。老张有一条 10-08 生效的组织调整记录，重建后它的部门第一次变成市场部，需要带出经理。
  - 选甲：看重建是哪天跑的。10-15 跑，经理是老李；10-25 跑，经理是老赵。同一份最终数据，哪天重建决定了结果；HR 当时选的“不调整员工经理”在 10-25 之后被绕过。
  - 选乙：这条记录 10-08 生效，就看 10-08 的配置，经理是老李。哪天重建都一样。
  - 选丙：看迟到调动原计划的 10-05，经理也是老李；但如果这条记录是 10-22 生效的，按丙仍是老李，与它生效当天实际的负责人（老赵）不一致。
- **按所选口径（甲）**：例子里重建在改上级之后执行（10-25），这条 10-08 生效的记录经理取**老赵**，并记为锚点；之后再重建不变。
- **当时推荐乙的理由（未采纳，留作记录）**：基线建单时带出派生值是按记录生效日读配置（`resolveDerivation` 的日期参数），重建沿用同一口径；结果与重建执行时间、两笔迟到的先后无关。
- **与 U1 A、DEC-269 例③ 的核对**：没有冲突。逐条核对与四处口径交界的取舍见 §6.5.3：同一区间两类记录的经理可以不同；“与落地先后无关”的承诺加前提；目标级拒绝规则不放宽；结果取决于哪天重建。U1、DEC-269 不改。
- **正文落点**：§6.5.3 第 3 步的取数日期取本次落地的实际执行日 `a`；§6.3 的限定；§6.8 承诺范围的前提；AC-ORG-41 的期望值（切片 S3'）。锚点“同一 `(规则, 引用)` 只解析一次”的规则不变。

### U9 两笔迟到争用同一旧值时，以什么顺序决定最终值——已定（DEC-945）：选甲

- **作用对象**：复刻系统（多笔迟到落地后，独立业务上的字段值）。
- **问题**：同一员工两笔迟到 L1、L2 都改同一个字段，后面有一条独立业务的这个字段等于旧值。两笔都想替换它，最后是谁的值？
- **与 U1 的区别**：U1 定候选范围（下界在哪）；U9 定两笔迟到的先后。U1 已选 A，不受本项影响。
- **选项甲（已选）**：按**如期视图**的唯一顺序（§6.8；DEC-945 的写法是“按生效日排定视图”）。把每笔迟到放回它的原计划位置，按“原计划日 → 操作序号”排先后；后落地的一笔若在这个顺序里排在前面，先撤回排在它后面的那笔写入的值，再依次重放。结果与真实批准、落地的先后无关，等于两笔都如期执行时的结果。
- **选项乙（未选）**：按真实执行次序，各自匹配一次，先落地的先替换。需要同步修订：§6.8“与执行先后无关”的承诺删去；AC-TRF-70 改成两种批准次序各写一个期望，并写明这是有意的。
- **白话例子**：老张有一张未来的调动草稿 X，工作地是“北京”。L1（原计划 10-05）把工作地改成“上海”，L2（原计划 10-08）把工作地改成“深圳”，两笔都迟到。
  - 选甲：不管先批哪一笔，X 最后都是“深圳”。按原计划 L1 在前：L1 把北京换成上海，L2 再把上海换成深圳，与两笔都按时执行的结果相同。
  - 选乙：先批 L1，X 由“北京”变“上海”，L2 再来时找不到“北京”，X 停在“上海”；先批 L2，X 由“北京”变“深圳”，L1 再来时找不到“北京”，X 停在“深圳”。同一份最终数据出现两种结果。
- **选甲的依据**：审查 P2-9 要求同一输入只有一个契约；审批人按什么顺序点“同意”不应决定员工的任职内容。
- **承诺的范围**：只对“最终时间轴相同、人工写入相同、只交换迟到业务的落地先后”这一种输入承诺结果相同（§6.8）。人工写入夹在两次落地之间属于不同的输入。派生字段另有前提：两次落地之间相关的派生配置没有改动（U8 选甲的后果，§6.5.3 交界 2）。
- **正文落点**：§6.8 的如期视图与撤回再重放；AC-TRF-70 的唯一期望（切片 S6'）；AC-TRF-75。§6.6 的匹配规则不变。
