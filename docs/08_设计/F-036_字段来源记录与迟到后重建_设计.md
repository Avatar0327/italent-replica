# F-036 字段来源记录与迟到后重建 设计

> 状态：设计第 1 轮，待审。只是设计文档，不含产品代码、迁移、测试。
> 基线：main `b0e4dad2f`。文中的文件路径与行号都按这个基线核对过；标“新增”的在基线上不存在。
> 作用对象：全文所有决定与待决项只影响**复刻系统**，不涉及北森测试租户。
> 待决项集中在 §9（U1～U6）。正文凡写“待确认（Un）”的地方，是按推荐项暂定，不是已定。

## 0. 一页结论

1. **阶段 ①（可单独派开发）**：新增一张只追加的“字段来源台账”表 `employment_field_origins`。每次追加任职载荷版本时，在同一事务里为**本次实际写入的字段**各记一行：谁写的、是哪一类来源、写入的值、从哪条记录或哪次传播来的。只沿用旧值的字段不记行。
2. 每个字段的来源状态分两层：**策略层**（创建时继承 / 延迟继承 / 不继承 / 整记录复制）和**覆盖层**（员工输入、HR 保存、审批节点编辑、HR 补录、向后更新、派生、序列同步、状态传播）。覆盖值不适用时（例如职位不属于新部门）不销毁，只记一行“回落”，字段退回策略层；条件恢复时再记一行“恢复”。这样“延迟继承”的策略不会因为被传播值盖过一次就丢失，#99 四轮同类问题的根因在这里。
3. 现有两列 `explicit_field_codes`、`deferred_field_codes` 保留，改为由来源状态经**一个投影函数**算出，不再由各写入口各自拼。判断“员工本次是否输入了某字段”改看请求体，判断“已保存的值是否可信”改看该字段最后一次实际写入的来源，逐字段判断，不再整单豁免。
4. **阶段 ②**：迟到执行不再遇到区间内有记录就交 HR，而是在同一事务里重建：区间内的组织调整按最终时间轴重新折叠；独立业务按 DEC-269 做值匹配向后更新；历史上的传播命令按“来源仍在目标之前、按重建后的前后值重新匹配、引用仍成立”三个条件重放。重建是“最终时间轴 + 两张台账”的纯函数，与多笔迟到的执行先后无关。
5. 阶段 ② 新增第二张只追加表 `employment_propagation_commands`（传播命令台账），记录每次向后更新 / 状态传播的来源、前后值与当时的配置，命中零条也记。
6. 两个阶段都**不新增路由**（待确认 U6）；HR 重试沿用已有的 `POST /api/tenant/employment/businesses/:id/activation/retry`。
7. 需要用户拍板的核心问题只有一个：迟到区间内的独立业务是否也按值匹配替换（U1）。其余待决都有不影响主结构的推荐项。

### 4.2 来源种类

`origin_kind` 取值，分三组：

**策略层**（这个字段在没有覆盖值时该怎么取值）

| 值 | 含义 | 派单要求的来源种类 |
| --- | --- | --- |
| `inherit` | 创建或重新处理时从前驱继承，值已取到，带 `source_record_id` | 继承 |
| `deferred` | 延迟继承：现在不取值，落地时才从实际前驱取 | 延迟继承 |
| `resolved` | 落地时延迟字段解析出的值，带 `source_record_id` | 延迟继承（落地） |
| `none` | 按继承设置不继承，也没有输入 | — |
| `copy` | 组织调整整记录复制前驱，带 `source_record_id` | HR / 系统保存 |

延迟继承的三种形态不单设种类，由逐字段的策略组合表达：

| 形态 | 部门 `preset:departmentId` | 职位 `preset:positionId` |
| --- | --- | --- |
| 部门延迟 | `deferred` | 非 `deferred` |
| 职位单独延迟 | 非 `deferred`（有覆盖值或已继承） | `deferred` |
| 两者都延迟 | `deferred` | `deferred` |

判定函数 `deferralShape` 见 §4.6。

**覆盖层**（有人或系统明确写了一个值）

| 值 | 含义 | 派单要求的来源种类 |
| --- | --- | --- |
| `employee-input` | 员工本人在自助单据上本次填写 | 员工本次输入 |
| `hr-input` | HR 在业务表单上新建 / 修改时填写（含导入新建） | HR / 系统保存 |
| `system-input` | 系统建单或系统改写：Offer 同步、实习生建单、岗位端口、调动联动、再入职工龄、迟到顺延改最后工作日等 | HR / 系统保存 |
| `approval-edit` | 审批节点编辑 | 审批节点编辑 |
| `hr-record` | HR 对已生效任职记录的补录 / 编辑（页面、导入编辑、批量编辑） | HR 补录 |
| `forward-update` | 值匹配向后更新写入，带来源业务、版本号和 `match_before` | 向后更新 |
| `derive` | 由引用带出的派生值（职务带序列、部门 / 职位带直线经理），带规则、引用和结果；向后更新连带带出的派生也用这一种，并带来源业务 | 向后更新（引用派生） |
| `sequence-sync` | F-021 序列同步写入，带职务引用 | 序列同步 |
| `status-propagate` | F-022 状态传播写入，只出现在 `status:*` 字段上 | 状态传播 |

**判定行**（不带新值，只改变状态）

| 值 | 含义 |
| --- | --- |
| `fallback` | 当前覆盖值不再适用，字段回落到策略层；`ref_seq` 指向被挂起的覆盖行 |
| `restore` | 被挂起的覆盖值重新适用；`ref_seq` 指向它 |
| `retain` | 来源被删除后保留当时的值（DEC-244②），`value` 为保留值；阶段 ② 写入 |

### 4.3 折叠规则

一个字段的状态 `FieldOriginState`：

```ts
interface FieldOriginState {
  policy: 'inherit' | 'deferred' | 'none' | 'copy' | null; // 最近一条策略行
  policyRow: OriginRow | null;
  resolved: OriginRow | null; // 最近一条 resolved（落地后才有）
  override: OriginRow | null; // 最近一条覆盖行
  suspended: boolean; // 覆盖值当前是否被挂起
  retained: OriginRow | null; // 最近一条 retain
  lastWriter: OriginRow | null; // 最后一次实际写入值的行
  anchors: Map<string, OriginRow>; // 派生锚点：按 (规则, 引用) 取最近一条 derive / sequence-sync
}
```

按 `seq` 从小到大处理该字段的行：

| 读到的行 | 状态变化 |
| --- | --- |
| `inherit` / `none` / `copy` | `policy`、`policyRow` 更新；`inherit`、`copy` 同时成为 `lastWriter`（前提是当前没有适用的覆盖值） |
| `deferred` | `policy = 'deferred'`；不动 `lastWriter` |
| `resolved` | `resolved` 更新；没有适用覆盖值时成为 `lastWriter` |
| 任一覆盖行 | `override` 更新，`suspended = false`，成为 `lastWriter`；`derive` / `sequence-sync` 另外登记进 `anchors` |
| `fallback` | `suspended = true`；`lastWriter` 退回策略层最近的写入行（`resolved`、`inherit`、`copy`），没有则为空 |
| `restore` | `suspended = false`；`lastWriter` 回到被恢复的覆盖行 |
| `retain` | `retained` 更新，成为 `lastWriter`；之后只有新的覆盖行或传播命令能改它 |

字段的**有效值**：

1. 有覆盖值且未挂起 → 覆盖值（包括值为 `null` 的显式清空）。
2. 否则按策略层：`inherit` / `copy` 取已记录的值；`deferred` 在落地前为空（待定），落地后取 `resolved`；`none` 为空。

折叠是纯函数，放在 `packages/domain/src/employment/field-origins.ts`（新增），没有 IO。

### 4.5 现有两列怎么办

`explicit_field_codes`、`deferred_field_codes` 保留为**投影列**，由 `projectOriginMarkers(states)`（新增，纯函数）算出，写点不再自己拼：

| 列 | 投影规则 |
| --- | --- |
| `explicit_field_codes` | 有覆盖值且未挂起的字段。含义收敛为“这个字段的值不由继承策略决定”，这正是 `prepareInheritance` 等读取方需要的 |
| `deferred_field_codes` | 策略是 `deferred`、没有适用的覆盖值、且尚未 `resolved` 的字段 |

- 投影以“与基线各写点写出的列值一致”为准，S2 用对拍测试固定（同一组操作序列，新旧实现写出的两列逐版相等）。有意的差异只有两处：`derive` 与 `status-propagate` 不进 explicit（与基线一致，基线也不进）；覆盖值被回落后该字段从 explicit 移出、策略为 `deferred` 时回到 deferred（基线做不到，属于修复）。
- “人工意图”“员工本次输入”“保存值是否可信”三件事不再从 explicit 推断，改用 §4.6 的函数。

### 4.7 只追加怎么守

- 两类写入都只有 INSERT：来源表有 `forbid_audit_mutation` 触发器；`app_user` 只被授予 `SELECT, INSERT`。
- “撤回一个覆盖值”不是删行，是追加 `fallback`；“恢复”是追加 `restore`；“删除来源后保留”是追加 `retain`。
- 载荷版本链照旧只追加；回落导致载荷列被清空时，照常追加一版新载荷，“变更前”从上一版取。
- 来源行与载荷版本、审计在同一事务；事务回滚时一起回滚，不会出现有载荷无来源或反过来。

### 4.8 没有来源行的值（待确认 U5）

DEC-402 下不回填。阶段 ① 合并前产生的载荷没有来源行。按推荐项暂定：**没有任何来源行的字段，按基线两列的口径判**——不在该版 `explicit_field_codes` 里的视为继承值（可信，与基线放行一致），在里面的视为不可信（与基线的 403 一致）。这样不回填也不改变旧数据上的结果，DEC-913 的升级用例不受影响。一旦该字段有了任何一条来源行，就只按来源行判。

### 4.9 阶段 ① 的权限、幂等与规模

- 没有新路由、没有新出参（待确认 U6），不新增权限点，授权版本不变。
- 来源行随所属写命令的命令 ID 幂等：命令台账命中缓存时不重复写；`requireEmployeeTransferBusiness` 在返回缓存前仍会重跑（撤权后重放不放行）。
- 规模：一版最多记“预置字段 26 个 + 该租户自定义字段数 + 状态 2 个”行；向后更新一次最多 1000 个目标（`forward-update.ts:57` `TARGET_LIMIT`），每个目标只记被替换的字段。读取按索引取最近行，与版本数无关。

### 6.3 总规则

**重建结果 = f（最终时间轴，字段来源台账，传播命令台账）**。它不读“上一次重建的输出”，所以与多笔迟到的执行先后无关（R2-P2-01、R8-P2-02、R8V3-P2-01）。只有一个地方会读当前配置：某个派生没有任何历史锚点时（§6.5）。

在同一事务、同一把员工锁内，按下面的顺序做：

| 步 | 做什么 | 小节 |
| --- | --- | --- |
| 1 | 取锁：员工闭包 → 业务头（ID 升序）→ 组织 → 编制（只读）。与 DEC-269 写的顺序一致 | — |
| 2 | 判残余情形；命中则照旧抛 `REBUILD_REQUIRED` 或 DEC-252① 的失败，不写任何东西 | §6.9 |
| 3 | L 改到 `a`：追加改期版本，已落地的重定位时间轴行（现有 `postponeLateTransfer`、`repositionEffectiveRecord` `late-transfer.ts:181`） | — |
| 4 | L 自身：策略层字段按新位置的前驱重新继承；覆盖层字段不动；派生按锚点规则；人员状态按新前驱重算（现有 `rederiveRepositionedStatus` `employee-status.ts:243`） | §6.4 |
| 5 | 独立业务：发一条 `trigger = 'late-execution'` 的值匹配向后更新 | §6.6 |
| 6 | 组织调整：重算集合内的记录按最终时间轴顺序逐条重新折叠 | §6.5 |
| 7 | 审计、outbox、编制警告 | §6.10 |

第 5 步在第 6 步之前，因为组织调整的前驱可能是一条刚被值匹配替换过的独立业务。

### 6.5 组织调整记录的重新折叠

**重算集合 W**：同一员工、同一任职周期（StaffID 相同）、`kind = 'org_adjustment'`、最终位置在 `p` 之后的全部记录。不只取窗口 `[p, a)` 内的：窗口外的组织调整若复制自窗口内的记录，也要跟着变（R8V3-P2-01）。上限见 §6.9。

对 W 按最终时间轴从前到后单遍处理。每条记录 O 的每个字段这样算：

1. **起点**。取 O 创建时那一版的来源行：
   - `copy`（纯联动复制，F-007）：值取 O 在**最终时间轴上的直接前驱的当前结果**。前驱若也在 W 里，用它本轮刚算出的结果；不是读前驱创建时的值（R8V3-P2-01 期望“O2 读到 O1 的当前结果甲”）。
   - `inherit` / `none`（F-006 这类按表单继承矩阵生成的组织调整）：`inherit` 同样取最终前驱的当前结果；`none` 保持空（R6-P2-03 十二例、R8-P2-03）。用哪套矩阵由创建时的策略行决定，重建不重新读继承开关（DEC-244③）。
   - O 自己写入的字段（`system-input`，例如 F-006 调整后的经理）：取该行的值。
2. **按 `seq` 依次处理 O 创建之后的事件**（两张台账合并排序）：

| 事件 | 处理 |
| --- | --- |
| 人工覆盖：`hr-record`、`hr-input`、`approval-edit` | 取该行的值。人工值不会被重建改写（DEC-255①）；它之后的合法传播命令仍可以按值匹配覆盖它 |
| 传播命令 `forward-update` | 三个条件都成立才应用：① 来源在最终时间轴上仍排在 O 之前，且来源没有被删除；② 字段在该命令 `config` 的允许集合内；③ 按**重建后**的前后值重新匹配——O 此刻的折叠值等于命令的 `before′` 才替换成 `after′`。`before′ / after′`：来源是迟到业务或在 W 内的，取来源重建后的“前驱值 / 自身值”；否则就是命令当时记下的 `before / after`。当时零命中的命令也照这三条重新判断 |
| 传播命令 `status-propagate` | 同上三条，匹配的是人员状态（from → to），目标的 `entryStatus` 保留自身值（F-007 设计 C-4） |
| `retain`（删除来源时写入，§6.7） | 取该行的值；它之前的事件对该字段不再起作用。之后只有新的人工覆盖或新的传播命令能改它 |
| `fallback` / `restore` | 按 §4.3 |

3. **派生字段**（序列、直线经理）最后算，见下。
4. **系统派生**（`employType`、人员状态）按最终前驱重算；被 `retain` 冻结的除外（R8-P2-04）。

算出的结果与 O 当前值逐字段比较：

- 值不同 → 追加一版记录快照载荷（`is_record_snapshot = true`），并为变了的字段记来源行。
- 值相同但依据变了（例如前驱换了一条）→ 不追加载荷版本，只追加来源行（新的 `copy` / `inherit`，带新的 `source_record_id`）。之后删除来源时要靠它找“实际依赖”（R8V2-P2-01）。
- 值和依据都没变 → 什么都不写。重复执行重建不产生新版本。

**派生锚点规则**（R6-P2-02、R8-P2-02、R8V2-P2-02、R8V4-P2-02）。派生字段没有适用的人工覆盖时：

1. 算出引用字段（职务、部门、职位）在本次折叠里的最终值 `ref`。
2. 在这条记录的锚点里找 `(规则, ref)`（`FieldOriginState.anchors`，含历次重建追加的锚点）。**找到就用锚点的值**，不读当前配置。
3. 找不到 → 按当前配置解析一次，并追加一条 `derive` 锚点行（规则、`ref`、结果）。之后再遇到同一个 `(规则, ref)` 就用这次的结果。

这样同一条记录对同一个引用只解析一次，往返多少次、哪笔先迟到，结果都一样。`sequence-sync` 行兼作 `(post-sequence, 职务)` 的锚点（R2-P2-02）。申请修改时“换职务带出序列”（DEC-107）、“换部门带出经理”（DEC-205 / 209）在阶段 ① 已记 `derive` 行（§4.4.2 #2），同样是锚点（R8V2-P2-03）。

合法传播把引用换成了新值时，派生要跟着新引用走（R8V4-P2-02）：规则 2、3 用的是折叠后的 `ref`，自然覆盖这种情况，不存在“重建期间禁止派生”的限制。

### 6.7 删除来源后保留（DEC-244②）

基线上删除入口是 `deleteEmploymentBusiness`（`transitions.ts:404`）：不级联、不重算。阶段 ② 之前，后续记录的值没人去动，自然保留；有了重建之后，必须显式记下来，否则下一次无关的迟到重建会把它们撤回（R7-P2-03、R8V2-P2-01）。

- 删除来源 S 时，在同一事务里找出**当前实际依赖 S** 的字段：同一员工后续记录上，`lastWriter` 的 `source_business_id = S` 或 `source_record_id` 属于 S 的字段（用 §4.1 的第二个索引）。包括历次重建追加的依据行，所以“重建后才开始依赖 S”的也能找到（R8V2-P2-01）；系统派生字段（`employType`、人员状态）同样按依据行找（R8-P2-04）。
- 为每个这样的字段追加一条 `retain` 行，`value` = **删除时的当前值**（含之前重建的结果），`reason = 'source-deleted'`。不追加载荷版本，值没有变。
- `retain` 只在删除来源时写。来源只是改期（迟到）时不写，改期后按 §6.5 的三个条件重新判断（R8V4-P2-03：不能把“删除后保留”推广成“改期时一律保留”）。
- 撤销离职、作废申请不是“删除来源”：已批准未生效的离职撤销是作废申请，没有版本可删（DEC-215，R8-P2-06）；已生效离职的撤销走既有恢复逻辑（`deletion-guards.ts` 的 `employment.record.restore`），离职本来就不是传播来源，不产生 `retain`。

### 6.8 多笔迟到与离职

**多笔迟到。** 定时任务按原计划日升序逐笔执行，每笔各自重建一次。因为组织调整每次都从“最终时间轴 + 台账”重新算，先执行哪笔不影响它们的结果。独立业务的值匹配是 R1 的既有语义（一次补录一次匹配）：审批触发的迟到可能以不同先后发生，S5' 用两种先后各写一条期望值手写的用例，把结果固定下来；发现两种先后结果不同的组合时，在该片 PR 上贴【等决定】，不自行选一种。

F-007 设计 §2.5 的协调（DEC-298 窄例外、联动足迹 `linkage-dependency.ts:34` `footprintFields`、`:138` `assertPredecessorsSettled`）在重建后只对 §6.9 的残余情形还有意义。代码保留，触发面缩小（待确认 U4）。F-007 为“HR 按后到前逐笔重试”改写过的用例（AC-JOB-08、AC-TRF-35、AC-TRF-49、AC-TRF-F017-late-pending）在 S5' 改回“自动执行、不需 HR 介入”。

**离职迟到顺延（DEC-263①、DEC-272）。** `postponeLateExit` 先重建、再顺延：

| 项 | 规则 | 依据 |
| --- | --- | --- |
| 日期 | 最后工作日 = `a − 1`，生效日 = `a`；原定生效日当天执行不顺延 | `resolveLateLeave`，C-1 |
| 区间内的组织调整 | 按 §6.5 重新折叠。它们排在离职之前，不再带“离职”状态 | §6.5 |
| 区间内的独立业务 | 离职不是传播来源，不发值匹配；它们排在离职之前，照常保留。离职记录自身的非显式字段按新前驱重新继承（§6.4） | C-6 |

## 9. 待决项

作用对象全部是**复刻系统**，不涉及北森测试租户。正文已按每条的推荐项暂定并标“待确认（Un）”；用户明确选择之前都不算已定。

### U1 迟到区间内的独立业务，要不要按值匹配替换（核心）

- **作用对象**：复刻系统（迟到执行后的任职记录内容）。
- **背景**：DEC-269 的例③写的是替换；#83 设计 v4 改成了不替换（审查称为 A′），审查 R8V4-P2-03 指出这没有经过批准。
- **选项 A（推荐）**：照 DEC-269 字面。迟到业务按“补录一条更早生效的记录”处理，原计划日到实际执行日之间的独立业务也参加值匹配。迟到业务自己的生效日仍是实际执行日。
- **选项 B**：只有排在实际执行日之后的独立业务参加值匹配；区间内的不动。选 B 需要改写 DEC-269 的例③。
- **白话例子**：老张 10-05 调入市场部（经理老李），这笔调动拖到 10-12 才执行。10-11 有一笔只改职级的调动按期生效了，上面写着“销售部、经理老王”。
  - 选 A：10-11 那条改成“市场部、老李”。结果是 10-11 的记录已经显示市场部，而调入市场部这笔调动本身 10-12 才生效。
  - 选 B：10-11 那条仍是“销售部、老王”，10-12 起才是市场部。
- **推荐 A 的理由**：DEC-269 是已确认决策，例③写得很具体。
- **对设计的影响**：只影响一个参数（§6.6 的候选下界），两种选择的代码相同；影响 AC-TRF-67 的例③期望值。

### U2 选 A 时，区间内的组织调整记录是否也按值匹配替换

- **作用对象**：复刻系统。
- **选项甲（推荐）**：不按值匹配。组织调整记录一律按最终时间轴重新算：它的值来自排在它前面那条记录的当前结果。
- **选项乙**：和独立业务一样，等于旧值就替换成迟到业务的新值。
- **白话例子**：老张 10-05 调入市场部，拖到 10-12 执行。10-08 销售部改名，系统给老张加了一条组织调整记录（部门是销售部）。
  - 选甲：10-08 那条看它前一条。前一条还是销售部（调动 10-12 才生效），所以保持销售部。
  - 选乙：10-08 那条的部门等于旧值，改成市场部。
- **推荐甲的理由**：DEC-269 对这两类记录的写法本来就不同（组织调整“重算”，独立业务“值匹配”）；审查 R8V3-P2-01 给的期望值也是“读前一条的当前结果”。
- **选甲的一个后果**：同一区间里，10-08 的组织调整显示销售部，10-11 的独立调动（按 U1 选 A）显示市场部。这是两条规则各自照做的结果，会用一条测试固定下来。

### U3 后续记录超过 1000 条时怎么办

- **作用对象**：复刻系统。
- **选项甲（推荐）**：保持现在的做法，记“迟到执行需重建，待 HR 处理”，不自动重建。
- **选项乙**：分多个事务分批重建。这会出现“一部分记录已改、一部分没改”的中间状态，与“一次提交整体成功或整体失败”（DEC-067）冲突。
- **白话例子**：某员工同一段任职里，迟到调动之后有 1001 条后续记录。选甲：这笔调动停在“生效失败”，HR 人工处理。实际业务里一个人一段任职不会有这么多记录，这条只是兜底。

### U4 DEC-298 的窄例外和 F-007 §2.5 的豁免，重建上线后还留不留

- **作用对象**：复刻系统。
- **背景**：DEC-298 允许“后一笔迟到在特定条件下先于卡住的前一笔执行”，并写明“F-036 第二阶段时复核本例外”。重建上线后，前一笔几乎不会再卡住。
- **选项甲（推荐）**：代码保留，只在 U3 那种残余情形下才会走到。DEC-298 的文字是否修改，由总编排在阶段 ② 合并时复核。
- **选项乙**：阶段 ② 一并删掉例外和豁免。残余情形下，后一笔一律等前一笔处理完。
- **白话例子**：老张有两笔迟到调动。前一笔因为后续记录超过 1000 条停在“待 HR 处理”；后一笔和前一笔没有联动关系，自己的区间里也没有别的记录。选甲：后一笔照常生效。选乙：后一笔一直等到 HR 处理完前一笔。

### U5 阶段 ① 上线前留下的值（没有来源行）怎么判

- **作用对象**：复刻系统。
- **选项甲（推荐）**：按现在两列的口径判（§4.8）。上线前后同一份旧草稿的判定结果不变。
- **选项乙**：一律当作不可信。
- **白话例子**：阶段 ① 上线前，员工建了一张本人调动草稿；上线后他只想改生效日。选甲：和上线前一样，职务没被人动过就放行。选乙：被拒绝，要等 HR 重新保存一次。
- **说明**：DEC-402 下不回填，两个选项都不写迁移脚本。选乙时 DEC-913 的升级用例可能要补夹具。

### U6 要不要提供“字段来源”只读查询接口

- **作用对象**：复刻系统。
- **选项甲（推荐）**：不提供。两个阶段都不新增路由。
- **选项乙**：新增 `GET /api/tenant/employment/businesses/:id/field-origins`，详情页可以显示“这个值是哪次操作带来的”。需要 F-039 登记、按字段权限裁剪、前端另开任务。
- **白话例子**：HR 想知道“老张这条调动上的经理为什么变成了老李”。选甲：看任职日志里已有的“向后更新”记录。选乙：详情页的字段旁直接显示“由 10-05 的调动向后更新带入”。
