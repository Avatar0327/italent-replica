## 1. 出口去向

### 1.1 现状

- 出口只有 `approve` / `disagree` 两种（`packages/domain/src/approval/types.ts:168`），去向写死：
  `EXIT_TARGETS = { approve: 'next', disagree: 'end' }`（`types.ts:174`）。注释已写明“复刻首版的流程是线性的”“自定义动作的出口线首版不做”。
- DB 约束 `approval_nodes_exits`：`cardinality(exits) BETWEEN 1 AND 2 AND exits <@ ARRAY['approve','disagree']`
  （`packages/db/src/schema/approval.ts` 节点表 145～290 行）。
- 退休预置只有两节点，注释“同时返聘的条件分支由 F-478 补齐”（`packages/domain/src/approval/presets.ts:458`）。

### 1.2 两类出口

| 类别     | 编码                                   | 族（family） | 说明                                                       |
| -------- | -------------------------------------- | ------------ | ---------------------------------------------------------- |
| 通用出口 | `approve`                              | approve      | 同意                                                       |
| 通用出口 | `disagree`                             | disagree     | 不同意                                                     |
| 业务出口 | `approve_no_rehire`                    | approve      | 同意（不返聘）；仅退休类型；守卫 `reEmployed = false`      |
| 业务出口 | `approve_rehire`                       | approve      | 同意（同时返聘）；仅退休类型；守卫 `reEmployed = true`     |

- 业务出口**按审批类型在代码里注册**，不是租户自由命名；守卫是代码中的固定函数，读适配器 `exitMetadata` 快照
  （退休已有 `reEmployed / retireType / expectedRetirementDate`，`apps/api/src/modules/approval/adapters.ts:233-245`）。
- 业务出口按“出口组”注册：退休组 `rehire_choice = [approve_no_rehire, approve_rehire]`，两个守卫互补，运行时**恰好一个可用**。
- 节点出口集合规则（定义校验 + DB CHECK 双重保证）：
  1. 使用某出口组时必须包含组内全部出口，且不得同时含 `approve`（否则自动处理和旧按钮会有两个同意族出口）；
  2. `disagree` 可与任一同意族组合；
  3. 业务出口只能出现在注册了该组的审批类型上，否则 400；
  4. 会签节点不得使用业务出口（§1.3）。
- 办理人**不改变** `reEmployed`：R2-T04 §8.2 规定“是否返聘”发起时选定、不可改，复刻保持。因此退休 HRBP 节点上
  只显示与本单一致的那一个按钮。原站是否两个按钮都显示、点“同意（同时返聘）”是否改写“是否返聘”，**原站未测、按复刻口径实现**，见 U-01。
- 守卫失败的提交（如旧页面对不返聘单提交 `approve_rehire`）返回 409 `APPROVAL_EXIT_NOT_AVAILABLE`；节点有出口组而请求不带出口
  返回 409 `APPROVAL_EXIT_REQUIRED`。两者都不改实例状态，客户端刷新详情后重新选择，不自动重试（AGENTS §10 并发）。

### 1.3 会签节点

会签节点的出口流转已由 DEC-144 规则决定（任一人 / 所有人 / 自定义），多人各选不同业务出口时语义不清；原站行为未测。
首版定义校验禁止会签节点使用业务出口（400 `APPROVAL_ROUTE_INVALID`，reason `countersign_business_exit`）；会签节点仍可配条件分支（§2）。

### 1.4 条件后继

每个出口可配一个**有序后继列表**；未配置时按规范缺省（不是兼容旧数据，是本模型的缺省规则）：

| 出口族   | 未配置后继       | 配置后继                                                         |
| -------- | ---------------- | ---------------------------------------------------------------- |
| approve  | 下一 seq 节点；无下一节点即结束（通过） | 按条件分支 / Else 选一条，目标为某节点或“结束” |
| disagree | 结束（不通过）   | 同上；目标“结束”= 不通过；目标节点 = 继续流转                    |

分支规则（`14` §8.1 原站规则 + D-005）：

- 分支类型：`condition`（带条件、带唯一优先级）、`else`（无条件，最多一条）、`direct`（无条件直连，只能单独出现）。
- 同一出口内条件分支优先级不得重复（D-005）；有任一条件分支时必须有 Else（避免运行时无路可走）；
  `direct` 不能与条件分支或 Else 共存。原站“无条件分支”优先级参与排序的混合用法首版不做。
- 目标只能是 seq 更大的节点或 `END`（只前向，图无环）；不得指向自身。
- 发布前校验：每个非首节点至少可从首节点经某条路径到达，否则 400 reason `unreachable_node`。
- 条件字段取该审批类型现有的发起条件字段（退休沿用 `LEAVE_CONDITION_FIELDS`，`types.ts:479`），运算符与发起条件相同；
  不新增字段目录。**例外**（S4 实现）：退休守卫事实 `business.reEmployed` 同时登记为退休的发起条件字段，取值为文本 `'true'` / `'false'`，来源是创建后不可改的退休申请（`exitMetadata.reEmployed`），办理人改不了。
- 条件在**办理人提交出口时**按当前业务快照求值。原站的求值时点未测，见 U-09。

## 2. 定义存取

### 2.1 数据模型（迁移草案）

迁移号由实现片合入时 `pnpm merge:main` 定号，不预占（DEC-221 / DEC-430①）。

```sql
-- 出口集合约束放宽：业务出口进入白名单；出口组完整性、与 approve 互斥由 CHECK 表达
ALTER TABLE approval_process_nodes DROP CONSTRAINT approval_nodes_exits;
ALTER TABLE approval_process_nodes ADD CONSTRAINT approval_nodes_exits CHECK (
  cardinality(exits) BETWEEN 1 AND 3
  AND exits <@ ARRAY['approve','disagree','approve_no_rehire','approve_rehire']::text[]
  AND (('approve_no_rehire' = ANY(exits)) = ('approve_rehire' = ANY(exits)))
  AND NOT ('approve' = ANY(exits) AND 'approve_rehire' = ANY(exits))
);
-- 会签节点不得用业务出口：并入现有会签 CHECK（approve_rule_kind / disagree_rule_kind 与 exits 的约束）

CREATE TABLE approval_node_exit_routes (
  tenant_id uuid NOT NULL,
  version_id uuid NOT NULL,
  node_key text NOT NULL,
  exit text NOT NULL,
  branch_no smallint NOT NULL CHECK (branch_no BETWEEN 1 AND 10),
  kind text NOT NULL CHECK (kind IN ('condition','else','direct')),
  priority smallint,                         -- 仅 condition 必填
  expression text,                           -- 条件项编号组合，同发起条件 expression 语法
  target_node_key text,                      -- NULL = END
  PRIMARY KEY (tenant_id, version_id, node_key, exit, branch_no),
  FOREIGN KEY (tenant_id, version_id, node_key) REFERENCES approval_process_nodes (tenant_id, version_id, node_key)
    ON DELETE CASCADE,
  FOREIGN KEY (tenant_id, version_id, target_node_key)
    REFERENCES approval_process_nodes (tenant_id, version_id, node_key),
  CHECK ((kind = 'condition') = (priority IS NOT NULL AND expression IS NOT NULL)),
  CHECK (target_node_key IS DISTINCT FROM node_key)
);
CREATE UNIQUE INDEX approval_exit_routes_priority
  ON approval_node_exit_routes (tenant_id, version_id, node_key, exit, priority) WHERE kind = 'condition';
CREATE UNIQUE INDEX approval_exit_routes_else
  ON approval_node_exit_routes (tenant_id, version_id, node_key, exit) WHERE kind IN ('else','direct');

CREATE TABLE approval_node_exit_route_conditions (
  tenant_id uuid NOT NULL,
  version_id uuid NOT NULL,
  node_key text NOT NULL,
  exit text NOT NULL,
  branch_no smallint NOT NULL,
  item_no integer NOT NULL CHECK (item_no BETWEEN 1 AND 20),

CREATE TABLE approval_node_activations (

-- 三张新表：ENABLE + FORCE ROW LEVEL SECURITY，策略与 approval_process_conditions 相同（tenant_id = 当前租户）；
-- 激活表另加与审批日志相同的禁止 UPDATE / DELETE 触发器
```

- **条件项照抄现有发起条件的单值 / 列表值两种载体**：现有 `approval_process_conditions` 用 `value_text` 存单值、
  `value_list text[]` 存列表值（`packages/db/src/schema/approval.ts:119-142`），领域类型
  `ConditionItem.value: string | readonly string[] | null`（`packages/domain/src/approval/types.ts:358-363`）。路由条件表

  - 写入：与 `definitions.ts:366-370` 相同的规则——`Array.isArray(value)` 写 `value_list`，字符串写 `value_text`，
    `is_empty / not_empty` 两列都为 NULL。实现片把这段插入抽成共用函数，发起条件与路由条件都调用它。
  - 读回：复用 `conditionItem(row)`（`definitions.ts:127-135`：`value_list ?? value_text`），列名对齐后无需改动。
  - 校验：每条分支的 `{ items, expression }` 交给现有 `conditionViolations(condition, fields)`（`conditions.ts:96`），
    其中 `valueViolations` 已要求 `in / not_in` 为非空字符串数组、`eq / ne` 为单个字符串（`conditions.ts:126-136`）。
  - 求值：复用 `evaluateCondition`（`conditions.ts:160`），`in / not_in` 按数组判断（`conditions.ts:149-150`；
    `not_in` 对空值为真，与发起条件一致）。
  - 不使用 JSON 承载分支或条件值（AGENTS §7）。
- 出口与节点、后继目标都在**同一版本**内，随版本发布冻结；`exit` 是否属于该节点 `exits` 由服务层校验（跨表 CHECK 不可写）。
- “目标 seq 更大”“可达性”“Else 必填”“优先级唯一”在领域纯函数 `validateRoutes` 中校验；DB 唯一索引兜底优先级与 Else 唯一。
- 任务表新增 `decision_exit` 列记录实际出口，激活表记录每次进入节点的来路；二者用于路径前驱、办理页路径和审计。
  前驱是流转事实，不是业务字段的“变更前”值，不违反“变更前不单独建列”。

### 2.2 读写接口

- `PUT /processes/:id/draft`：节点体增加
  `routes: [{ exit, branches: [{ kind, priority?, conditions?: { items: [{ no, field, operator, value }], expression }, target }] }]`，
  `value` 与发起条件同形（字符串 / 字符串数组 / null，`definition-input.ts` 现有条件 zod 复用），`target` 为节点 key 或 `"END"`。
  沿用 `If-Match` revision，revision 不一致 409。
- 业务出口在 S4 注册退休出口组之前，出口注册表里没有任何组：任何类型提交业务出口都按 `business_exit_type` 拒绝。
  这不是功能开关，只是注册代码随 S4 到达（§9）。
- 现有设计器保存草稿时把最新读回的版本整体克隆、逐节点展开后提交（`apps/web/src/approval/designer/model.ts:147-163`），
  未识别的 `routes` 会原样带回；因此 S2 开放 `routes` 后，S7 之前用旧设计器改名称等属性不会丢分支。
- 违规统一 400（错误码 `VALIDATION_FAILED`，reason `APPROVAL_ROUTE_INVALID`），
  `details.reason` ∈ `backward_target | self_target | duplicate_priority | missing_else |
  else_with_condition | direct_mixed | unreachable_node | unknown_field | invalid_condition | unknown_target | exit_not_on_node |
  business_exit_type | incomplete_exit_group | countersign_business_exit | too_many_branches`，带 `nodeKey / exit / branchNo`；
  `invalid_condition` 携带 `conditionViolations` 的原文（如“条件 2 需要非空的值列表”）。
- `GET /processes/:id` 与 published / latest 视图回带 `routes`；`definitions.ts` 加载器（100～125 行，`ORDER BY seq LIMIT 50`）
  同事务按 `(node_key, exit, branch_no, item_no)` 有界读出路由（每出口 ≤10 分支、每分支 ≤20 条件项）。
- 不保留“无 routes 字段的旧草稿形态”的并行读写路径（DEC-402）；缺省后继是模型规则，不是兼容层。

### 2.3 并发：定义修订与在途实例

- 实例在发起时绑定 `version_id`（现状），运行时只读该版本的节点与路由；发布新版本不影响在途实例。
- 草稿保存与发布沿用流程级 revision；两人同时改草稿，后到者 409。
- 已发布版本的节点 / 路由不可修改（沿用节点表现有只读保护；实现片核对触发器或服务守卫，并对路由表补同样保护）。

## 3. 运行推进

### 3.1 现状（全部按下标线性）

| `engine.ts:389-411` `advanceFrom(tx, run, index)`           | 从 `index` 起逐个进入节点；节点结果 `next` 即 `i+1`，循环结束 `complete()` |
| `engine.ts:793-838` `followExit`                            | `EXIT_TARGETS[exit] === 'next'` → `advanceFrom(nodeIndex+1)`，否则 `endDisapproved` |

| `actions.ts:1030-1062` jump / adminJump                     | `nodeIndex(target)` + `startHistoryAfter`                              |

### 3.2 新的推进规则

- 新增纯函数 `resolveSuccessor(version, nodeKey, exit, facts) → { target: nodeKey | 'END', branchNo | null }`（domain 包，无 IO）。
- `advanceFrom` 改为 `advanceTo(tx, run, nodeKey, from)`（`from` = 进入方式、来路激活、来路节点、出口、分支号，§3.2.1）：
  进入目标节点；节点被跳过 / 自动处理时，用该节点的默认同意族出口（见 3.3）再求后继，循环至停在人工节点或 `END`。
  `END` 来自同意族 → `complete()`；来自不同意族 → `endDisapproved()`。
- 每次进入节点都在 `approval_node_activations` 写一行（与任务的 `activation_id` 同号，§2.1），记录进入方式与来路。
- `decision_exit` 在任务完成时写入；条件求值、出口与目标写入审批日志（§8.3）。

#### 3.2.1 路径前驱

路径前驱按**实际激活与流转记录**确定，不按“最近一条已同意的任务”反推：当前任务的前驱 = 其 `activation_id` 对应激活行的
`from_node_key / from_activation_id`。各进入方式写入的来路如下：

| 进入方式                                                         | `entry_kind`      | 写入的前驱                                                                      |
| ---------------------------------------------------------------- | ----------------- | ------------------------------------------------------------------------------- |
| 发起；驳回重提 `restart` 进入首节点                              | `start`           | 无                                                                              |
| 节点出口流转：人工同意、人工不同意、自动同意、自动跳过、会签结算 | `flow`            | 产生该出口的节点及其激活；`from_exit` 记实际出口（不同意族、`skipped` 都算）    |
| 驳回到上一步，进入前驱 P                                         | `reject_previous` | 继承 P 被回退前那次激活的前驱，因此可以继续逐级“驳回到上一步”；P 本轮从未激活（被跳转越过）时取 P 的 seq 前一节点                   |
| 驳回重提 `rejecting_node`，进入驳回节点 R                        | `resubmit`        | 继承 R 被驳回时那次激活的前驱                                                   |
| 审批人跳转、管理员跳转，进入目标 T                               | `jump`            | 不经出口，没有流转来路：取版本内 seq 前一节点（T 为首节点则无），即现状规则（U-10） |
| 撤回 retrieve                                                    | 不新建激活        | 沿用原激活编号（现状，`approval.ts` activation 注释），前驱不变                 |

要点：

- **不同意 → 后继**：N1 不同意、不同意出口路由到 N3 时，N3 激活行记 `from_node_key = N1, from_exit = disagree`；
  N3 “驳回到上一步”回到 N1。原草案“最近一条已同意”的查找在此找不到 N1，已废弃。
- **自动跳过**：`autoProcess` 对跳过记 `status = 'skipped'`、审批人为空（`engine.ts:696`）。跳过节点按默认同意族出口流转，
  下游激活行的前驱就是这个被跳过的节点。下游“驳回到上一步”回到它：重新进入、按当前事实重新判定（`startHistoryAfter` 已重置
  历史边界）；仍被跳过时按其出口再次流转回下游，产生新激活。这与现状线性行为相同（`actions.ts:451` 取 `index-1` 不看其状态，
  `advanceFrom(index-1)` 再判定），本单不改。
- **回退后再推进**：驳回到上一步后，P 再次办理时其出口按**当时**的业务快照重新求后继，可以走与上一次不同的分支；
  `rejecting_node` 重提同理。
- **“与上一节点相同”（DEC-114）/ `previous_approved`**：比较对象由 `nodeKey === nodes[index-1].key` 的最后一次激活
  （`engine.ts:189-213`、`source-resolver.ts:21-31`）改为激活行指向的 `from_activation_id` 那一次激活的任务，仍先经
  `effectiveHistory`（`policies.ts:45`）裁剪。被跳过的前驱按现有 `previousNodeComparand` 取其候选人，`previous_approved`
  按 `actualApprovals` 不计跳过与自动处理——两者口径不变，只换“哪一个节点”。跳转与驳回后历史边界已重置，比较对象为空，同现状。
- **线性等价**：没有任何路由配置的版本里，`flow` 来路恒为 seq 前一节点，跳转按 seq 前一节点，故路径前驱恒等于
  `nodes[index-1]`；现有线性流程的驳回、同人自动处理、`previous_approved` 行为全部不变，由现有验收测试回归。
- 找不到激活行时（只可能是本片上线前已在途的实例）按 seq 前一节点处理，即现状规则；不另建并行读写路径（DEC-402）。

### 3.3 与撤回 / 驳回 / 自动审批的交互（`14` §12 / §14）

| 场景                        | 规则                                                                                                                       |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 自动处理（与上一节点相同、历史相同、主体回避跳过、自身回避后的处理） | 取节点上**守卫通过的唯一同意族出口**，按其后继流转；日志记录该出口。若不唯一（定义校验已排除，仅作防御）→ 不自动处理、转人工 |
| 撤回 retrieve（§14）        | 规则不变：本任务之后**实际创建的**任务都未处理才可撤；分支外节点没有任务，不影响判断；下游被自动处理后失去撤回（与 F-404 一致） |
| 驳回到上一步                | 回到当前任务激活行记录的**路径前驱**（§3.2.1，含不同意来路、跳过节点）；无前驱沿用现有 409 `APPROVAL_NO_PREVIOUS_NODE`     |
| 驳回重提 `restart`          | 从首节点重新推进，所有分支按重提后的业务快照重新求值                                                                        |
| 驳回重提 `rejecting_node`   | 回到驳回节点；其路径前驱继承驳回时那次激活的前驱（§3.2.1）                                                                  |
| 跳转 / 管理员跳转           | 可跳到版本内任一节点（含原路径外节点）；跳入节点之后按该节点出口求后继；前驱取 seq 前一节点；`startHistoryAfter` 不变      |
| 会签一人不同意（§12.2）     | 沿用 DEC-144：不同意族出口流转后其余待办“无需处理”；不同意出口若配了后继节点则按后继继续                                    |
| 审批中编辑                  | 编辑与提交出口在同一实例行锁下串行；出口提交时读编辑后的快照求值                                                          |

## 5. 新审批人来源

### 5.1 主体员工本人（`subject_employee`）

- 新表达式，类型 object_field（`packages/domain/src/approval/sources.ts:26` `EXPRESSION_SOURCE_TYPES`），解析为
  `candidateOf(subject.subjectEmployeeId)`——与现有 `assessment_employee / idp_employee / handover_employee` 相同的取法。
- 与 DEC-230 的关系：DEC-230 规定动态关系一律以**业务主体员工**（不是发起人）为起点；本来源取的就是同一个主体员工，
  只是不再沿关系走到其直线经理 / 部门负责人。HR 代发转正时，主体是被转正员工，自评任务派给该员工，不派给 HR。
- 只对**单主体**审批类型开放（转正、实习转正、离职、退休等）；多主体类型（F-048 批量）选该来源属于来源误用。
- 校验：使用该来源的节点必须 `avoidSelf = false` 且 `avoidSubjects = false`（开启回避会把任务永远改派走，自评无意义），
  同样按来源误用处理。
  这与 ASSESSMENT 自评节点（`avoidSelf:false`）和离职交接“员工确认”节点的先例一致，不构成 DEC-058 意义的自审放行：
  该节点是本人确认 / 自评环节，后续节点仍须他人审批。
- **来源误用一律 422**（DEC-697）：两项检查都加在统一来源检查 `approverSourceViolations`（`packages/domain/src/approval/definition.ts:75`）
  中，由保存入口按现有契约抛出——HTTP 422，错误码 `APPROVAL_SOURCE_INVALID`，reason `APPROVAL_DEFINITION_INVALID`，
  `details.violations` 为违规原文（`apps/api/src/modules/approval/definition-input.ts:227-229`；落库前复核同码、只带首条原文，
  `definitions.ts:374-375`）。违规原文：
  - `节点 {key} 的审批人“主体员工本人”只能用于单主体审批`；
  - `节点 {key} 使用“主体员工本人”时不能开启本人回避或主体回避`。
  不新增错误码或 reason，前端仍按 `APPROVAL_SOURCE_INVALID` 定位到来源字段。
- 空值：主体员工没有账号、账号停用、已离职 → 视为空（DEC-098）。首节点为空拒绝提交（DEC-054，`APPROVAL_FIRST_NODE_EMPTY`）；
  中间节点按 `noAssignee` 转异常管理员。主体员工本人发起时，自评仍派本人（与发起人相同，不回避）；原站该场景未测，见 U-05。

### 5.2 系统管理员（`system_admin`）

- 新表达式，类型 role。解析：本租户 `permission_admins` 中 `role = 'system_admin'`、记录有效、成员有效、账号可作审批人的人员，
  按 `created_at, id` 升序取**第一位**，作为单人节点审批人；读数通过 permission 模块的读取函数，在同一租户事务内（RLS）。
- 取第一位的理由：单人节点解析出多人会报 `APPROVAL_SINGLE_SOURCE_MULTIPLE`；现有“交接 HR 管理员”取授权顺序第一位
  （`handoverHrAdmin`）是同类先例；结果确定、可复现。DEC-537 已取证原站唯一可指派的管理员是“系统管理员（企业设置）”，
  故 `tenant_admin` 不在本来源内。
- 原站多名系统管理员时是否全员待办（或签）**原站未测、按复刻口径实现**，见 U-04；若取证为或签，改为允许该来源用于
  “任一人同意”会签节点，属于后续契约变更。
- 适用于所有审批类型，没有类型限制，不产生来源误用。
- 空值：无有效系统管理员 → 空；实习转正首节点 → 拒绝提交（`APPROVAL_FIRST_NODE_EMPTY`）；中间节点 → 异常管理员。
- 系统管理员作为审批人办理的是派给本人的任务，不是代签（DEC-063 不受影响）。回避：预置开 `avoidSelf`，
