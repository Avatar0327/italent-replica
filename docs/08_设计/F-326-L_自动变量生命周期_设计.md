## 1. 术语与两个在用集合

- **生命周期在途**：实例状态 `IN ('running','returned')`。DEC-862 规定撤回计入“已结束”，所以 `withdrawn` 不在内。
- **生命周期在用版本**（系统停用扫描的口径）：满足任一条的版本。
  1. 流程 `status='active'` 的草稿版本；
  2. 流程 `status='active'` 的 `current_version_id`；
  3. 任何流程（含已作废）中，有生命周期在途实例绑定的版本。
  - 作废流程的草稿与当前版本不算在用（DEC-861⑦）。U-17 原文“被任何当前发布版本 / 草稿 / 未结束在途单 / 其他流程引用的不停用”中的“当前发布版本 / 草稿”按此理解为未作废流程的，与 ⑦ 一致。
- **§6.1 在用版本**（主设计“查看引用”、停用影响清单、删角色列阻止、S7a 保存收尾、引用流程数共用）：不改，仍含 `withdrawn`，也不区分流程是否作废。理由：这几处是给人看的影响面与硬阻止，宁可多列；系统停用的口径另由 DEC-862、⑦ 定。
- 两个集合都在 `source-usages.ts` 定义，各一个常量：`RESUMABLE_INSTANCE_STATUSES`（§6.1，S4 已有）与本文新增的 `LIFECYCLE_INSTANCE_STATUSES = ['running','returned']`，外加“流程须 active”这一条件。引用扫描函数加一个口径参数 `usage: 'reference' | 'lifecycle'`，SQL 只此一份，不各写一份。
- **系统停用**：本文三个触发点做的 `auto_disable`。操作者为空（列表显示“系统”），`after.reason` 取下列两值之一：
  - `旧版本在途单清零自动停用`（派单原文，U-17）；
  - `作废流程在途单清零自动停用`（⑦，派单未规定原文，已定，见 §11 ②）。
- **候选**：被清零版本的节点三列（`approver_expression`、`approver_expressions`、`empty_approver_sources`）以 `public_variable` 引用、`origin='auto'`、`status='enabled'` 的变量。**按引用取，不按来源版本取**：
  - 被新版本复用的、来源版本更早的变量也在候选里，由扫描排除；
  - 其他流程的自动变量（DEC-860 跨流程选用）也在候选里。否则流程 B 不再用 A 的 X 之后，X 就无人停用。
  - 人工变量（`origin='manual'`）永不进候选。

## 2. U-17 旧版本在途清零自动停用（DEC-859，未取证假设）

### 2.1 规则

一个版本不再是生命周期在用版本时，系统停用它的候选中、已不被任何生命周期在用版本引用的变量。在途期间这些变量一直有效。停用记录作历史，不占位：S1 唯一索引 `approval_variables_origin_slot` 条件为 `origin='auto' AND status <> 'disabled'`（主设计 ⑤），停用后同一位置可再生成；可被管理员重新启用，规则同主设计 ④“手工重新启用”。

### 2.2 触发点（三个，全部在同一事务）

| 触发 | 挂点 | 条件 | 登记的版本 | `trigger` |
| --- | --- | --- | --- | --- |
| (a) 实例离开在途 | `engine.ts` `persistRun`（第 158 行），`updateInstance`（第 164 行）之后 | `run.before.status ∈ {running, returned}` 且 `saved.status ∉` 该集合 | `saved.versionId` | `{kind:'instance', instanceId, status}`，`status` 为写入后的状态 |
| (b) 发布替换当前版本 | `definitions.ts` `publishProcess`（第 548 行），`bump current_version_id`（第 564 行）之后 | 发布前的 `current_version_id` 非空 | 被替换的旧当前版本 | `{kind:'publish', newVersionId}` |
| (c) 作废流程 | `discardProcess`（第 621 行），`bump status='discarded'` 之后 | 无 | 该流程全部版本 | `{kind:'discard'}` |

- (a) 只此一处：`store.ts` 的 `updateInstance` 是唯一改实例状态的 UPDATE（第 511 行），只被 `persistRun` 调用；`withdraw` / `cancel` / `revokeBySystem` / 审批通过 / 拒绝结束 / 交接都经过它。
  - 覆盖的状态迁移：`running → approved / disapproved / cancelled / withdrawn`、`returned → cancelled / approved` 等。`withdrawn → cancelled`、`withdrawn → running`（重提）的前状态不在在途集合，不再登记；撤回那一刻已登记过。
  - 发起即自动通过（发起事务内直接到终态）：`launch` 的 `before` 是刚插入的 `running` 行，同样登记。
- (b) 只挂 `publishProcess`。`republishWithExceptionAdmin`（第 592 行，交接与 `restore.ts` 第 260 行）**不挂**：
  - 它以当前版本为底稿复制出下一版，只换异常管理员，新版本引用的变量集合包含旧版本的全部引用（存量 `specified` 在复制时落成新变量，只增不减，主设计 ⑧）。新版本成为当前版本、属于在用，所以旧版本的候选必然都被排除，挂了也停不了任何变量。
  - 旧版本之后在途清零时，由 (a) 检测，结果相同（仍被新版本引用，不停）。
  - 不挂也不需要锁变量；交接路径的锁序见 §3.4。
- (c) 见 §7。
- **不加定时扫描**。版本从在用变为不在用只有三种途径：最后一单离开在途；不再是当前版本；流程作废。草稿没有实例，只在作废时离开在用。三者都有触发点，定时扫描无事可做。
- **存量不回扫**：S7e 合入前已经清零的旧版本，其变量保持启用，不回填（DEC-402 同一思路）。这些变量的版本将来若有触发（如作废），照常检测。

### 2.3 提交前统一检测

三个触发点不当场检测，只把“版本 id + trigger + 上下文”登记到本事务的**提交前任务**；事务主体结束、`COMMIT` 之前，统一执行一次 `retireDrainedVersions`。仍在同一事务里，满足“同一事务检测”。

为什么不当场检测：一个事务可能先后结束多个实例（离职作废申请、合同恢复等批量路径逐单调 `cancel` / `revokeBySystem`）。当场检测会按实例处理顺序逐个锁变量行；两个批量事务若以相反顺序结束 v1、w1 的实例，就会互等成环（甲持 X 等 Y，乙持 Y 等 X）。统一到提交前，可以把本事务涉及的全部变量按 id 升序一次取锁，消除这类环（§3.2）。

提交前任务由契约片 C2 提供（`packages/db/src/after-commit.ts` 旁）：

- `beforeTransactionCommit(tx, key, payload, flush)`：同一 `key` 的 `payload` 追加到列表；根事务在回调返回之后、提交之前，以本事务句柄调用一次 `flush(tx, payloads)`。
- 保存点语义同现有 `afterTransactionCommit`：保存点成功时登记并入外层，回滚时丢弃。
- `flush` 抛错即整个事务回滚，不吞错（与 after-commit 的“已提交后记日志”不同，这里业务尚未提交）。
- 未登记在受管理事务上时抛错，与 `afterTransactionCommit` 一致。
- 本文的 key 为 `approval-auto-retire:<tenantId>`。

### 2.4 算法 `retireDrainedVersions(tx, payloads)`

放在新文件 `apps/api/src/modules/approval/auto-variable-lifecycle.ts`。同一 key 下的提交前任务有三种登记（统一由 `flushAutoVariableLifecycle` 处理，取锁只此一处）：停用检测（本节，三个触发点）、重提判定（§6.2）、交接 / 恢复重发推迟的保存收尾（§3.4）。下面先写停用检测，另两种只在第 1 步并入同一批锁。

0. **快路径**：不加锁查出全部登记版本节点三列引用的 `origin='auto'` 变量 id（不论状态），并上另两种登记要用的变量 id。集合为空就结束，不取任何锁。多数实例结束走到这里就返回。
   - 这一步读的是版本内容。已发布版本内容不可改；草稿只在作废时登记，此时流程头已被作废事务锁住。所以集合由不可变内容决定：**两个事务只要登记了同一版本，或登记的版本引用了同一变量，各自第 1 步的锁集合就都含该变量**，在它上面串行（§2.5、§3.5 的会合点论证依赖这一点）。
1. **一批取锁**：对上述集合按 id 升序 `SELECT id, status FROM approval_variables WHERE tenant_id=… AND id = ANY(…) ORDER BY id FOR UPDATE`。不论状态都锁，锁后再按状态过滤；不锁版本行（第 1 轮锁版本行会与外键的 `FOR KEY SHARE` 升级成环，§3.2）。本事务在中段已取过变量锁时，先过锁台账检查（§3.3）。
2. 用新语句（READ COMMITTED 下看得到已提交的并发结果）逐个判定登记版本是否已不在生命周期在用：
   - 有生命周期在途实例绑定 → 仍在用，跳过；
   - 流程 active 且版本是其 `current_version_id` 或草稿 → 仍在用，跳过。这里读流程头不加锁，理由见 §3.5。
3. 候选：剩下各版本的候选变量（§1，第 1 步锁住的、当前 `status='enabled'` 的），合并去重。候选都已在第 1 步锁住，这一步不再取锁。
4. 用新语句对候选做一次生命周期口径的租户内引用扫描（`source-usages.ts`，`usage:'lifecycle'`），去掉仍被任一在用版本引用的。扫描是取锁之后的新语句，所以看得到先拿到同一变量锁、已提交的那一方的结果。
5. `UPDATE approval_variables SET status='disabled', revision=revision+1, updated_by=NULL, updated_at=ctx.now WHERE tenant_id=… AND id = ANY(…) AND status='enabled' RETURNING id`，只对返回的行写审计。
6. 审计（S1 审计口径，`auditApproval`）：
   - objectType `approval-public-variable`，动作 `approval.public_variable.auto_disable`（不新增动作，`labels.ts` 仍显示“自动停用”，主设计 ⑨ 挂点）；
   - 上下文为 `{...登记时的 ctx, actorUserId: null}`：`actorOf` 返回空，操作者记“系统”，与 `revokeBySystem` 的“操作人强制为空（= 系统）”同一口径；`commandId` 沿用触发命令的，可回溯到是哪次审批 / 发布 / 作废引起；
   - 即使触发它的是某位审批人或管理员的操作，操作者也记系统；
   - `before`：`{status:'enabled'}`；
   - `after`：`{status:'disabled', reason, processId, versionId, versionNo, trigger}`。`versionId` / `versionNo` 取让这条变量可停用的版本：一条变量被本次多个清零版本引用时，取版本号最小的那个（同号取 id 小的），结果确定；
   - `reason`：该版本所属流程已作废取 `作废流程在途单清零自动停用`，否则取 `旧版本在途单清零自动停用`；
   - 新增的 `after` 键按 S1 的审计可见字段登记一并登记。
7. `updated_by` 置空：变量列表的“最近修改人”随审计显示“系统”。若 S1 的 `updated_by` 为非空列，改为保留原值、只以审计为准（实现时以 S1 实际定义为准，不加迁移）。“系统停用记系统、发布记发布人”已定（§11 ⑥），主设计第 539 行“操作人都是在设计器保存的人”随之回改（§10 第 29 条）。

S7a 的 `retireUnreferencedAutoVariables(tx, ctx, candidateIds, reason)` 签名不改（主设计 ⑨ 挂点）。本文的第 4～6 步复用它的内部实现：S7e 给它加可选参数 `options: {usage: 'lifecycle', after: (id) => 附加字段}`，第 5 步的守卫 UPDATE 与审计写法只此一份。

### 2.5 并发：不漏停、不重复停

- **两单同时结束**（同一版本 v1 的最后两个在途实例）：两事务的提交前任务按第 0 步算出同一个变量集合（含 X），都要取 X 的 `FOR UPDATE`。先拿到的一方在第 2 步看到另一实例仍是 `running`（对方未提交），跳过并提交；后一方拿到锁后用新语句重读，在途为 0，停用。只有后一方停用，只写一条审计。
- **跨版本同一变量**（A 的 v1 与 B 的 w1 都引用 X，各自最后一单同时结束）：两事务的锁集合都含 X，在 X 上串行。先拿到的一方扫描时看到对方版本仍在用（对方实例未提交），不停；后一方看到两边都已清零，停用。
- **最后一单结束与发布同时发生**：见 §3.5，两种先后都能停。
- **重复触发**：同一变量被两个事务先后判定可停用（如两个不同的清零版本都引用它），第 5 步的 `status='enabled'` 守卫让后者 `RETURNING` 为空，不写第二条审计。
- **有引用不停**：第 4 步在持有候选行锁后用新语句扫描。别的流程正在保存草稿引用 X：保存方对 X 取 `FOR SHARE`（主设计 §6.2），与第 1 步的 `FOR UPDATE` 互斥。保存先提交，扫描看得到新引用，不停用；扫描先提交，保存方读到“已停用”，返回 422（主设计 ④“并发”最后一条，同一机制）。

## 3. 锁顺序

第 1 轮用“版本行 `FOR UPDATE`”串行同一版本的检测，审查指出两处成环（`.dev_inputs/review_l1.md` P2-1、P2-2）。本轮改为**不锁版本行、只锁变量行**，并把重提的判定移进提交前任务。

### 3.1 全局顺序

> 业务锁（员工 / 业务单 → 组织 → 编制）→ 流程头 → 实例行 → 变量行（一个事务至多一批，按 id 升序）

- 版本行不再显式加锁。草稿版本行只在持有流程头 `FOR UPDATE` 时 UPDATE（存草稿、发布）；已发布版本行不再被 UPDATE。
- 插入实例时外键对流程头行、版本行取 `FOR KEY SHARE`，照旧，不进本序（理由见 §3.2 第 4 条）。

各路径只取其中一段，不逆序：

| 路径 | 取锁顺序 |
| --- | --- |
| 审批 / 撤回 / 作废 / 系统撤销（实例离开在途） | 业务锁 → 实例（`openRun` 第 116 行起，已有）→〔提交前〕变量一批 |
| 发起（`launch`） | 业务锁（调用方，已有）→ 流程头 `FOR SHARE`（§4 新增）→ 插入实例（外键 `FOR KEY SHARE`）→〔若当场结束，提交前〕变量一批 |
| 重提（`resume`，含重提后当场结束） | 业务锁 → 实例（`openRun`，已有）→〔提交前〕变量一批（重提判定与停用检测合在这一批，§6.3）。事务中段不取变量锁 |
| 发布（`publishProcess`） | 流程头 `FOR UPDATE`（`lockedForChange`，已有）→ 草稿版本（UPDATE，已有）→ 变量一批（待生效变量 ∪ 被替换版本引用的全部自动变量，§5.4）→〔提交前〕同一批，已持有，重入不等待 |
| 作废（`discardProcess`） | 流程头 `FOR UPDATE`（已有）→〔提交前〕变量一批（该流程全部版本引用的自动变量） |
| 设计器保存（S7a） | 流程头 → 草稿版本 → 变量一批（主设计 ④“并发”；合成一批见 §10 第 13 条）。不登记提交前任务 |
| 交接 / 恢复重发（`republishWithExceptionAdmin`）后逐单处理实例 | 业务锁（`lockHandoverParticipants`）→ 各流程头（按编码）→ 逐单实例 →〔提交前〕变量一批。重发时**不锁已有变量**（§3.4） |
| 管理员编辑 / 停用 / 启用变量 | 单个变量 `FOR UPDATE`（主设计 ④、§6.2） |

### 3.2 无环论证

两条规则保证无环：

- **R1 变量层是最后一层**：事务持有变量锁之后，只再碰三类行——已持有锁的变量；本事务已持有的流程头所护住的行（流程头本身、该流程的草稿版本）；本事务新插入的行（审计、新建变量，唯一索引的位置属于本事务锁住的流程）。不再等待实例、业务、流程头的锁，也不再取本批以外的变量锁。提交前任务之后只有 `COMMIT`；发布在变量一批之后只写草稿、流程头、新变量与审计。
- **R2 变量一批**：一个事务的变量锁至多一批，按 id 升序一次取完；同一事务后面再要变量锁，必须是已持有的子集（重入不等待），且不得把 `FOR SHARE` 升级为 `FOR UPDATE`。由锁台账在运行时把关（§3.3）。

由此：

1. 在变量层等待的事务，持有的只可能是上层的锁（业务、流程头、实例）和自己这一批里排在前面的变量。
2. 由 R1，持有变量锁的事务不会在上层等待。所以“甲持变量等上层、乙持上层等变量”的跨层环不存在。
3. 变量层内部：各事务都按 id 升序一次取一批，事务进入变量层之前不持有任何变量锁（R2），按序加锁的经典论证成立，不成环。
4. 外键的 `FOR KEY SHARE`：与它冲突的只有 `FOR UPDATE` 和改键列的 UPDATE / DELETE。本文不再对版本行取 `FOR UPDATE`；发布对草稿行的 UPDATE 不改键列，取的是 `FOR NO KEY UPDATE`，与 `FOR KEY SHARE` 相容（发起也只绑当前版本，不会对草稿行取 `KEY SHARE`）。流程头上，发布 / 作废的 `FOR UPDATE` 与发起的 `FOR SHARE`、`FOR KEY SHARE` 冲突，但发起方此后只在变量层等待，发布方此时还没进变量层（卡在流程头），不成环。

逐一对照审查指出的两处：

- **两个“发起即结束”实例（第 1 轮审查 P2-1）**：甲、乙都持流程头 `FOR SHARE` 与 v1 的 `FOR KEY SHARE`（两两相容），提交前都要 X 的 `FOR UPDATE`。甲先拿到，判定 v1 仍是当前版本、跳过、提交；乙随后拿到，同样跳过。没有锁升级，不成环（AC-59 ①）。
- **重提当场结束 × 发布（第 1 轮审查 P2-2）**：重提方持业务锁、实例，提交前等 X；发布方持流程头、X（事务中段一批），之后不再等上层。只在 X 上相遇，不成环（AC-60）。第 1 轮的问题在于重提事务中段先取 X 的 `FOR SHARE`、提交前又要 v1 锁；本轮两者都没有了。

- 已有的同一事务对多个流程发起（若存在）与交接的流程头竞争，现状就由外键的 `FOR KEY SHARE` 构成；§4 的 `FOR SHARE` 在同一时刻（插入前一步）对同一行取锁，冲突集合相同（都与 `FOR UPDATE` 冲突），不引入新的环。

### 3.3 事务中段取变量锁与锁台账

- 允许在事务中段取变量锁的只有：发布（`applyPendingAutoVariables`，§5.4）、设计器保存（S7a，不登记提交前任务）、管理员变量操作（单行，不登记提交前任务）。重提（§6）与交接 / 恢复重发（§3.4）在中段都不取。
- 发布的中段一批覆盖它提交前所需：发布只登记 (b)，(b) 要锁的是被替换版本引用的全部自动变量，已在中段一批里（§5.4 第 2 步）。
- **锁台账**：S7e 新增 `lockVariableBatch(tx, ctx, rows)`（`rows` 为 `{id, mode}` 列表，按 id 升序逐行取所需模式，`mode` 为 `share` / `update`；设计器保存一批里两种模式都有），变量行加锁一律经它，同时在本事务上记下各 id 的模式（与提交前任务同一事务槽位）。S7e 把 S7a 的 `applyPendingAutoVariables`、设计器保存与 S4 `assertSourceReferences` 的加锁调用点改为调它（只换调用，不改语义）。
  - 同一事务第二次调用：所要 id 不是台账的子集，或要 `FOR UPDATE` 而台账只有 `FOR SHARE`，即抛程序错误（500），整个事务回滚；
  - `flushAutoVariableLifecycle` 第 1 步照此检查：台账为空则正常取一批；台账非空则所需集合须是台账中 `FOR UPDATE` 部分的子集，否则抛程序错误。
  - 程序错误即 fail-closed：宁可让这次业务失败、由测试暴露，也不让未知的取锁组合在线上死锁。现有路径都满足规则，AC-59 ②③ 验证交接与发布不触发它，④ 验证它会触发。

### 3.4 交接与恢复重发不锁已有变量

- 问题：`republishWithExceptionAdmin` 经 `writeVersionContent` 落库（主设计第 536 行）。按主设计 S7a 的写法，它会对引用的变量取 `FOR SHARE`（`assertSourceReferences`）、对涉及的变量取 `FOR UPDATE`，并在中段做收尾停用（主设计 ③）。交接随后逐单锁实例并可能结束实例，提交前又要变量锁。于是：
  - 交接在中段持有 X 后，还要逐单锁实例、在提交前再取变量一批，违反 R1（§3.2）。批内实例倒不会因此成环：交接先经 `lockHandoverParticipants`（`handover.ts` 第 117 行）对批内实例的主体员工取锁，才重发流程，审批方持有批内实例时必然也持有其员工行，交接会先在员工行上等（AC-59 ②）。但持 X 等待本身就会让交接与其他在提交前要 X 的事务交错，且被锁台账判为程序错误；
  - 中段 `FOR SHARE`、提交前 `FOR UPDATE` 是锁升级。
- S7e 合入前不成问题：那时没有提交前取变量锁的路径，审批路径不碰变量。S7e 合入时须一并改（列入回改清单第 31 条）：
  - **引用校验不加锁**：重发照抄当前已发布版本的引用，不新增对已有变量的引用。S4 用 `FOR SHARE` 是为了让“保存新引用”与“停用”互斥；照抄的引用在旧当前版本上本来就在用，新旧当前版本在同一次提交里交替可见，停用方任何时刻都看得到其中一个在用版本，不会误停。校验结果仍按 S4 现有规则，只是不加锁。
  - **存量 `specified` 落成新变量**：只 INSERT 新行（主设计 ⑧），照旧。新行的位置属于本事务锁住的流程，不与他人竞争。
  - **收尾停用推迟到提交前**：重发时不在中段执行收尾，改为登记 `{kind:'save-close', candidateIds, ctx}`，由 `flushAutoVariableLifecycle` 在同一批锁之后，以原操作者、§6.1 口径、`reason='不再被引用'` 执行。同一事务、同一操作者、同一口径，结果与中段执行相同。
- 恢复（`restore.ts` 第 260 行，空操作者调用）走同一条路径，同样适用。
- 触发点 (b) 仍不挂重发（§2.2）。

### 3.5 实例结束不锁流程头为何安全

第 2 步读流程头的 `current_version_id` / `status` 不加锁。安全，因为：

1. `current_version_id` 只会前移到新发布的版本，不会回到旧版本；流程只会从 active 变为 discarded，不会复活。所以“读到旧值”只会让检测误判为“仍在用”而跳过，不会误停。
2. 误判跳过时，另一方必然补上。实例结束与发布 / 作废登记的是同一版本 v1，按 §2.4 第 0 步，两边的锁集合都含 v1 引用的全部自动变量，在其中的 X 上串行：
   - **实例先拿到 X 锁**：它读到 v1 仍是当前版本（发布未提交），跳过并提交、放锁。发布方随后拿到 X（中段一批），提交前任务用新语句数在途为 0（实例已提交），停用。
   - **发布先拿到 X 锁**：发布数到实例仍 `running`（未提交），跳过并提交。实例事务拿到 X 后用新语句重读：v1 已不是当前版本、在途为 0，停用。
   - 作废与实例结束同理，作废的提交前任务同样锁 X。
3. §4 修复后，旧版本不会再被新实例绑定；能让旧版本重新有在途的只有重提，它的判定也在提交前、同一批锁里（§6.3）。
4. 版本引用了自动变量、却在 §2.4 第 0 步得到空集合的情况不存在；版本不引用任何自动变量时，没有可停的变量，不需要串行。

## 4. 第 6 轮 P2-1：实例绑定与发布互斥

### 4.1 问题

发起事务在 `matching.ts` `candidateBatch`（第 67 行 `v.id=p.current_version_id`）不加锁读到 v1；同时发布 v2 并清零停用 X 提交；发起事务随后在 `insertInstance`（`engine.ts` 第 1086 行）插入绑定 v1 的实例。外键只保证版本存在。结果是“绑定 v1、X 已停用”的新实例，X 被解析为 `[nobody]`，错误进入空人策略。

### 4.2 方案

在 `launch`（第 1004 行）调用 `insertInstance` 之前，新增 `lockBoundProcess(tx, ctx, matched)`：

```sql
SELECT status, current_version_id FROM approval_processes
WHERE tenant_id = $tenant AND id = $matchedProcessId
FOR SHARE
```

- `status <> 'active'` 或 `current_version_id <> matched.version.id`：抛 409 `CONFLICT`，`reason` 为 `APPROVAL_PROCESS_VERSION_CHANGED`，文案“审批流程刚刚更新，请重新提交”。整个事务回滚，业务侧不变，命令台账不留记录（同事务），用户刷新后显式重提即按新版本匹配（DEC-067，客户端不自动盲重试）。
- 通过：持有该锁直到提交，继续插入实例。
- 三个发起入口都经 `launch`：普通发起（`startOrResume` 未命中可重提实例时）、`startNewHandover`（DEC-674）、`startSpecified`。只改 `launch` 一处。重提走 `resume`，沿用原版本，不经过这里（§6）。
- 锁放在 `launch` 而不是 `matching.ts`：匹配阶段一次读同类型的多个候选流程，在那里加锁会锁住全部候选；只有最终选中的那一个需要与发布互斥。主设计 ⑨ 挂点写的是“加在发起匹配读当前版本处”，本文改到绑定处，列入回改清单。
- 为什么用 `FOR SHARE`：发布（`processRow` / `lockedForChange` 的 `FOR UPDATE`）、作废、存草稿都先取流程头 `FOR UPDATE`，与 `FOR SHARE` 互斥；多个发起之间 `FOR SHARE` 相容，不互相阻塞。不用 `FOR KEY SHARE`：它不挡不先取 `FOR UPDATE`、直接 UPDATE 非键列的写入，`FOR SHARE` 连这类写入也挡住，更稳。
- 副作用：同一流程正在存草稿或发布时，新的发起会短暂等待其提交。存草稿提交后 `current_version_id` 不变，发起照常通过。

### 4.3 不做自动重新匹配的理由

- 重新匹配可能选中另一个流程，而那个流程在匹配时同样没有加锁，同样的竞争会再出现一次，规则只能写成“重试到稳定为止”，不确定。
- 409 让发起方看到结果、自行重提；这个窗口只在发布与发起几乎同时发生时出现，代价小。

### 4.4 两种先后

- **甲先匹配、乙先拿锁发布**：乙持流程头 `FOR UPDATE` 发布 v2、提交前停用 X 并提交；甲在 `lockBoundProcess` 读到 `current_version_id = v2` → 409，无实例。
- **甲先拿到 `FOR SHARE`**：乙的发布阻塞在 `lockedForChange`；甲插入 v1 实例并提交；乙继续，被替换的 v1 有 1 个在途，X 不停用。之后该实例结束时由 (a) 检测。

## 5. DEC-861⑤ 来源流程发布时才生效（未取证假设）

### 5.1 问题

DEC-860 定自动变量是租户级、跨流程共享的同一条，人员变化时原地更新（主设计 ③ 判定表末行）。若在**存草稿**时就原地更新，当前已发布版本、其他流程、在途单之后激活的节点会立即改派，违反 DEC-861⑤“存草稿不改在用流程的路由”。

### 5.2 哪些写入要推迟

按主设计 ③ 的 V 取法，草稿保存时的判定结果分两类：

- **立即写**（照主设计 ③）：
  - 新建（没有 V、V 已停用、类型不同）：新变量来源版本是本草稿，按 DEC-861① 只给本草稿用，不影响任何在用派单；
  - V 是**占位变量**（来源版本为本草稿）时的原地更新：同理只被本草稿引用；
  - 类型不同时停用占位变量腾位：同理。
- **推迟到发布**：V 是**继承变量**（来源版本不是本草稿，即已发布的旧版本），类型 = T，默认值 ≠ P。这是唯一会改到在用派单的写入。
  - 继承变量必然仍被当前已发布版本引用：草稿由“编辑最新版本”从当前版本复制而来，复制期间流程未作废；作废流程不能再编辑。

### 5.3 待生效值存放在草稿节点来源里

- 推迟的那一处，草稿节点照常以 `public_variable` 引用 V，来源对象多一个键：

  ```json
  {"type": "public_variable", "value": "<V 的 id>", "pendingUserIds": ["<P 的人员 id>", "..."]}
  ```

  - 未选人（P 为空集，U-15）：`pendingUserIds: []`，不写变量。草稿把继承变量清空为未选人时，当前已发布版本与其他流程**不受影响**（回答主设计 ② “运行时”一条的悬置问题）；这种草稿本身也发不出去（发布检查，§5.5）。
  - 再次保存时 P 等于 V 当前默认值（按集合比较）：去掉 `pendingUserIds`。
  - P 与已存的待生效值相同：照存，不写变量。
- **不新增迁移、不新增审计动作**：
  - 待生效值随草稿节点 jsonb 落库，S7 仍不带迁移（主设计 ⑤ 第 744 行的结论不变）。
  - 草稿内容的改动已由 `approval.process.draft.update` 审计覆盖（`snapshot(view)` 含 `latestVersion` 的节点），待生效值随之有前后值；变量本身此时没有变化，不写 `auto_update`。
- **为什么放草稿节点、不放变量行**：变量行是共享的，草稿只属于一个流程；放在节点来源上，作废草稿、丢弃草稿时待生效值自然随之失效，不会残留在共享对象上。也不需要第二条变量，不碰 S1 唯一索引（`origin_version_id` 仍是旧版本，位置不变）。
- 与其他规则自洽：
  - **DEC-861①**：只有已发布来源的变量才会有待生效值，草稿期变量本来就立即写，草稿期限制照旧。
  - **S1 唯一索引**：不新增变量行，不改 `origin_*`，索引不受影响。
  - **§6.1 扫描**：jsonb 包含查询 `@> {"type":"public_variable","value":V}` 仍能匹配带 `pendingUserIds` 的对象，草稿仍算引用 V，收尾扫描、引用流程数都不受影响。
  - **`assertSourceReferences`**：校验的仍是 `{type, value}`，V 须启用。
- 类型：草稿落库定义的来源类型为 `PersistedSource = ApproverSource | (PublicVariableSource & {pendingUserIds: string[]})`，复用 S7a 把 `ApprovalNode` / `ProcessDefinition` 改为带来源类型参数的泛型（主设计 ⑦）。已发布版本的定义类型仍为 `ApproverSource`，不含该键。
- 出口守卫：发布写完后，S7a 的 `persistedSourceViolations` 增加一条“已发布版本含 `pendingUserIds` 即程序错误”。
- 不复制待生效值的路径：`newVersion` 与 `republishWithExceptionAdmin` 都以已发布版本为底稿，已发布版本不含该键。`republishWithExceptionAdmin` 遇到草稿本来就拒绝（第 594 行），所以不会出现“交接重发时有待生效值”。

### 5.4 发布时原子切换

在 `publishProcess` 里，排在发布检查（S7d，主设计 ②）之后、版本置为 published 之前，新增 `applyPendingAutoVariables(tx, ctx, draft, replacedVersionId)`：

1. 不锁被替换版本行（第 1 轮的这一步已删，理由见 §3.2 第 4 条）。
2. 变量一批经 `lockVariableBatch` 按 id 升序 `FOR UPDATE`：草稿里全部带 `pendingUserIds` 的 V，并上被替换版本引用的全部自动变量（不论状态，与 §2.4 第 0 步同一取法，供提交前任务重入不等待）。集合为空则跳过。这是发布事务里唯一一次取变量锁（§3.3）。
3. 对每个带待生效值的位置，以 `P = pendingUserIds` 重新跑一次主设计 ③ 判定表（同一函数 `materializeSpecified`）：
   - V 仍启用、类型 = T、默认值 ≠ P → 原地更新 V（`auto_update`）。操作者为发布人（`ctx`），`after` 带 `trigger:{kind:'publish', versionId: 草稿 id}`；
   - V 的默认值已等于 P（如管理员在变量页改成了同一批人）→ 不写；
   - V 已停用（管理员在草稿期间停用了它）→ 按“V 已停用”新建，来源版本为本草稿。位置（本草稿 × 节点 × 位置）此时空闲：若有非停用占位变量，节点引用的就会是它，而不是继承变量；
   - 管理员在草稿期间把 V 的默认值改成别的人：以待生效值为准覆盖。与主设计 ④“并发”中“设计器不带变量 revision，以提交的设计器内容为准”同一口径（已定，§11 ③）。
4. 改写草稿节点三列，去掉全部 `pendingUserIds`；新建了变量的位置改指新变量。
5. 照原顺序：版本置为 published → `bump current_version_id` → `audited('publish')`。`publish` 审计的 `after` 是去掉待生效值之后的内容。
6. 登记提交前任务 (b)。提交前任务所需变量都在第 2 步的一批里，锁台账检查通过。

**何时看到新值**：上述写入与 `current_version_id` 切换在同一事务，提交那一刻一起可见。

- 其他流程、本流程旧版本的在途单：节点**之后**激活时按变量当前值派单（主设计 §3.6 实时读取），即看到新人员；已派出的任务不变（同 AC-13）。
- 新发起的单据绑定新版本，看到新人员。
- 发布事务回滚（任何发布检查失败）：变量与草稿都不变，待生效值留在草稿里。
- 作废流程时草稿上的待生效值永不生效，变量不变。

### 5.5 读侧按待生效值优先

| 位置 | 改法 | 片 |
| --- | --- | --- |
| 读视图 `GET /processes/:id` 等 | 草稿节点的本位置 `autoVariable` 增加 `pendingUserIds`（仅有待生效值时出现）；`userIds` 仍为变量当前值；节点来源对象本身不返回该键。`trimProcess` 投影放行 | S7a |

- 管理员在变量页编辑自动变量**立即生效**，不属于“存草稿”，不受 ⑤ 约束（主设计 ④“管理员在变量页手改自动变量”不变）。

## 6. DEC-862 撤回计入已结束、重提被拒

### 6.1 撤回触发停用

撤回（`running → withdrawn`）在 §2.2 (a) 中登记，与终态同等处理；`withdrawn` 不属于生命周期在途（§1）。所以一个旧版本的最后一单被撤回，就会检测并可能停用它的变量。

### 6.2 重提判定

- **位置**：引擎 `resume`（`engine.ts` 第 1109 行）。只此一处：
  - 审批侧 `actions.ts` `resubmit`（第 940 行起）先调适配器 `resubmit` 再 `startOrResume`，适用于审批侧可重提的业务（`personnel_change`、`idp` 等）；
  - 任职模块的重提只能经业务侧“提交”（`adapters.ts` 第 514 行，审批侧 `resubmit` 对任职一律 409 `APPROVAL_RESUBMIT_VIA_BUSINESS`），也经 `startOrResume` → `resumableInstanceOf` 命中 → `resume`；
  - 所以放在 `resume`，所有重提入口都覆盖，且只影响“沿原实例重提”这一条。
- **判定函数** `systemRetiredVariables(tx, ctx, versionId)`（只读，不取锁）：
  1. 取版本节点三列引用的 `origin='auto'` 变量，不论状态；没有就返回空。
  2. 读状态：全部启用就返回空。
  3. 对停用的变量查审计：按 `object_type='approval-public-variable'`、`object_id = ANY(ids)`，取每条变量最近一次状态类审计（`enable` / `disable` / `auto_disable`）。最近一次是 `auto_disable`、操作者为空、且 `after.reason` 属于两个系统原因（§1）之一，即“已被系统停用”。
     - 用审计判定、不加列（已定，§11 ⑦）：S7 不带迁移、变量表没有“停用来源”列，与主设计 ③ 用审计判定“手工重新启用过”同一做法。
     - 同时看操作者与 `reason`：`restore.ts` 以空操作者调用 `republishWithExceptionAdmin`，其中推迟到提交前的保存收尾（§3.4）若停用了变量，操作者也为空，但 `reason` 是“不再被引用”，不算系统停用。
  4. 返回被系统停用的变量。
- **两次调用**：
  1. **预检**（事务中段，不加锁）：`openRun` 锁实例、状态检查与发起人检查（第 1111～1115 行）通过之后、改实例为 `running` 之前调用。有结果即抛错（见下）。作用是给出明确的错误：否则后续的 `freezeRunSubjects`、`assertExceptionAdminAvailable`、`advanceTo` 可能先因 `[nobody]` 等原因报别的错。预检不取锁，所以重提事务中段不持有任何变量锁（§3.1）。
  2. **权威判定**（提交前）：`resume` 每次都登记 `{kind:'resume-check', versionId, instanceId}`（`withdrawn → running` 与 `returned → running` 都登记）。`flushAutoVariableLifecycle` 把该版本引用的全部自动变量并进同一批锁（§2.4 第 1 步），锁后用新语句再调一次判定函数；有结果即抛错。重提判定排在同一批的停用检测之前执行。
- **抛错**：409 `CONFLICT`，`reason` 为 `APPROVAL_PROCESS_UPDATED_RESTART`，文案“流程已更新，请重新发起”。整个事务回滚，适配器已做的业务侧改动一并撤销，实例仍为 `withdrawn`（或 `returned`），`round` 不变，无 `resubmit` 日志。
- **其他情况仍照 DEC-103**（沿用原实例、原版本，不改引擎通用规则）：
  - 变量全部启用；
  - 变量由管理员手工停用（`disable`），或由保存收尾停用（操作者为保存人）：放行，运行时按 `[nobody]` 走空人策略（主设计 §3.5）；
  - 被系统停用后又被管理员手工重新启用：最近一次是 `enable`，放行。
- `returned` 实例不会命中：`returned` 属于生命周期在途，它的版本不会被检测为清零，其变量不会被系统停用（除非被别的版本清零时停用——不可能，扫描会看到本版本在用）。判定仍对 `returned` 执行，代价是一次查询与提交前的一批锁。
- 被拒后的用户路径：在业务侧删除或作废原申请（业务删除走 `cancel`，实例 `withdrawn → cancelled`，不再触发检测），再新建申请，按当前版本重新匹配。复刻不提供“一键作废并重新发起”，本单不加；前端沿用通用错误提示显示服务端文案。

### 6.3 并发：停用与重提竞争

- 重提方与停用方都在提交前对同一版本引用的变量取 `FOR UPDATE`（§2.4 第 0 步，集合相同），在 X 上串行。
  - **重提先拿到 X**：判定读到 X 启用，通过；置为 `running` 的实例随提交可见。停用方拿到 X 后用新语句扫描，看到该版本有生命周期在途实例，不停用。
  - **停用先拿到 X**：重提方的预检此前已通过（当时 X 启用）。停用方数到该实例仍是 `withdrawn`（重提未提交），不算在途，停用并提交。重提方拿到 X 后用新语句判定：X 停用、最近审计为系统停用 → 409，整个事务回滚。
- **重提后当场结束**（如 `returned` 重提后剩余节点全部自动通过、实例直接 `approved`）：`persistRun` 因 `before='returned'` 登记 v1 的停用检测（§2.2 (a)），与重提判定在同一批锁里。与发布的两种先后：
  - **发布先拿到 X**（发布中段一批）：发布的提交前任务数到 I 仍是 `returned`（重提未提交），算在途，不停 X，提交。重提方拿到 X：判定 X 启用，通过；停用检测用新语句看到 v1 已不是当前版本、I（本事务写成 `approved`）不在途，停用 X，`trigger={kind:'instance', instanceId:<I>, status:'approved'}`。
  - **重提先拿到 X**：判定通过；停用检测读到 v1 仍是当前版本（发布未提交），跳过，提交。发布拿到 X 后，提交前任务用新语句数在途为 0，停用 X，`trigger={kind:'publish', newVersionId:<v2>}`。
  - 两种先后都只有一条 `auto_disable`，无死锁（AC-60）。
- 不需要版本锁：判定只读已发布版本的不可变内容；会被停的只有变量，锁变量就够了。
- 若只做预检、不在提交前复核：预检读到启用后、提交前，停用方用 READ COMMITTED 数到该实例仍是 `withdrawn`，于是停用；两者都提交后，就出现“已重提、变量已被系统停用”的实例。AC-55 ④ 反序区分这一实现。
- 若像第 1 轮那样在中段取 X 的 `FOR SHARE`：当场结束时提交前还要 X 的 `FOR UPDATE`，是锁升级；与发布形成反向等待。AC-60 区分这一实现。

## 7. DEC-861⑦ 作废流程的自动变量（未取证假设）

- 规则：流程作废后，其版本引用的自动变量，在这些版本都没有生命周期在途单、且不被其他在用版本引用时，由系统停用。作废流程的草稿与当前版本不算在用（§1）。
- 触发点：
  1. **作废时**：§2.2 (c)，`discardProcess` 登记该流程全部版本（含草稿、当前版本、旧版本）。提交前任务里，没有在途的版本参与检测，有在途的跳过。
  2. **作废后最后一单结束时**：§2.2 (a) 自然覆盖。此时流程已非 active，第 2 步不再因“是当前版本”而跳过，只看在途。
- `reason` 取 `作废流程在途单清零自动停用`（已定，§11 ②），`trigger` 分别为 `{kind:'discard'}` 与 `{kind:'instance', …}`。
- 作废与发起的竞争：发起方 `lockBoundProcess` 读到 `status='discarded'` → 409 `APPROVAL_PROCESS_VERSION_CHANGED`（§4）；作废先等发起方的 `FOR SHARE` 释放时，作废检测会看到新实例在途，跳过，等它结束再由 (a) 停用。
- 作废流程的变量被其他流程引用：扫描排除，不停用。之后那个流程不再引用、其版本清零时，由那个流程的触发点检测。
- 作废流程草稿上的待生效值（§5）不生效，变量保持原值。

## 8. 与保存收尾、DEC-861⑧ 的关系

| 停用路径 | 触发 | 操作者 | `reason` | 扫描口径 | 候选 |
| --- | --- | --- | --- | --- | --- |
| S7a 保存收尾（主设计 ③） | 设计器保存草稿（含 ⑧ 第三类：手工重新启用过的本流程自动变量） | 保存人 | `不再被引用` | §6.1（含 `withdrawn`） | 保存前引用过的、占位变量、手工重新启用过的 |
| 本文系统停用 | 实例离开在途 / 发布替换当前版本 / 作废 | 系统（空） | `旧版本在途单清零自动停用` 或 `作废流程在途单清零自动停用` | 生命周期（§1） | 清零版本引用的启用自动变量 |
| 管理员手工停用（主设计 ④ / §6.2） | 变量页 | 管理员 | 无 | 只做影响确认 | — |

- 动作都是 `approval.public_variable.auto_disable`（手工停用为 `disable`），区分靠操作者与 `reason`。DEC-862 的“系统停用”只认第二行（§6.2）。
- **不重复停**：两条自动路径的写入都是 `UPDATE ... WHERE status='enabled' RETURNING`，只对返回行写审计。同一变量同时被两条路径选中时，后到者拿不到行，不写审计。两条路径都对变量取 `FOR UPDATE`，互相串行。
- **候选重叠**：⑧ 第三类（手工重新启用过的本流程自动变量）可能同时是某个清零版本的候选。管理员重新启用后，若再无状态迁移，系统停用不会再次触发（它只在三个触发点运行）；下次该流程保存时由 ⑧ 停用，操作者为保存人。这正是 ⑧ 的原意，两者不冲突。
- **口径宽窄不同不矛盾**：保存收尾用 §6.1（`withdrawn` 算在用），比生命周期口径保守，可能留下系统停用会停的变量；之后该版本的触发点（如作废）会再检测。反过来，系统停用不会停保存收尾认为仍在用的变量以外的东西——生命周期口径只比 §6.1 少 `withdrawn` 与作废流程的草稿 / 当前版本，这两类正是 DEC-862 与 ⑦ 指明要算“已结束”的。
- 保存收尾不改：主设计 ③ 的三类候选、§6.1 口径、`reason` 原样保留，S7a 照主设计实现。
