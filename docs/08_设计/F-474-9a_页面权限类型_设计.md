# F-474-9a 页面权限类型与身份详情「页面权限 / 菜单组」页签：设计

> 任务：F-474 续批 9a（`F474_plan.md` 分批表 F-474-9；缺口 #26 的「页面权限 / 菜单组」部分）。只出设计，不改产品代码、测试、迁移、生成物。
> 作用对象：**复刻系统**。北森原站只有只读取证引用，本文不要求在北森测试租户做任何写入。
> 性质：**授权类**（DEC-441）。后续 9b 的 PR 触及身份授权、授权项编码与授权版本守卫，须先经 Codex 独立审查再进合并队列；审查重点见 §4.4。
> 口径来源：DEC-043、DEC-399、DEC-402（④ 页面权限 = 载体对象 + `app_page` 按钮，不新增权限类型；总原则不加开关、不兼容存量）、DEC-439④（授权版本）、DEC-441、DEC-778。
> 与 6a / 7a / 8b 的关系：7a、8b 各新增授权对象（改授权版本）；本篇**不新增授权编码**，与它们的版本顺序互不依赖。

## 0. 摘要与推荐

- **推荐（U1-A）：不新增存储、不新增授权编码种类。** 「页面权限」在复刻里仍落成「应用级载体对象 + `app_page` 按钮」（DEC-402④ 已定），本篇只补三件事：
  1. 域层加一份**页面目录**（`PAGE_CATALOG`：页面编码、所属应用、名称、载体对象），把散落在 `Qualification.Pages` 一处的约定变成可登记、可校验的目录；
  2. 身份详情加两个页签：**页面权限**（可增删，读写走现有「保存对象权限」入口）和**菜单组**（只读，由对象权限推导）；
  3. 授权版本、指纹、`standard-grant-changes.json`、`AC-PLAT-F061-grants` **默认不动**——9b 不改任何预置身份，授权项编码集合不变，守卫测试用「指纹不变」自证。
- **不做**：独立的页面权限表、`page:<编码>` 新授权项种类、可编辑的菜单授权。理由与代价见 §8 U1、U2。
- **首版页面范围（U3-A）只登记有运行时闸门的页面**：现仅「员工发展通道」一项。原站任职资格应用有 7 个页面、组织员工有 12 个同名候选（§1）；复刻其余页面没有页面级闸门，登记了也不起作用，等各模块真有页面闸门时随该模块 PR 登记。
- 规模：9b 一个 PR，约 1200～1600 行，远低于 3000。

## 3. 数据模型与迁移草案

**无迁移，无新表，无新列。**

### 3.1 页面目录（域层，纯函数、无 IO）

```
PageDefinition { pageCode, appCode, name, carrierObject }   // name 走资源文件（DEC-045）
PAGE_CATALOG: readonly PageDefinition[]                      // 现仅 EmployeeDevelopmentChannel
```

- 载体对象命名固定 `<应用>.Pages`，对象无字段、按钮 = 页面、`level = 'app_page'`（沿用 `QUALIFICATION_PAGES` 写法）；`PAGE_CATALOG` 与载体对象定义在同一文件里互相校验（页面编码 ⊂ 载体按钮；载体按钮 ⊂ 页面编码），由守卫测试把关。
- 载体对象只在 `apps/api/.../permission/catalog.ts` 的 `objectCatalog` 登记，**不进**各模块 `*_OBJECTS`（与 `QUALIFICATION_PAGES` 同一原因：避免被「全部对象」遍历）。

### 3.2 存储

沿用 `permission_profile_objects`（载体对象行）与 `permission_profile_buttons`（页面行：`button_code = pageCode`、`level = 'app_page'`）。租户隔离、RLS、主键、级别校验约束都已存在，不改。

页面权限可用的前提（已有的依赖链，页签要如实展示）：身份已含该**应用**（`permission_profile_apps`）→ 载体对象行存在（`op:view`）→ 页面按钮行。缺任一级，页面按钮没有授权效果（`grantParentCode` 的父子关系，`standard-grants.ts` 约 266-293 行）。

### 3.3 授权项编码与台账

- 页面行的授权项编码是现有按钮编码 `<身份>/<载体>/button:<页面>@app_page`，**不新增编码种类**，`parseGrantCode` 不改。
- 保存页面权限经现有 `setObjectPermission` → `registerManagedGrants`，会按现有规则写 `<身份>/<载体>/@modified` 标记，所以管理员删掉的页面不会被补装补回（撤销不补回，F-061）。
- 租户隔离：载体对象行、按钮行、台账均带 `tenant_id`，走现有 RLS；**不引入**任何跨租户共享的页面数据（页面目录是代码常量，不是表）。

## 4. 接口与权限

### 4.1 接口

**默认不新增路由。** 页签用现有三条：
- 读：`GET /api/tenant/permission/profiles/:id`（已返回 `objects[].buttons`，含载体行；ETag = revision）；
- 写：`PUT /api/tenant/permission/profiles/:id/objects/:objectCode`，`objectCode` 为载体对象，body 为 `{ fields: [], buttons: [...app_page 按钮], dataOperations: 全 false, expectedRevision }`；
- 页面目录由前端直接 import 域层 `PAGE_CATALOG`（与 `APP_OBJECT_DIRECTORY` 同一做法，前后端共用一份）。

菜单组页签（只读）：前端用 `GET /profiles/:id` 的 `objects` + `apps` 与 `APP_OBJECT_DIRECTORY` 推导「该身份能进入哪些应用、各应用的入口对象」，**不新增接口**。

### 4.2 权限

- 准入：与对象权限完全一致，管理员动作 `profile_manage`（`policy.ts:74-77`）；不新增管理员动作、不新增授权对象。
- 页面闸门：9b **不新增运行时闸门**，仍只有 `employeePageGranted` 一处。首版不改它的任何判定（含「员工」身份缺载体行默认授予）。
- 菜单：保持「菜单可见 = 应用下有可见入口对象」（`me-snapshot.ts`），页面权限、菜单组页签都不改变菜单可见性。

## 5. 前端页面与交互要点

身份详情（`ProfilesPage.tsx`，现为只读）在「基础信息」与现有对象页签之间加一个顶层页签组：**菜单组 / 页面权限 / 对象权限**（对象权限 = 现有按对象的子页签，载体对象不再出现在这里，避免两处可改）。

**页面权限页签**
- 列表按应用分组：页面名称、页面编码、所属应用、状态（已授予 / 默认授予 / 缺前置）。
- 「新增」：弹窗按应用分组列出 `PAGE_CATALOG` 中该身份尚未授予的页面，可按名称 / 编码筛选，多选后确定；「删除」：单行，确认框说明「删除后持有该身份的用户立即失去该页面」。
- 缺前置（身份未含该应用）：行置灰并提示「需先在应用范围中加入 X」，不静默替管理员加应用。
- 「页面内元素权限配置」列：原站有（§1.3），含义待取证，**首版不做**（U8 列在 §8 备注）。
- 保存走 `PUT /profiles/:id/objects/<载体>`，409 时提示刷新，不自动重试；有写权限判断沿用 `editable`。
- 文案走资源文件（DEC-045）。

**菜单组页签（只读）**
- 标题注明「由对象权限推导，调整请在对象权限中修改」。

## 7. 验收要点（编号 `AC-PGP-01..12`，后续开发单可直接抄）

1. **AC-PGP-01** 页面目录与载体对象互校验：`PAGE_CATALOG` 每页对应载体按钮，载体按钮都在目录里；载体对象无字段、按钮层级全为 `app_page`。
2. **AC-PGP-02** 载体对象只在 `objectCatalog` 登记；不出现在任一 `*_OBJECTS` 与「全部对象」遍历中（与现有 `QUALIFICATION_PAGES` 行为一致）。
3. **AC-PGP-03** 授权版本不变：`STANDARD_GRANT_CODES`、指纹、版本号与基线一致；`standard-grant-changes.json` 与 HISTORY 未改。
4. **AC-PGP-04** 页面权限页签读：展示身份已授予页面、可新增页面、缺前置页面；无 `profile_manage` 时 403，不泄露身份数据。
5. **AC-PGP-05** 新增页面：保存后 `permission_profile_buttons` 多一行 `app_page`；`employeePageGranted` 对持有该身份的用户由拒绝变放行。
6. **AC-PGP-06** 删除页面：对应行被删；放行变拒绝（`403 PAGE_PERMISSION_REQUIRED`）；补装不补回（`@modified`）。
7. **AC-PGP-07** 载体对象只能授按钮：载体 body 带字段、带任一数据操作为真均被拒（`VALIDATION_FAILED` 或沿用 `UNKNOWN_FIELD` 类错误码）；页签前端只会对载体对象发保存请求。
8. **AC-PGP-08** 「员工」身份缺载体行时页签显示「默认授予」；首次保存不改动的选择后，`employeePageGranted` 结果不变；清空选择才会变为拒绝。
9. **AC-PGP-09** 并发：`expectedRevision` 过期 → 409，前端提示刷新、不自动重试；目录变化 → 409 `CATALOG_CHANGED`。
10. **AC-PGP-10** 缺前置：身份未含应用时，页面行置灰且保存时不替管理员加应用。
11. **AC-PGP-11** 菜单组页签只读：内容 = 应用 × 入口对象，与 `me-snapshot` 的 `entryObjects` 口径一致；撤销对象查看后页签同步消失。
12. **AC-PGP-12** 租户隔离：租户 A 管理员读写不到租户 B 身份的页面行；`PAGE_PERMISSION_REQUIRED` 响应不含身份编码 / 名称。

## 8. 未决 / 假设

> 作用对象均为**复刻系统**；推荐项按 DEC-402「不加开关、不兼容存量、取最简单做法」给出。

**U1 页面权限落点**
- A（推荐）载体对象 + 页面目录，存储与授权编码不变，页签是视图 + 现有保存入口。例：为「员工」身份删除「员工发展通道」，保存的是 `Qualification.Pages` 的一行按钮删除，补装、接管、授权版本都无感。
- B 独立表 `permission_profile_pages` + 新编码种类 `page:<编码>`。例：编码变成 `employee_self_service/page:EmployeeDevelopmentChannel`，需迁移现有载体行、改补装 / 接管 / 守卫，且出现两套来源并存的判定风险（越权面更大）。
- C 不做页面权限，只做菜单只读页签。例：缺口 #26 的页面权限部分直接关闭，与 R1 底座「首版必做前三项」冲突。

**U2 菜单组**
- A（推荐）只读推导视图。例：身份只含「任职资格」应用且有 `Qualification.Pages` 查看 → 页签显示「任职资格 → 员工发展通道页面」。
- B 可编辑的菜单授权（新存储 + 菜单可见 = 菜单授权 ∧ 对象可见）。例：管理员取消勾选某菜单，即使对象可见该菜单也消失——这改变现有「菜单可见 = 对象可见」的授权语义，违反本篇前提，且原站「同步添加页面 / 对象权限」的行为本身待取证（§1.5）。
- C 不显示菜单组页签。例：身份详情只有页面权限与对象权限两栏，与原站页签数不一致。

**U3 首版页面范围**
- A（推荐）只登记有运行时闸门的页面（现仅「员工发展通道」）。例：页面权限页签对「员工」身份显示 1 行。
- B 为各应用主入口补页面闸门并登记。例：「人员管理 → 在职员工」加页面闸门——会让现有身份在升级后立刻失去入口，属授权语义变更，须另立任务逐模块做。

**U4 载体粒度**
- A（推荐）每应用一个载体 `<应用>.Pages`。例：将来「组织」应用的页面落 `TenantBase.Pages`，各应用权限边界一致（页面依赖应用授予）。
- B 全局单一载体。例：所有页面落一个对象，父子关系（对象 → 应用）无法表达「页面需先授予所属应用」。

**U5 「员工」身份缺载体行的呈现**
- A（推荐）显示「默认授予」，首次保存先固化有效默认值。例：管理员只想加一个别的页面，不会顺带关掉发展通道。
- B 不特殊处理，按「没行 = 未授权」显示。例：管理员首次保存空选，员工立刻看不到发展通道。

**U6 拦截提示是否列身份名**
- A（推荐）只列页面与应用。例：「缺少【任职资格】应用的【员工发展通道】页面权限」。
- B 照原站列出缺权限的身份名。例：普通用户能看到租户内自定义身份名称（信息披露面扩大，且原站提示格式待取证，§1 待取证⑥）。

**U7 是否同 PR 给其他预置身份补页面**
- A（推荐）不补，授权项编码集合与版本全不变。
- B 补（例如给人才发展类管理员加页面）。例：会改 `STANDARD_GRANT_VERSION` / 指纹 / HISTORY / `standard-grant-changes.json`，存量租户补装时新增授权，须单独评估。

**U8 「页面内元素权限配置」**
- 原站行有此项（§1.3），含义待取证（待取证②）。推荐首版不做，等取证后另开任务；9b 页签不预留占位。
