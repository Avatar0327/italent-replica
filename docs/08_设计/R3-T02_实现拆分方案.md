## 6. C2 评定流程（11 个子 PR，约 15,550 行）

C2 按“底座与离职接入 → 申报 → 审批与撤销 → 材料 → 场次 → 评分 → 校准 → 发布 → 完成活动 → 入口”拆。

**v2 关键调整（P2-02）**：离职事件捕获、离职终止处理器与周期写守卫 `EMPLOYEE_LEFT` 前移到 **C2-1b**，在第一个能产生评定数据的子 PR（C2-2）之前上线。所以 C2 任何时候合并到 main，已有评定的离职都会被捕获。

**唯一负责（P2-05）**：
- **终止内核** `terminateEvaluations(tx, ctx, ids, reason)` 由 C2-1a 建立；
- **撤销命令**只由 C2-3 实现；
- 在途审批的处置（Q-T02-12，DEC-365④ 已定：引擎 cancel 立即作废）由 C2-3 填进终止内核的审批步骤；
- 离职（C2-1b）、完成活动（C2-9）都调用同一内核，不各写一份。

## 10. F-055 修法说明（实现另派 Sonnet，单独 PR，须在 C1-4 与 C2 之前合并）

### 10.1 问题与现状（main 6b5fda8 核对）

**未来生效的记录在保存当时就落到时间轴上，并立即写出 `employment.record.create`。**
- 直接业务保存：`apps/api/src/modules/employment/write-service.ts` 的 `if (normalized.mode === 'direct') await materializeEmploymentRecord(…)`（后续任务表记的第 159 行，现第 163 行）→ `auditMaterialization`（记的第 836 行，现第 844～870 行）→ `context.ts` 的 `auditEmployment` 写进 `employment_outbox`，`created_at` 为保存时刻。

- 审批单：通过而未到生效日时停在 `approved`，到期由激活任务落地（`transitions.ts` 的 `activate` 校验 `EFFECTIVE_DATE_NOT_REACHED`），不提前写事件。

**现有消费方。** `apps/api/src/modules/transfer/completion.ts`（DEC-163 补全待办）已读 `employment.record.create`，并用“关联 `employment_timeline` 且 `t.start_date <= 租户今天`”做到期门禁：未到期或已不在时间轴的记录都不产生待办。它是**须保持行为不变的现有消费方**。

**将新增的消费方。** R3-T02 的 C1-4（资格同步）与 C2-1b（离职终止）以触发器订阅该事件入队。

**不在本次范围。** 任职状态钩子 `status-hooks.ts` 的 `onRecordMaterialized` 在落地时同步调用，注释已约定“未来日期由订阅方的夜间任务按生效日处理”（T05 A3 照此实现），F-055 不改钩子。

### 10.2 修法：方案 A′——不改表、不回填，把现有门禁抽成公共谓词并加复核

v1 曾提出给 `employment_outbox` 加 `effective_date` 列并回填。该表只允许追加，回填的 UPDATE 会被 0013 的触发器以 55000 拒绝（审查已复现）。受控暂停只追加约束会削弱审计不可变性，因此 v2 改为**不需要任何 UPDATE、也不加列**的方案。

**1. 到期门禁（事件何时发、到期如何处理）**
- 事件仍在落地事务里同事务写出，保持 DEC-019 / outbox 与业务写入同提交，写出时机不变。
- **到期不重新发出新事件**。“是否到期”不存在事件行上，而是读该事件对应记录的**当前**时间轴：
  - 新建 `apps/api/src/modules/employment/record-events.ts`，导出两个谓词，`today` 一律用租户时区当天（DEC-056）。
  - **`recordEventDueSql(eventAlias, today)`（严格到期）**：
    - `event_type <> 'employment.record.create'` 时恒真；
    - 否则要求 `EXISTS (SELECT 1 FROM employment_timeline t WHERE t.tenant_id = e.tenant_id AND t.record_id = e.object_id AND t.start_date <= today)`。
    - 这正是 `completion.ts` 已在用的门禁；抽出后 `completion.ts` 改用它，行为不变（已删除的记录不产生补全待办）。
  - **`recordEventReadySql(eventAlias, today)`（队列取数）** = 严格到期 **或记录已消失**：
    - 后者即 `NOT EXISTS (SELECT 1 FROM employment_timeline t WHERE t.tenant_id = e.tenant_id AND t.record_id = e.object_id)`，记录已删除 / 已撤销，不在时间轴上。
    - 状态队列消费者（C1-4、C2-1b）一律用它取数，“生效日前保存、消费前删除”的事件也会被取到，经复核得到 `gone` 后标 `skipped`，不会永远停在 pending。
    - 只有“仍在时间轴上且未到期”的事件不取。
- 调动改期挪动时间轴后，门禁自动按新日期判断。
- **消费方约束**：凡订阅 `employment.record.create` 的状态队列消费者，必须按“状态队列 + `recordEventReadySql`”取数，**不得用 `created_at` 高水位游标**，否则未到期事件会被游标越过。这条写进 `record-events.ts` 注释，C1-4 / C2-1b 遵守。
- **触发器入队**：C1-4 的触发器只记 `outbox_id`，到期比较在消费者里按租户当天做（触发器不知道租户时区）。

**2. 处理时复核记录仍有效（持员工锁后复核，再写派生数据）**
- `recheckRecordEvent(tx, ctx, recordId, today)` 返回三态：
  - `{ kind: 'effective', record }`：记录仍在时间轴上且 `start_date ≤ today`；
  - `{ kind: 'not_yet', effectiveDate }`：仍在时间轴上但 `start_date > today`，以**当前**时间轴日期为准，事件写出时的日期作废；
  - `{ kind: 'gone', reason: 'RECORD_NOT_EFFECTIVE' }`：已删除（有墓碑 / 不在时间轴）或已撤销。
- 读取方式：复用 `employment/read-model.ts` 的时间轴读取，不另写一套有效性判断。
- **并发约束**：消费者必须先 `lockEmploymentEmployee(tx, ctx, employeeId)`（`FOR NO KEY UPDATE`，与任职写入、删除、改期同一把员工锁），再调 `recheckRecordEvent`，再写派生数据（子集、终止评定），三步在同一事务。任职删除 / 改期也先持这把锁，两者因此串行：
  - 删除先提交时，消费者复核得到 `gone`；
  - 消费者先提交时，删除的联动按删除自己的规则处理（如 C1 撤销任职不删子集，DEC-335② 🟡）。
- 消费方对三态的处理（都在持员工锁、复核之后的同一事务里更新队列行）：
  - `gone` → `skipped: RECORD_NOT_EFFECTIVE`；
  - `not_yet` → 回 `pending`，`next_attempt_at` 不提前（下次仍由 `recordEventReadySql` 决定能否取到）；
  - `effective` → 正常处理后 `done`。

**3. 受影响的入口与下游**
- 写出事件的入口：
  - `write-service.ts` 直接保存 → `materializeEmploymentRecord` → `auditMaterialization`；
  - `transitions.ts` 审批即时生效与激活任务（同一函数，生效日 ≤ 今天，门禁自然放行）；
  - `org-adjustment.ts` 组织调整；
  - 导入路径（经 `materializeEmploymentRecord`）。
  - 这些入口本次都不改。
- 现有消费方：`transfer/completion.ts` 改用 `recordEventDueSql`（严格到期，不含“已消失”），行为不变，由回归测试锁定。
- 新消费方：C1-4 `qualification_sync`、C2-1b `evaluation_leave`。
- 不受影响：`status-hooks.ts` 订阅方（T05 / T06）；组织联动与重放足迹（`org/employment-linkage.ts`、`permission/employment-replay.ts`）只读 `object_id` / `command_id`。

**未采用的方案：**
- **方案 A（加列 + 回填）**：与只追加约束冲突。改成“在迁移事务里受控暂停触发器 → 回填 → 恢复”，等于为一次回填开了审计不可变表的口子，还要额外证明失败回滚后约束仍有效；而门禁信息本来就在时间轴上，不必冗余存一份。
- **方案 B（到期由夜间任务补发一条新事件）**：要新建按租户时区逐日扫描的定时任务及其幂等键、失败重试（DEC-052）；还会让同一记录有“保存时 / 生效时”两种事件，下游更容易用错。现有 `completion.ts` 已证明“读时间轴门禁”可行，没有必要另起任务。
