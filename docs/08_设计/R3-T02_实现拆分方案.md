## 8. F-055 修法说明（实现另派 Sonnet，单独 PR，须在 C1-4 与 C2 之前合并）

### 8.1 问题与现状（main 6b5fda8 核对）

**未来生效的记录在保存当时就落到时间轴上，并立即写出 `employment.record.create`。**
- 触发点一：`apps/api/src/modules/employment/write-service.ts` 的直接业务保存（`if (normalized.mode === 'direct') await materializeEmploymentRecord(…)`，后续任务表记的第 159 行，现第 163 行）。
- 由此进入 `auditMaterialization`（后续任务表记的第 836 行，现第 844～870 行），经 `context.ts` 的 `auditEmployment` 写进 `employment_outbox`，`created_at` 为保存时刻。
- 触发点二：组织调整的 `org-adjustment.ts` 同样写 `employment.record.create`（第 85 行附近）。

**审批单没有这个问题。**
- 审批单走 `transitions.ts`：审批通过而未到生效日时停在 `approved`，到期由激活任务落地（`activate` 动作校验 `EFFECTIVE_DATE_NOT_REACHED`）。
- 因此只有直接保存与组织调整两条路径会写出“未来生效”的事件。

**影响。**
- 目前 main 上没有按 `event_type = 'employment.record.create'` 消费的下游（`job/sequence-worker.ts` 只消费序列同步事件），所以 F-055 不改变现有行为。
- R3-T02 的 C1-4（资格同步）与 C2-9b（离职终止）将以触发器订阅这个事件，是第一批受影响的消费者。
- 任职状态钩子 `status-hooks.ts` 的 `onRecordMaterialized` 同样在落地时同步调用，但它的注释已约定“未来日期由订阅方的夜间任务按生效日处理”（T05 A3 照此实现），F-055 不改钩子。

### 8.2 修法（推荐方案 A：事件照常同事务写出，带生效日门禁；到期不补发）

1. **生效日到期门禁（事件何时发、到期如何处理）**
   - 迁移给 `employment_outbox` 加 `effective_date date NULL`，并加索引 `(tenant_id, event_type, effective_date)`。
   - 写入规则：`auditEmployment` 增加可选的 `effectiveDate` 参数并写入新列。`auditMaterialization` 传 `payload.effectiveDate`；组织调整传它的 `effectiveDate`；其他事件不传（NULL = 立即可消费）。
   - 存量回填：同一迁移把存量 `employment.record.create` 行按 `employment_records.start_date`（`object_id = id`）补齐。
   - 何时发：事件仍在落地事务里写出，保持 DEC-019 / outbox 与业务写入同事务提交。**到期不重新发出新事件**，事件行在租户本地日期到达 `effective_date` 时变为“可消费”。
   - 门禁谓词：在 `apps/api/src/modules/employment/record-events.ts` 导出 `employmentEventDueSql(alias, today)`，即 `alias.effective_date IS NULL OR alias.effective_date <= today`。`today` 一律用租户时区当天（DEC-056）。
   - 消费方约束：凡订阅 `employment.record.create` 的下游必须按“状态队列 + 到期门禁”取数，**不得用 `created_at` 高水位游标**，否则未到期事件会被游标越过。这条约束写进该文件注释，由 C1-4 / C2-9b 遵守。
   - 触发器入队规则：C1-4 的入队触发器把 `NEW.effective_date` 拷进队列的 `due_date`。触发器不知道租户时区，到期比较在消费者里按租户当天做。
2. **处理时复核记录仍有效**
   - 同一文件导出 `recheckRecordEvent(tx, tenantId, recordId, today)`，返回三态：
     - `{ kind: 'effective', record }`：记录仍在 `employment_timeline` 上，且 `start_date ≤ today`；
     - `{ kind: 'not_yet', effectiveDate }`：记录仍在时间轴上，但 `start_date > today`。这包括调动改期（`employment.transfer.rescheduled`）把生效日往后挪的情况，此时以**当前**记录的 `start_date` 为准，事件里的旧日期作废；
     - `{ kind: 'gone', reason: 'RECORD_NOT_EFFECTIVE' }`：记录已删除（墓碑 / 只留历史）或已撤销，不在时间轴上。
   - 消费方处理：`gone` → `skipped`（不生成子集、不终止评定）；`not_yet` → 回 `pending`，`due_date` 改为新的生效日；`effective` → 正常处理。
   - 读取方式：复用 `employment/read-model.ts` 的时间轴读取，不另写一套有效性判断。
3. **受影响的入口与下游**
   - 写出事件的入口（带日期）：`write-service.ts` 直接保存 → `materializeEmploymentRecord` → `auditMaterialization`；`transitions.ts` 审批即时生效与激活任务（同一 `materializeEmploymentRecord`，生效日 ≤ 今天，门禁自然放行）；`org-adjustment.ts` 组织调整；导入路径（经 `materializeEmploymentRecord`，自动覆盖）。
   - 下游消费者：C1-4 `qualification_sync`、C2-9b `evaluation_leave`（都以触发器入队，使用门禁与复核）。
   - 不变的部分：`status-hooks.ts` 订阅方（T05 继任、T06 人才池）与组织联动重放足迹（`org/employment-linkage.ts`、`permission/employment-replay.ts`）只读 `object_id` / `command_id`，不受新列影响，回归测试覆盖。

**未采用方案 B**（到期由夜间任务补发一条新事件）。原因：
- 要新建按租户时区逐日扫描的定时任务，还要处理幂等键与失败重试（DEC-052）；
- 到期前删除的记录还要补“撤销发出”；
- 两种事件语义（保存时 / 生效时）并存，下游更容易用错。

方案 A 只加一列、一个谓词、一个复核函数。
