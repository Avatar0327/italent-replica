# 演示配套：当前用户权限快照路由与授权声明

依据：DEC-456（前端 FE-0 演示配套契约）、DEC-469（Opus 设计、Claude Sonnet 实现）、AGENTS.md §10「权限」；沿用 F-039 当前 Markdown 声明格式（参照 F-058 人员头像路由声明）。

## 背景

FE-0 的左侧菜单在 `apps/web/src/demo-stubs/navigation.ts` 按应用逐个对象探测 `GET /api/tenant/permission/me/objects/:objectCode`（首屏 N+1），settings 另调 `admin-menus`，self / manager / approval 分别探测 `/self-service/profile`、`/employment/transfers/manager`、`/approval/todos`；数据范围恒为“不可用”；租户名、时区、显示名在 `demo-stubs/session.ts` 硬编码。本路由一次给出这些信息，前端切换由后续前端片完成（本 PR 不改 `apps/web`）。

## 授权契约

- 本人读取：当前用户由租户中间件确定，不接收用户 ID 或租户 ID 之外的任何参数。F-039 按 `member` 预设登记，必需项表写空数组（与 `me/objects` 同），不要求任何管理员能力或对象权限。
- 只读：不写业务表、不写审计 / outbox / 命令台账，没有幂等键和 If-Match；验收测试比较请求前后租户内全部带 `tenant_id` 的表行数。
- 每次请求从库里重新读取身份、管理员能力、员工绑定与数据范围，没有缓存（AGENTS.md §10）；撤权后下一次请求立即生效。
- 对象判定走 `modules/permission/object-access.ts` 的唯一入口，`/me/objects/:objectCode`、本快照与授权器对同一用户同一对象的 `object.view` 结论一致（见下“一致性约束”）。
- 只返回摘要：不含字段清单、按钮清单（任职对象 274 字段 / 349 按钮），不物化人员集合；响应体在默认 32KB 上限内（验收测试断言），无需在 `app.ts` 登记放宽。
- 授权项编码集合不变，不动授权版本与指纹。

## 新路由

| 方法 | 路径 | 类型、操作、按钮 | 范围 | 字段 | 写足迹、其他 |
|---|---|---|---|---|---|
| GET | `/api/tenant/permission/me/snapshot` | member；本人权限快照；无按钮 | 当前有效成员本人；数据范围只给摘要 | session、apps、scope、adminMenus（见下，权限结构而非业务字段） | 无写足迹；批次沿用权限模块 |

## 返回结构（四个字段全部必有）

```
{
  session:   { tenantId, tenantName, timezone, today, userId, displayName, employeeId | null },
  apps:      [{ app, visible, entryObjects: string[] }],
  scope:     [{ app, status: 'all' | 'limited' | 'none', organizationIds: string[], truncated: boolean }],
  adminMenus:[{ code, path, implemented, editable }]
}
```

### session

| 字段 | 来源 |
|---|---|
| tenantId、timezone | 租户中间件已校验的当前租户上下文 |
| tenantName | 平台租户资料（`tenants.name`），不硬编码 |
| today | 租户时区的当天日期（`tenantLocalDate(clock, timezone)`），格式 YYYY-MM-DD，也是经理身份、数据范围解析的 `asOf` |
| userId、displayName | 当前账号（`users.display_name`） |
| employeeId | 账号绑定的员工档案 ID；未绑定为 `null`（与 `self` 应用可见性同一判定） |

### apps

- 顺序固定为前端 `APP_ROUTES` 的 15 个应用键：org、job、staff、transfer、approval、self、manager、settings、talent、qualification、evaluation、survey360、talent-review、succession、idp。
- `entryObjects`：该应用菜单对象目录（`packages/domain/src/permission/app-directory.ts` 的 `APP_OBJECT_DIRECTORY`，后端与前端共用；每个应用的主入口对象排第一，其余按目录顺序）中，当前用户 `object.view` 判定为允许的对象编码。
- `visible`：
  | 应用 | 口径 |
  |---|---|
  | org、job、staff、transfer、talent、qualification、evaluation、survey360、talent-review、succession、idp | `entryObjects` 非空（至少一个菜单对象可查看） |
  | settings | `visibleEnterpriseMenus(管理员能力)` 非空（与 `GET /admin-menus` 同一函数） |
  | self | 当前用户有本人员工档案（复用 `/self-service/profile` 的 `boundEmployee`，不发 HTTP） |
  | manager | 能查看任职记录对象，且经理自助身份有效（`managerIdentity.active`），且 `Transfer.Manager`（canApply）或 `Transfer.Hr`（canViewReporting）按钮可执行；与 `GET /transfers/manager` 的放行条件 + `canApply \|\| canViewReporting` 同口径 |
  | approval | 恒为 true：`GET /approval/todos` 只按本人待办取数，任何有效成员都可访问 |

### scope

- 每个有数据范围概念的应用一项：org、job、staff、transfer、manager、talent、qualification、evaluation、survey360、talent-review、succession、idp。approval（本人待办）、self（本人档案）、settings（管理员能力）没有数据范围，不出现。
- 取值：以 `resolveModuleScopeInTransaction` / `resolveDataScope` 解析该应用“代表对象”的范围。代表对象是该应用 `entryObjects` 的第一个；manager 取任职记录对象（经理身份无效时为无）；没有可查看对象的应用直接为 `none`。
  - `all`：身份配置了“看全部”（`ModuleScope.all`）；`organizationIds` 为空数组。
  - `limited`：有任一数据范围项（组织集合、汇报关系、创建人）；`organizationIds` 是各项组织集合的并集去重，单个应用最多 200 个；另有**整包字节预算**（见下）。任何应用的组织集合被省略或截短都置 `truncated: true`（status 仍是 `limited`，不改成 `none`），前台不得把被截断的集合当作完整范围。按汇报关系或创建人取值的项没有组织，可能出现 `limited` 且 `organizationIds` 为空。
  - `none`：`EMPTY_SCOPE` 或 `hasDataPermission=false`（硬规则 1：默认为空，fail-closed）。
- 同一应用内不同对象的数据范围策略可能不同，摘要只代表该应用的主入口对象；对象级范围仍由各业务列表接口按对象裁剪。

- 整包预算：整个响应体（UTF-8 字节）≤ 32,768。先按“各应用 `organizationIds` 全空”算出 session / apps / adminMenus / scope 其余部分的字节数，剩余预算分给各应用的组织集合；轮流给每个应用补一个组织直到预算用完（小范围应用总是完整，大范围应用平分剩余预算）；同一组织 ID 出现在多个应用里重复计入预算。例：11 个应用都配到同一个 200 组织的管理单元，每个应用只返回约 50 个组织且 `truncated: true`。

### adminMenus

与现有 `GET /api/tenant/permission/admin-menus` 的 `items` 相同（同一函数 `visibleEnterpriseMenus`，输入为同一份有效管理员能力）。

## 与 /me/objects 的一致性约束

- 单一入口：`object-access.ts` 的 `createObjectAccess(...).resolve(objectCode)`。
  - 配置类对象（`EmploymentSettings`、`EmploymentCustomField`、`ContractSettings`、`ContractRenewalRule`）不走身份对象清单：任职类按 `admin.other_settings`，合同类按租户管理员或“合同配置”管理员记录（授权器 `configAllowed` 搬到此处，授权器改为引用它）。允许时 `/me/objects` 返回全部字段可查看、非系统字段可新增 / 编辑、不可删除、无按钮，与授权器对这些对象的 `object.view / create / update / delete / button` 结论一致。**这修正了旧 `/me/objects` 对租户管理员读任职 / 合同设置返回 403 的不一致。**
  - 其他对象按用户全部有效身份（含经理默认身份，`loadGrantedObjectPermissions` 带 `managerQuery`）的对象清单并集判定，只认身份登记了对象所属应用的权限（应用边界）；对象未登记视为无权限。
- 验收测试 `AC-PRM-ME-snapshot` 对六类演示身份（系统管理员、HR、经理、员工、审计管理员、无权限用户）逐对象比较：快照 `visible / entryObjects`、旧前端探测推出的结论、授权器 `object.view` 三者一致。
- 性能：一次请求内 `loadSubject` 不传 `objectCode`，一次取全部身份对象权限；配置类判定按种类只查一次库；不按对象逐个查库。

## 未覆盖项

- 不返回字段清单与按钮清单；对象级细节仍走 `GET /me/objects/:objectCode` 懒加载。
- 数据范围只给应用级摘要，不含人员集合、不逐对象；`limited` 的组织集合单应用最多 200 个，且受整包 32,768 字节预算约束，需要完整集合时由业务列表接口按范围裁剪。
- 范围解析按应用的代表对象各解析一次（同一权限应用下的不同前台应用仍各自解析），查询数较多；复用相同依赖留作后续优化。
- approval / self / settings 不给数据范围；self 的“本人数据”范围由 `/self-service/*` 自身保证。
- 应用 → 对象目录本 PR 只在 `packages/domain` 新增并由后端使用；前端 `demo-stubs/object-directory.ts` 暂不改，改为引用 domain 目录留给后续前端片；验收测试 `AC-PRM-ME-snapshot-unit` 守护两份目录顺序一致。
- 新增快照不改变 F-039 的授权口径；`manager` 可见性新增“canApply 或 canViewReporting”要求，比旧前端“`/transfers/manager` 返回 200 即可见”更严（经理身份有效但两个按钮都没有的用户不再显示管理者工作台）。
