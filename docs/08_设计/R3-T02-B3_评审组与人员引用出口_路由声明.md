# R3-T02 PR-B B3 评审组与人员引用出口：路由权限声明（F-039 格式，按现状契约）

> 依据：R3-T02 设计 §3.2、§5.1（人员引用的出口）、§8、§9；拆分方案第 4 节 B3 行；DEC-082、DEC-324②、DEC-331①、DEC-339②、DEC-067。
> 格式同 `R3-T02-B1a_评定底座与活动类型_路由声明.md`，已转写为 `apps/api/src/modules/evaluation/policy.ts`，必需项表
> `tests/acceptance/support/route-policy/required/evaluation.ts` 逐端点登记义务与证据锚点。
> 范围：**5 条**（评审组 × 列表 / 详情 / 新建 / 修改，成员候选 × 1），应用 `TEvaluation`。照原站（DEC-393，Q-M0-172）**没有删除入口**（第 1 轮的删除路由已移除，端点数 6 → 5）、**没有编码字段**、名称不要求唯一、允许零成员、被引用也能停用（不检查引用）。

## 1. 共用名称

| 简称 | 对象编码 | 范围锚点 |
|---|---|---|
| RG | `TEvaluation.ReviewGroup`（评审组，带嵌套成员） | 所属组织 `owner_org_id` 在范围内 ∪ 所属人 `owner_id`（创建人）；**无向下公开**（DEC-324②），读写同一谓词，范围外 404 |
| EI | `TenantBase.EmployeeInformation`（成员的人员引用、候选） | 人员范围（统一人员范围，同组织员工列表谓词，分页前生效） |

| 名称 | 说明 |
|---|---|
| 谓词 `ev.owned(ev_review_groups)` | `scopeSql(scope, { org: owner_org_id, creator: owner_id })`，分页之前 |
| 范围 `ev.reviewGroup.ownerOrg` | 新建：所选所属组织须存在且在范围内（范围外与不存在同一 404，DEC-082） |
| 守卫 `ev.ownerOrgInScope` | 改所属组织：新组织同样须在范围内；没改不重判 |
| 守卫 `ev.newPersonRefs` | 只校验**新增**的成员 ID（存在且在人员范围内，否则 404；无员工信息查看权 403 `NO_EMPLOYEE_ACCESS`）；新增成员须当前在职（DEC-416⑦，否则 400 `REVIEW_GROUP_MEMBER_NOT_EMPLOYED`）；原有范围外 ID 原样保留；删除成员不要求在范围内 |
| 披露 `memberRefs`（optional，非准入） | 成员 ID + 姓名 / 工号：范围内按字段权；范围外只有姓名、计入人数，人员详情仍 404；无员工信息对象查看权只给 ID（`person-refs.ts`） |
| 业务校验 | 组长 0 或 1 个（`REVIEW_GROUP_LEADER_TOO_MANY`，DEC-400② 改定：有成员时也可以不设组长，多于 1 个 400）、成员不重复（`REVIEW_GROUP_MEMBER_DUPLICATE`）、成员数 ≤ 200（系统保护，差异 D-071 🟡，超出 400 提示分批） |

## 2. 逐条声明

| 方法 | 路径 | 对象·操作·按钮 | 范围 | 其他 |
|---|---|---|---|---|
| GET | `/api/tenant/evaluation/candidates/review-members` | EI；view | list `ev.personScope` | 关键字只匹配可见的姓名 / 工号，都不可见而带关键字 403 `FILTER_FIELD_HIDDEN`；只列当前在职员工（DEC-416⑦） |
| GET | `/api/tenant/evaluation/review-groups` | RG；view | list `ev.owned(ev_review_groups)` | `ev.filterFieldVisible`；披露 `memberRefs` |
| GET | `/api/tenant/evaluation/review-groups/:id` | RG；view | point `ev.reviewGroup.byId`（404） | 披露 `memberRefs` |
| POST | `/api/tenant/evaluation/review-groups` | RG；create；`create@list` | `ev.reviewGroup.ownerOrg` | `ev.newPersonRefs` |
| PATCH | `/api/tenant/evaluation/review-groups/:id` | RG；update；`update@detail` | point `ev.reviewGroup.editable` | `ev.newPersonRefs`、`ev.ownerOrgInScope` |

写命令经 `runWrite`：权限、范围与员工信息访问（查看权 / 人员范围 / 字段）都在命令事务内由 `ledgerExit` 之前的 `before` 重新解析（首次、直接重放、失败后回查三条路径同一出口，DEC-388②）。

F-092（DEC-416⑦）：新建 / 编辑按 UUID 排序先取当前与提交成员的员工锁，再取评审组锁并校验 revision，与离职的“员工 → 评审组”顺序一致。离职记录到期在任职事务内自动退出所有组（含停用组），逐组推进 revision、写成员前后快照审计；未来直接离职同事务登记 `ev_sync_queue` 的 `review_group_exit`，到期消费者按 F-055 复核记录后移出。撤销离职不恢复成员，未到期记录被撤销后队列记 skipped。没有新增路由、对象授权编码或迁移。

F-092：删除钩子区分生效前取消、生效后撤销及删除重聘恢复离职；到期退出尚未消费时先完成退组和审计，已完成的退出不重复删除撤销后合法新增的成员。删除重聘使当前状态恢复离职时，再退出全部现有组。

新建组与编辑新增成员在写入前结清该员工旧周期的到期退出（含失败退避中的任务）。全部写路径共用 `lockReviewGroupState`：员工锁 → 队列锁 → 全部相关组（含编辑目标，按 UUID）→ 采样一次时钟。离职落地、删除钩子、新建、编辑和到期消费者均通过 `isDueReviewGroupLeave` 判定到期，通过 `reviewGroupEmployeeStatus` 读取同一业务日的当前状态；不能各自沿用请求开始的 `ctx.now`。HTTP 钩子复用请求上下文的实时钟函数，后台使用真实时钟，消费者支持显式注入。

编辑先在统一组锁内用结清前的 revision 校验客户端版本，再结清退出，并承接结清后的实际 revision 保存和审计。因此合法重聘者可在原组内退出并重新入组；旧表单仍返回 409，新增成员校验失败则退出、队列、版本及审计一起回滚。候选查询保持只读 SQL 当前在职过滤，不参与写路径取锁。

评审组路由单独成文件 `review-group-routes.ts`，不进通用注册器 `registerObject`：通用接口的权限事实里不会多出员工信息查看权。

## 3. 审计读取（不属于 F-039 路由声明）

评审组审计快照的成员条目只含员工 ID、冻结的当时姓名与组长标记。读取时（列表 changes / content、详情 before / after / snapshot）成员姓名按查看人**当前**的员工信息对象查看权与姓名字段权裁剪（`audit/visibility.ts` 的 `reviewGroupFields`，DEC-197）：没有对象查看权或姓名字段不可见时，成员只剩员工 ID 与组长标记。成员候选的排序只用查看人可见的字段（工号 → 姓名 → 员工 ID）。
