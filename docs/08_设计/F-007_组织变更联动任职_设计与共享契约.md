## 2. 迟到执行：窄口径 fail-closed（F-036 落地前）

设已落地的调动 L（直接未来调动，或审批通过后已落地待复查的调动）计划生效日 p，实际执行日 a（定时调度或 HR 重试当天的租户业务日）。

1. **是否迟到**只由 §3 C-1 的 `resolveLateExecution` 判定：a > p 才迟到；a = p 正常执行，不顺延、不进入本节。
2. **区间 [p, a)**：同一员工时间轴上位置在 L 之后（`(start_date, sort_order)` 大于 L 当前位置）且 `start_date < a` 的全部任职版本（组织调整、其他调动、离职 / 退休等，不分 kind），加上该员工尚未落地（不在时间轴上）、最新载荷生效日落在 `[p, a)` 的其他申请单（草稿 / 审批中 / 已批准 / 已驳回）。同日排在 L 之前的记录不随 L 移动，不算区间内。
3. **区间非空 → 拒绝执行**：不写任何任职数据，按 DEC-052 记一次生效尝试 `failed`，原因 `REBUILD_REQUIRED`（“生效失败：需重建，待 HR 处理”），detail 含 `plannedEffectiveDate`、`executionDate` 与 `blockers[{ id, kind, effectiveDate, materialized }]`；审计 `employment.activation.failed` 同事务写入，HR 待办（`/activation-todos`）按当前范围列出。HR 重试仍按同一规则判定；F-036 落地重建后由其接管这一分支。
4. **区间为空 → 简单迟到照常执行**（DEC-186 / 195）：L 改到 a，追加载荷版本、重建日期投影、审计 `employment.transfer.rescheduled{ originalEffectiveDate: p, effectiveDate: a }`，同日按原计划日排序（DEC-195①），人员状态按新位置前驱重算（F-022）。
5. **审批通过落地的申请单**（DEC-195②）此前不在时间轴上、没有依赖它的记录，不做区间判定：生效日改为批准当天后照常落地并按 R1 规则实时向后更新。
6. 多笔迟到：前一笔的区间含后一笔时前一笔失败、后一笔（区间为空）照常顺延；HR 重试前一笔时后一笔已离开区间，重试成功并按原计划日排在后一笔之前。自动协调归 F-036。
7. 区间内含离职时同样记 `REBUILD_REQUIRED`（不再按 DEC-252① 的“排在离职之后记失败”兜底）；离职的迟到执行同理由 #100 一并落实（DEC-278③）。

## 3. 共享契约：离职与迟到（#100 R2-T03 直接引用本节）

> 两边实现以此为准；共用函数“谁先合并谁实现，另一方引用”。本节替换 PR #83 评论区 v4 §C 的同名内容。

**C-1 迟到判定（DEC-272）**
- `resolveLateExecution({ plannedEffectiveDate, executionDate })` → `{ late, effectiveDate }`：`late ⇔ executionDate > plannedEffectiveDate`；`effectiveDate = late ? executionDate : plannedEffectiveDate`。**原定生效日当天执行属正常，不顺延。** 参数名两边统一为 `executionDate`。
- 调动：`plannedEffectiveDate` = 载荷生效日；迟到时生效日 = 实际执行日（DEC-186 / 195②）。
- 离职：`resolveLateLeave({ lastWorkDate, executionDate })`，原定生效日 = 最后工作日 + 1；迟到时**最后工作日 = 实际执行日 − 1、生效日 = 实际执行日**（DEC-263① 经 DEC-272 澄清）。例：最后工作日 5 日、生效 6 日——6 日执行不变；7 日执行则最后工作日 6 日、生效 7 日。
- 位置与调用点：`packages/domain/src/employment/late-execution.ts`（纯函数，无 IO，本 PR 实现）。#83 侧调用：`transitions.ts` 审批通过落地、`activation-checks.ts` 预检日期、`transfer/linkage/execute.ts` 联动日期、`late-transfer.ts` 顺延；SQL 投影 `greatest(effective_date, 执行日)`（`activation-store.ts` 排队、`forward-update.ts` 候选）与函数同义，AC-TRF-F017-dec272 断言等价。#100 侧：`postponeLateExit` 与审批通过时已逾期的离职调用 `resolveLateLeave`。
- 边界测试：调动三组（当天 / 晚 1 天 / 跨月，AC-TRF-F017-dec272）；离职三组由 domain 单元测试覆盖函数，#100 再覆盖入口。

**C-2 迟到执行的日期、位置与审计**
- 调动：生效日 = 实际执行日，不倒签；原计划日记审计 `employment.transfer.rescheduled`；多笔迟到改到同一天按原计划日排序（DEC-195①）；详情同时显示原计划日与实际生效日（DEC-195③）。
- 离职：按 C-1 顺延后，时间轴位置、编制区间与预释放（#100 §6，DEC-266①）、合同终止日、队列先后都用顺延后的日期；审批单上的原定日期不改（载荷只追加）。
- 审计动作名统一为 **`employment.leave.rescheduled`** 一个，覆盖迟到顺延与人工改期：meta `{ reason: 'late-execution' | 'reschedule', originalLastWorkDate, originalEffectiveDate, lastWorkDate, effectiveDate, executedAt(UTC) }`；查看规则与 `employment.transfer.rescheduled` 同一条（按记录所属员工 / 部门的 DEC-177 口径登记）。`employment.exit.rescheduled` 不再使用。
- 离职的迟到执行同样适用 §2 的窄口径 fail-closed（DEC-278③）：区间 [原定生效日, 实际执行日) 内另有该员工的任职版本或业务时记 `REBUILD_REQUIRED` 交 HR；区间为空的简单迟到按 C-1 顺延。

**C-3 同日排序（唯一规则）**
- 同一员工所有记录按 **最终生效日 → 原计划日（DEC-195①，无改期事件时等于生效日）→ 操作序号（DEC-108：申请取最近一次提交的状态事件、直接业务取保存事件；正在落地的直接业务视为最新操作）** 排序；这是 `employment/timeline.ts` `timelinePosition` 的既有实现，两边不另写规则。
- 离职 / 退休是终止业务：按上述顺序排在它之后的任职不能生效——保存 / 提交时即 409（`assertBusinessSequence`：终止任职后只能开新周期），已提交的申请在审批通过落地时 409、业务保持审批中，已落地待执行的调动按 DEC-052 / 252① 记生效失败交 HR；离职本身不变。
- 三个边界（AC-TRF-F017-same-day-order）：
  1. **两笔迟到**（原计划 10-05 与 10-08，都在 10-10 批准）：按原计划日 10-05 在前、10-08 在后，当日最终状态取 10-08 那笔；与如期执行一致。
  2. **正常离职 + 单笔迟到调动**（离职最后工作日 10-09 / 生效 10-10；原计划 10-05 的调动 10-10 稍后批准）：调动最终生效日 = 离职生效日，原计划日更早 → 排在离职之前生效（区间为空），离职仍是当日最后一条、其“变更前”读到该调动。
  3. **离职落地后才批准、最终生效日晚于离职生效日**（10-12 批准）：排在离职之后 → 批准 409，申请保持审批中，离职不变。
  4. **同原计划日**（调动计划 10-10、离职生效 10-10）：按操作序号——调动先提交则排在离职前生效；离职先保存则该调动申请在保存时即 409。
- 在 §2 的 fail-closed 口径下，区间 [p, a) 内含离职的**已落地**迟到调动不进入排序，直接记 `REBUILD_REQUIRED` 待 HR。

**C-4 F-022 状态传播**
- 独立 `status` 矩阵（只含 employeeStatus / entryStatus），端口 `propagateEmployeeStatus(source, from, to)`：候选 = 同周期（StaffID 相同）、位置在源之后、当前人员状态 = from 的生效版本（追加记录快照）与草稿 / 审批中 / 已批准 / 已驳回申请（追加载荷版本）；状态已不同（如 8 离职、已转正）或 StaffID 不同 → 不动；DEC-178 可见才改、不可见整单拒绝；审计 `employment.forward-update`。
- 触发：转正（试用 → 正式，29 PB-R7）；**完成入职（待入职 → 试用 / 正式）必须传播**（`completePendingEntry`），目标 entryStatus 保留自身值；实习转正同入职（DEC-234）。
- 不触发：取消 / 延期 / 改期恢复入职（`changePendingEntryStatus` 只改本记录 entryStatus）；离职 / 退休（终止状态不向后传播，离职版本永不作为来源）；迟到改期（`rederiveRepositionedStatus` 按新位置前驱重算，不是传播）。
- 覆盖（AC-TRF-42-F022-entry-completion）：{未来已落地版本, 草稿, 审批中, 已批准, 已驳回} × {有试用期 → 试用, 无试用期 → 正式} = 10；对照：状态已不同（离职 8）、StaffID 不同（重聘周期）不动；取消 / 延期 / 恢复不传播。

**C-5 DEC-263①②③、DEC-220、DEC-267、DEC-252① 的归属**
- ① 迟到离职日期 → C-1 / C-2。
- ② 已落地、生效日晚于最后工作日的未来直接调动 T：保存 / 提交离职时只提示（按操作人可见范围裁剪，看不到时只提示“存在未来生效的调动，需由有权限的人员处理”），不拦截、不自动删除，**离职照常生效**。**时间轴共存写定为“摘下 T 的时间轴行”**（与 #100 v1.3 §5.8 一致）：离职落地时删除 T 的 `employment_timeline` 行，T 的业务头、载荷版本、状态事件、生效尝试全部保留并记 `exit_effects(future_transfer_detached, detail.window)` 与审计 `employment.exit.future_transfer_warning`；离职记录区间开放到无穷，当前任职、占编、在岗统计、F-007 联动范围全部按时间轴，T 被摘下期间不计入、不作为任何向后更新候选；T 到期复查时发现不在时间轴上或前驱为离职 → 按 DEC-052 记 failed `EMPLOYEE_DEPARTED_BEFORE_TRANSFER`、HR 待办，不执行联动、不复查编制；撤销已生效离职时按 `detail.window` 把 T 的时间轴行挂回原位（R1-T11 守卫照常），HR 删除 T 照常。#83 不保留“离职止于 T 前一天”的旧写法。
- ③ 离职生效时：审批通过未生效、生效日晚于实际最后工作日的调动申请作废（DEC-220）；**草稿 / 已驳回的调动申请一并作废——按 DEC-263③ 原文不按日期过滤**（该员工全部草稿 / 已驳回调动申请）；审批中的按 DEC-267 开关；作废写审计 `employment.transfer.voided_by_exit` + outbox + 站内通知申请人（#100 命名与实现）。被作废申请保留历史，不进入任何重算、不是候选。
- DEC-267：离职生效时终止在途流程为租户级开关。默认不勾选 → 只终止最后工作日之后的在途任职流程与终止日期在最后工作日之后的在途合同流程；勾选 → 全部终止。**“最后工作日之后”按申请载荷的生效日（原定生效日）与顺延后的实际最后工作日 L′ 比较：`载荷生效日 > L′` 才终止，不得投影到执行日**（`greatest(载荷日, a) > L′` 会把全部较早申请都作废）。“最后工作日”= C-1 顺延后的实际最后工作日。未终止、继续流转的在途流程若生效时员工已离职 → 按 C-3 记生效失败。开关改动需管理员权限并写审计。DEC-222 其余（合同原地终止、撤销离职不自动恢复）不变。
- DEC-252①：入口拦截（员工存在已过计划日未执行的迟到调动时离职 / 退休入口 409）由 R2-T03 实现；`findOverdueTransfers` 只读判定两边合用，谁先合并谁实现；引擎兜底 = §2 的 `REBUILD_REQUIRED`（区间内含离职）与 C-3 的失败分支。
- 退休是否沿用 C-1 / C-2 由 R2-T04 定。

**C-6 DEC-269：值匹配向后更新与编制警告（F-036 实现，两边同一句）**
- 迟到执行 = 补录一条更早生效的记录：[计划日, 实际执行日) 内的组织调整重算，之后的独立业务（第二笔调动、离职等）复用 R1 值匹配向后更新（AC-FWD、`07` 附录 A5）：只替换等于变更前旧值的字段，已是其他值的不动，“是否部门负责人”不更新，职位与部门同时变化按原站规则②（DEC-120 记录级）。已知局限照原站：有意设回旧值会被误替换，写审计并测试固定；合法传播可覆盖人工值（DEC-255①）。
- **“编制不重算，超编只记警告。离职记录的部门被替换时，已在旧部门释放的编制也不重算、只记警告。”**（#100 §5.6 / §6 逐字一致）`exit_effects(establishment_pre_released)` 不追加修正行。
- 离职 / 退休记录作为候选：可被替换的只有 forward 矩阵字段；`lastWorkDate`、生效日、离职扩展字段、人员状态 8 不在匹配范围；离职记录仍在时间轴末尾；离职 / 退休永不作为传播来源。
- 本 PR 不实现这一条：F-036 落地前迟到执行遇区间内记录按 §2 交 HR。
