## 0. 先说结论：后端有通用删除，缺的是入口，以及“档案删除”自己的服务端判定

F-329 开发自报“后端没有直接删除任职记录的接口，未实现”。核对 main 后：

- 任职记录的 id 与业务 id 相同（`employment_records.id` = `employment_business_objects.id`），通用的 `DELETE /api/tenant/employment/businesses/:id`（`apps/api/src/modules/employment/routes.ts` 的 `registerBusinessTransitions`）对已生效的任职记录就是“删除任职”，R1-T11 已实现，守卫、重算、审计齐全（§2～§4）。
- **但通用删除的授权口径比编辑宽**：它先经 `transferBusinessContext`，调动记录可以因“目标部门例外”放行；而 `PATCH /records/:id`（档案里的“编辑任职”）没有这条例外。若档案页签直接调通用删除，同一员工、同一记录、同一权限，可能“不能编辑却能删除”（第 1 轮审查 P1-1）。因此档案页签的删除必须自带服务端判定，见 §1.2。
- 前端没有入口：`EmploymentRecords`（`apps/web/src/personnel/ProfileSections.tsx`）每条记录只有 `RecordEdit`；任职记录列表页说明 `apps/web/src/employment-records/annotations.ts` 还写着“删除任职……原站均未验证，不实现”。**前端目前没有任何入口调用通用 `DELETE /businesses/:id`**：调动草稿走专用的草稿删除接口（`apps/web/src/transfer/draft-server.ts` 的 `deleteServerDraft`，`draftPath(employeeId)/<id>`），待入职走 `DELETE /pending-entries/:id`（`apps/web/src/entries/DeleteBubble.tsx`）。
- 另有 U1～U11 共 11 项语义取舍，已由用户定（DEC-939，均按推荐项），见 §7 决策记录。

因此本任务的开发主体是**前端入口 + 档案删除的服务端判定（含新路由，U2-B 已定）+ 补齐少数口径 + 把现状锁成验收测试**；**不新增表、不新增迁移、不新增授权项**；新增路由带来的 F-039 义务见 §6。

### 1.2 设计（U1-A、U2-B 已定，DEC-939）

- **按钮沿用 `Employment.Delete`，不新增授权项**（U1-A，已定 DEC-939）。新增授权项编码要走授权版本流程（`STANDARD_GRANT_VERSION` / `STANDARD_GRANT_DIGEST`，DEC-439④），对“删除任职”一个动作没有额外收益。
- **档案页签的删除走专用路由 `DELETE /api/tenant/employment/records/:id`（U2-B，已定 DEC-939）**，与 `PATCH /records/:id` 对称，只服务档案页签的“删除任职”，通用 `DELETE /businesses/:id` **不改**（调动草稿、待入职、其他调用方继续用它或各自专用接口）。服务端判定（**“档案记录删除判定”**）如下，写成一个共用函数 `recordDeleteGuard`，**首次执行与同键重放都跑**（经命令台账的 guard 位，与 `recordEditGuard` 同构）：
  1. 记录存在且属于当前租户，否则 404（范围外与不存在同形，不暴露存在性）。
  2. 持有按钮 `Employment.Delete`（detail，delete），否则 403。
  3. **范围判定直接复用编辑实际使用的授权谓词**（`authorizeBusinessWrite` → `requireBusinessWriteScope`，底层是 `permission/module-access.ts` 的 `scopeSql` / `scopeAllowsInTransaction`），**不另写一份“双条件”**。该谓词按授权维度逐项判定、各维度取**并集**：组织维度看**记录部门**，汇报关系维度看**员工**，使用用户维度看**记录创建人**；只有未指定维度的默认口径才同时要求部门与人员。因此不能写成“记录部门 ∧ 员工当前任职”：例如 HR 只管甲部门，员工现已调到乙，要删的普通历史调动及其前驱都在甲，编辑的组织维度允许这次操作，档案删除也必须放行。**不加入 `transferTarget` 目标部门例外**，即不得宽于该员工、该记录的“编辑任职”（同一记录上 `PATCH /records/:id` 若会被拒，则本删除也必须拒，反之亦然）。范围为空（fail-closed）一律拒绝。（第 2 轮稿把它写成无条件双命中，已更正；标准调动等另有来源校验的情形由来源校验另判，不并入此处。）
  4. 前驱记录可见性沿用 DEC-177 / 178：恢复区间的前驱对操作人可见即可，不可见 404 `LINKED_RECORD_OUT_OF_SCOPE`（见 `assertRestoredPredecessor`）；这是“联动改写他人区间”的口径，不是写入口径，两者分开判。
  5. 通过后才进入通用删除内核（`transitionEmployment` 的 delete 分支，§3 同事务重算）；revision 不一致 409 `REVISION_CONFLICT`。
- **`recordDeleteGuard` 只管“当前授权”，不含任何业务计数**：命令台账先跑守卫、后查回执（`apps/api/src/commands.ts` 的 `ledgerExit`：`guard.before` → `findReplay` → `guard.replayed`），守卫里若放业务判断，已成功提交的命令在响应丢失后用原键重提，会在查台账前被业务判断拒绝，拿不到原成功回执。凡依赖“当前有几条记录”的判定（U7-A 的“仅剩一条”，已定 DEC-939），**只放在首次执行的业务体内、取得员工行锁与业务头锁之后判断**（`record-store.ts` 的 `lockEmploymentEmployee` / `lockEmploymentBusiness`）；锁前计数也挡不住两个不同命令串行后把最后一条删空。同键重放命中台账时直接返回原结果，不再判。
- **范围外不得借删除泄露存在性或字段**：拒绝详情经 `discloseDeletionBlock` 与响应裁剪后才返回（§2.3 明确披露边界）。
- **U2-A（不新增路由，前端调通用 `DELETE /businesses/:id`）已被否决（DEC-939 选 U2-B）**：它要给通用删除增加“来源 = 档案”的显式判定、对调动记录不加目标部门例外，会改变通用路径契约、影响调动草稿 / 待入职等其他调用方，范围更大。本任务不改通用路径。
- 撤销身份不连带删除范围（硬规则 6）：本任务不涉及授权写入。

## 2. 可删范围与拒绝口径（U4-A、U10-A 已定，DEC-939）

### 2.1 状态可删性

`transitions.ts` 的 `transitionPermitted`：动作 `delete` 允许的状态为 `draft / rejected / disapproved / voided / approved / effective`；其余（如审批中 `in_review`）返回 409 `CONFLICT`「当前状态不允许此动作」。

其中**“删除任职记录”只指 `effective`（已生效、已落时间轴）的记录**；草稿 / 驳回 / 作废 / 已批未生效是“删除申请”，由调动与入职各自入口处理，不属于本任务。

### 2.2 按业务类型

| 业务类型 | 删除行为 | 依据 |
|---|---|---|
| 调动 `transfer`、组织调整联动生成的记录、转岗等同类 | 走删除内核：摘下时间轴行、前驱区间恢复到后一条的生效日。**组织调整生成的记录允许在档案删除（U10-A，已定 DEC-939）**，沿用现有守卫 | `removeEmploymentTimeline` |
| 离职 `leave` | 通用 DELETE **路由到“撤销离职”**（`routesToCancel` → `runExitCancel`），**必填原因**，缺原因 400 `EXIT_CANCEL_REASON_REQUIRED` | R2-T03 §6B；`AC-EXIT-cancel-delete-reason` |
| 退休 `retirement` | 同样路由到撤销（`runExitCancel`），但**不接收原因**：请求体只认 `{confirmed?}`，带 `reason` 返回 400 `VALIDATION_FAILED`（DEC-714）；权限链先于校验 | `exit-routes.ts parseRetirementCancel`；`AC-RT-F351-cancel-no-reason` |
| 入职 `hire`、再入职、退休返聘、实习转正等“开新周期”类 | 其后**存在任何记录**（`next` 存在）即 409 `EMPLOYMENT_FUTURE_VERSION_EXISTS`「存在后续任职记录，不能删除历史记录」 | `timeline.ts removeEmploymentTimeline`：`next && (opensCycle \|\| next.staffId !== point.staffId)` |
| 普通调动等非开新周期记录 | 其后一条与本条**同一周期（同 `staffId`）**时可删；其后一条属于**另一周期**（`staffId` 不同）也拒绝，同样 409 `EMPLOYMENT_FUTURE_VERSION_EXISTS` | 同上 |
| 被离职摘下的未来调动（不在时间轴上） | 记录与墓碑照常处理，没有区间可恢复，也没有生效中的下游可通知 | `deleteEmploymentBusiness` 的 `isDetachedRecord` 分支 |

> 第 1 轮把“退休需要原因”写反了：**离职撤销必填原因，退休撤销不填原因（DEC-714）**。普通任职删除选填原因（U3-B，已定 DEC-939，§4.4）。

### 2.3 拒绝清单、错误信封与前端展示边界

下表全部来自现有实现，本任务**不改变其语义**，错误形状以真实响应信封为准（`{ error: { code, message, details: { reason, … } } }`，参见 `AC-TRF-07-10-36-revoke-delete` 的 `errorOf`）。**`REVISION_CONFLICT` 与业务拒绝分开**：前者是“数据已变更，刷新后显式重提”，后者是“规则不允许”，前端不得合并成同一条提示。

| 修订号不一致 | 409 `REVISION_CONFLICT`，`details.expected` / `actual`；**这是并发冲突，不是业务拒绝** | `context.ts assertRevision` |
| 状态不允许 | 409 `CONFLICT`「当前状态不允许此动作」 | `transitionPermitted` |

**前端展示边界**：现有前端 `ApiError`（`apps/web/src/foundation/client.ts`）只保留 `code`、`serverMessage`、`fieldErrors`，**丢弃结构化 `details`**（`deleteServerDraft` 因此自己读真实信封）。所以“按原因码给不同提示、在途申请渲染单号列表”需要在 S1 里新增**局部读取信封**的小函数，不改通用 `ApiError`（改它会影响全站，须另议）。披露边界：

- 在途申请：渲染服务端给出的 `applications[]`，不自行补全，`hiddenCount` 只显示“另有 N 个无权查看的申请”；
- 联动变更：页面只显示服务端按下方“有权 / 无权”投影后给出的文字，**不在前端自行裁剪**（前端裁剪挡不住原始 HTTP 信封）；`orgId`、角色码仅在有权投影里才会出现，页面不显示、不落到前端状态；
- 循环汇报：只显示通用提示，不显示路径与姓名（除非服务端已换成披露版）；
- 其他原因码：用 `message`（`rejectionMessage` 对 409 业务冲突本来就取服务端文案），不另写一份规则。

**联动错误的两种投影（档案新路由，服务端裁剪；U2-B 的一部分）**：新路由在 `recordDeleteGuard` 之外增加一层错误投影，对 `EMPLOYMENT_LINKED_CHANGES_EXIST` 按操作人当前权限分两种，`message` 与 `details` **一并**裁剪（探针把同一信息写进两处，只改一处等于没改）：

| 投影 | 适用 | 返回内容 |
|---|---|---|
| 有权 | **本次拒绝所含的每一种关系**（负责人、店长、HRBP、直线 / 虚线经理等）都已逐项验过查看权、且全部可见（按其对相应对象与字段的可见性判定，口径在 S2 对照字段可见性实现并实测落定） | 与现状一致：`message` / `label` 含组织名与角色，`details` 含 `orgId`、`roles`、`count` |
| 无权 / 无法证明全部可见 | 其余情形，**含混合权限**（同一次拒绝里只有部分关系可见） | 不含组织名、任何角色字样（负责人 / 店长 / HRBP 等）、`orgId`、`roles`；只保留 `reason=EMPLOYMENT_LINKED_CHANGES_EXIST`、不带关系名的通用提示（如“该记录联动改写的结果仍在，请先处理后再删除”）和可披露的件数 |

**混合权限边界**：同一次拒绝可同时含多个角色与下属关系，探针把每种关系各写进 `label` / `role`，顶层 `message` 又由全部标签拼成（`transfer/linkage/deletion-probes.ts`、`employment/deletion-guards.ts`）。因此规则是**只披露已验过权的关系；不能证明全部关系都可见时，整体用通用提示**，不做“可见的照给、不可见的删掉”的逐项拼接。例如 HR 能看负责人和店长、看不到 HRBP，删除一笔带 HRBP 转交的调动：响应与页面都不得出现 HRBP 关系，也不得出现由该关系带出的组织名。具体授权项到各关系的映射不在本设计拍板，S2 落定。

通用 `DELETE /businesses/:id` 的行为**不改**。（待确认：“有权”的判定口径为本设计暂定，S2 前须确认。）

> 原站的“删除历史周期第一条且区间内有薪酬数据则禁止”（`07` A11）：复刻按 §2.2 对开新周期记录已**更严**（后面有任何记录都不能删），所以只有“最后一个周期的唯一记录”才会走到薪酬判断，见 U5。

### 2.4 前端“可删”的显示条件（U4-A、U9-A 已定，DEC-939）

列表行 `GET /employees/:id/records`（`read-model.ts` 的 `recordsQuery`）返回的行**会按操作人的字段权限裁剪**（`context.ts` 的 `trimEmploymentResponse`）。因此入口条件必须**以“裁剪后的实际列表行”为准**，不能假设字段一定在：

1. 有 `Employment.Delete` 按钮权限（按钮权限来自权限接口，不来自行内字段）；
2. 行里有可用的稳定 `id` 与 `revision`（任一缺失 → 不显示入口，不猜）；
3. 行里的 `kind`（业务类型）**未被裁剪且是已知类型**：离职 / 退休类按 U4-A 处理（不显示），其余类型才显示；**`kind` 被裁剪或不认识时不显示入口**（与 `recordEditable` 对 `kind` 的做法一致：无法确定走哪条规则，就不放入口），并在记录旁不做任何额外暗示；
4. `status` 若存在必须是 `effective`；字段被裁剪缺失时，该接口只返回已落时间轴的记录，不据此拒显；
5. 不在前端预判业务守卫（在途申请 / 联动 / 周期 / 暂停 / 编制）：一律提交后按服务端原因展示，规则只有一份。

受限角色（只读类字段权限、无 `kind` 字段权限、无按钮权限）的行为由 AC-EMP-F361-01、AC-EMP-F361-05 覆盖。

### 4.3 删除后的展示

- **任职记录页签 / 列表页**：读模型以 `employment_timeline` 为主表，被删记录自然不再出现；不显示占位行（U8-A）。
- **数据变更日志**：审计查询按 `employment.record.delete` 能查到完整删除前快照与操作人；原站“对象操作日志不记录删除”是原站缺陷，复刻**不照搬**，保留审计（AGENTS §5）。
- **审计详情的可见字段**按查看人的权限裁剪（`audit/routes.ts` 的 `fieldsOf` / `visibleValue`）；删除类日志详情里 `before` 即快照（`snapshot`），`after` 恒为 `null`。

### 4.4 删除原因的完整链路（U3-B 已定，DEC-939）

第 1 轮只说“原因随审计一起落”，缺链路。核对现有代码后的约束与设计：

| 环节 | 结论 |
|---|---|
| **输入框在哪** | 档案页签“删除任职”的确认层（`Popconfirm` 换成小弹层 `Modal`，含“删除原因（选填，最多 200 字）”输入框）。原因只属于这一个入口，列表页不做入口（U6-A 已定） |
| **请求体** | 新路由 `DELETE /records/:id` 接收可选体 `{ reason?: string }`（≤200 字，首尾空白去除，去除后为空视为未填）；通用 `DELETE /businesses/:id` 仍为空体，**不改** |
| **归一化与指纹** | 命令指纹 = 方法 + 路径 + revision + **归一化后的 input**（`context.ts` 的 `runCommand` 指纹含 `input`）。因此“同键同原因”幂等重放返回原结果；**同键不同原因 → 命令冲突**（409 幂等冲突），不静默采用第一次的原因。未填与空白归一化后同为“无原因”，指纹相同 |
| **审计存放位置** | **不能**放 `auditEmployment` 的 `meta`：`meta` 只写入 outbox，**不进 `recordAudit`**，数据变更日志读不到。设计：删除审计 `employment.record.delete` 的 `before` 快照结构**不变**，原因作为 `after` 以外的**独立字段**随审计行记录——具体做法在 S2 实现时二选一并写进 PR：(a) 扩展 `recordAudit` 入参增加可选 `reason`（共享审计入口，需契约 PR 先单独合并）；(b) 把原因并入 `before` 快照的一个固定键 `deleteReason`。本设计**推荐 (b)**（不动共享审计入口），`after` 仍为 `null`（AC-EMP-F361-08 保持） |
| **读取路径** | 数据变更日志详情 `GET /audit/data-changes/:id`：`before` / `snapshot` 经 `fieldsOf` 裁剪后返回；`deleteReason` 需登记为“删除原因”可见字段，**按查看人对任职对象的字段权限裁剪**，无权者看不到该键，但其余快照照常显示 |
| **与 S1 / S2 的依赖** | 按 U2-B，`DELETE /records/:id` 由 S2 提供，**S1 依赖 S2 的路由先合入**（否则 HR 会看到一个点了确认却请求不存在路由的按钮）。S2 先验 HTTP、命令指纹、审计投影（AC-09）；S1 在路由合入后验“页面提交 → 审计读回”（AC-13） |

U3-A（不要原因）与 U3-C（必填原因）均已被否决（DEC-939 选 U3-B：选填，≤200 字）。

### U7 删除员工最后一条任职记录，对四个入口分别怎么处理（已定：A，DEC-939）

第 1 轮把 U7 写成“只剩一条则拒绝并新增原因码”，但没有区分入口。核对后：删除唯一记录的底层行为是——`removeEmploymentTimeline` 无前驱返回 `null`，只摘行，员工时间轴变空，人员主档保留（DEC-540）。**不同入口现状不同**：

| 入口 | 现状（已核 / 假设） | 若加“唯一记录拒绝”守卫会变什么 |
|---|---|---|
| ① 档案页签删除（本任务，新路由） | 已入职的唯一记录通过通用内核可删，删后员工无任职 | 新路由自己加判定，不影响他人 |
| ② 通用 `DELETE /businesses/:id`（含对已入职记录） | 已入职记录删除返回 200（`AC-EN-F199` 的“已入职业务通用删除成功”用例） | **改变通用路径契约**，F-199 既有用例会受影响 |
| ③ 专用 `DELETE /pending-entries/:id` | 待入职的唯一记录本来就是可以删空的：删后时间轴为空、人员主档保留（`AC-EN-BE2a` “删除后该员工没有任何任职记录”）；已入职 → 409 `NOT_PENDING_ENTRY` | **会破坏待入职删除的既有语义**，不可加 |
| ④ Offer 失效清理 `deleteLinkedEntry` | 与③共用 `deletePendingEntry → transitionEmployment` 内核，调用方期待删空 | 同③，不可加 |

因此“在共享内核里加守卫”会同时影响③④，**不推荐**。

| 选项 | 说明 |
|---|---|
| **A（已定，DEC-939）** 仅在新路由 `DELETE /records/:id` 的**首次执行业务内、取得员工锁与业务头锁之后**加“员工仅剩一条已生效时间轴记录 → 409 `EMPLOYMENT_SOLE_RECORD`（暂名）”，**不放进 `recordDeleteGuard`**；通用路径与专用删除、Offer 清理**契约不变** | 只改本任务新增的契约，不影响③④与 F-199；同键重放仍先走守卫再回原成功回执（§1.2） |
| B 不加守卫，保持现状，只用测试锁定“删后员工无任职、人员主档保留” | 零新原因码；但 HR 可在档案页签把员工删成“无任职” |
| C 在共享内核加守卫 | 会改③④与通用路径契约，须单独契约变更，不推荐 |

**已定口径（U7-A，DEC-939）**：“仅剩一条”口径是“时间轴行数 = 1”，不含离职摘下的未来调动；判定**只在首次执行业务内、取得员工锁与业务头锁后**做（§1.2），**不放进 `recordDeleteGuard`**：否则两条删到一条后，响应丢失、原键重提会在查台账前被 409 拒绝，拿不到已提交的成功回执；锁前计数也挡不住两个不同命令串行执行把最后一条删空。

**被拒之后 HR 怎么纠错（已定，随 U7-A，DEC-939）**：最后一条**正式主任职**记录在档案页签被拒后，本设计**没有删除办理路径**：已办理入职者转到专用待入职入口会收到 409 `NOT_PENDING_ENTRY`；通用 `DELETE /businesses/:id` 技术上仍能删，但它是通用入口，不作为 HR 的纠错办法。已定的纠错方式：该记录录错的字段用“编辑任职”改正；若整条入职本身录错，走离职 / 入职撤销类流程或另立任务，**本任务不新增**。U7-B（不加守卫）未选；HR 若需要自己删空，须另立“撤销入职”任务。

例子：赵六刚入职，只有 1 条入职记录。A 下 HR 在档案页签点删会被拒并提示；待入职阶段（还没办入职）的删除、Offer 失效时自动清理仍照常能删空。

### 9.1 验收编号与“旧实现反证”

“旧实现”指 main `eba240ca3`。后端行为已存在的 AC，反证用**反向自证**：临时去掉对应守卫 / 钩子，确认该 AC 变红，再还原（不得用手写夹具形状冒充后端回执；错误断言一律读真实错误信封 `{ error: { code, message, details } }`）。

**拒绝类用例的统一失败断言**（AC-03、07、08、09、10、11 适用）分**两种基线**，按用例场景选用，不得混用：

- **基线 1：首次就被拒**（该命令此前从未成功）：断言**没有任何成功副作用**，即无成功删除的业务审计（无 `employment.record.delete` 等）、无墓碑 `employment_record_tombstones`、无命令台账成功条目，时间轴与记录不变；
- **基线 2：已有成功记录后再被拒**（AC-09 同键换原因、AC-11 撤权后的同键重放，以及 AC-10(a) 之后的重提等）：此前的成功已经写了审计、墓碑与台账，所以**不能**断言“不存在”；改为与**重提前取的快照**比较（审计行、墓碑、台账、时间轴与记录），断言**没有新增、没有删除、没有改写**（既有撤权重放测试 `AC-PRM-F195-197-replay-guard` 即比较重提前后快照）。

两种基线下，**进入命令执行器后失败的业务拒绝仍留平台失败记录**（`outcome=business_failed`，含 `errorCode` 与操作人，见 `apps/api/src/commands.ts` 与 `commands.test.ts` 的现有断言）：“没有成功审计”不等于“没有任何记录”，两类分开断言；执行器之前的授权拒绝（403 / 404）是否留失败记录，由 S2 对照真实分类锁定，不预设。
