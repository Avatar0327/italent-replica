## 0. 先说结论：后端有通用删除，缺的是入口，以及“档案删除”自己的服务端判定

F-329 开发自报“后端没有直接删除任职记录的接口，未实现”。核对 main 后：

- 任职记录的 id 与业务 id 相同（`employment_records.id` = `employment_business_objects.id`），通用的 `DELETE /api/tenant/employment/businesses/:id`（`apps/api/src/modules/employment/routes.ts` 的 `registerBusinessTransitions`）对已生效的任职记录就是“删除任职”，R1-T11 已实现，守卫、重算、审计齐全（§2～§4）。
- **但通用删除的授权口径比编辑宽**：它先经 `transferBusinessContext`，调动记录可以因“目标部门例外”放行；而 `PATCH /records/:id`（档案里的“编辑任职”）没有这条例外。若档案页签直接调通用删除，同一员工、同一记录、同一权限，可能“不能编辑却能删除”（第 1 轮审查 P1-1）。因此档案页签的删除必须自带服务端判定，见 §1.2。
- 前端没有入口：`EmploymentRecords`（`apps/web/src/personnel/ProfileSections.tsx`）每条记录只有 `RecordEdit`；任职记录列表页说明 `apps/web/src/employment-records/annotations.ts` 还写着“删除任职……原站均未验证，不实现”。**前端目前没有任何入口调用通用 `DELETE /businesses/:id`**：调动草稿走专用的草稿删除接口（`apps/web/src/transfer/draft-server.ts` 的 `deleteServerDraft`，`draftPath(employeeId)/<id>`），待入职走 `DELETE /pending-entries/:id`（`apps/web/src/entries/DeleteBubble.tsx`）。
- 另有几处语义要拍板，见 §7 待决清单 U1～U11。

因此本任务的开发主体是**前端入口 + 档案删除的服务端判定（含新路由，推荐 U2-B）+ 补齐少数口径 + 把现状锁成验收测试**；**不新增表、不新增迁移、不新增授权项**；新增路由带来的 F-039 义务见 §6。

### 1.2 设计（暂定，待确认 U1、U2）

- **按钮沿用 `Employment.Delete`，不新增授权项**（U1-A）。新增授权项编码要走授权版本流程（`STANDARD_GRANT_VERSION` / `STANDARD_GRANT_DIGEST`，DEC-439④），对“删除任职”一个动作没有额外收益。
- **档案页签的删除走专用路由 `DELETE /api/tenant/employment/records/:id`（U2-B，暂定）**，与 `PATCH /records/:id` 对称，只服务档案页签的“删除任职”，通用 `DELETE /businesses/:id` **不改**（调动草稿、待入职、其他调用方继续用它或各自专用接口）。服务端判定（**“档案记录删除判定”**）如下，写成一个共用函数 `recordDeleteGuard`，**首次执行与同键重放都跑**（经命令台账的 guard 位，与 `recordEditGuard` 同构）：
  1. 记录存在且属于当前租户，否则 404（范围外与不存在同形，不暴露存在性）。
  2. 持有按钮 `Employment.Delete`（detail，delete），否则 403。
  3. `authorizeBusinessWrite` 的写口径：**记录部门 ∧ 员工当前任职都在 `BUSINESS_WRITE` 范围内**；**不加入 `transferTarget` 目标部门例外**，即不得宽于该员工、该记录的“编辑任职”（同一记录上 `PATCH /records/:id` 若会被拒，则本删除也必须拒）。范围为空（fail-closed）一律拒绝。
  4. 前驱记录可见性沿用 DEC-177 / 178：恢复区间的前驱对操作人可见即可，不可见 404 `LINKED_RECORD_OUT_OF_SCOPE`（见 `assertRestoredPredecessor`）；这是“联动改写他人区间”的口径，不是写入口径，两者分开判。
  5. 通过后才进入通用删除内核（`transitionEmployment` 的 delete 分支，§3 同事务重算）；revision 不一致 409 `REVISION_CONFLICT`。
- **范围外不得借删除泄露存在性或字段**：拒绝详情经 `discloseDeletionBlock` 与响应裁剪后才返回（§2.3 明确披露边界）。
- 若用户选 **U2-A（不新增路由）**：前端调通用 `DELETE /businesses/:id`，则 P1-1 的差异必须在通用路径上消除，做法是给通用删除增加“来源 = 档案”的显式判定、对调动记录**不加**目标部门例外；这会改变通用路径的契约，影响调动草稿 / 待入职等其他调用方，范围更大，故不推荐。
- 撤销身份不连带删除范围（硬规则 6）：本任务不涉及授权写入。

## 2. 可删范围与拒绝口径（待确认）

### 2.1 状态可删性

`transitions.ts` 的 `transitionPermitted`：动作 `delete` 允许的状态为 `draft / rejected / disapproved / voided / approved / effective`；其余（如审批中 `in_review`）返回 409 `CONFLICT`「当前状态不允许此动作」。

其中**“删除任职记录”只指 `effective`（已生效、已落时间轴）的记录**；草稿 / 驳回 / 作废 / 已批未生效是“删除申请”，由调动与入职各自入口处理，不属于本任务。

### 2.2 按业务类型

| 业务类型 | 删除行为 | 依据 |
|---|---|---|
| 调动 `transfer`、组织调整联动生成的记录、转岗等同类 | 走删除内核：摘下时间轴行、前驱区间恢复到后一条的生效日。**组织调整生成的记录是否允许在档案删除**见 U10 | `removeEmploymentTimeline` |
| 离职 `leave` | 通用 DELETE **路由到“撤销离职”**（`routesToCancel` → `runExitCancel`），**必填原因**，缺原因 400 `EXIT_CANCEL_REASON_REQUIRED` | R2-T03 §6B；`AC-EXIT-cancel-delete-reason` |
| 退休 `retirement` | 同样路由到撤销（`runExitCancel`），但**不接收原因**：请求体只认 `{confirmed?}`，带 `reason` 返回 400 `VALIDATION_FAILED`（DEC-714）；权限链先于校验 | `exit-routes.ts parseRetirementCancel`；`AC-RT-F351-cancel-no-reason` |
| 入职 `hire`、再入职、退休返聘、实习转正等“开新周期”类 | 其后**存在任何记录**（`next` 存在）即 409 `EMPLOYMENT_FUTURE_VERSION_EXISTS`「存在后续任职记录，不能删除历史记录」 | `timeline.ts removeEmploymentTimeline`：`next && (opensCycle \|\| next.staffId !== point.staffId)` |
| 普通调动等非开新周期记录 | 其后一条与本条**同一周期（同 `staffId`）**时可删；其后一条属于**另一周期**（`staffId` 不同）也拒绝，同样 409 `EMPLOYMENT_FUTURE_VERSION_EXISTS` | 同上 |
| 被离职摘下的未来调动（不在时间轴上） | 记录与墓碑照常处理，没有区间可恢复，也没有生效中的下游可通知 | `deleteEmploymentBusiness` 的 `isDetachedRecord` 分支 |

> 第 1 轮把“退休需要原因”写反了：**离职撤销必填原因，退休撤销不填原因（DEC-714）**。普通任职删除是否填原因见 U3。

### 2.3 拒绝清单、错误信封与前端展示边界

下表全部来自现有实现，本任务**不改变其语义**，错误形状以真实响应信封为准（`{ error: { code, message, details: { reason, … } } }`，参见 `AC-TRF-07-10-36-revoke-delete` 的 `errorOf`）。**`REVISION_CONFLICT` 与业务拒绝分开**：前者是“数据已变更，刷新后显式重提”，后者是“规则不允许”，前端不得合并成同一条提示。

| 场景 | 状态码 / `code` / `details.reason` | 来源 |
|---|---|---|
| 其后有审批中或已批未生效、生效日不早于被删记录的申请（DEC-126） | 409 `CONFLICT` / `EMPLOYMENT_PENDING_APPLICATION_EXISTS`；`details.applications[]` 列出 `id`、`effectiveDate`、`status`（按操作人范围与字段权限披露，范围外只给 `hiddenCount`） | `deletion-guards.ts assertNoPendingApplication` / `PendingApplicationError` / `disclosePendingApplications` |
| 联动改写结果仍在（合同、下属经理、组织角色、兼职；DEC-012 / 172） | 409 `CONFLICT` / `EMPLOYMENT_LINKED_CHANGES_EXIST`；**详情不只是件数**：组织联动会带 `label`（含组织名与负责人 / 店长角色）、`orgId`、`roles`，直线经理带 `count`，兼职 / 合同探针各带自己的标签 | `assertNoLinkedChanges`；探针 `transfer/linkage/deletion-probes.ts`、`part-time/install.ts`、`organizationLinkage`（组织联动取自 `employment.transfer.linked` 事件） |
| 恢复区间的前驱对操作人不可见（DEC-177 / 178） | 404 `LINKED_RECORD_OUT_OF_SCOPE` | `assertRestoredPredecessor` |
| 恢复区间的部门已停用 | 409 `EMPLOYMENT_DEPARTMENT_DISABLED`（离职撤销路径统一用此码；普通删除路径的引用复核另见下行 400） | `validateRestoredReferences` |
| 恢复区间引用复核失败（引用失效等） | 400 `VALIDATION_FAILED` + 字段错误 | `validateRestoredReferences` |
| 删除后前驱直线经理会成环 | 400 `VALIDATION_FAILED` / `REPORTING_CYCLE`，`details.fields.directManagerId`；默认**不暴露路径与姓名**，仅当确认路径上的人都可见且经理字段可看才换成披露版 | `ReportingCycleDeletionError` |
| 组织调整正在执行（R2-T08 §7.6）：被删记录或恢复的前驱涉及暂停中的组织 | 409 `CONFLICT` / `ORG_ADJUSTMENT_EXECUTING`，文案「相关组织正在执行组织调整，请执行完成后再操作」 | `transitions.ts assertDeletionNotPaused`、`org-adjustment/pause.ts`；离职 / 退休不判 |
| 严格编制：恢复区间会使前驱部门超编 | 409 `CONFLICT` / `ESTABLISHMENT_EXCEEDED`，文案「已超出设定编制，不可继续操作」 | `assertRestoredEstablishment` → `assertEstablishmentCapacity`（`activation-checks.ts`） |
| 其后存在需保留的记录（见 §2.2 两行） | 409 `EMPLOYMENT_FUTURE_VERSION_EXISTS`（错误类 `EmploymentError`） | `timeline.ts`、`errors.ts` |
| 普通转正（`kind='regularization'`）已把“正式”传播到后续版本（DEC-231） | 409 `CONFLICT` / `REGULARIZATION_STATUS_PROPAGATED`；实习转正是另一个 kind，不经此守卫 | `employee-status.ts assertRegularizationNotPropagated` |
| 修订号不一致 | 409 `REVISION_CONFLICT`，`details.expected` / `actual`；**这是并发冲突，不是业务拒绝** | `context.ts assertRevision` |
| 状态不允许 | 409 `CONFLICT`「当前状态不允许此动作」 | `transitionPermitted` |

**前端展示边界**：现有前端 `ApiError`（`apps/web/src/foundation/client.ts`）只保留 `code`、`serverMessage`、`fieldErrors`，**丢弃结构化 `details`**（`deleteServerDraft` 因此自己读真实信封）。所以“按原因码给不同提示、在途申请渲染单号列表”需要在 S1 里新增**局部读取信封**的小函数，不改通用 `ApiError`（改它会影响全站，须另议）。披露边界：

- 在途申请：渲染服务端给出的 `applications[]`，不自行补全，`hiddenCount` 只显示“另有 N 个无权查看的申请”；
- 联动变更：**只显示服务端给出的 `label`**；`orgId`、角色码不进页面（页面不需要，也不额外落到前端状态里）；
- 循环汇报：只显示通用提示，不显示路径与姓名（除非服务端已换成披露版）；
- 其他原因码：用 `message`（`rejectionMessage` 对 409 业务冲突本来就取服务端文案），不另写一份规则。

> 原站的“删除历史周期第一条且区间内有薪酬数据则禁止”（`07` A11）：复刻按 §2.2 对开新周期记录已**更严**（后面有任何记录都不能删），所以只有“最后一个周期的唯一记录”才会走到薪酬判断，见 U5。

### 2.4 前端“可删”的显示条件（暂定）

列表行 `GET /employees/:id/records`（`read-model.ts` 的 `recordsQuery`）返回的行**会按操作人的字段权限裁剪**（`context.ts` 的 `trimEmploymentResponse`）。因此入口条件必须**以“裁剪后的实际列表行”为准**，不能假设字段一定在：

1. 有 `Employment.Delete` 按钮权限（按钮权限来自权限接口，不来自行内字段）；
2. 行里有可用的稳定 `id` 与 `revision`（任一缺失 → 不显示入口，不猜）；
3. 行里的 `kind`（业务类型）**未被裁剪且是已知类型**：离职 / 退休类按 U4 处理，其余类型才显示；**`kind` 被裁剪或不认识时不显示入口**（与 `recordEditable` 对 `kind` 的做法一致：无法确定走哪条规则，就不放入口），并在记录旁不做任何额外暗示；
4. `status` 若存在必须是 `effective`；字段被裁剪缺失时，该接口只返回已落时间轴的记录，不据此拒显；
5. 不在前端预判业务守卫（在途申请 / 联动 / 周期 / 暂停 / 编制）：一律提交后按服务端原因展示，规则只有一份。

受限角色（只读类字段权限、无 `kind` 字段权限、无按钮权限）的行为由 AC-EMP-F361-01、AC-EMP-F361-05 覆盖。

## 3. 删除后的重算（同一事务）

全部在 `transitionEmployment` 的 delete 分支内、同一 `runWrite` 事务里完成；员工行锁由任职命令统一持有，并发写同一员工的任职被串行化。新路由 `DELETE /records/:id`（U2-B）只在入口多一层 `recordDeleteGuard`，重算内核不变。

| 重算对象 | 做法 | 位置 |
|---|---|---|
| 版本链 | **软删除**：写墓碑 `employment_record_tombstones`，追加状态事件 `deleted`（`appendEmploymentState`），**不改写、不删除** `employment_records` / `employment_payload_versions` / `employment_state_events`；不新增“变更前”列，前驱仍从版本链上一条读取（硬规则 2、3） | `deleteEmploymentBusiness` |
| 时间轴与有效区间 | 删除 `employment_timeline` 行；前一条的 `valid_during` 延伸到后一条的生效日（无后一条则开放）；后续记录与同日顺序号**不重算**（W-013、W-424）；当前任职由 `valid_during @> 查询日` 读时计算（`isCurrent`），不存在需要回写的“当前任职快照”列 | `timeline.ts removeEmploymentTimeline`、`read-model.ts recordsQuery` |
| 前驱恢复段校验 | 前驱在恢复区间重新生效，复核引用、部门可用、循环汇报、严格编制 | `assertRestoredPredecessor` |
| 员工状态与下游订阅方 | `employeeStatusHooks.recordDeleted`（离职记录被删则按订阅方口径恢复在职），订阅方：`esign/deletion.ts`、`employment/exit-account-hooks.ts`、`succession/exit-store.ts`、`evaluation/review-group-exit.ts` | `status-hooks.ts` |
| 员工履历 | `personnelHooks.sync` → `syncEmploymentHistory`：被删记录对应 `personnel_job_history` 软删（`deleted=true`、revision+1），前驱履历的结束日随恢复区间重算 | `personnel/employment-sync.ts` |
| 编制 | 调动携带的编制回退 `reverseCarriedEstablishment`；入职再入职工龄 `restoreRehireSeniority` | `transitions.ts` |
| 待入职合同 / 试用期 | `releasePendingContract`、`clearPendingProbation`（F-199 / F-203） | `deleteEmploymentBusiness` |
| 组织 / 职位在岗人数 | **读时实时计算，无需回写**：`org/headcount.ts` 按“主职、人员状态试用 / 正式、数据日期当天有效的任职记录”现算（F-474-2b，DEC-778②），经 `org/read-views.ts` 返回；记录删除后时间轴行消失，下次读取自然少一人。第 1 轮写的“main 仅占位、无物化计数”是**错的**，已更正 | `apps/api/src/modules/org/headcount.ts`、`read-views.ts` |
| 不回滚的联动 | 合同终止日、已发放的身份授权等：本设计不级联；有联动结果时靠 DEC-012 **拦截**而不是回滚 | D-001、DEC-012 |

**并发与幂等**：写请求携带对象 `revision`（取自列表行的 `revision`），不一致 409 `REVISION_CONFLICT`，客户端刷新后显式重提，禁止盲重试；写命令带客户端命令 ID，走命令台账，同键同内容返回原结果、同键异内容冲突（DEC-067）；前端用既有 `useConflictCommand`。结果未知时先回查再重试。

## 4. 审计

### 4.1 写入内容（已实现，同一事务）

| 审计动作 | 对象 | before | after | 位置 |
|---|---|---|---|---|
| `employment.record.delete` | `employment-record` / 记录 id | 删除前**完整快照**（`deletionSnapshot(raw)` + 载荷版本 id + 预置字段镜像 + 员工状态 / 入职状态 + `custom:<id>` 自定义字段） | `null` | `transitions.ts auditDeletedRecord` |
| `employment.business.delete` | `employment-business` / 业务 id | 业务载荷（含 `state`、`revision`、`payloadVersionId`） | `null` | `deleteEmploymentBusiness` |
| `employment.record.restore` | 前驱记录 | 恢复段 | — | `deletion-guards.ts`（`assertRestoredPredecessor` 写入） |

操作人与命令 ID 由 `auditEmployment`（`context.ts`）带入 `actorUserId`、`commandId`、`occurredAt`；业务变更与审计同事务，失败回滚不留审计残留（AGENTS §10“审计”）。

### 4.2 软删，且是否提供恢复入口（待确认 U8）

**软删**：记录行、载荷版本、状态事件全部保留；墓碑让记录从读模型消失。原站确认框写“删除的任职将不可恢复”，复刻沿用这句文案。**本设计不做“恢复已删除任职”功能，也不在时间轴上留“已删除”占位行**（原站实测删除后列表直接消失，W-424）；若要做恢复或占位，另立项（U8）。

### 4.3 删除后的展示

- **任职记录页签 / 列表页**：读模型以 `employment_timeline` 为主表，被删记录自然不再出现；不显示占位行（U8-A）。
- **数据变更日志**：审计查询按 `employment.record.delete` 能查到完整删除前快照与操作人；原站“对象操作日志不记录删除”是原站缺陷，复刻**不照搬**，保留审计（AGENTS §5）。
- **审计详情的可见字段**按查看人的权限裁剪（`audit/routes.ts` 的 `fieldsOf` / `visibleValue`）；删除类日志详情里 `before` 即快照（`snapshot`），`after` 恒为 `null`。

### 4.4 删除原因的完整链路（U3-B 暂定，待确认）

第 1 轮只说“原因随审计一起落”，缺链路。核对现有代码后的约束与设计：

| 环节 | 结论 |
|---|---|
| **输入框在哪** | 档案页签“删除任职”的确认层（`Popconfirm` 换成小弹层 `Modal`，含“删除原因（选填，最多 200 字）”输入框）。原因只属于这一个入口，列表页入口（U6-B 才有）复用同一组件 |
| **请求体** | 新路由 `DELETE /records/:id` 接收可选体 `{ reason?: string }`（≤200 字，首尾空白去除，去除后为空视为未填）；通用 `DELETE /businesses/:id` 仍为空体，**不改** |
| **归一化与指纹** | 命令指纹 = 方法 + 路径 + revision + **归一化后的 input**（`context.ts` 的 `runCommand` 指纹含 `input`）。因此“同键同原因”幂等重放返回原结果；**同键不同原因 → 命令冲突**（409 幂等冲突），不静默采用第一次的原因。未填与空白归一化后同为“无原因”，指纹相同 |
| **审计存放位置** | **不能**放 `auditEmployment` 的 `meta`：`meta` 只写入 outbox，**不进 `recordAudit`**，数据变更日志读不到。设计：删除审计 `employment.record.delete` 的 `before` 快照结构**不变**，原因作为 `after` 以外的**独立字段**随审计行记录——具体做法在 S2 实现时二选一并写进 PR：(a) 扩展 `recordAudit` 入参增加可选 `reason`（共享审计入口，需契约 PR 先单独合并）；(b) 把原因并入 `before` 快照的一个固定键 `deleteReason`。本设计**推荐 (b)**（不动共享审计入口），`after` 仍为 `null`（AC-EMP-F361-08 保持） |
| **读取路径** | 数据变更日志详情 `GET /audit/data-changes/:id`：`before` / `snapshot` 经 `fieldsOf` 裁剪后返回；`deleteReason` 需登记为“删除原因”可见字段，**按查看人对任职对象的字段权限裁剪**，无权者看不到该键，但其余快照照常显示 |
| **与 S1 / S2 的依赖** | S1（前端）先按“原因框 + 请求体 `reason`”做，若 S2 未合并则服务端忽略未知键会被 `strict` 校验拒绝，故 **S1 在 U3-B 下依赖 S2 先合并或同时合并**；U3-A（无原因）则 S1 无依赖 |

若选 U3-A（不要原因），本节整节不适用，S2 不含 reason。

### U7 删除员工最后一条任职记录，对四个入口分别怎么处理

第 1 轮把 U7 写成“只剩一条则拒绝并新增原因码”，但没有区分入口。核对后：删除唯一记录的底层行为是——`removeEmploymentTimeline` 无前驱返回 `null`，只摘行，员工时间轴变空，人员主档保留（DEC-540）。**不同入口现状不同**：

| 入口 | 现状（已核 / 假设） | 若加“唯一记录拒绝”守卫会变什么 |
|---|---|---|
| ① 档案页签删除（本任务，新路由） | 已入职的唯一记录通过通用内核可删，删后员工无任职 | 新路由自己加判定，不影响他人 |
| ② 通用 `DELETE /businesses/:id`（含对已入职记录） | 已入职记录删除返回 200（`AC-EN-F199` 的“已入职业务通用删除成功”用例） | **改变通用路径契约**，F-199 既有用例会受影响 |
| ③ 专用 `DELETE /pending-entries/:id` | 待入职的唯一记录本来就是可以删空的：删后时间轴为空、人员主档保留（`AC-EN-BE2a` “删除后该员工没有任何任职记录”）；已入职 → 409 `NOT_PENDING_ENTRY` | **会破坏待入职删除的既有语义**，不可加 |
| ④ Offer 失效清理 `deleteLinkedEntry` | 与③共用 `deletePendingEntry → transitionEmployment` 内核，调用方期待删空 | 同③，不可加 |

因此“在共享内核里加守卫”会同时影响③④，**不推荐**。

| 选项 | 说明 |
|---|---|
| **A（推荐）** 仅在新路由 `DELETE /records/:id` 的 `recordDeleteGuard` 里加“员工仅剩一条已生效时间轴记录 → 409 `EMPLOYMENT_SOLE_RECORD`（暂名）”，通用路径与专用删除、Offer 清理**契约不变** | 只改本任务新增的契约，不影响③④与 F-199 |
| B 不加守卫，保持现状，只用测试锁定“删后员工无任职、人员主档保留” | 零新原因码；但 HR 可在档案页签把员工删成“无任职” |
| C 在共享内核加守卫 | 会改③④与通用路径契约，须单独契约变更，不推荐 |

**待确认**：选 A 时，“仅剩一条”口径是“时间轴行数 = 1”，不含离职摘下的未来调动。

例子：赵六刚入职，只有 1 条入职记录。A 下 HR 在档案页签点删会被拒并提示；待入职阶段（还没办入职）的删除、Offer 失效时自动清理仍照常能删空。
