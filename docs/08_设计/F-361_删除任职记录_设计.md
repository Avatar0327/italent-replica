# F-361① 删除任职记录：设计说明（v1，第 1 轮交审）

> 状态：设计稿，**待审、待用户拍板**；本文不含产品代码、迁移或测试。凡标“待确认”的内容都是跟随推荐项的暂定写法，不是已定。
> 依据：DEC-929①（用户弹窗选“做，先出设计再开发”）、DEC-915（不再登录北森取证，按复刻现行设计，查不到写待决）、DEC-402（复刻尚未上线，不做存量数据兼容）、DEC-126（在途申请拦截）、DEC-012 / DEC-172（联动变更拦截）、DEC-178、DEC-145、DEC-067、DEC-625。
> 代码基线：main `eba240ca3`。
> 作用对象：本文所有决定都只作用于**复刻系统**，不涉及北森测试租户。

## 0. 先说结论：后端早就有删除，缺的是入口和几处口径

F-329 开发自报“后端没有直接删除任职记录的接口，未实现”。核对 main 后，**这句话对后端不成立**：

- 任职记录的 id 与业务 id 相同（`employment_records.id` = `employment_business_objects.id`），通用的 `DELETE /api/tenant/employment/businesses/:id`（`apps/api/src/modules/employment/routes.ts` 的 `registerBusinessTransitions`）对已生效的任职记录就是“删除任职”，R1-T11 已实现，守卫、重算、审计齐全（§2～§4 逐项列出）。
- 真正没有的是**前端入口**：员工档案“任职记录”页签的 `EmploymentRecords`（`apps/web/src/personnel/ProfileSections.tsx`）每条记录只有 `RecordEdit`；任职记录列表页的说明文字 `apps/web/src/employment-records/annotations.ts` 还写着“删除任职……原站均未验证，不实现”。全仓库里调用通用删除接口的前端只有调动草稿（`apps/web/src/transfer/draft-server.ts`）和待入职条目（`apps/web/src/entries/DeleteBubble.tsx`）。
- 另有几处语义要拍板（权限是否单列按钮、是否要填原因、唯一记录怎么办、列表页要不要入口），见 §7 待决清单 U1～U6。

因此本任务的开发主体是**前端入口 + 补齐少数后端口径 + 把现状锁成验收测试**，**不新增表、不新增迁移**；是否新增路由取决于 U2（推荐不新增）。

## 1. 权限归属（待确认）

### 1.1 现状（已核对）

| 项 | 现状 | 位置 |
|---|---|---|
| 授权对象 | 员工任职 `EMPLOYMENT`；前端读取用 `TenantBase.EmploymentRecord` | `policy.ts`、`ProfileSections.tsx` |
| 操作 | `object.delete` | `routes.ts` 的 `readContext(c, deps, 'object.delete', …)` |
| 按钮 | `Employment.Delete`（位置 detail，操作 delete） | `policy.ts` 的 `'DELETE /businesses/:id'` 声明；`transition-access.ts` 的 `requireEmploymentTransitionWrite`；按钮登记在 `packages/domain/src/permission/module-actions.ts` |
| 数据范围 | `BUSINESS_WRITE`（`employment.businessWrite`），与编辑同一道写入口径：记录部门 ∧ 员工当前任职都在范围内；联动改写的前驱按 DEC-177 / 178 可见即可 | `policy.ts`、`routes.ts` 的 `authorizeBusinessWrite`、`requireBusinessWriteScope` |
| 守卫 | `[TRANSFER_SOURCE, LINKAGE]`；写链路 `assertRevision`、`assertTransition`、`assertNoPendingApplication`、`requireLinkedEmploymentRecord` | `policy.ts` |
| 默认范围 | 空（fail-closed）：无范围的身份连入口都进不去，不存在“全部组织”写死 | 硬规则 1 |

北森原站有两个按钮编码：详情页 `EmploymentRecord.Delete`、列表行 `EmploymentRecord.LineOp.DelRecord`。复刻的 `module-actions.ts` 里没有这两个编码，只有 `Employment.Delete`。

### 1.2 设计（暂定，待确认 U1）

- **沿用 `Employment.Delete`，不新增授权项**。理由：该按钮已登记在 `module-actions.ts` 且被 `DELETE /businesses/:id` 声明使用；新增授权项编码要走授权版本流程（`STANDARD_GRANT_VERSION` / `STANDARD_GRANT_DIGEST`，DEC-439④），对“删除任职”一个动作没有额外收益。`Employment.Delete` 是否已在标准身份授权项里出现**未核对**，见 §8。
- 档案页签入口的显示条件：持有对象 `TenantBase.EmploymentRecord` 或 `Employment` 下的 `Employment.Delete` 按钮，**且**该行 `recordDeletable`（§2.4）为真。前端只做显隐，权威判定仍在服务端，每次请求都重新校验成员、租户、范围（AGENTS §10“权限”）。
- **数据范围不得宽于编辑**：删除与 `PATCH /records/:id` 走同一个 `BUSINESS_WRITE` 判定，范围外记录一律 404（不暴露存在性），字段不可见的拒绝详情按范围与字段权限裁剪（`discloseDeletionBlock`）。
- 撤销身份不连带删除范围（硬规则 6）：本任务不涉及授权写入，仅复用现有判定。

## 2. 可删范围与拒绝口径（待确认）

### 2.1 状态可删性

`transitions.ts` 的 `transitionPermitted`：动作 `delete` 允许的状态为 `draft / rejected / disapproved / voided / approved / effective`；其余（如审批中 `in_review`）返回 409 `CONFLICT`「当前状态不允许此动作」。

其中**“删除任职记录”只指 `effective`（已生效、已落时间轴）的记录**；草稿 / 驳回 / 作废 / 已批未生效是“删除申请”，由调动与入职各自入口处理，不属于本任务。

### 2.2 按业务类型

| 业务类型 | 删除行为 | 依据 |
|---|---|---|
| 调动 `transfer`、组织调整联动生成的记录、转岗等同类 | 走通用删除：摘下时间轴行、前驱区间恢复到后一条的生效日 | `removeEmploymentTimeline` |
| 离职 `leave`、退休 `retirement` | 通用 DELETE **路由到“撤销离职 / 撤销退休”**（`routesToCancel` → `runExitCancel`），**必填原因**，缺原因 400 `EXIT_CANCEL_REASON_REQUIRED`；退休另见 DEC-714 | R2-T03 §6B；`AC-EXIT-cancel-delete-reason` |
| 入职 `hire`、再入职、退休返聘、实习转正等“开新周期”类 | 只有**其后没有同周期记录、也没有下一周期记录**时可删，否则 409 `EMPLOYMENT_FUTURE_VERSION_EXISTS`「存在后续任职记录，不能删除历史记录」 | `timeline.ts removeEmploymentTimeline` 的 `opensCycle` 判定；`NEW_CYCLE_KINDS` + DEC-797 |
| 被离职摘下的未来调动（不在时间轴上） | 记录与墓碑照常处理，没有区间可恢复，也没有生效中的下游可通知 | `deleteEmploymentBusiness` 的 `isDetachedRecord` 分支 |

### 2.3 拒绝清单与错误码

下表全部来自现有实现，本任务**不改变其语义**；前端只需把原因原样展示、不自动重试（AGENTS §10“并发”）。

| 场景 | 状态码 / 原因码 | 来源 |
|---|---|---|
| 其后有审批中或已批未生效、生效日不早于被删记录的申请（DEC-126） | 409 `EMPLOYMENT_PENDING_APPLICATION_EXISTS`，详情按范围与字段权限披露单号，范围外只给件数 `hiddenCount` | `deletion-guards.ts assertNoPendingApplication` / `PendingApplicationError` / `disclosePendingApplications` |
| 联动改写结果仍在（合同、下属经理、组织角色、兼职；DEC-012 / 172） | 409 `EMPLOYMENT_LINKED_CHANGES_EXIST`，只给件数 | `assertNoLinkedChanges`；探针 `transfer/linkage/deletion-probes.ts`、`part-time/install.ts`、`organizationLinkage` |
| 恢复区间前驱不可见 / 部门停用 / 严格编制不满足（DEC-178 / DEC-145） | 404 `LINKED_RECORD_OUT_OF_SCOPE` / 400 `EMPLOYMENT_DEPARTMENT_DISABLED` / 编制类拒绝 | `assertRestoredPredecessor`、`assertRestoredEstablishment` |
| 删除后前驱直线经理会成环 | 400 `REPORTING_CYCLE`（默认不暴露路径与姓名） | `ReportingCycleDeletionError` |
| 组织调整暂停期内被删记录或前驱涉及暂停组织（R2-T08 §7.6） | 409 | `transitions.ts assertDeletionNotPaused` |
| 开新周期记录其后还有记录 | 409 `EMPLOYMENT_FUTURE_VERSION_EXISTS` | `timeline.ts`、`errors.ts` |
| 实习转正已向后传播 | 409 | `employee-status.ts assertRegularizationNotPropagated` |
| 修订号不一致 | 409（`assertRevision`） | `policy.ts` 写链路 |
| 状态不允许 | 409 `CONFLICT` | `transitionPermitted` |

> 原站的“删除历史周期第一条且区间内有薪酬数据则禁止”（`07` A11）：复刻按 §2.2 对开新周期记录已**比原站更严**（后面有任何记录都不能删），所以只有“最后一个周期的唯一记录”才会走到薪酬判断，见 U5。

### 2.4 前端“可删”的显示条件（暂定）

列表行 `GET /employees/:id/records`（`read-model.ts`）已返回 `id`、`revision`、`kind`、`effectiveDate`、`stopDate`、`isCurrent`、`isLatest`、`status`、`staffId`。前端对一行显示“删除任职”须同时满足：

1. 有 `Employment.Delete` 按钮权限；
2. `status === 'effective'`（该接口只返回已落时间轴的记录，天然满足）；
3. 不依赖前端猜测业务守卫：**不在前端预判在途申请 / 联动 / 周期**，一律提交后按服务端原因展示。这样规则只有一份，避免前端与后端口径漂移（对照 F-329 `recordEditable` 的做法，`edit-model.ts`）。

## 3. 删除后的重算（同一事务）

全部在 `transitionEmployment` 的 delete 分支内、同一 `runWrite` 事务里完成；员工行锁由任职命令统一持有，并发写同一员工的任职被串行化。

| 重算对象 | 做法 | 位置 |
|---|---|---|
| 版本链 | **软删除**：写墓碑 `employment_record_tombstones`，追加状态事件 `deleted`（`appendEmploymentState`），**不改写、不删除** `employment_records` / `employment_payload_versions` / `employment_state_events`；不新增“变更前”列，前驱仍从版本链上一条读取（硬规则 2、3） | `deleteEmploymentBusiness` |
| 时间轴与有效区间 | 删除 `employment_timeline` 行；前一条的 `valid_during` 延伸到后一条的生效日（无后一条则开放）；后续记录与同日顺序号**不重算**（W-013、W-424）；当前任职由 `valid_during @> 查询日` 读时计算（`isCurrent`），不存在需要回写的“当前任职快照”列 | `timeline.ts removeEmploymentTimeline`、`read-model.ts recordsQuery` |
| 前驱恢复段校验 | 前驱在恢复区间重新生效，复核引用、部门可用、循环汇报、严格编制 | `assertRestoredPredecessor` |
| 员工状态与下游订阅方 | `employeeStatusHooks.recordDeleted`（离职记录被删则按订阅方口径恢复在职），订阅方：`esign/deletion.ts`、`employment/exit-account-hooks.ts`、`succession/exit-store.ts`、`evaluation/review-group-exit.ts` | `status-hooks.ts` |
| 员工履历 | `personnelHooks.sync` → `syncEmploymentHistory`：被删记录对应 `personnel_job_history` 软删（`deleted=true`、revision+1），前驱履历的结束日随恢复区间重算 | `personnel/employment-sync.ts` |
| 编制 | 调动携带的编制回退 `reverseCarriedEstablishment`；入职再入职工龄 `restoreRehireSeniority` | `transitions.ts` |
| 待入职合同 / 试用期 | `releasePendingContract`、`clearPendingProbation`（F-199 / F-203） | `deleteEmploymentBusiness` |
| 组织 / 职位在岗人数 | main 上在岗人数仍是占位（DEC-850 登记 F-474-2 时“在岗人数在 main 仅 503 占位”），不存在物化计数，**无需重算**；将来物化时须挂在 `employeeStatusHooks` 订阅方上（假设，见 §8） | — |
| 不回滚的联动 | 合同终止日、已发放的身份授权等：本设计不级联；有联动结果时靠 DEC-012 **拦截**而不是回滚 | D-001、DEC-012 |

**并发与幂等**：写请求携带对象 `revision`（取自列表行的 `revision`），不一致 409，客户端刷新后显式重提，禁止盲重试；写命令带客户端命令 ID，走命令台账，同键同内容返回原结果、同键异内容冲突（DEC-067）；前端用既有 `useConflictCommand`（见 `EditCommands.tsx`）。结果未知时先回查再重试。

## 4. 审计

### 4.1 写入内容（已实现，同一事务）

| 审计动作 | 对象 | before | after | 位置 |
|---|---|---|---|---|
| `employment.record.delete` | `employment-record` / 记录 id | 删除前**完整快照**（`deletionSnapshot(raw)` + 载荷版本 id + 预置字段镜像 + 员工状态 / 入职状态 + `custom:<id>` 自定义字段） | `null` | `transitions.ts auditDeletedRecord` |
| `employment.business.delete` | `employment-business` / 业务 id | 业务载荷（含 `state`、`revision`、`payloadVersionId`） | `null` | `deleteEmploymentBusiness` |
| `employment.record.restore` | 前驱记录 | 恢复段 | — | `deletion-guards.ts assertRestoredPredecessor` |

操作人与命令 ID 由 `auditEmployment`（`context.ts`）带入 `actorUserId`、`commandId`、`occurredAt`；业务变更与审计同事务，失败回滚不留审计残留（AGENTS §10“审计”）。

### 4.2 软删还是物理删（待确认 U3 的前提）

**软删，且不提供恢复入口**。记录行、载荷版本、状态事件全部保留；墓碑让记录从读模型消失。原站确认框写“删除的任职将不可恢复”，复刻沿用这句文案，不做“恢复已删除任职”功能（需另立项）。

### 4.3 删除后的展示

- **任职记录页签 / 列表页**：读模型 `recordsQuery` 以 `employment_timeline` 为主表，被删记录自然不再出现；不显示“已删除”占位行（原站同，W-424 实测删除后列表直接消失）。
- **数据变更日志**：审计查询按 `employment.record.delete` 能查到完整删除前快照与操作人；原站“对象操作日志不记录删除”是原站缺陷，复刻**不照搬**，保留审计（硬规则“所有写操作进入统一的字段级变更日志”，AGENTS §5）。
- **删除原因**：见 U3；普通调动记录目前没有原因字段，离职 / 退休撤销已有必填原因。

## 5. 前端设计（暂定）

- 位置：`EmploymentRecords`（`ProfileSections.tsx`）每条记录 `header` 内，紧挨 `RecordEdit`，新增 `RecordDelete`（放在 `EditCommands.tsx`，与 `RecordEdit` 同构）。
- 交互：`Popconfirm`，文案沿用原站“删除的任职将不可恢复，是否继续”；确认后发 `DELETE /api/tenant/employment/businesses/<record.id>`，带 `revision`（取自该行）与客户端命令 ID。
- 成功：提示“删除任职记录成功”（原站文案），刷新列表；员工页其他区块（当前任职、履历子集）也要刷新，沿用 F-329 `saved` 回调扩展。
- 失败：按 §2.3 的原因码展示可读原因（`rowFailure` 同类 helper），409 提示“记录已变更，请刷新后重试”，**不自动重试**；在途申请单号列表按服务端披露结果渲染，不自行补全。
- 文案进资源文件 `apps/web/src/personnel/messages.ts`（DEC-045），不写死在组件里。
- 离职 / 退休记录：按 U4 的结论决定是显示“删除任职”还是只显示“撤销离职”。

## 7. 待决清单（均只作用于**复刻系统**；推荐项已暂写入正文，标“待确认”）

### U1 删除任职的权限挂在哪个按钮

| 选项 | 说明 |
|---|---|
| **A（推荐）** 沿用 `Employment.Delete` | 已在标准授权里，零授权变更；删除与编辑的数据范围同一口径 |
| B 新增 `EmploymentRecord.Delete`（北森编码） | 可把“删除已生效记录”单独授权给更少的人，但要改授权项目录、指纹与版本，且现有持有 `Employment.Delete` 的身份需补授权 |

例子：A 下，能删调动草稿的 HR 同样能看到“删除任职”入口；B 下，只有被单独授予的 HR 才看得到。

### U2 是否新增以记录为键的删除路由

| 选项 | 说明 |
|---|---|
| **A（推荐）** 不新增，前端用记录 id 调 `DELETE /businesses/:id` | 记录 id 即业务 id；零新路由，不走 F-039 新声明 |
| B 新增 `DELETE /records/:id` 别名 | 与 `PATCH /records/:id` 对称，但要完整重复一套声明与回归，收益只是路径好看 |

### U3 普通任职记录删除是否要填原因

| 选项 | 说明 |
|---|---|
| A 不要原因 | 与原站一致；审计仍有操作人与命令 ID |
| **B（推荐）** 选填原因（≤200 字） | 随审计一起落，查误删有据；离职 / 退休撤销本就必填，口径不矛盾；请求体由空体改为可选 `reason`，需放宽 `commandOnly` 声明 |
| C 必填原因 | 对误录入的多数场景过重 |

例子：HR 发现 9-20 的调动是误录入，选 B 可以填“误录入，已核对”，之后审计里能查到这句话。

### U4 离职 / 退休记录在档案页签里怎么处理

现状通用 DELETE 会路由到撤销流程并要求必填原因。

| 选项 | 说明 |
|---|---|
| **A（推荐）** 档案页签对离职 / 退休记录**不显示**“删除任职”，由离职 / 退休管理里的“撤销”入口负责 | 避免同一动作两个入口、两套原因要求 |
