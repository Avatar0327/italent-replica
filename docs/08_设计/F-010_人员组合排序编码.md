# F-010 人员组合排序编码

依据 DEC-148、DEC-170、DEC-171 与 `15_任职记录对象_字段规格.md` §12，人员组合名次仅由定时批量（默认每 3 小时，可配置）或手动触发重算，不做实时增量；DEC-170 取代 DEC-037 / DEC-148 中关于组合名次“变更时增量刷新”的旧措辞。旧的组织 / 职务属性名次保持原有刷新机制；本次只补人员组合名次，不改任职版本链、合同或组织编码。

## 比较与读取

- 启用的规则按配置数组顺序逐项比较，每项可升序 / 降序：`department`（从行政根到部门的顺序号路径，父先于子）、`post`（职务编码）、`position`（职位顺序号）、`level`（职级级别）、`grade`（职等等级）、`code`（工号）。编码与工号是文本，使用数据库 C 字节顺序（例如字符串 `10` 在 `9` 前）；行政顺序号、职位顺序号、职级级别、职等等级是整数，按数值比较。
- 使用 SQL `rank()`，相同比较项允许并列，例如 1、1、3。人员 ID / 工号回退不参与名次，除非工号本身是启用规则项。
- 不拼接分段、不补位。规则项缺失时使用 SQL `NULLS LAST`；全部已启用项相同（包括同为 NULL）时并列。没有当前主职的人员不参与排名，`orderCode` 为 `null`。规则整体停用或无启用项时重算清空名次。
- 当前主职取租户业务日及既有主职时间轴，读取最新记录快照。未来版本在到期后的下一次重算生效，不提前生效。离职 / 退休人员只要仍有主职时间轴记录就参与排名，依据该日最新主职记录快照；本轮明确并保留现有口径，未新增“仅在职”过滤。相同行政路径顺序号仍视为并列，不追加部门编码或 ID 改变名次语义。
- DEC-171：未配置时 GET 返回 `{revision:0, enabled:false, items:[]}`，没有内置默认规则。手动或定时重算均不计算、不新增名次行；如旧版本曾按默认规则写入名次，则清空已有名次。配置后在下一次定时或手动重算时计算；删除 / 停用全部规则项后重算也清空名次。
- 人员列表默认按已存储名次升序，未计算 / 无名次排末尾；并列与无名次按工号（C 排序）、人员 ID 升序。子集再按子集 ID 稳定排序。显式 `sortBy` 优先，`orderCode` 可作排序 / 筛选字段，沿用字段权限校验及结果裁剪。详情直接返回同一存储值。

## 租户接口

统一前缀 `/api/tenant/personnel/order-code`，租户来自已认证请求上下文，不接受请求体指定租户。

| 方法与路径 | 权限 / 输入 | 返回 |
|---|---|---|
| GET `/settings` | `tenant.settings.read`，资源 `personnel.order_code` | `{revision, enabled, items}`，ETag 为配置 revision |
| PUT `/settings` | `tenant.settings.write`；If-Match、Idempotency-Key；`{enabled, items:[{field,direction,enabled}]}` | 新配置 revision；最多 6 项且不得重复；仅保存，不立即重算 |
| POST `/recompute` | `tenant.settings.write`；If-Match 为配置 revision，Idempotency-Key；空对象 `{}` | `{revision, changed, businessDate, outcome}`；不返回全租户人员；outcome 为 computed（已计算）、not_configured（未配置，未计算）、disabled（规则整体停用）、no_enabled_rules（无启用项） |

每次调用（含幂等重放）重新校验权限；写事务再次校验。revision 不符 409；同键异内容 409；无命令键 400。配置变更记录同事务审计；名次变化同事务写字段级审计、personnel_outbox 和命令台账。结果未变化时不提高名次 revision、不重复写人员字段审计 / outbox。每个成功的手动重算命令（包括未配置或零改动）另写一条 `personnel.order.run` 运行级审计，含操作人、配置 revision、changed、outcome、businessDate；同一命令重放不重复写入。

## 存储、并发与调度

迁移 `0045_personnel_order_code.sql` 由 `pnpm db:generate` 生成结构与快照，再补标准 `enable_tenant_isolation` 与 app_user 授权：

- `personnel_employee_order_codes`：以 tenant_id + employee_id 为主键，复合外键指向 employment_employees，名次与派生 revision；不改 employment 表。
- `personnel_order_settings` / `personnel_order_rules`：独立的租户配置和有序规则项。
- `personnel_order_runs`：租户 + 命令键、状态、尝试数、错误码与 UTC 执行时间；用于调度回查与运维定位。

重算进入事务先设置 `SET LOCAL lock_timeout = '5s'`，限制等待配置 / 外键锁的时间（不是整个重算的执行时限）；超时整体回滚，手动接口返回 503，调度记录 unknown，可重试。重算锁定本模块的配置行；组织、任职等数据通过同一 SQL 快照读取。数据库内计算全租户窗口并在单个事务原子发布，避免应用内全量加载或分页产生局部名次。外键写入按员工 ID 顺序，不取业务或审批实例锁，也不改员工；不主动反向取得 PR #50 所规定的员工 → 业务 → 实例锁。名次与 outbox 的外键检查仍会取得员工 KEY SHARE 锁；两遍写入与其他多员工事务可能发生等待或死锁，数据库中止时整单回滚后重试，不能把排序当作不会影响业务写入的保证。

重算使用精简的主职 / 职务体系 JOIN，不再读取人员版本、账号、入职周期和已有属性名次。人员数影响单次租户事务耗时；本实现没有应用层人员分页，较大租户需关注该 SQL 执行时间。租户目录按每页 100 条扫描，业务数据始终在 withTenant + RLS 下访问。

万人合成基准 `AC-EMP-16-benchmark.test.ts`：每人一个主职、按工号排序，本地 Node 24.19.0 + PGlite，接口整次耗时首算 1033 ms、无变化 287 ms、反向全量变化 987 ms（2026-10-05；不含造数 / 迁移）。仅作规模估算，不是生产 SLA；未模拟深组织、多历史版本或并行业务写入。测试核对 10000 条名次、无变化零写入及反向变化，耗时不作机器相关断言；可用 `pnpm exec vitest run tests/acceptance/AC-EMP-16-benchmark.test.ts --disableConsoleIntercept` 复测。生产 PostgreSQL 的锁争用与硬件差异需另行观测。

`server.ts` 启动 personnel 独立调度器，默认每 3 小时运行，并在进程启动时执行当前周期。`PERSONNEL_ORDER_CODE_INTERVAL_MS` 可调整周期（1000～2147483647 毫秒）；`PERSONNEL_ORDER_CODE_SCHEDULER=off` 关闭本进程调度。每个租户按间隔 + UTC 时间槽生成幂等命令键，主职有效日期仍按租户时区计算；多实例同槽只提交一次，一进程前一轮未结束不启动重叠轮次。

定时重算失败时先回查成功命令；可识别业务错误记 failed，存储 / 结果未知记 unknown，保留尝试数和机器错误码。单租户失败不阻断其他租户；同槽再调用可重试，下周期也会重新计算当前数据。失败回执本身也设置 5 秒锁等待上限；回执不可写时向进程 onError 报告，并继续本轮其余租户，不伪造持久状态。成功重放不重新执行；失败回执不进入成功命令台账。
