# F-474-6a 组织 / 人员自定义字段机制：设计

> 任务：F-474-6a（DEC-776 / DEC-778；续批规划 `F474_plan.md` F-474-6 行）。只出设计，实现另派（6b 组织自定义字段 #3、6c 人员自定义字段 #19）。
> 基线：main `c20147c6f`。作用对象全部是**复刻系统**；北森原站只引用已有取证，没有证据的一律标“待取证”，不臆造。
> 约束：DEC-005（标准字段 + 可扩展自定义字段）、DEC-402（不加开关、不考虑存量兼容）、DEC-376（字段 ID 绑定，改名自动跟随）、AGENTS.md §2 八条硬规则。

## 0. 一页摘要

- 复刻系统里**任职记录、合同协议**已经有一套自定义字段机制；**组织、人员主档目前没有**。
- 推荐**一套机制、多个对象**：沿用现有定义表和 `custom:<id>` 字段编码，把对象类型从 `{employment, contract}` 扩到 `{…, organization, personnel}`；值各自存在对象版本行的 `custom_fields jsonb` 列里，键是字段 ID。
- 字段权限、字段目录、审计、F-082 字段 ID 绑定都已按“`custom:<id>` + `registerTenantFieldSource`”设计，接入组织、人员只需**新增两处登记**，不改授权语义、不新增授权编码，所以**不触发授权版本变化**。
- 首批字段类型：现有 5 种（文本 / 整数 / 小数 / 布尔 / 日期）+ 单选下拉（原站有组织“成本中心”扩展字段的取证）。员工选择、日期时间、多选列为后补，见 §8。
- 需要一个很小的**契约 PR（6b-0）**先合并：F-039 写入字段来源增加“正文 + 自定义字段”写法，以及迁移里放宽对象类型 CHECK。

## 3. 数据模型与迁移草案

迁移序号只是占位（当前最大 0187），实际序号由 `pnpm merge:main` 定。

### 3.1 定义表：沿用现有表，放宽对象类型，加选项集

```sql
-- 6b-0 / 6b 迁移（草案）
ALTER TABLE employment_custom_field_objects DROP CONSTRAINT employment_custom_field_object_type_valid;
ALTER TABLE employment_custom_field_objects ADD CONSTRAINT employment_custom_field_object_type_valid
  CHECK (object_type IN ('employment','contract','organization','personnel'));
ALTER TABLE employment_custom_field_objects DROP CONSTRAINT employment_custom_field_value_type_valid;
ALTER TABLE employment_custom_field_objects ADD CONSTRAINT employment_custom_field_value_type_valid
  CHECK (value_type IN ('text','integer','decimal','boolean','date','select'));
ALTER TABLE employment_custom_field_objects
  ADD COLUMN options jsonb NOT NULL DEFAULT '[]'::jsonb
  CONSTRAINT employment_custom_field_options_array CHECK (jsonb_typeof(options) = 'array');
-- select 类型必须有选项；其他类型必须是空数组
ALTER TABLE employment_custom_field_objects ADD CONSTRAINT employment_custom_field_select_options
  CHECK ((value_type = 'select') = (jsonb_array_length(options) > 0));
```

- 约束名以现有迁移里的实际名为准（实现单核对，上面是示意）。
- **不改表名**。表名里的 `employment_` 前缀留作历史命名（DEC-402 不考虑存量兼容，但改名会牵动 RLS 函数、审计标签、授权对象编码等多处，收益只是好看，不做）。
- 选项集放在定义行的 `options jsonb`：`[{ "value": "<稳定编码>", "label": "名称", "enabled": true }, …]`，≤ 50 项；选项只可新增、改名、停用，**不物理删除**，所以历史值永远能解析出名称。选项变更用定义行的 `revision` 做乐观锁（409）。
- 编码仍用 `ext_<租户>_<uuid>`（内部标识，与业务编码分离，AGENTS §10 标识）；原站 `ext<拼音>_<租户ID>_<随机数>` 的“扩展前缀 + 租户隔离 + 唯一后缀”三要素已满足，拼音部分是展示习惯，待取证是否出现在导入模板里（§1）。
- 推荐采用定义行 `options`（§8-U3-A），不另建选项版本表。**列授权和触发器须一起改**：现有 `0013_employment_rls_timeline.sql:85-107` 的共用 `protect_employment_head_metadata()` 只排除 `revision`，仅加 `UPDATE(options)` 仍会被 SQLSTATE `55000` 拒绝。
- 6b-0 **新增迁移**：保留共用函数及员工、业务对象、设置表的触发器；仅替换 `employment_custom_field_objects_metadata_only`，改绑本表专用函数 `protect_employment_custom_field_metadata()`。核心判断为 `(to_jsonb(NEW) - ARRAY['revision','options']) IS DISTINCT FROM (to_jsonb(OLD) - ARRAY['revision','options'])` 时抛 `55000`，否则返回 `NEW`。采用排除两列的写法，使以后新增的元数据列默认仍受保护；函数沿用固定 `search_path = pg_catalog, public`，不提权。
- 同一迁移授予 `app_user` **列级** `UPDATE(revision, options)`，不授整表 UPDATE；保留 `SELECT, INSERT`、RLS / FORCE RLS、无 DELETE，以及现有禁止 DELETE / TRUNCATE 的触发器。`id / tenant_id / object_type / code / name / value_type / created_at` 均不可借此更新；这里的“改名”仅指选项 `label`，不放开字段定义名。
- 选项新增 / 改名 / 启停由配置入口校验稳定编码不可改、旧项不可删、最多 50 项，CAS 同时更新 `options` 与 `revision` 并在同事务记审计；失败不改选项、不递增 revision。不得通过修改共用函数放宽其他头表，也不得改写已合并的 0013 迁移。

### 3.2 值：对象版本行上加 `custom_fields jsonb`

```sql
ALTER TABLE org_versions
  ADD COLUMN custom_fields jsonb NOT NULL DEFAULT '{}'::jsonb,
  ADD CONSTRAINT org_versions_custom_fields_object CHECK (jsonb_typeof(custom_fields) = 'object');
ALTER TABLE personnel_employee_versions
  ADD COLUMN custom_fields jsonb NOT NULL DEFAULT '{}'::jsonb,
  ADD CONSTRAINT personnel_employee_versions_custom_fields_object CHECK (jsonb_typeof(custom_fields) = 'object');
```

- 值放**版本行**而不是对象头：组织、人员主档都是“一次业务一条新版本”的追加链（硬规则：不得单表 UPDATE 覆盖当前值；“变更前”一律取上一版本），自定义字段跟标准字段同待遇，生效日期、历史查询、审计前后值自然一致。
- 键 = 字段 ID（不是编码、不是名称），改名自动跟随（DEC-376）；这点与任职、合同完全一致。
- 写入时服务端逐键校验：字段 ID 必须是**当前租户**、**对应对象类型**的定义（否则 400，不接受未知键，不静默忽略）；值按 `valueType` 校验；`select` 值必须是该字段的**启用**选项编码或沿用上一版本里的同值。
- 租户隔离：值表本身已有 RLS；跨租户字段 ID 在定义表 RLS 下查不到，等同未知键，被拒绝。
- 不建索引、不支持按自定义字段筛选 / 排序（首批）；需要时再按字段建表达式索引，属于 §8-U5。
- 复制 / 继承：新版本默认**整体带上一版本的 `custom_fields`**，再叠加本次改动；组织、人员没有“是否继承”开关（任职、合同才有，DEC-402 也不再加）。

### 3.3 不做的事

- 不做 EAV 值表：核心对象不用通用实体表（AGENTS §7），而且字段权限、审计、导入都要按字段 ID 取值，jsonb 已够。
- 不迁存量：新列默认 `{}`，没有回填（DEC-402）。
- 不新增“自定义字段删除”：与现有任职、合同一致，定义行无 DELETE；是否支持停用见 §8-U4。

## 4. 接口与权限

### 4.1 定义管理（配置类，沿用现有路由）

| 路由 | 变化 |
|---|---|
| `GET /api/tenant/employment/custom-fields?objectType=` | `objectType` 允许值扩到 `organization`、`personnel`；返回项增加 `options` |
| `POST /api/tenant/employment/custom-fields` | body 严格 `{ name, valueType, objectType, options? }`；`select` 必须带 `options`，其他类型带则 400；每租户每对象类型仍最多 200 个（超出 503） |
| `PUT /api/tenant/employment/custom-fields/:id/options`（**新增**） | 仅 `select`；body `{ options }`，`If-Match` = 定义行 `revision`；不允许删除已存在选项，只可新增 / 改名 / 启停 |
| `PUT /api/tenant/employment/custom-fields/:id/inheritance` | **不变**，只对 `employment`、`contract` 有意义；对组织 / 人员字段调用 → 400 |

路径仍在 `employment` 下，不搬家（搬家只会多出一批 F-039 登记和授权码改名；页面上由前端统一展示为“自定义字段”，见 §5）。

### 4.2 授权对象：不新增授权编码

- 管理这些定义的权限继续是配置对象 `TenantBase.EmploymentCustomField`（`create / update / view`）。**组织、人员自定义字段与任职、合同字段共用这一对象**——拥有它的人能管理四类对象的字段定义。
- 理由：不新增授权项 → `STANDARD_GRANT_DIGEST` / `STANDARD_GRANT_VERSION` / `standard-grant-changes.json` 都不动，不触发授权类单独审（DEC-441 里的“授权类”），也不需要 F-061 补装。只改**展示名**（审计标签 `employment_custom_field` 的“任职自定义字段”改成“自定义字段”，`labels.ts:57`），不改授权编码。
- 需要“按对象类型分别授权”的话，要新增配置对象，属于授权类，见 §8-U1。

### 4.3 字段权限与字段目录

两处登记，写在各自业务模块加载时（沿用 `tenant-catalog.ts` 的模式，当前已有任职、合同）：

```ts
registerTenantFieldSource(MODULE_OBJECTS.organization.code, customFields('organization'));
registerTenantFieldSource(PERSONNEL_OBJECT, customFields('personnel'));
```

- `customFields(objectType)` 的类型参数从 `'employment' | 'contract'` 放宽到四种。其余——`custom:<id>` 编码、`TENANT_FIELD_LIMIT = 1000`、保存身份对象权限时按扩展目录校验——都不变。
- **新字段默认谁也看不到**：标准身份的对象权限从**静态**目录推导（`standard-presets.ts` 的 `full(def)`，见 `F-061_标准身份授权补装_方案.md` §1.1），租户字段不在其中；字段创建后，必须在身份详情的字段权限里显式勾选“查看 / 编辑”。这与任职、合同现状相同，也符合“fail-closed”。
- 编辑权：自定义字段不是系统字段（`system:false`），可以授编辑。
- 读取出口：组织读模型、人员员工读取（`employee-read.ts` / `employee-projection.ts`）必须像任职 `context.ts` 那样，把 `customFields` 按**当前查看人**可见的 `custom:<id>` 裁剪；列表、详情、导出、审批详情里嵌套的值都走同一裁剪。历史版本读取同样按当前权限裁（AGENTS §10 权限）。
- 写入入口：按字段做编辑权校验——提交的 `customFields` 里出现任何查看人**无编辑权**的字段 → 403；未提交的字段保持上一版本的值，不被清空。
- 审计：值的前后值走既有路径 `customFields.<id>`（`labels.ts:476-478`），可见性裁剪沿用 `visibility.ts:1294` 的映射；组织、人员的审计对象编码已存在，**实现单需核对**它们的前后值是否经过同一 SQL 裁剪，没有则补齐，这是越权读取的主要风险点。
- 数据范围：自定义字段值属于所在组织 / 人员，范围判定不变；**不新增范围维度**。

## 5. 前端页面与交互要点

- **配置页**：原有“任职自定义字段”设置页改名“自定义字段”，对象类型下拉增加“组织”“人员”；列表列 = 名称、类型、对象、（任职 / 合同才有）是否继承。新建抽屉：名称、类型、（下拉类型）选项编辑器（增、改名、启停、拖拽排序，不可删已存在项）。组织 / 人员的配置页形态**待取证**（§1），首批按任职页形态做。
- **组织**：新建 / 编辑抽屉在“其他信息”下追加自定义字段分组，按字段权限显示 / 只读 / 隐藏；组织列表在列设置里出现可见字段，**默认不显示**，不支持按自定义字段筛选或排序（首批）；详情页展示；组织架构图卡片不显示（与 F-474-2 的 #2 卡片字段互不影响）。
- **人员**：员工信息详情 / 编辑的“基本信息”分组追加自定义字段；员工列表列设置里可选；人员子集（教育 / 证书等）不在本设计范围（§8-U6）。
- 控件按类型：文本 → 单行输入（≤ 2000 字，与 `validateCustomValue` 一致）；整数 / 小数 → 数字框（小数不设定精度，沿用现有口径）；布尔 → 开关；日期 → 日期选择；下拉 → 单选，停用选项只在已选时显示（灰色标记）。
- 所有控件文案走资源文件（DEC-045）。
- 空值显示 `--`，与标准字段一致；字段无查看权时整项不渲染，不出现占位。

## 7. 验收要点（后续开发单可直接抄作 AC）

编号待分配，下面用占位 `AC-CF-xx`。

1. **AC-CF-01 创建与上限**：对 `organization`、`personnel` 各创建文本 / 整数 / 小数 / 布尔 / 日期 / 下拉字段成功；非法类型、`select` 无选项、非 `select` 带选项均 400；同租户同对象类型第 201 个 → 503；另一租户不受影响。
2. **AC-CF-02 租户隔离**：A 租户的字段 ID 出现在 B 租户的组织 / 人员保存请求里 → 400（未知字段），且 B 租户的版本行不含该键；B 租户直接读 A 租户定义行 → 0 行。
3. **AC-CF-03 字段权限 fail-closed**：新字段创建后，未授权身份读组织 / 人员详情、列表、导出、审计差异都**看不到**该字段的值，也看不到键；仅授“查看”的身份提交该字段 → 403；授“编辑”后可写。
4. **AC-CF-04 版本链**：改组织 / 人员某自定义字段 → 产生**新版本行**，上一版本值不变；未提交的自定义字段值在新版本里保持上一版本的值；“变更前”从上一版本取，没有单独列。
5. **AC-CF-05 值校验**：整数传小数 / 字符串、日期格式非法、文本超 2000 字、下拉传不在选项集的值 → 400；`null` 清空合法；停用选项不能新选，但保留历史值可读。
6. **AC-CF-06 改名跟随**：字段改名后，历史版本、审计、已存的字段权限都继续指向同一 ID（DEC-376）。
7. **AC-CF-07 权限撤销后裁剪**：撤销身份的某字段查看权后，下一次请求即不再返回；历史版本读取同样按当前权限裁剪。
8. **AC-CF-08 定义授权**：只有持有 `TenantBase.EmploymentCustomField` 创建权的身份能新建；任职、合同字段的现有行为（继承开关、200 上限）不变（回归）。
9. **AC-CF-09 授权版本不变**：`STANDARD_GRANT_DIGEST` / `STANDARD_GRANT_VERSION` / `standard-grant-changes.json` 无变化（若实现单为此新增了授权项，须回到 §8-U1 重新决策）。
10. **AC-CF-10 审计**：定义新建 / 选项变更、值变更各写审计（与业务变更同事务）；无字段查看权的审计读取者看不到前后值中的该字段。
11. **AC-CF-11 F-039**：新增路由已登记；组织、人员写路由的字段来源包含 `customFields`；基准 / 发现探测 / 摘要由 `merge:main` 重算后严格校验通过。
12. **AC-CF-12 选项更新与元数据保护**：普通 `app_owner` 连接经 `withTenant` 以 `app_user` 执行，管理员走真实 `PUT …/options` 分别新增、改 `label`、停用成功，revision 各加 1 且审计一致；旧 revision 返回 409、结果不变。权限目录授权与列授权齐备时不再报 `55000`。分别尝试更新上述受保护列：租户角色因无列授权被拒；迁移所有者绕过列授权后仍被专用触发器以 `55000` 拒绝（在回滚事务中逐列测），证明不是仅靠 GRANT 挡住。另测员工 / 业务对象 / 设置头仍只允许 revision 更新，以及定义行 DELETE / TRUNCATE 仍被拒；跨租户更新影响 0 行。新验收覆盖真实迁移后的数据库，不只测试内存选项校验。
