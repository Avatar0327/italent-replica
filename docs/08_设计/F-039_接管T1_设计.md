## 0. 一页摘要

- **T1 要做的事**：把每条路由的**准入判定**从处理函数里搬到框架。
  - 准入判定包括：功能 / 管理员能力、写字段、按钮、范围点校验 / 看全部 / 范围守卫、本人身份。
  - 框架在调用处理函数之前，按声明执行这些判定；处理函数里对应的手写调用删除，并用测试禁止再写回去。
  - **不在 T1**：列表查询的范围过滤 SQL（T2，QuerySpec）、命令事务内复核与返回后复核（T3）、出口字段裁剪（T4）。T1 期间这三类仍由处理函数调用现有实现，它们的证据和检查原样保留。
- **核心原则（§2）**：
  1. **框架编排，模块实现**：框架决定“查什么、什么时候查、查不过就停”；每个具名定位器 / 守卫的实现由模块登记，实现直接调用现有函数（`objectContext`、`writeFields`、`button`、`requestScope`、`visibleCapacity` …）。错误码、错误文案、SQL 都出自同一段代码。
  2. **按“义务 × 执行阶段”登记（§2.6）**：声明里的每个名称都标明归 T1（引擎执行）、T2（列表 SQL 谓词）、T3（命令事务内 / 返回后复核）还是命令内前提。引擎只执行 T1 的；T2 / T3 的检查留在原位，证据也保持原来的调用点。
  3. **保序**：框架按固定的阶段顺序执行，这个顺序取自现有处理函数的主流写法；每条路由的输入解析放在现有代码解析它的位置。试点模块逐条核对后**零偏差**。
  4. **查询形态不变**：
     - 列表范围用显式的 `await access.getScope()`，在原 `await requestScope` 的位置、业务事务之前解析（§2.2）；
     - 点校验沿用现有的事务边界（独立事务，或与处理函数共用同一事务）。
  5. **错误原样传播**：引擎不在运行时比较、改写或记录任何错误。声明的拒绝码是否正确，只在测试里用授权拒绝样本核对（§2.3）。
- **试点：编制模块（16 个端点，§3）**。选择理由：
  - 端点数适中；
  - 授权写法是组织类公共辅助函数（`module-route-access.ts`）最纯的用法，这套写法直接或经各模块 `access.ts` 包装覆盖约半数端点；
  - 覆盖对象操作、按钮、写字段（含 `subdivisions` 展开）、列表 / 点 / 看全部（带数据集与创建人）/ 范围守卫、管理员能力、“本人 AND 对象”组合、CSV 出口；
  - 没有动态选择器、“或”组合、导入、跨模块联动，风险可控；
  - 23 个 `AC-EST-*` 验收测试文件作为回归网；PR-A 审定台账显示编制“差异 0”。
- **运行时行为（§4）**：
  - **按推荐方案，试点零变化**：授权结果、错误码与文案、响应字段、SQL 语句序列都不变。§4.1 列出零变化的判据与证明方法。
  - **会变化的地方逐条单列（§4.2），全部待用户确认**：
    - C-1：执行顺序改为 C2 统一顺序（Q-T1-1 ②）。已定清最小解析的边界，逐路由列出错误优先级、授权调用与失败记录的变化：12 条路由、6 类组合；
    - C-2：程序缺陷时的新失败方式（Q-T1-3）；
    - C-3：回滚期双重校验（Q-T1-4 ②）；
    - C-4：推广阶段已知的变化候选，按阶段逐路由列清后再确认，不整包预批准。
- **与 PR-B 的关系（§6）**：
  - 引擎骨架（T1-1）不依赖 PR-B，可以与 PR-B 并行；
  - 试点 Tier 1 与对拍语料（T1-0）依赖 PR-B 的 B4a / B4b / B5a；
  - 门禁接管模式（T1-2）依赖 B1 / B2 / **B6**；
  - 试点接管（T1-3）依赖上面三者与 **B6**：接管与回滚都必须在 `required/changes.ts` 登记，不设“B6 未合并”的兼容路径。
  - 文件归属表避免两边同时改同一文件。
- **验证与回滚（§5、§7）**：
  - 接管前冻结四样东西：
    - 编制 Tier 1 事实；
    - 编制 recorded 事实；
    - “接管对拍语料”：请求 → 规范化响应、库校验和、台账、SQL 语句序列、授权调用轨迹；
    - PR-A 静态基准的编制条目。
  - 接管后逐字节比对。
  - 回滚走**前向回滚 PR**：保留原登记，追加逆向变更登记，再恢复业务代码并重新生成生成件，能通过 PR-B 的只增登记门禁（§7）。
  - 不提供运行时开关：手写调用删除后再关掉引擎会 fail-open。
- **拆分（§8）**：试点 4 个 PR（T1-1 / T1-0 / T1-2 / T1-3）。每个以约 1500 行为**拆分目标**，不是已验证的估算，超出就再拆。推广分 7 个阶段，每阶段先出一页阶段设计和变化清单交用户确认。
- **口径（§9）**：Q-T1-1～Q-T1-8，均为**复刻系统**口径，不涉及北森测试租户。其中 Q-T1-1、Q-T1-3、Q-T1-4 改变运行时行为，**由用户定**；其余由总编排定。

## 1. 现状与 T1 的边界

### 1.1 现状（main d990e32；编制模块与 `route-policy/` 代码自 490881c 起未变）

- **387 个端点**都有现状声明，集中在各模块 `policy.ts`。`policed / policedSub` 代理按登记表注册；`createApp` 末尾的 `verifyRouteDeclarations` 实现“缺失即失败”。
- 包装函数 `routePolicyWrapper`（`route-policy/declare.ts`）只做两件事：
  - 自检：有效方法 HEAD → GET，`routePath` 与声明一致；
  - 原样调用处理函数。
- **声明不参与运行时判定**。授权全部由处理函数自己调用：
  - `objectContext / button / writeFields / requestScope / visible / readContext`；
  - 各模块的 `access.ts`、`context.ts`；
  - 审批 `access.ts` 等。
- 声明的真实性由两道门禁保证：
  - 显式必需表（`required/*.ts`，人工逐条审定）硬比对声明；
  - 静态基准（`observed-contract.json`）由 AST 扫描**处理函数闭包**得到，第二道比较要求声明“不弱于”它。
  - 两道门禁的证据都锚定在处理函数里的调用点上（evidence 的 `call` 角色、scan 的闭包原语）。

### 1.2 T1 的边界

| 归 T1 | 不归 T1（保持现状调用） |
|---|---|
| 身份前置：成员 / 平台 / 公开（现由中间件做，T1 只在引擎里核对一致） | 列表 / 计数 / 聚合的范围过滤 SQL（T2，QuerySpec） |
| 功能权限：对象 × 操作、管理员能力（含 `tenant.*` 别名） | 命令事务内复核、重放前复核、返回后复核（T3，`write.footprint / result`） |
| 写字段：按 `write.fields` 提取后 `requireObjectWrite` | 命令内业务前提（`preconditions`，永远留在命令内） |
| 按钮 | 出口字段裁剪、CSV 列过滤（T4） |
| 范围：点校验、看全部、具名范围守卫、列表范围的**解析**（不含 SQL 拼接） | 失败导入日志包装（推广阶段 1 再定，Q-T1-7） |
| 关系、本人绑定（推广阶段引入，试点不涉及） | 统一范围 helper 与绕开检查（DEC-317②，DEC-359 定为转 T2） |

上表是按能力的粗分。同一个声明名称可能横跨两个阶段：例如复制任务的来源编制校验，命令前一次、命令事务内又一次。所以落到每个名称、每处检查时，以 §2.6 的“义务 × 执行阶段”登记为准。

**“现状已有保证”与“计划新增保证”分开**（PR-A 设计 §10.7 提醒 1）：

- T1 只接管**现状已经在执行**的准入判定。
- 声明里登记的、现状并不存在的守卫名，T1 不执行，也不当作已执行：
  - 如 `config.audited:*`、`permission.adminCommand`，属于 T3 计划新增；
  - 引擎对 `write.footprint / result` 一律不读。
- 试点中编制两处写足迹的情况：
  - `establishment.replay` 是现状已有的复核（`job/context.runWrite` 内 `authorizeEstablishmentReplay`），T1 不动它，留在 `runWrite` 里；
  - `config.audited:establishment_settings` 是计划新增，T1 不执行。

## 2. 执行模型

### 2.1 阶段顺序（“保序主序”）

一次请求在包装函数里的执行顺序（`route-policy/enforce.ts`）。S0 为现有中间件，不变：

```
S0  tenantContext / platformContext → captureCommandFailures（现有中间件，不变）
    包装自检：HEAD → GET、routePath 与声明一致（PR-A，不变）
    以下只对“已接管模块”的路由执行；其余路由原样调用处理函数（PR-A 行为）
S1  写请求的 If-Match 格式（现有 revision(c)：现状在所有判定之前求值）
S2  功能权限：object.<operation>（复用 objectContext，fields: []）或 admin 能力（复用 readContext）
    动态选择器的最小解析放在 S2 之前（推广阶段 1 引入，试点无）
S3  授权所需输入的解析：路径标识、授权要用到的请求体 / 查询参数（按路由登记的输入规格，用现有 zod schema 与 uuidParam）
S4  写字段：按 write.fields 提取 → 复用 writeFields（requireObjectWrite）
S5  按钮：复用 button()
S6  范围（只执行 §2.6 登记为 T1 的名称；登记为 T2 / T3 / 命令内的名称引擎不执行，留在处理函数原位）：
    - list：引擎不解析；处理函数在原 `await requestScope` 的位置调用 `await access.getScope()`（§2.2）
    - point / see-all / guard：引擎先解析范围（事务外，与现状 `await requestScope` 同位），再调用模块登记的实现，按登记的事务方式执行（§2.4）
S7  处理函数(c, access)：业务校验、命令执行（runWrite 内的事务内复核照旧）、列表 SQL（照旧用 scopeSql）、出口裁剪（照旧）
S8  响应前核对：登记为“共用事务”的点校验必须已执行并通过，否则丢弃响应、500 ROUTE_POLICY_UNCHECKED（§2.4）
```

- **为什么不是 C2 顺序**：PR-A 设计 §7 C2 定的接管顺序是“最小安全解析 → 鉴权 → 业务校验”，并注明“审查可否决”。按 C2 执行，试点会出现 §4.2 列出的错误码变化。
  - 保序主序是现状主流写法的抽象：`objectContext → 解析 → writeFields → button → 范围`。
  - 编制 16 条路由逐条核对零偏差（§3.2）。
  - 选哪种顺序由用户定（Q-T1-1）。
- **推广阶段遇到偏离主序的路由**：在阶段设计里逐条列出，并逐条给出两个选项交用户确认：
  - 把该路由的偏离登记为“输入阶段标记”，保持零变化；
  - 或改为主序，列为行为变化。
  - 不允许按路由随意排序：阶段顺序是全局常量，路由只能声明自己的输入在哪个阶段解析。

### 2.2 `access` 对象（T1 版）

处理函数签名从 `(c) => …` 改为 `(c, access) => …`，仅限已接管模块。字段如下：

| 字段 | 含义 | 来源 |
|---|---|---|
| `access.ctx` | `ScopeBusinessContext`：租户、用户、时区、`expectedRevision`、`now`、`commandId: ''` | S1 + S2（与 `objectContext / readContext` 返回值相同） |
| `access.input` | S3 解析结果：`{ params, query, body }`，只含登记过的输入 | S3 |
| `access.getScope()` | **异步**：返回本请求的 `ModuleScope`，内部仍是 `requestScope(c, deps, ctx, object, view)`，同一请求只解析一次（沿用现有缓存）。列表路由由处理函数在原位置调用；点校验路由由引擎在 S6 先调用，处理函数再取到的是同一对象 | 处理函数（list）/ S6（其余） |
| `access.point` | 点校验返回的记录（定位器返回值，如 `visibleCapacity` 的 `CapacityRecord`） | S6 |
| `access.inScopedTx(fn)` | “共用事务”方式：引擎开 `withTenant`，**先**执行点校验，再在同一事务里调用 `fn(tx, record)` | S6 / S8 |

**不提供 `listQuery / command / project / csv` 直通适配器**（对 PR-A 设计 §10.7 提醒 2 的回答）：

- T2 的 `listQuery(tx, spec)` 要求处理函数交出 QuerySpec，T3 的 `command` 要求声明足迹钩子，T4 的投影要求形状登记。
- 它们的签名都与现有 `scopeSql / runWrite / trim*` 不同。
- 如果 T1 先包一层同签名的直通适配器，T2～T4 仍要再改一遍处理函数，等于多改一次、多一层没有语义的抽象。

因此 T1 期间，处理函数继续**直接**调用现有实现，只把参数换成 `access` 提供的值。适配器清单与替换顺序如下：

| 能力 | T1 期间的实现 | 由谁替换 | 替换时机 |
|---|---|---|---|
| 列表范围过滤 | 处理函数在原 `await requestScope` 处改为 `const scope = await access.getScope()`，之后照旧 `withTenant(…, tx => …scopeSql(scope, …))` | T2：`access.listQuery(tx, spec)` + `ROUTE_POLICY_UNSCOPED` | 该模块 T2 PR |
| 命令执行与事务内复核 | 处理函数照旧 `runWrite(…, execute, OBJECT)`；`execute` 内的 `checkScheme` 等复核照旧，范围取命令前已拿到的 `scope` 变量（来自 `await access.getScope()`） | T3：`access.command` + 足迹钩子 | 该模块 T3 PR |
| 出口裁剪 | 照旧 `trimModuleResponse / trimCapacities / readCopyJobReport(fields)` | T4：投影器 + 出口兜底 | 该模块 T4 PR（DEC-291 Q3 修订的时机） |

**`getScope()` 的位置规则（防止列表请求阻塞）**：

- 现有三个列表路由（方案、编制、通知）都是先 `await requestScope`，再开业务事务。
- 真实授权器解析范围时会另开事务。如果在业务事务里第一次解析，就会出现：外层事务等范围，范围等外层释放连接。PGlite 只有一个连接，审查的最小模型 1 秒超时。
- 因此规定：
  - `getScope()` 必须是显式 `await` 的异步调用，不提供同步属性，不做“首次读取时解析”；
  - 已接管模块的处理函数里，`getScope()` 只能出现在 `withTenant` / `runWrite` 回调**之外**。由退役检查（§5.3）用 AST 断言：调用点不在任何 `withTenant(`、`runWrite(` 实参函数体内。
- 事务内复核需要范围时，使用事务外已取得的 `scope` 变量（现状写法相同）。
- 引擎反例测试（T1-1）用真实授权器 + PGlite 跑一个列表夹具：按规定位置调用能完成；在事务内调用会被 AST 断言拦下。

### 2.3 实现登记：框架编排、模块实现

- 每个已接管模块新增 `<模块>/access-impl.ts`，用 `defineImplementations(module, { locators, guards, seeAll, inputs })` 登记。
  - 键 = 声明里的具名定位器 / 守卫 / 看全部定位器 / 输入规格名；
  - 值 = 调用现有函数的薄封装。
  - 例：`'establishment.capacity.byId': (tx, access) => visibleCapacity(tx, access.ctx, scope, id, asOf)`。
- **启动期校验**：在 `verifyRouteDeclarations` 里执行，失败码 `ROUTE_POLICY_IMPL_MISSING`。任一项不满足，应用都无法启动（fail-closed，硬规则 1）：
  - 已接管模块的声明里出现的每个名称，都必须在 §2.6 的阶段登记里**有归类**：
    - 归 T1 的必须有登记实现；
    - 归 T2 / T3 / 命令内的，只需登记阶段，不要实现，引擎也不执行。
  - 每条路由用到的 T1 输入都必须有输入规格。
- **运行时不做拒绝码自检**：
  - 实现抛出的任何错误都原样传播，引擎不比较、不改写、不额外记日志。这些错误包括：授权拒绝、输入校验错误（如定位器内解析 `asOf` 得到的 400）、业务错误、存储错误。
  - v1 的运行时自检会把复制任务四条路由的 `?asOf=bad`（400 `VALIDATION_FAILED`）误判成与声明的 404 不符（审查 P2-3），v2 删除。
- **声明拒绝码的核对放在测试里**：由 PR-B B-09 的 `MISMATCH:denial` 做，只取**授权拒绝样本**（范围外、不存在、缺权），不拿输入错误的样本比较。T1-0 冻结编制的这些事实，T1-3 接管后逐字节比对（§5）。
- **复用而非重写**：
  - 引擎本身不含任何对象编码、按钮编码、范围算法；
  - S2 / S4 / S5 直接调用 `objectContext / readContext / writeFields / button`，S6 调用登记实现；
  - 因此 `requirePermission` 的错误文案（“无权执行该操作”）、`visible` 的 404 文案（“编制在该时点不存在” 等）、授权器调用参数都不变。

### 2.4 范围点校验的事务方式（查询形态不变的关键）

现有代码里点校验有两种事务边界。T1 按路由登记，保持原样：

| 方式 | 现状写法 | 引擎行为 | 编制路由 |
|---|---|---|---|
| `own`（独立事务） | 处理函数先 `withTenant(db, tid, tx => checkX(tx…))`，再做别的 | S6 开 `withTenant` 调用登记实现，返回记录放进 `access.point` | schemes/:id GET、PATCH、DELETE；capacities/:id GET、PATCH；copy-jobs POST、:id GET、:id/execute |
| `shared`（共用事务） | 同一个 `withTenant` 里先校验再读别的数据 | 处理函数调用 `access.inScopedTx(fn)`：引擎开事务，先执行登记实现，再执行 `fn`。S8 核对确实调用过，否则 500 `ROUTE_POLICY_UNCHECKED`（测试环境抛错），响应丢弃 | copy-jobs/:id/report（`visibleCopyJob` 与 `readCopyJobReport` 同事务） |
| 无事务 | 纯内存判定（`visible(scope, input.orgId)`） | S6 直接调用 | schemes POST（看全部 / 创建人）、capacities POST（`body.orgId`） |

- 三种方式下，范围都由引擎在 S6 **先**在事务外 `getScope()` 解析，再进入点校验事务。这与现状“先 `await requestScope`，后 `withTenant`”一致，不会出现 §2.2 的连接等待。
- 引擎只执行 §2.6 登记为 T1 的命令前检查。PATCH / DELETE / copy-jobs / execute 在 `runWrite` 事务内的复核属于 T3，仍由处理函数原位执行。
- 三个详情 GET 的现有事务里只有校验函数本身（`visibleScheme / visibleCapacity / visibleCopyJob` 同时完成加载），所以 `own` 方式的语句序列与现状完全相同。
- `shared` 方式的局限：引擎能保证校验在 `fn` 之前、在同一事务里执行，但不能证明响应只来自 `fn` 读到的数据。
  - 这与 T2 的第 3 轮 P2-3 残留同类（执行过受限查询不等于响应来自它）。
  - 试点只有 1 条路由用到，由 S8 核对 + 退役检查（§5.3）+ 对拍语料兜底；T2 设计统一解决。

### 2.5 已接管模块的登记与退役

- **唯一来源**：`route-policy/takeover.ts` 导出常量 `TAKEN_OVER_MODULES`（试点前为空数组）。
  - 引擎只对其中模块的路由执行 S1～S8；
  - 门禁接管模式（§5.3）也只读这个常量。
- **同一 PR 内完成接管和退役**：模块加入 `TAKEN_OVER_MODULES` 的 PR，同时删除该模块路由文件里的手写准入调用。
  - 退役检查是一个 AST 测试，规则按 §2.6 的阶段区分：
    - 已接管模块的路由文件里，**命令前**（`runWrite` / `withTenant` 回调之外）不得调用 `objectContext / readContext / button / writeFields / requestScope / visible / requirePermission`；
    - `runWrite` 的 `execute` 回调里，只允许调用 §2.6 登记为 T3 的复核（如 `checkScheme`、`orgIdInScope` 的 `visible`）；
    - T2 谓词（如通知的本人谓词）在查询函数里，不受影响；
    - `getScope()` 只能出现在事务回调之外（§2.2）。
  - 检查不过，CI 失败。
- **不提供运行时开关**（详见 §7、Q-T1-4）：手写调用删除后，把模块切回“不接管”就等于没有任何准入判定（fail-open）。

### 2.6 义务 × 执行阶段登记（T1 / T2 / T3 / 命令内）

**为什么需要**：声明的 `guards`、范围守卫、谓词里混着不同阶段执行的检查。v1 把它们一律当作 T1，有两个后果（审查 P2-1）：

- **错误优先级会变**：例如 `establishment.orgIdInScope` 现状只在命令事务内检查（`routes.ts` PATCH capacities 的 `runWrite` 回调）。提前到 S6，会把“缺 Idempotency-Key 的 400 `IDEMPOTENCY_KEY_REQUIRED`”变成“范围外 404”。
- **启动校验与证据规则会自相矛盾**：不给它登记实现，启动完整性检查就失败；把它的证据改成 `enforced`，又与它仍在处理函数里执行的事实不符。

**登记方式**：每个已接管模块的 `access-impl.ts` 用 `defineImplementations(module, { t1: { … }, deferred: { 名称: 阶段 } })` 声明全部名称的阶段。

| 阶段 | 含义 | 谁执行 | 证据（§5.3） |
|---|---|---|---|
| `T1` | 命令前的准入判定 | 引擎 S2～S6，调用登记实现 | `enforced`（引擎阶段单元）+ `impl`（登记实现及其调用的现有函数）+ `const` |
| `T2` | 列表 / 计数 SQL 里的范围或本人谓词 | 处理函数 / 查询函数，原位不动 | 保持 `call` + `impl`，锚点不变或随重构更新 |
| `T3` | 命令事务内复核、重放前复核、返回后复核 | `runWrite` 及其 `execute` 回调，原位不动 | 保持 `call` + `impl` |
| `命令内` | `write.preconditions` | 命令内，永远不搬 | 不在显式表的准入证据里（PR-A 现状） |

同一个名称可以**同时**有 T1 与 T3 两处执行，例如来源编制校验命令前一次、事务内一次。这种情况在表里登记两条，分别对应各自的证据：T1 那条改为 `enforced`，T3 那条保留 `call`。

| 名称 / 义务 | 所在路由（§3.2 编号） | 阶段 | 说明 |
|---|---|---|---|

**门禁**（§5.3）按阶段核对证据：

- T1 义务不得再有处理函数命令前的 `call` 锚点；
- T2 / T3 义务必须仍有处理函数或查询函数里的真实 `call` 锚点，否则报 `DEFERRED_WITHOUT_CALL`，防止“登记成 T3、实际被删掉”。

  - 若引擎在 S6 提前解析，asOf 非法时会多出范围解析的查询；
  - 若推迟到业务事务里首次解析，会出现连接等待（§2.2）。
  - 所以由处理函数在原 `await requestScope` 的那一行调用 `await access.getScope()`。
- **asOf 的解析位置按路由区分**：
  - 路由 12～15 的 asOf 在 `visibleCapacity / visibleCopyJob` 的实参里，在事务回调内、按钮之后才求值。登记实现照抄这段代码，`queryDate` 仍在同一位置；它抛出的 400 原样传播（§2.3），不参与任何拒绝码比较；
  - 路由 2 / 7 在 S3，与现状一致。
- **两个 PATCH 的 `effectiveDate` 与保留键**：
  - `effectiveDate` 现状会作为字段交给 `requireObjectWrite`（`writeFields` 只去掉 `expectedRevision / confirmed / reservationId`）；
  - 引擎复用 `writeFields`，行为相同。T1 不修正这一点；如需修正，另立问题。

#### C-2　新增程序缺陷类失败方式（Q-T1-3）

#### C-3　回滚期双重校验（仅当 Q-T1-4 选②）

保留手写校验一个发布周期，引擎与处理函数各校验一次：

- **授权器调用翻倍**：`objectContext`、`writeFields`、`button` 各两次。
- **点校验查询翻倍**：定位器的 SQL 执行两次。
- **范围解析不翻倍**：同一请求有 `requestScope` 缓存。
- **错误结果可能不同**：两次授权之间权限被撤销时，第一次通过、第二次 403。现状只校验一次，这种并发下会通过。
- 选 ② 时，需要按上述四项另列一份完整变化清单，逐路由给出多出的调用与查询，再交确认。

推荐 ①：不保留双重校验，回滚走 §7 的前向回滚 PR。

- `enforced` 角色指向的是引擎实现单元，不是 `policy.ts`；
- 声明的内容由显式表硬比对，不需要锚点。

**回滚门禁的正反例**（T1-2 用夹具模块提供）：

## 7. 回滚方案

**原则**：接管 PR 会向 `required/changes.ts` 追加登记，而 PR-B B-11 规定删除已有登记报 `CHANGES_REMOVED`。所以回滚不能直接 `git revert`，要走**前向回滚 PR**。

### 7.1 回滚一个已接管模块（如编制）

1. 从最新 main 开回滚分支，用 `git revert --no-commit <接管 PR 的合并提交>` 恢复业务代码，内容包括：
   - 处理函数里的手写调用；
   - `routes.ts` 内的 `visible*` / `check*` 函数；
   - 内联 schema；
   - 把模块移出 `TAKEN_OVER_MODULES`。
2. **保留原登记**：把 `required/changes.ts` 恢复为 main 上的版本，不删除接管时追加的任何条目。
3. **追加逆向登记**：接管时登记过的每一项，追加一条逆向变更。项目包括证据角色 `enforced → call`、定位器改名、基准从“冻结 ∪ 当前”回到“当前扫描”。每条写明项键、前后摘要、理由（“回滚 T1-3：<原因>”）、PR 号。
4. **更新生成件**：用 `ROUTE_POLICY_UPDATE_DIGESTS=1`、`ROUTE_POLICY_UPDATE_BASELINE=1` 重新生成摘要与基准。
5. **核对后删除 pre 文件**：测试断言该模块重新扫描的基准条目 = `baseline/takeover/<模块>.pre.json`，证明手写调用完整恢复。然后删除该 pre 文件，删除也在 `changes.ts` 登记。
6. Tier 1、recorded、对拍语料、`AC-EST-*` 不改，必须全绿；回滚 PR 的门禁正例见 §5.3。
7. 无迁移、无数据结构变化，不需要数据回滚。

### 7.2 其他场景

| 场景 | 做法 |
|---|---|
| 引擎骨架（T1-1）有缺陷，**尚无模块接管** | 未接管模块不走引擎，可以直接 revert T1-1；此时 `changes.ts` 里没有接管登记，不冲突 |
| 引擎骨架有缺陷，**已有模块接管** | 优先就地修复引擎（前向修复）。确需撤掉引擎时，先按 §7.1 逐个回滚全部已接管模块，`TAKEN_OVER_MODULES` 清空后，才能 revert 或停用引擎。顺序不能颠倒：已接管模块的处理函数没有手写校验，先撤引擎就是 fail-open |
| 希望不发版就“关掉接管” | **不提供**：手写调用已删，关掉引擎等于没有准入判定（fail-open，违反硬规则 1）。若要求热切换，只能选 Q-T1-4 ②（保留双重校验一个周期，代价见 C-3，需另列完整变化清单） |
| 推广阶段 | 每个模块一个接管 PR，各自按 §7.1 独立回滚；模块之间没有依赖 |
