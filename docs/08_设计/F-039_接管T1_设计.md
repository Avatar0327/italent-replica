## 0. 一页摘要

- **T1 要做的事**：把每条路由的**准入判定**（功能 / 管理员能力、写字段、按钮、范围点校验 / 看全部 / 范围守卫、本人身份）从处理函数里搬到框架：框架在调用处理函数之前，按声明执行这些判定；处理函数里对应的手写调用删除，并用测试禁止再写回去。
  - **不在 T1**：列表查询的范围过滤改写（T2，QuerySpec）、命令事务内复核与返回后复核（T3）、出口字段裁剪（T4）。T1 期间这三类仍由处理函数调用现有实现。
- **核心原则（§2）**：
  1. **框架编排，模块实现**：框架决定“查什么、什么时候查、查不过就停”；每个具名定位器 / 守卫的实现由模块登记，实现直接调用现有函数（`objectContext`、`writeFields`、`button`、`requestScope`、`visibleCapacity` …）。错误码、错误文案、SQL 都出自同一段代码。
  2. **保序**：框架按固定的阶段顺序执行，这个顺序取自现有处理函数的主流写法；每条路由的输入解析放在现有代码解析它的位置。试点模块逐条核对后**零偏差**。
  3. **查询形态不变**：列表范围按需解析（与现有 `requestScope` 缓存同语义）；点校验沿用现有的事务边界（独立事务，或与处理函数共用同一事务）。
- **试点：编制模块（16 个端点，§3）**。选择理由：
  - 端点数适中；
  - 授权写法是组织类公共辅助函数（`module-route-access.ts`）最纯的用法，这套写法直接或经各模块 `access.ts` 包装覆盖约半数端点；
  - 覆盖对象操作、按钮、写字段（含 `subdivisions` 展开）、列表 / 点 / 看全部（带数据集与创建人）/ 范围守卫、管理员能力、“本人 AND 对象”组合、CSV 出口；
  - 没有动态选择器、“或”组合、导入、跨模块联动，风险可控；
  - 23 个 `AC-EST-*` 验收测试文件作为回归网；PR-A 审定台账显示编制“差异 0”。
- **运行时行为（§4）**：
  - **按推荐方案，试点零变化**：授权结果、错误码与文案、响应字段、SQL 语句序列都不变。§4.1 列出零变化的判据与证明方法。
  - **会变化的地方逐条单列（§4.2），全部待用户确认**：执行顺序改为 C2 统一顺序（Q-T1-1 ②，试点有 4 类、13 条路由的错误码变化）、程序缺陷时的新 500 错误码（Q-T1-3）、回滚期双重校验的额外查询（Q-T1-4 ②）。另列推广阶段已知的变化候选，按阶段再交用户确认。
- **与 PR-B 的关系（§6）**：
  - 引擎骨架（T1-1）不依赖 PR-B，可以与 PR-B 并行；
  - 试点 Tier 1 与对拍语料（T1-0）依赖 PR-B 的探测框架（B4a / B4b / B5a）；
  - 门禁接管模式（T1-2）依赖 B1 / B2；
  - 试点接管（T1-3）依赖上面三者。
  - 文件归属表避免两边同时改同一文件。
- **验证与回滚（§5、§7）**：
  - 接管前冻结三样东西：编制 Tier 1 事实、“接管对拍语料”（请求 → 规范化响应、库校验和、台账、SQL 语句序列、授权调用轨迹）、PR-A 静态基准的编制条目；
  - 接管后逐字节比对；
  - 回滚 = revert 接管 PR（无迁移、无数据变化）；不提供运行时开关（会 fail-open，§7）。
- **拆分（§8）**：试点 4 个 PR（T1-0 / T1-1 / T1-2 / T1-3，每个约 900～1500 行，不含生成文件）；推广分 7 个阶段，每阶段先出一页阶段设计和变化清单交用户确认。
- **口径（§9）**：Q-T1-1～Q-T1-8，均为**复刻系统**口径，不涉及北森测试租户。其中 Q-T1-1、Q-T1-3、Q-T1-4 改变运行时行为，**由用户定**；其余由总编排定。

## 1. 现状与 T1 的边界

### 1.1 现状（main 490881c）

- **387 个端点**都有现状声明，集中在各模块 `policy.ts`。`policed / policedSub` 代理按登记表注册；`createApp` 末尾的 `verifyRouteDeclarations` 实现“缺失即失败”。
- 包装函数 `routePolicyWrapper`（`route-policy/declare.ts`）只做两件事：
  - 自检：有效方法 HEAD → GET，`routePath` 与声明一致；
  - 原样调用处理函数。
- **声明不参与运行时判定**。授权全部由处理函数自己调用：
  - `objectContext / button / writeFields / requestScope / visible / readContext`；
  - 各模块的 `access.ts`、`context.ts`；
  - 审批 `access.ts` 等。
- 声明的真实性由两道门禁保证：
  - 显式必需表（`required/*.ts`，人工逐条审定）硬比对声明；
  - 静态基准（`observed-contract.json`）由 AST 扫描**处理函数闭包**得到，第二道比较要求声明“不弱于”它。
  - 两道门禁的证据都锚定在处理函数里的调用点上（evidence 的 `call` 角色、scan 的闭包原语）。

### 1.2 T1 的边界

| 归 T1 | 不归 T1（保持现状调用） |
|---|---|
| 身份前置：成员 / 平台 / 公开（现由中间件做，T1 只在引擎里核对一致） | 列表 / 计数 / 聚合的范围过滤 SQL（T2，QuerySpec） |
| 功能权限：对象 × 操作、管理员能力（含 `tenant.*` 别名） | 命令事务内复核、重放前复核、返回后复核（T3，`write.footprint / result`） |
| 写字段：按 `write.fields` 提取后 `requireObjectWrite` | 命令内业务前提（`preconditions`，永远留在命令内） |
| 按钮 | 出口字段裁剪、CSV 列过滤（T4） |
| 范围：点校验、看全部、具名范围守卫、列表范围的**解析**（不含 SQL 拼接） | 失败导入日志包装（推广阶段 1 再定，Q-T1-7） |
| 关系、本人绑定（推广阶段引入，试点不涉及） | 统一范围 helper 与绕开检查（DEC-317②，转 T2，PR-B Q-B7） |

**“现状已有保证”与“计划新增保证”分开**（PR-A 设计 §10.7 提醒 1）：

- T1 只接管**现状已经在执行**的准入判定。
- 声明里登记的、现状并不存在的守卫名，T1 不执行，也不当作已执行：
  - 如 `config.audited:*`、`permission.adminCommand`，属于 T3 计划新增；
  - 引擎对 `write.footprint / result` 一律不读。
- 试点中编制两处写足迹的情况：
  - `establishment.replay` 是现状已有的复核（`job/context.runWrite` 内 `authorizeEstablishmentReplay`），T1 不动它，留在 `runWrite` 里；
  - `config.audited:establishment_settings` 是计划新增，T1 不执行。

## 2. 执行模型

### 2.1 阶段顺序（“保序主序”）

一次请求在包装函数里的执行顺序（`route-policy/enforce.ts`）。S0 为现有中间件，不变：

```
S0  tenantContext / platformContext → captureCommandFailures（现有中间件，不变）
    包装自检：HEAD → GET、routePath 与声明一致（PR-A，不变）
    以下只对“已接管模块”的路由执行；其余路由原样调用处理函数（PR-A 行为）
S1  写请求的 If-Match 格式（现有 revision(c)：现状在所有判定之前求值）
S2  功能权限：object.<operation>（复用 objectContext，fields: []）或 admin 能力（复用 readContext）
    动态选择器的最小解析放在 S2 之前（推广阶段 1 引入，试点无）
S3  授权所需输入的解析：路径标识、授权要用到的请求体 / 查询参数（按路由登记的输入规格，用现有 zod schema 与 uuidParam）
S4  写字段：按 write.fields 提取 → 复用 writeFields（requireObjectWrite）
S5  按钮：复用 button()
S6  范围：
    - list：不在此处解析；处理函数首次读取 access.scope 时才解析（与现有 requestScope 同一缓存、同一时机）
    - point / see-all / guard：调用模块登记的实现，按登记的事务方式执行（§2.4）
S7  处理函数(c, access)：业务校验、命令执行（runWrite 内的事务内复核照旧）、列表 SQL（照旧用 scopeSql）、出口裁剪（照旧）
S8  响应前核对：登记为“共用事务”的点校验必须已执行并通过，否则丢弃响应、500 ROUTE_POLICY_UNCHECKED（§2.4）
```

- **为什么不是 C2 顺序**：PR-A 设计 §7 C2 定的接管顺序是“最小安全解析 → 鉴权 → 业务校验”，并注明“审查可否决”。按 C2 执行，试点会出现 §4.2 列出的错误码变化。
  - 保序主序是现状主流写法的抽象：`objectContext → 解析 → writeFields → button → 范围`。
  - 编制 16 条路由逐条核对零偏差（§3.2）。
  - 选哪种顺序由用户定（Q-T1-1）。
- **推广阶段遇到偏离主序的路由**：在阶段设计里逐条列出，并逐条给出两个选项交用户确认：
  - 把该路由的偏离登记为“输入阶段标记”，保持零变化；
  - 或改为主序，列为行为变化。
  - 不允许按路由随意排序：阶段顺序是全局常量，路由只能声明自己的输入在哪个阶段解析。

### 2.2 `access` 对象（T1 版）

处理函数签名从 `(c) => …` 改为 `(c, access) => …`，仅限已接管模块。字段如下：

| 字段 | 含义 | 来源 |
|---|---|---|
| `access.ctx` | `ScopeBusinessContext`：租户、用户、时区、`expectedRevision`、`now`、`commandId: ''` | S1 + S2（与 `objectContext / readContext` 返回值相同） |
| `access.input` | S3 解析结果：`{ params, query, body }`，只含登记过的输入 | S3 |
| `access.scope` | 列表范围：首次读取时解析，内部仍是 `requestScope(c, deps, ctx, object, view)` | S6（惰性） |
| `access.point` | 点校验返回的记录（定位器返回值，如 `visibleCapacity` 的 `CapacityRecord`） | S6 |
| `access.inScopedTx(fn)` | “共用事务”方式：引擎开 `withTenant`，**先**执行点校验，再在同一事务里调用 `fn(tx, record)` | S6 / S8 |

**不提供 `listQuery / command / project / csv` 直通适配器**（对 PR-A 设计 §10.7 提醒 2 的回答）：

- T2 的 `listQuery(tx, spec)` 要求处理函数交出 QuerySpec，T3 的 `command` 要求声明足迹钩子，T4 的投影要求形状登记。
- 它们的签名都与现有 `scopeSql / runWrite / trim*` 不同。
- 如果 T1 先包一层同签名的直通适配器，T2～T4 仍要再改一遍处理函数，等于多改一次、多一层没有语义的抽象。

因此 T1 期间，处理函数继续**直接**调用现有实现，只把参数换成 `access` 提供的值。适配器清单与替换顺序如下：

| 能力 | T1 期间的实现 | 由谁替换 | 替换时机 |
|---|---|---|---|
| 列表范围过滤 | 处理函数照旧 `scopeSql(access.scope, …)` | T2：`access.listQuery(tx, spec)` + `ROUTE_POLICY_UNSCOPED` | 该模块 T2 PR |
| 命令执行与事务内复核 | 处理函数照旧 `runWrite(…, execute, OBJECT)`；`execute` 内的 `checkScheme` 等复核照旧，范围取 `access.scope` | T3：`access.command` + 足迹钩子 | 该模块 T3 PR |
| 出口裁剪 | 照旧 `trimModuleResponse / trimCapacities / readCopyJobReport(fields)` | T4：投影器 + 出口兜底 | 该模块 T4 PR（DEC-291 Q3 修订的时机） |

### 2.3 实现登记：框架编排、模块实现

- 每个已接管模块新增 `<模块>/access-impl.ts`，用 `defineImplementations(module, { locators, guards, seeAll, inputs })` 登记。
  - 键 = 声明里的具名定位器 / 守卫 / 看全部定位器 / 输入规格名；
  - 值 = 调用现有函数的薄封装。
  - 例：`'establishment.capacity.byId': (tx, access) => visibleCapacity(tx, access.ctx, scope, id, asOf)`。
- **启动期校验**：在 `verifyRouteDeclarations` 里执行，缺任一项都会让应用无法启动（fail-closed，硬规则 1），失败码 `ROUTE_POLICY_IMPL_MISSING`：
  - 已接管模块的声明里出现的每个名称，都必须有登记实现；
  - 每条路由用到的输入都必须有输入规格。
- **拒绝码自检**：实现抛出的 `AppError` 与声明的 `denied`（status + code）比对。
  - 测试环境不一致即抛错，作为声明错误的又一道检查；
  - 生产环境照原样返回模块抛出的错误（零变化），并写结构化日志 `route_policy_denial_mismatch`。
  - 只记日志、不改响应。
- **复用而非重写**：
  - 引擎本身不含任何对象编码、按钮编码、范围算法；
  - S2 / S4 / S5 直接调用 `objectContext / readContext / writeFields / button`，S6 调用登记实现；
  - 因此 `requirePermission` 的错误文案（“无权执行该操作”）、`visible` 的 404 文案（“编制在该时点不存在” 等）、授权器调用参数都不变。

### 2.4 范围点校验的事务方式（查询形态不变的关键）

现有代码里点校验有两种事务边界。T1 按路由登记，保持原样：

| 方式 | 现状写法 | 引擎行为 | 编制路由 |
|---|---|---|---|
| `own`（独立事务） | 处理函数先 `withTenant(db, tid, tx => checkX(tx…))`，再做别的 | S6 开 `withTenant` 调用登记实现，返回记录放进 `access.point` | schemes/:id GET、PATCH、DELETE；capacities/:id GET、PATCH；copy-jobs POST、:id GET、:id/execute |
| `shared`（共用事务） | 同一个 `withTenant` 里先校验再读别的数据 | 处理函数调用 `access.inScopedTx(fn)`：引擎开事务，先执行登记实现，再执行 `fn`。S8 核对确实调用过，否则 500 `ROUTE_POLICY_UNCHECKED`（测试环境抛错），响应丢弃 | copy-jobs/:id/report（`visibleCopyJob` 与 `readCopyJobReport` 同事务） |
| 无事务 | 纯内存判定（`visible(scope, input.orgId)`） | S6 直接调用 | schemes POST（看全部 / 创建人）、capacities POST（`body.orgId`） |

- 三个详情 GET 的现有事务里只有校验函数本身（`visibleScheme / visibleCapacity / visibleCopyJob` 同时完成加载），所以 `own` 方式的语句序列与现状完全相同。
- `shared` 方式的局限：引擎能保证校验在 `fn` 之前、在同一事务里执行，但不能证明响应只来自 `fn` 读到的数据。
  - 这与 T2 的第 3 轮 P2-3 残留同类（执行过受限查询不等于响应来自它）。
  - 试点只有 1 条路由用到，由 S8 核对 + 退役检查（§5.3）+ 对拍语料兜底；T2 设计统一解决。

### 2.5 已接管模块的登记与退役

- **唯一来源**：`route-policy/takeover.ts` 导出常量 `TAKEN_OVER_MODULES`（试点前为空数组）。
  - 引擎只对其中模块的路由执行 S1～S8；
  - 门禁接管模式（§5.3）也只读这个常量。
- **同一 PR 内完成接管和退役**：模块加入 `TAKEN_OVER_MODULES` 的 PR，同时删除该模块路由文件里的手写准入调用。
  - 退役检查是一个 AST 测试：已接管模块的路由文件不得调用 `objectContext / readContext / button / writeFields / requestScope / visible / requirePermission`，这些调用只允许出现在 `access-impl.ts` 与 `runWrite` 的事务内复核里。
  - 检查不过，CI 失败。
- **不提供运行时开关**（详见 §7、Q-T1-4）：手写调用删除后，把模块切回“不接管”就等于没有任何准入判定（fail-open）。

## 3. 试点：编制模块

### 3.1 选择标准与候选比较

| 标准 | 编制（选定） | 职务 | 组织 | 租户设置 + 审计 | 人员 |
|---|---|---|---|---|---|
| 端点数（适中 = 10～20） | 16 | 14 | 14 | 3 + 4 | 18 |

### 4.2 会变化的部分（逐条单列，**待用户确认后才实现**）

#### C-1　执行顺序改为 C2 统一顺序（仅当 Q-T1-1 选②）

C2 = “最小安全解析（路径 / 查询标识、If-Match、请求体是 JSON 对象）→ 功能 / 写字段 / 按钮 / 范围 → 业务校验（zod）”。在编制模块会出现以下变化：

| 编号 | 变化 | 条件（谁、做什么） | 现状 → 改后 | 涉及路由（§3.2 编号） |
|---|---|---|---|---|
| C-1a | 标识非法先于功能权限 | 没有编制查看 / 操作权的用户，带非法 `:id`、非法 asOf 或非法 page 请求 | 403 FORBIDDEN → 400 VALIDATION_FAILED | 2、4、5、7、9、13、14、15（路径 id）；若 asOf / page 也归入最小解析，另加 1、2、6、7、13、15 |
| C-1b | 未知字段由“请求非法”改为“无权写” | 有操作权的用户，请求体带 schema 之外的键（`z.strictObject`） | 400 VALIDATION_FAILED → 403 FORBIDDEN（`fieldWriteViolations` 的 UNKNOWN_FIELD） | 3、4、8、9、12、14 |
| C-1c | 按钮先于请求体校验 | 有 create / update 权、没有 copy / execute 按钮的用户，发送格式错误的请求体 | 400 → 403 | 12、14 |
| C-1d | 范围先于请求体校验 | 有权、目标在范围外，且请求体其他字段格式错误（如日期非法） | 400 → 404 | 3、4、8、9、12、14 |
| C-1e | 多个参数同时非法时报哪一个 | 同时带多个非法参数 | 报错参数（message）可能不同，code 均为 VALIDATION_FAILED | 1、6 |

C2 的好处：所有已接管模块统一“先鉴权、后业务校验”，无权用户拿不到请求体格式的反馈（C-1b / c / d）。代价：

- 上表的错误码变化；
- C-1a 是反方向的：无权用户能先得到“标识格式不对”的反馈。

推荐 ①（T1 保序，零变化）。C2 的统一顺序可在全部模块接管后另行决定，届时一次切换、一次确认。

#### C-2　新增程序缺陷类 500 错误码（Q-T1-3）

| 错误码 | 何时出现 | 生产环境 | 测试环境 |
|---|---|---|---|
| `ROUTE_POLICY_UNCHECKED`（新） | `shared` 方式的处理函数没有调用 `access.inScopedTx` 就返回 | 丢弃响应，500 + 结构化日志 | 抛错 |
| `ROUTE_POLICY_IMPL_MISSING`（新，启动期） | 已接管模块的声明引用了未登记的实现 | 应用无法启动（同 `ROUTE_UNDECLARED`） | 同左 |
| `route_policy_denial_mismatch`（日志，不是错误码） | 实现抛出的拒绝码与声明的 `denied` 不一致 | 原样返回模块抛出的错误，只写日志 | 抛错 |

这些只在程序有缺陷时出现，正常请求不会遇到。仍单列出来，因为它们是新的失败方式。推荐 ①：与 PR-A 的 C8（`ROUTE_POLICY_MISMATCH` 500 fail-closed）同口径。

#### C-3　回滚期双重校验（仅当 Q-T1-4 选②）

保留手写校验一个发布周期，引擎与处理函数各校验一次：

- 每个请求的授权器调用、范围解析、点校验查询**翻倍**（试点约每请求多 2～4 条 SQL）；
- 错误结果不变（同一函数先后执行两次）。

推荐 ①：不保留双重校验，回滚靠 revert。

#### C-4　推广阶段已知的变化候选（试点不涉及，每阶段开工前单独交用户确认）

| `any` 全部分支失败时的拒绝码 / 文案 | 阶段 3（人才 / IDP）、阶段 7（审批） | 现状由最后一个判定的错误决定 → 声明“按第一个分支”可能不同 | PR-A 设计 §2.1 `any` 注释 |

### 5.3 门禁的“接管模式”（T1-2）

接管后，处理函数里不再有授权调用。PR-A 的两道门禁都依赖处理函数里的调用点，需要相应调整；同时不能失去“独立于声明”的性质。

| 门禁 | 接管前 | 已接管模块的路由 |
|---|---|---|
| 显式表（R1～R9） | 声明对表硬比对 | **不变**：表仍然人工审定、独立于声明，是接管后声明正确性的主要静态保证 |
| 证据 `call` 角色 | 锚定处理函数里的调用点 | 改为新角色 `enforced`：`route-policy/enforce.ts#<阶段>` + 声明键（引擎阶段的实现单元有摘要）；`impl` 角色锚定 `access-impl.ts` 的登记实现，以及它调用的现有函数；`const` 不变。处理函数里如果仍有旧调用点锚点，报 `EVIDENCE_TAKEOVER_STALE` |
| 静态基准（scan 闭包原语） | 每次重新扫描 | 改为“接管前冻结 ∪ 当前扫描”：冻结部分来自 `establishment.pre.json`（T1-0 时的 sha，不再重生成），当前扫描仍会发现处理函数里重新出现的授权调用。第二道“不弱于基准”继续生效 |
| 退役检查（新） | — | 已接管模块的路由文件出现手写准入调用 → 失败（§2.5） |
| 变更登记（PR-B B-11） | — | 证据角色变化、基准改为冻结 ∪ 当前，都属于“内容变化”，在 `required/changes.ts` 登记，理由写“接管：由引擎执行” |
| 运行时（Tier 1、对拍语料） | 测现状 | 接管后声明直接决定行为：声明被削弱，HTTP 行为随之改变，由冻结事实报出。这是接管后的第二道保证 |

**不用声明当证据**：PR-A 的规则“证据不得指向登记表文件”继续有效。

- `enforced` 角色指向的是引擎实现单元，不是 `policy.ts`；
- 声明的内容由显式表硬比对，不需要锚点。

## 7. 回滚方案

| 场景 | 做法 | 依据 |
|---|---|---|
| 接管 PR 合并后发现行为差异或缺陷 | `git revert` 该 PR，一次恢复手写调用，并把模块移出 `TAKEN_OVER_MODULES` | 接管与退役在同一 PR（§2.5）；无迁移、无数据结构变化，revert 后与接管前逐字节一致（由对拍语料验证） |
