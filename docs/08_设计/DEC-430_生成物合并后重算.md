# DEC-430① 生成物合并后重算、迁移编号与授权版本合并时分配

> 依据：DEC-430①（DEC-385① 落地）；DEC-439④（授权版本合并时定号，DEC-404 落地）。合并队列为审查合并窗口的 safemerge，单队列串行。
> 目的：一个 PR 合并后，其余在途 PR 不再因为生成物、端点计数、迁移编号而必须立刻重合 main、手工重算。

`=1` 时不一致判红；未设或 `=0` 时只警告（日志里输出明细，GitHub Actions 上另有 `::warning` 注解）。

## 2. CI 什么时候严格

`changes` job 算出模式，写进 job 日志的 notice 和运行摘要，传给 PGlite 与 PostgreSQL 分片：

- push 到 main、每周定时、手动触发：`GENERATED_STRICT=1`；
- pull_request：GitHub 测试合并提交与 PR 头的树相同（PR 头已包含最新 main）时为 1，否则为 0。

合并队列先在 PR 分支上跑 `pnpm merge:main` 并推送，此时 PR 头已包含最新 main，CI 按严格模式校验后再合并；
所以 main 上的生成物始终是重算过的。没排到队首的 PR 只看到警告，不必跟着每次合并重算。
DEC-454① 起 merge:main 改在云端跑、在途 PR 只跑轻量检查，见第 6 节。

## 3. `pnpm merge:main`

`scripts/merge-main.mjs`（纯函数在 `scripts/merge-main-lib.mjs`，单测 `tests/merge-main.test.ts`）：

1. `git fetch origin main` 后 `git merge --no-commit origin/main`；
2. 冲突文件只要在生成物白名单内就取 main 的版本：
   `tests/acceptance/support/route-policy/required/digests/**`、
   `baseline/observed-contract.json`、`baseline/recorded.json`、`baseline/endpoint-counts.json`、`baseline/probe/*.json`、
   `packages/db/migrations/meta/_journal.json`、`packages/db/migrations/meta/NNNN_snapshot.json`。
   白名单之外的冲突（含人工维护的 probe-known-gaps.json / probe-redundant-observations.json、迁移 SQL、业务代码）停下并列出，
   手工解决、`git add` 后运行 `pnpm merge:main --continue`；
3. 迁移编号：本分支 journal 里 tag 不在 main 的条目，按原顺序接在 main 最后一条之后改号（SQL、快照文件改名，
   journal 的 idx / tag 改写，when 严格大于 main 最后一条）；快照按“该迁移相对本分支 journal 里前一条的增量”逐条三方合并：第一条叠在 main 最新快照上，之后每条叠在上一条的结果上，
   prevId 接到 main 最新快照 id；两边改了同一处则停下交人工。仍引用旧迁移名的文件会列出提醒；
   **叠放 PR 的旧名迁移（F-109，DEC-463②）**：base 是另一个未合并 PR 分支的叠放 PR，会带着上游合并前的旧名迁移，
   它们与 main 上改号后的迁移 SQL 相同。所以“本分支自己的迁移”不只按完整迁移名比对：tag 不在 main 的条目，
   若 SQL 原始内容的 sha256 与 main 上某条迁移（本分支 journal 里没有的 tag）相同，就认定为“上游已合并但改了号”，
   清理旧名 SQL、旧 idx 的快照（该路径在 main 上有文件就恢复成 main 版本）和 journal 条目，不改号、不重算快照；
   只有 SQL 内容不同的才是本分支新增，照上面定号。规则细节：
   - 摘要对原始内容（`sqlDigest`，不做任何规范化）：引号字符串、双引号标识符、dollar quote 内部的空白与换行都是内容，
     规范化（去行尾空白、换行转换）会把内容不同的迁移抹成相同而误删，所以逐字节比较；改号只改文件名，内容逐字节不变，真正的旧名迁移不受影响；
   - 必须一一对应：同一份内容在旧名一侧出现多次，或在 main 一侧出现多次（一对多 / 多对一），都不清理，
     脚本报错停下，信息里列出涉及的旧名、main 名和 sha256，须人工处理；本分支已带着的 main 同名迁移不参与匹配；
   - 空迁移不参与去重（`isBlankSql`，词法扫描，不用正则剥注释）：读不到 SQL，或只有空白、分号、行注释（`--` 到行尾）、
     块注释（PostgreSQL 允许嵌套，按嵌套深度配对）的迁移没有摘要，不算“内容相同”，照常按新增处理。
     `--` 之后到行尾都是行注释，其中的 `/*` 不开启块注释：`-- /*` … `-- */` 两行包住的 CREATE TABLE 仍是语句；
     遇到其他任何字符（语句、引号、dollar quote、单个 `/`）即判有内容；没有结尾的块注释按空处理（保守，不参与去重）。
     drizzle 的 `--> statement-breakpoint` 以 `--` 开头，按行注释处理（现有迁移文件里它写在语句末尾或独占一行，是语句分隔标记，不是语句）；
   - 重复快照身份检查（`checkSnapshotIdentity`）：摘要只比原始内容，已提交的格式漂移（CRLF、行尾空格等）会让真正的旧名迁移漏判成“新增”。
     所以改号前先查每条要保留的迁移：它的快照 id（改号不改 id，是迁移的身份）若与 main 上某条、或与其他保留项重复，就停下，
     不改号、不写入，退出码非 0，`--check` 预演同样报告并非 0 退出；信息列出文件对、两边的 sha256，以及与 main 最新一条重复时的“id = prevId 自环”提示。
     人工处理方式：确认是同一条迁移后，把本分支的旧名 SQL 改成与 main 逐字节相同（或直接删掉该旧名迁移及其快照、journal 条目）再运行；
     不放宽摘要口径（不恢复规范化）；
   - 快照增量基准：每条真正新增的迁移，基准是它在本分支 journal 里的前一条（可能是被清理的旧名条目，其快照含上游改动，读合并前本分支的文件）。
     新增与旧名交错（U1→N1→U2→N2，U 为上游已合并、N 为本分支新增）时，N2 只叠它相对 U2 的增量，U2 的上游变化不会被当成本分支改动重算；
   - 输出留证：预演（`--check`）和正式运行都会在清理清单里逐对列出（`formatStale`，单测覆盖），格式为
     `  <旧名 tag> → <main 上的 tag>  sha256=<SQL 原始内容的 64 位十六进制摘要>`，例如
     `  0113_woozy_inhumans → 0117_woozy_inhumans  sha256=…`，可原样贴进 PR 评论留证。
4. 授权版本定号（DEC-439④，见第 7 节）：按合并结果算授权项编码指纹，与 main 不同则 version 定为 main + 1；
5. 重算（`GENERATED_STRICT=0` 下跑，生成器命令如下），全部通过后提交 `merge: 合入 main 并重算生成物`：
   - `ROUTE_POLICY_UPDATE_BASELINE=1 pnpm test tests/acceptance/AC-PRM-FW-02.test.ts`
   - `ROUTE_POLICY_UPDATE_BASELINE=1 pnpm test tests/acceptance/AC-PRM-FW-01.test.ts tests/acceptance/AC-PRM-FW-01-recorded.test.ts tests/acceptance/AC-PRM-FW-08.discovery.test.ts`
   - `ROUTE_POLICY_UPDATE_DIGESTS=1 pnpm test tests/acceptance/AC-PRM-FW-02-required.test.ts`

   注意：vitest 5 下 `pnpm test -- <文件>` 的 `--` 会让过滤失效、跑全量，文件名直接跟在 `pnpm test` 后面。

选项：`--check` 只预演（列出会冲突的文件、迁移改号与授权版本定号计划，不改工作区；有业务冲突退出码 1）；`--no-regen` 不重算；`--no-fetch` 不拉取；
`--take-ours-for-counts` 见下。

“只改计数”的业务冲突（补充）：典型是 main 把端点计数字面量 592 改成 593，而本分支已删掉字面量、改读 `baseline/endpoint-counts.json`。
对白名单之外的冲突文件，脚本按“本分支 / 分叉点 / main”三方逐处比较：若每一处冲突 main 一侧相对分叉点只有独立的数字字面量不同
（`592`、`1_024`、`0.5`；标识符里的数字如 `FW-01`、`v2` 不算），就在业务冲突清单下注明，建议冲突处保留本分支一侧，
`git add` 后 `pnpm merge:main --continue` 重算生成物。默认仍停下交人工（业务冲突一律人工处理）；
显式加 `--take-ours-for-counts` 时，只对“整份文件的冲突全是只改计数”的文件把冲突处取本分支一侧并 `git add`（文件里不冲突的 main 改动保留），
其余文件照旧停下。数字可能是业务常量而非计数，用这个选项前先看一眼提示里的文件。

开发线程：开发中不必为生成物重合 main；需要拿到 main 的新代码时用 `pnpm merge:main`，不要手工合生成物。

## 4. main 变红怎么办

责任方是审查合并窗口（合并队列）：发现 main 上生成物不一致后暂停队列，在 1 小时内从 main 拉修复分支，
跑 `pnpm merge:main`（分支已包含 main 时只重算并提交），开修复 PR，按严格模式通过后合入；修好前不合其他 PR。

## 5. 上线前恢复每个 PR 严格

随 F-087（上线后权限与安全待办）：上线前把 CI 的 `GENERATED_STRICT` 恒设为 1（或把 `generated-gate.ts` 的
`DEFAULT_GENERATED_STRICT` 改成 true），恢复每个 PR 都要求生成物与最新 main 一致。

## 6. DEC-454①：merge:main 上云、在途 PR 只跑轻量检查

### 6.1 CI 三种模式

`ci.yml` 的 `changes` job 输出 `mode`：

| 模式 | 什么时候 | 跑什么 | 两个必需检查 |
|---|---|---|---|
| docs | 目标分支为 main 的纯文档 PR（DEC-344） | 不跑 | 以必需名称快速通过 |
| light | pull_request，且 PR 没有 `queue-head` 标签，或目标分支不是 main | `light checks (lint / typecheck / build / unit, Node 24)`：lint、typecheck、build、`packages/domain` 与 merge:main 纯函数单测，约 4 分钟 | **改名**为“PGlite / PostgreSQL 完整测试待队首运行”报告；必需名称在该提交上没有结果，分支保护显示“等待中”，**合不进去** |
| full | 目标分支为 main、带 `queue-head` 标签的 pull_request 运行（队列关闭再重开 PR 触发 reopened，或标签在时推送）；push 到 main、每周定时、手动 workflow_dispatch（后者不关联 PR、不能放行合并） | light job + PGlite 5 片 + PostgreSQL 5 片 + F-043 并发 | 以必需名称报告，要求 light job 与全部分片成功 |

**只有 pull_request 运行能放行合并**（DEC-458）：workflow_dispatch 运行的检查虽然挂在同一提交上，但不关联 PR，
分支保护不认（#294 实测：233abddf 上派发的完整 CI 全绿，`gh pr merge` 仍报 “base branch policy prohibits the merge”，
`gh pr checks --required` 显示 no required checks reported）。所以队首的完整运行必须是带 `queue-head` 标签的 pull_request 运行。

为什么合并仍安全：分支保护按名称（`lint / typecheck / test (PGlite, Node 24)`、`test (PostgreSQL 16)`，GitHub Actions 应用）
认 PR 头提交上的检查结果。轻量运行只报改过名的检查，这两个名称只会由完整运行（或纯文档运行）报告，
而汇总 job 在完整模式下要求所有分片成功；分类 job 失败、模式未知时也用必需名称报告并判红。
不能用 `if` 跳过汇总 job 代替改名：被跳过的 job 报 skipped，分支保护会当作通过。
同一提交上先后有轻量和完整运行时互不覆盖（名称不同）。已摘掉 `queue-head` 标签的 PR 再推新提交，新提交上只有轻量结果，
必需检查回到“等待中”（标签还在时推送仍跑完整测试）。

**docs 模式只对目标分支为 main 的 PR 生效**（第 2 轮 P2-1）：必需名称上的成功挂在头提交上，改 base 不会使其失效（strict=false）。
若从功能分支 B 切出只加文档的 H、向 B 开 PR 也判 docs，再把 base 改成 main，同一个 H 上的“纯文档”绿灯就会放行 B 上未经完整测试的代码；
仅补 `edited` 触发也撤销不了已有的成功结果。所以 `scripts/ci-classify.sh` 对 base 不是 main 的 PR 一律判 light
（`queue-head` 也不生效），回归测试 `tests/ci-classify.test.ts`。改 base 为 main 后没有新运行，必需检查保持等待，推送或关闭重开后重新判定。
注意：仓库管理员可用 `gh pr merge --admin` 绕过必需检查（enforce_admins 未开），合并队列不得使用。

审查合并窗口“CI 绿了再审”的口径改为看 light checks（和纯文档 PR 的必需检查）；必需检查“等待中”是在途 PR 的正常状态。

### 6.2 队首流程：云端 merge:main → 打标签 → 关闭重开 PR（DEC-458）

合并队列（队列脚本，用维护者本人的 gh 身份）对队首 PR 执行：

```bash
gh workflow run merge-main.yml -f pr=<编号>             # 可加 -f take_ours_for_counts=true
gh run watch <运行编号> --exit-status                    # 失败时看运行摘要里的冲突清单；成功时摘要给出 PR 头完整 SHA
gh pr view <编号> --json headRefOid,labels              # 核对头等于摘要里的 SHA、已带 queue-head
gh pr close <编号> && gh pr reopen <编号>                # 触发 reopened 的 pull_request 运行，带标签 → 完整模式
gh pr checks <编号> --required --watch                  # 等两个必需检查（见下注）
gh pr merge <编号> --merge --match-head-commit <SHA>    # 合并前再读 OPEN / base / 头；禁止 --admin
```

注：完整运行的必需检查出现前，`gh pr checks --required` 会直接报 “no required checks reported” 并退出，
队列须先轮询到 reopened 触发的 ci.yml 运行已开始（`gh run list --workflow ci.yml --branch <分支> --event pull_request`，
核对 headSha），再等必需检查；不能把空列表当成通过。

为什么要关闭重开：云端流程用默认 `GITHUB_TOKEN` 推送、打标签，这些都不触发工作流（GitHub 防递归），
`ci.yml` 也不监听 labeled；关闭 / 重开必须由队列脚本用自己的身份做，GitHub 才会发出 reopened 事件。
重开的运行在 GitHub 测试合并提交上跑，PR 头已含最新 main，`GENERATED_STRICT=1`。

`merge-main.yml` 的步骤：校验 PR 为本仓库分支、base 为 main、未关闭，记下头提交 → 按该提交检出全历史 → `pnpm merge:main`
（main 自分叉点以来改过 `pnpm-lock.yaml` / `package.json` 时先只合并、重新 `pnpm install`、再重算）→ 打 `queue-head` 标签 →
推送前复核 OPEN / base / 头未变 → 有新提交就推回 PR 分支（不强推，期间有人推送则被拒，重新触发即可）；
运行摘要写出 PR 头完整 SHA 与下一步。复核脚本写在工作流文件里，不用 PR 分支的文件。本流程不触发 CI。

兜底（本机路径）：
- 业务冲突：job 判红，冲突清单与“只改计数”提示写进运行摘要；在本机该分支 `pnpm merge:main`、解决冲突、`--continue`；
- `GITHUB_TOKEN` 没有 workflows 权限：合并提交改动 `.github/workflows/`（main 期间改过 CI）时推送前即判红，改在本机 `pnpm merge:main`；
- 本机路径推送前先 `gh pr edit <编号> --add-label queue-head`，推送本身（维护者身份）就触发带标签的 synchronize 运行，走完整模式，无需再关闭重开；
- 对已是最新、只缺完整运行的队首 PR：打标签后关闭重开即可。

`queue-head` 标签由合并队列维护：出队（不合并、退回返工）时摘掉，否则之后的推送都会跑完整 CI。开发方不要自己打。

以后如用户配置仓库机密 `MERGE_BOT_TOKEN`（细粒度 PAT：contents 写 + workflows），云端推送即可直接触发 pull_request 运行、
也能推改动 workflows 的合并提交；那需要另改 `merge-main.yml`，本流程目前不使用它。

已知遗留（登记 F-087）：PR 分支的安装、脚本与测试在持有写权限凭据的同一 job 里执行；后续把代码执行与推送隔离并绑定已审 SHA。

### 6.3 评估过、没做的

- **只改配置或纯函数的 PR 少跑 PostgreSQL 组**：10-12 统计最近 40 个已合并 PR，非文档改动只落在 `packages/domain` 或纯脚本的只有 #260
  （merge:main 脚本）1 个，其余都动了 `apps/api` / `packages/db` / `tests/acceptance`；PostgreSQL 组与 PGlite 组并行、不在关键路径上，
  跳过它不缩短队首等待，只省分钟，且 domain 规则经 API 落库的行为差异正是 PG 组要抓的。收益小、有漏测风险，不做。

## 7. 授权版本合并时定号（DEC-439④）

起因：#256 / #262 / #267 在串行队列里反复撞同一个 `STANDARD_GRANT_VERSION`。DEC-404 要求“合并前最后一次合 main 时以 main + 1 定号并重算指纹”，
但这一步是手工的，每合一个改授权项的 PR，其余在途 PR 都要重改版本、指纹和 HISTORY。现在由 `pnpm merge:main` 自动完成，同迁移号。

涉及三处（都在 git 里，脚本按行改写，请保持写法）：
`packages/domain/src/platform/standard-grants.ts` 的 `export const STANDARD_GRANT_VERSION = N;`、`export const STANDARD_GRANT_DIGEST = '…';` 两行单行字面量；
`tests/acceptance/AC-PLAT-F061-grants.test.ts` 里 `const HISTORY: Record<number, string> = { … };` 块（块内只放 `N: '指纹',` 条目与 `//` 注释行）。

**开发方的占位写法**：改了授权项编码（对象目录、STANDARD_PROFILES、看全部批准清单等）时，

- 指纹写“指纹与 version 匹配”测试提示的值（这条检查始终判红，必须与本分支编码一致）；
- version 写占位：当时 main 的 version + 1 即可，HISTORY 追加同号一行，上方注释写 PR / 任务与原因（定号时沿用这条注释）；
- 与别的 PR 撞号不用管，也不必在 main 前进后手工重定；分支里递增过几次都行，合并时并成一行。
- 也可以只改编码、直接跑 `pnpm merge:main`（分支已含 main 时也会定号），注释会用分支名，审查前补成有意义的说明。

**合并时的规则**（`planGrantVersion`）：先按常规合并，再用 vite 的 `runnerImport` 加载工作区的 `standard-grants.ts`
（不需要构建、不新增依赖）算合并结果的 `grantCodesDigest(STANDARD_GRANT_CODES)`：

| 合并结果指纹 | version | 指纹 | HISTORY |
|---|---|---|---|
| 等于 main 的 `STANDARD_GRANT_DIGEST`（本分支没改编码，或改得与 main 相同） | 取 main | 取 main | 取 main |
| 不等于 | main + 1 | 合并结果重算 | main 的全部条目 + 一行（注释取本分支历史里 main 没有的条目的注释，去重；没有就用分支名） |

重复运行结果不变。main 自身的常量与 HISTORY 最后一行对不上时拒绝定号、停下交人工。

**冲突自动处理范围**：`standard-grants.ts` 里冲突处只含上述两行常量、F061 测试里冲突处位于 HISTORY 块内且只含条目 / 注释行时，取 main 一侧再按上表改写；
同一文件里还有其他冲突（业务代码、HISTORY 之外的改动、常量与其他代码挤在同一处）照旧停下交人工。
编码增删声明 `standard-grant-changes.json`（见下）不逐行合并：本分支相对分叉点改过就整份取本分支，否则取 main（git 自动合并成功时也改写）。

**`--check` 预告（F-097 P3-2）**：与实际定号同口径，按“合并结果”而不是“本分支 vs 分叉点”预告。脚本用 `git merge-tree --write-tree` 写出合并结果树，
导出 `packages/domain/src` 到临时目录加载算指纹（`standard-grants.ts` 只在两行常量冲突时按上面的规则处理）：
与 main 相同则预告“取 main 的 version N”（两个 PR 加了同一编码时就是这样，旧预告会误报 N + 1），不同则预告“main + 1”并给出指纹。
`packages/domain/src` 里有业务冲突、算不出合并结果时给条件式提示：“合并后若编码与 main 相同则取 main，否则 main + 1”。

**编码增删的动态基线（F-097 P3-1）**：删掉钉死快照后，另由 `AC-PLAT-F061-grants`“编码增删与本 PR 的声明一致”守住“只增删了本 PR 想增删的编码”：

- 声明：改了授权项编码的 PR 把 `packages/domain/src/platform/standard-grant-changes.json` 整份改写为本 PR 的
  `{ "reason": "PR / 任务与原因", "add": [...], "remove": [...] }`；条目是完整编码，或以 `*` 结尾的前缀（至少写到 `身份/`）。
  文件内容与基线相同（从 main 继承的上一个 PR 的声明）视为没有声明，所以旧声明不必清空，也不会放过后来的 PR；
- 基线：CI 的 pull_request 运行检出的是测试合并提交，`GRANT_BASE_REV=HEAD^1` 即 base 分支当前提交（PGlite / PostgreSQL 分片的 checkout 为此取
  `fetch-depth: 2`），比较的正是“合进最新 main 后本 PR 带来的增删”；本地与其余事件用 `git merge-base origin/main HEAD`（main 上即 HEAD 本身，无增删）。
  基线提交的编码用 `git archive` 导出 `packages/domain/src` 后加载。设了 `GRANT_BASE_REV` 却解析不到时判红；没设且取不到 merge-base 时跳过并注明原因；
- 判红：实际新增 / 删除的编码不被任一声明条目覆盖；声明新增的条目在当前编码里一个都没有；声明删除的条目当前仍有。
  声明新增的编码基线已有（别的 PR 先加了同一编码）不算失败。

为什么不只读最新 origin/main：分支落后 main 时，main 新增的编码会被算成“本分支删除”；以测试合并提交的 base / merge-base 为基线才只看本 PR 的改动。
没放到 `merge:main` 或队列里单独跑：放在测试里每个 PR 都判红，审查方在 CI 上就能看到，且只多拉一层提交历史。

**测试严格度**：授权版本的三条检查（以及上面的动态基线）都**不受** `GENERATED_STRICT` 影响，每个 PR 都判红——
① 指纹 = 当前编码集合的指纹（防止真实的目录漂移漏登记，审查方据此看到“这个 PR 会给存量标准身份补授权”）；
② `HISTORY[version]` = 指纹，且 version 是历史里最大的；③ 相邻两版指纹不同（编码没变不递增）。
这三条在开发占位和定号后都成立，不会因 main 前进而变红。挪到合并时的只是“version 必须比 main 当前值大 1”：
原 `AC-QL-employee-profile` 必测 11 里钉死“合并进来的 main 版本 / 指纹”的快照对比已删除（下一个改编码的 PR 合并后它必然失效），改为只核对编码内容、指纹一致与 version 下限；增删范围由上面的动态基线守。

## 8. 登记类冲突自动取并集（F-133，DEC-491④）

起因：多个在途 PR 往同一份清单里各加几行（声明集合、模块注册表、路由挂载、表导出），加在同一个位置就必冲突，
每次合并都靠人工逐个解。这类冲突内容上没有取舍（两边的条目都要），所以 `pnpm merge:main` 自动取并集，
并在处理后核对“本分支新增 ∪ main 新增”都在结果里。同迁移改号、授权版本定号的做法：先识别、再处理、不认识的照旧留给人工。

### 8.1 三类冲突的边界（以 main 9250df0 的实际文件为准）

| 类别 | 文件 | 处理 |

| ① F-039 登记 | `tests/acceptance/support/route-policy/required/declared/<模块>.ts`（F-124 的各模块声明集合） | **结构化三方并集**：解析成“种类 → 条目列表”，两边新增都保留、去重、一侧删除另一侧没动则删除；三份都有序就整体按码点排序，否则本分支顺序在前、main 新增在后；新种类追加在后；结果按 prettier 重新格式化，与仓库写法逐字一致 |

### 8.2 单一入口：登记区解析器 + 按条目身份比较（第 2 轮，DEC-431①）

第 1 轮审查发现四个绕过（删改分叉点已有条目仍被合并、同名异值与重复挂载按整行比较漏检、多行 export 被忽略、登记文件被删后跳过核对），
是同一类问题：**核对按整行 / 单行形状比较，且“看不懂”和“文件不在”被当成没问题**。现在自动合并与提交前核对共用一个入口
（`scripts/merge-main-registry-lib.mjs` 的 `parseEntries` + `compareEntries`，由 `registryProblems` 串起来）：

- **解析器 `parseEntries`**：用 TypeScript 语法树把登记类文件取成条目 `{ id, value }`，按身份而不是按行：

  | 文件 | 身份（id） | 值（value） |
  |---|---|---|
  | `required/declared/<模块>.ts` | 种类 + 条目（字符串或元组） | 固定 |
  | `apps/api/src/app.ts` | 每个 import 的导入绑定；`TENANT_MODULES` 的每个元素文本 | 来源模块与导入名；元素文本（尾注释、空白不算） |
  | `packages/db/src/schema/index.ts` | 导出名（`export *` 以来源模块为身份；多行 `export { … } from` 逐名展开） | 来源模块与原名 |
  | `required/index.ts`、`required/declared/index.ts` | 每个 import 的导入绑定；`REQUIRED_BY_MODULE` / `DECLARED` 的每个属性键 | 来源与导入名；属性值文本 |

  登记区里有无法识别的形状（schema 导出文件里出现 `export … from` 以外的语句、找不到登记变量、变量不是字面量、属性不是键值……）
  **一律抛出，视为无法核对 = 失败**，不再被正则静默过滤。
- **比较 `compareEntries`**（同一个函数两种口径）：
  - `strict`（自动合并的接受条件）：分叉点已有的条目被任一边删除或改动 → 须人工；同一身份两边都新增但值不同 → 冲突、须人工；
    结果必须正好是两边新增的并集（丢项、多项、值不对都不通过）；
  - 非 strict（提交前核对，含 Git 无冲突自动合并和人工解决过的文件）：期望值“只有一边改了就取那一边”，两边改成不同的值由人决定；
    结果里同一身份出现多次（同一键两边值不同、同一挂载函数两边各加一份，不论位置是否相邻、有无 Git 冲突）= 重复 = 失败。
- **提交前核对 `verifyRegistries`**：两边都改过的登记类文件，工作区文件**缺失**（`git rm` 掉了）直接失败；缺 typescript / prettier 也失败（不静默跳过）。
- 冲突处的逐行预筛（`unionLineHunk`，按整行并集）只决定“能不能先拼出一个候选结果”，**不是接受条件**：候选结果必须整份通过 `strict` 比较。

同类位置清单（本 PR 内所有“自动合并 / 核对”的出口，已全部走同一入口）：`resolveRegistryFile`（声明文件、逐行登记文件）、
`mergeDeclared` 的结果核对、`verifyRegistries`（提交前）、`--check` 预演（复用 `resolveRegistryFile`）。

### 8.3 用法

不需要新参数：`pnpm merge:main` / `--check` / `--continue` 照旧。`--check` 会在“登记类冲突（合并时自动取并集）”下列出会自动处理的文件，
在“登记类文件的冲突不是两边纯新增”下列出留给人工的文件和原因，并在末尾列出登记类文件清单；有业务冲突仍以退出码 1 结束。
重算完成并提交后，脚本再跑一遍 `node scripts/explain-graph-diff.mjs`，把“待说明”汇总打在日志里（只提示，不改退出码；待说明项仍要在 PR 描述里逐条说明）。
