## 1. 结论摘要

1. **一步提交，后台执行**：删除 `POST /exits/import/preview`。`POST /exits/import` 改为“保存即提交”：校验报文形状后落一条导入批次和逐行明细，返回 `202 { batchId, status: 'queued', total }`。提交事务提交后只**唤醒**后台执行器，不等它跑完（§6.2）；执行器逐行导入，进程重启或执行器异常时由调度轮询和租约接续，完成时给提交人发一条站内消息，内容为成功 / 失败行数（DEC-834②）。
2. **逐行事务，允许部分成功**：每行单独一个事务。业务写入与该行结果状态在同一事务里提交，失败行写入原因码。不再整批回滚（DEC-834②，F-490 U5 / U7）。
3. **单批上限 1000 行**（DEC-834①）。该路由的请求体上限放宽到 1 MiB，其余路由仍为 32KB（§5）。
4. **按邮箱识别，取消工号列**：模板目标是北森完整的 26 列（逐列列名待 N2 取证，列映射契约是 S4b 的前置，§9.1）；以“邮箱”为唯一键。必填列为姓名、邮箱、部门编码、入职日期、最后工作日。同批内重复邮箱，两行都拒（DEC-834③）。邮箱已被平台登录名占用，或已被本租户人员档案占用的，按行拒绝。工号由系统生成（§3.3，北森口径未测，见 §13 #N1）。
5. **建停用账号**：每个成功行新建一个全局账号，**创建时就是停用状态**，然后绑定人员，并登记一条“已自动停用”的离职账号任务。终态与员工正常离职、账号被停用之后完全相同（§4）。不复用已有账号，不可能产生可登录账号。
6. **编制满不提示**：删除导入专用的编制评估、409 确认协议和 `confirmed` 字段（§7.2）。
7. **列表不显示导入标识**：对外投影里 `exit_requests.mode = 'import'` 一律显示为 `'direct'`。筛选取消 `initiation=import`；`initiation=direct` 同时匹配 import。导入行在列表与详情里的 `batchId` 输出为 `null`（键保留，因为批量离职申请仍要用它，见 §7.1）。内部的 `exit_requests.mode = 'import'` 保留，供审计、改期替代时复制。
8. **结果查看**：新增 `GET /exits/import/batches`（列出本人提交的批次）和 `GET /exits/import/batches/:id`（批次详情与逐行结果）。前端提供“导入记录”和“下载错误文件”。站内消息的后端已有登记与读取接口（`approval_notifications` 表 + 审批模块的 `GET /notifications`，`approval/routes.ts:519`），但**前端目前没有消息中心页面**。本 F 不新建消息中心，按 DEC-774 标“未完成”（§9.3）。
9. **不变的部分**：F-139 §4 的有限区间校验（U3 保守保留，见 §2 和 §14 #A3）、§7 不走 `activateExit`、不触发 `onEffective`、只写勾选的手动黑名单（U4 已测一致：开关打开时导入也不触发自动加黑）、§8 的排序与改期，均保持原样。
10. **拆分**：S1 契约 → S2a 提交与执行 → S2b 恢复、重试与执行期复核 → S3 查询、通知与去标识 → S4a 前端提交与结果 → S4b 完整模板列映射（N2 前置），共六片（§11）。

## 3. 行字段、识别与工号

### 3.1 请求体（替换 F-139 §2.2）

```jsonc
{
  "rows": [
    {
      "rowNo": 2, // Excel 原始行号（首行为列名，数据从 2 起），回执与通知按它排序；批内唯一
      "name": "合成甲",
      "email": "syn.a@example.com", // 新增，必填；识别键与登录名
      "entryDate": "2023-03-01", // H
      "departmentCode": "D-SYN-01",
      "lastWorkDate": "2025-06-30", // L
      "positionCode": null, // 以下可选，规则同 F-139 §3
      "postCode": null,
      "exitTypeCode": null,
      "exitReasonCode": null,
      "exitDestinationCode": null,
      "addToBlacklist": false,
      "blacklistReason": null,
      "blacklistExpiryDate": null,
      "blacklistNote": null,
    },
  ],
}
```

- 仍为严格模式：带 `employeeNo` 或 `confirmed` 等未知键，整批 400 `VALIDATION_FAILED`。旧客户端沿用旧报文时会明确失败，不会被静默忽略（DEC-402，不做兼容）。
- **整批拒绝**（不落批次，同步 400）只有以下几种：报文不是对象或缺少 `rows`、`rows` 为空、超过 1000 行（`BATCH_LIMIT_EXCEEDED`）、`rowNo` 重复（`DUPLICATE_ROW_NO`）、行不是对象或带未知键。这几种错误发生时还谈不上“逐行”。
- 其余问题一律在**行级**报告，包括必填为空、格式错误、日期、引用、字典、邮箱冲突。为此，行内各字段在 zod 层只约束类型（`string | null`），长度、格式、必填都移到行级校验（F-139 的 `SHAPE_RULES` 改为逐行出错，不再整批失败）。这样北森“101 行出现 101 个错误”的逐行体验可以复现。

### 3.3 工号由系统生成

`employment_employees.code` 为 NOT NULL，按租户 `lower(code)` 唯一，并且不允许空白。仓库里没有工号规则模块（grep `工号规则`、`employeeCode` 生成均无结果）。北森模板没有工号列，导入后人员的工号取值也**未取证**（§13 #N1）。首期取最保守、无需新增配置的做法：

- `code = 'IMP-' + 人员 UUID 去掉连字符后的前 12 位，转大写`（例如 `IMP-3F2A9C10B7D4`）。人员 ID 在建档前由服务端 `randomUUID()` 生成，再传给 `createEmployee`。
- 撞上本租户已有工号的概率可以忽略；万一撞上，`createEmployee` 的 `ON CONFLICT` 抛 409，本行的事务回滚，记 `EMPLOYEE_CODE_CONFLICT`（`field = null`，提示“系统生成工号冲突，请重新导入该行”）。不做自动重试，避免掩盖问题。
- `IMP-` 前缀只是生成格式，**不是**导入标识：列表的工号列照常显示，不另加“导入”字样（§7.1）。
- 取证结果出来后（例如北森按工号规则生成，或允许为空），由 F 行修订本节；本 F 不预留开关（DEC-402）。

### 3.4 版本链、幂等、锁怎么改

- **版本链不变**：仍是一条 hire（effectiveDate = H）、一条 leave（E = L+1），各自写 `version_no = 1` 的人工版本（F-139 §8）。识别键改成邮箱，不影响版本链。
- **锁**：F-139 §6 步骤 0 按工号取事务级 advisory lock，改为按 `租户 + lower(邮箱)` 取。现在每行一个事务，每个事务只锁本行邮箱，所以不需要排序（一个事务只持有一把锁）。组织设置锁、编制锁照旧按 `org/locks.ts` 的顺序取。编制评估虽然删除了，但离职 / 入职的落地本身仍会写编制占用，所以编制锁仍要取。
- **与在职建档互斥**：`POST /employees` 的登录邮箱走 `provisionAccount`，全局唯一键由 `users.email` 兜底。导入行命中已存在的账号就拒（§4.2），所以“同邮箱同时手工建档 + 导入”最多只有一方成功。
- **命令幂等**：批次级。见 §6.4。

## 4. 账号：创建即停用（U2）

### 4.1 每个成功行的账号终态

| 对象 | 写入 | 说明 |
|---|---|---|
| `users`（全局） | 新建一行：email = 规范化邮箱，display_name = 姓名，**status = `disabled`** | 新的 SECURITY DEFINER 函数直接插入停用行（§4.2），不存在“先建为 active 再停用”的窗口 |
| `tenant_memberships` | 新建 active / internal | 与员工正常离职后的成员关系相同（离职停用只改全局 `users.status`，不撤销成员关系）。撤销身份不连带删除范围（硬规则 6），本行也不授予任何身份或范围 |
| `permission_user_person_links` | 绑定该人员 | 与 `provisionEmployeeUser` 相同的绑定表与锁（`lockPersonLink`） |
| `exit_account_tasks` | 新建一行：business_id = 离职业务，status = `disabled`，`auto_revision` = 新账号的 revision，`attempts = 0` | 表示“这个账号由离职规则停用”。之后撤销离职或改期替代时，现有恢复判定要求 `restoreRequested && autoRevision === user.revision`（`exit-account-worker.ts:121-131`），有了这一行才能正确恢复启用；不登记就恢复不了 |
| 角色 / 身份 / 数据范围 | 不写 | 历史离职人员不授权；数据范围默认为空（硬规则 1） |

不可登录的依据：登录以全局 `users.status = 'active'` 为前提，停用账号无法通过认证。AC-F493-04 用真 HTTP 登录接口验证这一点。

### 4.2 新增 SQL 函数（S1 迁移）

`tenant_provision_disabled_account(p_email text, p_display_name text, p_actor uuid, p_command_id text) RETURNS uuid`，SECURITY DEFINER，与 `tenant_provision_account`（迁移 0033）放在同一组权限下：

- 先 `INSERT INTO users(..., status) VALUES (..., 'disabled') ON CONFLICT (email) DO NOTHING RETURNING id`。插入成功就返回新 ID，并写 `platform_audit_events` 的 `user.create`（after 带 `status: 'disabled'`、`source: 'exit_import'`），和 0033 同一写法、同一事务。
- 冲突时返回 NULL，**不返回**已有账号的 ID 或状态。调用方据此把本行记为 `EMAIL_TAKEN`，然后回滚本行事务。
- 只接受已规范化的小写邮箱；函数内再做一次 `lower(btrim())` 校验，不一致就抛错（防止绕过）。
- 只授予 `app_owner` 等应用角色 EXECUTE（照 0033）。

为什么不复用已有账号：一是北森的口径就是“邮箱已存在即拒”（U5）；二是全局账号跨租户共享，停用它会影响该用户在其他租户的登录（DEC-142 / DEC-684）；保持它为启用，又等于给历史离职人员一个能登录本租户的账号。两条路都不能走，只能拒。代价是：`EMAIL_TAKEN` 会让有导入权限的管理员得知“这个邮箱在平台上已有账号”。现有的重聘改登录邮箱（`user-provisioning.ts:148-164`）在同样情况下也返回 `EMAIL_TAKEN`，属于已接受的口径。原因码不区分“本租户”和“其他租户”（§14 #A2）。

### 4.3 与登录、权限、重聘的关系

- **登录**：停用账号不能登录任何租户。新账号只属于本租户，不影响别人。
- **权限**：没有身份，没有范围。即使日后启用，也只能看到默认的空范围（硬规则 1）。
- **重聘**：日后在入职管理中重聘该人员时，走现有的 `enableRehireAccount`（`tenant_rehire_enable_account`）启用账号，本 F 不改。
- **撤销已导入的离职**（§4.4）。

### 4.4 撤销离职与改期

F-139 §10 说导入单可以撤销，并且“账号订阅方因为没有关联用户而直接返回”。现在有了绑定，`onCancelled → queueExitAccount(restore = true)` 会找到 §4.1 登记的任务，按现有恢复判定把账号恢复为 active。这与北森“删除离职记录后账号变启用”一致（F-490 清理路径 1）。改期替代（F-139 §8.3 第 2 行）走 `replaceExit`，同样经现有订阅方处理。导入不需要另写分支，只需在验收里覆盖（AC-F493-17）。

## 5. 上限、请求体与性能边界

| 项 | 取值 | 依据 / 说明 |
|---|---|---|
| 单批行数 | 1 ～ 1000 | DEC-834①；`EXIT_IMPORT_ROW_LIMIT` 从 100 改为 1000（domain 常量，前后端共用） |

## 6. 异步导入（U7）

### 6.1 提交（`POST /exits/import`，同步部分）

1. 权限链同 F-139 §5.1，五步全部照旧（功能权、按钮、字段写权、显式看全部范围、命令守卫复核），**判定的对象和字段不变**（P2-2，依据见下）：
   - 人员对象：新增权加字段写权 `{ code, name }`（现行 `exit-import.ts:177`，与 `POST /employees` 判的同一组字段，`routes.ts:190`）。模板虽然取消了工号列，但系统仍会写入 `code`（§3.3），所以 `code` 的写权照旧要求，不放宽。
   - 任职对象：按 `writtenFields(rows)` 判本批实际写入的字段（现行 `exit-import.ts:191`，不变）。
   - **邮箱不进入任何字段权限判定**。人员对象在权限目录里只登记了 `code`、`name` 两个字段（`module-actions.ts:443`），登录邮箱不是人员字段；真实授权器遇到未登记的字段会返回 403，所以不能把 `email` 加进字段写权。现有 `POST /employees` 的做法是：登录邮箱不参与字段校验，交给权限模块的账号端口（`routes.ts:176` 的注释，`splitLoginEmail` 在 `routes.ts:821`），F-039 声明登记为控制项 `controls: ['loginEmail']`（`policy.ts:900`）。导入沿用这一契约：`writtenFields` 不加 `email`；`POST /exits/import` 的 write 声明加 `controls: ['email']`（行内键 `rows[*].email`），F-039 义务同步登记。能写邮箱的门槛，就是能新建人员加显式看全部范围，与 `POST /employees` 相同。
   - 因此**不新增权限项**，授权版本不动（§10.2）。如果 F-039 的行字段推导不认 `controls`，S2a 停下报告，不得把 `email` 登记成人员字段，也不得新增授权项。
   - 验收用真实授权器（AC-F493-23），不能只用全放行的 `authorize` 替身。
2. 报文形状校验（§3.1 整批拒绝的那几项）。
3. 在 `runWrite` 命令台账内（`Idempotency-Key` 必填），同一事务里：
   - 插入 `exit_import_batches`：status = `queued`，total = 行数，submitted_by = 当前用户，command_id = 本命令。
   - 插入 `exit_import_rows`：每行一条，存原始字段值（§6.5）。形状不合法的行，以及 `duplicateEmailRows` 命中的行，直接写 status = `failed` 和原因；其余写 `pending`。
   - 写审计 `employment.exit_import.submitted`（对象为该批次，after 为 `{ total, prefailed }`，不含行内容）。
   - `afterTransactionCommit` 登记键 `exit-import:<tenant>:<batchId>`，回调**只调用** `wakeExitImports(db, tenantId)`，不在回调里执行批次。原因：`afterTransactionCommit` 的消费者会逐个 `await` 回调（`packages/db/src/after-commit.ts:58`），`runWrite` 要等它返回后才回响应；如果在回调里直接跑执行器，HTTP 要等整批 1000 行跑完才返回 202，这就成了同步导入。
4. 返回 `202 { batchId, status: 'queued', total }`。不返回逐行结果，与北森一致：结果要等消息通知。命令台账重放时同样返回 202，不再唤醒（回调只在首次提交的事务里登记）；即使漏唤醒，也由调度轮询接续（§6.2）。

提交时**不**检查邮箱占用和引用：这些检查依赖执行时的库内状态，放在执行器里做，避免出现“提交时通过、执行时失败”的双口径。

### 6.2 执行器（S2a 主体，S2b 恢复与重试）

- 文件：`apps/api/src/modules/employment/exit-import-worker.ts`，导出 `drainExitImports(db, tenantId)`、`wakeExitImports(db, tenantId)`、`startExitImportScheduler(db, options)`。
- **唤醒（S2a）**：`wakeExitImports` 是同步函数，只做两件事：把 `tenantId` 放进本进程的待处理集合；如果本进程还没有在跑的循环，就用 `setImmediate` 排一个循环，然后立即返回。循环依次取出租户，调用 `drainExitImports(db, tenantId)`；处理过批次的租户重新放回集合，直到没有可认领的批次为止。同一进程同一时间只有一个循环（单飞），状态按 `Db` 实例存放在 `WeakMap` 里。循环里的异常一律捕获，记一条结构化日志 `{ type: 'employment.exit-import.wake-failed', tenantId, category }`（只记错误类别，不写行内容、不写堆栈），**不往上抛**，因为这时 HTTP 已经返回，业务也已提交。
- **调度兜底（S2b）**：`startExitImportScheduler` 照 `startExitAccountScheduler` 的写法（`exit-account-worker.ts:305`），在 `startEmploymentActivationScheduler` 里与它并列启动（`activation-scheduler.ts:264`），间隔取 `min(60s, intervalMs)`，每一轮遍历启用中的租户，各调一次 `drainExitImports`；上一轮没结束时不叠加；`stop()` 等当前一轮结束。不改 `server.ts`，也不新增环境变量。`EMPLOYMENT_ACTIVATION_SCHEDULER=off` 时，兜底与离职账号的兜底一起关闭，只剩提交后唤醒，这是现有口径。
- 认领批次：`UPDATE exit_import_batches SET status = 'running', lease_until = now() + interval '5 minutes', attempts = attempts + 1, started_at = COALESCE(started_at, now()) WHERE tenant_id = $1 AND id = (SELECT id FROM exit_import_batches WHERE tenant_id = $1 AND (status = 'queued' OR (status = 'running' AND lease_until < now())) ORDER BY created_at, id LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING *`。多实例之间只有一方能认领；`drainExitImports` 每次只认领、处理一个批次，返回是否处理过，以免一个租户的长批次连续占住循环。
- 执行期权限复核（S2b）：认领之后、处理第一行之前，用提交人的身份重新解析权限（与提交时的 §6.1 第 1 步同一函数，用 system 上下文加 `userId = submitted_by` 构造），并核对成员关系仍为 active。不通过时，该批次所有 `pending` 行一次性记为 `failed`，原因 `SUBMITTER_FORBIDDEN`，然后进入收尾（§6.3）。这满足 AGENTS §10“每次在服务端重新校验成员、租户、范围”。
- 逐行处理：按 `rowNo` 升序取 `pending` 行，每次取 50 行（有界查询）。每行一个 `withTenant` 事务：
  1. 再次核对本行仍为 `pending`（`SELECT … FOR UPDATE`）；不是就跳过。崩溃恢复后不会重复写入。
  2. 取锁：邮箱 advisory lock，然后取组织设置锁、编制锁。
  3. 行级判定：F-139 §6 步骤 1 的单行版本，加上 §3.2 的邮箱判定。
  4. 写入：建档（系统生成工号）→ `tenant_provision_disabled_account`（返回 NULL 就记 `EMAIL_TAKEN`）→ 绑定 → 入职业务 → 离职业务 → 状态事件 → 落地 → 账号任务 → 黑名单（勾选时）→ 防御断言 → 审计（§10）。与 F-139 §6 步骤 2～8 相同，只把步骤 2 的“不建账号”改成上述账号三步。
  5. 本行改为 `succeeded`，记下 employee_id、exit_business_id；续租（`lease_until = now() + 5 min`）。
  6. 第 3 步判定失败，或第 4 步抛出**业务** `AppError`（4xx 类）时：回滚本行事务，再用一个新事务把本行记为 `failed`，写入 `errors`（取 `AppError.details` 中的 reason / field，一行可以有多条）。
- 系统错误（非 `AppError`、5xx、锁超时、连接断开）：本行事务回滚，**不**记失败，本次执行中止；批次保持 `running`，在 `last_error` 记下错误类别（不写堆栈、不写行内容），并把 `lease_until` 改为 `now() + 1 min`（退避），由下一次唤醒或调度轮询重新认领，从这一行重新开始（S2b 加次数上限，§6.3）。
- **测试接缝（S2a 建，S2b 扩展）**：`installExitImportTestHooks(db, { beforeBatch?, beforeRow?, failRow? })` 与 `exitImportIdle(db)`（等本进程的循环空闲）。安装时用 `isIsolatedTestDb(db)` 校验，不是 `useTestDb()` 建的隔离库就抛错，与 `formula-binding-switch.ts:19` 同一守法；产品代码路径不读环境变量、不留开关（DEC-402）。

**失败兜底：各种中断之后批次怎么收敛**

| 中断 | 停在什么状态 | 怎么收敛 | 片 |
|---|---|---|---|
| 提交已提交，唤醒没跑（进程在 `setImmediate` 之前退出） | `queued` | 进程重启后，调度第一轮（≤ 60 秒）认领 | S2b |
| 执行到一半进程崩溃 | `running`，租约 ≤ 5 分钟后到期 | 租约到期后由调度或下一次唤醒重新认领，`attempts + 1`，从第一条 `pending` 行继续；已 `succeeded` 的行因第 1 步复核被跳过，不会重复建人 | S2a 认领 SQL；S2b 调度 |
| 某行遇到系统错误 | `running`，租约退避 1 分钟 | 同上；`attempts` 达到 `EXIT_IMPORT_MAX_ATTEMPTS` 后进入 `failed` 收尾 | S2b |
| 循环本身抛错（如认领时数据库断开） | 不变（`queued` 或 `running`） | 记 `wake-failed` 日志，不重试；由调度轮询接续 | S2a 日志；S2b 调度 |
| 收尾事务失败 | `running`，已没有 `pending` 行 | 下一次认领时直接进入收尾；收尾用 `WHERE status = 'running'` 守住，消息只发一次 | S2a |

S2a 合入到 S2b 合入之间，没有调度兜底：唤醒丢失或进程崩溃时，批次要等同一租户下一次提交时的唤醒才会继续。这个窗口写进 S2a 的 PR 描述；前端要到 S4a 才接入新接口，窗口内没有用户路径会触发导入。

### 6.3 收尾、重试上限与状态机

批次状态：`queued → running → completed`，或 `running → failed`。状态机与收尾在 S2a；`attempts` 上限和 `failed` 终态在 S2b。

| 状态 | 进入条件 | 离开 |
|---|---|---|
| `queued` | 提交事务提交 | 被认领 → `running` |
| `running` | 被认领；租约到期可以被重新认领 | 没有 `pending` 行 → 收尾；`attempts` 达到 5 且再次遇到系统错误 → `failed` 收尾 |
| `completed` | 所有行都是 `succeeded` / `failed` | 终态 |
| `failed` | 系统错误重试 5 次仍失败：剩余 `pending` 行一次性记 `failed`，原因 `SYSTEM_ERROR` | 终态 |

收尾在一个事务里完成：

1. 统计 `succeeded_count`、`failed_count`，写入批次行，设置 `finished_at`。
2. 写入站内消息（§8.1）。
3. 写操作日志（§10）。

收尾用 `WHERE status = 'running' AND id = $batch` 守住，只有一方能收尾，消息只发一次（AC-F493-08）。第 2 步的通知接线在 S3（§11）；S2a、S2b 的收尾先只做第 1、3 步。`attempts` 上限 5 写成 domain 常量 `EXIT_IMPORT_MAX_ATTEMPTS`。按 AGENTS §10 的定时任务约定：失败记 failed、次数和原因；终态 `failed` 的批次首期不提供人工重试按钮，重新导入即可（失败行会因为邮箱未被占用而正常处理）。

### 6.4 重复提交与幂等

| 情况 | 结果 |
|---|---|
| 同键、同内容（网络重试） | 命令台账重放：返回同一个 `202 { batchId }`，不新建批次 |
| 同键、不同内容 | 409（命令台账的“同键异内容”） |
| 结果未知（超时） | 客户端用原键重提，等同于第 1 行；或者查 `GET /exits/import/batches`，看是否已有该批次（前端按 §9.1 处理） |
| 不同键、相同内容（用户重复点保存） | 新建第二个批次。第一批已成功的行，在第二批里因为邮箱已被占用而失败（`EMAIL_TAKEN`），不会建出重复的人。两批同时执行时，由邮箱 advisory lock 加全局唯一键保证同一邮箱只成功一次 |
| 撤权后同键重放 | 命令守卫复核失败，返回 403，不回放（F-139 §5.1 第 5 条，不变） |

前端点“保存”后立即禁用按钮，直到收到回执（§9.1），尽量减少第 4 行的情况；但它不是正确性的保证。

|---|---|---|

- **按读取人当前的字段查看权裁剪**（P2-3）。不因为“是提交人自己录入的”而豁免：撤权以后，提交人不应再通过导入记录看到已经无权查看的字段。依据与现有历史读取的裁剪约定一致：AGENTS §10“读取历史记录时仍按当前权限裁剪”；DEC-507（任职历史失败的首次、重放统一按读取人当前的字段权与范围裁剪，`context.ts:276`）；DEC-197 / DEC-203（审计查询按查看人当前的字段权限裁剪，`audit/visibility.ts` 文件头）。
- 可见字段集合用现有的 `getModuleViewableFields(deps, ctx, objectCode)`（`trimEmploymentResponse` 用的同一函数，`context.ts:331`），人员对象、任职对象各取一次；返回 `undefined`（该对象不受字段权约束）时视为全部可见，与现有约定相同。导入列与权限字段的对应关系，和提交时 `writtenFields` 的映射相同：

| 明细 input 键 | 权限对象.字段 |
|---|---|
| `name` | 人员.`name` |
| `entryDate` | 任职.`effectiveDate` |
| `departmentCode` / `lastWorkDate` / `positionCode` / `postCode` | 任职.`departmentId` / `lastWorkDate` / `positionId` / `postId` |
| `exitTypeCode` / `exitReasonCode` / `exitDestinationCode` | 任职.`exitTypeCode` / `reasonCode` / `whereaboutsCode` |
| `addToBlacklist` / `blacklistReason` / `blacklistExpiryDate` / `blacklistNote` | 任职.同名字段 |
| `email`，以及成功行的 `employeeId` | 没有字段权限项（§6.1）。取最保守的口径：只有读取人**当前**仍满足提交时的人员门槛（人员对象新增权 + `code` / `name` 写权 + 人员对象显式看全部范围，§6.1 第 1 步）时才返回，否则输出 `null` |

- 不可见的键输出 `null`，键本身保留，形状固定。
- `errors` 同样裁剪：`field` 不可见的错误，每行合并为一条 `{ field: null, reason: 'FIELD_HIDDEN' }`，不输出原原因码，因为像 `REFERENCE_NOT_FOUND` 这样的原因码本身就会透露该编码存不存在。`field` 为 `email` 的错误按上表 `email` 的规则处理。不带字段的错误（`SUBMITTER_FORBIDDEN`、`SYSTEM_ERROR`、`EMPLOYEE_CODE_CONFLICT`）照原样输出。`FIELD_HIDDEN` 列入 `EXIT_IMPORT_REASONS`（S1）。
- 错误文件由前端根据裁剪后的明细生成，所以同样被裁剪：不可见的列留空（§9.2）。
- `GET /exits/import/batches` 只返回计数和时间，不含字段值，不需要裁剪。站内消息的 payload 也只有计数（§8.1）。
- 投影在 F-039 登记为 `projector('employment.exitImportBatch', …)`，不写 `none`（§10.1）。
- 提交人失去导入按钮或功能权后，这两个查询都返回 403。“读取历史记录时仍按当前权限裁剪”（AGENTS §10）。
- 租户管理员查看全租户的导入批次：首期不做，审计里可以查（§14 #A5）。
