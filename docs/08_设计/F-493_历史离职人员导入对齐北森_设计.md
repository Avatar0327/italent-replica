## 0. 写法选择与理由

选择**新建本文**，并在 F-139 的相应节加“已由 F-493 修订”的链接，不在 F-139 上直接改。理由：

1. F-139 已经实现并合入，它的结论正是本次改动的“现行实现”。原文保留，审查时可以逐条对照“现行 → 改为”。直接改写会丢掉对照基线。
2. 派单要求“不改其他设计文档的结论”。新建文档、只在 F-139 加链接，不会改动 F-139 的结论文字。
3. 改动横跨 F-139 的十多节。集中写在一份文档里，实现片只需要读本文，再按链接回查 F-139 中未改动的条款（§4 区间校验、§7 与 `activateExit` 的关系、§8 排序与改期）。

第 2 版仍在同一份文档上改（不另开 F-493b），文首修订记录列出改动的节，便于对照第 1 版审查结论。

## 1. 结论摘要

1. **一步提交，后台执行**：删除 `POST /exits/import/preview`。`POST /exits/import` 改为“保存即提交”：校验报文形状后落一条导入批次和逐行明细，返回 `202 { batchId, status: 'queued', total }`。提交事务提交后只**唤醒**后台执行器，不等它跑完（§6.2）；执行器逐行导入，进程重启或执行器异常时由调度轮询和租约接续（DEC-834②）。
2. **逐行事务，允许部分成功**：每行单独一个事务。业务写入与该行结果状态在同一事务里提交，失败行写入原因码。不再整批回滚。
3. **单批上限 1000 行**（DEC-834①，北森无上限，记差异 §15）。该路由的请求体上限放宽到 1 MiB，其余路由仍为 32KB（§5）。
4. **模板 26 列，按电子邮件识别**：A 列「导入结果」只在错误文件里有内容，B～Z 共 25 列是数据列；必填为 B 姓名、C 电子邮件、D 部门编码、E 入职日期、V 最后工作日，只靠列名前的「*」标识；没有逐列说明、批注和示例行（§3.1）。复刻没有对应字段的列（Z 离职说明）为空时放行、有值时本行报错（§3.2）。N 性别、P 民族、Q 政治面貌只认北森选项原文（3 / 60 / 15 项），可以留空，留空不填默认值（§3.6，DEC-840①）。
5. **工号为空**：导入建的人员 `code = NULL`，不再生成 `IMP-`；放开员工表工号列的 NOT NULL，唯一索引对 NULL 不生效；其他建人入口的工号规则不变。各处按工号排序、搜索、导出、展示的空值口径见 §3.5。
6. **邮箱用途**：C「电子邮件」写入人员档案的 `email`，也就是账号的“联系邮箱”（账号上不另存，取绑定档案的最新电子邮件，与 F-328 的定义相同）；**不作登录名**。登录名由系统分配虚拟登录名 `va-<32 位十六进制>@virtualaccount.invalid`（§4.2）。M「个人邮箱」写入档案 `backupMail`。
7. **三类冲突**（§4.4）：
   - a. 与本租户**全部未删除人员**（含在职、离职、待入职，DEC-839①）的「电子邮件」重复：整行拦截，不建人，报「X在员工信息中已存在，不允许导入」；
   - b. 与任一账号的登录名重复：报「当前邮箱已被使用，请更换邮箱」，但人员、档案、两条任职、离职、账号照建，账号**没有登录名**（`users.email = NULL`），这一行计 1 条错误；
   - c. 同一文件内重复：两行都拒，报「…在导入文件中重复出现，无法导入」（DEC-834③）。
   个人邮箱不参与判定。复刻没有删除人员的功能，所以“已删除人员不参与判定”在复刻里没有可触发的场景。
8. **建停用账号**：每个建了人的行（含 b 类）新建一个全局账号，**创建时就是停用状态**，然后绑定人员，并登记一条“已自动停用”的离职账号任务。终态与员工正常离职、账号被停用之后相同（§4.1）。不复用已有账号。
9. **结果入口：消息通知 + 导入历史页**：没有进度条和取消。保存后提示「导入进行中，执行结果请关注消息通知」。完成后给**操作人本人**发一条站内通知，发送人显示为操作人（DEC-839②），正文照北森；有错误时带「查看详情」，直接下载错误文件；错误文件保留 15 天（§8）。顶栏信封的「通知」页签接入现有 `GET /notifications`（§9.2），关闭第 1 版 A1。另做「导入历史」页（DEC-840②，§8.4、§9.5）：列出本人提交的导入批次，可下载错误报告和原文件，不做取消。
   **两种计数**（DEC-840①）：错误数按**错误条数**算（一行多条错误各算一条），存 `error_count`，用于通知和导入历史；错误**行**数另存 `error_row_count`，用于错误文件行数和操作日志失败数（§6.3）。
10. **编制满不提示、列表不显示导入标识、去掉预览**：同第 1 版（§7）。
11. **原部门已停用也放行**（DEC-839③）：导入不再做 F-139 §4 的区间可用性校验和入职日启用校验，部门只需存在、入职日不早于设立日；之后撤销这条离职会被现有校验拦截，与北森“删除离职记录被拦”（U3_04）一致（§4.7）。
    **不变的部分**：§7 不走 `activateExit`、不触发 `onEffective`、不触发自动加黑（U4 已测一致）、§8 的排序与改期，均保持原样。模板里没有黑名单列，所以导入不再写手动黑名单（§3.2 末尾）。
12. **拆分**：S1 工号与登录名可空 → S2 导入契约 → S3a 提交与执行 → S3b 恢复、重试与清理 → S3c 错误文件、通知与去标识 → S3d 导入历史后端 → S4a 前端导入 → S4b 前端消息与空值展示 → S4c 前端导入历史页，共九片（§11）。

### 3.3 行级校验顺序与错误文案（N5 原文格式）

- 同文件重复在**提交时**判定（§6.1）：它取决于整批，执行器重启后也不能改变结论。比较键为 `lower(btrim(C))`；C 为空或格式不对的行不参与重复判定（已经有自己的错误）。

### 3.4 版本链、幂等、锁怎么改

- **版本链不变**：一条 hire（effectiveDate = H）、一条 leave（E = L+1），各自写 `version_no = 1` 的人工版本（F-139 §8）。两条任职的 `jobNumber` 写 `null`（员工工号为空，§3.5）。
- **档案**：人员档案首个版本由档案写入端口 `appendEmployee(tx, { ...ctx, expectedRevision: 0 }, employeeId, patch, false)` 写入（签名 `(tx, ctx, employeeId, patch, checkRevision)`，revision 放在上下文里；与入职落地同一端口和同一写法，`entry-actions.ts:407`），patch 为本行非空的档案列（至少含 `name`、`email`）。T / U 有值时，由 `saveSubset` 写一条教育经历（与 `intern-profile.ts` 同一端口）。系统反写列（`lastSchool`、`major`）由子集端口照常反写，导入不直接写。
- **锁**：按 `租户 + lower(btrim(电子邮件))` 取事务级 advisory lock（替换 F-139 的工号锁）。每行一个事务，每个事务只锁本行邮箱，不需要排序。组织设置锁、编制锁照旧按 `org/locks.ts` 的顺序取（离职 / 入职落地本身仍写编制占用）。
- **与其他建档入口互斥**：a 类判定读的是档案最新版本的 `email`。手工入职建档写档案 `email` 时不取同一把 advisory lock，所以“同一邮箱同时手工建档 + 导入”在极窄的并发窗口里可能两边都成功，结果是两个人员档案电子邮件相同。复刻的档案 `email` 本来就没有唯一约束（手工入职也允许重复），这一点不比现状更差；不新增跨入口锁，记 §14 A11。
- **命令幂等**：批次级，见 §6.4。

### 3.5 工号为空（N1）

**迁移（S1）**：`ALTER TABLE employment_employees ALTER COLUMN code DROP NOT NULL`。

- 唯一索引 `employment_employees_tenant_code (tenant_id, lower(code))` 保留：PostgreSQL 唯一索引里 NULL 互不相等，同一租户可以有任意多个工号为空的人员；非空工号之间的唯一性不变。
- 检查约束 `employment_employees_code_nonempty (btrim(code) <> '')` 保留：NULL 使检查结果为 unknown，按 SQL 规则视为通过；空白字符串仍被拒，所以“空”只有 NULL 一种表示。
- Drizzle 类型变为 `code: string | null`；`createEmployee(tx, ctx, { code: string | null; name })`（`employees.ts:46`）。
- **其他建人入口不变**：`POST /employees`、入职、实习生建档、批量入职等入口的 zod 仍要求工号非空，校验口径不改；只有历史离职导入传 `null`。迁移不回填任何数据（DEC-402）。

### 4.2 虚拟登录名

- 格式：`va-<账号 ID 去掉连字符后的 32 位小写十六进制>@virtualaccount.invalid`，例如 `va-3f2a9c10b7d44e8f9a1b2c3d4e5f6a7b@virtualaccount.invalid`。
- 生成：在 §4.5 的 SQL 函数里，先 `v_id := gen_random_uuid()`，再用 `v_id` 拼出登录名，`INSERT INTO users (id, email, …)` 一条语句写入。应用层不拼、不传。
- 唯一性：由账号 ID（UUID）唯一推出；`users.email` 的 UNIQUE 约束兜底。万一 23505（UUID 碰撞，可以忽略），函数不吞，按系统错误处理（§6.2 退避重试，下次换一个 UUID）。
- 为什么不照抄北森的 `<13位数字>@virtualaccount.upaas`：`.invalid` 是 RFC 2606 保留的顶级域，保证这个地址不可能被注册、也不可能收到邮件；用账号 ID 生成无需再建序号表，也不会暴露账号创建顺序。北森的 13 位数字规则未取证（看起来像时间戳或序号）。差异登记 §15。
- 用途：只是一个“占位登录名”，没有发放任何凭据，用户不知道它，所以不能用来登录（§4.6）。重聘时由 F-328 把登录名改为员工电子邮件（`docs/02_业务建模/30` 第 630 行：登录用户名从虚拟账号变为联系邮箱），本 F 不改这条链路。
- 小写：满足 `users_email_lowercase` 检查。

### 4.3 联系邮箱：取绑定档案的电子邮件，不新增列

- 核对结果：`users` 只有 `email` 一列（`tenancy.ts:60`），它是登录名；账号上**没有**单独的联系邮箱列。复刻的“全部用户”页（`settings/user-columns.tsx:20`）把 `email` 列显示为“联系邮箱”，实际展示的是登录名。

- 判定时点：c 类在提交时（§6.1）；a 类在执行器取到邮箱锁之后、写入之前；b 类在写账号时由 SQL 函数判定（§4.5），与插入在同一语句里，没有“先查后插”的竞态。

**关闭第 1 版 A2**（`EMAIL_TAKEN` 暴露“邮箱在平台上已有账号”）：新口径下没有“平台已有账号就整行拒”的判定了。b 类照北森原样报「当前邮箱已被使用，请更换邮箱」，它确实会让有导入权限的人得知“这个字符串是某个账号的登录名”，但：①这是北森的原样行为（F-496 N4 A 行），DEC-838① 已拍板照做；②只有满足导入门槛（§6.1：人员新增权、档案字段写权、两个对象的显式看全部范围、导入按钮）的人能触发，与现有重聘改登录名返回 `EMAIL_TAKEN` 的暴露程度相同（`user-provisioning.ts`）；③不返回对方账号的 ID、状态、租户。所以 A2 关闭，不再单列。

### 4.5 迁移与 SQL 函数（S1 放开登录名非空；S2 新函数）

**S1 迁移**（新增一个迁移文件，编号由 `pnpm merge:main` 顺延；不改 0033）：同一迁移里**先**改函数、**后**放开约束：

1. `CREATE OR REPLACE FUNCTION tenant_provision_account(p_email text, p_display_name text, p_actor uuid, p_command_id text)`：签名、返回、`SECURITY DEFINER`、`search_path` 与 0033 相同，函数体只改第 22 行的条件，前面补一项 `normalized IS NULL OR`：`IF normalized IS NULL OR normalized !~ '^[^@[:space:]]+@[^@[:space:]]+$' OR btrim(coalesce(p_display_name, '')) = '' THEN RAISE … check_violation`。迁移里照 0033 再写一遍 `REVOKE … FROM PUBLIC` / `GRANT … TO app_user`（`CREATE OR REPLACE` 本来保留权限，重写一遍是为了迁移可读）。
2. `ALTER TABLE users ALTER COLUMN email DROP NOT NULL`。

为什么必须补：0033 的校验写成 `normalized !~ …`，遇 NULL 结果为 NULL，`IF` 不成立。放开 NOT NULL 之前，NULL 由列约束挡住（`23502`）；放开之后，传 NULL 会走到 `INSERT … ON CONFLICT (email) DO NOTHING` 插入一条 `email = NULL、status = active` 的账号，最后的 `WHERE u.email = normalized` 又查不到它，函数返回零行（审查方在内存 PGlite 上用 0033 原函数和最小合成表复现：放开前 `23502`，放开后零行且落账号）。所以“0033 原样就能拒 NULL”不成立，第 1 步是放开约束的前提，两步在同一迁移里。

其他写 `users.email` 的位置已核对，不需要改：F-328 `tenant_rehire_login_email`（0184）已显式写 `normalized IS NULL OR …`（`0184:25`）；平台建账号 `platform-ops.ts:112` 的入参由 `platform/routes.ts:85` 的 zod 要求非空邮箱。

- UNIQUE(email) 保留：多个 NULL 互不冲突；非空登录名唯一性不变。
- `users_email_lowercase (email = lower(email))` 保留：NULL 使检查为 unknown，视为通过。
- Drizzle 类型 `email: string | null`。只有本 F 的导入函数（S2 `tenant_provision_import_account`）会写 NULL；`tenant_provision_account` 经第 1 步补上显式 NULL 拒绝后，与 0184、平台建账号一起继续拒绝 NULL / 不合法邮箱。

**S2 新函数**：`tenant_provision_import_account(p_contact_email text, p_display_name text, p_actor uuid, p_command_id text) RETURNS TABLE (account_id uuid, login_assigned boolean)`，SECURITY DEFINER，与 `tenant_provision_account`（0033）同一组权限：

1. 校验 `p_contact_email` 等于 `lower(btrim(p_contact_email))` 且非空，不一致就抛错（防止调用方绕过规范化）。
2. `v_id := gen_random_uuid()`；如果 `EXISTS (SELECT 1 FROM users WHERE email = p_contact_email)`，`v_login := NULL`、`login_assigned := false`；否则 `v_login := 'va-' || replace(v_id::text, '-', '') || '@virtualaccount.invalid'`、`login_assigned := true`。
3. `INSERT INTO users (id, email, display_name, status) VALUES (v_id, v_login, p_display_name, 'disabled')`。
4. 写 `platform_audit_events` 的 `user.create`（after 带 `status: 'disabled'`、`source: 'exit_import'`、`loginAssigned`，**不写**联系邮箱或登录名原文以外的字段），和 0033 同一写法、同一事务。
5. 返回 `(v_id, login_assigned)`。不返回任何已有账号的 ID、状态或租户。

- 第 2 步的 `EXISTS` 与第 3 步的插入不需要锁：插入的登录名要么是 NULL，要么是由新 UUID 生成的虚拟登录名，都不会和并发插入的其他登录名撞上；b 类判定结果只决定“有没有登录名”，即使并发窗口里对方账号刚建好，最坏结果是本行拿到了虚拟登录名而没报 b 类错误——这与“导入在先、对方建账号在后”的结果相同，不产生重复登录名。
- 只授予 `app_owner` 等应用角色 EXECUTE（照 0033）。应用角色仍不能直接 `INSERT INTO users`。
- 第 1 版的 `tenant_provision_disabled_account` **不建**。

### 4.6 登录侧行为

- 复刻目前没有按登录名登录的接口：身份由 `IdentityResolver` 解析出 userId（开发期 HMAC 头，正式登录由 B-01 提供），`tenantContext` 只放行 `users.status = 'active'` 的账号（`apps/api/src/tenant-context.ts:34`），停用账号一律 401 `UNAUTHENTICATED`。导入建的账号都是停用的，所以不能进入任何租户。
- 按登录名查找的现有位置：平台运维 CLI `ops/platform-cli.ts:95`（`eq(users.email, email)`，输入是非空邮箱，NULL 永远不命中）、平台建账号 `platform/routes.ts:85`（入参必填邮箱）、`tenant_provision_account`（`ON CONFLICT (email)`，NULL 不会成为冲突目标）。登录名为 NULL 的账号不参与任何按登录名的查找，这些位置都不用改，AC-31 断言 CLI 查找不命中。
- **登录名的两种值**（S1）：
  - **内部值**：`tenant-users.ts` 的 `Account.email`（`accountsOf` 读 `tenant_member_accounts`）类型改为 `string | null`，NULL 原样保留。凡是要拿登录名去调账号函数、做比较的地方，一律用内部值。
  - **展示值**：`TenantUserView.email` 仍是 `string`，`viewsOf` 照现行 `account?.email ?? ''`（`:134`）投影为空串，供 `GET /permission/users` 出参与审计快照使用。展示值不得再传回账号函数。
  - `tenant-users.ts` 新导出一个只读函数 `accountLogin(tx, userId): Promise<string | null>`，复用 `accountsOf`，只回答本租户成员的账号，返回内部值。
- **`keepBinding`（`user-provisioning.ts:106-129`）改为按内部值判定**。现行写法用 `getTenantUser` 的 `current.email` 调 `provisionAccount`（`:120`），而 `current.email` 是展示值：登录名为 NULL 时得到空串，`current.email === null` 这种守卫永远不命中，空串传给 `tenant_provision_account` 后报 `check_violation`，接口返回数据库异常。改后的顺序：
  1. `const login = await accountLogin(tx, userId)`；
  2. 改绑判定照旧，但比较对象换成 `login`：`asked && asked !== login && renamedInTx…` → 409 `USER_REBIND_FORBIDDEN`。登录名为 NULL 时，请求里带了任何 `loginEmail` 都按改绑拒绝（与现行“入职不能借机改登录名”一致；改登录名只走 F-328 重聘链路）；
  3. 成员关系 active → 原样返回（导入建的成员关系是 active，正常走到这里就结束）；
  4. **新增**：`login === null` → 409 `ACCOUNT_LOGIN_MISSING`（「该账号还没有登录名，请先维护员工电子邮件后再办理」），在 `provisionAccount` 之前抛出；
  5. `provisionAccount(tx, write, login, current.displayName)`，其余照旧。
- **可达路径**：HR 导入一名 b 类人员 → 管理员经 `POST /permission/users/:userId/remove` 移出其成员关系 → 再经 `POST /employees/:id/businesses` 创建入职类业务（`kind = hire`，离职后允许）、不传 `loginEmail` → `routes.ts:318 ensureHiredAccount` → `provisionEmployeeUser` → `keepBinding` 第 4 步 409。409 在业务事务内抛出，`createEmploymentBusiness` 已写的入职业务随事务整体回滚。AC-31④ 走这条真实入口断言。
- 撤销离职后账号会恢复 active（§4.7），这时登录名为虚拟登录名或 NULL，都没有发放凭据，仍无法登录；正式登录（B-01）上线时，须保证“没有登录名或登录名是 `@virtualaccount.invalid` 的账号不能作为登录入口”。这一条是 B-01 的约束，记 §14 A13。

### 4.7 撤销离职、改期、重聘、幂等与重试

- **撤销离职**：`onCancelled → queueExitAccount(restore = true)` 找到 §4.1 登记的任务，按现有恢复判定把账号恢复为 active（与北森“删除离职记录后账号变启用”一致，F-490 清理路径 1）。b 类账号恢复为 active 后仍没有登录名；登录名不在撤销时补，与北森一致（北森 N4 A 行账号的登录用户名为「--」）。导入不需要另写分支，验收覆盖（AC-17）。
- **原部门已停用时撤销被拦（DEC-839③，照北森 U3_04）**：导入放行了已停用部门（§3.3 区间一步不再判停用）之后，撤销这条离职就是北森的“删除离职记录”。撤销会把人员恢复为在职，在职段从 L+1 起向后延续（不封顶），现有撤销校验 `exit-cancel-intervals.ts:133` 对这一段 ΔO 逐段调用 `assertEmploymentDepartmentAvailableWithin`：
  - 原部门在 L+1 当天或之后的任一天处于停用状态（包括在 L 之前停用、之后一直没有启用），撤销返回 409，reason `EMPLOYMENT_DEPARTMENT_DISABLED`，提示「任职部门【…】已被停用（停用日期：…），请检查」（部门对操作人不可见时不带部门名，现行口径）；离职、任职、账号任务都不变，不写审计；
  - 原部门在 [H, L] 内停用过、但 L+1 起已重新启用，撤销照常成功。
  这条拦截是现有代码，不需要为导入加分支；要先启用原部门（或改由调动等业务把人员调到可用部门）才能撤销，与北森相同。离职改期把 L 往后推时，`exit-projection.ts:96` 对延长的在职段做同一校验，同样会拦。AC-18⑤⑥ 覆盖。
- **改期替代**：`replaceExit`（F-139 §8.3 第 2 行）经现有订阅方处理，不变。
- **重聘**：日后在入职管理中重聘该人员时，F-328 `tenant_rehire_login_email`（0184）把登录名从虚拟登录名或 NULL 改为档案电子邮件，再由 `enableRehireAccount` 启用。b 类人员的档案电子邮件恰好是别人的登录名，重聘时会得到 `EMAIL_TAKEN`，要先把档案电子邮件改掉才能重聘；这是现有重聘口径，本 F 不改，AC-22 覆盖成功路径和这条拦截。
- **幂等与重试**：
  - b 类行在**同一个行事务**里完成全部写入并把行状态记为 `created_with_error`，不存在“建了一半”的中间态；执行器崩溃重启后，该行已不是 `pending`，第 1 步复核跳过它（§6.2），不会重复建人。
  - 用户拿错误文件改正后重导：b 类行如果没改 C 列，会命中 a 类（档案里已经有这个电子邮件）而被整行拦截，不会建第二个人；改了 C 列则视为另一个人，照新邮箱判定。这是北森同样的结果（同一邮箱在员工信息里已存在）。
  - 命令重放与重复提交见 §6.4。

## 6. 异步导入（U7）

### 6.1 提交（`POST /exits/import`，同步部分）

1. 权限链同 F-139 §5.1，五步照旧（功能权、按钮、字段写权、显式看全部范围、命令守卫复核），**档案字段改为按真实写入判写权**：

   - 任职对象：按 `writtenFields(rows)` 判本批实际写入的任职字段（现行 `exit-import.ts:191`）；新增的 `levelId`、`place` 随之进入判定。

   - **修订第 1 版 P2-2 的结论**：第 1 版说“邮箱不进入任何字段权限判定”，依据是当时的邮箱只作登录名、而登录名不是人员字段。N3 取证后，C 列写的是档案 `email` 字段（`personnel/fields.ts:34` 登记的普通档案字段），所以它**必须**判档案字段写权；登录名改为系统分配，不来自用户输入，不需要判权。F-039 不再登记 `controls: ['email']`，改为与实习生建档相同的 `guards: [..., 'employment.exitImportProfile']` 加 `controls: ['profile']`（§10.1）。
   - 不新增授权项，授权版本不动（§10.2）。验收用真实授权器（AC-23、AC-37）。
2. 报文形状校验（§3.2 整批拒绝的那几项）。
3. 在 `runWrite` 命令台账内（`Idempotency-Key` 必填），同一事务里：
   - 插入 `exit_import_batches`：status = `queued`，total = 行数，file_name，submitted_by = 当前用户，command_id = 本命令。
   - 插入 `exit_import_rows`：每行一条，存 25 个原始值（§6.5）。形状不合法的行，以及 c 类命中的行，直接写 status = `failed` 和错误；其余写 `pending`。
   - 写审计 `employment.exit_import.submitted`（对象为该批次，after 为 `{ total, prefailed }`，不含行内容和文件名）。
   - `afterTransactionCommit` 登记键 `exit-import:<tenant>:<batchId>`，回调**只调用** `wakeExitImports(db, tenantId)`，不在回调里执行批次（`packages/db/src/after-commit.ts:58` 会逐个 `await` 回调，`runWrite` 要等它返回后才回响应）。
4. 返回 `202 { batchId, status: 'queued', total }`。命令台账重放时同样返回 202，不再唤醒；即使漏唤醒，也由调度轮询接续（§6.2）。前端只用回执关闭弹窗，不展示 batchId。

提交时**不**做 a 类判定和引用判定：这些依赖执行时的库内状态，放在执行器里做，避免“提交时通过、执行时失败”的双口径。

### 6.2 执行器（S3a 主体，S3b 恢复与重试）

第 1 版的唤醒、单飞、调度兜底、认领 SQL、租约、测试接缝**原样保留**，只把片号 S2a / S2b 改为 S3a / S3b：

- 文件：`apps/api/src/modules/employment/exit-import-worker.ts`，导出 `drainExitImports(db, tenantId)`、`wakeExitImports(db, tenantId)`、`startExitImportScheduler(db, options)`。
- **唤醒（S3a）**：`wakeExitImports` 同步把 `tenantId` 放进本进程待处理集合，没有在跑的循环时用 `setImmediate` 排一个，立即返回；同一进程同一时间只有一个循环，状态按 `Db` 实例存在 `WeakMap`；循环异常只记 `{ type: 'employment.exit-import.wake-failed', tenantId, category }`，不往上抛。
- **调度兜底（S3b）**：照 `startExitAccountScheduler`（`exit-account-worker.ts:305`），在 `startEmploymentActivationScheduler`（`activation-scheduler.ts:264`）里并列启动，间隔 `min(60s, intervalMs)`；每一轮遍历启用中的租户，先调一次 `drainExitImports`，再做一次过期清理（§8.3）。不改 `server.ts`，不新增环境变量。
- 认领：`UPDATE exit_import_batches SET status = 'running', lease_until = now() + interval '5 minutes', attempts = attempts + 1, started_at = COALESCE(started_at, now()) WHERE tenant_id = $1 AND id = (SELECT id … WHERE tenant_id = $1 AND (status = 'queued' OR (status = 'running' AND lease_until < now())) ORDER BY created_at, id LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING *`；每次只认领、处理一个批次。
- 执行期权限复核（S3b）：认领后、处理第一行前，用提交人身份重算 §6.1 第 1 步（含档案字段写权），并核对成员关系仍为 active；不通过时所有 `pending` 行一次性记 `failed`（`SUBMITTER_FORBIDDEN`），然后收尾。
- 逐行处理：按 `rowNo` 升序每次取 50 条 `pending` 行，每行一个 `withTenant` 事务：
  1. `SELECT … FOR UPDATE` 复核本行仍为 `pending`，不是就跳过。
  2. 取锁：电子邮件 advisory lock → 组织设置锁 → 编制锁。
  3. 行级判定：§3.3 的顺序（a 类、引用、字典、区间、不支持的列）。
  4. 写入：建档（`code = NULL`）→ 档案首个版本（§3.4）→ 教育经历（T / U 有值时）→ `tenant_provision_import_account` → 成员关系与绑定 → 入职业务 → 离职业务 → 状态事件 → 落地 → 账号任务 → 防御断言 → 审计（§10.3）。与 F-139 §6 步骤 2～8 相同，去掉手动黑名单一步。
  5. 账号函数返回 `login_assigned = true`：本行记 `succeeded`；返回 `false`：本行记 `created_with_error`，errors = `[{ column: 'C', reason: 'LOGIN_TAKEN' }]`。两者都记下 employee_id、exit_business_id，并续租。
  6. 第 3 步判定失败，或第 4 步抛出**业务** `AppError`（4xx 类，含档案端口的字段校验错误）时：回滚本行事务，再用一个新事务把本行记为 `failed`，按错误的字段映射回列字母写入 errors。
- 系统错误（非 `AppError`、5xx、锁超时、连接断开、虚拟登录名 23505）：本行事务回滚，**不**记失败，本次执行中止；批次保持 `running`，`last_error` 记错误类别，`lease_until = now() + 1 min`，由下一次唤醒或调度重新认领（S3b 加次数上限）。
- **测试接缝（S3a 建，S3b 扩展）**：`installExitImportTestHooks(db, { beforeBatch?, beforeRow?, failRow? })` 与 `exitImportIdle(db)`；安装时用 `isIsolatedTestDb(db)` 校验（与 `formula-binding-switch.ts:19` 同一守法），产品代码路径不读环境变量、不留开关（DEC-402）。

**失败兜底**（同第 1 版，片号顺延）：

| 中断 | 停在什么状态 | 怎么收敛 | 片 |
|---|---|---|---|
| 提交已提交，唤醒没跑 | `queued` | 进程重启后调度第一轮（≤ 60 秒）认领 | S3b |
| 执行到一半进程崩溃 | `running`，租约 ≤ 5 分钟后到期 | 重新认领，`attempts + 1`，从第一条 `pending` 行继续；已 `succeeded` / `created_with_error` 的行被第 1 步跳过 | S3a 认领；S3b 调度 |
| 某行遇到系统错误 | `running`，退避 1 分钟 | 同上；达到 `EXIT_IMPORT_MAX_ATTEMPTS` 后 `failed` 收尾 | S3b |

### 6.3 收尾、重试上限与状态机

批次状态：`queued → running → completed`，或 `running → failed`（同第 1 版）。

| 状态 | 进入条件 | 离开 |
|---|---|---|
| `queued` | 提交事务提交 | 被认领 → `running` |
| `running` | 被认领；租约到期可以被重新认领 | 没有 `pending` 行 → 收尾；`attempts` 达到 5 且再次遇到系统错误 → `failed` 收尾 |
| `completed` | 所有行都不是 `pending` | 终态 |
| `failed` | 系统错误重试 5 次仍失败：剩余 `pending` 行一次性记 `failed`（`SYSTEM_ERROR`） | 终态 |

行状态：`pending → succeeded | created_with_error | failed`，三个都是终态。

收尾在一个事务里完成：

1. 统计三个计数写入批次行，设置 `finished_at`、`expires_at = finished_at + interval '15 days'`（DEC-840①，**行数和错误条数分开**）：
   - `created_count` = `succeeded` + `created_with_error` 的行数（已建人数）；
   - `error_row_count` = `failed` + `created_with_error` 的**行数**，即错误文件的数据行数、操作日志的 `failureCount`；
   - `error_count` = 这些行 `errors` 数组**项数之和**（错误条数），即通知正文和导入历史结果里的 N。b 类行只有 1 条 `LOGIN_TAKEN`；`SYSTEM_ERROR` 收尾的行各 1 条。
   例：F-499 第 02～08、11 行失败，其中第 11 行 3 条错误 → `error_row_count = 8`，`error_count = 10`，通知「出现10个错误」。
2. 不再清空 `succeeded` 行的原始值（第 2 版第 1 轮的这一步删除）：导入历史要能下载原文件（§8.4），原文件需要全部行；全部行的原始值统一在 `expires_at` 后由过期清理置 NULL（§8.3）。
3. 写站内通知（§8.1，S3c 接线；S3a、S3b 的收尾先只做第 1、4 步）。
4. 写操作日志（§10.3）。

收尾用 `WHERE status = 'running' AND id = $batch` 守住，只有一方能收尾，通知只发一次（AC-08）。`EXIT_IMPORT_MAX_ATTEMPTS = 5` 为 domain 常量。`failed` 终态的批次不提供人工重试，重新导入即可。系统失败的批次同样发通知，N 含未处理的行（每行 1 条 `SYSTEM_ERROR`，它们也在错误文件里，原因「系统处理中断…」）。

### 6.4 重复提交与幂等

| 情况 | 结果 |
|---|---|
| 同键、同内容（网络重试） | 命令台账重放：返回同一个 `202 { batchId }`，不新建批次 |
| 同键、不同内容 | 409（命令台账的“同键异内容”） |

  - 只有提交人能下载；批次不属于本人时返回 404（不暴露别人的批次是否存在），租户不符同样 404。
  - 下载时重新校验当前权限：功能权、导入按钮、人员 / 档案两个对象的显式看全部范围，任一不满足 403。
  - 字段裁剪：用 `getModuleViewableFields(deps, ctx, objectCode)`（`permission/module-access.ts:97`）对人员对象、档案对象、任职对象各取一次可见字段；某列对应的字段当前不可见时，该列的值留空，该列上的错误原文改为 `FIELD_HIDDEN` 文案（不输出原原因，因为“不存在”这类原因本身会透露编码是否存在）。列与字段的对应同 §3.1（B → 人员 `name`；C、I、K、L、M、N、O、P、Q、R、S → 档案同名字段；T、U → 教育经历子集；D～H、J、V～Y → 任职字段；Z 没有字段，按可见处理）。
  - 不带列的错误（`SUBMITTER_FORBIDDEN`、`SYSTEM_ERROR`）原样输出。
- 状态与时效：
  - 批次还没有终态 → 409 `EXIT_IMPORT_NOT_FINISHED`（正常路径不会出现：通知只在收尾时发）。
  - `error_count = 0`（此时 `error_row_count` 也为 0）→ 404，reason `EXIT_IMPORT_NO_ERROR_FILE`（通知里没有链接，导入历史显示「--」，正常路径不会出现）。
  - `now() ≥ expires_at` → 404，reason `EXIT_IMPORT_FILE_EXPIRED`（按 `expires_at` 判，不等清理任务跑完，边界精确）。前端提示“文件已过期”（§9.2）。
- F-039：登记为文件下载路由，写法参照现有导出路由（`hr-analysis/roster-routes.ts` 的 `/export`），投影说明写“按当前字段权裁剪的 xlsx”，不写 `none`（§10.1）。
- 模板下载 `GET /exits/import/template` 用同一写出器，只写第 1 行列名；权限同导入入口（功能权 + 导入按钮），不含任何数据。

### 8.3 错误文件与原文件保留 15 天

- `expires_at = finished_at + 15 天`（UTC 时间点，15 × 24 小时；北森只说“15天后过期”，未取证是按自然日还是按小时，复刻按时间点，差异登记 §15）。
- 原文件（导入历史的「导入附件」，§8.4）用同一个 `expires_at`，不另设时限。理由：两者都由 `exit_import_rows` 的原始值生成，原始值含姓名、证件号、手机号，保留越短越好（数据最小化，§6.5）；北森导入附件的保留期没有取证，通知里只写了错误文件“15天后过期”，复刻不为原文件另造一个更长的期限；用同一时点清理，一次清空全部行即可，不需要“错误行留、成功行删”两套时限。记差异 D13（§15）。
- 到期后：错误文件、原文件下载都返回 404 `EXIT_IMPORT_FILE_EXPIRED`；通知本身保留（正文仍是“文件将于15天后过期”，与北森一致），点「查看详情」得到“文件已过期”提示；导入历史的批次行保留，两个下载链接改为「已过期」（§9.5）。
- 清理（S3b）：调度每一轮在 `drainExitImports` 之后，对本租户 `expires_at < now() AND purged_at IS NULL` 的批次，每次最多 20 个，一个事务里把它们的 `exit_import_rows` 全部行（含成功行）的原始值置 NULL、`purged_at = now()`。errors（只有列字母和原因码）、计数、人员 ID 保留，供审计追溯。清理可重复执行（条件里带 `purged_at IS NULL`），失败只记日志，下一轮再来（AGENTS §10 定时任务约定）。
- 批次行本身长期保留（不含个人数据，只有文件名、计数和时间），导入历史长期能看到这一批的记录。

### 8.4 导入历史后端（S3d，DEC-840②）

北森在 组织员工 > 设置 > 公共设置 > 导入历史 列出离职人员导入记录（F-496 N7 更正）：列为导入类型（离职人员）、导入时间、导入者、状态、导入结果、附件（错误报告）、导入附件（原文件）；状态可筛 失败 / 成功 / 执行中；有错误的批次也显示「成功」，结果如「尝试导入11条记录，出现10个错误。」；没有取消。复刻照做列表与两个下载，**不做取消**。

**谁能看到哪些记录（复刻取舍，D16）**：**只列本人提交的批次**（`submitted_by = 当前用户`），管理员也看不到别人的批次。推荐理由：

- 与同一批次的其他出口一致：通知只发操作人（F-496 N6），错误文件只有提交人能下载（§8.2）；如果列表让别人看到、却下载不了，或者能下载，就与这两处口径不一。
- 两个附件都含原始个人数据（姓名、证件号、手机号），而且原文件里是**全部行**，包括没有建成人、不进任何人员 / 组织范围的失败行，无法按数据范围裁剪到行；只给提交人是最小暴露面。
- 北森取证只用了一个管理员账号，看不出别人的批次是否可见，不能作为放宽的依据。
- 以后要放开给管理员，只需把谓词从 `own` 换成范围判定，不改表和接口形状。

**列表**：`GET /exits/import/batches`

| 项 | 写法 |
|---|---|
| 权限 | 功能权与导入按钮同导入入口（`IMPORT_EMPLOYEE_CREATE` 的对象权 + `Employment.DimissionImport`，§9.1）+ `own` 谓词；不要求显式看全部范围（列表只有本人的文件名和计数，不含行数据；下载时才查范围） |
| 查询参数 | `status`：`running` / `succeeded` / `failed`，可多选（逗号分隔），缺省为全部；`from`、`to`：租户时区的业务日期（含两端），按 `created_at` 换算到租户时区比较；`page` 从 1 起，每页 15 条（`EXIT_IMPORT_HISTORY_PAGE_SIZE`，domain 常量） |
| SQL | `withTenant` 内 `WHERE tenant_id = $t AND submitted_by = $me [AND status IN (…)] [AND created_at 在区间内] ORDER BY created_at DESC, id DESC LIMIT 16 OFFSET …`（多取 1 条判断有无下一页），走 §6.5 恢复的索引；有界查询 |
| 出参（每条） | `id`；`importType: 'exit'`（前端文案「离职人员」）；`createdAt`（UTC ISO）；`submitterName`（提交人当前 `users.display_name`，本人列表里就是自己）；`status`（下表映射后的三值）；`total`；`errorCount`（错误条数 `error_count`，执行中为 null）；`hasErrorFile`（终态且 `error_count ≥ 1`）；`fileName`；`filesExpired`（`now() ≥ expires_at`） |
| 分页出参 | `{ items, page, hasNext }` |
| 不出 | `error_row_count`、`created_count`、`attempts`、`last_error`、`command_id`、行明细 |

**状态映射**（DEC-840②：有错误也显示「成功」）：

| 批次 `status` | 出参 `status` | 界面 |
|---|---|---|
| `queued`、`running` | `running` | 执行中 |
| `completed`（不论 `error_count` 多少） | `succeeded` | 成功 |
| `failed`（系统错误重试 5 次仍失败，§6.3） | `failed` | 失败 |

**结果文字**由前端用资源文案拼（DEC-045，接口不出中文句子）：终态为「尝试导入{total}条记录，出现{errorCount}个错误。」，`errorCount` 是错误条数；执行中显示「--」。F-499 的批次显示「尝试导入11条记录，出现10个错误。」，与北森一致。

**原文件下载**：`GET /exits/import/batches/:id/source-file`

- 返回 xlsx，`Content-Disposition` 用 `attachmentHeader(<file_name 去掉扩展名>.xlsx)`；生成方式与错误文件相同（`statWorkbook`、`inlineStr`、不写公式，§8.2）。
- 内容：第 1 行 26 个列名原文；从第 2 行起是本批**全部行**（不论成功失败），按 `rowNo` 升序，A 列「导入结果」留空，B～Z 写 `exit_import_rows` 里的原始值（日期列按提交时的文本原样写）。
- **不是用户上传的原始字节**：前端在浏览器里解析文件、只提交 25 个键的 JSON（§9.1），服务端从来没有收到文件本身；照存原始字节要新建上传通道（按附件约定先登记元数据再上传）并多存用户没有导入的内容（模板以外的列、A 列）。所以原文件由明细原始值按模板重建：列序是模板顺序（用户原文件的列序可以不同，§9.1），全空行、模板以外的列不在其中。记差异 D13（§15）。
- 权限与错误文件完全相同（§8.2）：只有提交人，别人的批次、别的租户的批次都 404；下载时重查功能权、导入按钮、人员 / 档案两个对象的显式看全部范围，任一不满足 403；按当前字段权裁剪列值（不可见列留空）。
- 状态与时效：执行中也可以下载（原始值在提交时就已落库）；`now() ≥ expires_at` → 404 `EXIT_IMPORT_FILE_EXPIRED`；`purged_at` 非空时同样 404。
- 审计：同错误文件，记一条操作日志 `behavior = export`（对象为该批次，`{ rows }`）。

**错误报告下载**沿用 §8.2 的 `GET /exits/import/batches/:id/error-file`，导入历史与通知「查看详情」调用同一个路由。

**租户隔离**：三个路由都在 `withTenant` 里查询，`exit_import_batches` / `exit_import_rows` FORCE RLS；SQL 同时带 `tenant_id` 与 `submitted_by` 条件；按 ID 查到的批次不属于本人或不属于本租户时一律 404，不区分“不存在”和“无权”（AC-41、AC-42 的跨租户、跨用户反证）。

**收尾操作日志的映射**（只用现有 `OperationLogItem` / `errorReport` 契约，`packages/db/src/audit.ts:111`；不给 `outcome` 加新值，不在 item 上加 `reasons`——写入器 `normalizeItem` 也会丢掉它）：

| 批次行状态 | `items[].outcome` | item 归属字段 | `errorReport` 条目 |
|---|---|---|---|
| `succeeded` | `succeeded` | `employeeId` = 新人员、`objectId` = 离职业务 ID、`orgId` = 解析出的部门 | 无 |

`withFailedImportLog` 只包住提交的同步部分，覆盖整批拒绝的情况。逐行失败由收尾时的操作日志记录，不重复写入。

|---|---|---|---|---|
| D1 | 单批行数上限（N8） | 没有上限（1001 行无提示，正常处理） | 1000 行，1001 行整批 400 `BATCH_LIMIT_EXCEEDED` | DEC-834①、DEC-838④：保护单租户后台执行时长与请求体大小 |
