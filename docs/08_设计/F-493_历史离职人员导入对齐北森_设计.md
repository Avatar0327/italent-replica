## 1. 结论摘要

1. **一步提交，后台执行**：删除 `POST /exits/import/preview`。`POST /exits/import` 改为“保存即提交”：校验报文形状后落一条导入批次和逐行明细，返回 `202 { batchId, status: 'queued', total }`。提交事务提交后只**唤醒**后台执行器，不等它跑完（§6.2）；执行器逐行导入，进程重启或执行器异常时由调度轮询和租约接续（DEC-834②）。
2. **逐行事务，允许部分成功**：每行单独一个事务。业务写入与该行结果状态在同一事务里提交，失败行写入原因码。不再整批回滚。
3. **单批上限 1000 行**（DEC-834①，北森无上限，记差异 §15）。该路由的请求体上限放宽到 1 MiB，其余路由仍为 32KB（§5）。
4. **模板 26 列，按电子邮件识别**：A 列「导入结果」只在错误文件里有内容，B～Z 共 25 列是数据列；必填为 B 姓名、C 电子邮件、D 部门编码、E 入职日期、V 最后工作日，只靠列名前的「*」标识；没有逐列说明、批注和示例行（§3.1）。复刻没有对应字段的列（Z 离职说明）为空时放行、有值时本行报错（§3.2）。
5. **工号为空**：导入建的人员 `code = NULL`，不再生成 `IMP-`；放开员工表工号列的 NOT NULL，唯一索引对 NULL 不生效；其他建人入口的工号规则不变。各处按工号排序、搜索、导出、展示的空值口径见 §3.5。
6. **邮箱用途**：C「电子邮件」写入人员档案的 `email`，也就是账号的“联系邮箱”（账号上不另存，取绑定档案的最新电子邮件，与 F-328 的定义相同）；**不作登录名**。登录名由系统分配虚拟登录名 `va-<32 位十六进制>@virtualaccount.invalid`（§4.2）。M「个人邮箱」写入档案 `backupMail`。
7. **三类冲突**（§4.4）：
   - a. 与本租户人员的「电子邮件」重复：整行拦截，不建人，报「X在员工信息中已存在，不允许导入」；
   - b. 与任一账号的登录名重复：报「当前邮箱已被使用，请更换邮箱」，但人员、档案、两条任职、离职、账号照建，账号**没有登录名**（`users.email = NULL`），这一行计入错误数；
   - c. 同一文件内重复：两行都拒，报「…在导入文件中重复出现，无法导入」（DEC-834③）。
   个人邮箱不参与判定。复刻没有删除人员的功能，所以“已删除人员不参与判定”在复刻里没有可触发的场景。
8. **建停用账号**：每个建了人的行（含 b 类）新建一个全局账号，**创建时就是停用状态**，然后绑定人员，并登记一条“已自动停用”的离职账号任务。终态与员工正常离职、账号被停用之后相同（§4.1）。不复用已有账号。
9. **结果入口只有消息通知**：没有导入记录、任务列表、进度条和取消。保存后提示「导入进行中，执行结果请关注消息通知」。完成后给**操作人本人**发一条站内通知，正文照北森；有错误时带「查看详情」，直接下载错误文件；错误文件保留 15 天（§8）。顶栏信封的「通知」页签接入现有 `GET /notifications`（§9.2），关闭第 1 版 A1。
10. **编制满不提示、列表不显示导入标识、去掉预览**：同第 1 版（§7）。
11. **不变的部分**：F-139 §4 的有限区间校验（U3 保守保留，§14 A3）、§7 不走 `activateExit`、不触发 `onEffective`、不触发自动加黑（U4 已测一致）、§8 的排序与改期，均保持原样。模板里没有黑名单列，所以导入不再写手动黑名单（§3.2 末尾）。
12. **拆分**：S1 工号与登录名可空 → S2 导入契约 → S3a 提交与执行 → S3b 恢复、重试与清理 → S3c 错误文件、通知与去标识 → S4a 前端导入 → S4b 前端消息与空值展示，共七片（§11）。

### 3.2 请求体（替换 F-139 §2.2 与第 1 版 §3.1）

```jsonc
{
  "fileName": "历史离职人员.xlsx", // 新增：上传文件名，只用于通知正文（§8.1）
  "rows": [
    {
      "rowNo": 2, // Excel 原始行号（首行为列名，数据从 2 起）；批内唯一
      "name": "合成甲",
      "email": "syn.a@example.com",
      "departmentCode": "D-SYN-01",
      "entryDate": "2023/03/01",
      "positionName": null, // 以下 21 个键都是 string | null，原样传单元格文本
      "postName": null,
      "levelName": null,
      "workDate": null,
      "place": null,
      "idNumber": null,
      "mobilePhone": null,
      "personalEmail": null,
      "gender": null,
      "birthday": null,
      "nation": null,
      "politicalStatus": null,
      "householdAddress": null,
      "registAddress": null,
      "school": null,
      "major": null,
      "lastWorkDate": "2025/06/30",
      "exitTypeName": null,
      "exitReasonName": null,
      "whereaboutsName": null,
      "exitNote": null,
    },
  ],
}
```

- 仍为严格模式：每行恰好是 `rowNo` 加 25 个数据键（键必须齐全，值可以为 `null`），带 `employeeNo`、`addToBlacklist`、`confirmed` 等未知键，整批 400 `VALIDATION_FAILED`（DEC-402，不做兼容）。
- `fileName`：去首尾空白后 1～255 个字符；控制字符（U+0000～U+001F、U+007F）删除后再判长度；为空整批 400。通知里按纯文本渲染，不解析标记。
- **整批拒绝**（不落批次，同步 400）只有：报文不是对象、缺 `rows` 或 `fileName`、`rows` 为空、超过 1000 行（`BATCH_LIMIT_EXCEEDED`）、`rowNo` 重复（`DUPLICATE_ROW_NO`）、行不是对象或键不齐、带未知键、某个值不是 `string | null`、单个值超过 2000 个字符（防止撑爆明细表；超长的正常文本按行级规则报错）。
- 其余问题一律在**行级**报告。zod 层只约束类型，必填、长度、格式、引用都在行级校验，这样北森“1001 行出现 1001 个错误”的逐行体验可以复现。
- 日期列（E、I、O、V）接受 `yyyy-mm-dd`、`yyyy/mm/dd`、`yyyy/m/d` 三种文本，后端规整为 ISO 日期再用。Excel 日期单元格由前端按现有 `dateOf` 转成 `yyyy-mm-dd` 文本（`exit-import-model.ts:59`），后端不接收序列号。

### 3.3 行级校验顺序与错误文案（N5 原文格式）

每行的错误存在 `exit_import_rows.errors`（jsonb，`[{ column: 'D', reason: 'REFERENCE_NOT_FOUND' }]`，只存列字母和原因码，不存值）。错误文件生成时，用 domain 函数 `exitImportErrorText(column, reason, value)` 按下表拼出中文原文；一行有多条错误时用「；」连接（北森多错误的连接方式未取证，复刻自定，§15）。

格式：`[<列名>]：<列名>【<值>】<后缀>`，列名带不带「*」照模板原文。值取本行该列的原始文本；日期列取规整后的 `yyyy/mm/dd`（规整不了就取原文）。

| 原因码 | 适用列 | 原文（以 D 列、值 `zzf496nope` 为例） | 判定 |
|---|---|---|---|
| `REQUIRED` | B、C、D、E、V | `[*部门编码]：*部门编码不能为空` | 去首尾空白后为空 |
| `TOO_LONG` | 文本列 | `[姓名]：姓名【…】长度不能超过200个字符`（各列上限照档案 / 任职字段现有 zod 上限） | 超长 |
| `INVALID_DATE` | E、I、O、V | `[*入职日期]：*入职日期【2023/13/01】不是有效日期，请按yyyy/mm/dd填写` | 不是三种格式之一或日期不存在 |
| `INVALID_EMAIL` | C、M | `[*电子邮件]：*电子邮件【abc】格式不正确` | 用档案 `email` 字段的同一 zod 规则（`z.email().max(320)`，`personnel/validation.ts:39`）；比较前去首尾空白并转小写 |
| `INVALID_FORMAT` | K、L 等档案字段 | `[身份证号]：身份证号【…】格式不正确` | 档案写入端口 `appendEmployee` 抛出的字段校验错误，按字段映射回列 |
| `REFERENCE_NOT_FOUND` | D、F、G、H、W、X、Y | `[*部门编码]：*部门编码【zzf496nope】不存在或者已被删除，请检查`（F-496 N5 原文） | 编码 / 名称查不到 |
| `REFERENCE_AMBIGUOUS` | F、G、H、W、X、Y | `[职位名称]：职位名称【开发】对应多条记录，请检查` | 名称匹配到多条（职位、职务、职级、字典名称都不唯一） |
| `REFERENCE_DISABLED` | W、X、Y | `[离职类型]：离职类型【主动离职】已停用，请检查` | 字典项已停用（F-139 口径） |
| `DEPARTMENT_DISABLED` | D | `[*部门编码]：*部门编码【D-01】在任职期间已停用，请检查` | F-139 §4 区间校验（U3 保守保留） |
| `RANGE_INVERTED` | V | `[*最后工作日]：*最后工作日【2020/01/01】不能早于入职日期` | H > L |
| `NOT_HISTORICAL` | V | `[*最后工作日]：*最后工作日【2026/12/01】必须早于今天，今天及以后的离职请走离职流程` | L ≥ 今天（租户时区） |
| `NOT_SUPPORTED` | Z | `[离职说明]：离职说明【…】暂不支持导入，请清空后再导入` | 复刻没有对应字段的列有值 |
| `EMAIL_IN_EMPLOYEE` | C | `[*电子邮件]：*电子邮件【syn.a@example.com】在员工信息中已存在，不允许导入` | §4.4 a 类 |
| `EMAIL_DUPLICATE_IN_FILE` | C | `[*电子邮件]：*电子邮件【syn.a@example.com】在导入文件中重复出现，无法导入` | §4.4 c 类 |
| `LOGIN_TAKEN` | C | `[*电子邮件]：当前邮箱已被使用，请更换邮箱` | §4.4 b 类（报错但已建） |
| `FIELD_HIDDEN` | 任一列 | `[*部门编码]：无查看权限，错误原因已隐藏` | 下载人当前看不到该列对应的字段（§8.2） |
| `SUBMITTER_FORBIDDEN` | 无列 | `提交人已无导入权限，本行未导入` | 执行期权限复核失败（§6.2） |
| `SYSTEM_ERROR` | 无列 | `系统处理中断，本行未导入，请重新导入` | 重试上限后仍失败（§6.3） |

- 原因码集合导出为 domain 常量 `EXIT_IMPORT_REASONS`，单测逐个核对都有文案（新增原因码漏配文案时变红）。文案放在 domain 的文案常量里，前端不再映射原因码（错误文件只由后端生成），页面上不出现英文原因码（DEC-045）。
- 北森只取证到 D 列“不存在”这一条的完整原文，以及 a、b、c 三类的后半句。前缀 `[<列名>]：` 套用到 a、b、c 三类、其余原因码的后缀都是复刻按同一格式自拟的，差异登记（§15）。
- 判定顺序：形状（必填 / 长度 / 格式 / 日期）→ 同文件重复（c 类，提交时判定）→ 在职员工电子邮件（a 类）→ 引用与字典 → 区间 → 不支持的列 → 写入（档案端口校验）→ 账号登录名（b 类，写入时由账号函数判定，§4.5）。前一步出错的行不再做后面的业务判定，但同一步内的多个列错误一起报（例如 B 和 D 同时为空，两条都报）。
- 同文件重复在**提交时**判定（§6.1）：它取决于整批，执行器重启后也不能改变结论。比较键为 `lower(btrim(C))`；C 为空或格式不对的行不参与重复判定（已经有自己的错误）。

### 3.4 版本链、幂等、锁怎么改

- **版本链不变**：一条 hire（effectiveDate = H）、一条 leave（E = L+1），各自写 `version_no = 1` 的人工版本（F-139 §8）。两条任职的 `jobNumber` 写 `null`（员工工号为空，§3.5）。
- **档案**：人员档案首个版本由档案写入端口 `appendEmployee(tx, ctx, employeeId, patch, 0, false)` 写入（与入职落地同一端口，`entry-actions.ts:407`），patch 为本行非空的档案列（至少含 `name`、`email`）。T / U 有值时，由 `saveSubset` 写一条教育经历（与 `intern-profile.ts` 同一端口）。系统反写列（`lastSchool`、`major`）由子集端口照常反写，导入不直接写。
- **锁**：按 `租户 + lower(btrim(电子邮件))` 取事务级 advisory lock（替换 F-139 的工号锁）。每行一个事务，每个事务只锁本行邮箱，不需要排序。组织设置锁、编制锁照旧按 `org/locks.ts` 的顺序取（离职 / 入职落地本身仍写编制占用）。
- **与其他建档入口互斥**：a 类判定读的是档案最新版本的 `email`。手工入职建档写档案 `email` 时不取同一把 advisory lock，所以“同一邮箱同时手工建档 + 导入”在极窄的并发窗口里可能两边都成功，结果是两个人员档案电子邮件相同。复刻的档案 `email` 本来就没有唯一约束（手工入职也允许重复），这一点不比现状更差；不新增跨入口锁，记 §14 A11。
- **命令幂等**：批次级，见 §6.4。

### 3.5 工号为空（N1）

**迁移（S1）**：`ALTER TABLE employment_employees ALTER COLUMN code DROP NOT NULL`。

- 唯一索引 `employment_employees_tenant_code (tenant_id, lower(code))` 保留：PostgreSQL 唯一索引里 NULL 互不相等，同一租户可以有任意多个工号为空的人员；非空工号之间的唯一性不变。

### 4.1 每个建了人的行的账号终态

### 4.2 虚拟登录名

- 格式：`va-<账号 ID 去掉连字符后的 32 位小写十六进制>@virtualaccount.invalid`，例如 `va-3f2a9c10b7d44e8f9a1b2c3d4e5f6a7b@virtualaccount.invalid`。
- 生成：在 §4.5 的 SQL 函数里，先 `v_id := gen_random_uuid()`，再用 `v_id` 拼出登录名，`INSERT INTO users (id, email, …)` 一条语句写入。应用层不拼、不传。
- 唯一性：由账号 ID（UUID）唯一推出；`users.email` 的 UNIQUE 约束兜底。万一 23505（UUID 碰撞，可以忽略），函数不吞，按系统错误处理（§6.2 退避重试，下次换一个 UUID）。
- 为什么不照抄北森的 `<13位数字>@virtualaccount.upaas`：`.invalid` 是 RFC 2606 保留的顶级域，保证这个地址不可能被注册、也不可能收到邮件；用账号 ID 生成无需再建序号表，也不会暴露账号创建顺序。北森的 13 位数字规则未取证（看起来像时间戳或序号）。差异登记 §15。
- 用途：只是一个“占位登录名”，没有发放任何凭据，用户不知道它，所以不能用来登录（§4.6）。重聘时由 F-328 把登录名改为员工电子邮件（`docs/02_业务建模/30` 第 630 行：登录用户名从虚拟账号变为联系邮箱），本 F 不改这条链路。
- 小写：满足 `users_email_lowercase` 检查。

### 4.3 联系邮箱：取绑定档案的电子邮件，不新增列

- 核对结果：`users` 只有 `email` 一列（`tenancy.ts:60`），它是登录名；账号上**没有**单独的联系邮箱列。复刻的“全部用户”页（`settings/user-columns.tsx:20`）把 `email` 列显示为“联系邮箱”，实际展示的是登录名。
- F-328 规格把联系邮箱定义为“员工电子邮件”（`docs/02_业务建模/30` 第 630 行），所以最小做法是**不新增列**：联系邮箱 = 该账号绑定人员档案最新版本的 `email`；没有绑定人员（外部用户等）时为空。
- 后端（S1）：`tenant-users.ts` 的 `viewsOf`（`:116-145`）在现有 `email` 之外加一个键 `contactEmail: string | null`，读绑定人员的档案最新版本 `email`（一次批量查询，有界，与 `accountsOf` 同页）。`email` 键的含义不变，仍是登录名；登录名为 NULL 时照现行 `account?.email ?? ''` 输出空串。`GET /permission/users` 与 `GET /permission/users/:userId`（`user-routes.ts:50、60`）的 F-039 投影登记 `contactEmail`，生成物按 DEC-430① 重算。
- 前端（S4b）：“全部用户”页把现在的“联系邮箱”列改名为“登录用户名”（数据仍是 `email`，空串显示「--」），新增“联系邮箱”列（`contactEmail`，空值显示「--」）。北森账号页同时有“登录用户名”和“联系邮箱”两项（F-496 N3、N4 A 行），与此对应。
- 不做：不把联系邮箱写进 `users` 表，不新增 SQL 函数，不改外部用户登记的口径。

### 4.4 三类冲突（替换第 1 版 §3.2 的“邮箱已占用”）

比较键一律是 `lower(btrim(C))`。

| 类 | 判定范围 | 结果 | 行状态 / 计数 |
|---|---|---|---|
| a | 本租户**全部人员**档案最新版本的 `email` 字段（任一雇佣状态：在职、离职、待入职都算）。不看 `backupMail`（个人邮箱）、`workEmail` | 整行拦截，**不写任何数据**；`EMAIL_IN_EMPLOYEE` | `failed`，计入错误数 |
| b | 平台**全部**账号的登录名 `users.email`（任一租户、任一状态，含虚拟登录名），且本行没有命中 a 类 | 照常建人员、档案、两条任职、离职、账号；账号**没有登录名**（`users.email = NULL`）；`LOGIN_TAKEN` | `created_with_error`，计入错误数，也计入已建人数 |
| c | 同一批（同一文件）内其他行 | 所有命中行都拒（DEC-834③），不写任何数据；`EMAIL_DUPLICATE_IN_FILE` | `failed`，计入错误数 |

- 个人邮箱（M 列、档案 `backupMail`）不参与判定：既不拿 M 去比，也不拿别人的个人邮箱来比（F-496 N4 B 行）。
- “已删除人员不参与判定”（F-496 N4 C 行）：复刻没有删除人员的功能（没有删除 `employment_employees` 的代码路径），所以这一条在复刻里没有可触发的场景，不写分支。
- a 类的范围取“全部人员”，不是字面上的“在职员工”：北森的范围是“员工信息里的电子邮件，不含已删除人员”（F-496 N4 小结①），离职人员也在员工信息里；如果只看在职，同一份文件导两次就会建出两个同邮箱的离职人员。记 §14 A12。
- 判定时点：c 类在提交时（§6.1）；a 类在执行器取到邮箱锁之后、写入之前；b 类在写账号时由 SQL 函数判定（§4.5），与插入在同一语句里，没有“先查后插”的竞态。
- 第 1 版“本租户档案的工作邮箱 / 个人邮箱算已占用”“全局账号已存在就整行拒”两条口径**作废**。

**关闭第 1 版 A2**（`EMAIL_TAKEN` 暴露“邮箱在平台上已有账号”）：新口径下没有“平台已有账号就整行拒”的判定了。b 类照北森原样报「当前邮箱已被使用，请更换邮箱」，它确实会让有导入权限的人得知“这个字符串是某个账号的登录名”，但：①这是北森的原样行为（F-496 N4 A 行），DEC-838① 已拍板照做；②只有满足导入门槛（§6.1：人员新增权、档案字段写权、两个对象的显式看全部范围、导入按钮）的人能触发，与现有重聘改登录名返回 `EMAIL_TAKEN` 的暴露程度相同（`user-provisioning.ts`）；③不返回对方账号的 ID、状态、租户。所以 A2 关闭，不再单列。

### 4.5 迁移与 SQL 函数（S1 放开登录名非空；S2 新函数）

**S1 迁移**：`ALTER TABLE users ALTER COLUMN email DROP NOT NULL`。

- UNIQUE(email) 保留：多个 NULL 互不冲突；非空登录名唯一性不变。
- `users_email_lowercase (email = lower(email))` 保留：NULL 使检查为 unknown，视为通过。
- Drizzle 类型 `email: string | null`。只有本 F 的导入函数会写 NULL；`tenant_provision_account`（0033）仍拒绝 NULL / 不合法邮箱，其他建账号入口不变。

**S2 新函数**：`tenant_provision_import_account(p_contact_email text, p_display_name text, p_actor uuid, p_command_id text) RETURNS TABLE (account_id uuid, login_assigned boolean)`，SECURITY DEFINER，与 `tenant_provision_account`（0033）同一组权限：

1. 校验 `p_contact_email` 等于 `lower(btrim(p_contact_email))` 且非空，不一致就抛错（防止调用方绕过规范化）。
2. `v_id := gen_random_uuid()`；如果 `EXISTS (SELECT 1 FROM users WHERE email = p_contact_email)`，`v_login := NULL`、`login_assigned := false`；否则 `v_login := 'va-' || replace(v_id::text, '-', '') || '@virtualaccount.invalid'`、`login_assigned := true`。
3. `INSERT INTO users (id, email, display_name, status) VALUES (v_id, v_login, p_display_name, 'disabled')`。
4. 写 `platform_audit_events` 的 `user.create`（after 带 `status: 'disabled'`、`source: 'exit_import'`、`loginAssigned`，**不写**联系邮箱或登录名原文以外的字段），和 0033 同一写法、同一事务。
5. 返回 `(v_id, login_assigned)`。不返回任何已有账号的 ID、状态或租户。

- 第 2 步的 `EXISTS` 与第 3 步的插入不需要锁：插入的登录名要么是 NULL，要么是由新 UUID 生成的虚拟登录名，都不会和并发插入的其他登录名撞上；b 类判定结果只决定“有没有登录名”，即使并发窗口里对方账号刚建好，最坏结果是本行拿到了虚拟登录名而没报 b 类错误——这与“导入在先、对方建账号在后”的结果相同，不产生重复登录名。
- 只授予 `app_owner` 等应用角色 EXECUTE（照 0033）。应用角色仍不能直接 `INSERT INTO users`。
- 第 1 版的 `tenant_provision_disabled_account` **不建**。

### 4.6 登录侧行为

- 复刻目前没有按登录名登录的接口：身份由 `IdentityResolver` 解析出 userId（开发期 HMAC 头，正式登录由 B-01 提供），`tenantContext` 只放行 `users.status = 'active'` 的账号（`apps/api/src/tenant-context.ts:34`），停用账号一律 401 `UNAUTHENTICATED`。导入建的账号都是停用的，所以不能进入任何租户。
- 按登录名查找的现有位置：平台运维 CLI `ops/platform-cli.ts:95`（`eq(users.email, email)`，输入是非空邮箱，NULL 永远不命中）、平台建账号 `platform/routes.ts:85`（入参必填邮箱）、`tenant_provision_account`（`ON CONFLICT (email)`，NULL 不会成为冲突目标）。登录名为 NULL 的账号不参与任何按登录名的查找，这些位置都不用改，AC-31 断言 CLI 查找不命中。
- 读登录名的现有位置：`tenant-users.ts:134`（已是 `?? ''`）、`getTenantUser`（类型改 `string | null`）、`user-provisioning.ts` 的 `keepBinding`（`:106-129`）。`keepBinding` 在成员关系不是 active 时会用 `current.email` 调 `provisionAccount`（`:120`）：登录名为 NULL 时 `tenant_provision_account` 会拒绝。导入建的成员关系是 active，正常走不到这里；为防万一，S1 在 `keepBinding` 里对 `current.email === null` 先抛 409 `ACCOUNT_LOGIN_MISSING`（「该账号还没有登录名，请先维护员工电子邮件后再办理」），不让它变成 500。AC-31④ 覆盖。
- 撤销离职后账号会恢复 active（§4.7），这时登录名为虚拟登录名或 NULL，都没有发放凭据，仍无法登录；正式登录（B-01）上线时，须保证“没有登录名或登录名是 `@virtualaccount.invalid` 的账号不能作为登录入口”。这一条是 B-01 的约束，记 §14 A13。

### 4.7 撤销离职、改期、重聘、幂等与重试

- **撤销离职**：`onCancelled → queueExitAccount(restore = true)` 找到 §4.1 登记的任务，按现有恢复判定把账号恢复为 active（与北森“删除离职记录后账号变启用”一致，F-490 清理路径 1）。b 类账号恢复为 active 后仍没有登录名；登录名不在撤销时补，与北森一致（北森 N4 A 行账号的登录用户名为「--」）。导入不需要另写分支，验收覆盖（AC-17）。
- **改期替代**：`replaceExit`（F-139 §8.3 第 2 行）经现有订阅方处理，不变。
- **重聘**：日后在入职管理中重聘该人员时，F-328 `tenant_rehire_login_email`（0184）把登录名从虚拟登录名或 NULL 改为档案电子邮件，再由 `enableRehireAccount` 启用。b 类人员的档案电子邮件恰好是别人的登录名，重聘时会得到 `EMAIL_TAKEN`，要先把档案电子邮件改掉才能重聘；这是现有重聘口径，本 F 不改，AC-22 覆盖成功路径和这条拦截。
- **幂等与重试**：
  - b 类行在**同一个行事务**里完成全部写入并把行状态记为 `created_with_error`，不存在“建了一半”的中间态；执行器崩溃重启后，该行已不是 `pending`，第 1 步复核跳过它（§6.2），不会重复建人。
  - 用户拿错误文件改正后重导：b 类行如果没改 C 列，会命中 a 类（档案里已经有这个电子邮件）而被整行拦截，不会建第二个人；改了 C 列则视为另一个人，照新邮箱判定。这是北森同样的结果（同一邮箱在员工信息里已存在）。
  - 命令重放与重复提交见 §6.4。

## 6. 异步导入（U7）

### 6.1 提交（`POST /exits/import`，同步部分）

1. 权限链同 F-139 §5.1，五步照旧（功能权、按钮、字段写权、显式看全部范围、命令守卫复核），**档案字段改为按真实写入判写权**：
   - 人员对象（`EMPLOYEE`）：新增权加字段写权 `{ code, name }`（现行 `exit-import.ts:177`，与 `POST /employees` 同一组字段）。导入不写工号，但建人入口的门槛与 `POST /employees` 保持一致，不因为本入口不写工号而放宽 `code` 的写权要求（最保守，§14 A14）。
   - 任职对象：按 `writtenFields(rows)` 判本批实际写入的任职字段（现行 `exit-import.ts:191`）；新增的 `levelId`、`place` 随之进入判定。
   - **人员档案对象（`PERSONNEL_OBJECT`，新增）**：本批所有行非空档案列的并集（`email` 必在其中，另有 `backupMail`、`idType`、`idNumber`、`mobilePhone`、`gender`、`birthday`、`nation`、`politicalStatus`、`householdAddress`、`registAddress`、`workDate` 中出现的那些）判 `update` 字段写权；T / U 有值时再判教育经历子集的 `create` 权。判法与实习生建档 `requireInternProfileAccess`（`intern-profile.ts:66-96`）相同：任一字段无权整批 403；范围要求 `PERSONNEL_OBJECT` 的显式看全部（与人员对象一致）。
   - **修订第 1 版 P2-2 的结论**：第 1 版说“邮箱不进入任何字段权限判定”，依据是当时的邮箱只作登录名、而登录名不是人员字段。N3 取证后，C 列写的是档案 `email` 字段（`personnel/fields.ts:34` 登记的普通档案字段），所以它**必须**判档案字段写权；登录名改为系统分配，不来自用户输入，不需要判权。F-039 不再登记 `controls: ['email']`，改为与实习生建档相同的 `guards: [..., 'employment.exitImportProfile']` 加 `controls: ['profile']`（§10.1）。
   - 不新增授权项，授权版本不动（§10.2）。验收用真实授权器（AC-23、AC-37）。
2. 报文形状校验（§3.2 整批拒绝的那几项）。
3. 在 `runWrite` 命令台账内（`Idempotency-Key` 必填），同一事务里：
   - 插入 `exit_import_batches`：status = `queued`，total = 行数，file_name，submitted_by = 当前用户，command_id = 本命令。
   - 插入 `exit_import_rows`：每行一条，存 25 个原始值（§6.5）。形状不合法的行，以及 c 类命中的行，直接写 status = `failed` 和错误；其余写 `pending`。
   - 写审计 `employment.exit_import.submitted`（对象为该批次，after 为 `{ total, prefailed }`，不含行内容和文件名）。
   - `afterTransactionCommit` 登记键 `exit-import:<tenant>:<batchId>`，回调**只调用** `wakeExitImports(db, tenantId)`，不在回调里执行批次（`packages/db/src/after-commit.ts:58` 会逐个 `await` 回调，`runWrite` 要等它返回后才回响应）。
4. 返回 `202 { batchId, status: 'queued', total }`。命令台账重放时同样返回 202，不再唤醒；即使漏唤醒，也由调度轮询接续（§6.2）。前端只用回执关闭弹窗，不展示 batchId。

提交时**不**做 a 类判定和引用判定：这些依赖执行时的库内状态，放在执行器里做，避免“提交时通过、执行时失败”的双口径。

### 6.2 执行器（S3a 主体，S3b 恢复与重试）

第 1 版的唤醒、单飞、调度兜底、认领 SQL、租约、测试接缝**原样保留**，只把片号 S2a / S2b 改为 S3a / S3b：

- 文件：`apps/api/src/modules/employment/exit-import-worker.ts`，导出 `drainExitImports(db, tenantId)`、`wakeExitImports(db, tenantId)`、`startExitImportScheduler(db, options)`。
- **唤醒（S3a）**：`wakeExitImports` 同步把 `tenantId` 放进本进程待处理集合，没有在跑的循环时用 `setImmediate` 排一个，立即返回；同一进程同一时间只有一个循环，状态按 `Db` 实例存在 `WeakMap`；循环异常只记 `{ type: 'employment.exit-import.wake-failed', tenantId, category }`，不往上抛。
- **调度兜底（S3b）**：照 `startExitAccountScheduler`（`exit-account-worker.ts:305`），在 `startEmploymentActivationScheduler`（`activation-scheduler.ts:264`）里并列启动，间隔 `min(60s, intervalMs)`；每一轮遍历启用中的租户，先调一次 `drainExitImports`，再做一次过期清理（§8.3）。不改 `server.ts`，不新增环境变量。
- 认领：`UPDATE exit_import_batches SET status = 'running', lease_until = now() + interval '5 minutes', attempts = attempts + 1, started_at = COALESCE(started_at, now()) WHERE tenant_id = $1 AND id = (SELECT id … WHERE tenant_id = $1 AND (status = 'queued' OR (status = 'running' AND lease_until < now())) ORDER BY created_at, id LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING *`；每次只认领、处理一个批次。
- 执行期权限复核（S3b）：认领后、处理第一行前，用提交人身份重算 §6.1 第 1 步（含档案字段写权），并核对成员关系仍为 active；不通过时所有 `pending` 行一次性记 `failed`（`SUBMITTER_FORBIDDEN`），然后收尾。
- 逐行处理：按 `rowNo` 升序每次取 50 条 `pending` 行，每行一个 `withTenant` 事务：
  1. `SELECT … FOR UPDATE` 复核本行仍为 `pending`，不是就跳过。
  2. 取锁：电子邮件 advisory lock → 组织设置锁 → 编制锁。
  3. 行级判定：§3.3 的顺序（a 类、引用、字典、区间、不支持的列）。
  4. 写入：建档（`code = NULL`）→ 档案首个版本（§3.4）→ 教育经历（T / U 有值时）→ `tenant_provision_import_account` → 成员关系与绑定 → 入职业务 → 离职业务 → 状态事件 → 落地 → 账号任务 → 防御断言 → 审计（§10.3）。与 F-139 §6 步骤 2～8 相同，去掉手动黑名单一步。
  5. 账号函数返回 `login_assigned = true`：本行记 `succeeded`；返回 `false`：本行记 `created_with_error`，errors = `[{ column: 'C', reason: 'LOGIN_TAKEN' }]`。两者都记下 employee_id、exit_business_id，并续租。
  6. 第 3 步判定失败，或第 4 步抛出**业务** `AppError`（4xx 类，含档案端口的字段校验错误）时：回滚本行事务，再用一个新事务把本行记为 `failed`，按错误的字段映射回列字母写入 errors。
- 系统错误（非 `AppError`、5xx、锁超时、连接断开、虚拟登录名 23505）：本行事务回滚，**不**记失败，本次执行中止；批次保持 `running`，`last_error` 记错误类别，`lease_until = now() + 1 min`，由下一次唤醒或调度重新认领（S3b 加次数上限）。
- **测试接缝（S3a 建，S3b 扩展）**：`installExitImportTestHooks(db, { beforeBatch?, beforeRow?, failRow? })` 与 `exitImportIdle(db)`；安装时用 `isIsolatedTestDb(db)` 校验（与 `formula-binding-switch.ts:19` 同一守法），产品代码路径不读环境变量、不留开关（DEC-402）。

**失败兜底**（同第 1 版，片号顺延）：

| 中断 | 停在什么状态 | 怎么收敛 | 片 |
|---|---|---|---|
| 提交已提交，唤醒没跑 | `queued` | 进程重启后调度第一轮（≤ 60 秒）认领 | S3b |
| 执行到一半进程崩溃 | `running`，租约 ≤ 5 分钟后到期 | 重新认领，`attempts + 1`，从第一条 `pending` 行继续；已 `succeeded` / `created_with_error` 的行被第 1 步跳过 | S3a 认领；S3b 调度 |
| 某行遇到系统错误 | `running`，退避 1 分钟 | 同上；达到 `EXIT_IMPORT_MAX_ATTEMPTS` 后 `failed` 收尾 | S3b |
| 循环本身抛错 | 不变 | 记 `wake-failed`，由调度接续 | S3a 日志；S3b 调度 |
| 收尾事务失败 | `running`，没有 `pending` 行 | 下一次认领直接收尾；`WHERE status = 'running'` 守住，通知只发一次 | S3a |

S3a 合入到 S3b 合入之间没有调度兜底，写进 S3a 的 PR 描述；前端要到 S4a 才接入新接口，窗口内没有用户路径会触发导入。

### 6.3 收尾、重试上限与状态机

批次状态：`queued → running → completed`，或 `running → failed`（同第 1 版）。

| 状态 | 进入条件 | 离开 |
|---|---|---|
| `queued` | 提交事务提交 | 被认领 → `running` |
| `running` | 被认领；租约到期可以被重新认领 | 没有 `pending` 行 → 收尾；`attempts` 达到 5 且再次遇到系统错误 → `failed` 收尾 |
| `completed` | 所有行都不是 `pending` | 终态 |
| `failed` | 系统错误重试 5 次仍失败：剩余 `pending` 行一次性记 `failed`（`SYSTEM_ERROR`） | 终态 |

行状态：`pending → succeeded | created_with_error | failed`，三个都是终态。

收尾在一个事务里完成：

1. 统计 `created_count`（`succeeded` + `created_with_error`）、`error_count`（`failed` + `created_with_error`，即错误文件的行数，也是通知里的 N），写入批次行，设置 `finished_at`、`expires_at = finished_at + interval '15 days'`。
2. 把 `succeeded` 行的 25 个原始值置 NULL（数据最小化：成功行不进错误文件，不再需要原值）。
3. 写站内通知（§8.1，S3c 接线；S3a、S3b 的收尾先只做第 1、2、4 步）。
4. 写操作日志（§10.3）。

收尾用 `WHERE status = 'running' AND id = $batch` 守住，只有一方能收尾，通知只发一次（AC-08）。`EXIT_IMPORT_MAX_ATTEMPTS = 5` 为 domain 常量。`failed` 终态的批次不提供人工重试，重新导入即可。系统失败的批次同样发通知，N 含未处理的行（它们也在错误文件里，原因「系统处理中断…」）。

### 6.4 重复提交与幂等

|---|---|

### 8.3 错误文件保留 15 天

|---|---|---|---|---|
