## 1. 约束 1：业务内单调序号

**选用**：`employment_payload_versions.version_no`。

- 分配（main 实际写法，v1.1 更正）：
  - 人工写日期：`updateEmploymentBusiness`（`write-service.ts:258～264`）先 `bumpEmploymentBusiness` 递增业务 revision，再以**递增后的 revision** 作为新版本的 `version_no`（`appendEmploymentPayload` 的 `versionNo` 参数），因此人工版本的序号可能跳号；新建取 1。
  - 系统派生（迟到顺延、向后更新、序列同步、状态传播）：取 `previous.versionNo + 1`。迟到顺延与序列同步在 `lockEmploymentBusiness`（`record-store.ts:107`，员工行锁 + 业务头 `FOR UPDATE`）之后写；向后更新与状态传播依靠员工行锁串行。
  - 共同保证：同一员工的全部任职写入都先持员工行锁，同一业务的版本不会并发分配；唯一约束 `(tenant_id, business_id, version_no)` 使任何撞号直接报错而不是静默覆盖。同一事务内连续写出的两个版本（例如人工改期后立即迟到顺延）也有严格先后。
  - 计划日只依赖“同一业务内新版本的序号大于旧版本”。main 上人工编辑只发生在批准前（draft / in_review / rejected），且之前的派生写入都会递增 revision，revision 不小于最新序号，该前提成立。**F-140b 的人工改期发生在派生版本之后，不得再用 revision 作序号**：一律取 `previous.versionNo + 1` 并同时递增 revision；F-140b 迁移在计划列触发器里加断言 `NEW.version_no > 上一版本.version_no`，违反即拒绝写入。
- 写入面：凡会改变日期的写入，都落成一个载荷版本：人工写日期（新建、草稿 / 驳回 / 审批中修改、审批编辑，以及 F-140b 的人工改期），系统迟到顺延（`postponeLateTransfer`，R2-T03 的 `postponeLateExit`），立即生效时的顺延。
- 读取：计划日只读“最新版本（按 `version_no`）的计划列”，不读 outbox 改期事件。outbox 和审计事件照常写出，用于审计和对账；`employment.transfer.rescheduled` 的 `after` 增加 `versionNo`（F-140a 已加）。**任何读取点都不得用 `created_at` + `id` 判断日期先后**（同一事务共用 `ctx.now`，`id` 为 `gen_random_uuid()`）。
- 其他已有的单调序号，F-140b 沿用：状态事件 `event_no`（业务内）/ `event_seq`（全局 identity，`timeline.ts operationKey` 已按它取）；生效尝试 `attempt_no`（业务内）。

## 2. 约束 2：人工计划与系统实际分字段（F-140a，已实现）

### 2.1 列与规则

迁移 `0130_employment_planned_effective_date`：`employment_payload_versions.planned_effective_date date NOT NULL`。

| 版本类别 | 判定 | `effective_date` | `planned_effective_date` |
|---|---|---|---|
| 人工写日期 | `trigger_business_id IS NULL`，或首版（`previous_version_id IS NULL`） | 人工填写的日期 | = 本版本 `effective_date` |
| 系统派生 | `trigger_business_id IS NOT NULL` 且非首版 | 系统写入的实际日期（顺延时为执行日 a，其他派生版本照抄上一版本） | = 上一版本的计划（**沿用，不得改**） |

由 `BEFORE INSERT` 触发器 `employment_payload_versions_planned_date` 维护：

- 该列**一律由触发器推导**，插入时传入的值被覆盖。这是 DB 层护栏：任何写入方（包括绕过应用层的裸 SQL、整行复制的测试夹具）都不能直接设置计划，系统写入不可能把实际日期写成计划日。
- 应用层 `insertEmploymentRow`（`record-store.ts`）丢弃调用方带来的 `plannedEffectiveDate`。原因：派生写法普遍展开旧载荷（`...previous`），不丢弃就会把旧值带进来。这与 F-022 人员状态列的做法相同：读自库，写入时丢弃，由触发器维护。

### 2.3 纯函数镜像

`packages/domain/src/employment/planned-date.ts`：

```ts
resolvePlannedEffectiveDate(input: { versions: readonly PlanVersion[]; fallback: string }): string
PlanVersion = { versionNo: number; effectiveDate: string; manual: boolean }
```

先按 `versionNo` 排序再折叠：首版或人工版本把计划设为本版本日期，派生版本保持不变。输入顺序任意打乱，结果相同。序号重复抛 `RangeError`，按数据损坏处理，不任选一条。验收测试断言：命名反例与 24 组随机序列（全部版本同一 `created_at`）下，SQL 与纯函数结果一致。

### 2.4 离职的计划最后工作日

离职生效日 E = L + 1（`fields.ts parseEmploymentInput`），计划最后工作日 = 计划生效日 − 1，不另存列。R2-T03 D-14（列表与详情的“原定最后工作日”）照此计算。

### 2.5 与旧规则的等价性（为什么 main 行为不变）

- **main 旧规则**：首条调动改期事件的原日期，否则取最新载荷。main 上调动只能在批准前（draft / in_review / rejected）人工改日期，批准后载荷不可改（`PAYLOAD_IMMUTABLE`）。顺延只发生在批准后，首条顺延事件的原日期就是“顺延前最新版本的日期”，也就是最后一个人工版本的日期（中间的向后更新、序列同步、状态传播版本都照抄日期）。没有顺延时，最新载荷日期同样等于最后一个人工版本的日期。因此新旧两种规则对 main 可达数据结果相同。其他 kind 没有顺延，两种规则也相同。
- **R2-T03 v1.9 规则**（全部顺延事件原日期的最小值，否则最新载荷）：v1.9 不允许人工改期，论证同上，结果相同。
- **引入人工改期后（F-140b）**，只有新规则正确：第 6 轮的“首条改期事件”会取到人工改期前的旧日期；第 7 轮的“最后人工事件之后的首条顺延事件”依赖同一 `created_at` 下的 UUID 大小。新规则只看版本序号和类别，这两个问题都不存在（§5 F-140a 部分的 R-1～R-4）。

回归：AC-TRF-F017-*（含 same-day-order、late-pending、approval-dates）、AC-ORG-32-late-fail-closed*、AC-EMP-18～21、AC-JOB-08-11、AC-EST-* 与编制投影原样通过（§6）。

## 3. 人工改期命令（F-140b，设计）

### 3.1 入口与放开范围（约束 4 末条：未放开的入口仍拒绝且无写入）

改期入口来自规格 `30` 第 84 行：离职管理【编辑离职】改最后工作日；审批中的离职由当前审批人在【同意 / 编辑】中修改；原站另有任职记录【编辑任职】改离职记录开始日期。R2-T03 §7.2 的 #1～#7 在 F-140b 中逐行处理：

| R2-T03 §7.2 # | 入口 | F-140b |
|---|---|---|
| 1 | `PATCH exits/:id`（draft / rejected / in_review / approved / effective） | **放开**：draft / rejected 写人工版本；in_review 同 #3 / #4；approved 按 §3.2；effective 按 §3.4 |
| 2 | 通用 `PATCH businesses/:id` | **放开 draft / rejected**（与 #1 同一判定点、同一实现）；approved / effective 仍拒绝 `EXIT_DATE_IMMUTABLE`，引导走 `PATCH exits/:id`，确保改期一定经过 §3.2 的重算 |
| 3 / 4 | 审批编辑 / 编辑并同意 | **放开**：写人工版本；授权与盲审检查先于日期判定（第 8 轮 P3-01），因日期被拒绝的请求无业务写入；编辑并同意时人工版本先写，随后审批落地读到的计划列就是新日期 |
| 5 / 6 / 7 | `PATCH records/:id`、`records/batch-edit`、导入 edit 行 | **保持拒绝** `RECORD_DATE_IMMUTABLE`，无写入。原站“编辑任职改离职记录开始日期”入口留待取证后再议（§7 待定 P-3） |

**调动**：approved 调动**不开放**改期。依据 `08` Q-M0-50② 手册：审批通过的离职可以在【编辑离职】改最后工作日，调动则只见撤销后重新发起。草稿、审批中、驳回调动的改日期 main 已经支持，写的是人工版本，约束 2 自动适用，不需要新代码。若以后要开放 approved 调动改期，按本节同一规则另行设计。

判定点：沿用 R2-T03 §7.2 “规范化后与当前最新载荷不同”的比较，比较对象改为当前计划列（= 当前人工意图）。日期相同不视为改期。

**第 7 轮自构①在本设计下**：approved 离职 E = 11-10，11-01 改到 E = 10-20。R3 写出人工版本 v(n+1)，计划 10-20；R6 窗口为空，写出派生版本 v(n+2)，实际 11-01，计划沿用 10-20。两条版本的 `created_at` 相同，但 `version_no` 不同，计划日恒为 10-20（F-140a 的 R-1 已在字段层验证）。

### 3.2A 三种日期的校验分工（v1.1，关第 1 轮 P2-2）

改期涉及三种日期，各自只在一个地方校验，互不替代：

| 日期 | 定义 | 在哪校验 | 校验什么 | 不校验什么 |
|---|---|---|---|---|
| 人工计划日 E₁ / L₁ | 改期命令写入的意图（计划列） | R1 | 合法日期；L₁ ≥ 本周期入职日；与当前计划相同不算改期 | 不与已落地记录的日期比较 |
| 最终执行日期 f | `finalExecutionDate`：离职 = max(E₁, a)，a 为执行日 | R6、调度、HR 重试进入 `activateExit` 时 | 0a 前序（§5.0 队列，按 f → 计划日 → 开新周期 → 操作序号排序）；步骤 0 迟到窗口 [E₁, a)：位置在离职之后且起始 < a 的已落地记录 ∪ 计划日 ∈ [E₁, a) 且排在离职之后的未落地申请，非空即 `REBUILD_REQUIRED`（fail-closed，交 HR）；**步骤 0d 后续已落地记录**：同周期、时间轴位置在离职之后的已落地非调动记录，存在即 `EXIT_LATER_RECORD_EXISTS`（fail-closed，§3.2C）；周期（`EMPLOYMENT_CYCLE_MISMATCH`）；§6B 在职段延长 | — |
| 同日位置 | `timelinePosition(f, 计划列, 操作序号)` | 落地时 | 契约 C-3：同一 f 上按计划日、再按操作序号定位，决定前驱与继承来源；落地后起始晚于 L′ 的已落地未来调动按 R2-T03 §5.8 摘下 | — |

已生效离职的重定位（§3.4 第 1 行）是另一回事：它直接把记录的**实际**起始日改成 E₁（不经顺延），比较对象也是已落地记录的实际日期，所以保留“不越过同周期其他记录”（`EXIT_RESCHEDULE_CROSSES_RECORD`）。approved 改期只改计划，实际日期在执行时才确定，因此不适用这条规则。

**逐例推演**（公共条件同 §5.2；“R1”列为人工计划日校验，“执行”列为 R6 或调度时的 f、窗口与位置）：

| 例 | 改期 | R1 | 执行 | 结果 |
|---|---|---|---|---|
| F-1 | 10-08：E 10-16 → 10-30 | 过（10-30 > 入职日；不与任何记录比较） | 10-08 < E₁，不执行。11-01 调度：f(T) = f(离职) = 11-01，计划 10-20 < 10-30 → 队列 [T, 离职]；T 窗口 [10-20, 11-01) 含离职申请（计划 10-30，排在 T 之后）| T `REBUILD_REQUIRED`；离职 0a 前序失败 → suspended；T 不被作废 |

| F-4 | 11-01：E 11-10 → 10-20 | 过 | R6：0a 无前序；窗口 [10-20, 11-01) 为空 → 派生版本 实际 11-01 / 计划 10-20；当日无其他记录，追加 | 11-01 落地，L′ = 10-31，计划日 10-20 |

### 3.2C 执行时的后续已落地记录校验（v1.2，关第 2 轮 P2）

**问题**：v1.1 放宽 R1 后，人工计划日可以早于已落地的未来记录。迟到窗口只看 [E₁, a) 内的记录；`assertSuccessorSequence`（`write-service.ts:370`）只在同日插入（`position.shifted`）时检查紧随的那一条。两者都看不到“最终执行日期之后”的已落地记录。

第 2 轮反例：
- 员工 10-01 入职，同周期已有 11-10 生效的直接转正（已落地）；离职原计划 E 11-20。
- 10-06 HR 把离职改到 L 10-19 / E 10-20；10-20 离职正常执行，时间轴把离职区间写成 `[10-20, 11-10)`。
- 到 11-10，当前记录又变回转正，人员状态 = 3（正式）：员工在离职后重新在职。

**选择：执行时拦截**，不在改期时拒绝。理由：
- 最终执行日期 f 和插入位置要到执行时才确定；
- 改期之后、执行之前，仍可能新增已落地记录；
- 这一步放在 `activateExit` 里，审批落地、R6 立即执行、调度、HR 重试四个入口自动共用，不会漏入口。

| 项 | 规则 |
|---|---|
| 位置 | `activateExit` **步骤 0d**：在步骤 0（最终日期 f、迟到窗口）之后，步骤 1（作废在途申请）和步骤 2（落地）之前，与其他步骤同一保存点 |
| 判定 | 先按 `timelinePosition(f, 离职)` 求离职的插入位置（同日按计划日、再按操作序号，C-3）。取同一员工、同一任职周期（`staff_id` = 离职所属周期）中，时间轴位置在插入位置**之后**的全部已落地记录：`(start_date, sort_order) ≥ (f, order)`，同日被挤后的那条也算 |
| 例外 | `kind = 'transfer'` 的记录不在此拦截，按 R2-T03 §5.8 摘下并提示 HR（DEC-263②） |
| 结果 | 存在其他 kind 的记录（转正、实习转正、组织调整、离职、退休等）时：<br>① 不写任何任职数据；<br>② 生效尝试记 `failed`，`reason = EXIT_LATER_RECORD_EXISTS`，detail `{ plannedEffectiveDate, finalEffectiveDate: f, blockers: [{ id, kind, startDate }] }`，范围外的记录只计件数；<br>③ 审计 / outbox 写 `employment.activation.failed`；<br>④ HR 待办提示：“离职生效日之后已有任职记录（如转正），离职生效后员工会重新变为在职。请先删除或调整这些记录，或把最后工作日改到它们之后，然后重试。” |
| R6 下的表现 | 改期命令本身（R3 / R4）照常提交；立即执行在保存点内失败，响应的 `activation` 带出这次失败。与审批通过后落地失败的处理一致 |
| 与同日规则的关系 | 同日位置在离职之后的非调动记录也由本步拦截，先于步骤 2 的 `assertSuccessorSequence`（后者保留作兜底）。同日位置在离职之前的记录（如 F-5 对照组的 T）不在判定范围 |
| 适用范围 | 本规则不依赖改期：离职创建时填的 L 就早于已落地未来记录，也会落入同一缺口。规则写在 `activateExit` 内，建议 R2-T03 **B3-1** 实现 `activateExit` 时一并加入（提请总编排同步到 B3-1 派发单），F-140b 只复用 |

**同日情形下 §5.8 的摘下条件**（第 2 轮 P3，v1.2 明确）：§5.8 写的“起始日 S > L′”在同日情形下要按位置理解，只有时间轴位置在离职插入位置**之后**的调动记录才摘下。

同日位置在离职之前的调动（F-5 对照组：S = E′，但按 C-3 排在离职之前）不摘下。它的区间按 DEC-108 收缩为空，并作为离职的前驱。

实现时，摘下与步骤 0d 用同一个“插入位置之后”的记录集合，再按 kind 分流：调动走摘下，其余 kind 走 `EXIT_LATER_RECORD_EXISTS`。

| 例 | 场景 | 0d 判定 | 结果 |
|---|---|---|---|
| **F-16** | 10-01 入职；同周期已落地 11-10 直接转正；离职 E 11-20，10-06 改到 L 10-19 / E 10-20 | 10-20 执行：f = 10-20，插入位置之后有转正（11-10） | R1 通过，改期提交；10-20 记 failed `EXIT_LATER_RECORD_EXISTS`（blockers = [转正 11-10]），时间轴与人员状态不变，出现 HR 待办 |
| F-16 对照 | 同上，但改到 L 11-14 / E 11-15 | 插入位置之后没有同周期记录 | 11-15 正常落地 |
| F-5 | 同日调动 T 的位置在离职之后 | 调动属于例外 | 按 §5.8 摘下 T，离职落地 |
| F-5 对照 | 同日调动 T 的位置在离职之前 | 不在判定范围 | 离职落地，T 的区间收缩为空 |
