# F-474-8b 社保建模与调动薪资字段口径：设计

> 任务：F-474-8b（DEC-776 / DEC-778；续批规划 F-474-8 行）。只出设计，实现另派 8c（缺口 #12）。
> 基线：main `c20147c6f`。作用对象全部是**复刻系统**；北森原站只引用 02 的只读取证说明 `8a_说明.md`（2026-11-03，截图只在本机取证目录，不入库；下文称“8a 取证”）。没有证据的标“待取证”。
> 约束：DEC-402（不加兼容开关、不考虑存量）；DEC-002 把薪酬社保列为**暂缓**模块，所以本设计的主轴是“**调动所需最小集**”，完整社保模块列为“不做 / 后补”选项交 00 定（§8-U1）。

## 0. 一页摘要

- 原站调动表单的“薪资调整”组其实**只有社保三对字段**：缴交地 / 缴交方案 / 缴交公司，各有只读“原值”和可改“调整后”，6 个全部非必填，且与“是否调整薪资”选项无关。
- “原值”不属于任职记录，来自员工的**社保档案**；“缴交公司”也不是方案的属性，是**档案规则**按“合同公司”等规则带出到档案上。所以光有调动表单上的 3 个新字段无法闭环，必须有一个最小的“社保档案”做原值来源和落点。
- **推荐（U1-A）**：只建调动需要的最小集 = 地区字典 + 缴交方案主数据（头 + 版本，不含险种明细）+ 员工社保档案版本链 + 调动联动写档案；险种明细、档案规则、待增减员处理、月结账单全部后补。
- 复用：缴交公司取合同公司主数据（`contract_companies`），不另建；调整值随调动联动版本保存，生效日由现有定时联动落到档案版本链；“变更前”不单列，从档案上一版取。
- 授权类变化：新增档案对象 / 方案对象进授权目录，见 §4.3、§8-U5。

## 3. 数据模型与迁移草案

以下只对“最小集”（U1-A）建模；迁移序号占位，由 `pnpm merge:main` 定；除 §3.1 的公开全局字典外，所有业务表带 `tenant_id`、`enable_tenant_isolation`，授予 `app_user` 的权限最小化。

### 3.1 地区字典（全局只读，非租户）

```sql
CREATE TABLE admin_regions (
  code        text PRIMARY KEY,                 -- 行政区划代码（6 位）
  parent_code text REFERENCES admin_regions(code),
  level       smallint NOT NULL CHECK (level BETWEEN 1 AND 3),
  name        text NOT NULL,
  CONSTRAINT admin_regions_level_parent CHECK ((level = 1) = (parent_code IS NULL))
);
GRANT SELECT ON admin_regions TO app_user;      -- 不授予写；随迁移播种
```

- 这是公开的全局字典，不含租户数据，所以不做 RLS；实现单必须同时在 `tests/guard-rls.test.ts:103-135` 的 **`platformTables` 非租户表豁免**和 **`tenantReadable` 租户角色可读白名单**登记 `admin_regions`，理由写“公开行政区划、无租户数据、仅 SELECT”。表注释写同一理由，不引用未经核实的先例。
- 数据来源拟用公开行政区划标准，具体版本 / 发布来源由实现单固定并记录摘要，当前尚未选定，不能声称已核出精确行数。最低到区县（3 级），待取证 ④ 决定是否更细；按每区划一行数据记录，暂预留 **N ≤ 4000 行生成数据**，与手写迁移、生成 / 校验脚本、测试分开计（§6）。不得压成长行规避预算。
- 历史区划变更不处理（DEC-402 不考虑存量）；档案里保存区划 `code`，展示名取字典当前名。

### 3.2 `social_insurance_plans` + `social_insurance_plan_versions`（缴交方案，版本表）

```sql
CREATE TABLE social_insurance_plans (
  tenant_id uuid NOT NULL REFERENCES tenants(id),
  id        uuid NOT NULL DEFAULT gen_random_uuid(),
  code      text NOT NULL,                      -- 业务编码，租户内唯一
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, id),
  UNIQUE (tenant_id, code)
);
CREATE TABLE social_insurance_plan_versions (
  tenant_id   uuid NOT NULL,
  id          uuid NOT NULL DEFAULT gen_random_uuid(),
  plan_id     uuid NOT NULL,
  name        text NOT NULL,
  region_code text NOT NULL REFERENCES admin_regions(code),
  effective_month date NOT NULL CHECK (effective_month = date_trunc('month', effective_month)::date),
  stop_month  date,                              -- 空 = 长期有效
  enabled     boolean NOT NULL DEFAULT true,
  revision    integer NOT NULL DEFAULT 1 CHECK (revision > 0),
  PRIMARY KEY (tenant_id, id),
  FOREIGN KEY (tenant_id, plan_id) REFERENCES social_insurance_plans(tenant_id, id),
  UNIQUE (tenant_id, plan_id, effective_month),
  CHECK (stop_month IS NULL OR stop_month > effective_month)
);
```

- 方案**不含公司**（8a 取证 §1.3）、**不含险种明细**（U1-A）：最小集里它只是一个“带缴交地的名称”，供调动下拉和档案引用。完整方案（险种明细、基数比例、薪资组、服务费）属 U1-B。
- 版本规则沿用职务体系的“对象 + 版本”写法：同一方案同月不重复生效；区间不重叠由 8c 的应用层与排他约束保证（沿用 `job_*_versions` 做法）。
- 不设“变更前”列；“变动历史”页签就是版本列表。

### 3.3 `social_insurance_archive_versions`（员工社保档案版本链）

```sql
CREATE TABLE social_insurance_archive_versions (
  tenant_id     uuid NOT NULL,
  id            uuid NOT NULL DEFAULT gen_random_uuid(),
  employee_id   uuid NOT NULL,
  version_no    integer NOT NULL CHECK (version_no > 0),
  effective_date date NOT NULL,                 -- 本次实际生效日，租户时区
  planned_effective_date date NOT NULL,         -- 来源业务的原计划日，同日排序键
  operation_seq bigint NOT NULL,                -- 来源业务操作事件序号，同日排序键
  region_code   text REFERENCES admin_regions(code), -- 本业务填写的调整值；null = 沿用前驱
  plan_id       uuid,
  company_id    uuid,                           -- 合同公司
  source        text NOT NULL CHECK (source IN ('transfer')),   -- 最小集只有调动一种来源
  source_business_id uuid NOT NULL,             -- 调动单业务对象，亦为来源幂等键
  command_id    text NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, id),
  UNIQUE (tenant_id, employee_id, version_no),
  UNIQUE (tenant_id, source, source_business_id),
  FOREIGN KEY (tenant_id, source_business_id) REFERENCES employment_business_objects(tenant_id, id),
  FOREIGN KEY (tenant_id, employee_id) REFERENCES employment_employees(tenant_id, id),
  FOREIGN KEY (tenant_id, plan_id) REFERENCES social_insurance_plans(tenant_id, id),
  FOREIGN KEY (tenant_id, company_id) REFERENCES contract_companies(tenant_id, id)
);
```

- **事件溯源版本链**：一次业务追加一条，允许同员工同生效日多条，**不按日期唯一**；幂等唯一性是 `(tenant_id, source, source_business_id)`。`version_no` 是员工锁内分配的追加序号（max + 1），只表达写入次序，不能作为业务顺序或前驱条件。来源业务须属于同租户同员工，由应用校验；三项存该业务的调整事件，null 表示未填写 / 沿用，不复制生成时的完整当前值，无 `before_*` 列。
- **业务位置复用现有时间线规则**：`apps/api/src/modules/employment/timeline.ts:19-37,68-98` 的 `operationKey / plannedEffectiveDate / timelinePosition` 是唯一排序来源：同日按操作序号（申请提交 / 直接保存），迟到业务同日按原计划日、再按操作序号（DEC-108 / DEC-195），不按审批完成时间、落档时间、UUID 或 version_no 排。事件写入时从上述助手取来源业务的 `planned_effective_date / operation_seq`，与实际 `effective_date` 组成稳定业务位置；已有任职时间线上的相对顺序必须与此三元组一致，不能另造序号。记录来源的排序依据，不复制会因插入而移动的 `sort_order`；若操作事件尚未存在则推迟档案写入，不以写入时刻兜底。新业务未落地时用同一 `timelinePosition` 预算插入点，最终位置在落档事务内重新取值。
- **前驱与继承**：从严格早于本业务位置的档案事件前缀按业务顺序折叠，初值三项均 null；每条只覆盖本条非空调整值。折叠结果就是本业务“原值”，加上本业务事件得到其“调整后”；同日较早业务必须包含，同日后序必须排除。当前档案取全前缀折叠结果，详情 / 审批取各自业务位置的前缀（审批已固定快照不回写）。
- **迟到插入**：迟到事件按稳定业务位置插入同日中间后，读取按业务顺序重新折叠已有事件，后序未填写项随新前驱推导，后序显式填写项保持自身值；不 UPDATE 已有档案事件，也不另写继承快照覆盖旧值。读写均在对应 `withTenant` 内，写入与位置读取持员工锁；已落档事件的排序键不随后续人工改期重写，与 §4.2 / U7 保留已写版本的边界一致。这是复刻事件模型的设计选择，原站同日社保继承表现仍待取证。
- 三个业务列都可空（原站三对字段均非必填）；全空的版本不写（调动没填任何社保字段时不产生档案版本）。
- `source` 目前只允许 `'transfer'`：完整模块后补时再放开入职、离职等（改 CHECK 要走新迁移，DEC-402 允许直接改，不加兼容）。
- 无“待增员 / 待减员 / 在缴 / 停缴”状态：最小集不处理增减员流程，状态机留给 U1-B。

### 3.4 调整值随联动版本保存

`transfer_linkage_versions` 追加三列（可空）：

```
adjusted_insurance_region_code text REFERENCES admin_regions(code),
adjusted_insurance_plan_id     uuid,   -- (tenant_id, plan_id) 外键
adjusted_insurance_company_id  uuid    -- (tenant_id, id) 外键 contract_companies
```

- 联动版本本来就是“随表单保存追加”的不可变版本（`transfer.ts:281` 头注释），符合“审批通过 ≠ 生效”：审批通过后档案仍不变，生效日才写档案版本（§4.2）。
- 不新增“原值”列：原值每次读取时由档案事件链按调动业务位置推出（§4.1），审批快照里的“原: 旧值”也由此生成。
- 与“是否调整薪资”（`adjust_salary`）**无约束关系**（8a 取证 §1.1）：保留 `adjust_salary` 作为“待调薪提醒”依据，不用它控制社保三项。

### 3.5 不新增什么

不建险种（福利项目）表、方案明细表、档案规则表、增减员待办表、月结账单表；不改 `employment_*` 任职表；不在 Offer 上做社保落档。

### 4.2 写与生效

- 调动表单保存（既有联动接口）请求体追加三个可选字段（调整后缴交地 `adjustedInsuranceRegionCode`、方案 `adjustedInsurancePlanId`、公司 `adjustedInsuranceCompanyId`）；校验：方案须在“生效日当月有效且启用”；公司须存在于合同公司；缴交地须为字典内 3 级之一（原站回填末级）；三项均可空；任一项带值即写联动版本。
- **生效**：审批通过后不改档案；生效日由既有定时联动在 `applyTransferCrossLinkage`（`execute.ts:60`）创建一个新子项 `insurance_archive`，在自己的保存点里写一条 `social_insurance_archive_versions`：只存本单实际填写的三项调整值，读取时按 §3.3 的业务顺序继承。幂等键 = 租户 + 来源 transfer + 调动单业务 ID，由 §3.3 唯一约束兜底；重复执行命中原事件、不分配新 version_no、不重复审计；同来源不同调整值报冲突，不覆盖。任职尚未落地或处于 REBUILD_REQUIRED 时不得先写档案。
- **失败**：业务拒绝（方案已停用、公司已删除等）只记子项失败（原因 / 次数）并可重试，不回滚任职生效，也不能伪造成功（对齐 `items.ts` 既有约定）。
- **撤销 / 改期**：调动在生效前撤销，则不写档案；改期（F-017 / F-140）沿用联动子项随生效日改期的现有路径；已生效后的人工改期是否回滚档案版本——待取证 ⑦，先按“已写入的版本保留，后续人工处理”保守。
- 审计：档案版本追加与联动子项结果同事务写审计（AGENTS §10）；字段级变更日志记新增版本的三项值（DEC-019）。
- 并发：写档案前取员工锁（沿用 `lockTransferParticipants`）；`If-Match` / `revision` 沿用调动联动版本现有约定。
- 三个联动开关：**最小集不实现开关**（DEC-402）。固定行为 = 本租户原站当前值：“填写”开 → 有填写则写档案；“不填写”（按规则匹配生成待增减员）和“编辑调动记录联动档案”依赖档案规则和增减员流程，随 U1-B 后补，在文档与 UI 上均不出现。详见 §8-U2。
