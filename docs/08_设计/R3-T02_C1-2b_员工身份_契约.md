## 0. 一句话

开通时多装一个标准身份 `employee_self_service`（名称“员工”，`source='standard'`），身份里放 DEC-205 的任职字段默认值和
任职资格应用的“员工发展通道”页面权限。员工照旧经本人入口的叠加授权器“按关系自动持有”它，不发授权行；这个身份不能授予、
不能删除。存量租户经 F-061 的两个登记项补装。没有这一行的租户（存量未回补、测试直接建的租户）继续用代码里的同一份默认值，
所以对外行为不变。

## 1. 现状与差距

| 项 | 现状（main） | DEC-399 要求 |
|---|---|---|
| 身份行 | 开通不建；`employeeFieldPolicy` 找租户里编码为 `employee_self_service`、挂 `TenantBase` 的身份（只可能是租户手工建的 custom 行），找不到就用 DEC-205 默认值 | 开通即有标准身份，不可删，所有员工按关系自动持有 |
| 默认值所在 | `policy.ts` 的 `DEFAULT_EDIT` / `DEFAULT_READ`（`DEFAULT_READ` = 可编辑 4 项 + `EMPLOYEE_READONLY_FIELDS` 3 项），`create: true` | 迁进身份，行为不变，租户之后可改 |
| 自动持有 | `access.ts` 的 `selfAccess` 叠加授权器：只对绑定了员工的本人路由生效，任职对象查看恒真，三个按钮白名单，字段按 `employeeFieldPolicy` | 不变（见 §2.3） |
| 发展通道入口 | 无（C1-6 未做） | 任职资格应用“员工发展通道”页面权限；不授 DevelopmentChannel / QualificationStandard 对象 |
| 页面权限 | 权限模型没有“页面权限”类型（只有应用、对象、字段、按钮、数据操作、范围） | 须给出表示法（§3） |
| 存量租户 | — | DEC-361 补装；同编码 custom 行按 `CODE_TAKEN` 计入已有、不覆盖，并在回补报告中列出 |

## 2. 身份定义与“自动持有”

### 2.1 定义（`packages/domain`）

在 `standard-presets.ts` 追加一条，进入 `STANDARD_PROFILES`（不再单独起登记项，见 §5）：

| 属性 | 值 | 依据 |
|---|---|---|
| `code` | `employee_self_service`（沿用 `EMPLOYEE_PROFILE_CODE`，不改编码） | DEC-399① |
| `name` / `description` | “员工” / “自助身份-员工” | 23 §19 原站名称与描述 |
| `licenseType` | `null`（不占名额） | 原站“授权范围 企业员工”，非按人授予 |
| `apps` | `TenantBase`、`Qualification` | 任职字段在 `TenantBase`；页面载体在 `Qualification`（§3） |
| `hr` / `seeAll` | `false` / 无 | 硬规则：数据范围默认空；员工的范围是叠加授权器给的“本人” |
| `autoHeld`（新属性） | `true` | 见 §2.2 |
| 对象 `TenantBase.EmploymentRecord` | 字段：`DEFAULT_READ` 7 项 `view=true`，其中 `DEFAULT_EDIT` 4 项 `edit=true`；数据操作 `create=true`、`update=false`、`delete=false`；按钮 `[]` | DEC-205；按钮见 §2.4 |
| 对象 `Qualification.Pages`（页面载体，§3） | 字段 `[]`；数据操作全 `false`；按钮 `EmployeeDevelopmentChannel@app_page` | DEC-399② |

- **单一来源**：在 `packages/domain` 新建 `platform/employee-self-service.ts`，导出 `EMPLOYEE_SELF_SERVICE_CODE`、
  `EMPLOYEE_DEFAULT_EDIT_FIELDS`（4 项）、`EMPLOYEE_READONLY_FIELDS`（`postId` / `levelId` / `sequenceId`）、
  `EMPLOYEE_DEFAULT_CREATE = true`、`EMPLOYEE_PAGES`（见 §3）。身份定义和 `employeeFieldPolicy` 的兜底值都从这里推出，不能各写一份。
  `apps/api/src/modules/transfer/employee-policy.ts` 的 `EMPLOYEE_READONLY_FIELDS` 改为由 domain 常量构造的 `Set`，导出名与类型不变。
- 字段子集要新写一个构造函数（如 `fieldSubset(definition, view, edit, ops)`），现有 `full` / `readOnly` / `partial` 都是“全部字段可见”，不适用。
  构造时按对象目录校验，字段不存在或系统字段给 `edit` 时，开通整笔回滚（沿用 `insertObject` 的校验）。

### 2.2 “自动持有”的实现口径：不发授权行

“所有员工按关系自动持有”沿用现有的叠加授权器，**不**为每个员工物化 `permission_grants`（`source='auto'`）。理由：

- 行为与现在逐字相同：本人入口的鉴权路径、字段并集、撤权实时生效都不变；
- 不引入“绑定 / 解绑 / 入离职时重算 5,000 级授权行”的新联动，也不让这个身份出现在 HR 端接口的鉴权里
  （物化授权会让员工在 HR 端也带上任职对象的字段权限，属于越权放大）；
- 原站约 5,500 条授权记录是平台内部物化，租户侧只能看到“授权范围 企业员工”，复刻不需要逐条展示。

因此 `autoHeld` 身份有三条硬约束：

1. **不可授予**：`createGrant` 遇到 `autoHeld` 的标准身份返回 403 `FORBIDDEN`，`reason='PROFILE_AUTO_HELD'`
   （先于 `PROFILE_NOT_GRANTABLE` 判断）。`PUT /admins/:id`、`POST /admins` 的 `grantableProfileIds` 含它时同样 403 `PROFILE_AUTO_HELD`，
   即使操作人是租户管理员（租户管理员跳过“只能交出自己可授权的”检查，这里另加一条）。
2. **不进可授权集合**：开通时首位租户管理员的可授权业务身份、回补新装身份后加给有效租户管理员的可授权身份，都排除 `autoHeld`
   （`provisioning.ts` 传给 `bootstrapTenantAdminIn` 的 id 列表；`standard-profiles.ts#grantableToTenantAdmins` 的调用方）。
   首位管理员只授 `FIRST_ADMIN_PROFILE`，不变。
3. **不可删除**：现有接口本来就没有删除身份的路由（F-061 §1.1），不需改代码；契约在此登记，以后谁加删除路由须拒绝 `source='standard'`。

只按“`source='standard'` 且定义里 `autoHeld`”判断。租户手工建的同编码 custom 行（`CODE_TAKEN`）不受上述约束，保持现状。

### 2.3 现有入口怎么切换

| 入口 | 改动 | 行为 |
|---|---|---|
| `employeeFieldPolicy(tx, tenantId)` | 查询不变（按编码 + `TenantBase` 找行，不看 `source`）。**找不到行时的兜底值改为由 domain 单一来源推出**（与身份定义同一份），删除 `policy.ts` 里的 `DEFAULT_EDIT` / `DEFAULT_READ` 字面量 | 有标准行：读标准行（开通时装的就是默认值）；有 custom 行：读 custom 行（同现在）；没有行：默认值（同现在） |
| `selfAccess`（`access.ts`） | 不改 | 任职对象查看恒真、`BUTTONS` 白名单、`COMMAND_FIELDS`、只读字段拒绝、字段并集，全部照旧 |
| `transferFieldAccess`、`discloseOwnRecord`、预览 / 提交 / 引用候选 | 不改（都经 `employeeFieldPolicy` 或叠加授权器） | 同上 |
| 员工发展通道页面判定 | 新增 `employeePageGranted(tx, ctx, page)`（§3.2），C1-6 的本人入口调用 | 新能力，没有既有行为 |
| 身份管理（`GET /profiles`、`GET /profiles/:id`、`PUT /profiles/:id/objects/:objectCode`） | 不改 | 员工身份作为一条标准身份出现；租户在这里改任职字段或页面权限，实时生效 |

### 2.4 范围外（照现状，登记为已知差异）

- **按钮仍走白名单**：`Transfer.Self`、`Employment.Create`、`Employment.Submit` 由叠加授权器直接放行，身份里**不写**这三个按钮。
  DEC-205 的“出厂默认”是字段权限（决策原文“可见 / 可编辑字段按发起人身份的字段权限裁剪”），按钮白名单来自 R1-T13 实现，
  F-039 已登记为“身份配置撤不掉”（`policy.ts` 的 `whitelistedButtons`）。若要让租户能在员工身份里关掉本人调动，属于新口径，
  须改 F-039 声明，另开 F 任务，不在 C1-2b。
- 员工身份上配置其他对象（例如租户给它加组织、合同对象）**不产生效果**：复刻只读它的任职字段与页面权限两处。原站员工身份关联
  50 多个应用，复刻只登记本期用到的两个（🟡，后续模块需要时各自追加并经 F-061 补装）。
- 原站任职资格应用下另有 6 个页面权限（移动端页、标准预览页、4 个视图页）和 4 个对象的字段查看。本期 PC 端（DEC-007），
  DEC-399② 只要求“员工发展通道”，且员工端不显示各级标准明细（23 §19），所以都不登记。

## 3. 页面权限的表示法

### 3.1 选型：应用级“页面载体”对象 + `app_page` 按钮

在任职资格应用登记一个**页面载体对象** `Qualification.Pages`，没有字段，按钮即页面：
`{ code: 'EmployeeDevelopmentChannel', level: 'app_page' }`（按钮层级 `app_page` = 应用页，`BUTTON_LEVELS` 已有）。

- 授权项编码沿用 F-061 现有格式，不加新种类：
  - `employee_self_service/app:Qualification`；
  - `employee_self_service/Qualification.Pages/op:view`；
  - `employee_self_service/Qualification.Pages/button:EmployeeDevelopmentChannel@app_page`。
- 租户“去掉页面权限”= 在身份管理里保存该对象、按钮不勾（`PUT /profiles/:id/objects/Qualification.Pages`，`buttons: []`）。
  这条路径已接 F-061 的保存登记（`@modified` 与保存前后已授予项），所以回补不会补回。
- 载体对象**不放进** `QUALIFICATION_OBJECTS`：该常量被审计可见性（`audit/visibility.ts`）、任职资格策略（`qualification/policy.ts`）、
  #203 的“任职资格系统管理员 = 全部对象”遍历，混进去会给它们带来无意义的对象。单独导出 `QUALIFICATION_PAGES`，在
  `permission/catalog.ts` 的对象目录里追加一行。任职资格系统管理员**不带**这个载体（管理员看发展通道走 C1-6 的管理入口）。

不另建页面权限表的理由：新表要配套新路由（身份管理页签）、F-039 登记、F-061 新授权项种类与台账规则，体量约为本方案的 3 倍；
本期只有一个页面，载体对象复用全部现有机制。以后页面权限多了（其他应用也要），再评估是否升级为独立表（迁移时编码可一对一映射）。

### 3.2 判定函数（C1-2b 提供，C1-6 调用）

`employeePageGranted(tx, ctx: { tenantId, userId }, page: 'EmployeeDevelopmentChannel'): Promise<boolean>`，放在
`apps/api/src/modules/employee-self-service/`（与 `employeeFieldPolicy` 同目录）。结果为下面两项的**并集**：

1. **员工身份**（按编码找行，不看 `source`）：
   - 没有这一行，或这一行**没有** `Qualification.Pages` 对象行 → 取默认值（授予）；
   - 有对象行 → 看按钮行里有没有 `EmployeeDevelopmentChannel@app_page`。
2. **用户自己持有的身份**：经用户自身授权器判 `object.button`，资源 `Qualification.Pages#EmployeeDevelopmentChannel@app_page`
   （与 `selfAccess` 对按钮的 `|| base(request)` 同一口径；原站页面权限按身份并集）。

调用方须先确认用户绑定了员工（`boundEmployee`），未绑定照现有 403“当前用户未绑定员工”。判定不看 Qualification 数据范围（关系入口，拆分方案 §8）。

“没有对象行 → 默认授予”与字段策略的“有行就读行”不同，原因：租户手工建的同编码 custom 行（`CODE_TAKEN`）只能在建身份时选应用，
现有接口不能给已建身份加应用，若按“有行就读行”，这些租户的员工永远看不到发展通道且无法自救。标准行开通时一定带对象行，
所以标准行上“去掉”是可表达、可生效的。

无权时 C1-6 返回 403 `FORBIDDEN`，`reason='PAGE_PERMISSION_REQUIRED'`，`details: { app: 'Qualification', page: 'EmployeeDevelopmentChannel' }`；
前端按原站文案提示（文案进资源文件，DEC-045）：“请联系管理员配置以下权限：配置【任职资格】应用中的【员工发展通道】页面权限”。
卡片数据由页面后端按本人直接读取，不要求 DevelopmentChannel / QualificationStandard 的对象权限（DEC-399② 🟡）。这些是 C1-6 的契约，C1-2b 只交判定函数。

## 5. 存量租户补装（DEC-361 / F-061）

- **不再单独起登记项**：员工身份在 `STANDARD_PROFILES` 里，由 F-061 现有两个登记项覆盖：
  - `permission/standard-profiles`：缺整个身份时装（`installProfile`，装入即记账）；
  - `permission/standard-profile-grants`：已装身份上缺的授权项（以后目录给它加字段 / 页面时用）。
  `permission/standard-seeds.ts` 对 `STANDARD_PROFILES` 逐个 `registerManagedGrants`，所以员工身份的保存登记自动生效。
  拆分方案旧写的 `qualification/employee-profile-grants`、`qualification_seed_grant_installs`、自建接管都作废。
- **同编码 custom 行**：两个登记项都计入已有、不装、不往 custom 行写授权（现状）。DEC-399③ 要求“在回补报告中列出”：
  `permission/standard-profiles` 的 `existing` 改为只认 `source='standard'`；custom 同编码因此算缺失、进入 `install`。`install` 先在同一事务里
  读出租户已有的 custom 同编码，把它们从待装列表剔除（否则撞（租户，编码）唯一约束），只装其余身份，并返回
  `skipped: [{ code, reason: 'CODE_TAKEN' }]`，对这些编码不写任何行。#160 报告形状不变（`skipped` 本来就是“没装的编码与原因”），
  效果是 `CODE_TAKEN` 从 `existing` 计数移到 `skipped` 列表。**对所有标准身份统一生效**（不只员工身份）；每次回补都会列出，无写入、无审计。
  `permission/standard-profile-grants` 不变（custom 行下的授权项照旧计入 `existing`，不逐条列出，避免报告被几十条编码淹没）。
- **新装身份不进可授权集合**：`installProfilesForTenantAdmins` 把 `autoHeld` 身份从 `grantableToTenantAdmins` 的 id 里去掉（§2.2）。
- **version / 指纹**：员工身份带来新授权项编码，`STANDARD_GRANT_VERSION` 在实现 PR 合并时的 main 值上 +1，`STANDARD_GRANT_DIGEST`
  按守卫测试重算（#203 合并后 main 是 5，届时 C1-2b 为 6；以合并时为准）。`permission/standard-profiles` 的 `version` 不变（它的 codes 是身份编码，加一个身份按 #160 口径不升）。
  `SEE_ALL_BACKFILL_APPROVED` 不动（员工身份没有看全部）。
- **撤销保留**：开通装入即记账（`install`）；存量租户补装同样记账；租户去掉页面或字段 → `@modified` + 保存前已授予项登记为 `tenant_saved` → 回补不恢复。
