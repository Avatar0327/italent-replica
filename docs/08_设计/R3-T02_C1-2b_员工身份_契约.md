## 0. 一句话

开通时多装一个标准身份 `employee_self_service`（名称“员工”，`source='standard'`），身份里放 DEC-205 的任职字段默认值、
本人调动的三个功能按钮（DEC-402②）和任职资格应用的“员工发展通道”页面权限。员工照旧经本人入口的叠加授权器“按关系自动持有”它，
不发授权行；这个身份不能授予、不能删除，管理端只显示“自动适用于全体员工”（DEC-402③）。存量租户经 F-061 的两个登记项补装。
没有这一行的租户（存量未回补、测试直接建的租户）继续用代码里的同一份默认值，所以**默认**行为不变；之后管理员在“员工”身份里
关掉字段、按钮或页面即实时生效。
**总原则（DEC-402，用户定）**：复刻系统尚未上线，“老租户 / 存量数据兼容”不作为设计约束，取最简单做法，不为此加开关或配置。

## 2. 身份定义与“自动持有”

### 2.1 定义（`packages/domain`）

在 `standard-presets.ts` 追加一条，进入 `STANDARD_PROFILES`（不再单独起登记项，见 §5）：

| 属性 | 值 | 依据 |
|---|---|---|
| `code` | `employee_self_service`（沿用 `EMPLOYEE_PROFILE_CODE`，不改编码） | DEC-399① |
| `name` / `description` | “员工” / “自助身份-员工” | 23 §19 原站名称与描述 |
| `licenseType` | `null`（不占名额） | 原站“授权范围 企业员工”，非按人授予 |
| `apps` | `TenantBase`、`Qualification` | 任职字段在 `TenantBase`；页面载体在 `Qualification`（§3） |
| `hr` / `seeAll` | `false` / 无 | 硬规则：数据范围默认空；员工的范围是叠加授权器给的“本人” |
| `autoHeld`（新属性） | `true` | 见 §2.2 |
| 对象 `TenantBase.EmploymentRecord` | 字段：`DEFAULT_READ` 7 项 `view=true`，其中 `DEFAULT_EDIT` 4 项 `edit=true`；数据操作 `create=true`、`update=false`、`delete=false`；按钮 `Transfer.Self@detail`、`Employment.Create@detail`、`Employment.Submit@detail` | DEC-205；按钮 DEC-402②（§2.3） |
| 对象 `Qualification.Pages`（页面载体，§3） | 字段 `[]`；数据操作全 `false`；按钮 `EmployeeDevelopmentChannel@app_page` | DEC-399② |

- **单一来源**：在 `packages/domain` 新建 `platform/employee-self-service.ts`，导出 `EMPLOYEE_SELF_SERVICE_CODE`、
  `EMPLOYEE_DEFAULT_EDIT_FIELDS`（4 项）、`EMPLOYEE_READONLY_FIELDS`（`postId` / `levelId` / `sequenceId`）、
  `EMPLOYEE_DEFAULT_CREATE = true`、`EMPLOYEE_SELF_SERVICE_BUTTONS`（上表三个按钮）、`EMPLOYEE_PAGES`（见 §3）。身份定义和 `employeeFieldPolicy` 的兜底值都从这里推出，不能各写一份。
  `apps/api/src/modules/transfer/employee-policy.ts` 的 `EMPLOYEE_READONLY_FIELDS` 改为由 domain 常量构造的 `Set`，导出名与类型不变。
- 字段子集要新写一个构造函数（如 `fieldSubset(definition, view, edit, ops)`），现有 `full` / `readOnly` / `partial` 都是“全部字段可见”，不适用。
  构造时按对象目录校验，字段不存在或系统字段给 `edit` 时，开通整笔回滚（沿用 `insertObject` 的校验）。

### 2.2 “自动持有”的实现口径：不发授权行

“所有员工按关系自动持有”沿用现有的叠加授权器，**不**为每个员工物化 `permission_grants`（`source='auto'`）。理由：

- 行为与现在逐字相同：本人入口的鉴权路径、字段并集、撤权实时生效都不变；
- 不引入“绑定 / 解绑 / 入离职时重算 5,000 级授权行”的新联动，也不让这个身份出现在 HR 端接口的鉴权里
  （物化授权会让员工在 HR 端也带上任职对象的字段权限，属于越权放大）；
- 不物化是**复刻的实现选择**，不是照原站：原站在租户侧的用户授权全量扫描里能看到员工身份约 5,516 条“用户 × 身份”记录（06 §8，按关系自动物化，🟢 数量 / 🟡 机制）。所以复刻管理端的授权记录列表里**没有**这些逐人记录，与原站展示不一致。**展示口径按 DEC-402③**：身份管理照常可见、可配置“员工”身份；`GET /profiles`、`GET /profiles/:id` 的身份视图加只读字段 `autoHeld: true`（其他身份为 `false`），管理端授权人员处据此只显示“自动适用于全体员工”（文案进资源文件，DEC-045；当前没有身份管理前端页，C1-2b 只交接口字段），不逐人列出；`GET /grants` 里没有它。

因此 `autoHeld` 身份有三条硬约束（DEC-402③）：

1. **不可授予**：`createGrant` 遇到 `autoHeld` 的标准身份返回 403 `FORBIDDEN`，`reason='PROFILE_AUTO_HELD'`
   （先于 `PROFILE_NOT_GRANTABLE` 判断）。`PUT /admins/:id`、`POST /admins` 的 `grantableProfileIds` 含它时同样 403 `PROFILE_AUTO_HELD`，
   即使操作人是租户管理员（租户管理员跳过“只能交出自己可授权的”检查，这里另加一条）。没有授权行，所以也谈不上“撤销到个人”。
2. **不进可授权集合（授权选择器不列它）**：开通时首位租户管理员的可授权业务身份、回补新装身份后加给有效租户管理员的可授权身份，都排除 `autoHeld`
   （`provisioning.ts` 传给 `bootstrapTenantAdminIn` 的 id 列表；`standard-profiles.ts#grantableToTenantAdmins` 的调用方）。
   首位管理员只授 `FIRST_ADMIN_PROFILE`，不变。`GET /grantable-profiles`（授权选择器的数据源）因此不含它。
3. **不可删除**：现有接口本来就没有删除身份的路由（F-061 §1.1），不需改代码；契约在此登记，以后谁加删除路由须拒绝 `source='standard'`。

只按“`source='standard'` 且定义里 `autoHeld`”判断。租户手工建的同编码 custom 行（`CODE_TAKEN`）不受上述约束，保持现状。

### 2.3 现有入口怎么切换

| 入口 | 改动 | 行为 |
|---|---|---|
| `employeeFieldPolicy(tx, tenantId)` | 查询不变（按编码 + `TenantBase` 找行，不看 `source`）。返回值加 `buttons: Set<string>`（该行任职对象上的按钮编码）。**找不到行时的兜底值改为由 domain 单一来源推出**（与身份定义同一份，`buttons` 兜底 = 三个按钮），删除 `policy.ts` 里的 `DEFAULT_EDIT` / `DEFAULT_READ` 字面量 | 有标准行：读标准行（开通时装的就是默认值）；有 custom 行：读 custom 行（字段同现在；按钮也读该行，见下）；没有行：默认值（同现在） |
| `selfAccess`（`access.ts`） | `BUTTONS` 白名单改为按身份校验（DEC-402②）：`object.button` 请求的按钮属于 `EMPLOYEE_SELF_SERVICE_BUTTONS` **且** `policy.buttons` 含它 → 允许；否则走 `base(request)`（用户自己的身份，同现在）。只认这三个按钮：管理员给员工身份勾上其他任职按钮（如 `Employment.Delete`）**不**经叠加授权器生效。不检查按钮的 `requires` 数据操作，与现白名单一致（`Employment.Submit` 声明需要 `update`，而员工身份 `update=false`，DEC-205 不改数据操作）。其余（任职对象查看恒真、`COMMAND_FIELDS`、只读字段拒绝、字段并集）不改 | 有标准行且未改：三个按钮都在，同现状；管理员关掉任一按钮 → 用到它的本人入口 403、不产生申请；没有行：兜底三个按钮，同现状；custom 同编码行：按该行按钮判定（该行没勾这三个按钮时本人调动 403；存量 custom 情形按 DEC-402 总原则不另兼容） |
| 本人入口路由声明（`employee-self-service/policy.ts`） | `whitelistedButtons` 由“白名单、身份配置撤不掉”改为可撤销按钮声明；`POST /transfer/preview`、`POST /transfer` 按代码实际检查的按钮登记；同步 `required/self-service.ts` 的义务与证据、`ROUTE_POLICY_UPDATE_DIGESTS=1` 摘要与基准，跑 `explain-graph-diff`，结果写进 PR 描述 | 声明与新校验一致 |
| `transferFieldAccess`、`discloseOwnRecord`、预览 / 提交 / 引用候选 | 不改（都经 `employeeFieldPolicy` 或叠加授权器） | 同上 |
| 员工发展通道页面判定 | 新增 `employeePageGranted(tx, ctx, page)`（§3.2），C1-6 的本人入口调用 | 新能力，没有既有行为 |
| 身份管理（`GET /profiles`、`GET /profiles/:id`、`PUT /profiles/:id/objects/:objectCode`） | 身份视图加只读 `autoHeld`（§2.2）；保存接口不改 | 员工身份作为一条标准身份出现；租户在这里改任职字段、三个按钮或页面权限，实时生效 |

### 2.4 范围外（登记为已知差异）

- 员工身份上配置其他对象（例如租户给它加组织、合同对象）**不产生效果**：复刻只读它的任职字段、三个本人调动按钮与页面权限。原站员工身份关联
  50 多个应用，复刻只登记本期用到的两个（🟡，后续模块需要时各自追加并经 F-061 补装）。
- 原站任职资格应用下另有 6 个页面权限（移动端页、标准预览页、4 个视图页）和 4 个对象的字段查看。本期 PC 端（DEC-007），
  DEC-399② 只要求“员工发展通道”，且员工端不显示各级标准明细（23 §19），所以都不登记。

## 3. 页面权限的表示法

### 3.1 选型：应用级“页面载体”对象 + `app_page` 按钮

在任职资格应用登记一个**页面载体对象** `Qualification.Pages`，没有字段，按钮即页面：
`{ code: 'EmployeeDevelopmentChannel', level: 'app_page' }`（按钮层级 `app_page` = 应用页，`BUTTON_LEVELS` 已有）。

- 授权项编码沿用 F-061 现有格式，不加新种类：
  - `employee_self_service/app:Qualification`；
  - `employee_self_service/Qualification.Pages/op:view`；
  - `employee_self_service/Qualification.Pages/button:EmployeeDevelopmentChannel@app_page`。
- 租户“去掉页面权限”= 在身份管理里保存该对象、按钮不勾（`PUT /profiles/:id/objects/Qualification.Pages`，`buttons: []`）。
  这条路径已接 F-061 的保存登记（`@modified` 与保存前后已授予项），所以回补不会补回。
- 载体对象**不放进** `QUALIFICATION_OBJECTS`：该常量被审计可见性（`audit/visibility.ts`）、任职资格策略（`qualification/policy.ts`）、
  #203 的“任职资格系统管理员 = 全部对象”遍历，混进去会给它们带来无意义的对象。单独导出 `QUALIFICATION_PAGES`，在
  `permission/catalog.ts` 的对象目录里追加一行。任职资格系统管理员**不带**这个载体（管理员看发展通道走 C1-6 的管理入口）。

不另建页面权限表的理由：新表要配套新路由（身份管理页签）、F-039 登记、F-061 新授权项种类与台账规则，体量约为本方案的 3 倍；
本期只有一个页面，载体对象复用全部现有机制。以后页面权限多了（其他应用也要），再评估是否升级为独立表（迁移时编码可一对一映射）。

### 3.2 判定函数（C1-2b 提供，C1-6 调用）

`employeePageGranted(tx, ctx: { tenantId, userId }, page: 'EmployeeDevelopmentChannel'): Promise<boolean>`，放在
`apps/api/src/modules/employee-self-service/`（与 `employeeFieldPolicy` 同目录）。结果为下面两项的**并集**：

1. **员工身份**（按编码找行，不看 `source`）：
   - 没有这一行，或这一行**没有** `Qualification.Pages` 对象行 → 取默认值（授予）；
   - 有对象行 → 看按钮行里有没有 `EmployeeDevelopmentChannel@app_page`。
2. **用户自己持有的身份**：经用户自身授权器判 `object.button`，资源 `Qualification.Pages#EmployeeDevelopmentChannel@app_page`
   （与 `selfAccess` 对按钮的 `|| base(request)` 同一口径；原站页面权限按身份并集）。

调用方须先确认用户绑定了员工（`boundEmployee`），未绑定照现有 403“当前用户未绑定员工”。判定不看 Qualification 数据范围（关系入口，拆分方案 §8）。

“没有对象行 → 默认授予”与字段策略的“有行就读行”不同，**依据 DEC-402①**：缺载体行时默认显示，不另加关闭开关。
标准行开通时一定带对象行，所以标准行上“去掉”是可表达、可生效的；同编码 custom 行（只有 `TenantBase`、加不了应用）上无法关闭，
属存量兼容情形，按 DEC-402 总原则不考虑（复刻未上线）。第 1 轮审查 P2-1 据此结案。

无权时 C1-6 返回 403 `FORBIDDEN`，`reason='PAGE_PERMISSION_REQUIRED'`，`details: { app: 'Qualification', page: 'EmployeeDevelopmentChannel' }`；
前端按原站文案提示（文案进资源文件，DEC-045）：“请联系管理员配置以下权限：配置【任职资格】应用中的【员工发展通道】页面权限”。
卡片数据由页面后端按本人直接读取，不要求 DevelopmentChannel / QualificationStandard 的对象权限（DEC-399② 🟡）。这些是 C1-6 的契约，C1-2b 只交判定函数。

## 4. 默认行为不变：怎么证明

| 证据 | 内容 |
|---|---|
| E1 单一来源 | 身份定义与 `employeeFieldPolicy` 兜底值都由 `platform/employee-self-service.ts` 推出；守卫单元测试把**改动前**的字面量（`DEFAULT_EDIT` 4 项、`DEFAULT_READ` 7 项、`create: true`、`access.ts` 的 `BUTTONS` 三项）抄进测试作“旧值”，断言：① 由身份定义算出的 `{ view, edit, create, buttons }` 等于旧值；② 兜底值等于旧值 |
| E2 新旧两条路径同输出 | 同一组操作分别跑在 A“直接建的租户（无身份行，走兜底）”与 B“装有标准员工身份的租户”（平台开通，或在 `approvalWorld` 租户里用开通同一安装函数 `installProfile` 装入员工身份）上，结果逐字段相同（id 归一后比较）：`GET /profile` 的披露字段、`POST /transfer/preview` 的 `form.fieldModes` / `basicFieldModes` / `fields` / `reasons`、每个可见字段的 `GET /transfer/references/:code` 状态码、写只读字段（`postId`）403、写不可见字段 403、正常提交 201 |
| E3 存量升级前后同输出 | F-061 夹具 `legacyWorld(..., skipCodes=['employee_self_service'])`（旧版本开通、不含员工身份）：回补前取 `employeeFieldPolicy` 结果与 `GET /profile` 披露得 X（夹具能建员工与调动时再加 E2 的预览操作），`seeds/backfill` 后再取得 Y，`X = Y`；回补报告里 `permission/standard-profiles` 的 `installed` 含 `employee_self_service` |
| E4 现有测试 | §6 列为“不变”的测试文件一行不改通过（它们都在直接建的租户上跑，走兜底路径） |
| E5 可调整 | 平台开通租户里经 `PUT /profiles/:id/objects/TenantBase.EmploymentRecord` 收紧标准员工身份（去掉 `reasonCode`），预览立即隐藏原因（同 AC-TRF-39 现有 custom 行用例，换成标准行）；去掉任一本人调动按钮，用到它的入口立即 403（DEC-402②） |

## 5. 存量租户补装（DEC-361 / F-061）

- **不再单独起登记项**：员工身份在 `STANDARD_PROFILES` 里，由 F-061 现有两个登记项覆盖：
  - `permission/standard-profiles`：缺整个身份时装（`installProfile`，装入即记账）；
  - `permission/standard-profile-grants`：已装身份上缺的授权项（以后目录给它加字段 / 页面时用）。
  `permission/standard-managed-grants.ts` 对 `STANDARD_PROFILES` 逐个 `registerManagedGrants`（由 `profiles.ts` 与 `standard-seeds.ts` 共同 import），所以员工身份的保存登记自动生效，C1-2b 不另写登记代码。
  拆分方案旧写的 `qualification/employee-profile-grants`、`qualification_seed_grant_installs`、自建接管都作废。
- **同编码 custom 行**：两个登记项都计入已有、不装、不往 custom 行写授权（现状，计数不变）。DEC-399③ 要求“在回补报告中列出”，
  按 **DEC-402⑤ 保留原计数、另加明细**：
  - `seeds/registry.ts`（#160 共享文件，只加可选项）：`SeedEntry` 加可选 `existingDetails?: (tx, tenantId) => Promise<readonly SeedSkip[]>`；
    `SeedReportItem` 加可选 `existingDetails?: readonly SeedSkip[]`（计入 `existing` 的编码里需要说明原因的那些）。`installMissingSeeds`
