## 1. 结论与范围

1. Offer 在既有行操作矩阵的“已接受 / 已入职”提供单条手动发起；入职在“全部待入职 / 今日待入职”的现有行菜单提供单条手动发起。选 1～20 个模板后立即生成任务，不等待新的审批或入职生效。
2. 第一节点仍用 F-481 的 `employee`，含义是业务本人；第二节点仍是发起人 `enterprise`。只使用本租户有效成员的既有绑定账号，不匹配邮箱猜人、不自动建账号、不提前同步 Offer。
3. Offer 尚无可验证人员关联时返回明确的 409；已有人员但没有有效账号时，沿用 `failed / EMPLOYEE_NO_ACCOUNT` 任务。两者分别是“来源条件不满足”和“发起失败”，不假装发出。
4. 签署完成只更新签署任务。Offer 接受 / 拒绝 / 入职、入职办理 / 取消 / 审批均维持自己的状态机。业务界面显示签署只读摘要与历史，不给 Offer、任职头行新增签署状态列。
5. 复用当前五态：`signing / completed / revoked / expired / failed`。本单不增加拒签操作或新状态；§6 明确拒签与业务拒绝的区别。
6. 发起复用 Offer 对象编辑权、任职对象编辑权与 `Employment.Edit`；记录查看、提醒、撤销、下载复用 `ESignRecord`；本人签署复用 `own(esign.signer)`。不新增授权对象、字段、按钮、编码或版本。
7. 需迁移：现有任职外键不能承载 Offer。采用稳定 Offer 来源锚点及明确的两类来源列，保留历史文件；不修改已合入迁移。

**本单不做**：批量发起、自动发起、发送 Offer 时发起、接受前签署门槛（34 OF-R6）、入职必须签完门槛（EN-R10）、新增动态业务变量、审批表单电子签开关、真实服务 / 回调路由、短信 / 邮件 / 认证 / 印章、自定义流程、其余场景、完整 Offer 编辑功能。既有这类占位配置不能因本单被标为已交付。范围取舍集中在 §14，尤其 U1、U2、U3、U4。

## 3. 发起入口、可用状态与模板

### 3.1 Offer

- 单行“发起电子签署”，只在 `status in (accepted, onboarded)` 且具有 `TenantBase.Offer` 编辑权时由后端返回 `rowActions.sign`；前端不自行补出动作。待发（包括审批通过）、已发、已拒绝、已失效均不发起。
- 弹窗打开时读取 §8 的发起上下文，取得**同一次服务端读取**的 Offer revision、可用性及模板选项；不拼旧列表 revision 与新内容。Offer 冻结办理份不是发起上下文，历史审批查看权不能发起。
- 人员解析：有同步产物时沿 `currentEntryIds` 找本租户最新业务，读取并验证 `employee_id`；若同步产物已删除且没有替代，拒绝。无同步产物时，仅可使用现有、可验证的 `linkedEmployeeId`（关联实习生），不按姓名、邮箱、手机号推断。两个关联同时存在而指向不同人员时失败闭合 `ESIGN_SOURCE_UNAVAILABLE`。
- 解析使用来源授权下的窄查询，只取该 Offer 已关联业务的人员 ID 和账号绑定，不给调用方新增人员列表能力，不复用 `inboundEmploymentContext` 的全范围特例。
- 没有任何人员关联：409 `ESIGN_OWNER_UNAVAILABLE`，提示“尚无可用于签署的人员关联，请先完成现有同步或关联流程”。本命令不代做同步。账号缺失 / 停用 / 非有效租户成员则落失败任务，见 §5。
- `owner_department_id` 快照 Offer 的录用部门；签署记录的读取仍按当前人员范围，不能拿这份部门快照扩大历史记录访问。

### 3.2 入职

- 保持既有行菜单位置，仅对记录本身处于待入职、未取消、未删除且 `kind in (hire, rehire, retire_rehire)` 的行开放。未来入职日不阻止签署；不要求当天生效。
- “已取消”无发起入口；“已入职”只显示已有签署记录，不在本单增加补签入口。办理入职后已有任务可以继续，不因人员当前已入职而关闭。
- 第一签署人取**该记录所属人员**的绑定账号，不取经办人或主管；重聘 / 返聘账号未恢复时，同样落 `EMPLOYEE_NO_ACCOUNT`，本单不恢复账号。
- 发起锁内核对业务头与记录状态；不能只看 `entryStatus`，还须核对待入职人员状态快照及业务未删除。被改期替换的旧 ID 返回 404；不自动追到新 ID 后发起，新 ID 必须由操作者刷新确认。

### 3.3 可选模板与变量（U2）

共同规则：本租户、`enabled`、按 `sort_order / name / id` 稳定排序；不按模板名称、Offer 类型或组织猜适用场景，不建立场景绑定。一次 1～20 个不重复 ID，顺序按选项顺序，所选每份各生成一份文件；不自动选唯一模板。

**新增两场景只允许静态正文，或仅使用现有四个通用变量的模板**：`{员工姓名}`、`{工号}`、`{发起日期}`、`{企业名称}`。正文出现任何调动 / 新合同变量即不列为可选，不把“调入部门”等变量强行解释为“录用部门”。不向客户端返回被过滤模板的正文、数量或 ID；空列表提示“暂无适用于本场景的启用模板，可使用纯文本或通用变量”。这是新场景的保守兼容性过滤，不改变调动原先全部启用模板可选的规则。

| 变量     | 两场景取值                             | 额外披露约束                                                                                    |
| -------- | -------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 员工姓名 | 解析出的人员当前姓名，供该人员自己签署 | 发起操作人须同时具备 TenantBase.Employee.view、当前人员读范围与 name 读权，模板确实使用时才检查 |
| 工号     | 同一人员当前工号；业务值空为 `--`      | 同上，检查 code 读权；无权不能替换为 `--` 冒充空值                                              |
| 发起日期 | 服务端按租户时区计算的当日             | 不取浏览器日期                                                                                  |
| 企业名称 | 租户名称                               | 不当作 Offer 合同法人名称                                                                       |

模板正文仍由有 ESignSettings 维护权者编写，选项只出 id/name。发起时重新检查变量兼容性和当前权限；无字段读权返回 403 `FIELD_FORBIDDEN`，不落任务、不生成正文。这样具有 Offer 编辑权但无人员范围的招聘人员仍可用纯文本、发起日期、企业名称模板，不得借模板取到人员姓名 / 工号。新增人员变量授权绕不过既有范围。

发起事务以模板 ID 升序读取并加共享锁，防止检查后停用 / 改正文；签署内容取提交时最新模板，不做旧模板版本确认。弹窗写明“使用提交时的模板内容”。一项不可用则整个单条命令 400 `ESIGN_TEMPLATE_UNAVAILABLE`，不返回其他租户模板是否存在；不兼容统一 400 `ESIGN_TEMPLATE_INCOMPATIBLE`。已发任务文件永不随模板修改变化。

## 4. 数据模型与迁移

### 4.1 来源必须可追溯，Offer 删除不能删签署历史

新增 `esign_offer_sources`（明确业务锚点，不是通用 JSON 实体）：`tenant_id`、`offer_id` 复合主键，`created_at`、`deleted_at` 可空。首次发起在 Offer 行锁内 `INSERT ... SELECT` 本租户 Offer 建锚点；插入触发器验证相同 tenant/id 的 Offer 确实存在。只允许由服务插入与标记删除，不接受 HTTP 传入锚点对象。

该锚点是保留身份的历史来源，**有意不对会物理删除的 offers 建永久外键**。Offer 删除内核在原删除事务里标记锚点 `deleted_at`，撤销在途任务，然后才删 Offer；锚点禁止删除，标记后不允许重新发起。数据库删除触发器只负责补充约束：有锚点但未标记、或仍有 signing 任务时拒绝物理删除，防止漏接内核产生孤立在途任务；不在 SQL 触发器里发通知。无锚点的旧业务按原逻辑删除。审计与已完成文件继续留存，不强迫保留整份 Offer 或其个人信息副本。

### 4.3 迁移与升级验证

S1 独立契约片先合：新表 ENABLE + FORCE RLS、`app_owner` 授权、复合外键、CHECK、索引、来源端口及公共类型一起交付。迁移号开发时生成、不预占；不改 0208 或已合入 SQL，不加兼容分支、不回填历史数据（DEC-402）。已有 transfer 行天然满足新约束，升级用例保留它们以验证迁移安全，不等于产品存量兼容。

本迁移改变现有写入列及约束，**DEC-913 适用**：开发在 PG16 普通 `app_owner` 跑仓库全部 `migrateBefore` / 旧结构造数升级用例（开发时动态枚举，不固定“22 个”）；补查旧结构夹具不得提前引用新列，旧迁移阶段不能调用依赖新列的新写接口。另验迁移前已存在 transfer signing / completed、迁移后新 Offer / entry、非法跨租户锚点 / 外键拒绝、裸连接隔离。不能只跑本单 AC 替代升级集合。

## 5. 发起服务、并发和未知结果

入口分别为单条 Offer / 入职命令；不得直接调用 `initiateTransferSign` 把业务种类假装成 transfer。抽取无来源假设的公共发起落库服务，输入为服务端已经解析的 scene、来源键、人员、部门、发起人、通用变量、模板快照；这些值不进入客户端输入。调动仍独立算自己的任职 / 合同变量。

事务顺序：命令守卫重校有效成员、对象 / 按钮 / 当前范围 → 来源行锁与 revision → 来源资格与人员绑定 → 同来源在途检查（已超时的先用现有过期函数结束）→ 模板锁 / 可用性 / 变量字段读权 → 账号有效性 → 场景设置快照 → 任务、文件、审计 / outbox 同事务写入。模拟 provider 继续为空操作，真实外部调用不进入事务。

新任务成功为 `signing / employee`；已有人员但账号不可用记 `failed / EMPLOYEE_NO_ACCOUNT`；发起人账号失效在事务守卫拒绝，不把被撤权的人继续当有效操作者。纯渲染异常记 `RENDER_FAILED`，数据库异常抛出并回滚，不能转成失败任务掩盖存储故障。失败任务不发通知、不自动重试；操作人显式再次选择模板发起新任务。

- Offer 锁序沿用 `sync-lock.ts`：关联 Offer → 员工闭包 → 任职业务 → 已有组织锁 → 签署任务（ID 升序）；入职入口先走 `entryOfferHooks.beforeAction`，再锁员工 / 业务，最后锁任务。需要解析来源时先无锁定位，再按上述顺序加锁重读。
- 本人确认、手动撤销 / 提醒、定时器只锁任务，不在持有任务锁后再取 Offer / 员工 / 业务锁。来源撤销先持业务锁再取任务锁；确认先完成则保留 completed，来源撤销先完成则确认 409。无需倒置锁序去做双向业务回写。
- `If-Match` 是来源 revision；POST 不改 Offer 内容、不追加任职版本、不无故增加来源 revision。任务自身 revision 从 1 开始，后续签署用任务 revision。唯一索引及来源锁保证两个新命令不能同时产生两条 signing。
- 所有命令带 `Idempotency-Key`，指纹包含租户、路由、来源 ID、来源 revision、规范化模板 ID 序列。同键同内容返回同任务；异内容 409。不因模板后来停用或原任务已完成而重新执行旧命令。
- 重放 / 命令回查仍检查当前成员、入口权限、来源当前范围及本任务 `variable_read_fields` 所记字段的当前读权与人员读范围；模板后来修改不改变这份校验集合，不能按当前模板重新推导历史命令所读字段；来源删除 / 替换给 404，不能交出旧回执。**不再执行原来源资格、旧 revision 或“无在途任务”前置条件**，以免成功命令把自己的任务当冲突。首次执行和重放返回同一最小回执 `{sourceId, taskId}`，不缓存正文或字段摘要。
- 网络错误 / 503：保留原命令 ID、请求体与来源 revision，走既有命令状态回查；处理中 / unknown 时禁止新键发起。查明成功后用 mine 详情按当前权限读最新任务；查明未执行才允许原键恢复。409 须重读来源，再由操作者显式新键重提；读不到来源保持 unknown / 不可用，不跨旧新 ID 自动重试。

Offer 和 entry 是独立来源：只改期入职不改 Offer 文本，不因同一个人就撤销 Offer 任务；但取消入职若按既有配置联动 Offer 为 rejected，则两边各按自身状态撤销。恢复入职或 Offer 回到 accepted 不复活旧任务。源业务操作回滚时，任务、审计、通知、锚点标记一并回滚；自动撤销是已授权源业务动作的派生行为，不额外要求操作者持 ESignRecord.Revoke，也不得给其读取任务正文的权利。

## 7. 通知、文件与业务界面投影

通知五模板、收件人、幂等、站内 channel 与 F-481 相同：手动提醒发当前节点；到期前 24 小时仅提醒 employee 且一次；完成 / 撤销各员工与发起人一条；不加待签、失败、过期通知。有效期仍 N×24 小时（2～30，默认 2）；scheduler 对三场景一起处理，无新定时任务。标题和正文按资源文件与 `sceneLabel(task.scene)` 生成，通知目标仍 `esign_task / task.id`，点开按本人任务重新验权，不能只凭通知接收人读来源对象。

签署记录、我的签署、PDF / ZIP 都复用。PDF 保留“复刻模拟签署、无电子印章”；模板名与正文冻结，尾注姓名 / 企业名仍取下载时现值（DEC-920），本单不另加冻结名字迁移。文件只给 completed；ESignRecord.Download + 当前人员范围 + files 读权缺一不可；zip 名是否含姓名仍按 owner 字段权，own 下载仍只给签署人本人。

Offer / 入职各增加“电子签署”只读区（单行签署记录入口 / 抽屉，同一组件）：显示本来源最新任务及历史列表，按 `initiated_at DESC, id DESC` 排序；最新 failed 不掩掉之前完成的历史。状态、失败原因用 ESignRecord.status 读权，模板名 / 文件用 files 读权，来源业务自己的状态列继续原文案。

**不是无条件往 Offer / 任职响应挂 esign 协议字段**：签署区单独调用 §8 来源历史接口，在来源当前 view / 范围之外，还要求 ESignRecord.view、当前人员读范围及逐字段裁剪。无记录查看权隐藏签署区，不写“未发起”；空历史统一显示“暂无可见签署记录”，不以裁剪后的空结果断言整个来源从未发起；“未发起”仅用于尚未产生任何任务且已完整授权的发起上下文。来源已被删除统一 404；人员范围不可判定时不泄露任务存在性。历史查询按每条任务的人员范围先做 SQL 过滤，再排序分页；最新任务指当前可见任务中的最新一条，不返回隐藏任务数量。无 ESignRecord 查看权的发起人提交成功后可凭 taskId 到已有“我的签署”看本人的任务，不自动获得全部来源历史。

入职被换 ID 后，新记录只显示自己的任务；旧任务仍在签署记录 / 我的签署中按历史来源保存，不并入新记录的完成判定。源列表增加签署入口时不得在前端循环拉全租户任务再按 ID 筛选。

## 10. 前端行为与恢复

- Offer 的 sign 接入实际 HTTP，不走 demo-stubs；入职替换固定 disabled 项，先按权限隐藏，再按服务端上下文决定可用性。入口不依赖前端能否看见状态字段；若源记录缺 revision，先读上下文，不拿 0 代替。
- 共用 `SourceSignDialog` + `TemplatePicker`。模板读取失败与空列表分开显示；失败不清空成“没有模板”；全选超过 20 时提示上限，不静默截断。发送期间禁用确定；失败任务要显示明确的“发起失败”及原因，不能只弹“成功”。
- 选项接口读权等同写入口，只有发起权限而无配置权限的人仍能完成流程；没有人员变量读权时可选模板，但提交会明确 403，弹窗说明这类模板需相应人员字段权限，不前端猜测填值。
- 成功后以回执 taskId 读取 mine 详情展示实时状态；来源区域有记录权限则独立刷新。读任务失败显示“已提交，状态读取失败”，不能重新发一个任务。未提交状态才允许关闭并放弃草稿。
- 会话、租户、身份、来源类型、来源 ID 作为缓存 / 草稿键；关闭弹窗、换页、换来源后旧响应按 epoch 丢弃。unknown 草稿保留原键与来源 revision；新 ID 不能继承旧命令。403/404 清理不可读内容并停止回查；409 提示刷新后显式重提。
- 场景页三行独立 revision / 保存状态，改 Offer 设置不影响入职或调动；记录、mine、通知统一场景标签映射，未知值显示受控不可识别文案，不能回落为“调动”。所有新文案进入 offers / entries / esign 资源文件。
