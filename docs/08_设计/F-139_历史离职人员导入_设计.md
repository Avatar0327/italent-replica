## 0. 结论摘要

> 已由 F-493 修订：见 [F-493 设计](F-493_历史离职人员导入对齐北森_设计.md) §1、§2（第 3、4、6、7、8 条结论已改：异步、1000 行、按邮箱识别、建停用账号、编制满不提示、列表不显示导入标识）。

1. 两步式入口：`POST /exits/import/preview`（只校验）→ `POST /exits/import`（写入），单批 ≤ 100 行，整批成功或整批失败。
2. 每行在同一事务内做三件事：建档（不开通账号）→ 入职业务落地（effectiveDate = H）→ 离职业务直接落地为 effective（`exit_requests.mode = 'import'`，业务载荷 mode 仍为 `'direct'`；L 原样、不顺延）。
3. **P2-06 的修订**：可信导入的入职步骤只校验**有限在职区间** `[H, L]`（闭区间，内部按半开区间 `[H, L+1)` 传给 `assertEmploymentDepartmentAvailableWithin`），不按 `[H, ∞)` 拦截。离职之后（≥ L+1）部门才停用，照样可以导入。
4. 历史导入**不走** `activateExit`，也**不触发** `exitPostEffectHooks.onEffective` 的任何订阅方。因此不会作废在途申请、不终止流程、不作废评审、不进账号停用队列，也不调合同端口、不做职责转交或交接。依据见 §7。黑名单只在行里明确勾选时直接写名单（§7.3）。
5. 排序口径与 F-140 一致：两条业务各自在版本链上写 `version_no = 1` 的人工版本，计划列由触发器推导（hire = H，leave = E = L+1）。历史导入没有“系统顺延”，所以不写任何系统派生版本。回执、操作日志和审计按**行号**排序，不按时间戳或 UUID。
6. 编制：历史段 `[H, E)` 经编制模块新增的导入专用评估入口 `importedTenureExcesses` 判超编（§4.4）。现有评估器只判 transfer / intern_regularization / retire_rehire，hire 直接返回无超编；普通 hire 的这一口径不变。
7. 导入成功的已生效离职可以经 `PATCH /exits/:id` 改期，复用 F-140 §3.4 的改期编排（重定位 / 替代），不另开口子，也不拒绝（§8.3）。
8. 新增：按钮 `Employment.DimissionImport`、`exit_requests.mode` 取值 `'import'`（迁移改 check）、`ctx.trustedExit` 取值 `'import'`。实现规模估算：产品代码约 1345 行，手写总量约 3215 行，超出单 PR 的 3000 行上限，按 §11.2 拆成后端、前端两片。

## 1. 用途与边界

规格 `docs/02_业务建模/30_离职退休与职责转交_规格.md` §1.1 第 16 行，“导入离职”的第 ② 项：导入**历史离职人员**，即系统中不存在的人，供上线初始化使用。

| 场景 | 走哪里 | 本设计 |
|---|---|---|
| 在职员工批量离职（规格导入 ①） | `POST /exits/batch`：前端把 Excel 行转成批量请求，后端只有这一套规则 | 不涉及 |
| 在职员工的任职导入（`POST /employees/:id/import`）带 kind=leave 的行 | 整批 400 `EXIT_IMPORT_USE_EXIT_ENDPOINT`（R2-T03 B-54，不变） | 不改；B-54 的提示文案保持不变，前端可以在提示里给出本入口 |
| 系统里还没有这个人，要带着一段已结束的历史任职导入 | **本设计** `POST /exits/import` | ✓ |
| 系统里已有此工号（在职、离职、待入职都算） | 本入口按行拒绝 `EMPLOYEE_NO_EXISTS`；离职重聘、补录历史段走各自的既有入口 | 只拒绝 |

一行只表示**一个人的一段任职**（一次入职到一次离职）。多段历史（离职后重聘再离职）首期不支持：同一批出现重复工号按行拒绝（§4.2 #R3）。这一点列入 §13 原站未测项。

## 2. 入口与报文

> 已由 F-493 修订：见 [F-493 设计](F-493_历史离职人员导入对齐北森_设计.md) §3.1、§6（删除预览；`POST /exits/import` 改为 202 入队；请求体去掉 `employeeNo` 与 `confirmed`、加 `email`）。

### 2.1 路由

| 路由 | 作用 | 写入 |
|---|---|---|
| `POST /exits/import/preview` | 解析、逐行校验、编制评估，返回逐行结果和警告；**不**写业务数据 | 无（只读事务，不走命令台账） |
| `POST /exits/import` | 整批写入 | `Idempotency-Key` 必填，走 `runWrite` 命令台账；body 带 `confirmed?` |

两个路由挂在 `apps/api/src/modules/employment/exit-routes.ts`，与离职的其他入口放在一起；实现文件为 `exit-import.ts`（§11）。

### 2.2 请求体

```jsonc
{
  "rows": [
    {
      "rowNo": 1, // 前端从 Excel 带上的原始行号（1 起），回执按它排序；缺省时按数组下标 + 1
      "employeeNo": "H0001",
      "name": "合成甲",
      "entryDate": "2023-03-01", // H
      "departmentCode": "D-SYN-01", // 按租户业务编码解析（DEC-060）
      "positionCode": "P-SYN-01", // 可选
      "postCode": null, // 可选，职务
      "lastWorkDate": "2025-06-30", // L
      "exitTypeCode": "resign", // 可选；须为启用项
      "exitReasonCode": null, // 可选
      "exitDestinationCode": null, // 可选
      "addToBlacklist": false, // 可选，默认 false
      "blacklistReason": null, // addToBlacklist=true 时必填，同 §4A 的加黑三项
      "blacklistExpiryDate": null,
      "blacklistNote": null,
    },
  ],
  "confirmed": false, // DEC-258：编制警告确认
}
```

- 严格模式：出现未知键返回 400 `VALIDATION_FAILED`。`rows` 为空或超过 100 行返回 400，超限时 reason 为 `BATCH_LIMIT_EXCEEDED`，沿用 `MAX_LOOKUP_ROWS = 100`。
- 请求体上限沿用默认 32KB 不放宽（100 行 × 约 300 字节，足够）。若实现时实测超限，再按 AGENTS §10 单独放宽，并在 PR 中写明。
- 不接受 `employeeId`、`kind`、`mode`、`effectiveDate`、`initiator` 等系统字段。H、L 只能从上面这两个字段进入。

### 2.3 响应

- preview：`200 { rows: [{ rowNo, ok, errors: [{ field?, reason, message }], warnings: [...] }], hiddenCount, summary: { total, ok, failed, warned } }`。
- import 成功：`201 { batchId, rows: [{ rowNo, employeeId, hireBusinessId, exitBusinessId }] }`。出参按 §5.3 裁剪。
- import 失败：整批 400 `IMPORT_ROWS_INVALID`，`details.rows[]` 带逐行原因。编制警告未确认时返回 409 `CONFLICT`，`details` 为 `{ reason: 'CONFIRMATION_REQUIRED', rows: [{ rowNo, warnings }], hiddenCount }`，警告形态见 §4.4。两种情况都**零写入**，前后读取一致。

## 3. 行字段与校验规则

> 已由 F-493 修订：见 [F-493 设计](F-493_历史离职人员导入对齐北森_设计.md) §3.2、§3.3（工号列删除、邮箱必填、批内重复邮箱两行都拒、`EMAIL_TAKEN`、系统生成工号）。

| 字段 | 必填 | 规则 | 违反时 reason |
|---|---|---|---|
| 工号 | ✓ | 租户内不存在（含已删除、待入职）；批内不重复 | `EMPLOYEE_NO_EXISTS` / `DUPLICATE_IN_BATCH` |
| 姓名 | ✓ | 同 `createEmployee` 现有规则 | `VALIDATION_FAILED` |
| 入职日期 H | ✓ | 合法日期 | `VALIDATION_FAILED` |
| 最后工作日 L | ✓ | `H ≤ L`，且 `L < 今天`（按租户时区，DEC-056） | `EXIT_IMPORT_RANGE_INVERTED` / `EXIT_IMPORT_NOT_HISTORICAL` |
| 部门编码 | ✓ | 能解析到本租户组织；在 `[H, L]` 内每天可用（§4.1）；H 不早于设立日 | `REFERENCE_NOT_FOUND` / `EMPLOYMENT_DEPARTMENT_DISABLED` / `ENTRY_BEFORE_DEPARTMENT_FOUNDED` |
| 职位 / 职务编码 | — | 能解析到本租户对象；按 H 时点校验启用与区间（`validateEmploymentReferences`，asOf = H） | `REFERENCE_NOT_FOUND` / `VALIDATION_FAILED` |
| 离职类型 / 原因 / 去向 | — | 当前启用项（字典是“当前”配置，不是任职区间的事实），复用 `exit-dictionaries.ts` 的校验 | `EXIT_DICTIONARY_DISABLED` / `EXIT_DICTIONARY_UNKNOWN`（与 §4A 同码） |
| 加黑三项 | — | `addToBlacklist=true` 时原因必填；有效截止日 ≥ E 或为空 | `VALIDATION_FAILED` |

L = 今天被拒绝：L 为今天时 E = 明天，离职尚未生效，这是“在职员工办离职”，应走 `exits/batch`。

## 4. 有限区间校验（P2-06 的修订）

### 4.1 规则

对新建的这一段在职期 `O = [H, L]`（闭区间），**只**校验这一段内的事实：

| 校验 | 区间 | 函数（现有） | 说明 |
|---|---|---|---|
| 部门在段内每一天可用 | `[H, L+1)` 半开 | `assertEmploymentDepartmentAvailableWithin(tx, ctx, deptId, H, E)` | 与撤销离职、迟到顺延的 ΔO 校验同一实现（R2-T03 §6B.2） |
| 入职日不早于部门设立日 | H | `assertNotBeforeFounded` | 入职类既有规则（DEC-138 / 139），保留 |
| 部门在 H 存在且属于本租户 | H | `assertOrg` | 保留 |
| 职位 / 职务 / 职级等引用 | asOf = H | `validateEmploymentReferences` | 只看 H 那一版，L 之后停用不影响 |
| 编制 | `[H, E)` | 新增 `importedTenureExcesses`（§4.4）：与 `employmentEstablishmentExcesses` 共用明细求值 `evaluateEstablishment`，`until = E`，在 H 与段内每个编制周期起点各判一次，绕开 kind 过滤只对这一入口生效 | 与撤销离职 ΔP 同口径；严格、非严格超编都只警告、要确认（DEC-258），不拦。普通 hire 照旧不判 |
| 组织调整执行中 | 当下 | `assertNotPausedByOrgAdjustment` | 保留：这是并发保护（调整执行期间不准任何任职写入），不是对区间的状态判断；409 `ORG_ADJUSTMENT_EXECUTING`，等调整执行完再导入 |

**不按“当前”或 `[H, ∞)` 判断的项**：

- 部门“现在”是否停用；
- 职位“现在”是否停用；
- 员工“现在”的状态（新人没有状态）。

旧实现的问题在于：v1.6 第 2 步复用了通用 hire 校验，即 `validateNewEmploymentReferences → assertEmploymentDepartmentAvailable(…, H, entry=true)`。它的 SQL（`org/employment-validity.ts`）把“开始日之后出现的**任何**停用段”都算作不可用，相当于按 `[H, ∞)` 校验。

### 4.2 正例与反例

设：今天 = 2026-11-05；部门 D 设立于 2020-01-01；H = 2023-03-01；L = 2025-06-30；E = 2025-07-01。

| # | 部门 D 的版本 | 期望 | 旧实现（v1.6 复用通用 hire 校验） |
|---|---|---|---|
| P1 | 2025-08-01 起停用（晚于 L） | ✓ 导入成功 | ✗ 误拒 `EMPLOYMENT_DEPARTMENT_DISABLED`（P2-06） |
| P2 | 2025-07-01 起停用（= E，L 当天还可用） | ✓ | ✗ 误拒 |
| P3 | `stop_date = 2025-06-30`，之后没有接续版本（不可用段从 L+1 开始） | ✓ | ✗ 误拒 |
| P4 | 2021-05-01～2022-01-01 停用后恢复启用（早于 H） | ✓ | ✓（旧实现同样放行，回归保护） |
| R1 | 2024-01-01 起停用（落在段内） | ✗ 行错误 `EMPLOYMENT_DEPARTMENT_DISABLED`，`disabledOn = 2024-01-01` | ✓ 拒绝（旧实现碰巧也拒） |
| R2 | 2024-01-01～2024-02-01 停用后恢复（段内短暂停用） | ✗ 同上 | ✓ 拒绝 |
| R3 | 2023-01-01 起停用、2023-06-01 恢复（H 落在停用期内） | ✗ 行错误，用入职提示“在入职日期时为停用状态” | ✓ |
| R4 | 部门设立于 2023-05-01（晚于 H） | ✗ `ENTRY_BEFORE_DEPARTMENT_FOUNDED` | ✓ |
| R5 | H = 2025-07-01、L = 2025-06-30（区间倒置） | ✗ `EXIT_IMPORT_RANGE_INVERTED` | ✗ 无此校验（v1.6 只写了 `H ≤ L`，没有给出码） |
| R6 | L = 今天，或 L 晚于今天 | ✗ `EXIT_IMPORT_NOT_HISTORICAL` | — |
| R7 | 工号已存在（任意状态） | ✗ `EMPLOYEE_NO_EXISTS` | ✓ |
| R8 | 同一批两行工号相同（同一人的两段，区间可能重叠，也可能不重叠） | ✗ 两行都报 `DUPLICATE_IN_BATCH` | 未定义 |
| R9 | H = L（只在职一天） | ✓（闭区间含端点） | ✓ |

“与已有记录重叠”在本入口的表现是：一个新人员不可能已有任职记录，所以重叠只会以 R7（工号已存在，库里已有这个人的记录）或 R8（同一批内同一个人的两段）出现。两者都按行拒绝，不做区间合并或拼接。

### 4.4 编制评估的接入（第 1 轮 P2-2）

> 已由 F-493 修订：见 [F-493 设计](F-493_历史离职人员导入对齐北森_设计.md) §7.2（导入入口不再做编制评估与确认）。

**现状**：`evaluateEstablishment`（`establishment/employment-check.ts:112`）在 `:120` 先判 `if (!CAPACITY_KINDS.includes(target.kind) || !target.departmentId) return none;`，`CAPACITY_KINDS = ['transfer', 'intern_regularization', 'retire_rehire']`（`:71`，注释写明“入职、重聘等不判”）。撤销离职的 ΔP（`exit-cancel-intervals.ts:164-175` `segmentExcesses`）能评估，是因为它以 `kind: 'transfer'` 调用。导入如果按 hire 传参，就一定返回 `none`。

**适配**：在 `establishment/employment-check.ts` 新增导入专用入口，普通入口和 `CAPACITY_KINDS` 都不动。

```ts
/** F-139 §4.4：历史导入段 [from, until) 的编制评估（明细版）；只供 exit-import 调用，普通 hire 仍按 CAPACITY_KINDS 不判。 */
export interface ImportedTenureSegment {
  readonly key: string; // `import-row:${rowNo}`，批内唯一；预检时人员尚未建档，不能用 employeeId
  readonly employeeId: string | null;
  readonly departmentId: string;
  readonly positionId: string | null;
  readonly fields: Partial<PresetFields>; // 与第 3 步落地相同的字段（含 employType、占编条件字段）
  readonly from: string; // H
  readonly until: string; // E，必填：只评估有限区间
}
export async function importedTenureExcesses(
  tx: Tx,
  ctx: EmploymentContext,
  segment: ImportedTenureSegment,
  peers: readonly ImportedTenureSegment[],
): Promise<CapacityExcess[]>;
```

| 要点 | 做法 | 依据 / 理由 |
|---|---|---|
| 绕开 kind 过滤 | `evaluateEstablishment` 增加内部参数 `scope: 'default' \| 'imported_tenure'`（不导出、不进 `ActivationTarget`）；过滤改为 `scope === 'default' && !CAPACITY_KINDS.includes(kind)` 时返回 `none`。target 的 `kind` 仍写 `'hire'`，不冒充调动 | 不放到 `ActivationTarget` 上，是为了让 `assertEstablishmentCapacity`、`employmentEstablishmentExceeded`、定时生效等现有调用方无法打开它，普通 hire 的口径不会被顺手放宽 |
| 有限区间 | 每次求值都传 `until = E`；按 `[H, ...establishmentPeriodStartsWithin(H, E)]`（`:222`）逐个起点调用，与 `segmentExcesses` 同一循环；同一编制对象（`capacityId + positionId`）取最大峰值 | `projectedMembers` 在给了 `until` 时窗口截到 `until`（`:301`），L 之后的人数不会进入峰值；周期起点循环保证跨多个编制周期的段每个周期都判 |
| 目标本人 | `reconcileCarried: false`、`propagates: false`、`fields` 直接给出；新人员没有前序，`findPredecessor` 为空，来源部门取目标部门 | 不模拟携编、不模拟向后更新（新人员没有后续记录） |
| 批内其他行 | `peers` 为同批中**其他**已通过第 1 步非编制校验的行。每次求值（即 §4.4 循环里的每个起点）先算本次的评估窗口 `W = [effectiveDate, min(E, periodEnd + 1))`：`effectiveDate` 是本次起点（H 或段内某个编制周期起点），`periodEnd + 1` 与 `projectedMembers` 的 `periodEnd` 同义（`employment-check.ts:300-301`），E 是目标行的 `until`。每个 peer 的 `[from, until)` **先与 W 求交**，交集为空的 peer 本次不计入；非空的交集作为独立成员（键 = `peer.key`）在目标本人投影之后加入，再走 `clipMembership` 裁到组织成员窗口 | 预检时批内各行都还没写库；不计入同批其他行，就会出现“上限 1、库里 0 人，同批导入 2 人”两行各自峰值 1、都不提示。只交给 `clipMembership` 不够：它只按组织成员窗口裁剪（`membership-windows.ts:43-54`），窗口可延伸到编制周期末；`target.until` 只截断库内成员和目标本人（`occupancyRows` 取到 `windowEnd`），不会作用于后插入的 peers。不先求交，目标行的峰值会算进它离职之后才入职的 peer，给目标行误报警告并写确认审计（AC-DM-30-06 ⑥） |
| 外部人员 | `fields.employType === 'external'` 时返回空（与 `:139` 现有口径一致） | 不新造规则 |
| 严格 / 非严格 | 两者都进入警告，**都**只确认、不拒绝；明细与撤销离职同形态，不另加字段 | DEC-258 及 R2-T03 §6 第 3 条“严格控编同样只确认”，与撤销离职 ΔP 同口径 |

**preview 与 import 共用**：两条路由都在 §6 第 1 步（锁内预检）调用同一函数 `assessImportRows(tx, ctx, rows)`（`exit-import.ts`）：先收齐全部行错误；行错误为空时，再逐行调用 `importedTenureExcesses(segment, peers)`。preview 返回逐行警告；import 有警告且 `confirmed !== true` 时整批 409，零写入。两边入参和求值函数相同，结果只会因两次调用之间库里数据的变化而不同；import 在 ⑤ 编制锁内求值，以 import 这次为准。

**警告明细**（与撤销离职同一形态，`exit-cancel-intervals.ts:224-233`）：`{ reason: 'ESTABLISHMENT_EXCEEDED', capacityId, departmentId, positionId, from: H, to: E, peak, limit }`。裁剪：部门可见性由 §5.1 第 4 条的“显式看全部范围”前提保证；编制对象另按 `capacityVisible`（F-251）逐项判，不可见的只计入 `hiddenCount`，不返回 ID、峰值和上限。

## 7. 与离职生效（`activateExit`）的关系

### 7.1 结论

历史导入**不调用** `activateExit`，也**不运行** `runExitEffectiveHooks`。以下是 `runSteps` 及 effective 订阅方的逐项去留：

| `activateExit` / 订阅方的步骤 | 导入 | 依据 |
|---|---|---|
| 0a 迟到顺延 `postponeLateExit` | ✗ | §8.2 |
| 0c ΔO 有终点校验 | 改为 §4 的整段校验 | 导入的整段都是新增段 |
| 0d 摘下未来调动 `followingTransfers` / `detachAndVoid` | ✗ | 新人员没有未来调动 |
| 1 作废在途任职申请 `voidInFlightApplications`（DEC-496① → DEC-578 / DEC-725①） | ✗ | 见 §7.2 |
| 1′ 超限确认重算 `reconcileConfirmedSet`（DEC-626） | ✗ | 没有在途调动 |
| 2 落地 `materializeEmploymentRecord` | ✓（§6 第 5 步） | 版本链、时间轴事实须与真实离职一致 |
| 3 不新增占编断言 `assertNoNewEstablishmentOccupancy` | 改为 §4 的编制评估 | P 投影的新增段就是 `[H, E)` 本身，按 DEC-258 确认 |
| 4 合同端口 `handleContractsOnExitEffective` | ✗ | 不生成合同（§6 第 3 步） |
| 5 重聘 `createRehireIfPlanned` | ✗ | 只适用于退休；离职导入不支持重聘计划（§13 #U5） |
| 6 职责转交 `runExitDutyTransfer` | ✗ | 新人员没有职责 |
| 8 订阅方：终止其他流程 `terminateOtherFlows`（DEC-725①） | ✗ | 没有在途流程 |
| 8 订阅方：作废在途评审 `voidInFlightAssessments` | ✗ | 没有评审 |
| 8 订阅方：黑名单 `writeExitBlacklist` | ✗（改由 §6 第 6 步直接写手动名单） | §7.3 |
| 8 订阅方：账号停用队列 `queueExitAccount`（F-261） | ✗ | 没有开通账号 |
| confirmed 端口：预减 `registerPreRelease`、交接 `launchExitHandover` | ✗ | 不经过 confirmed 阶段；`pre_release_date` 直接写 E，等于“没有预减期” |

### 7.2 为什么不触发“作废在途申请”

- DEC-496① 的原文（及后来取代它的 DEC-725①）针对的是“离职**生效时**员工名下的在途流程”。DEC-578 把这一步归给 R2-T03 B3-2，依据是 §5.1-1，前提都是：员工此前在职，身上挂着调动、合同等申请，离职让这些申请失去意义。
- 历史导入的人员在同一事务内才被创建。导入之前系统里没有这个人，所以“在途申请”这个集合从定义上就是空的；第 7 步的断言保证了这一点。不调用它，不是绕开规则，而是规则的适用前提不成立。
- 主动不调用（而不是“调用了也无事可做”）的理由：effective 订阅方会持续增加（F-261、BE-8 等）。导入如果挂在这个端口上，以后任何一个新订阅方都可能对导入人员产生副作用，比如写交接、发通知、发起账号命令。本设计把“导入不触发生效副作用”定为契约，并用 AC-DM-30-07 测试守住：测试中注册一个探针订阅方，断言导入时它没有被调用。

### 7.3 黑名单

- 行里勾选加黑：直接写手动名单，效果与 §4A 直接离职勾选加黑后生效的结果相同。不做的话，HR 迁移来的黑名单就丢了，之后同一人重聘时 DEC-569 拦不住。
- 不跑自动加黑规则（`matchBlacklistRule`）。自动规则依据“生效前的部门链”和“已生效离职次数”，属于离职**生效**时的租户策略。历史数据按今天的规则补算，结果不一定是原站当年的结果。原站未测，见 §13 #U4。
- 加黑写入失败（例如工号对应的人已在有效名单里），在导入场景下不可能发生（新人员）。如果发生，按 `writeExitBlacklist` 的口径：`BLACKLIST_DUPLICATE` 跳过并留痕，其他错误整批回滚。

### 7.4 入职步骤的黑名单查重（DEC-569）照常执行

`assertNotBlacklisted`（`blacklist.ts:426`）按 `employeeId` 查有效名单。导入人员在同一事务里才创建，名单上不可能有他，这一步对导入总是放行。所以不给导入另开跳过分支，少一条可信例外。第 6 步的加黑写在入职之后，不会自我拦截。

## 8. 排序与版本链口径（DEC-499 / F-140）

### 8.1 单一排序

- 每条业务的版本链只有 `version_no = 1` 一条人工版本。`planned_effective_date` 由 F-140a 的 BEFORE INSERT 触发器推导：hire = H，leave = E。
- 导入**不写**系统派生版本（不顺延），所以“人工计划日”和“系统顺延日”两列不会出现分歧。读计划日一律走 `plannedEffectiveDate(tenantId, businessId, fallback)`，导入服务不另写一份 SQL。
- 两条业务都直接以生效状态落地，不进待生效队列，因此不参与 `finalExecutionDateSql` 的队列排序。它们在时间轴上的顺序由 `employment_timeline.start_date + sort_order` 决定；同一员工内 hire 在前、leave 在后，由 `insertEmploymentTimeline` 现有规则保证。
- 状态事件用 `event_no`（业务内单调）和 `event_seq`（全局 identity）排序。批内回执、操作日志明细、审计 meta 一律按 `rowNo` 排序，**不**用 `created_at`、UUID 或数组的偶然顺序。

### 8.2 为什么不顺延 L

`resolveLateLeave`（DEC-263① / DEC-272）处理的情况是：离职**计划**在某天生效，系统实际晚于这一天才执行。这时把最后工作日顺延到执行日的前一天，保证“生效前一直在职”的事实成立。历史导入不是“计划后晚执行”，而是“补录已经发生过的事实”：L 就是事实本身，顺延到今天会把人员凭空延长成在职到昨天，与原站数据不符。这一点承接 v1.6 的假设 A-4。R2-T03 v1.9 删除 A-4，是因为它跟随 §4C 一起移出了，不代表结论被推翻。

### 8.3 与 F-140 人工改期的关系

（第 1 轮 P2-1 修正：上一稿写成“拒绝改期”，误读 F-140。）

导入的离职单状态为 effective。F-140 §3.4 允许已生效离职改期，`rescheduleExit` 接受 `effective` 状态（`exit-reschedule.ts:109-117`）并进入 `rescheduleEffectiveExit`。所以 HR 要更正导入的最后工作日时，走 `PATCH /exits/:id`，**复用 F-140 改期编排**，导入不另写改期分支，也不拒绝：

| 新日期 | 处理（全部是 F-140 / R2-T03 现有规则，本设计不新造） | 依据 |
|---|---|---|
| 新 E ≤ 今天（新 L 仍在过去，含仍落在原历史区间内的改早、改晚） | **同一业务重定位** `repositionExit`：追加人工快照版本（`version_no = 2`、`manual_plan = true`，计划日 = 实际日 = 新 E），时间轴删掉后按新 E 重插，入职段的 `valid_during` 随之变为 `[H, 新 E)`；人员状态按新位置重新派生（仍为 8）；写 `employment.leave.replanned`；调用 `onRecordRescheduled`。**不**重放离职生效副作用（`exit-reposition.ts:1`） | F-140 §3.4 第 1 行；`exit-reschedule.ts:156-158` |

## 9. 审计、操作日志与幂等

> 已由 F-493 修订：见 [F-493 设计](F-493_历史离职人员导入对齐北森_设计.md) §3.4、§6.4、§10.3（批次级幂等、逐行事务、收尾操作日志）。

### 9.1 审计（同事务，DEC-019）

每行写入：

1. `employment.employee.create`（既有）；
2. hire 落地的 `employment.record.create`（既有，`auditMaterialization`）；
3. leave 落地的 `employment.record.create`（既有）；
4. 新增 `employment.exit.imported`：对象 exit-request，after 为 `{ state: 'effective', mode: 'import', lastWorkDate, effectiveDate }`，meta 为 `{ batchId, rowNo, employeeId }`；
5. 若加黑，写入 `addBlacklistEntry` 的既有审计；
6. 带 `confirmed: true` 且该行有编制警告时，写 `employment.exit.over_capacity_confirmed`（§4.4）。

整批另写一条操作日志：`recordOperationLog`，behavior 为 `'import'`，`importedItems` 按 `rowNo` 列出每行的 `employeeId` / `exitBusinessId`。写法照 `importEmployment`（`routes.ts`）。

### 9.2 失败留痕

`POST /exits/import` 外层套 `withFailedImportLog`。整批 400、409 或 503 时，在**独立事务**里记一条失败导入日志（批次号、行数、失败原因码的汇总），不记行内的个人字段；归属锚点用 `failedImportAnchors` 的现有写法。业务失败、存储不可写、结果未知三类分开记（AGENTS §10）。

### 9.3 幂等（AGENTS §10）

- `Idempotency-Key` 必填，命令台账按（租户、用户、路由、键）记录请求体指纹：
  - 同键同内容：回放第一次的结果，前提是 §5.1 的权限链复核通过；
  - 同键不同内容：409 `IDEMPOTENCY_CONFLICT`。
- `confirmed` 属于请求内容。先不带确认收到 409，再带 `confirmed: true` 重提时，客户端必须**换新键**，规则与离职撤销、批量离职的 DEC-258 协议一致。前端提示文案须照此实现。
- 结果未知（网络超时）时，客户端用**原键**重放，台账会返回第一次的结果。不允许换键盲目重试，否则可能产生两批“工号已存在”的错误回执（第二批会整批 400，不会重复写入，但会误导用户）。
- preview 不走台账。

### 9.4 并发

- 与 `POST /employees` 同工号同时提交：工号 advisory lock 与唯一约束保证只有一方成功，另一方返回 400 `EMPLOYEE_NO_EXISTS`（导入），或者 `createEmployee` 现有的冲突码。
- 与组织停用同时提交：两边都持 ④ 组织设置锁，并在锁内复查。导入先执行时，停用命令按 `org/deactivation.ts` `countDepartmentStaff` 的现有口径，统计停用日起仍在职的任职；停用日晚于 L 时，导入人员不应被计入，这一点由 AC-DM-30-02 的追加断言守住。停用先执行时，导入按 §4 复查。
- 两批导入同时提交：工号 advisory lock 按工号排序后获取，不会死锁。

| # | 假设 | 取最保守做法的理由 | 作用对象 |
