### 0.2 对照你规划包里的 8 条硬规则（R1 在制分支）
| # | 硬规则 | 结论 | 要点 |
|---|---|---|---|
| 1 | 数据范围默认空 | ✅ 基本符合 | 空范围即拒绝；但管理员角色写死为“全部组织” |
| 2 | 任职记录做成事件溯源版本链 | 🟡 部分 | 版本表只追加、不可改；但实体头行原地 UPSERT，旧表同时双写；生效日被强制改成执行当天；没有 StaffID 任职周期 |
| 3 | “变更前”字段不单独建列 | 🟡 部分 | 旧历史表有 `from_org_id` 这类列 |
| 4 | 审批通过 ≠ 生效 | 🟡 部分 | 状态分开了；**没有定时生效任务**，只能人工执行 |
| 5 | 组织多套层级 | ❌ 不符合 | 只有一个 `parent_id`，没有行政、业务、财务多套上级 |
| 6 | 身份与数据范围多对一 | ❌ 不符合 | 范围以 JSON 存在每条授权里，不是独立实体 |
| 7 | 租户隔离 | 🟡 部分 | 表上有 tenant_id；但安装记录只有一行、成员主键是 user_id：**一个部署只能有一个租户，一个用户只能属于一个租户**，不满足 DEC-006 对外多租户 SaaS |
| 8 | 流程匹配 | 🟡 部分 | 按业务类型隔离做到了；没有“优先级条件”匹配 |

另外：**完全没有向后更新**（R1-T06）；R3 只是通用记录表上的增删改查；代码写得很密（`lib/hris` 平均每行约 280 字符），人和 AI 都难读。

**值得保留的部分**：并发与安全的防护思路（CAS 乐观锁、幂等键、不可变触发器、有界查询）；测试框架（`node:sqlite` 内存库，不需要网络和 Cloudflare，云端容器可以直接跑）；审批委托与转办；报表引擎（R2-T10 可以参考）；员工门户；11 类人员子集导入；原站取证分支。

### 0.3 结论：当前规划仍需调整
1. **访问问题没变**：两个云端代理仍然只能读 GitHub 仓库（v1 的第一部分依然有效）。
2. **多了一个前置决策 D-C：以谁为开发基线。** 我推荐 **方案 B：新建仓库，严格按 v0.18 规格开发，GPT 代码作为只读参考库**。
   - 理由 1：GPT 版有 5 处核心数据模型与硬规则冲突（组织层级、数据范围实体、版本链、向后更新、多租户）。它们都在最底层，改造等于重写，还要额外背负双写和迁移门禁这两层包袱。
   - 理由 2：60% 的代码在范围外，而且可读性差，会拖慢两个代理。
   - 理由 3：你的规划包是逐项取证后定下的规格，比 GPT 版的依据更扎实。
3. **合并前还要对齐一次决策**：GPT 项目里有自己的已批准设计（D1–D7、CP-002/003）。例如“调动必须调出、调入两级审批”“授权 HR 手动执行生效”“原站保存即生效不复制”，这些可能和你的 DEC-006～046 冲突，需要逐条对照后由你拍板。

| 方案 | 做法 | 适合的情况 | 代价 |
|---|---|---|---|
| A. 在 GPT 代码上改 | 修 11 项失败测试，逐步重构数据模型 | 你很看重已有页面，想尽快有个能演示的系统 | 前几轮都在做底层重构，很难并行；硬规则 5/6/7 必须动表结构，还要考虑 82 张表的迁移 |
| **B. 新建，GPT 代码作参考（推荐）** | 新仓库按规格开发；每个任务都附上“可参考的 GPT 文件”清单 | 追求长期正确、规则可追溯 | 前两轮看不到完整页面；GPT 的页面和交互要重新做 |
| C. 新建，但沿用 GPT 的技术栈 | 同 B，技术栈直接用 Cloudflare Worker + D1 + Drizzle + React | 想省掉选型时间，并直接搬用测试框架 | D1 是 SQLite：单批最多 74 条语句，也没有行级锁，对多租户 SaaS 下复杂的版本链是一个约束，需要评估 |

> B 和 C 的区别只在技术栈（D-B）。我的倾向：先按 C 评估，如果 D1 的限制会影响版本链和批量操作，就改用 Postgres（例如 Neon 或 Supabase）+ 同一套 TypeScript 前后端。M0 的第一步就是出这份评估。

## 第一部分：让两个云端代理能访问项目（更新）

### 步骤 1：两个 GitHub 私有仓库
| 仓库 | 内容 | 用途 |
|---|---|---|
| `italent-replica`（主仓库） | 规划包 `docs/` + 新代码 | 两个代理都在这里开发 |
| `italent-gpt-legacy`（参考仓库，只读） | GPT 的 bundle，含全部 14 个分支 | 代理按需查阅；不改动、不部署 |

- 主仓库本机已准备好：`~/Code/italent-replica`，已完成首次提交。
- 参考仓库由 bundle 直接恢复：`git clone <bundle>` 后改 remote 推送，14 个分支全部保留。本机扫描过一遍，没发现凭据；GPT 已替换 1121 处邮箱，并排除了 14 个含隐私的二进制文件。
- 两边都**只授权这两个仓库**。参考仓库在两边的环境里可以作为第二个仓库挂载；如果不支持挂载，就在主仓库里用 `git submodule` 引用，或者由 setup 脚本 clone 进来。

### 步骤 2：推送前的敏感检查（沿用 v1）
- 主仓库：原始提示词已放在 `_private/`，不入库（已完成）。
- 参考仓库：推送后在 GitHub 上搜一遍 `quark_s`、`@qq.`、`@163.`、`huaxia`，确认结果为空。

### 步骤 3：云端环境的 setup 脚本（按审计结果写）
- Node **24**（测试用到 `registerHooks` 和 `node:sqlite`）。
- 用 `npm ci`，**不要用** GPT 的 `install:ci`：那是 ChatGPT Sites 专用脚本，依赖 flock 和一个特定的 HOME 目录，在云端环境会失败。
- setup 阶段需要能访问 npm（workerd、esbuild 要下载平台二进制包）。安装完成后，代理运行时可以断网。
- 测试不需要网络，也不需要 Cloudflare，两边容器都能跑。

### 步骤 4：本机保留什么（沿用 v1）
北森原站取证仍然只在本机桌面 App 里做。云端代理遇到规格没写到的地方，开 `需取证` issue，不自己猜。
