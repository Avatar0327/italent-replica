# M0-02 技术栈评估（D-B）

> 版本：v0.1（2026-09-30）｜状态：**待拍板**（D-B）｜作用对象：**只影响复刻系统**，不涉及北森测试租户。
> 依据：DEC-006/007/019/024/045/047/048；`04_路线图/00`、`01`（8 条 R1 硬约束、B-01~B-15）；`02_业务建模/07`、`11`、`14`；`reference/gpt-legacy/`。

## 0. 一句话结论

**推荐方案 B2：TypeScript 全栈 + PostgreSQL，打包成普通容器部署**（不绑定 Cloudflare）。
理由三条：① 任职版本链与向后更新需要“先读、再判断、再写”的真事务和行级锁，D1 做不到；② 用户和客户在中国大陆，Cloudflare 的数据库与连接加速在大陆都没有节点，而容器 + Postgres 可以原样搬到阿里云 / 腾讯云；③ 两个云端代理的容器里都能离线跑 Postgres 测试（Claude 容器自带 PostgreSQL 16，Codex 可在 setup 阶段安装；另有纯 npm 包 PGlite）。
代价：GPT 的数据层代码（D1 原生 SQL + 810 处 SQLite 触发器）基本不能直接搬，只能借鉴思路和测试用例；需要自己管一台服务器（或买托管数据库）。

## 2. 关键外部事实（2026-09 核实）

### 2.1 Cloudflare D1
| 项 | 事实 | 来源 |
|---|---|---|
| 单库大小上限 | 付费 10 GB，免费 500 MB | [D1 Limits] |
| 每账号数据库数 | 付费 50,000（可申请提高），免费 10 | [D1 Limits] |
| 写吞吐 | **每个库串行处理查询**：平均 1 ms 的查询约 1,000 次/秒，100 ms 的查询只有 10 次/秒；排队满了返回 overloaded | [D1 Limits] |
| 单次调用查询数 | 付费每次 Worker 调用最多 1,000 条查询；单条 SQL ≤ 100 KB；**每条最多 100 个绑定参数**；单条最长 30 秒 | [D1 Limits] |
| 事务语义 | `batch()` 是一个事务，任一条失败整体回滚；**不支持 `BEGIN TRANSACTION` 交互式事务**（不能在事务中间读结果再决定写什么） | [D1 API]、[Drizzle #2463]、[dev.to 实测] |
| 行级锁 | 无（SQLite 整库单写者；D1 串行执行） | [D1 Limits] |
| 本地测试陷阱 | 本地 Miniflare 是普通 SQLite，**接受** `BEGIN`，本地通过、线上失败 | [dev.to 实测] |
| 读副本区域 | ENAM/WNAM/WEUR/EEUR/APAC/OC，**没有中国大陆** | [D1 读复制] |
| GPT 代码现状 | `lib/hris/r1-command.ts` 自设“单批 > 74 条语句即拒绝”；迁移与代码中 810 处 `CREATE TRIGGER`、186 处 `RAISE(ABORT…)`、163 处 `json_extract`（本地 grep 统计） | 本仓库 |

### 2.2 Postgres 托管与 Hyperdrive
| 项 | 事实 | 来源 |
|---|---|---|
| Hyperdrive | 让 Workers 连现有 Postgres/MySQL（含 Neon、AWS 等），维持连接池；**事务池模式**：连接归还时执行 `RESET`，`SET` 状态不保留；读查询可缓存且**写后不自动失效**；Worker 就近放置可把每次往返从 20–30 ms 降到 1–3 ms | [Hyperdrive]、[Hyperdrive 原理] |
| Neon | 支持 PG 14–18（2026-08 为 18.6）；亚洲只有新加坡、悉尼 | [Neon 版本]、[Neon 区域] |
| Supabase | 仅 AWS；亚洲有新加坡、东京、首尔 | [Supabase 区域] |
| 阿里云 RDS PostgreSQL | 2025-12-12 起支持 PG 18 | [阿里云 RDS PG] |
| 腾讯云 PostgreSQL | 已支持 PG 11–18，支持 9–18 跨版本升级 | [腾讯云 PG] |
| PG 18 时间约束 | 新增 `WITHOUT OVERLAPS` 主键 / `PERIOD` 外键；PG 16 起已可用 `daterange` + `EXCLUDE USING gist`（配 `btree_gist`）实现同等效果 | [PG18 时间约束] |

### 2.3 中国大陆访问
| 项 | 事实 | 来源 |
|---|---|---|
| Cloudflare 中国网络 | 由京东云运营，**需企业版合同 + 每个根域名的 ICP 备案**；可用产品含 Workers、KV，**未列 D1、Hyperdrive** | [CF 中国网络]、[CF 中国可用产品] |
| 普通账号 | `workers.dev` 曾遭 DNS 污染；社区普遍反映直连延迟高（估算：数百毫秒到 1 秒以上，未实测） | [腾讯云社区]、[V2EX] |
| 境外托管 PG | Neon / Supabase 最近在新加坡 / 东京，经跨境链路访问，存在速度与合规双重问题 | [21YunBox] |
| 国内云 | 内地区域对外提供网站服务需 ICP 备案；香港区域无需备案、从大陆访问延迟较低（估算：几十毫秒量级，未实测） | 常识，部署前需实测 |

## 3. 候选方案

- **A. 沿用 GPT 栈**：Cloudflare Workers + D1 + Drizzle + React/Vite（Vinext）。
- **B. TypeScript 全栈 + PostgreSQL**：Hono 后端 + React/Vite 前端 + Drizzle + Postgres。两种部署：
  - **B1**：Cloudflare Workers + Hyperdrive + Neon/Supabase（托管，零服务器）；
  - **B2**：普通 Docker 容器 + Postgres（自建或阿里云 / 腾讯云 RDS）。
- **C. Java（Spring Boot）+ PostgreSQL + React**：国内企业 SaaS 最常见的组合（北森本身也是 Java 系）。
- 附：D. Workers + Durable Objects（每租户一个 SQLite）—— 有交互式事务，但同样是 Cloudflare 专有、大陆不可用、生态更小，不单列。

## 4. 分维度对比

评分：✅ 满足且省心｜🟡 能做但有代价｜❌ 明显不适合

| 维度 | A：Workers + D1 | B1：Workers + Hyperdrive + PG | B2：容器 + PG（推荐） | C：Java + PG |
|---|---|---|---|---|
| **多租户隔离** | 🟡 可“一租户一库”（5 万库上限），隔离最彻底，但跨库迁移、统计、平台层（L1）查询要逐库执行；共享库则只能靠代码自觉 | ✅ PG 行级安全（RLS）兜底；注意事务池模式下必须在**每个事务内** `SET LOCAL app.tenant_id` | ✅ 同 B1，且可用长连接；应用角色不给 `BYPASSRLS`，漏写条件也查不到别家数据 | ✅ 同 B2 |
| **版本链 / 有效期查询** | 🟡 无区间类型、无排除约束；“区间不重叠”只能靠触发器（GPT 版即如此，810 个触发器） | ✅ `daterange` + `EXCLUDE USING gist` 在库里保证同一人同周期生效区间不重叠；“某日当时生效”用 `@>` 一条索引查询 | ✅ 同 B1 | ✅ 同 B1 |
| **事务与并发**（向后更新、定时生效批量） | ❌ 无交互式事务：向后更新必须先查、在 Worker 里算、再一次性 batch 写，中间可能被别的请求插入；无行锁；单库串行，批量生效会拖慢全部租户（共享库时）；100 个参数上限迫使拆批 | ✅ 真事务 + `SELECT … FOR UPDATE` / advisory lock 按员工加锁；但每次往返经 Hyperdrive，长事务不划算 | ✅ 真事务、行锁、`SKIP LOCKED`；批量生效可分批并发跑 | ✅ 同 B2 |
| **定时任务 / 队列** | 🟡 Cron Triggers + Queues 可用，但每次调用有查询数与时长上限，需自拆批 | 🟡 Workers 无常驻进程，不能跑 pg-boss；仍靠 Cron Triggers | ✅ pg-boss（队列 + cron，存在 PG 里，带重试、死信、时区）；与业务同库同事务 | ✅ Quartz / XXL-Job 等成熟方案 |
| **审计日志体量** | 🟡 单库 10 GB 上限；万人级租户几年字段级日志有触顶风险（估算），只能拆库 | ✅ 按月分区表，按租户保留期删分区外数据 | ✅ 同 B1 | ✅ 同 B1 |
| **表达式引擎**（DEC-024） | ✅ 纯 TS，与数据库无关 | ✅ 同 A | ✅ 同 A | ✅ Java 有现成表达式库，但前后端两套语言，前端预览需另写或调接口 |
| **离线测试 / 云端容器友好度** | ✅ `node:sqlite` 内存库，GPT 框架可直接用；❌ 但本地通过 ≠ 线上通过（事务差异） | 🟡 同 B2，另需模拟 Hyperdrive 的 RESET 行为 | ✅ 三层：PGlite（纯 npm、离线、每测试一个新库）+ 容器内真 PG 16（Claude 预装，Codex 装一次）测并发 + 可选 Docker | 🟡 JDK 两边都有；Maven/Gradle 首次下载依赖慢；Testcontainers 需 Docker，Codex 无 |
| **AI 代理熟悉度 / 可读性** | 🟡 D1 专有 API + SQLite 方言；AI 常写出本地能跑、线上不行的事务代码 | ✅ Postgres + Drizzle + React 是 AI 最熟悉的组合之一 | ✅ 同 B1，且无平台特殊约束 | ✅ Spring 也很熟，但代码量大、改一处牵动多层 |
| **复用 GPT 参考代码** | ✅ 最高：UI、测试框架、部分 SQL 可照搬（但 DEC-047 已定“只读参考”，且 5 处核心模型要重写） | 🟡 UI 组件、React 页面、业务规则、测试用例可借鉴；数据层重写 | 🟡 同 B1 | ❌ 只能借鉴业务规则与测试用例 |
| **国内部署与可移植性** | ❌ D1 在大陆无节点，中国网络需企业版 + ICP 且未列 D1；日后迁国内云等于重写数据层与运行时 | ❌ Hyperdrive 同样未进中国网络；Neon/Supabase 在境外 | ✅ 同一个 Docker 镜像可跑在香港、内地、任何云；阿里云 / 腾讯云均有托管 PG 18 | ✅ 同 B2，国内人才与运维经验最多 |
| **成本与单人运维** | ✅ 最省：Workers 付费计划起步低（估算每月 5 美元量级），零运维 | ✅ 较省：Neon/Supabase 有免费档 | 🟡 需一台服务器 + 数据库；估算每月数十到数百元人民币；要自己做备份、升级、监控（可用托管 RDS 减负） | 🟡 同 B2，内存占用更高 |
| **按租户恢复**（DEC-045） | ✅ 一租户一库时天然支持（D1 Time Travel） | 🟡 需自写“按 tenant_id 导出 / 导入”工具 | 🟡 同 B1 | 🟡 同 B1 |

**小结**：A 的优势（省钱、零运维、可复用、一租户一库）真实存在，但它在 N3（向后更新的事务）和“国内访问 / 迁国内云”两点上是**结构性缺陷**，不是多写代码能补的。B1 解决了事务问题，但没解决国内问题。C 能做，但一人双代理用两种语言，效率明显低于全 TS。**B2 是唯一在所有硬需求上都不踩雷的方案。**

## 5. 两套系统对照表（给产品负责人的通俗版）

> 只比较真正要拍板的两个：沿用 GPT 的 Cloudflare 路线（A） vs 推荐的“普通服务器 + Postgres”路线（B2）。

| 你关心的事 | 沿用 GPT 路线（A） | 推荐路线（B2） | 对你意味着什么 |
|---|---|---|---|
| 调动补录后，把后面的记录一起改对（向后更新） | 数据库不支持“边查边改”的整包操作，只能分步写，中途出错可能改一半 | 数据库原生支持，要么全改、要么全不改；同一员工同时两笔会自动排队 | 首版验收第 1 条的核心，B2 风险明显更低 |
| 员工的历史任职不会“时间重叠” | 靠几百个手写触发器守着，容易漏 | 数据库一条规则保证 | 少一类难查的数据错误 |
| 张三公司看不到李四公司的数据 | 可以一家一个库，最彻底；但做平台管理、统一升级很麻烦 | 所有公司一个库，数据库自己按公司过滤，代码漏写也查不到 | 两者都能做到，B2 管理更简单 |
| 国内客户打开速度 | Cloudflare 在大陆要企业版 + 备案，且数据库本身不进大陆 | 放香港或内地服务器，和国内普通网站一样 | 面向国内客户，B2 基本是必选 |
| 以后搬到阿里云 / 腾讯云 | 要重写数据层和运行方式 | 同一个镜像直接搬，数据库导出导入即可 | B2 不锁定供应商 |
| 每月花费 | 很低，基本不用管服务器 | 一台服务器 + 数据库，每月几十到几百元（估算） | B2 贵一些，多一点运维 |
| 你要亲自操心的事 | 几乎没有 | 买服务器、开数据库备份（用云厂商托管数据库可基本自动） | B2 多一次性的部署准备 |
| 能用多少 GPT 旧代码 | 界面和测试框架可大量参考 | 界面、业务规则、测试用例可参考；数据库部分重写 | 按 DEC-047 本来就是重写，差距不大 |
| 两个 AI 代理干活顺不顺 | 本地测过、上线失败的坑较多 | 云端容器自带数据库，测试结果和线上一致 | B2 返工更少 |

## 6. 推荐选型清单（方案 B2）

| 类别 | 选型 | 说明 |
|---|---|---|
| 语言 | TypeScript 5.x，`strict` | 前后端同一语言；表达式引擎可前后端共用 |
| 运行时 | **Node 24 LTS**（生产）；代码须兼容 Node 22（`engines: ">=22.12"`） | Claude 容器默认 22，Codex 可选 24；不再依赖 `node:sqlite` / `registerHooks` |
| 包管理器 | **pnpm 10**（workspace 单仓多包） | 两边镜像都自带；`--frozen-lockfile` 保证一致 |
| 仓库结构 | `apps/web`（前端）、`apps/api`（后端 + 定时任务进程）、`packages/domain`（纯业务规则：版本链、向后更新、流程匹配、权限展开，不碰数据库）、`packages/db`（表结构、迁移、仓储）、`packages/expr`（表达式引擎）、`packages/shared`（类型、文案资源） | 与 AGENTS.md“按目录分车道”一致；domain 纯函数最利于两个代理并行与测试 |
| 后端框架 | **Hono**（跑在 Node 上）+ zod 校验 | 轻量、AI 熟；同一套代码日后也能跑在 Workers 上，保留退路 |
| 前端 | React 19 + Vite + TanStack Router / Query + Tailwind 4 + shadcn/ui；react-hook-form + zod | 纯 SPA 管理后台（PC、无 SEO）；可借鉴 GPT 的 shadcn 组件与页面交互 |
| 数据库 | **PostgreSQL 18**（生产）；功能基线限定在 **PG 16 可用**的特性（`daterange`、`EXCLUDE`+`btree_gist`、RLS、分区、递归 CTE、JSONB） | 保证 Claude 容器的 PG 16、PGlite、阿里云 / 腾讯云都能跑；暂不用 PG 18 独有的 `WITHOUT OVERLAPS` |
| ORM / 迁移 | **Drizzle ORM** + drizzle-kit 生成迁移；RLS 策略、排除约束、分区等用**手写 SQL 迁移**；迁移只增不改 | 与 GPT 同 ORM，AI 熟；复杂 SQL 用 `sql` 模板 |
| 多租户 | 共享库共享表，每表 `tenant_id` + 复合主外键 `(tenant_id, id)`；RLS `USING (tenant_id = current_setting('app.tenant_id')::uuid)`；每个请求一个事务并 `SET LOCAL`；平台层（L1）用单独角色 | 满足硬规则 7；跨租户测试列入 M1 |
| 版本链 | `employment_record` 只追加；`valid_during daterange`；对“生效”状态加排除约束；按员工 `pg_advisory_xact_lock` 串行化向后更新 | 对应 R1-T05/T06 |
| 审计日志 | `audit_change` 按月分区、JSONB 存字段前后值；删除存完整快照；表只允许 INSERT（沿用 GPT 的“不可变”思路） | DEC-019、R1-T16 |
| 定时任务 | **pg-boss**：每日按租户时区（默认 Asia/Shanghai）派发“到期生效”任务；任务幂等、可重跑；测试中直接调用处理函数并注入时钟 | B-10、R1-T08 |
| 身份认证 | **Better Auth**（邮箱 + 密码、会话 Cookie、Drizzle 适配器）只管“你是谁”；租户成员、身份、权限全部放自己的领域表 | 不自造密码与会话轮子；一人可属多租户；SSO 后续可加 |
| 测试 | **Vitest**；三层：① `packages/domain` 纯单元测试；② 数据层与验收测试跑 **PGlite**（离线、每个测试文件一个新库）；③ 并发 / 锁 / RLS 角色测试跑容器内**真 PG 16**；E2E（Playwright）R1 后期再加 | 验收测试放 `tests/acceptance/AC-*.test.ts`；PGlite 单连接，所以③不可省 |
| Lint / 格式 | ESLint 9 + typescript-eslint + Prettier；限制单行 120 字符、单函数长度 | 防止重现 GPT 版“每行 280 字符”的问题 |
| CI | GitHub Actions：`pnpm install` → typecheck → lint → test（services 起 postgres:16） | 与云端容器同一套脚本 |
| 部署 | Docker 镜像（api + web 静态文件）+ Caddy 反代；演示期：**阿里云 / 腾讯云香港**轻量服务器 + 托管 PG 或同机 PG；商用前：备案后迁**内地区域**，数据库换 RDS PostgreSQL | 同一镜像，不改代码；备份用 RDS 自动备份 + 自写按租户导出工具（DEC-045 ③） |

## 7. 云端环境 setup 脚本草稿（Codex 与 Claude Code 通用）

放在仓库 `scripts/cloud-setup.sh`；两边的环境设置里只写一行 `bash scripts/cloud-setup.sh`。Codex 另设环境变量 `CODEX_ENV_NODE_VERSION=24`。

```bash
#!/usr/bin/env bash
# 云端开发容器初始化（Ubuntu 24.04；Claude Code 云端 / Codex universal 通用）
# 原则：只在 setup 阶段联网；之后测试全部离线。脚本可重复执行。
set -euo pipefail
cd "$(git rev-parse --show-toplevel 2>/dev/null || pwd)"
SUDO=""; [ "$(id -u)" -ne 0 ] && SUDO="sudo"

# 1) Node：要求 >=22.12；Codex 由 CODEX_ENV_NODE_VERSION=24 提供，Claude 默认 22 即可
node -e 'const [a,b]=process.versions.node.split(".").map(Number);process.exit(a>22||(a===22&&b>=12)?0:1)' \
  || { echo "Node 版本过低：$(node -v)"; exit 1; }

# 2) pnpm：两边镜像已带；按 package.json 的 packageManager 字段锁定版本
corepack enable >/dev/null 2>&1 || true
pnpm --version >/dev/null 2>&1 || npm i -g pnpm@10

# 3) PostgreSQL 16：Claude 已预装；Codex 未装则安装（Ubuntu 24.04 官方源即 16）
if ! command -v pg_ctlcluster >/dev/null 2>&1; then
  $SUDO apt-get update -qq
  DEBIAN_FRONTEND=noninteractive $SUDO apt-get install -y -qq postgresql postgresql-contrib
fi

# 4) 依赖（PGlite 的 WASM 随 npm 包下载，之后离线可用）
pnpm install --frozen-lockfile

# 5) 预热：编译检查一次，确保缓存快照里已有构建产物
pnpm -r run --if-present build:types

echo "setup 完成。测试前运行：bash scripts/dev-db.sh（启动本地 PG，幂等）"
```

配套 `scripts/dev-db.sh`（每次会话由 `pnpm test:pg` 自动调用，因为 Claude 的缓存不保留运行中的进程）：

```bash
#!/usr/bin/env bash
set -euo pipefail
SUDO=""; [ "$(id -u)" -ne 0 ] && SUDO="sudo"
$SUDO service postgresql start >/dev/null 2>&1 || $SUDO pg_ctlcluster 16 main start
until pg_isready -q -h localhost; do sleep 0.5; done
$SUDO -u postgres psql -qtAc "SELECT 1 FROM pg_roles WHERE rolname='app'" | grep -q 1 \
  || $SUDO -u postgres psql -qc "CREATE ROLE app LOGIN PASSWORD 'app' NOSUPERUSER NOBYPASSRLS; CREATE ROLE app_owner LOGIN PASSWORD 'app_owner' CREATEDB;"
$SUDO -u postgres psql -qtAc "SELECT 1 FROM pg_database WHERE datname='italent_test'" | grep -q 1 \
  || $SUDO -u postgres createdb -O app_owner italent_test
$SUDO -u postgres psql -q -d italent_test -c "CREATE EXTENSION IF NOT EXISTS btree_gist;"
echo "DATABASE_URL=postgres://app:app@localhost:5432/italent_test"
```

> 说明：以上账号口令仅用于容器内一次性测试库（写入 `.env.example` 的只有键名）；生产口令走平台 Secret。`pnpm test` 只跑 PGlite 与纯单元测试，**无需任何数据库服务**；`pnpm test:pg` 才需要本地 PG。Codex 若未来改为 Docker 可用，也可改用 `docker compose`，但不作为前提。

## 8. 风险与待确认

| # | 风险 / 待确认 | 应对 |
|---|---|---|
| R-1 | PGlite 单连接、与真 PG 小版本可能有差异 | 并发、锁、RLS 角色相关测试强制在真 PG 上跑；CI 以真 PG 结果为准 |
| R-2 | RLS 写错会导致“全看不到”或“漏过滤” | M1 先写跨租户验收测试（AC-TEN-01~03），每张新表的 PR 必须带 RLS 策略与测试；CI 检查“无 RLS 的业务表” |
| R-3 | 单人运维（备份、升级、监控） | 优先用托管 RDS；自写按租户导出 / 恢复工具并纳入 R1-T00/T17 验收 |
| R-4 | 国内延迟与备案未实测 | 部署阶段在香港与内地各开按量实例实测后定；商用前完成 ICP 备案 |
| R-5 | 放弃 D1 后 GPT 数据层与测试框架不能直接复用 | 按 AGENTS.md §6 只借鉴思路；把 GPT 的有效测试场景改写为 AC 测试 |
| R-6 | Better Auth 的租户 / 组织插件与本项目权限模型不一致 | 只用其认证与会话核心，不用组织插件 |
| R-7 | Claude 容器默认 Node 22，Codex 用 24，行为差异 | 代码限定在 Node 22 可用的 API；CI 同时跑 22 与 24 |

**需要你拍板的事**（均只影响复刻系统）：
1. **D-B 技术栈**：选 B2（推荐）/ A / B1 / C。
2. **演示期部署位置**：香港区域（推荐，免备案、先跑起来） / 直接内地（需先备案） / 暂不部署、只在云端容器里验收。
3. **数据库形态**：云厂商托管 PostgreSQL（推荐，备份省心，贵一些） / 同机自建（便宜，备份自己管）。
