# 部署运行手册：平台运营与按租户备份恢复（R1-T17）

> 作用对象：**只影响复刻系统**（不涉及北森测试租户）。依据：DEC-006、DEC-056、DEC-061（修订 DEC-045③）、AGENTS.md §10「恢复」、REQ-PLT-001。
> 状态：R1-T17 提供应用侧工具与演练测试；本手册中的 RPO / RTO / 保留期 / 加密存储属**部署阶段验收**（AC-TEN-06 时限部分），须在部署环境就绪后按 §5 演练并记录结果。

## 1. 角色与边界

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| 平台运营身份（`platform_operators`） | 调 `/api/platform/*`：开通租户、停用 / 重新启用、发放许可；执行备份恢复命令行 | 不因此成为任何租户的成员，不能访问 `/api/tenant/*` |
| 租户管理员 | 租户内企业设置（含查看许可余额与使用明细） | 不能调用平台接口；不能自助恢复（REQ-PLT-001 R6） |

- 平台接口每次请求都重新校验“账号有效 + 平台运营身份有效”，撤销立即生效。
- 所有平台命令写 `platform_audit_events`；与租户相关的（开通、状态、成员关系、许可、备份恢复）同时写该租户的 `audit_events`，平台审计用 `subject_tenant_id` 标出所涉租户。按租户恢复会把租户审计带回备份时点，平台审计不受影响。

## 2. 首次部署：登记首位平台运营

```bash
pnpm build
# 现网库的迁移角色连接（与 pnpm db:migrate 相同）
export DATABASE_URL=...           # 只放 Secret 管理
node apps/api/dist/ops/platform-cli.js grant-operator --email ops@example.com
```

账号须已存在（全局账号由平台接口 `POST /api/platform/users` 或初始化脚本建立）。首位平台运营以“系统”记账（操作人为空），之后的平台运营由平台方经同一命令登记或撤销。

### 2.1 F-016 升级迁移角色（DEC-190）

`0054_contract_calibration.sql` 是结构迁移；`0055_contract_inflight_quarantine.sql` 扫描全租户重复在途合同，写隔离待办、审计与 outbox。相关表启用了 **FORCE ROW LEVEL SECURITY**，普通表属主也会受租户策略限制；未设置租户上下文时不能以“执行成功”判断扫描完成。

部署此次升级时，`pnpm db:migrate` 必须使用**专用升级角色**：具有所需 DDL / 读写权限且带 `BYPASSRLS`，或使用受控超级用户连接。在执行前用该连接核对：

```sql
SELECT current_user, rolsuper, rolbypassrls
FROM pg_roles WHERE rolname = current_user;
```

`rolsuper` 与 `rolbypassrls` 至少一项必须为 true，否则停止此次升级。升级完成后核对各租户冲突组均生成 `CONTRACT_IN_FLIGHT_QUARANTINED` 待办，并由有权 HR 撤销多余申请后重新提交；不自动选择获胜者。升级凭据仅供部署作业使用，不授予应用运行角色。此角色要求仅用于全租户升级迁移；§5 的按租户备份恢复命令仍必须使用非超级用户、无 BYPASSRLS 的表属主连接，两者凭据分开配置。

## 3. 租户生命周期（平台接口）

写请求一律带 `Idempotency-Key`（同键同内容重放，异内容 409）；改已有对象带 `If-Match: "<revision>"`（不一致 409，刷新后显式重提）。

| 操作 | 接口 | 说明 |
|---|---|---|
| 开通 | `POST /api/platform/tenants` | 一个事务完成：建租户（`timezone` 缺省 `Asia/Shanghai`，DEC-056）→ 首位租户管理员与异常管理员的成员关系 → 标准业务身份（DEC-121 预置看全部）→ 首位租户管理员（8 类管理员身份可授、标准身份可授，并授予“标准版系统管理员（组织员工）”，占 1 个核心人力名额）→ 可选的许可发放 → 标准开关（允许直接调动 = 开，DEC-051；同一部门下职位允许重复 = 关，DEC-062a）→ 全部预置流程配置异常管理员后发布（DEC-018）。`exceptionAdminUserId` 必填，缺失即 400，不建租户。 |
| 查看 | `GET /api/platform/tenants/:id` | 返回租户与 revision（ETag） |
| 停用 / 重新启用 | `POST /api/platform/tenants/:id/status`，体 `{"status":"suspended"|"active"}` | 停用后租户内所有请求 403 `TENANT_UNAVAILABLE`，数据保留；不影响其他租户。恢复隔离中（restoring）的租户不能从这里开放，只能经 §5 的 `open`。 |
| 许可发放 / 调整 | `PUT /api/platform/tenants/:id/licenses/:licenseType`，体 `{"quota":N}` | 按产品线（许可类型，如 `pa_user`、`core_hr`、`digital_talent`）。返回发放后的余额，口径与租户侧“许可管理 / 余额”一致：余额 = 总数 − 仍在用的名额（DEC-141），余额不足照常授权并标出超额（DEC-143），由平台补发。 |
| 余额 | `GET /api/platform/tenants/:id/licenses` | 与租户侧余额接口同一数据 |

## 4. 备份策略与目标值（DEC-061）

| 指标 | 目标 | 怎么达成（部署阶段落实） |
|---|---|---|
| RPO ≤ 1h | 任一租户可恢复到 1 小时内的时间点 | ① 托管 PostgreSQL 开启连续归档（WAL）与时间点恢复，覆盖整库灾难；② 每小时对每个租户执行一次 `export`（逻辑备份，§5.1），覆盖“只恢复一个租户、不动其他租户”的场景 |
| RTO ≤ 4h | 从开始恢复到开放访问不超过 4 小时 | 隔离环境（空库，预先迁移到当前版本）常备；`restore` → 核对 → `open` 三步均为命令行，报告里有 `startedAt` / `verifiedAt` / `openedAt`，演练时记录实际耗时 |
| 保留 30 天 | 备份文件与 WAL 归档保留 30 天 | 对象存储生命周期规则按 30 天过期；过期删除走存储侧，不在应用内 |
| 传输与存储加密 | 备份文件不出现明文 | `export` 输出即 AES-256-GCM 密文（`BACKUP_ENCRYPTION_KEY`，32 字节，只放 Secret 管理）；对象存储另开服务端加密；传输走 TLS |

成本不可行时由用户决定降档（备选 RPO 24h / RTO 8h，DEC-061）。

## 5. 按租户恢复（演练与实战同一流程）

恢复单元 = 租户数据的一致快照 + 附件清单与哈希 + 代码 / 迁移版本（AGENTS.md §10）。

### 5.1 导出

```bash
export DATABASE_URL=...  BACKUP_ENCRYPTION_KEY=...  APP_VERSION=<镜像标签>
node apps/api/dist/ops/platform-cli.js export --tenant <租户ID> --out <租户ID>-<时间>.itb
```

- 只读、可重复读事务：所有表同一快照；读到任何其他租户的行即中止。
- 清单含：快照时点（UTC）、代码版本、迁移版本（条数 + 最后一条哈希）、每表行数、附件清单（ID、员工、SHA-256、大小、状态）、整体校验和。
- 平台审计记 `tenant.backup.export`。

### 5.2 恢复到隔离环境

**运行身份（硬性要求）**：导出、恢复、开放一律用迁移角色（表属主）连接——**非超级用户、不带 BYPASSRLS**，受 FORCE RLS 约束。命令行启动时检查，否则拒绝执行。读写时都先设 `app.tenant_id`，租户隔离由数据库兜底；行级校验（下文）不依赖这一点。

1. 新建**空库**（没有任何租户），用**备份清单里的代码版本**执行 `pnpm db:migrate`（迁移版本必须完全一致，否则拒绝恢复）。
2. 从对象存储按附件清单计算各附件内容的 SHA-256，存成 `{ "附件ID": "sha256" }` 的 JSON（接入对象存储模块后改为直接读取）。
3. 执行（`DATABASE_URL` 指向**现网**，对账以现网为准）：

```bash
node apps/api/dist/ops/platform-cli.js restore --in <文件> --target-url <隔离库连接> --hashes <哈希JSON> \
  --command-id restore-<租户ID>-<日期>
```

restore 依次做：
- **写入前校验**（任何一项不过即拒绝，隔离库不发生任何写入）：格式、迁移版本、校验和；隔离库**没有任何租户**；备份里只有这一个租户，每一行的 `tenant_id` 都属于它；各表行数与清单一致。
- **导入**（一个事务，含隔离校验、平台审计与命令台账）：租户状态一律置为 `restoring`（除平台方外一律拒绝访问）；系统预置**整表按备份值写回**（含没有租户覆盖的键，覆盖隔离库迁移带来的默认值）；在途事件 / 通知由 `pending` 改记 `unknown`（不补发消息）；审批数据按快照原样恢复，不推进、不重放已处理节点；导入后把所有序列推进到已导入最大值之后（如任职状态事件序号，同日排序依赖它）；原样加回全部外键，对全部行重新校验引用完整性；导入后隔离校验（他租户行 = 0、租户数 = 1、无清单外账号、行数一致）不过即整体回滚。
- **附件核对**：缺失或哈希不符都判不通过（待清理的附件不要求存在）。
- **授权对账**（以现网**此刻**的有效授权为准）：把现网该租户的授权子图——成员关系、身份及其对象 / 字段 / 按钮权限、授权、企业管理员、许可、管理单元、用户范围、身份数据权限（含 DEC-121 看全部）、数据权限策略、动态授权、用户与人员绑定——镜像到隔离库；全局账号按现网同步状态（停用的不复活）。现网没有的删、不同的改成现网的值；现网有而隔离库没有的补入，引用的业务对象在备份时点还不存在的跳过（只会更窄）。删不掉（被业务数据引用）的列入问题。
- **审批对账**（DEC-098 / 123）：对账后不可用的账号若仍是可用流程的异常管理员，改指现网该流程当前的异常管理员；其名下的在途异常待办按停用时的既有路径改派（以现网指定的替代人为准，否则租户管理员，DEC-091 回避）。**恢复期间只改派、不结算**：接手人已在同一会签节点占席（改派会合并席位并重新结算、推进流转甚至批准业务）的，不自动处理，列入问题。做不到的都列入问题。
- **授权对账的执行顺序**：删、改、补反复尝试直到不再有进展（如撤销后重授同一身份：许可名额改指新授权须等新授权先补入），最后仍做不到的删 / 改列入问题。
- 报告 `ok = true`（隔离、附件、对账均无问题）才可开放；结论与对账结果在同一事务记入隔离库（平台审计 `tenant.restore.reconcile` / `tenant.restore.verify`、租户审计 `tenant.restore.reconcile`）。

### 5.3 开放访问

```bash
node apps/api/dist/ops/platform-cli.js open --in <文件> --target-url <隔离库连接> --command-id open-<租户ID>-<日期>
```

只有隔离库里最近一次校验通过、租户仍处于 `restoring` 时才开放；**开放前重新读取现网并再次做授权与审批对账**（restore 之后、open 之前的撤权同样生效），再做一次隔离校验，任一有问题即拒绝开放。对账、状态变更、审计与命令台账同一事务提交。之后把该租户的流量切到隔离库（切换方式随部署架构定，见 §6）。建议在 open 前后暂停现网该租户（`POST /api/platform/tenants/:id/status`），切换期间不再产生新的授权变化。

### 5.3.1 结果未知时的重试

restore 与 open 的每个阶段（导入、校验、开放）都在隔离库的平台命令台账登记，键为“阶段 + 命令 ID 的 SHA-256”（定长，不截断）。命令 ID 须为 1～100 位字母、数字与 `: _ -`，否则拒绝执行。网络中断等结果未知时，**用同一 `--command-id` 重跑同一命令**：已完成的阶段直接返回首次结果，不重复执行；未完成的阶段整体回滚过，可安全重做。不同内容用同一命令 ID 会被拒绝（409）。

### 5.3.2 校验未通过后重新校验

restore 报告 `ok = false`（如附件缺失、对账有待人工处理的事项）时，租户保持 `restoring`。处理掉问题（补齐附件、在现网完成交接等）后，**换一个新的 `--command-id` 再执行 restore**：隔离库已有同一份备份（按校验和认定）的导入、租户仍在恢复隔离中时，不重复导入，直接重新附件核对、对账与校验。同一命令 ID 重跑仍返回首次（失败）结果；已开放的租户不能再这样重新校验。

### 5.4 演练记录（部署阶段验收 AC-TEN-06）

每次演练记录：备份时点、故障假设时点（RPO = 两者之差）、`startedAt` → `openedAt`（RTO）、报告中的隔离校验与对账结果、B 租户在演练期间的可用性（应不受影响）。应用侧演练已由 `tests/acceptance/AC-TEN-06.test.ts` 覆盖（PGlite 与真 PostgreSQL 16 均跑）。

## 6. 审计日志（R1-T16）

- **请求来源**：数据变更日志的 IP 取 `X-Forwarded-For` 第一跳（其次 `X-Real-IP`、套接字地址）。部署时反向代理必须**覆盖**（而不是追加）客户端传来的 `X-Forwarded-For`，否则 IP 可被伪造。来源页面、来源动作、前端版本由前端随请求带 `X-Source-Page`、`X-Source-Page-Type`、`X-Source-Action`（中文按 URL 编码）、`X-Client-Version`；TraceID 取 `X-Trace-Id` 或 W3C `traceparent`，都没有时服务端生成并回写响应头 `X-Trace-Id`。
- **查询可见性**：审计查询按查看人当前的数据范围与字段权限逐条裁剪（DEC-197），每种对象类型复用其业务查看规则；新增写审计的对象类型须在 `apps/api/src/audit/visibility.ts` 登记规则（或在 `AUDIT_CONFIG_OBJECT_TYPES` 登记为配置对象，DEC-203），未登记的不返回；配置对象若有字段权限定义，须同时登记其字段权限对象（配置日志的字段权限照常裁剪）。
- **保留期清理**：`server.ts` 默认每天运行一次（`AUDIT_RETENTION_INTERVAL_MS` 调整，不小于 60000；`AUDIT_RETENTION_SCHEDULER=off` 关闭本进程调度）。清理经平台路径调用定义者函数 `purge_expired_audit`（只授予 `app_platform`，业务角色不能调用；保留月数由函数读取租户配置 `audit.retention.retainMonths`，调用方不能缩短），到期日志整条删除（DEC-198），每批每表最多 5000 行、每批一个事务、锁等待 5 秒超时，每批在同一事务里留一条「日志清理」对象操作日志；同一时间槽多实例只登记一次结果。数据范围「创建人」所需的最小元数据（对象、创建人、创建时间）另存于 `audit_object_creators`，不随清理删除。
- **失败命令兜底通道**：租户命令的失败审计写不进数据库时，以一行 JSON（`type = audit.command_failure.fallback`，带与数据库记录相同的事件编号 `id`）写到进程标准错误；平台命令失败写 `platform_command_failures`（只有平台运营经 `GET /api/platform/command-failures` 可读），写不进去时同样落 `type = audit.platform_command_failure.fallback`。日志采集须保留这两类行。
- **失败的导入任务**：导入整批失败（含格式、字段权限、范围校验失败）时在独立事务里写任务级日志：条数、结果、错误报告（行号、错误码、原因与出错字段编码），不存输入值；请求里识别不出导入行的只留失败命令审计。平台命令进入执行器之前的失败（请求体、If-Match、参数校验）同样写平台失败通道。
- **升级（迁移 0057 / 0058，须停写并在维护窗口执行）**：迁移器把待执行的迁移放在**同一个事务**里：0057 对 `audit_events` 执行 `ALTER TABLE ... ADD COLUMN` 与建索引，取得 **ACCESS EXCLUSIVE** 锁；0058 临时卸下只追加触发器、按租户一次 UPDATE 回填历史行的操作类型、字段差异与归属，并回填创建人元数据。该锁一直持有到整个迁移事务提交（即回填结束），期间 `audit_events` 的**读写都不可用**——审计查询会阻塞，所有写审计的业务写入也会阻塞，因此须停写执行，并预留足够的维护窗口。

  下表是 PostgreSQL 16 上单租户、合成数据（4 类对象、每行少量字段）的一次实测，**只作为容量估算参考**；实际耗时与 WAL 取决于行宽、字段差异的复杂度、租户数、磁盘与 WAL 归档 / 复制带宽，不承诺按固定比例完成：

  | 历史审计行 | 迁移耗时 | WAL | 迁移后表大小 |
  |---|---|---|---|
  | 20 万 | 约 40 秒 | 约 0.3 GB | 约 0.32 GB |
  | 100 万 | 约 3.7 分钟 | 约 2.7 GB | 约 1.6 GB |

  建议先在生产数据的副本上演练一次，按实测结果确定窗口与归档带宽。回填会产生同等数量的旧行版本，升级后执行一次 `VACUUM (ANALYZE) audit_events`。

## 6.1 360 通用网址作答凭据（F-076 PR-1）

- **密钥配置（只放 Secret 管理，值不进仓库，键名见 `.env.example`）**：`SURVEY360_CREDENTIAL_KEYS`（`版本:base64密钥`，至多 4 个、每个 32 字节）、`SURVEY360_CREDENTIAL_KEY_CURRENT`、`SURVEY360_CREDENTIAL_KEYS_RETIRED` / `_COMPROMISED`、`SURVEY360_THROTTLE_KEY`、`SURVEY360_OUTBOX_KEYS` / `SURVEY360_OUTBOX_KEY_CURRENT`。**生产（`NODE_ENV` 不是 development / test）缺失或长度、版本关系不合法时进程拒绝启动**；邀请 outbox 里的链接令牌（及序列号、密码）无论开关是否打开都加密保存，所以 outbox 密钥是必配项。密钥丢失 = 未发送的邀请无法解封，须重发邮件邀请。
- **开关**：`SURVEY360_PORTAL_CREDENTIALS=on` 才让作答链接进入凭据待发放；缺省关闭。打开前确认本进程或其他实例运行着凭据维护任务（`SURVEY360_CREDENTIAL_MAINTENANCE_SCHEDULER` 不为 `off`，间隔 `SURVEY360_CREDENTIAL_MAINTENANCE_INTERVAL_MS`，缺省 60000），否则会出现无人发放的待发邀请。PR-2a 合并前没有登录入口，凭据只是先发出去。
- **轮换**：配置里加入新版本并设为 CURRENT，运行 `node apps/api/dist/ops/survey360-credentials.js rotate --to <版本>`（每租户写一条 `key_rotated`）；旧版本保留到它发放的凭据所在活动都已停用或 90 天（以先到者为准），可用 `stats --version <旧版本>` 查看仍以旧版本存摘要的有效凭据数。
- **计划退役**：把旧版本从 KEYS 移到 RETIRED，运行 `retire --version <旧版本>`；输出的“手动重发清单”（租户 / 活动 / 链接行 ID 与人数，不含凭据）交各租户管理员手动“重发邮件邀请”，不自动群发。
- **泄露处置**：新版本设为 CURRENT，把泄露版本同时放进 RETIRED 与 COMPROMISED（部署即生效，不等批处理），再运行 `retire --version <版本> --compromised`；中断后用 `--resume <运行ID>` 续跑。连接角色与 `platform-cli` 相同（迁移角色，非超级用户、不带 BYPASSRLS）。

## 6.2 计算公式字段引用按 ID 绑定（F-082，契约 `docs/08_设计/F-082_公式字段引用ID绑定_契约.md` §6.5，DEC-381 / 383 / 386）

作用对象：**复刻系统**。总开关 `formulaIdBinding`（默认值只在 `apps/api/src/modules/talent-review/formula-binding-switch.ts` 的常量 `FORMULA_ID_BINDING_DEFAULT` 定义，F082-5 起为 `true`）打开后，盘点计算规则的公式存“规范文本（字段 ID 句柄）+ 引用表”，新响应形状、新格式审计、改绑路由都随之生效。**这一步不可逆**：开关打开后只前进修复（DEC-383），不提供把规范文本转回名称文本的工具，也不做保留数据的回退。

**连接标识**：API、全部后台入口（定时任务所在的 API 进程、`platform-cli`、`survey360-credentials`）与迁移命令 `pnpm db:migrate` 的连接 `application_name` 都设为 `italent-api:<APP_VERSION>`（环境变量 `APP_VERSION`，缺省 `dev`）；以后新增的连接入口也必须设置（`AC-TR-F082-23-appname` 源码扫描会拦住漏设的）。检查脚本据此数目标库上的应用连接，并且把**应用运行时数据库角色**名下未带这个前缀的连接（例如启用前版本的旧默认连接名 `postgres.js`）也一并计数、报告——所以 `pre-enable` / `post-restore` 必须用 `--app-role=<应用运行时数据库角色>`（或环境变量 `APP_DB_ROLE`）告诉脚本是哪个角色，缺省则该项失败。

**检查账号的权限（先判定、后计数：看不到 / 认不出不等于没有）**：检查脚本先确认账号“看得全”，不满足就判该项失败、不出“没有”的结论。按阶段：

| 阶段 | 账号须具备 | 不具备时 |
|---|---|---|
| `pre-enable`、`post-restore` 的连接检查 | 超级用户，或拥有内建角色 `pg_read_all_stats` 的权限（`GRANT pg_read_all_stats TO <检查账号>`；须按继承生效，即检查账号不是 `NOINHERIT`） | 其他角色会话的 `backend_type`、`state` 等列是 `NULL`，应用连接会被漏数——脚本直接判“目标库上没有应用连接”失败；另外逐行兜底，任何会话信息不可见同样判失败 |
| `post-restore` 的数据检查（`bound` 行、新格式审计、含句柄台账） | 超级用户或 `BYPASSRLS`，并能 `SELECT` 这三张表 | 受行级安全约束时看到的“0 行”不可信——三项数据检查都判失败、不执行计数（`platform-cli` 用的迁移角色受 FORCE RLS 约束，属于这种账号） |
| 迁移检查（三个阶段） | 能读 `drizzle.__drizzle_migrations`（`drizzle` 模式的 `USAGE` 与该表的 `SELECT`） | 读不了即报错、该项失败 |
| `deploy` | 只需迁移检查的读权限 | 同上 |

推荐做法：建一个专用的只读检查账号（例如 `italent_deploy_check`：`LOGIN`、保持默认的 `INHERIT`、`BYPASSRLS`，再 `GRANT pg_read_all_stats` 与上述表的 `SELECT`），**不要用应用运行时角色当检查账号**（应用角色名下的连接本身就要被计数）。

### 6.2.1 首次打开开关（部署前置条件，不做运行时互斥）

1. **停止全部旧实例**：所有运行开关关闭代码或 F-082 之前代码的 API 进程，以及定时任务、平台命令、`platform-cli`、`survey360-credentials` 等后台写入者。先摘流量、排空在途请求，再停进程。
2. **运行只读检查脚本**（`DATABASE_URL` 指向目标库；账号权限见上表——须是超级用户或拥有 `pg_read_all_stats`，否则连接检查判失败）：

   ```bash
   DATABASE_URL=... node scripts/check-deploy-target.mjs --phase=pre-enable --app-role=<应用运行时数据库角色>
   ```

   检查项：目标库上没有应用连接（`italent-api:*` 前缀的，以及应用角色名下未带前缀的）；已应用迁移与待部署代码一致（条数与最后一条的时间戳）；待部署代码的开关默认值为 `true`。任一项不满足 → 退出码非零，**部署中止**。
3. **只启动新实例**（开关默认打开的版本）。启动时进程内的能力检查（`items` 投影、响应 / 重放投影、`calcRuleSources` 审计裁剪）任一未登记即拒绝启动。
4. **立即对每个租户改绑一次**（改绑路由只在开关打开时注册；平台运营身份；一个租户一个事务，可重复执行）：

   ```bash
   node apps/api/dist/ops/platform-cli.js rebind-calc-formulas --tenant <租户ID> --command-id rebind-<租户ID>-<日期>
   ```

   或直接调用 `POST /api/platform/tenants/<租户ID>/talent-review/calc-formulas/rebind`（带 `Idempotency-Key`，请求体 `{}`，可选 `{"retryUnresolved": true}`）。报告 `{ rules, bound, unresolved: [{ ruleId, targetFieldId, reason }] }` 只有 ID 与原因码；**`unresolved > 0` 的租户通知其管理员**在页面上修正公式并重新保存（保存成功即变为 bound）。管理员修完后可用 `--retry-unresolved` 复查。改绑期间被引用的字段由引用表与候选引用保护，不会被删除。
5. 改绑中途失败（锁等待超时、异常）整个租户回滚、不留任何半成品，换新的命令 ID 重试即可。

### 6.2.2 之后的每次部署

只能部署开关默认打开的版本；旧实例不得重新加入（包括自动扩容、回滚流水线、旧镜像重启）。每次部署前运行：

```bash
DATABASE_URL=... node scripts/check-deploy-target.mjs --phase=deploy
```

检查项：待部署代码的开关默认值为 `true`；迁移序号不得低于库里已应用的序号。开关打开之后，F-082 的不同版本之间可以照常滚动部署（各版本都按新格式读写），所以这一阶段不检查应用连接。

### 6.2.3 开发期确需回退时（复刻系统目前没有生产部署和真实租户）

1. **停写**：停止全部 API 与后台进程，排空请求。
2. **恢复 / 重建**，二选一：恢复到**开关打开前**的一致备份点（DEC-061 的恢复单元须包含**全部表**——不能只恢复当前租户或公式相关表——以及对应的代码 / 迁移版本；该备份点里没有 `bound` 行、新格式审计与新格式台账）；或重建环境（重新开通租户、导入合成数据）。
3. **校验**（账号权限见上表：连接检查要 `pg_read_all_stats`，数据检查要能绕过行级安全；`platform-cli` 用的迁移角色受 FORCE RLS 约束，数据检查会全部判失败）：

   ```bash
   DATABASE_URL=... node scripts/check-deploy-target.mjs --phase=post-restore --app-role=<应用运行时数据库角色>
   ```

   检查项：没有应用连接；迁移与要启动的代码一致；库里没有 `bound` 行；没有计算规则的新格式审计（快照含 `formulaBinding`）；没有含句柄 `@{tr-field:` 的命令台账结果。任一项不满足就**不启动服务**，回到第 2 步。
4. **再启动**：用备份点对应版本的代码启动。

**禁止**：开关打开过的库，不经上述第 2、3 步直接用开关关闭的代码或 F-082 之前的代码运行。这是部署手册的禁止条件，由检查脚本的各阶段把关；代码里不做运行时拦截（DEC-386）。复刻系统将来有生产部署时，再评估回退方案（DEC-383）；F-082 完成之前如果出现了生产部署或真实租户，需要重新评估是否改回分阶段兼容（契约 §15.3）。

## 7. 已知限制（待部署阶段定）

- **360 报告 PDF / 报表 PNG 下载用项目内置的中文字体（F-080，DEC-375①）**：文件在服务端用 sharp 栅格化，字体是随代码发布的思源黑体（Noto Sans SC）常用字子集（`apps/api/assets/fonts`，SIL OFL 1.1，约 4.4 MB，来源与重新生成方法见该目录 README 与 `scripts/fonts/build-cjk-subset.py`），**不再依赖服务器安装的字体，运行镜像不需要装 fontconfig / 中文字体**。部署包必须带上整个 `apps/api/assets/`（含 `raster-worker.mjs` 与字体），进程启动时校验两个字体文件的 SHA-256，缺失或被改动即拒绝启动（`EXPORT_FONT_MISSING` / `EXPORT_FONT_CORRUPT`），运行期不再有“缺字体 503”。字表是 GB 2312（6763 个常用汉字），生僻字（部分人名用字）会缺字形。栅格化在子进程里执行（Node 同一可执行文件），超时（默认 60 秒）即终止子进程并释放名额。PDF 页内是位图（文字不可选，文本层见 F-083），清单 > 300 行或报告 > 80 页返回 413（`EXPORT_TOO_LARGE`，提示“数据过多，请分批导出”）。
- 恢复后切回共享现网库（而不是让该租户继续使用隔离库）需要按租户替换数据，涉及只追加审计表的处理，尚未实现；部署方案定下前，恢复后的租户以隔离库对外服务。
- 附件内容的对象存储尚未接入，附件核对暂以运维提供的哈希表为准。
- 命令行运行身份为迁移角色（表属主）：恢复时需要在隔离库内临时卸下外键与业务触发器，现网运行时角色无此权限，也不应授予。超级用户与 BYPASSRLS 角色被命令行拒绝（测试环境中的 PGlite / CI postgres 为超级用户，行级校验保证同样拒绝他租户行）。
- 授权对账镜像的是授权子图；业务数据（组织、任职、审批实例等）停在备份时点，这是恢复的本义。
