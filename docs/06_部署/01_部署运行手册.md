# 部署运行手册：平台运营与按租户备份恢复（R1-T17）

> 作用对象：**只影响复刻系统**（不涉及北森测试租户）。依据：DEC-006、DEC-056、DEC-061（修订 DEC-045③）、AGENTS.md §10「恢复」、REQ-PLT-001。
> 状态：R1-T17 提供应用侧工具与演练测试；本手册中的 RPO / RTO / 保留期 / 加密存储属**部署阶段验收**（AC-TEN-06 时限部分），须在部署环境就绪后按 §5 演练并记录结果。

## 1. 角色与边界

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| 平台运营身份（`platform_operators`） | 调 `/api/platform/*`：开通租户、停用 / 重新启用、发放许可；执行备份恢复命令行 | 不因此成为任何租户的成员，不能访问 `/api/tenant/*` |
| 租户管理员 | 租户内企业设置（含查看许可余额与使用明细） | 不能调用平台接口；不能自助恢复（REQ-PLT-001 R6） |

- 平台接口每次请求都重新校验“账号有效 + 平台运营身份有效”，撤销立即生效。
- 所有平台命令写 `platform_audit_events`；与租户相关的（开通、状态、成员关系、许可、备份恢复）同时写该租户的 `audit_events`，平台审计用 `subject_tenant_id` 标出所涉租户。按租户恢复会把租户审计带回备份时点，平台审计不受影响。

## 2. 首次部署：登记首位平台运营

```bash
pnpm build
# 现网库的迁移角色连接（与 pnpm db:migrate 相同）
export DATABASE_URL=...           # 只放 Secret 管理
node apps/api/dist/ops/platform-cli.js grant-operator --email ops@example.com
```

账号须已存在（全局账号由平台接口 `POST /api/platform/users` 或初始化脚本建立）。首位平台运营以“系统”记账（操作人为空），之后的平台运营由平台方经同一命令登记或撤销。

## 3. 租户生命周期（平台接口）

写请求一律带 `Idempotency-Key`（同键同内容重放，异内容 409）；改已有对象带 `If-Match: "<revision>"`（不一致 409，刷新后显式重提）。

| 操作 | 接口 | 说明 |
|---|---|---|
| 开通 | `POST /api/platform/tenants` | 一个事务完成：建租户（`timezone` 缺省 `Asia/Shanghai`，DEC-056）→ 首位租户管理员与异常管理员的成员关系 → 标准业务身份（DEC-121 预置看全部）→ 首位租户管理员（8 类管理员身份可授、标准身份可授，并授予“标准版系统管理员（组织员工）”，占 1 个核心人力名额）→ 可选的许可发放 → 标准开关（允许直接调动 = 开，DEC-051；同一部门下职位允许重复 = 关，DEC-062a）→ 全部预置流程配置异常管理员后发布（DEC-018）。`exceptionAdminUserId` 必填，缺失即 400，不建租户。 |
| 查看 | `GET /api/platform/tenants/:id` | 返回租户与 revision（ETag） |
| 停用 / 重新启用 | `POST /api/platform/tenants/:id/status`，体 `{"status":"suspended"|"active"}` | 停用后租户内所有请求 403 `TENANT_UNAVAILABLE`，数据保留；不影响其他租户。恢复隔离中（restoring）的租户不能从这里开放，只能经 §5 的 `open`。 |
| 许可发放 / 调整 | `PUT /api/platform/tenants/:id/licenses/:licenseType`，体 `{"quota":N}` | 按产品线（许可类型，如 `pa_user`、`core_hr`、`digital_talent`）。返回发放后的余额，口径与租户侧“许可管理 / 余额”一致：余额 = 总数 − 仍在用的名额（DEC-141），余额不足照常授权并标出超额（DEC-143），由平台补发。 |
| 余额 | `GET /api/platform/tenants/:id/licenses` | 与租户侧余额接口同一数据 |

## 4. 备份策略与目标值（DEC-061）

| 指标 | 目标 | 怎么达成（部署阶段落实） |
|---|---|---|
| RPO ≤ 1h | 任一租户可恢复到 1 小时内的时间点 | ① 托管 PostgreSQL 开启连续归档（WAL）与时间点恢复，覆盖整库灾难；② 每小时对每个租户执行一次 `export`（逻辑备份，§5.1），覆盖“只恢复一个租户、不动其他租户”的场景 |
| RTO ≤ 4h | 从开始恢复到开放访问不超过 4 小时 | 隔离环境（空库，预先迁移到当前版本）常备；`restore` → 核对 → `open` 三步均为命令行，报告里有 `startedAt` / `verifiedAt` / `openedAt`，演练时记录实际耗时 |
| 保留 30 天 | 备份文件与 WAL 归档保留 30 天 | 对象存储生命周期规则按 30 天过期；过期删除走存储侧，不在应用内 |
| 传输与存储加密 | 备份文件不出现明文 | `export` 输出即 AES-256-GCM 密文（`BACKUP_ENCRYPTION_KEY`，32 字节，只放 Secret 管理）；对象存储另开服务端加密；传输走 TLS |

成本不可行时由用户决定降档（备选 RPO 24h / RTO 8h，DEC-061）。

## 5. 按租户恢复（演练与实战同一流程）

恢复单元 = 租户数据的一致快照 + 附件清单与哈希 + 代码 / 迁移版本（AGENTS.md §10）。

### 5.1 导出

```bash
export DATABASE_URL=...  BACKUP_ENCRYPTION_KEY=...  APP_VERSION=<镜像标签>
node apps/api/dist/ops/platform-cli.js export --tenant <租户ID> --out <租户ID>-<时间>.itb
```

- 只读、可重复读事务：所有表同一快照；读到任何其他租户的行即中止。
- 清单含：快照时点（UTC）、代码版本、迁移版本（条数 + 最后一条哈希）、每表行数、附件清单（ID、员工、SHA-256、大小、状态）、整体校验和。
- 平台审计记 `tenant.backup.export`。

### 5.2 恢复到隔离环境

**运行身份（硬性要求）**：导出、恢复、开放一律用迁移角色（表属主）连接——**非超级用户、不带 BYPASSRLS**，受 FORCE RLS 约束。命令行启动时检查，否则拒绝执行。读写时都先设 `app.tenant_id`，租户隔离由数据库兜底；行级校验（下文）不依赖这一点。

1. 新建**空库**（没有任何租户），用**备份清单里的代码版本**执行 `pnpm db:migrate`（迁移版本必须完全一致，否则拒绝恢复）。
2. 从对象存储按附件清单计算各附件内容的 SHA-256，存成 `{ "附件ID": "sha256" }` 的 JSON（接入对象存储模块后改为直接读取）。
3. 执行（`DATABASE_URL` 指向**现网**，对账以现网为准）：

```bash
node apps/api/dist/ops/platform-cli.js restore --in <文件> --target-url <隔离库连接> --hashes <哈希JSON> \
  --command-id restore-<租户ID>-<日期>
```

restore 依次做：
- **写入前校验**（任何一项不过即拒绝，隔离库不发生任何写入）：格式、迁移版本、校验和；隔离库**没有任何租户**；备份里只有这一个租户，每一行的 `tenant_id` 都属于它；各表行数与清单一致。
- **导入**（一个事务，含隔离校验、平台审计与命令台账）：租户状态一律置为 `restoring`（除平台方外一律拒绝访问）；系统预置**整表按备份值写回**（含没有租户覆盖的键，覆盖隔离库迁移带来的默认值）；在途事件 / 通知由 `pending` 改记 `unknown`（不补发消息）；审批数据按快照原样恢复，不推进、不重放已处理节点；导入后把所有序列推进到已导入最大值之后（如任职状态事件序号，同日排序依赖它）；原样加回全部外键，对全部行重新校验引用完整性；导入后隔离校验（他租户行 = 0、租户数 = 1、无清单外账号、行数一致）不过即整体回滚。
- **附件核对**：缺失或哈希不符都判不通过（待清理的附件不要求存在）。
- **授权对账**（以现网**此刻**的有效授权为准）：把现网该租户的授权子图——成员关系、身份及其对象 / 字段 / 按钮权限、授权、企业管理员、许可、管理单元、用户范围、身份数据权限（含 DEC-121 看全部）、数据权限策略、动态授权、用户与人员绑定——镜像到隔离库；全局账号按现网同步状态（停用的不复活）。现网没有的删、不同的改成现网的值；现网有而隔离库没有的补入，引用的业务对象在备份时点还不存在的跳过（只会更窄）。删不掉（被业务数据引用）的列入问题。
- **审批对账**（DEC-098 / 123）：对账后不可用的账号若仍是可用流程的异常管理员，改指现网该流程当前的异常管理员；其名下的在途异常待办按停用时的既有路径改派（以现网指定的替代人为准，否则租户管理员，DEC-091 回避）。**恢复期间只改派、不结算**：接手人已在同一会签节点占席（改派会合并席位并重新结算、推进流转甚至批准业务）的，不自动处理，列入问题。做不到的都列入问题。
- **授权对账的执行顺序**：删、改、补反复尝试直到不再有进展（如撤销后重授同一身份：许可名额改指新授权须等新授权先补入），最后仍做不到的删 / 改列入问题。
- 报告 `ok = true`（隔离、附件、对账均无问题）才可开放；结论与对账结果在同一事务记入隔离库（平台审计 `tenant.restore.reconcile` / `tenant.restore.verify`、租户审计 `tenant.restore.reconcile`）。

### 5.3 开放访问

```bash
node apps/api/dist/ops/platform-cli.js open --in <文件> --target-url <隔离库连接> --command-id open-<租户ID>-<日期>
```

只有隔离库里最近一次校验通过、租户仍处于 `restoring` 时才开放；**开放前重新读取现网并再次做授权与审批对账**（restore 之后、open 之前的撤权同样生效），再做一次隔离校验，任一有问题即拒绝开放。对账、状态变更、审计与命令台账同一事务提交。之后把该租户的流量切到隔离库（切换方式随部署架构定，见 §6）。建议在 open 前后暂停现网该租户（`POST /api/platform/tenants/:id/status`），切换期间不再产生新的授权变化。

### 5.3.1 结果未知时的重试

restore 与 open 的每个阶段（导入、校验、开放）都在隔离库的平台命令台账登记，键为“阶段 + 命令 ID 的 SHA-256”（定长，不截断）。命令 ID 须为 1～100 位字母、数字与 `: _ -`，否则拒绝执行。网络中断等结果未知时，**用同一 `--command-id` 重跑同一命令**：已完成的阶段直接返回首次结果，不重复执行；未完成的阶段整体回滚过，可安全重做。不同内容用同一命令 ID 会被拒绝（409）。

### 5.3.2 校验未通过后重新校验

restore 报告 `ok = false`（如附件缺失、对账有待人工处理的事项）时，租户保持 `restoring`。处理掉问题（补齐附件、在现网完成交接等）后，**换一个新的 `--command-id` 再执行 restore**：隔离库已有同一份备份（按校验和认定）的导入、租户仍在恢复隔离中时，不重复导入，直接重新附件核对、对账与校验。同一命令 ID 重跑仍返回首次（失败）结果；已开放的租户不能再这样重新校验。

### 5.4 演练记录（部署阶段验收 AC-TEN-06）

每次演练记录：备份时点、故障假设时点（RPO = 两者之差）、`startedAt` → `openedAt`（RTO）、报告中的隔离校验与对账结果、B 租户在演练期间的可用性（应不受影响）。应用侧演练已由 `tests/acceptance/AC-TEN-06.test.ts` 覆盖（PGlite 与真 PostgreSQL 16 均跑）。

## 6. 审计日志（R1-T16）

- **请求来源**：数据变更日志的 IP 取 `X-Forwarded-For` 第一跳（其次 `X-Real-IP`、套接字地址）。部署时反向代理必须**覆盖**（而不是追加）客户端传来的 `X-Forwarded-For`，否则 IP 可被伪造。来源页面、来源动作、前端版本由前端随请求带 `X-Source-Page`、`X-Source-Page-Type`、`X-Source-Action`（中文按 URL 编码）、`X-Client-Version`；TraceID 取 `X-Trace-Id` 或 W3C `traceparent`，都没有时服务端生成并回写响应头 `X-Trace-Id`。
- **保留期清理**：`server.ts` 默认每天运行一次（`AUDIT_RETENTION_INTERVAL_MS` 调整，不小于 60000；`AUDIT_RETENTION_SCHEDULER=off` 关闭本进程调度），按各租户 `audit.retention.retainMonths` 删除过期的数据变更日志、对象操作日志与失败命令审计；同一时间槽多实例只登记一次结果。每个对象的首个新增事件是数据范围「创建人」的判定依据，清理时保留。
- **兜底通道**：失败命令审计写不进数据库时，以一行 JSON（`type = audit.command_failure.fallback`）写到进程标准错误，日志采集须保留这类行。

## 7. 已知限制（待部署阶段定）

- 恢复后切回共享现网库（而不是让该租户继续使用隔离库）需要按租户替换数据，涉及只追加审计表的处理，尚未实现；部署方案定下前，恢复后的租户以隔离库对外服务。
- 附件内容的对象存储尚未接入，附件核对暂以运维提供的哈希表为准。
- 命令行运行身份为迁移角色（表属主）：恢复时需要在隔离库内临时卸下外键与业务触发器，现网运行时角色无此权限，也不应授予。超级用户与 BYPASSRLS 角色被命令行拒绝（测试环境中的 PGlite / CI postgres 为超级用户，行级校验保证同样拒绝他租户行）。
- 授权对账镜像的是授权子图；业务数据（组织、任职、审批实例等）停在备份时点，这是恢复的本义。
