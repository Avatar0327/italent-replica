> 来源类型：**配置证据**（配置中心 → 组织员工 → 业务系统配置 → 字段，字段说明为原站原文）
> 采集：2026-09-22 ｜ 验证状态：🟢 已读取
> 接口：`POST /ldapi/Implementer/BusinessScenariosSetting/GetMetaFieldList`（`MetaDataType: 0`=标准，`1`=自定义）
> 规模：**标准字段 120 个 + 本租户自定义字段 80 个 = 200 个**

## 1. ⭐⭐ 版本链的两个标志位（极易混淆，必须分别实现）

| 字段 | 编码 | 原站说明（原文） |
|---|---|---|
| **是否当前生效** | `IsCurrentRecord` | 「此字段在**审批状态=生效**时才有参考价值。是否当前生效=是，意味着任职记录的**生效日期 ~ 失效日期的时间段包含操作当日**」 |
| **是否最新主职记录** | `IsLatestRecord` | 「此字段在**任职类型=主职，且审批状态=生效**时才有参考价值。是否最新主职记录=是，意味着这条任职记录是**时间轴上最新的一条审批状态为生效的任职**，在其之后没有更靠后的生效任职」 |

> 🔴 **这是两个不同的概念，不能合并**：
> - `IsCurrentRecord` = 「今天」落在 [生效日期, 失效日期] 区间内
> - `IsLatestRecord` = 时间轴上最后一条生效记录（**可能是未来生效的**）
>
> 举例：员工有一条 2026-12-01 生效的调动记录（已审批生效但未到期）。
> 该记录 `IsLatestRecord=是`，但 `IsCurrentRecord=否`；当前仍是旧记录 `IsCurrentRecord=是`。
> **复刻若只做一个标志位，未来生效记录的查询会全错。**

### 1.1 生效区间字段
| 字段 | 编码 | 规则 |
|---|---|---|
| 生效日期 | `StartDate` | 「标记任职记录生效时段的开始日期；**此字段可以手动修改**」 |
| 失效日期 | `StopDate` | 「标记任职记录生效时段的结束日期。**兼职记录中此字段可手动修改**，用以调整兼职结束日期；**主职记录中由系统根据时间轴逻辑自动赋值，不可手动修改**」 |

### 1.2 任职周期
| 字段 | 编码 | 说明 |
|---|---|---|
| 员工ID | `StaffID` | 「**一个任职周期的唯一标示**」 |
| 入职日期 | `EntryDate` | 「标记员工本次进入公司的入职日期，入职后发生的转正、调动、离职任职记录中，入职日期**不会变化**；若员工离职后重聘入职，入职日期与上段任职周期不同」 |
| 入职类型 | `EntryType` | 记录任职周期的入职类型 |
| 是否是插入的任职记录 | `IsInserted` | 「如果是插入的任职记录则为 true」← **补录标记，向后更新的触发依据** |

## 2. ⭐⭐ 「变更前」值的实现机制（确认推断）

| 字段 | 编码 | 原站说明（原文） |
|---|---|---|
| **任职变动记录LookUp** | `EmploymentChangeLookUp` | 「1、**主职任职记录创建后，系统自动为其生成一条任职变动记录**，记录其在时间轴上**前一条生效主职任职记录的 id**，和此任职自身的 id<br>2、**可以用此字段下钻变动前任职记录的关联关系字段，显示变动前的任职情况**」 |

> ✅ **完全印证**了此前从调动管理视图字段编码 `\<guid>\<guid>~...OIdDepartment` 推断出的结论：
> 「调动前部门」不是独立字段，而是**通过「任职变动记录」这一中间对象**，关联到上一条生效主职记录的同名字段。
>
> **复刻的数据模型**：
> ```
> 任职记录 EmploymentRecord
>   └── 任职变动记录 EmploymentChange   （主职记录创建时自动生成）
>        ├── current_record_id   本条任职记录 id
>        └── previous_record_id  时间轴上前一条「生效主职」记录 id
> ```
> 「变更前 XX」= 沿 `previous_record_id` 取同名字段。**不得为每个字段建前/后两列。**

## 5. ⭐ 计算字段的公式（原文）

| 字段 | 编码 | 公式 |
|---|---|---|
| 累计司龄（年） | `WorkYearCompanyTotal` | 「=（**当前日期或最后工作日** − 入职日期）/ 365 + 司龄校正值（年）；取整方式：按此字段的**小数位数设置向下舍位**」 |
| 司龄校正值（年） | `WorkYearCompanyBefore` | 「如果设置了**离职重聘累计司龄**或**实习期间累计司龄**，则在离职重聘和实习生转正时**系统自动计算需累计期间的司龄并赋值**；在职人员最终累计司龄 = 当前日期 − 入职日期 + 司龄校正值」 |
| 累计工龄（年） | `WorkYearTotal` | 「=（当前日期或最后工作日 − **参加工作日期**）/ 365 + 工龄校正值（年）。**每天通过定时任务计算在职人员的累计工龄**；取整方式按小数位数向下舍位。**修改后的取整方式在第二天定时任务计算后生效**」 |
| 工龄校正值（年） | `WorkYearBefore` | 「单位为【年】，**可维护成正数或负数**」 |
| 实际试用结束日期 | `ProbationActualStopDate` | 「人员转正后自动计算，为**转正生效日期的前一天**」 |
| 最后工作日 | `LastWorkDate` | 「**最后工作日员工仍为在职状态**；最后工作日的次日为离职、退休生效日期」 |
| 试用到期天数 | `DaysDueForTrial` | 用于搜索即将到期的试用期人员 |

> 📌 **除以 365（不是 365.25，不考虑闰年）**，**向下舍位**（不是四舍五入）。这类细节复刻必须照搬，否则年限差一天就对不上。
> 📌 累计工龄靠**每日定时任务**刷新 → 又一个定时任务依赖。

## 6. ⭐ 主职 / 兼职模型

| 字段 | 编码 | 说明 |
|---|---|---|
| 任职类型 | `ServiceType` | 「记录任职是员工**主职还是兼职**。主职记录的任职类型为主职，兼职记录可选具体的任职类型。**创建任职后不可修改**」 |
| 任职状态 | `ServiceStatus` | 「记录**兼职任职**的 `任职中` / `任职结束` 状态。**任职状态仅针对兼职记录有意义**，主职记录中此状态虽有值但没有使用意义」 |

> 📌 结合 `IsLatestRecord`（仅主职有意义）、`StopDate`（仅兼职可手改）、向后更新（仅主职触发）：
> **主职与兼职在同一张表上走两套规则**。复刻必须显式区分，不能用统一逻辑。

### 11.1 ⚠️ 命名陷阱
**`AfterRecordLookUp` 字段名带 "After"，但存的是「变动前」任职记录 ID**；
真正指向"本条（变动后）"记录的是 `AfterEmpRecordID`。
旧字段 `BeforeRecordLookUp` 名称正确，但已被标为「请勿使用，兼容历史数据」，**仍需存值**。
→ 复刻不要照搬这套命名；需求中用 `current_record_id` / `previous_record_id` 表达，并在对照表中注明原站字段。

### 11.2 由此确认的模型
```
任职记录 EmploymentRecord (本条)
   └─ EmploymentChangeLookUp ──► 任职变动记录 EmploymentChange
                                    ├─ AfterEmpRecordID   → 本条任职记录
                                    ├─ AfterRecordLookUp  → 上一条生效主职任职记录（变动前）
                                    ├─ 业务类型/异动类型/变动类型/变动原因/变动日期（冗余）
                                    └─ ChangeContractLookUp → 变更后合同
```
「调动前部门」= 本条 → EmploymentChangeLookUp → AfterRecordLookUp → OIdDepartment。
与调动管理视图字段编码 `\<guid>\<guid>~TenantBase.EmploymentRecord.OIdDepartment` 的两段关系路径**完全对应**。

## 12. 场景对字段集的影响
直接按对象查询（不带业务场景参数）时，任职记录**标准字段为 170 个**；
在「调动管理」业务场景下查询为 **120 个**。
→ **业务场景会过滤对象可见字段**。复刻若提供字段配置界面，需按场景裁剪可选字段（DEC-001 下首版固定，不涉及）。

## 12. 排序编码的实际取值（Q-M0-07 / Q-M0-36，2026-10-04，A5 只读）

> 来源：组织详情、任职记录详情的 `DetailPage` 接口返回。本租户组织排序规则**停用**、人员排序规则启用（所属部门 ↑ → 工号 ↑ → 职级 ↑，见 G-036 补证）。

| 对象 | 观察 |
|---|---|
| 组织（华夏九洲集团详情） | 只有 `OrderAdmin`（行政维度顺序号）= 9，**没有排序编码字段的值**——与组织规则停用一致 |
| 任职记录（列表前 8 条的详情） | `OrderCode` 依次为 1、2、3、4、5、5、7、4；同时带 `OrganizaitonOrderNum`（组织排序号，如 55、1、53、10、5、12）和 `JobLevelOrderNum`（职级排序号，如 1632、1039、224、359、551） |

- 观察结论：
  1. `OrderCode` 在本租户是**小整数**，且有重复，看不出“各段固定位数拼成一个长整数”的结构；各属性排序号也是**名次型**数值（组织排序号 1～几十，职级排序号上千），不是定宽编码。
  2. `OrderCode` 与组织排序号的先后并不一致（组织排序号 1 的记录排在 55 之后），抽到的多为非当前记录，可能是原站每 3 小时刷新留下的旧值；所以**无法从现有数据反推出完整的组合算法**。
- 对复刻的含义：DEC-037 / DEC-089 已定复刻自行预计算各属性名次。按上面的观察，排序编码按“规则项依次比较后的名次”实现即可，**不需要定义分段宽度、空值占位与溢出规则**；与原站数值逐一对上不是目标。若要确认原站算法，需读手册 39387531 正文（用户社区登录后）。


- **手册补证（2026-10-05，HRSAAS 39387531「排序规则」、CustomerKB 171639751 / 127632332 / 225903222）**：
  - 排序编码不是用户输入，也不是分段拼接：设置「人员默认排序规则」后，系统**按规则自动给员工信息、任职记录、合同协议的【排序编码】写值，每三小时刷新一次**；组织同理（组织单元的【排序编码】）。列表要按规则排，需在列表“结果集排序”里选排序编码。
  - 各规则项的比较依据：所属部门 = 行政上级 + 行政维度顺序号；职务 = 编码；职位 = 顺序号；职级 = 级别；职等 = 等级；工号 = 工号。组织规则：行政隶属关系 = 层级 + 行政维度顺序号；或编码。
  - 插入新组织时的编号：开启组织排序规则后，新建组织的行政维度顺序号**按设立日期与上级组织联动自动带出**（未填设立日期则不显示），即顺序号由系统给，不是手填拼接。
  - 结论：没有分段宽度、空值占位、溢出这类概念；排序编码 = 按规则项依次比较后的名次（可并列），定时批量重算。与 DEC-037 / DEC-089（复刻预计算名次）一致，无差异。复刻可选：实时重算或定时重算，原站为 3 小时批量。

## 9. 人员状态与入职状态（F-022 开工前，Q-M0-96～99，2026-10-06 只读）
来源：A0 只读；字段说明取自 `01_证据/导出/任职记录_标准字段_120.tsv`；枚举取自原站视图数据源；分布统计为全部任职视图（未删除，按修改时间倒序前 4000 条）。

### 9.1 枚举（🟢 原站数据源）
- 人员状态 `EmployeeStatus`（`TenantBase.EmployeeStatus`）：待入职 1、试用 2、正式 3、调出 4、待调入 5、退休 6、离职 8、非正式 12。
- 入职状态 `EntryStatus`（`TenantBase.EntryStatus`）：正常 0、取消 1、延期 2；另有“空（未填写）”，待入职视图把空也当作有效待入职（Q-M0-76）。

### 9.2 写在哪里、何时变（Q-M0-96、97）
- 🟢 **人员状态是任职记录每一个版本上的字段**，表示该版本的目标状态；员工“当前”状态取当前生效主职版本的值。分布统计：离职记录无论审批中 / 草稿 / 作废，均为 人员状态 = 离职、任职状态 = 任职结束；转正记录无论审批中 / 草稿 / 作废 / 审批通过，均为 正式；待入职人员的入职记录为 待入职（生效、当前）；入职记录按是否有试用期为 试用 或 正式（另有少量 非正式）。因此**状态切换的时点 = 承载新状态的版本生效的时点**，不是审批通过时。
- 转正：转正记录把状态由试用改正式，生效日 = 转正日期（未来日期则到期生效）；时间轴上晚于转正生效日的后续版本一并改为正式（`29` PB-R4、PB-R7，🟡 手册）。
- 🟢 试用状态不随试用期结束日期自动变化：有试用期结束日早于今天仍为“试用”的样本（Q-M0-76）。
- 入职：添加待入职 → 入职记录 人员状态 = 待入职、入职状态 = 正常（W-433′ 实例 🟢）；办理入职生效后按是否有试用期变为 试用 / 正式（`34` EN-R11，🟡）。
- 入职状态：字段说明原文要点——录入待入职人员、进行**延期入职或取消入职**操作时由系统赋值，**不可手动修改**（🟢 字段说明）。改期延后 → 延期；取消入职 → 取消；已取消的人可通过改期恢复（`34` EN-R8、EN-R9，🟡）。“确认到岗”未见对应取值，入职生效后该字段不再参与在职口径。
- 离职：离职记录创建时即为 人员状态 = 离职、任职状态 = 任职结束；原站审批中就写入版本链（D-031），复刻按 DEC-125 / DEC-215 生效时才写。

### 9.3 展示与编辑（Q-M0-98）
- 🟢 人员状态字段说明：不可直接编辑，只能通过【调整试用信息】维护试用期信息来更新；任职记录「编辑」弹窗中该字段为灰色不可选。
- 🟢 入职状态不可手动修改（字段说明）。
- 两者都随任职版本存储，因此天然带生效日期（版本开始日期）与历史；列表与高级筛选按取值筛选（工作台各视图的固定筛选见 `12` 附录 §8）。

### 9.4 工作台口径对照（Q-M0-99）
- 试用中 = 当前生效主职版本 人员状态 = 试用 2（+ 雇佣关系 ∈ {内部员工, 实习生}、任职中、未删除）。
- 待入职 = 人员状态 = 待入职 1、入职状态 ∈ {空, 正常, 延期}、变动类型 ∈ {新增入职, 重聘入职}，不限当前记录。
- 与 Q-M0-76 一致，无新增差异。
