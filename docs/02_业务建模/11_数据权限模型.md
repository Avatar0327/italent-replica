## 1. 核心结论（已实测验证）

> ### 功能权限与数据权限是**两套完全独立**的机制，必须分别建模、分别验证。

实测证据（A4 账号）：

| 层 | 状态 |
|---|---|
| **功能权限** | ✅ 通 —— 菜单出现 21 个顶级项；`TenantBase.EmploymentRecord` / `Organization` / `EmployeeInformation` 三个对象的 IndexPage 全部返回 200 且视图元数据完整 |
| **数据权限** | ❌ 空 —— 组织列表清空筛选后 **0 条**；任职记录默认筛选 **0 条**；A0 下能搜到的组织在 A4 下搜不到 |

**→ 「菜单可见 + 接口 200 + 元数据正常」不能推出「能看到数据」。**

## 2. ⭐ 「默认管理单元」的真实语义

A4 的授权记录中，`组织员工` 对应的管理单元显示为 **`默认管理单元`**。
实测结果：**覆盖范围为空，不是全部**。

| 错误假设 | 实际 |
|---|---|
| 默认管理单元 = 默认给全部数据 | ❌ |
| 默认管理单元 = **未配置具体范围 = 无数据** | ✅ |

> **复刻硬性要求**：数据范围的"默认值"语义必须显式定义为**空（拒绝）**，不能是**全部（放行）**。
> 若实现成"未配置即全部"，等于系统性越权。这是安全默认值（fail-closed）原则在本系统的体现。

## 3. 数据范围的表达形式（来自 A0 授权列表实测）

一条授权记录 = 用户 × 身份 × **该身份覆盖的每个应用各自的管理单元**。
实测到四种表达：

| # | 形式 | 实例 | 语义 |
|---|---|---|---|
| 1 | `默认管理单元` | `目标管理：默认管理单元` | **未配置 → 空** |
| 2 | `<租户/集团名>` | `任务：北京SR样板间`、`标签库：华夏集团` | 按租户/集团单元 |
| 3 | **`组织范围【<组织名>(<编码>)(包含下级)】`** | `组织员工：组织范围【HT公司(zz10224)(包含下级)】`<br>`审批中心：组织范围【HT公司(zz10224)(包含下级)】` | **组织树范围 + 是否含下级** |
| 4 | **`薪资组范围【<组1>(编码)(包含下级)，<组2>(编码)(包含下级)】`** | `薪酬管理：薪资组范围【HT薪资组2(HT2)(包含下级)，HT薪资组1(HT1)(包含下级)】` | **薪资组范围，可多选** |

### 3.1 关键结构特征
1. **范围维度因应用而异**：组织员工/审批中心用「组织范围」，薪酬管理用「薪资组范围」，其他用「管理单元」。
   → 不能设计成一个全局的 `org_scope` 字段。
2. **支持"包含下级"标志**：范围是子树而非单节点。
3. **可多值**：薪资组范围实例中一次绑定了两个薪资组。
4. **逐应用独立配置**：同一个身份（如「部门负责人」横跨 31 个应用）在**每个应用上分别指定管理单元**。
   实例：HT管理员的「部门负责人」身份 —— 组织员工是组织范围、薪酬管理是薪资组范围、其余 20+ 个应用是默认管理单元。

## 4. 建议的复刻数据模型

```
授权记录 (UserPermission)
├── user_id
├── profile_id                     ← 身份
└── app_scopes[]                   ← 每个应用一条
    ├── app_code                   ← TenantBase / Compensation / ApprovalCentre …
    ├── scope_type                 ← DEFAULT(空) | TENANT | ORG_RANGE | PAYROLL_GROUP_RANGE | …
    ├── scope_values[]             ← 可多值
    │   ├── target_id              ← 组织/薪资组 的 ID
    │   ├── target_code            ← 编码（展示用）
    │   └── include_descendants    ← 是否包含下级
    └── （scope_type 的可选集合由 app_code 决定）
```

**要点**：
- `scope_type = DEFAULT` 必须解释为**空集**（fail-closed）
- `scope_type` 的可选值是**每个应用自己定义的**，属于应用元数据的一部分
- 复刻若取 DEC-001 的 R1（固定配置），仍需保留这个结构，因为范围值本身是运行期数据（哪些组织），不是配置

## 5. 与其他权限层的关系

| 层 | 控制什么 | 载体 | 本轮证据 |
|---|---|---|---|
| **许可（License）** | 是否购买了该产品的使用名额 | 许可管理（PA用户/核心人力用户/数字人才用户余额） | 授权弹窗实时显示余额（649/638/493） |
| **功能权限** | 能看到哪些菜单、能调哪些对象/操作 | 身份（Profile）× 应用 | A4 授权后菜单 37→140 |
| **数据权限** | 在有权限的对象上，能看到哪些**记录** | 管理单元 / 组织范围 / 薪资组范围 | A4 功能通但数据 0 条 |
| **字段权限** | 记录内哪些字段可见/可编辑 | 待取证（身份目录中有 `标准版系统管理员（组织员工）字段限制`、`测试身份 仅部分字段`） | **未验证** |
| **业务状态** | 记录处于某状态时能否操作 | 待取证（如审批中的记录能否编辑） | **未验证** |
| **管理员可授权范围** | 管理员能把哪些身份授予别人 | 管理员记录的「可授权业务身份」集合 | A0 实测 296/297 项已勾选 |

> 📌 **字段权限确有其事**：身份目录中存在 `标准版系统管理员（组织员工）字段限制`（描述"拥有组织员工的所有业务功能的权限"）
> 与 `测试身份`（描述**"仅部分字段"**）。→ 证明原站支持**同一对象上按身份限制字段**。缺口 G-018，需取证。

## 6. 由本模型产生的验收场景
| # | 场景 | 预期 |
|---|---|---|
| D-1 | 用户有功能权限但数据范围为空 | 列表 0 条；**系统应可区分"无数据"与"无数据权限"**（原站不可区分，见 D-003） |
| D-2 | 数据范围 = 组织范围【X(包含下级)】 | 能看到 X 及其所有下级组织的数据，看不到 X 之外的 |
| D-3 | 数据范围 = 组织范围【X(不含下级)】 | 只能看到 X 本级 |
| D-4 | 同一身份在 A 应用有范围、B 应用为默认 | A 应用有数据，B 应用 0 条 |
| D-5 | 多身份叠加，范围不同 | 取**并集**（官方："若同一人员拥有不同的身份，则取并集"） |
| D-6 | 数据范围内的组织被停用 | 待验证：范围是否自动收缩 |
| D-7 | 员工被调动出数据范围 | 待验证：原 HR 是否还能看到该员工的历史任职记录 |
| D-8 | 许可余额为 0 时授予身份 | 待验证：是否阻止 |

> D-7 对**调动闭环**尤其关键：调出方 HR 在员工调走后还能否看到他？这决定了"调出方/调入方"的数据可见性边界。

## 12. ⭐⭐ 模型修正：管理单元的存储粒度是（用户 × 应用），不是（用户 × 身份 × 应用）

### 12.1 实证过程
1. A4 有 **2 条**授权记录：`标准版系统管理员（组织员工）_简` 与 `员工`，两条的 `组织员工` 管理单元均为 `默认管理单元`
2. **只编辑了其中一条**（`标准版系统管理员（组织员工）_简`），把 `组织员工` 的范围改为 `组织范围【华夏九洲集团(HXJZ)(包含下级)】`
3. 回查结果：**两条记录的 `组织员工` 范围都变成了** `组织范围【华夏九洲集团(HXJZ)(包含下级)】`
4. 对照组：A2、A3 未做任何操作，其 `组织员工` 范围仍全部为 `默认管理单元`（各有 3 条记录覆盖该应用）

### 12.2 结论
> **同一用户在同一应用下只有一份数据范围，由该用户的所有身份共享。**
>
> 授权列表把管理单元显示在每一行（每个身份）上，容易误以为是逐身份配置；
> 实际存储与生效粒度是 **(user_id, app_code) → scope**。

> **DEC-043（2026-09-30）**：复刻照搬此粒度。

### 12.3 对复刻的直接影响
**修正后的数据模型：**
```
授权记录 UserProfile            数据范围 UserAppScope
├── user_id                    ├── user_id          ┐
├── profile_id                 ├── app_code         ┘ 联合主键
└──（功能权限来源）             ├── scope_kind       ← MOU | ORG_RANGE | DEFAULT(空)
                               ├── mou_id
                               └── org_ranges[]
                                   ├── org_id / org_code / org_name
                                   └── include_descendants
```
- **两张表，不是一张**：身份（功能权限）与数据范围（数据权限）**多对一**，不是一对一
- 撤销某个身份时，**不应**连带删除数据范围（其他身份还在用）
- 新增身份时，若该用户在该应用已有范围，**自动沿用**，不重复配置

### 12.4 由此新增/修正的验收场景
| 编号 | 场景 | 预期 |
|---|---|---|
| AC-PRM-14 | 用户有身份 P1、P2 均覆盖应用 A；编辑 P1 记录中 A 的数据范围 | **P2 记录中 A 的范围同步变更** |
| AC-PRM-15 | 撤销身份 P1，用户仍持有 P2（同样覆盖应用 A） | A 的数据范围**保留**，P2 仍可按该范围取数 |
| AC-PRM-16 | 用户在应用 A 已有范围，新授予一个也覆盖 A 的身份 | ~~新身份自动沿用已有范围~~ 更正（W-313 实测）：原站授权表单管理单元为空，保存即覆盖该用户在 A 的共享范围；复刻表单预填现有范围并提示共享（增强） |

> ⚠️ 若复刻时误把数据范围建成 (user, profile, app) 粒度，会出现：
> 同一用户不同身份的范围不一致 → 取数结果依赖"以哪个身份进入" → 与原站行为不符，且难以解释。

## 13. ⭐ 平台级数据权限体系（2026-09-22 补，官方文档为主）

> 前 12 节讲的是**授权侧**：用户 × 应用 → 数据范围，也就是“这个人被授了什么范围”。本节讲的是**消费侧**：某个实体或页面**拿哪个字段、去和哪种范围比对**。复刻两侧都要实现。

### 13.1 四类数据权限 + 两类辅助
来源：HRSAAS/135169310（数据权限设置）、86410516/86410519/86410521/86410523、SenFAQ/93816098（优先级）

| 类型 | 作用对象 | 语义 |
|---|---|---|
| 实体数据权限 | 实体（对象） | 控制该实体下所有视图和数据源的可见数据。例外：详情页里直接配置的相关对象列表不受它控制 |
| 页面（视图）数据权限 | 某个视图 | 配置后，这个视图**不再受**实体数据权限控制 |
| 数据源数据权限 | 某个实体数据源 | 配置后，这个数据源**不再受**实体数据权限控制 |
| 身份数据权限 | 身份 × 应用，或 身份 × 指定实体/页面/数据源 | 让指定身份**看全部数据**，不受数据权限控制 |
| 数据权限触发器（辅助） | 脚本 | 配合前四类做定制鉴权。标准触发器不能编辑也不能删除，自定义触发器可以删除。一般只有客开客户使用 |
| 数据范围场景管理（辅助） | — | 为前四类提供更多配置项 |

**优先级**：身份数据权限 > 页面数据权限 > 实体数据权限；身份数据权限 > 数据源数据权限 > 实体数据权限。**覆盖关系是“更具体者替换”，不是叠加。**
**边界**：以上各类都**不控制 Ocean 报表**，报表有独立的数据权限体系，首版 ⏸。
**标准配置的可改性**：部分标准实体/页面的数据权限允许租户编辑，编辑后可以「恢复」为系统级配置；另一部分标准配置的编辑按钮是禁用的。**复刻要区分“系统预置、只读”与“系统预置、可覆盖、可恢复”两种状态。**

### 13.2 权限规则 + 鉴权字段（两层抽象）
来源：HRSAAS/135169312（权限规则设置）、135169314（鉴权字段设置）

- **权限规则**：用范围类型组合出的条件模板，例如 `管理人员范围 AND 管理组织范围`。可以选已有规则，范围是 当前应用 + 组织员工 + 企业设置 的规则；也可以按实体自定义。
- **鉴权字段**：每个实体声明**哪个字段充当“人员”**、**哪个字段充当“部门”**。
- 官方原例：**任职记录的数据权限 = `任职记录.人员 ∈ 管理人员范围 AND 任职记录.部门 ∈ 管理组织范围`**。试工管理套用同一条规则，只是鉴权字段不同。
- 复刻数据模型：`permission_rule(id, app, expr)` 加 `entity_auth_field(entity, role: person|department|project|creator, field)`。实体数据权限 = 引用规则 + 字段映射，**运行时展开**。

### 13.3 页面数据权限的 5 种授权维度
来源：HRSAAS/144048938、144048941、144048943、158924943、144048945

| 维度 | 可见数据 | 典型用户 |
|---|---|---|
| 管理单元 | 用户在当前应用被授的管理单元范围（即本文 §1–§12 的授权侧） | HR |
| 汇报关系 | 用户的下属。可选：直线下级 / 所有直线下级 / 虚线下级 / 直线下级及其直线和虚线下级 / 虚线下级及其直线和虚线下级 / 所有兼职直线下级（兼职、返聘、借调、外派，不含主职）。**多条规则取并集** | 直线经理 |
| 组织关系 | 用户在组织上担任某个角色（如 HRBP、负责人）时，可见 实体部门字段 ∈ 该组织及全部下级 | 部门负责人、HRBP |
| 项目关系 | 用户是项目负责人时，可见 实体项目字段 ∈ 该项目及下级 | 项目负责人（首版 ⏸） |
| 使用用户 | 只见 创建人 = 自己 的数据 | 普通员工 |

**对本项目的意义**：
1. 解释了部门负责人和直线经理**不配管理单元也能看到本部门或下属**的原因：他们的数据范围来自**组织关系和汇报关系维度**，而不是管理单元。这与 §2「默认管理单元 = 无范围」不矛盾，两者是不同维度。
2. 与 06 §7.3 动态授权“组织角色 + 默认管理单元”的例外是同一套机制。
3. **REQ-PRM-002 需要补一个“范围来源”**：管理单元 / 组织范围（授权侧）之外，还要支持 汇报关系、组织关系、使用用户 三种**关系派生范围**（消费侧，按页面配置）。已写入缺口 G-019。

### 13.3a 补充：管理人员范围、页面 / 数据源规则的关系（Q-M0-29 / 31 / 32，2026-10-05 手册 + 只读）

- **页面规则与数据源规则不竞争（Q-M0-32 ✅）**：两者作用对象不同。页面（视图）数据权限管的是某个视图的列表与页面内同实体组件（手册 PaaSGuide 65176299：“应用页中页面所属实体的组件按页面数据权限鉴权，其他实体的组件按组件所属实体的实体数据权限鉴权”）；数据源数据权限管的是表单字段绑定的实体数据源 / 触发器数据源的**候选项**（65176199 例：Offer 上薪级、薪等字段只能选管理单元“薪级薪等数据范围”内的值）。各自“替换”实体数据权限，互不覆盖。官方优先级（SenFAQ 93816098）只有两条链：身份 > 页面 > 实体、身份 > 数据源 > 实体。复刻：页面规则用于列表 / 详情行可见性，数据源规则用于下拉 / 查找候选，二者同时存在时各管各的，不需要裁决顺序。
- **管理人员范围的定位与条件（Q-M0-29 🟡）**：是管理单元上与“管理组织范围”并列的第二种范围（手册 2262640）：“设置一定的筛选条件，然后系统将自动计算出对应的人员”，条件写法如 `任职记录.用工形式 = 外包`（CustomerKB 234095386）。要点：
  - 只匹配 `是否当前生效 = 是` 的任职记录（同上 234095386：未来入职的待入职人员因此不在范围内；标准待入职视图单独做了解析，自定义视图不支持）。
  - 页面要受它控制，还需租户管理员在后台打开对应开关（2262640）。
  - **组织范围为空时人员范围不生效**（CustomerKB 229245925），即两者是交集而非并集。
  - 另有按业务的变体，如“管理人员范围（社保）”以社保档案为底再套条件（242846220）。
  - 未能读到实际条件结构：A0 打开管理单元详情只显示基本信息，范围区块不渲染；对象 `UserFramework.Mou` 上也没有人员范围字段（§14）。条件对象 / 运算符的完整清单待有租户管理员权限时补读。
- **兼职 / 副职是否计入管理人员范围（Q-M0-31 🟡）**：手册未直接说明。可确定的是：①人员范围按任职记录筛选，只取当前生效的记录；②原站对兼职有单独的“汇报关系 - 所有兼职直线下级（兼职、返聘、借调、外派，不含主职）”维度（§13.3），说明兼职关系默认不混入主职口径；③其他模块有“取生效日期倒序第一条、没区分主兼职”导致取到兼职部门的已知问题（CustomerKB 253166304）。推定管理人员范围按条件匹配任职记录，兼职任职记录若满足条件也会被算入，需实测确认（要建兼职记录，属写入）。

## 14. 管理单元对象 `UserFramework.Mou` 的结构（G-020，2026-09-22 🟢 配置证据）

来源：`GetMetaFieldList?app=UserFramework&metaObjName=UserFramework.Mou`（标准字段 36 个，只读）

| 类别 | 字段 | 含义 |
|---|---|---|
| 标识与层级 | `OId`、`Name`（编码）、`Title`/`TitleNew`（名称）、`PMou`（上级管理单元）、`Level`、`MouPath`、`HasSub`、`SortNumber` | 管理单元本身是一棵树（印证 06 §1.3 的集团层级：华夏集团 → 北京SR样板间） |
| 范围 | `ReferenceObjectIDs`（组织范围，JSON 字符串）、`IsContainsLower`（是否包含下级） | 组织范围是**正向枚举**的组织 ID 列表 |
| ⭐ 虚拟管理单元（字段分组名就叫“虚拟管理单元”） | `Type`、`OwnerId`（所属人 UserID）、`Application`（所属人应用编码） | 在用户授权里**直接选组织范围**时，系统会生成一个**归属于（用户 × 应用）的虚拟管理单元**。所以 §10 的两个页签（具名管理单元 / 组织范围）在存储上是**同一个对象**，只是 Type 不同 |
| 生命周期 | `Status`（启停）、`ApproveStatus`、`WorkFlowProcessId`、`ApprovalObjectDataId` | 管理单元的变更**可以走审批流** |
| 说明 | `Descriprion`（原字段名拼写如此） | — |

**结论**：
1. **G-020**：对象上没有“排除组织 / 排除子树”一类字段，组织范围只能正向枚举。**原站不支持负向表达**。要实现“A 公司除去 B 部门”，只能把 A 下 B 以外的节点逐个列出（不含下级），或另用“管理人员范围”的筛选条件实现。
2. `IsContainsLower` 在对象上只有一个，但授权列表显示为每个组织各自带“(包含下级)”标记（§3）。推断每个组织的“含下级”标志存放在 `ReferenceObjectIDs` 的 JSON 里，单个字段是兼容用的（🟡 待证）。
3. 「管理人员范围」（按条件动态算出人员）在本对象上**没有对应字段**，应存放在其他对象中（⏸ 未定位；官方 2262640 说明需要租户管理员打开开关后才生效）。
4. **复刻数据模型修正**：`mou(id, parent_id, kind: named|virtual, owner_user_id?, app_code?, org_refs: [{org_id, include_descendants}], status)`。用户授权中的“组织范围”即为 `kind=virtual` 的 MOU，这样授权侧就只需要一个 `mou_id` 外键，不必再维护两套范围结构。
