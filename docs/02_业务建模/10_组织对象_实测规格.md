## 2. ⭐ 多维组织：三条并行层级

新建表单的「多维组织」分组包含**三套独立的上级 + 顺序号**：

| 维度 | 上级字段 | 顺序号字段 |
|---|---|---|
| **行政维度** | 行政维度上级 | 行政维度顺序号 |
| **业务维度** | 业务维度上级 | 业务维度顺序号 |
| **财务维度** | 财务维度上级 | 财务维度顺序号 |

> **建模含义**：组织**不是一棵树**，而是同一组织节点在三条并行层级中各有一个父节点与排序。
> 复刻若用单一 `parent_id` 实现，将无法表达业务口径与财务口径的汇总路径。
>
> 与菜单中「业务组织查看人员列表」「停用业务组织人员任职」「利润中心查看人员列表」「停用利润中心人员任职」等入口相印证。
> 配置入口：组织员工 → 设置 → 组织 → **多维度组织设置**（鲁班页 `pageCode=tenantbaseSetting&SwitchTypes=88,89,90,91,92`）
>
> ⏳ 待验证：三个维度是否都必填？未填时默认继承行政维度？维度是否可由租户增减（`SwitchTypes` 有 5 个编号，暗示可能不止三维）

## 4. ⭐ 写入链路：三段式

实测一次「新建组织」触发的接口序列：

```
① POST /mrest/TenantBase/TenantBaseOrganization/100000/FrontExt/buttonBasedSecondaryConfirmation
   → 返回 { FieldsDic, showMoreMessage, confirmText, cancelText, linkPermission,
            rehireMessageList, rehireTypeInfo, StrictControl, flag, IsBeyondEstablishment, ... }

② POST /mrest/TenantBase/TenantBaseOrganization/100000/org
   → { "code":200, "message":"操作成功", "param":"{ \"OId\":\"3664975\"}" }

③ POST /mrest/TenantBase/TenantBaseSettingsSystem/100000/FrontExt/SetCodeUnUsed
   → { "code":"200", "Data":"成功" }
```

### 4.1 ① 提交前二次确认层（重要）
`buttonBasedSecondaryConfirmation` 是**统一的写前校验与二次确认端点**，返回字段揭示了它承担的职责：

| 返回字段 | 推断职责 |
|---|---|
| **`IsBeyondEstablishment`** | **是否超编**（编制控制） |
| **`StrictControl`** | 强控级别（1 = 强控？区分"阻止"与"仅提醒"） |
| `confirmText` / `cancelText` | 二次确认弹窗的文案（服务端下发） |
| `rehireMessageList` / `rehireTypeInfo` | 重聘相关提示（用于人员类业务） |
| `linkPermission` | 关联权限校验 |
| `FieldsDic` / `showMoreMessage` / `moreMessage` | 字段级校验信息 |

> **复刻含义**：原站把「保存前的业务校验 + 二次确认文案」做成了**服务端统一下发的一层**，
> 而不是散落在各个前端表单里。复刻必须把它建成独立机制，否则：
> - 超编控制、重聘提醒这类跨场景规则会被重复实现且不一致
> - 二次确认文案无法由配置驱动
>
> ⏳ 待验证：`StrictControl` 的取值含义；超编时是**阻止提交**还是**提示后可继续**。

### 4.2 ③ 编码的预占与释放
- 打开新建表单时，系统**预先分配**编码（本次 `zz10228`、`zz10229`），直接显示在表单上
- 无论提交成功还是取消，最后都会调用 `SetCodeUnUsed`
- 对应配置：组织员工 → 设置 → 公共设置 → **自动编码**

> **复刻含义**：自动编码是**有状态的预占机制**，不是提交时才生成。
> 这影响并发场景：两个管理员同时打开新建表单会各自预占不同编码。
> 若复刻时改成"提交时生成"，行为会不同（表单上看不到编码），属产品差异。

## 8. 登录后补证（2026-09-22 第二批）

### 8.1 G-011 已解决：人事侧与平台侧组织是同一份数据
在人事侧 `TenantBase.Organization` 新建的 `RUN20260922_ORG_SRC`，在平台侧「企业设置 → 组织架构 → 组织」（`UserFramework.Organization`）可直接查到：
编码 `zz10228`、序号 `59`、上级 `华夏九洲集团`，与人事侧完全一致。🟢
→ 复刻**只需一个组织主数据**，两个入口是同一对象的不同视图（平台侧列 7 列、人事侧 42 列）。
（平台侧组织总数 1549 条。）

### 8.2 G-013 已解决：组织维度是 5 个可开关的维度
设置页 `SwitchTypes=88,89,90,91,92`（组织员工 → 设置 → 组织 → 多维度组织设置）实测：

| SwitchType | 设置页名称 | 状态 | 字段元数据名称 | 字段编码 |
|---|---|---|---|---|
| 88 | 业务组织 | ✅ 开 | 业务维度 | `POIdOrgReserve2` |
| 89 | 利润中心 | ✅ 开 | 产品维度 | `POIdOrgReserve3` |
| 90 | 成本中心 | ❌ 关（提示「请前往【薪酬社保>成本中心】维护数据」） | — | `CostCenterOId`（独立对象） |
| 91 | 预留组织4 | ✅ 开 | 预留维度4 | `POIdOrgReserve4` |
| 92 | 预留组织5 | ✅ 开 | 预留维度5 | `POIdOrgReserve5` |
| — | 行政维度（恒在） | — | 行政维度 | `POIdOrgAdmin` |

说明原文：「开启后，可管理此维度组织，以及按此维度查看架构图」。

**关键结论**
1. 维度 = **1 个恒在的行政维度 + 4 个可开关的扩展维度**（利润中心所在的 Reserve3 在元数据里叫"产品维度"）
2. **成本中心不是组织维度**，是薪酬社保侧的独立对象，组织上只存引用 `CostCenterOId`
3. **同一维度三处叫法不同**：元数据「产品维度」、设置页「利润中心」、新建表单「财务维度上级」→ 又一例场景别名（G-037）
4. 每个维度各自有 `上级`、`顺序号`、`_TreePath`、`_TreeLevel` 四个字段
5. 本次新建时只填了行政维度即成功 → 扩展维度**非必填** 🟢

## 9. 停用上级组织时仍有启用下级（Q-M0-12，2026-10-04，A5 只读）

| 证据 | 内容 |
|---|---|
| 停用弹窗（测试组织 EST_B，下有启用的 EST_B1～B3；只打开查看，取消未保存） | 字段：停用日期、停用组织、**是否分批转移**、停用组织的职位 / 人员转移到、**同步调整编制**（“勾选后，各上级组织的【含下级编制】同步减少 62 个”，62 即 EST_B 的含下级编制）。弹窗**没有**“存在启用下级，不能停用”之类的拦截或提示 |
| 「是否分批转移」说明原文 | “选择‘否’，则可以将组织中的职位、任职统一转移到一个组织中；选择‘是’，则可以将**组织及其下级组织**中的职位、任职分批转移到多个组织中”；「转移到」说明：“被停用组织的在职人员和职位，将转入替换组织”。分批转移列表带“所属组织”列（EST_B 一支没有职位、任职，显示 0 / 0） |
| 本租户停用组织的数据 | 721 个停用组织中，“上级、下级都已停用”的 613 对里，**584 对是同一天停用**；另 29 对全部是**下级先停、上级后停**；**没有一例**是上级停用后下级还继续启用、之后才停 |

- 结论（强推断，未写入实测）：原站停用上级组织时**级联停用整支下级**（同一停用日），整支内的在职人员与职位一并转入指定的替换组织（可分批转到多个组织）；含下级编制可选同步扣减各上级。
- 未确认：整支内有人员却不指定转移目标时是否拒绝；能否只停上级、保留下级（数据上没有这种情况）。要确证需写入实测（停用一个有下级的测试组织），需先征得同意。
- 复刻系统现状：`apps/api/src/modules/org/write-service.ts` 更新组织时不检查下级（TODO Q-M0-12），即允许上级停用而下级仍启用，与原站不同 → 登记册 **D-035** 用户选②，已登记 **DEC-129**：级联停用整支下级，整支内还有人员或职位即拒绝，不做自动转移（与 DEC-016 一致）；“不指定转移目标”的原站行为不再实测。
