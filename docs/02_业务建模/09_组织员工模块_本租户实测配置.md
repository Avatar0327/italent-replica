## 1. ⭐ 核心建模发现：任职记录是唯一主对象

A0 可见的「组织员工」共 **182 个菜单项**。其中**任职管理**下的绝大多数菜单指向**同一个业务对象**：

| 菜单 | metaObjName | 页面类型 |
|---|---|---|
| 入职管理 | **`TenantBase.EmploymentRecord`** | CustomPage |
| 试用期管理 | **`TenantBase.EmploymentRecord`** | CustomPage |
| **调动管理** | **`TenantBase.EmploymentRecord`** | ViewPage |
| 离职管理 | **`TenantBase.EmploymentRecord`** | CustomPage |
| 兼职管理 | **`TenantBase.EmploymentRecord`** | ViewPage |
| 退休管理 | **`TenantBase.EmploymentRecord`** | ViewPage |
| 任职记录 | **`TenantBase.EmploymentRecord`**（视图 `TenantBase.AllEmployeeNavView`） | CustomPage |
| 新员工融入 | **`TenantBase.EmploymentRecord`** | ViewPage |

> 📌 **结论**：入职 / 转正 / 调动 / 离职 / 退休 / 兼职 **不是六个对象，而是同一个「任职记录」对象的六个视图**，
> 靠 **业务类型（异动类型）** 字段区分，各视图有自己的默认过滤条件与按钮集。
> 这与手册中「每次业务新生成一条任职记录」完全一致，互相印证。
>
> **复刻含义**：不要为入职/调动/离职各建一张表。应建**单一任职记录表 + 异动类型 + 版本链**，
> 六个业务页面是同一对象上的不同视图与按钮集合。

### 2.2 ⭐⭐ 「调动前」字段的实现方式（关键建模点）
`调动前部门` 的字段编码是 **`\7642614b-…\63595ea5-…~TenantBase.EmploymentRecord.OIdDepartment`**
—— 与「调动后部门」**是同一个字段** `OIdDepartment`，只是前面带了**实体关系路径**（两段 GUID）。

> **结论**：原站的「调动前 XX」**不是独立存储的字段**，而是**通过实体关系指向上一条任职记录的同一字段**。
> 这与「任职记录是版本链」完全自洽：前值 = 链上前一个版本的同名字段。
>
> **复刻含义**：不要为每个字段建「调动前/调动后」两列。前值应从版本链上一条记录取，
> 否则会出现前值与历史记录不一致、且向后更新逻辑无法实现。
>
> 同时说明字段引用语法支持 **`\<关系ID>\<关系ID>~<应用.对象.字段>`** 的跨对象路径表达。

### 2.4 ⭐ 本租户实际启用的调动按钮（20 个）
| 类别 | 按钮 |
|---|---|
| 申请类 | `调动申请`、`跨部门调动申请`、`跨公司调动申请`、`职务职位调整申请`（**出现 2 次**）、`职级调整申请`、`外派申请`、`他人调动申请` |
| 直接操作 | `调动`、`调动处理` |
| 批量类 | `批量调动`、`批量申请`、`批量调动申请(一单)`、`批量调动申请(多单)`、`批量发起调动交接` |
| 导入导出 | `导入调动记录`、`导入`、`下载模板`、`导出数据` |
| 其他 | `调动发起电子签署` |

**观察**：
1. **`职务职位调整申请` 出现两次** —— 实证了手册所说「一个调动类型会有多个同名按钮，需看功能按钮描述确定场景」。本租户确实存在同名按钮，复刻时必须支持"同名不同场景"的按钮配置。
2. **`外派申请`、`跨公司调动申请`** 不在官方预置类型（调动申请/跨部门/职务职位/职级/跨业务单元/调入/调动类型1-7）中，
   推断为本租户用 **调动类型 1–7** 自定义出来的。→ 印证「调动类型可租户自定义」。
3. **`批量调动申请(一单)` vs `(多单)`** 是两种批量语义：合并为一个审批单 vs 拆成多个审批单。这是需求里必须写死的差异。

## 附：开关参数对象 `TenantBase.Switch` 的结构（G-024，2026-09-22 🟢 配置证据）

来源：`GetMetaFieldList?metaObjName=TenantBase.Switch`（标准字段 70 个，只读）

| 类别 | 字段 | 说明 |
|---|---|---|
| 身份 | `SwitchType`（单选列表）、`Name`（含日、法、英、繁体）、`Classification`（分类）、`SortNumber`（排序号） | 每种开关一条记录，用 SwitchType 编号寻址（即鲁班页 `SwitchTypes=<n>`） |
| 主开关 | `IsEnable`（是否启用） | — |
| 作用范围 | `ApplicableOrg`（适用部门范围，说明原文：“开启功能后，仅在适用部门范围生效”）、`OrganizationControl`（不显示的部门） | **开关可以只对部分部门生效** |
| 通用参数槽 | `CommonRadio1–4`、`CommonInt1–2`、`CommonSingleChoice1–2`、`CommonMultipleFields`/`CommonMultipleFields1`、`CommonTextArea1`、`CommonTimeHHMM`、`CommonEmployeeMulti`、`CommonPictureAttachment1`、`ConfigFirst`/`ConfigSecond`、`CommonConfig`、`AdvancedSetting` | 不同 SwitchType **复用同一批通用字段**，各自解释含义 |
| 专用参数 | 如 `ChangeRecordSupportOrgRole`（调整组织角色时生成组织变更记录，对应 SwitchType 98）、`TransferSalaryItemRange`（调动前后薪资项目显示范围）、`DutyTransfer*`（职责转交 5 项）、`*SyncJobHistory`（入职、调动、离职同步工作履历）、`GenerateJobNumStage` / `RestartJobNumStage` / `TraineePositiveJobNumStage` / `LaborToInner`（工号生成时机）、`DismissionReEntryRuleSetting`（重聘和返聘判定规则） | — |

**结论（G-024）**：对象上**没有任何字段声明依赖**，例如 SwitchType 95 依赖「任职信息联动薪资范围」。依赖只写在页面说明文字里，由业务代码隐式处理。
→ 建议差异 **D-007**：复刻版的开关元数据增加 `depends_on`（前置开关 + 期望值）。保存时校验，并在界面上把失效的开关置灰、给出原因。
→ 复刻数据模型：`switch(type PK, enabled, applicable_org_ids[], params JSON, classification, sort)`。参数改用按 type 定义的 JSON Schema，不照搬“通用字段槽”的做法（这是原站为了兼容元数据平台的妥协）→ 属于实现建议，不改变业务行为。
