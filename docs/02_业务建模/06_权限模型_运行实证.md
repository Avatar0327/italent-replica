## 1. 权限模型的实际数据结构

### 1.1 授权记录（对象 `UserFramework.UserPermissionV2`）
一条授权记录的字段：**姓名 ｜ 邮箱 ｜ 手机号码 ｜ 身份 ｜ 管理单元 ｜ 产品 ｜ 操作(编辑/撤销)**

- 本租户共 **10,955 条** 授权记录
- 视图 `UserFramework.UserPermissionViewV2`，列表视图 `UserFramework.SingleObjectListView.UserPermissionListV2`，搜索视图 `UserFramework.Search`
- 默认过滤：`UserType=3（内部员工）`、`StaffStatus=1,2（在职、待确认）`
- 默认排序：`ModifiedTime desc, CreatedTime desc`
- 页面按钮：`新增`｜`撤销`｜`查看身份说明`｜`导入权限`｜`导出权限`｜行级 `编辑`/`撤销`

> 核心结构：**一条记录 = 一个用户 × 一个身份 × 该身份覆盖的每个应用各自的管理单元**。
> 同一用户持有 N 个身份 = N 条记录。

### 1.2 管理单元（数据范围）的三种表达 ⭐
实测到的三种写法，**不同应用用不同的范围维度**：

| 表达形式 | 实例 | 含义 |
|---|---|---|
| `默认管理单元` | `目标管理：默认管理单元` | 系统默认范围 |
| `<租户/集团名>` | `任务：北京SR样板间`、`标签库：华夏集团` | 按租户/集团单元 |
| `组织范围【<组织名>(<编码>)(包含下级)】` | `组织员工：组织范围【HT公司(zz10224)(包含下级)】` | **组织树范围 + 是否含下级** |
| `薪资组范围【<组1>(编码)(包含下级)，<组2>(编码)(包含下级)】` | `薪酬管理：薪资组范围【HT薪资组2(HT2)(包含下级)，HT薪资组1(HT1)(包含下级)】` | **薪资组范围，可多选** |

> ⚠️ **复刻关键**：数据范围不是一个全局"组织范围"字段，而是**按应用各自定义范围维度**。
> 薪酬用"薪资组"，组织员工用"组织"，其他用"管理单元"。对象模型必须支持 **应用 → 范围维度 → 范围值(多)+含下级标志**。
> 一个身份（如"部门负责人"）横跨 31 个应用，**每个应用单独指定管理单元**。

### 1.3 集团化结构实证
A0 的授权中同时出现 `华夏集团` 与 `北京SR样板间` 两级管理单元；管理员列表中廖国江的管理单元是 `华夏集团`，其余多数是 `北京SR样板间`。
→ 印证手册中「集团化」章节：**管理单元存在层级**，不是单一租户。

### 7.2 身份「配置权限」的完整结构 ⭐（G-018）

入口：应用配置 → 身份管理 → 某身份「配置权限」。共 8 个页签：**菜单组 / 页面权限 / 对象权限 / AI权限 / 默认详情页 / 报表权限 / Ocean主题权限 / BI设计器权限**。

**对象权限**：每个身份维护一张「对象清单」，可 新增/删除 对象。实测规模：人事管理员（组织员工）209 个对象，其中含 `CadreTalent.*` 等跨应用对象；部门负责人 601 个对象，其中组织员工应用 116 个。每个对象有三类子权限：

| 子权限 | 结构 | 任职记录 `TenantBase.EmploymentRecord` 实测 |
|---|---|---|
| **字段权限** | 每个字段有「查看」「编辑」两个勾选框；弹窗原文：“当前字段权限配置，对列表和表单均会生效” | 共 274 个字段。两个身份都是 274 个可查看、258 个可编辑。另有 16 个系统字段的「编辑」列是禁用状态，不能勾选（创建人/修改人/时间、工作流实例Id、当前审批人、部门_路径/层级、入职日期年/月/日等） |
| **功能权限** | 每个按钮一个「查看」勾选框；按钮按 **级别** 分为 列表 / 列表行 / 详情页 / 应用页 | 共 349 个按钮。**人事管理员勾选 274 个，部门负责人勾选 67 个**（明细见下） |
| **数据操作权限** | 新增、编辑、删除 三项，每项在 开启/关闭 中单选；原文：“配置身份对数据的新增、编辑、删除权限” | 两个身份三项都是开启 |

功能权限对比（导出 `01_证据/导出/身份对比_任职记录_功能权限_349.tsv`）：

| | 部门负责人 ✅ | 部门负责人 ❌ |
|---|---|---|
| 人事管理员 ✅ | 55（申请类、打印、审批同意/不同意、办理交接、编辑） | 220（直接执行类：调动/离职/转正/退休、删除任职、批量编辑、导入导出等） |
| 人事管理员 ❌ | 12（合并待办 `MergeTodo*` 的同意/驳回/转交/批量编辑、实习转正申请、评定提名等） | 62（废弃按钮、劳务转正式、店长控制台等） |

**关键发现**：
1. 本租户**没有用字段权限来区分这两个身份**，两者字段权限完全相同；**区分靠的是功能权限（按钮）加数据范围**。部门负责人只拿到“发起申请 + 审批”类按钮，拿不到“直接变更”类按钮。这正是“申请制 vs 直改制”在权限层的落点。
2. 同一业务动作有多个按钮编码（如调动：`Employment.Tranfer` 直接调动、`EmploymentRecord.TransferApproval` 他人调动申请、`MyTransition.transferApproval` 本人调动申请、`EmploymentRecord.LineOp.TransferApproval` 行级调动申请，以及调动类型 1–7 各一套）。**复刻的按钮权限粒度必须是“按钮编码 × 级别”**，不能只做到“动作”。
3. 字段权限只有 查看/编辑 两档，作用于列表和表单。本次核对的弹窗里**没有看到按 PC/移动端分设的选项**（结论为受限验证）。
4. 数据操作权限（增/改/删）是对象级的总开关，和功能按钮叠加生效。两者都满足时动作才可执行：这是由结构推断的🟡，未做负向实测。

→ 权限判定公式（复刻用）：**可见数据 = 数据范围（管理单元）∩ 对象在身份对象清单中；可见字段 = 字段查看；可执行动作 = 功能按钮勾选 ∧ 数据操作权限开启 ∧ 字段编辑（针对写入字段）**。其中「∧」的组合方式标 🟡，待负向实测。

### 7.3 动态授权规则（G-010，手册层）

来源：`HRSAAS / 4751390`《动态授权功能介绍》，路径 企业设置 → 权限管理 → 动态授权（按 §7.1 只有租户管理员可见）。

- **定义**：按条件表达式自动给员工授予身份。条件可以取组织（如 组织单元.店长）、人员、任职字段（如 任职记录.职务），多条件之间可以用 and（交集）或 or（并集）组合。**字段值变化后自动授权**；列表页的「执行规则」按钮会对存量员工补跑一次。
- **规则 1**：用户同时命中多条规则时，所有规则对应的身份都会授给他（取并集）。
- **规则 2（数据范围例外）⭐**：如果某人是因为**担任某些组织的角色**而通过动态授权拿到身份，并且他的管理单元是【默认管理单元】，那么他**可以查看和操作这些组织的数据**。这条规则只适用于人事、假勤。
- **规则 3**：用户授权里如果又给这个动态身份设置了管理单元，那么数据范围 = 所设管理单元。同样只适用于人事、假勤。
- **对 REQ-PRM-002 的修正**：「默认管理单元 = 无数据范围」这条 fail-closed 规则**有一个例外**：当身份来自“组织角色型”动态授权，且业务属于人事或假勤时，默认管理单元 = 该角色所担任的组织。这条例外已写入需求基线。

### 7.4 管理单元与「数据权限设置」（G-020 部分）

- 来源：`HRSAAS / 2262640`《管理单元功能介绍》。**管理单元 = 管理组织范围 + 管理人员范围**：
  - 组织范围：决定前台能看到哪些部门/员工的数据；
  - 人员范围：按筛选条件动态算出人员集合。**这项需要租户管理员在后台打开对应开关，页面才会受人员范围控制**（默认不生效）。
  - 管理单元支持 **停用/启用**（启用时可以改上级和名称），可以**导出数据范围**供审计使用；管理单元详情页有新旧两种样式，新样式需要灰度开通。
- 来源：`HRSAAS / 2262642`《数据权限设置》。这个页面**只有招聘产品在用**：它控制招聘角色对职位、渠道等对象是否受管理单元约束。**这个页面不在首版范围**。
- G-020「能否排除某棵子树」手册没有提到；后续从 `UserFramework.Mou` 的字段结构确认**不支持排除**（`11` §14，G-020 已关闭）。

### 7.6 A0 的数据范围（G-007）

- 这 74 条里出现的范围：

| 应用 | 范围值 | 持有该应用的身份数（示例） |
|---|---|---|
| 组织员工 | 具名管理单元「北京SR样板间」 | 8 条（标准版系统管理员（组织员工）、评定管理员、管理员（盘点与发展）、部门负责人、经理…） |

| 假勤管理 | 具名管理单元「北京SR样板间」 | 5 条 |

- 结论：
  1. A0 能看到全部员工，是因为它的管理单元（租户根单元）**恰好覆盖**全部组织，**不是**因为存在一个“全部数据”标志。

  3. 审批中心的范围比组织员工高一级（集团 vs 租户）。**同一个用户在不同应用可以处于不同的集团层级。**

## 8. C-003 复核：经理 / 员工身份是“天然拥有”还是“显式授权”（2026-09-28，A0 只读）

取证：身份目录（`MetaDataManagement.ProfileV2`，388 个身份，其中 265 个标准、23 个自定义已读）＋ 用户授权全量扫描（16,981 条“用户 × 身份”记录，只统计各身份条数，不导出个人信息）。

**两层身份并存：**

| 层 | 身份（编码） | 目录说明 | 授权记录数 | 性质 |
|---|---|---|---|---|
| **自助身份**（按关系自动持有） | 员工 `StaffRole`、经理 `Manager`、部门负责人 `DepManager`、虚线经理 `DottedLineManager`、HRBP `StandardHRBP`、门店店长 `Shopowner`、行政助理、劳务人员 | 「自助身份-经理」等 | 员工 5,516；部门负责人 767；经理 700；虚线经理 21 | 跨 30 个应用，管理单元为默认（租户全体）。数量级与“有下级的人 / 负责人 / 全员”吻合，是系统**按汇报关系、负责人关系自动物化**的授权记录（手册所说的“天然拥有”）🟢 数量 / 🟡 自动机制 |
| **应用级扩展身份**（须显式授予） | 经理身份（组织员工）`CommonManager`、部门负责人身份（组织员工）`DepartmentLeader`、普通员工身份（组织员工）`CommonEmployee` | 「若要查看并使用组织人事产品的经理 / 员工自助端功能，须对此身份配置相应权限」 | 10 / 7 / 3 | 标准身份，需要人工授予，本租户几乎不用 |

另见：租户自建了「勿动_全量经理自助」「勿动_全量部门负责人自助」等**自助身份副本**（自定义），说明自助身份可以复制后改权限。

**结论**：
- 手册说的“天然拥有”指的是**自助身份层**；身份目录中“须配置相应权限”的是**应用级扩展身份**。两者不矛盾，C-003 转为复刻方案的选择。
- 经理自助功能的实际来源是「经理 / 部门负责人」自助身份（其授权范围包含组织员工）。扩展身份只在少数账号上叠加。
- ⏸ 未做：用一个“只持有自助身份、没有扩展身份”的经理账号登录核对前台按钮。这需要该账号的密码，按约定不做。

## 9. 系统用户与人员档案的绑定（Q-M0-30，2026-10-04，A5 只读）

> 来源：企业设置 → 用户管理（内部员工 / 外部用户 / 全部用户）列表与详情，对象 `UserFramework.User`；列表接口与详情接口的字段取值；任职记录接口的 `UserID`。手册正文因用户社区会话过期未读，只用了目录标题（CustomerKB「企业设置 / 用户管理」、HRSAAS「用户管理」）。

| 事实 | 原站证据 |
|---|---|
| **租户内用户 = 人员，同一个 ID** | 测试员工 F3 的用户详情 `OId = 411912305`，与其全部任职记录的 `UserID` 相同；组织汇报路径 `Path` 也由这些 ID 串成 |
| 另有一层**全局登录账号** | 同一详情另有 `AccountId`（与 OId 不同），登录用户名 / 登录手机号挂在这层；用户管理里“设置用户名”“邀请绑定登录手机号”改的就是它 |
| 内部员工账号随人员档案产生 | 开通组织员工后，用户管理的新增按钮是「前往新增员工」，即没有“先建账号、再绑人”的入口；详情的“任职信息”（部门、工号、职务、直线经理）直接取自人员档案 |
| 用户类型 | `UserType`：3 = 内部员工（4149），2 = 外部用户（112）；本租户共 4261 个（含已删除标记过滤后） |
