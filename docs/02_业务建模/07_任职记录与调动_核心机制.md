# 任职记录与调动 — 核心机制规格

> 来源类型：**官方文档正文**（登录态读取）｜ 采集：2026-09-22
> 文档：`继承字段和不继承字段介绍`(112855715, 更新 2026-02-12)、`任职周期介绍`(112855717, 更新 2023-08-07)、`各调动类型表单自动带出调动前任职的规则说明`(223510946, 更新 2025-07-13)
> 验证状态：**官方文档已读，本租户运行行为未验证**
> 优先级：**P0** —— 这是整个人事模块最不可猜的机制，实现错了全盘皆错。

## 1. 任职记录的基本模型

**核心范式**：员工的每一次人事业务（入职/转正/调动/晋升/组织调整/离职/退休）都**新生成一条任职记录**，
新记录**只写入本次业务实际变更的字段**，其余字段从上一条记录**继承**。

> 这意味着：任职记录是**事件溯源式的版本链**，不是"一条员工记录被反复 UPDATE"。
> 复刻时若用单表 UPDATE 实现，将无法支持历史快照、生效日期追溯与向后更新。

举例（官方原文）：
- 转正 → 仅维护转正生效日期 + 人员状态「试用」→「正式」；部门/职位/职级等未变更字段**继承**
- 调动 → 仅维护调动生效日期 + 调动后的部门、直线经理；其余**继承**

## 2. 任职周期（Employment Cycle）

| 项 | 规则 |
|---|---|
| 定义 | 员工从入职到离职的全生命周期 = 一个任职周期 |
| 载体字段 | **`StaffID`**（同一任职周期内该字段值相同） |
| 判定 | 完成一次入职 + 一次离职 = 完成一个任职周期，与在职时长无关 |

### 2.1 是否更新 `StaffID` 的业务矩阵（官方原表）
| 业务类型 | 变动类型 | 是否更新 StaffID |
|---|---|---|
| 入职 | 新增入职 | **是** |
| 入职 | 实习转正 | 否 |
| 入职 | 重聘入职 | **是** |
| 入职 | 退休返聘 | **是** |
| 转正 | — | 否 |
| 调动 | — | 否 |
| 组织调整 | — | 否 |
| 离职 | — | 否 |
| 退休 | — | 否 |

> ⚠️ **继承只发生在同一任职周期内；跨任职周期的信息一律不继承。**
> → 重聘/退休返聘会开启新周期，因此不会继承上一段任职的任何信息。

## 3. 字段继承规则

### 3.1 系统预置字段
- **合同协议**：全部字段均继承
- **任职记录**：以下字段继承（未列出的字段不继承，或有按场景自动赋值的逻辑）

| 中文名 | 字段编码 |
|---|---|
| 部门 | `OIdDepartment` |
| 职位 | `OIdJobPosition` |
| 职务 | `OIdJobPost` |
| 职级 | `OIdJobLevel` |
| 职等 | `OidJobGrade` ⚠️ 原站拼写为小写 `d` |
| 工作地点 | `Place` |
| 直线经理 | `POIdEmpAdmin` |
| 虚线经理 | `POIdEmpReserve2` |
| 人员类别 | `EmploymentType` |
| 人员来源 | `EmploymentSource` |
| 用工形式 | `EmploymentForm` |
| 身份类型 | `IdentityLabel` |
| 职务序列 | `OIdJobSequence` |
| 专业条线 | `OIdProfessionalLine` |
| 预留3 / 4 / 5 | `POIdEmpReserve3` / `4` / `5` |
| 是否关键人员 | `IsKeyPerson` |
| 预置编制维度 1–5 | `Dimension1` … `Dimension5` |
| 工号 | `JobNumber` |
| 备注 | `Remarks` |
| 业务单元 | `StdBusinessUnitID`（见调动带出规则，继承清单中未单列） |

### 3.2 自定义字段的继承开关
**配置路径**：组织员工 → 设置 → 公共设置 → **不继承字段设置**（文档 39387557）
- 支持对象：**任职记录**、**合同协议**
- 操作：新建 → 选择信息集（任职记录/合同协议）→ 选择该对象的自定义字段
- 效果：加入该设置的字段，在转正、调动、离职/退休、实习转正、组织调整、合同变更、续签等业务中，新记录**不会**从上一条带入其值

### 3.3 继承逻辑判定矩阵（官方原表）
| 是否设为非继承 | 业务类型 | 继承逻辑 |
|---|---|---|
| 否（默认继承） | 入职 | **不继承** |
| 否（默认继承） | 转正/调动/实习转正/组织调整/离职/退休 | ① 表单拖出该字段 → 取**该任职记录生效日期的上一条任职记录**上同字段的值<br>② 表单未拖出 → 该任职记录**生效时**取生效日期上一条记录的值 |
| 是（非继承） | 入职 | **不继承** |
| 是（非继承） | 转正/调动/实习转正/组织调整/离职/退休 | ① 表单拖出**且可编辑** → 值为**空**<br>　（若为**只读或隐藏**，**仍会带出**上一条的值）<br>② 表单未拖出 → 赋值为**空** |

> ⚠️ **「只读/隐藏仍继承，可编辑才置空」是极易实现错的边界**，必须写入验收场景。

### 3.4 生效日期的定义
| 业务 | 生效日期 |
|---|---|
| 转正 | 转正日期 |
| 调动 | 调动日期 |
| 离职 | **最后工作日的第二天** |
| 其他 | 以此类推 |

### 3.5 注意事项（官方原文）
1. 新增**待入职、入职**业务时，新生成的任职记录**不受字段继承设置控制，所有字段均不继承**
2. 任职记录字段未做过继承设置时，**默认为「继承」**；发起转正/调动/实习转正/离职/退休表单时，该字段默认显示当前或上一条记录的信息
3. 租户新建的自定义表单，**必须设置分组为「转正」「调动」「实习转正」「离职」「退休」**，才能按上述默认值规则显示

## 4. 调动表单注册表（官方，带元数据视图名）

**前置设置项**：组织人事 → 设置 → 调动 → 其他设置 → **【发起调动时调动后任职自动带出为调动前信息】**
开启后，调动后任职记录的大部分可继承字段、调动后薪资字段、调动后合同字段，都默认带出人员当前任职/薪资/合同的对应值，填写人可再调整。

| 表单 | 元数据视图名 |
|---|---|
| 调动类型 1~7 多表单[人事申请] | `TenantBase.PersonalCustomized1~7TransferMultiFormView` |
| 跨部门调动多表单[人事申请] | `TenantBase.PersonalCrossDepartmentTransferMultiFormView` |
| 职级调整多表单[人事申请] | `TenantBase.PersonalJobLevelTransferMultiFormView` |
| 职务职位调整多表单[人事申请] | `TenantBase.PersonalJobPostTransferMultiFormView` |

> 📌 **这组 `Personal*` 表单是决定性证据**：原站为「员工自助发起的人事申请」单独准备了调动表单。
> 结合 A2/A3 拥有 `自助服务 → 人事申请` 入口、官方称普通员工身份「可以发起转正、**调动**、离职等业务申请」，
> 调动闭环的真实形态确认为：**员工/经理通过人事申请发起 → 审批流转 → HR 执行生效**。
> 原先设想的「调出方 HR 发起 → 调入方 HR 接收」**不是原站的主路径**。

### 4.3 调动带出的关联对象
| 关联 | 可带出字段 | 带出值来源 | 条件 |
|---|---|---|---|
| `任职记录.LU_调薪管理 → 调薪管理.主键` | 编码以 **`Adjusted`** 结尾的字段（含系统标准字段与自定义字段） | 调动日期薪资档案上的同编码字段 | **仅当表单配置了【是否调薪】且切换为【是】**；未配置则不带出 |
| `任职记录.LU_调动变更合同 → 合同协议.主键` | 所有业务字段 | 调动前合同的同编码字段 | — |

> 📌 揭示了 Lookup 关联命名规范：`LU_<关联名>`，并且**调动可同时联动调薪与合同变更**——三个对象在一次业务中一起生成新版本。

### 4.4 带出规则的设计意图
「本场景的高频调整字段不默认带出」——例如职级调整表单不带出职级/职等，因为那正是本次要改的值。
**分组=调动的自定义表单，所有字段均可带出**（不做场景例外）。

# 附：向后更新（任职记录追溯变更）机制

> 来源：官方文档 `向后更新`（pageId 112855719，更新 2023-08-07）｜ 优先级 **P0**

## A1 业务问题
任职记录通常按时间顺序从前往后生成，自动继承。但存在**后发生的业务先落地、先发生的业务后补录**的场景。

官方举例：2022-01-01 全公司组织架构调整，但直到 02-01 才落地系统；期间 01-15 已生成一条工作地变更的调动记录。
若 02-01 补录 01-01 的组织变更（改了部门、直线上级、职位），**必须把这些变更同步到 01-15 那条记录上**，否则当前生效任职的数据就是错的。

→ 把插入记录的变更同步到**生效日期更晚**的后续任职记录，称为 **任职记录向后更新**。

## A2 触发条件（两个条件同时满足）
① 有对应的字段变化
② 业务开始日期**之后**存在该人员**当前任职周期**内审批状态 = `生效` 的数据；
　 或业务开始日期**及之后**存在该人员当前任职周期内审批状态 = `审批通过` / `审批中` / `草稿` / `已驳回` 的数据

> 📌 由此得到**任职记录审批状态枚举**：`草稿` / `审批中` / `审批通过` / `已驳回` / `生效`
> 📌 `审批通过` 与 `生效` 是**两个不同状态** —— 审批与生效确实分离。

## A3 各业务的触发时机（官方原表）
| 发生数据插入的业务 | 向后更新时机 | 其他条件 |
|---|---|---|
| 直接调动 / 转正；定时任务直接转正 | **数据保存时** | — |
| 转正考核 / 试用期考核审批通过且结果为转正 | 插入转正记录时 | — |
| **调动 / 转正申请**、批量调动申请、第三方 | ① 审批通过后**立刻生效**（审批通过日期 ≥ 调动日期）<br>② 提前审批完成（审批通过日期 < 调动日期）→ 由**定时任务**在调动日期当天生效 | — |
| 对外接口插入调动 / 转正 | 数据插入成功时 | — |
| 导入调动；导入任职-新增模式（调动/转正/组织调整） | 数据导入成功时 | 【是否更新后续任职】**未填或填「是」**才向后更新 |
| 对外接口插入调动 / 转正 / 组织调整 | 数据插入成功时 | — |

> ⭐ **直接回答「保存是否直接生效、审批与生效是否分离」**：
> - **直接调动** → **保存即生效**，无审批
> - **调动申请** → 走审批；审批通过日期 ≥ 调动日期则**立即生效**；审批通过日期 < 调动日期则**挂起，由定时任务在调动日期当天生效**
> → 复刻必须实现**定时生效任务**，不能把"审批通过"等同于"生效"。

## A4 向后更新的字段范围
所有**未标记不继承**的任职记录自定义字段，加上标准字段：
`OIdDepartment` 部门、`OIdJobPosition` 职位、`OIdJobPost` 职务、`OIdJobLevel` 职级、`OidJobGrade` 职等、`Place` 工作地点、`POIdEmpAdmin` 直线经理、`POIdEmpReserve2` 虚线经理、`EmploymentType` 人员类别、`EmploymentSource` 人员来源、`EmploymentForm` 用工形式、`IdentityLabel` 身份类型、`OIdJobSequence` 职务序列、`OIdProfessionalLine` 专业条线、`POIdEmpReserve3/4/5` 预留3/4/5、`IsKeyPerson` 是否关键人员、`Dimension1~5` 预置编制维度、`JobNumber` 工号

## A5 更新规则 ⭐⭐ 最易实现错的部分
**不是无条件覆盖，而是「值匹配替换」**：

> 设插入记录把 部门 从 `OD` 改为 `人事部（北京公司）`、直线经理 从 `栗宗人` 改为 `王大海`：
> - 后续任职记录中**部门 == `OD`（变动前的值）** 的 → 替换为 `人事部（北京公司）`
> - 后续任职记录中**部门 ≠ `OD`** 的 → **不替换**
> - 直线经理同理
>
> 若插入记录某字段与前一条**相同**（例如职务都是"高级经理"），则该字段**不向后更新**。

### A5.1 四条特殊规则（官方原文）
| # | 规则 |
|---|---|
| ① | 字段用到的**部门、人员、职务等值已停用**时，**不向后更新** |
| ② | **职位和部门同时变化**时，只更新后续数据中**职位和部门与变动前的值都相同**的记录 |
| ③ | **职务 / 职位 和 职务序列会一并向后更新** |
| ④ | **「是否部门负责人」字段不自动向后更新** —— 官方理由：该字段相关业务复杂，更新不符合预期时**会引发数据泄露问题**；需业务插入后**手动更新** |

> 📌 规则④ 是一条明确的**安全设计**，复刻时必须保留，不能"顺手"一起更新。

## A6 导入历史任职时可关闭向后更新
批量导入新增历史任职 / 批量导入历史调动时，可把 **【是否更新后续任职】填「否」**（需在导入模板中配置出该字段）。
使用场景：企业梳理上线前的历史任职，仅用于统计分析，不希望影响当前正确的任职数据。

## A7 编辑任职时的向后更新
需**同时满足**四个条件：
① 有对应字段变化
② 被编辑的任职记录为**当前或未来生效的主职任职记录**（📌 说明存在「主职 / 兼职」之分，且只有主职触发）
③ 被编辑记录的开始日期之后存在该人员当前任职周期内 `生效` 的数据；或开始日期及之后存在 `审批通过`/`审批中`/`草稿`/`已驳回` 的数据
④ 从**特定入口**编辑

### A7.1 编辑入口支持矩阵（官方原表）
| 编辑入口 | 是否支持向后同步 |
|---|---|
| 页面单条编辑任职记录（任职记录视图-编辑、员工详情页编辑等） | ✅ 支持 |
| 编辑人员、编辑实习生（员工信息+任职记录合并表单） | ✅ 支持 |
| 批量导入内部员工/实习生（编辑模式、有则编辑无则新增模式） | ✅ 支持 |
| 对外接口编辑任职 | ✅ 支持 |
| 调动交接，编辑到已生效的调动记录时 | ✅ 支持 |
| **批量编辑任职记录** | ❌ **不支持**（官方建议改用导入方式） |

> 📌 「批量编辑不触发向后更新，批量导入却会触发」是一条反直觉的差异，必须写入需求与验收。
