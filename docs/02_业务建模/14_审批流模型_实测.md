### 2.1 ⭐⭐⭐ 审批人全部是动态表达式（核心发现）

**没有任何一个节点把审批人写死成具体的人**，全部通过**对象关系路径**动态解析：

| 节点 | 审批人变量名 | 解析路径（variable） | 中文路径 |
|---|---|---|---|
| 开始 | `流程所有者` | `owner` | — |
| **调出部门负责人审批** | **调动前部门负责人** | `bc:TenantBase.EmploymentRecord:UserID` → `fcme:TenantBase:CurrentRecord:OIdDepartment` → `fcme:TenantBase:CurrentOrgInfo:PersonInCharge` | 任职记录 - 人员 - **最新任职记录** - 部门 - 部门基本信息 - 负责人 |
| **调入部门HRBP审核** | **调动后部门HRBP** | `bc:TenantBase.EmploymentRecord:OIdDepartment` → `fcme:TenantBase:CurrentOrgInfo:HRBP` | 任职记录 - 部门 - 部门基本信息 - **HRBP** |
| **调入部门负责人审批** | **调动后部门负责人** | `bc:TenantBase.EmploymentRecord:OIdDepartment` → `fcme:TenantBase:CurrentOrgInfo:PersonInCharge` | 任职记录 - 部门 - 部门基本信息 - 负责人 |
| **单人审批** | **调动后一级组织负责人** | `bc:TenantBase.EmploymentRecord:OIdDepartment` → `fcme:TenantBase:CurrentOrgInfo:FirstLevelOrganization` → `fcme:TenantBase:CurrentOrgInfo:PersonInCharge` | 任职记录 - 部门 - 部门基本信息 - **一级组织** - 部门基本信息 - 负责人 |

**审批人类型**：全部为 `type: "4"`，`typeText: "汇报关系"`，`source: "object_fetch"`，`isCommVariable: true`

#### 关键含义
1. **「调出方 / 调入方」的语义由表达式中的对象路径表达**，不是由角色或账号表达：
   - **调出方** = `人员 → 最新任职记录 → 部门 → 负责人`（取**当前**任职的部门）
   - **调入方** = `任职记录 → 部门 → 负责人`（取**本次调动记录**的部门，即调动后部门）
   > 同一个"部门负责人"概念，靠**从哪条任职记录取部门**来区分调出与调入。设计非常精巧。
2. **组织对象上的 `负责人` `HRBP` 字段是审批路由的关键字段** —— 它们不只是展示字段，而是**流程参与人的来源**。
   → 复刻时这两个字段必须是结构化的人员引用，不能是文本。
3. 支持**多级向上路由**：`一级组织负责人` 通过 `FirstLevelOrganization` 再取 `PersonInCharge`。
4. 表达式语法：`bc:<对象>:<字段>` 起步，`fcme:<应用>:<上下文>:<字段>` 逐级跳转。
   - `bc` = 业务上下文起点
   - `fcme:TenantBase:CurrentRecord` = 当前（最新）记录
   - `fcme:TenantBase:CurrentOrgInfo` = 当前组织信息

### 2.2 每个审批节点的可配置项（assignKeys 实测）
```
approverSelectType            审批人选择方式
assignee                      审批人表达式
noAssignee / noAssigneeSkipConfig          审批人为空时的处理
isSameAssigneeSkip / sameAssigneeSkipOutcome / sameAssigneeSkipConfig
                              相同审批人是否跳过 + 跳过后的结果
isHistorySameAssigneeSkip / historySameAssigneeSkipOutcome / historySameAssigneeSkipConfig
                              历史相同审批人是否跳过 + 结果
appointApproverExtends        指定审批人扩展
```
> 📌 **「审批人为空」「相同审批人跳过」「历史相同审批人跳过」是三个独立的内建机制**，
> 各自可配置跳过结果。这类规则在复刻时极易遗漏，但在真实组织里高频触发
> （例：调出与调入是同一个负责人；某部门没有 HRBP）。
> 本流程中 `noAssignee.type = "0"`（「无操作」）—— 即审批人为空时**不做处理**（行为待验证，G-030）。

## 4. ⭐ 流程版本与配置变更的影响（产品 UI 原文）

> 页面原文（流程列表页）：
> 「问题四：修改了流程配置，在审批流程中为何没有生效？
> 　回答：修改流程配置后点击**发布**，流程状态变为"发布"才能生效，**并且只对新发起的流程生效，对已经发起审批的流程不生效**。」
>
> 流程详情页原文：
> 「已发布流程的属性不支持修改，如需修改流程属性，可以【编辑最新版本】后发布流程，**流程发布后只对新发起的流程生效，对已经发起的审批流程不生效**。」

### 4.1 由此确立的规则（直接回答用户提出的「配置变更对运行中流程的影响」）
| 规则 | 内容 |
|---|---|
| R1 | 流程有**版本**概念（本流程为版本 1） |
| R2 | **已发布的流程属性不可直接修改**，必须「编辑最新版本」产生新版本后再发布 |
| R3 | 发布后的新版本**只对新发起的流程实例生效** |
| R4 | **已在途的审批实例继续使用其发起时的流程版本** |
| R5 | 流程状态：`草稿` → `发布`；另有 `废弃`（从可用流程列表移除） |

> **复刻硬要求**：流程实例必须**绑定发起时的流程版本快照**，不能引用"当前最新定义"。
> 否则改一次流程会让所有在途审批的节点/审批人发生变化，与原站行为不符且不可解释。

## 8. 补充取证（2026-09-22）

### 8.1 流程匹配与优先级（G-029 ✅，官方文档）
来源：SenFAQ/76185961、SenFAQ/75367871、CustomerKB/231703283、CustomerKB/168722460

| 发起方式 | 匹配规则 |
|---|---|
| 指定**流程定义 ID** | 只看这一条定义：满足发起条件就发起，不满足则**发起失败** |
| 指定**流程编码**（调动按钮就是这种，见 13 §流程编码绑定） | 找这个编码下**已发布**的定义：满足发起条件就发起，不满足则**发起失败**，**不会回退**到其他编码 |
| 指定**实体编码** / 自由流 | 取该实体下所有已发布的流程，按 **排序号从小到大** 逐条判断发起条件，第一个满足的发起 |
| 集团版 | 先找**全局**且满足条件的流程，再找对应 **BU** 的流程，最后按排序号 |

**分支优先级（另一个概念）**：分支分为 无条件分支、条件分支、Else 分支。
- 优先判断优先级数值**小**的分支；条件满足（无条件分支视为满足）就只激活这一条分支。
- ⚠️ **如果多个分支优先级相同且条件都满足，原站随机激活其中一条。**
- Else 分支只在其余分支全部不满足时才激活，与它自身的排序值无关。

→ 本流程的「优先级 -1」属于流程级的排序号语义，排序号越小越先匹配。调动走的是流程编码发起，所以这个排序号**对调动不起作用**。 ⚠️ **本句已被 §8.6 推翻**：本租户调动申请实际按实体发起，排序号对调动起作用。
→ **建议差异 D-005**：原站“同优先级分支随机激活”行为不确定。建议复刻时**配置阶段禁止保存同优先级的条件分支**，或按连线创建顺序确定性选择。

### 8.2 抄送与消息（G-033 ✅，配置证据）
来源：流程定义 `5eb0f5e9-…` 的 LAYOUT JSON（只读 GET）

- `isCopySend=true`（仅 调入部门HRBP 节点）的含义是：该节点审批人的操作栏里多出一个系统动作「**抄送**」（`action=CopySend`，意见“显示，不必填”），由审批人**手动选人抄送**。流程定义里**没有固定的抄送对象清单**。
- 同一节点还配了**消息规则**：动作 = 同意时，给 **流程所有者 - 员工本人** 同时发邮件和站内消息，模板为「【员工】调动通知」（`TenantBase.Ygddtz`），不发短信，“在审批区显示”开启。
- 同节点还开启了 转交（`isRetweeted`）、撤回（`isRetrieve`）、加签（`isAddSign`），并有系统动作「驳回到发起人」「提交到驳回节点」。其余审批节点这些开关均为关闭。

→ 复刻数据模型：节点上是 **动作开关集**（抄送/转交/撤回/加签/跳转）加 **消息规则数组**（触发动作 → 渠道[邮件/短信/站内] → 模板 → 接收人表达式）。

### 8.4 本租户调动发起的推论（G-039 🟡）

### 8.5 G-039 实测结果：推翻 §8.4 的推断（2026-09-27 🟢）

### 8.6 C-006 根因：调动申请为什么落到离职流程（2026-09-27 🟢 以 A0 只读查看配置）

取证：`setting-cloud.italent.cn/WorkFlow/ProcessV2/GetProcessList?app=TenantBase&processStatus=0`（117 条可用流程，其中挂在“任职记录”对象上的有 40 条）、`ProcessV2/Get?...&operateType=LAYOUT`（版本节点）、`ProcessNewestVersionLook`（最新版本 ID）。全部为 GET，没有修改任何配置。

**证据链**
1. 实例 `a7f8d16c` 使用的流程定义 `2b269659` 与「**新版标准离职流程**」（编码 `DimissionProcessNew`，流程 ID `3c9c7195`，审批类型 = 离职）的节点完全一致：直接上级、HR访谈，审批人引用公共变量“新版标准离职流程-直接上级 / HR访谈”。这条流程的“最近发起日期”恰好是 2026-09-27。
2. 该流程**没有任何发起条件**。任职记录上没有发起条件的共 4 条：新版标准离职（离职）、新版标准调动（调动）、新版标准转正（转正）、离职标准流程（审批类型为“废弃”）。其余 36 条都带「流程编码 等于 X」一类条件。
3. 列表中这条流程的版本状态显示「草稿」，最新版本 ID = `3c9c7195`（`ProcessNewestVersionLook`）。但实例用的是另一个版本 `2b269659` → **列表上的“版本状态”只代表最新版本；较早发布的版本在新版本处于草稿时仍然生效**。
4. 2026-09-20 20:00:44–49，账号 405788408（A0）在 5 秒内批量修改了 28 条任职记录流程，它们的最新版本全部变为草稿。这次批量修改早于本项目在该租户的写操作记录（W-001 起），不是本项目所为；从时间和 A1 专用流程的描述（“发布前必须限制精确测试员工”）推断，目的是“只保留 A1 专用调动流程可用”。但由于旧发布版本仍然生效，**这个目的实际没有达到**。
5. 匹配方式：调动按钮不是“按流程编码精确发起”（官方 FAQ 的第 2 种方式），而是**按实体（任职记录）发起**（第 3 种方式）：按优先级从小到大扫描已发布的流程，第一个满足发起条件的即发起，**与审批类型无关**。“流程编码”只是发起时传入的一个变量，供发起条件引用。
   - 优先级 -1 的 A1 专用流程：被调动人不是 A1，不满足；
   - 优先级 0：带“流程编码=其他值”条件的流程不满足；**无条件的流程全部满足**，结果选中了新版标准离职流程。
6. 为什么在同为优先级 0、同为无条件的「新版标准调动流程」和「新版标准离职流程」之间选了离职：配置上看不出来（可能是两者的发布版本状态不同，也可能是并列时的内部排序）→ 🟡 未定。

**结论**
- C-006 → 🟡 部分解决：“为什么会落到非调动流程”已查清（按实体扫描 + 无条件流程兜底 + 旧发布版本仍生效）；“并列时为什么是离职而不是调动”未定。
- **修正 G-034 的结论**：原记录“4 条调动流程中仅 1 条发布”是按列表的版本状态得出的，**不可靠**。列表状态 = 最新版本状态，旧发布版本可能仍在生效。
- 修正 §8.1：官方 FAQ 的三种发起方式都存在；本租户的**调动申请走的是按实体发起**，所以优先级（排序号）**对调动起作用**。§8.1 中“排序号对调动不起作用”的说法作废。

4. 优先级相同且都满足条件时，必须有确定性规则（D-005）。

### 8.7 G-030 实测：中间节点审批人为空（2026-09-28 🟢 写入测试）
- 构造：清空调入部门 ORG_001 的 HRBP（W-012），推进 A1 在途调动（实例 `c7d01091`）；A0 以管理员身份把 A2、A3 的任务**转交**给自己并同意（W-014、W-015）。
- **实例的实际节点顺序**：开始 → 调出部门负责人 → **调入部门负责人** → **调入部门 HRBP** → 结束，**没有**“一级组织负责人”节点。这与 §2 按流程定义记录的顺序（HRBP 在前、另有单人审批节点）不同。→ 实例使用的是发起时的流程版本，§2 记录的是后来编辑过的最新版本。**再次印证：流程修改只影响新发起的实例。**
- **结果**：到达“调入部门 HRBP 审核”时，审批人表达式解析为空（`noAssignee = 无操作`）→ 任务**自动派给流程的异常管理员**「廖国江（异常管理员）」，节点处于审批中。流程**没有卡死，也没有自动跳过**。
- 结论：“无操作”的实际含义是**不做自动处理，转交异常管理员人工处理**。复刻要求：
  1. 流程定义必须配置**异常管理员**（必填）；
  2. 节点审批人为空时：按节点配置执行“自动跳过 / 自动同意 / 转异常管理员”三选一，默认“转异常管理员”；
  3. 异常管理员的待办上要标明“（异常管理员）”，便于识别；
  4. 验收 AC-APV-04 预期更新为“派给异常管理员”。

## 9. 时效、不计时时段与流程仿真（2026-09-28 只读补证，G-031 / G-032）

### 9.1 时效（⏸ DEC-035 首版不做，模型备用）
- 流程级“时效设置”对全部节点生效；节点可选 同步流程级 / 启用节点级 / 不启用。
- 计划时长 `timeSpan`：1–9999 小时。
- 到期前：提前 N 小时提醒（N < 计划时长），可重复（间隔小时、次数 ≤ 20，间隔 ≤ N），选消息模板与渠道（邮件 / 消息 / 短信）。
- 到期后：发送催办消息（可重复）或**自动审批**（执行节点上指定的动作，如同意 / 驳回）。到期前、到期后至少选一种。
- 不计时时段（流程级）：国家法定节假日及双休日、每日某时段，两者可同时选；不计入计划时长。流程侧不引用假勤工作日历。
- 复刻预留：节点上保留 `timeSpan / timeEffectBefore / timeEffect / period` 字段结构，首版不计算。

### 9.2 催办（首版随审批中心）
- 流程级开关 + 节点级覆盖；详情页“催办”按钮给当前节点未审批人发通知。

### 9.3 流程仿真（✅ DEC-036 首版做）
- 单流程仿真：设计器内，任意状态的流程可仿真；输入数据项（自动汇总发起条件、连接线条件、节点执行人、消息接收人中用到的变量）→ 输出发起日志与流程日志（节点状态 通过 / 警告 / 异常、预计审批人、审批区域、条件核算结果、消息接收人）；数据全部虚拟，不发消息与待办。
- 按对象仿真：选 审批类型 + 对象 + 范围（已发布版本 / 最新版本）→ 输入数据 → 按优先级依次核算该对象下所有流程的发起条件，命中的继续核算提交条件；可跳到对应流程的仿真详情。
- 复刻按 D-009 / DEC-017 先按业务类型过滤，仿真结果同时展示“按原站规则会命中哪条”与“按复刻规则命中哪条”，便于迁移核对。
