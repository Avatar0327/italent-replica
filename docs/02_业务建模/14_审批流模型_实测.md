### 2.1 ⭐⭐⭐ 审批人全部是动态表达式（核心发现）

**没有任何一个节点把审批人写死成具体的人**，全部通过**对象关系路径**动态解析：

| 节点 | 审批人变量名 | 解析路径（variable） | 中文路径 |
|---|---|---|---|
| 开始 | `流程所有者` | `owner` | — |
| **调出部门负责人审批** | **调动前部门负责人** | `bc:TenantBase.EmploymentRecord:UserID` → `fcme:TenantBase:CurrentRecord:OIdDepartment` → `fcme:TenantBase:CurrentOrgInfo:PersonInCharge` | 任职记录 - 人员 - **最新任职记录** - 部门 - 部门基本信息 - 负责人 |
| **调入部门HRBP审核** | **调动后部门HRBP** | `bc:TenantBase.EmploymentRecord:OIdDepartment` → `fcme:TenantBase:CurrentOrgInfo:HRBP` | 任职记录 - 部门 - 部门基本信息 - **HRBP** |
| **调入部门负责人审批** | **调动后部门负责人** | `bc:TenantBase.EmploymentRecord:OIdDepartment` → `fcme:TenantBase:CurrentOrgInfo:PersonInCharge` | 任职记录 - 部门 - 部门基本信息 - 负责人 |
| **单人审批** | **调动后一级组织负责人** | `bc:TenantBase.EmploymentRecord:OIdDepartment` → `fcme:TenantBase:CurrentOrgInfo:FirstLevelOrganization` → `fcme:TenantBase:CurrentOrgInfo:PersonInCharge` | 任职记录 - 部门 - 部门基本信息 - **一级组织** - 部门基本信息 - 负责人 |

**审批人类型**：全部为 `type: "4"`，`typeText: "汇报关系"`，`source: "object_fetch"`，`isCommVariable: true`

#### 关键含义
1. **「调出方 / 调入方」的语义由表达式中的对象路径表达**，不是由角色或账号表达：
   - **调出方** = `人员 → 最新任职记录 → 部门 → 负责人`（取**当前**任职的部门）
   - **调入方** = `任职记录 → 部门 → 负责人`（取**本次调动记录**的部门，即调动后部门）
   > 同一个"部门负责人"概念，靠**从哪条任职记录取部门**来区分调出与调入。设计非常精巧。
2. **组织对象上的 `负责人` `HRBP` 字段是审批路由的关键字段** —— 它们不只是展示字段，而是**流程参与人的来源**。
   → 复刻时这两个字段必须是结构化的人员引用，不能是文本。
3. 支持**多级向上路由**：`一级组织负责人` 通过 `FirstLevelOrganization` 再取 `PersonInCharge`。
4. 表达式语法：`bc:<对象>:<字段>` 起步，`fcme:<应用>:<上下文>:<字段>` 逐级跳转。
   - `bc` = 业务上下文起点
   - `fcme:TenantBase:CurrentRecord` = 当前（最新）记录
   - `fcme:TenantBase:CurrentOrgInfo` = 当前组织信息

### 2.1.1 复刻新增“直接上级”（F-028 / DEC-230）

- 表达式 `direct_manager`，中文名 **直接上级**，与现有五种表达式并存。
- 取流程主体员工在租户当前业务日期上的**最新生效主职任职记录**的 `directManagerId`；复用主职版本链读模型（当前表受 `primary` 约束），不读取申请中的新经理或未来未生效记录。字段可由任职维护或 F-006 / DEC-011 职位同步写入，解析端统一读取最终生效快照。
- 无主体 / 无经理、经理已离职或账号停用均按 DEC-054 / DEC-098：首节点提交报错且不建实例，中间节点转异常管理员。经理为发起人或异动员工时按 DEC-058 / DEC-068 自审跳过，不计同意，转该经理的直线经理或异常管理员。
- 定义、发布、单人 / 会签节点和虚拟仿真均支持；仿真通过 `relations.direct_manager` 提供虚拟账号，自审回避仍用 `managers`，不查真实人员关系。
- 出厂 `standard_leave` 的“直接上级”节点使用新表达式；其他预置部门负责人节点并非该近似，不替换。已有安装与发布版本不自动重写。
- **待取证 [#95](https://github.com/Avatar0327/italent-replica/issues/95)**：原站“直接上级”的直线经理字段 / 汇报关系、主职 / 兼职及主体选择来源，先按本次派发指定口径实现，不能把上述复刻口径视作原站实测。
- 验收：AC-APV-38～42，见追溯表 M 节。

### 2.2 每个审批节点的可配置项（assignKeys 实测）
```
approverSelectType            审批人选择方式
assignee                      审批人表达式
noAssignee / noAssigneeSkipConfig          审批人为空时的处理
isSameAssigneeSkip / sameAssigneeSkipOutcome / sameAssigneeSkipConfig
                              相同审批人是否跳过 + 跳过后的结果
isHistorySameAssigneeSkip / historySameAssigneeSkipOutcome / historySameAssigneeSkipConfig
                              历史相同审批人是否跳过 + 结果
appointApproverExtends        指定审批人扩展
```
> 📌 **「审批人为空」「相同审批人跳过」「历史相同审批人跳过」是三个独立的内建机制**，
> 各自可配置跳过结果。这类规则在复刻时极易遗漏，但在真实组织里高频触发
> （例：调出与调入是同一个负责人；某部门没有 HRBP）。
> 本流程中 `noAssignee.type = "0"`（「无操作」）—— 即审批人为空时**不做处理**（行为待验证，G-030）。

## 4. ⭐ 流程版本与配置变更的影响（产品 UI 原文）

> 页面原文（流程列表页）：
> 「问题四：修改了流程配置，在审批流程中为何没有生效？
> 　回答：修改流程配置后点击**发布**，流程状态变为"发布"才能生效，**并且只对新发起的流程生效，对已经发起审批的流程不生效**。」
>
> 流程详情页原文：
> 「已发布流程的属性不支持修改，如需修改流程属性，可以【编辑最新版本】后发布流程，**流程发布后只对新发起的流程生效，对已经发起的审批流程不生效**。」

### 4.1 由此确立的规则（直接回答用户提出的「配置变更对运行中流程的影响」）
| 规则 | 内容 |
|---|---|
| R1 | 流程有**版本**概念（本流程为版本 1） |
| R2 | **已发布的流程属性不可直接修改**，必须「编辑最新版本」产生新版本后再发布 |
| R3 | 发布后的新版本**只对新发起的流程实例生效** |
| R4 | **已在途的审批实例继续使用其发起时的流程版本** |
| R5 | 流程状态：`草稿` → `发布`；另有 `废弃`（从可用流程列表移除） |

> **复刻硬要求**：流程实例必须**绑定发起时的流程版本快照**，不能引用"当前最新定义"。
> 否则改一次流程会让所有在途审批的节点/审批人发生变化，与原站行为不符且不可解释。

### 8.1 流程匹配与优先级（G-029 ✅，官方文档）
来源：SenFAQ/76185961、SenFAQ/75367871、CustomerKB/231703283、CustomerKB/168722460

| 发起方式 | 匹配规则 |
|---|---|
| 指定**流程定义 ID** | 只看这一条定义：满足发起条件就发起，不满足则**发起失败** |
| 指定**流程编码**（调动按钮就是这种，见 13 §流程编码绑定） | 找这个编码下**已发布**的定义：满足发起条件就发起，不满足则**发起失败**，**不会回退**到其他编码 |
| 指定**实体编码** / 自由流 | 取该实体下所有已发布的流程，按 **排序号从小到大** 逐条判断发起条件，第一个满足的发起 |
| 集团版 | 先找**全局**且满足条件的流程，再找对应 **BU** 的流程，最后按排序号 |

**分支优先级（另一个概念）**：分支分为 无条件分支、条件分支、Else 分支。
- 优先判断优先级数值**小**的分支；条件满足（无条件分支视为满足）就只激活这一条分支。
- ⚠️ **如果多个分支优先级相同且条件都满足，原站随机激活其中一条。**
- Else 分支只在其余分支全部不满足时才激活，与它自身的排序值无关。

→ 本流程的「优先级 -1」属于流程级的排序号语义，排序号越小越先匹配。调动走的是流程编码发起，所以这个排序号**对调动不起作用**。 ⚠️ **本句已被 §8.6 推翻**：本租户调动申请实际按实体发起，排序号对调动起作用。
→ **建议差异 D-005**：原站“同优先级分支随机激活”行为不确定。建议复刻时**配置阶段禁止保存同优先级的条件分支**，或按连线创建顺序确定性选择。

### 8.2 抄送与消息（G-033 ✅，配置证据）
来源：流程定义 `5eb0f5e9-…` 的 LAYOUT JSON（只读 GET）

### 8.6 C-006 根因：调动申请为什么落到离职流程（2026-09-27 🟢 以 A0 只读查看配置）

取证：`setting-cloud.italent.cn/WorkFlow/ProcessV2/GetProcessList?app=TenantBase&processStatus=0`（117 条可用流程，其中挂在“任职记录”对象上的有 40 条）、`ProcessV2/Get?...&operateType=LAYOUT`（版本节点）、`ProcessNewestVersionLook`（最新版本 ID）。全部为 GET，没有修改任何配置。

**证据链**
1. 实例 `a7f8d16c` 使用的流程定义 `2b269659` 与「**新版标准离职流程**」（编码 `DimissionProcessNew`，流程 ID `3c9c7195`，审批类型 = 离职）的节点完全一致：直接上级、HR访谈，审批人引用公共变量“新版标准离职流程-直接上级 / HR访谈”。这条流程的“最近发起日期”恰好是 2026-09-27。
2. 该流程**没有任何发起条件**。任职记录上没有发起条件的共 4 条：新版标准离职（离职）、新版标准调动（调动）、新版标准转正（转正）、离职标准流程（审批类型为“废弃”）。其余 36 条都带「流程编码 等于 X」一类条件。
3. 列表中这条流程的版本状态显示「草稿」，最新版本 ID = `3c9c7195`（`ProcessNewestVersionLook`）。但实例用的是另一个版本 `2b269659` → **列表上的“版本状态”只代表最新版本；较早发布的版本在新版本处于草稿时仍然生效**。
4. 2026-09-20 20:00:44–49，账号 405788408（A0）在 5 秒内批量修改了 28 条任职记录流程，它们的最新版本全部变为草稿。这次批量修改早于本项目在该租户的写操作记录（W-001 起），不是本项目所为；从时间和 A1 专用流程的描述（“发布前必须限制精确测试员工”）推断，目的是“只保留 A1 专用调动流程可用”。但由于旧发布版本仍然生效，**这个目的实际没有达到**。
5. 匹配方式：调动按钮不是“按流程编码精确发起”（官方 FAQ 的第 2 种方式），而是**按实体（任职记录）发起**（第 3 种方式）：按优先级从小到大扫描已发布的流程，第一个满足发起条件的即发起，**与审批类型无关**。“流程编码”只是发起时传入的一个变量，供发起条件引用。
   - 优先级 -1 的 A1 专用流程：被调动人不是 A1，不满足；
   - 优先级 0：带“流程编码=其他值”条件的流程不满足；**无条件的流程全部满足**，结果选中了新版标准离职流程。
6. 为什么在同为优先级 0、同为无条件的「新版标准调动流程」和「新版标准离职流程」之间选了离职：配置上看不出来（可能是两者的发布版本状态不同，也可能是并列时的内部排序）→ 🟡 未定。

**结论**
- C-006 → 🟡 部分解决：“为什么会落到非调动流程”已查清（按实体扫描 + 无条件流程兜底 + 旧发布版本仍生效）；“并列时为什么是离职而不是调动”未定。
- **修正 G-034 的结论**：原记录“4 条调动流程中仅 1 条发布”是按列表的版本状态得出的，**不可靠**。列表状态 = 最新版本状态，旧发布版本可能仍在生效。
- 修正 §8.1：官方 FAQ 的三种发起方式都存在；本租户的**调动申请走的是按实体发起**，所以优先级（排序号）**对调动起作用**。§8.1 中“排序号对调动不起作用”的说法作废。

## 9. 时效、不计时时段与流程仿真（2026-09-28 只读补证，G-031 / G-032）

### 11.3 审批中编辑（Q-M0-40）
- 原站机制（手册 133530957、185008911）：节点「编辑表单内容」（原“关联业务操作”）给某个出口动作（通常是「同意」）绑定对象详情页上的业务按钮；审批人点该动作时弹出按钮表单，可改数据后再流转。另一种方式是在预置审批详情页上开启「同意」按钮的编辑。节点配置了编辑表单后**不能批量审批、快速审批**；同时配置加签时，只有本节点原审批人能编辑，加签人不能（手册 255656540）。
- 本租户实际绑定：离职「直接上级」、转正「上级评价 / 员工自评」、调动 `TransferProcessNew`「调入直线上级审批」的「同意」都绑了 `ApprovalingEdit`（“编辑：用于审批中编辑、不校验职责转交”）；交接流程绑了 `AgreeWithJobHandover` / `HandleHandover` / `CheckTransferHandoverV2`（办理交接校验）。
- **员工子集变更**：原站支持审批中编辑——给子集变更流程的「同意」绑定「审批中编辑」，审批人改的值随审批流转，**审批通过后按改后的值更新子集**；审批页显示“原内容 + 变更后内容”（仅标准预置详情页显示变更标识，手册 226689077）。已发起变更申请的子集行在审批结束前不能再编辑（手册 243630918）。本租户两条子集变更流程（「员工能力评估」`A12321214`、预置子集 1）**都没有绑定**，即本租户未开启。
- 审批人改了哪些内容，原站从任职记录的「操作日志」查看（CustomerKB 155650752），审批记录本身不展示字段差异。

### 11.4 加签（Q-M0-41 / 46）
- 节点开关 `isAddSign`；加签类型由**节点类型**决定（手册 133531112、65175917，FAQ 63832480、138118007、129269776）：

| 节点 | 可用加签 | 流转顺序 | 何时算通过 |
|---|---|---|---|
| 单人审批 | 前加签、后加签（**不支持并加签**） | 前加签人 → 原审批人 → 后加签人；多个加签人按选择顺序**依次**审批 | 前加签人全部同意后回到原审批人；原审批人同意后后加签人依次审批，全部完成才离开节点 |
| 会签审批 | 并加签；2024-06 起另有前加签（按应用灰度，组织人事 2024-07 支持） | 并加签人与原审批人同时审批、无先后 | 并加签人**计入节点流转规则**（如“1 人同意即通过”时，加签人同意即可通过） |

- 加签人的操作：2026-04 前只有同意 / 不同意；2026-04 起，**只要原节点开了驳回到发起人 / 驳回到历史节点，加签人也能驳回到发起人 / 历史节点**（手册 255656540）。后加签一提交就写入操作记录（2024-06）。加签可配待办，不支持配消息（SenFAQ 63832457）。节点勾选加签时必须有「同意」出口线（CustomerKB 109710739）。
- 本租户开启加签的节点：调动 `TransferProcessNew` 两个节点、测试流程「调入部门HRBP审核」、入职两个节点、新增员工两个节点、转正「上级评价」、离职「HR访谈」、个人信息变更「HRBP审核」、组织调整两个节点。

### 11.5 流程配置权与流程管理员（Q-M0-42）
- **流程配置**（新建 / 编辑 / 发布 / 废弃）：在配置中心「流程任务管理」里，由**租户管理员 / 系统管理员**操作（手册 133531112、112859839）；从审批中心进入的流程配置页只读（手册 210141934）。审批详情页的“小飞机”（跳到后台流程配置）也只有租户管理员 / 系统管理员可见。
- **实例干预**：审批中心应用的三个身份（手册 2262724、83001813、83001824、103252575），本租户身份目录里有前两个：

| 身份 | 菜单 | 能做什么 | 范围 |
|---|---|---|---|
| 业务管理员（审批中心） | 流程管理 | 批量催办 / 转交 / 撤销 / 导出；单条流程干预、撤销、看版本 / 状态 / 催办历史 / 流程图；管理员委托 | **受其管理单元的组织范围限制** |
| 流程管理员（审批中心） | 流程监控 | 导出；单条流程干预、撤销、看版本 / 状态 | 租户内**全部**流程 |
| OA 业务管理员（审批中心） | 审批管理 | 只看、导出 | 全部，不受管理单元限制 |

- A5 有「流程管理」菜单，列表在途 734 条、全部 1,354 条。手册对菜单归属说法不一：2262724 写流程管理员用「流程监控」，103252575 写流程管理员和业务管理员都能看到「流程管理」。审批中心「设置 - 开关参数」（如隐藏跳过节点）由流程管理员、业务管理员操作。
- 结论：原站**配置权与干预权分属两类主体**（管理员类别 vs 审批中心身份），与 DEC-102 一致。差异：原站「流程管理员」看全租户、不受范围限制；复刻按硬规则“数据范围默认空”不设无范围的身份。

### 11.6 相同 / 历史相同审批人跳过的结果（Q-M0-43）
- 设计器文案：「与上一节点审批人相同时 / 与历史节点审批人相同时 / 审批人与 X 相同时 / 审批人为空时」各自二选一：**不自动审批（需人工操作）**，或**自动审批，执行〔动作〕**。
- 〔动作〕下拉的取值（前端代码 `getChildren`）：**「跳过」**（仅单人审批节点、且节点有「同意」出口线时出现；实际沿「同意」线走，处理人记为“系统”）+ 节点的**全部出口线动作**（同意、不同意、自定义动作）；并行中间节点去掉「不同意」。存储为 `xxxSkipOutcome`（动作值）+ `xxxSkipOutcomeText`（显示名）+ `xxxSkipConfig.skipType`（0 = 未启用或其他动作，1 = 同意，2 = 跳过）。
- 「跳过」是 2024-10 新增的（手册 194769096）：跳过和自动同意的记录可由审批中心开关「隐藏跳过节点 / 隐藏自动同意节点」在审批页和打印中隐藏（只对之后发布的流程生效，流程图仍显示）。
- 本租户只有 2 条流程启用了相同审批人跳过：「调动类型1申请流程」的派入部门 HRBP 节点（相同 + 历史，结果“跳过”）、「员工能力评估」（历史，结果“跳过”）。
- 仍未确认：“历史节点”是否跨驳回重提的轮次计算（手册只说明流程干预、跳转后，之前的节点不再算历史节点，120981507）。

### 11.7 审批人无账号 / 离职（Q-M0-44）
- 手册 112859839：节点找不到审批人时转异常管理员；**找到了审批人但其已离职，同样转异常管理员**；若节点配了“审批人为空时指定审批人”，先找指定审批人，都找不到才转异常管理员。
- 手册 138118019：节点配置“审批人为空时自动执行同意”时，审批人离职后该节点会**自动通过**。
- 待办生成后审批人才离职的，不会自动改派，需由业务管理员在流程管理中转交（手册 112862735、103979029）。
- ~~仍未确认~~ **2026-10-06 写入实测（W-509～W-512，用户同意）在职但账号未激活**：把 A1 的直线经理临时改为在职、账号「未激活」的测试员工 EST_EMP_01（W-509），A1 发起「他人调动申请」EST_EMP_02 → Q48B、10-27（W-510）。流程「开始（A1）→ 直接上级 → HR访谈 → 结束」中，**直接上级节点的处理人为异常管理员“森豆”**，不是 EST_EMP_01（流程图当前节点、调动中员工“当前审批人”列一致）。即：解析到的审批人账号未激活，按**审批人为空**处理，转异常管理员——与已离职同口径，DEC-098 首版做法与原站一致。随后撤销申请（W-511，记录作废）并把 A1 直线经理改回空（W-512）。账号**停用**（已激活后停用）的情形未单独测，推定同口径。
- 附带发现：这张「他人调动申请」的流程发起日志显示，按优先级逐个匹配后**命中的是「新版标准离职流程」（DimissionProcessNew）**，而不是「新版标准调动流程」（TransferProcessNew，待匹配）；这解释了此前审批详情页用离职布局（W-495 必填“最后工作日”）的现象。说明本租户调动申请实际走的是离职流程的定义（配置问题，非产品规则）。

### 11.8 驳回后重提是否重新匹配流程（Q-M0-45）
- 原站**不重新匹配**：驳回（到发起人 / 上一步 / 历史节点）只是把当前节点调回被驳回节点，**重提后仍走原流程的原版本**（CustomerKB 150013180）；重提也**不会再次触发“流程发起”触发器**（SenFAQ 157549143）。同理，撤回后重提也走原版本（CustomerKB 150013177）。
- 重提方式由驳回节点的「驳回后提交方式」决定：逐级审批 / 直达本节点 / 驳回人选择（默认逐级审批）（手册 124880977、130056690）。

### 11.9 审批意见的可见性（Q-M0-47）
- 原站**默认所有能打开审批详情页的人都能看到全部审批意见和沟通**。
- 节点级开关「审批记录查看权限」（`info.feedType = 1`）：勾选后，**本节点审批人**进入详情页时隐藏「审批记录」和「沟通记录」；开始节点上勾选则隐藏的是**发起人**看到的（手册 36798578、65175917；前端文案“节点审批人 / 流程发起人进入详情页时，隐藏「审批记录」和「沟通记录」”）。2026-04 起移动端同时隐藏当前审批人（手册 255656540）。
- 例外：消息接收人从消息进入详情页时，若不是该节点审批人，**不受此开关限制**，仍能看到。
- 没有“某条意见仅部分人可见”的私有意见设置；控制的是“谁看不到”，不是“这条意见给谁看”。本租户已读的 21 条流程都**没有**勾选该开关。

## 12. 会签节点的流转规则与驳回（Q-M0-56 / 57，2026-10-04，A5 只读）

来源：本租户 132 个人事流程（`WorkFlow/ProcessV2/GetProcessList` + `Get?operateType=LAYOUT`），其中 12 个流程含会签节点（`category = CotSign`、`activityType = 4`）；流程设计器前端代码中的节点属性面板；手册 133530906、148439094、150013213、148439308、132516004、129269776、129271967。

### 12.1 流转规则（Q-M0-56）
- 节点属性面板「流转规则」，副标题“多人审批时采用的审批方式”，单选三项（字段 `info.transitionRuleType`）：

| 选项 | 值 | 保存时生成的 `transitionRules` | 面板提示 |
|---|---|---|---|
| 任一人同意即可（**新拖入的会签节点默认**） | `"2"` | 节点每个出口动作都是“整数 1” | 任一审批人不同意，流程流转结束 |
| 需所有人同意 | `"1"` | 「同意」= “百分比 100%”，其他出口动作 = “整数 1” | 任一审批人不同意，流程流转结束 |
| 自定义审批方式 | `"0"`（非 1/2 都按自定义显示） | 用户逐行设置 | — |

- 自定义：表格每行对应节点**出口连线上的一个动作**（由连线去重得到，如「同意」「不同意」；节点没勾选「不同意」就没有这一行，手册 148439308）。每行选「整数」或「百分比」：
  - 整数：≥ 1 的整数，“输入 3 表示只有 3 人点击了该操作，流程才会流转到下一节点”；
  - 百分比：≤ 100% 的百分数（可带两位小数），**向上取整**，“输入 50%，有 5 人审批则至少 3 人点击了当前操作才流转”。
- 某个动作的点击人数先达到它的规则，节点就沿该动作的连线流转。例如手册 132516004：规则为“整数 1”时一人同意即流转；改成“百分比 100%”才需全部同意。
- 并加签人计入流转规则（手册 129269776，`14` §11.4）。
- 本租户实际配置（19 个会签节点）：任一人 / 自定义整数 1（同意、不同意各 1 人）最多；需所有人同意（同意 100%、不同意 1 人）若干。没有使用其他整数或百分比的节点。

### 12.2 驳回与不同意（Q-M0-57）
- **不同意**：是出口连线动作，受流转规则约束。两种预设下「不同意」都是“整数 1”，即**任一人不同意，节点立即沿「不同意」连线流转**（本租户都连到结束 = 流程结束，面板提示“任一审批人不同意，流程流转结束”）。自定义时可把「不同意」设成 N 人或百分比。
- **驳回**（驳回到发起人 / 上一步 / 历史节点）：是节点开关（`isRejectToStart` 等），不是出口连线，**不进入流转规则表**。会签节点可以勾选这些驳回操作（手册 129271967 列出会签节点可勾选：驳回到发起人、驳回到上一步、驳回到历史节点、不同意）。
- 推断（未写入实测）：会签中任一人点「驳回」即整单驳回，不等其他人。依据是驳回不参与流转规则计数，这和单人节点的驳回语义一致。其他未处理人的待办如何收回，没有运行证据；手册 94537992 只说明已完成的会签节点在详情页显示“实际审批过的人”。
- 若要确证驳回的运行表现，需在原站建一个含会签节点的测试流程并发起审批（写入，需先征得用户同意）。
- **2026-10-07 写入实测（方案 B，W-521～525）**：测试调动流程 `5eb0f5e9…` 新版本 20261007083012959（定义 `67033acb…`）在「开始」后加会签节点（需所有人同意，审批人 A0 + A5，勾选驳回到发起人、不同意）。A0 为 A1 发起调动（实例 `54f2063f…`，W-524 由用户本人提交），会签节点同时给 A0、A5 各派一条待办（流程快照 `assignesApprovalIn` 两人）。
  - A0 在 A5 尚未查看时点「驳回到发起人」（W-525）：会签节点**立即结束**（completeTime 08:53:58），不等 A5；实例状态 = **已驳回**，新生成一个「开始」节点派给发起人 A0（按钮：重新提交 / 删除 / 流程管理）。
  - A5 的待办被系统收回：流程管理「当前审批人」只剩 A0；流程快照里该会签节点的审批人只剩 A0（已处理），A5 **既不在待办也不在已取消列表**；「查看流程状态」中 A5 那行仍保留，状态“未查看”、无审批时间。进度条显示「会签审批：何份晓」，即只显示实际处理过的人（与手册 94537992 一致）。
  - 结论：**任一人驳回即整单驳回、其他人待办立即收回**，推断成立，与 F-003 / DEC-144 暂定口径一致。
  - 「不同意」在“需所有人同意”下的运行表现：重新提交被安全分类器拦截，**尚未实测**（配置证据仍为任一人不同意即流转）。
