# 试用期、转正与试岗：规格（R2-T02）

> 取证：2026-09-28，A0 只读。官方文档 🟡：HRSAAS 24248365、39387237/53/69/91、39387223、120194678、39387335、177410890、109725441/47/501、156569196/98、126747409/11/13、156569136。
> 本租户配置与数据：见 §6（待取证）。与 R1 的衔接：转正是任职版本链上的一种变动（`07`），审批走 R1 审批中心（`14`）。

## 1. 业务对象

| 对象 | 说明 |
|---|---|
| 任职记录（转正） | 变动类型 = 转正；人员状态 试用 → 正式；带 转正日期 |
| 试用中考核 / 转正考核 | 两类考核记录，各自一条审批流；字段：考核名称、考核日期、员工自评、经理评价（表现一般 / 满足预期 / 超出预期 / 未达到预期）、**转正意见**（正常转正 / 提前转正 / 延期转正 / 不通过 / 延期试用）、提前转正日期 |
| 试用期信息（员工信息 / 任职记录上） | 是否有试用期、试用开始日期、试用期（月）、预计试用结束日期、实际转正日期；入职表单上预计试用结束日期按入职日期 + 试用期（月）自动算，可手改（R2e6） |
| 自动发起规则（两套） | 自动发起试用期考核；自动转正 / 自动发起转正申请 |
| 试岗期信息 `OnTrialInformation` + 试岗考核 `OnTrialEvaluation` | 调动时设置；见 `21` |

## 2. 规则

### 2.1 试用期管理视图
| # | 规则 |
|---|---|
| PB-R1 | 视图：**即将试用到期**（30 天内到期且未发起转正考核 / 转正申请）、考核中、转正审批中、全部试用员工、已转正 |
| PB-R2 | 试用到期提醒通过定时任务（收件人：直线上级、HRBP 只收到自己相关的数据；按身份时按其权限范围） |

### 2.2 考核
| # | 规则 |
|---|---|
| PB-R3 | 试用中考核、转正考核：手动（选人批量发起）或自动发起；流程一般为 员工自评 → 经理评价；审批中可编辑（同意按钮关联“编辑”） |
| PB-R4 | **试用中考核**的转正意见 = **提前转正** → 审批完成时自动新增一条转正任职记录（生效日 = 提前转正日期，到期自动生效）；其他意见不生成记录 |
| PB-R5 | **转正考核**的转正意见 = 正常 / 提前 / 延期转正 → 审批完成时自动新增转正任职记录；不通过不生成 |
| PB-R6 | 以上自动生成**只对审批人审批时**选择的意见生效；审批通过后再编辑考核记录的转正意见，**不会**补生成或修改任职记录 |
| PB-R7 | 转正记录把人员状态由“试用”改为“正式”；时间轴上**晚于试用期生效日期**的后续任职记录一并改为“正式”（向后更新，`07`） |

### 2.3 转正
| # | 规则 |
|---|---|
| PB-R8 | 转正（直接，无审批）/ 转正申请（走审批）；可单个或批量；批量时可统一转正日期，不填则各按预计试用结束日期；批量申请 = **每人一条独立流程** |
| PB-R9 | **互斥校验**：试用中考核、转正考核、转正申请三者只要有一个在审批中，其余都不能发起，也不能直接转正或调整试用期信息<br>**例外**（R2e5 spec 第 79～86 行）：设置里有“试用期考核并行规则”两个开关（试用中考核流程并行规则、转正考核流程并行规则），**默认关**；打开后多出“选择可发起流程”多选。转正考核这一项的候选是转正考核、转正；试用中考核这一项，页面说明列了试用中考核、转正考核、转正，下拉候选未读到。勾选的流程在对应流程审批中时仍可发起；放行效果未验证（R2e5 没有保存开关）。复刻：互斥校验读取并行配置，出厂两项都关 |
| PB-R10 | 存在“审批通过但转正日期在未来”的转正记录时，不能调整试用期信息（须先删除该未生效记录） |
| PB-R11 | 已有生效的转正记录时，调整试用期信息时转正日期不能为空，且不能把“是否有试用期”改为否 |
| PB-R12 | 调整试用期：试用开始日期不能早于入职日期；预计结束日期不能早于开始日期；“是否有试用期”由是改否 → 人员状态直接变“正式” |
| PB-R13 | 修改转正记录的转正日期后，**之后的任职记录上的转正日期自动更新**<br>复刻做法（DEC-589，取 B）：转正单用专用改期命令改日期（复用迟到改期重排，业务 ID 不变，审计记原日期→新日期）；新日期须在本任职周期内；可跨过区间内的其他任职记录，并重算其人员状态（提前 → 正式，推后 → 回退试用）；区间内有离职、另一条转正或入职时拒绝并列出冲突记录；通用编辑入口仍不许改日期（DEC-231 不变） |
| PB-R14 | 导入试用信息（初始化用）：填了转正日期且早于今天 → 更新转正日期并把状态改为正式 |
| PB-R15 | 转正审批中可催办、转交、撤销（撤销只对转正申请，不对考核流程） |

### 2.4 自动发起（设置 > 转正）
| # | 规则 |
|---|---|
| PB-R16 | 两个开关：自动发起试用期考核、自动转正；各有多条规则，规则 = 适用组织范围 + 附加人员条件（员工信息 / 任职记录 / 合同公司的**白名单字段**及单选类自定义字段）+ 规则详情<br>（R2e5 spec 第 68～69 行）原站只有总开关，**单条规则没有启用 / 停用**，行操作：自动转正为编辑 / 复制 / 删除，自动考核为编辑 / 删除；**复刻增加单条启停**（偏离原站，复刻取舍，DEC-533②）。自动转正规则表单：适用组织范围*、附加范围（职务序列、工作地点、用工形式、人员类别）、业务处理规则*、发起人类型*、发送失败通知。规则有优先级，适用范围可取消“包含下级”（R2e6）。原站到点执行：R2e6 建规则后观察约 2 小时未执行，执行时刻仍未验证，转 R2e7（F-183，DEC-537①）隔夜补测。**复刻**（DEC-539①）：两类规则每天固定时点执行一次，另加“立即执行”按钮；R2e7 测出原站时刻后再对齐 |
| PB-R17 | 自动考核规则：考核名称、类型（试用中 / 转正）、**入职后第 N 天发起**（当天 = N 才发起）；失败通知规则中的发起人，找不到则通知系统管理员<br>R2e6：N 取 1～999（填 0 报“请设置1至999的整数”）；规则有优先级、附加条件（如试用期(月)）；发起人可按身份（如 HRBP） |
| PB-R18 | 自动转正规则：类型 = 自动转正（直接生成）或自动发起转正申请（到期当天或到期前 N 天；**≤ 当天的都会发起**，即补发）<br>R2e6：到期前天数取 0～999（空值报“请设置0至999的整数”）；原站规则表单没有名称字段，**复刻加“规则名称”**（偏离原站，复刻取舍，DEC-539②；配合 DEC-533② 单条启停便于区分） |
| PB-R19 | 适用对象：**内部员工**，当前生效**主职**为试用状态，开关已开，命中规则范围 |
| PB-R20 | 自动考核失败条件：本任职周期内存在 转正记录（审批中 / 通过 / 生效）或 审批中的考核 |
| PB-R21 | 自动转正失败条件：本任职周期内存在 转正记录（已驳回 / 不通过 / 作废 / 审批中 / 通过 / 生效）；转正考核（草稿 / 驳回 / 审批中 / 不通过 / 作废，或生效但意见 ≠ 正常转正）；试用中考核（审批中，或生效且意见 = 提前转正） |
| PB-R22 | 修改规则不影响已转正或已在转正流程中的人；删除规则不影响已发起的 |

### 2.5 试岗期（调动后）
| # | 规则 |
|---|---|
| PB-R23 | 调动时可设置试岗（方式、期限、开始日期 → 预计结束日期）；调动生效后出现在试岗期管理 |
| PB-R24 | 视图：试岗中（含未发起考核和考核中）、考核中、试岗不通过、试岗通过、全部 |
| PB-R25 | 试岗考核可单个或批量发起，员工自评 + 上级评价，审批中可编辑；**不通过时系统不自动调回**，由 HR 在调动管理中手动调回或另行调动 |

| PB-R27 | 数据权限：管理单元（组织、工作地、职级、法人公司多维组合） |

## 补充：DEC-709 转正申请 / 转正考核 的「暂存」草稿（2026-10-31，A0）

入口：组织员工 → 任职管理 → 试用期管理（即将试用到期页签）。用 ZZ_ 试用期人员测，没有提交；写入的测试文字最后已清掉。

| 表单 | 有没有暂存 | 原站表现 |
|---|---|---|
| 转正申请（行操作「转正申请」，表单 `TenantBase.PositiveMultiFormNewView`） | ✅ 有，底部按钮为「取消 / 暂存 / 提交」 | 见下面的步骤 |
| 转正考核（勾选人员后点「发起转正考核」） | ❌ 没有，只有「取消 / 提交」 | 字段：考核名称、考核日期、考核说明、上传附件、考核内容、总等级 |

**转正申请暂存实测步骤**
1. 在「转正评价」里填了一段 ZZ_ 测试文字，点「暂存」。页面没有提示，表单也不关闭。
2. 点「暂存」时只发出一个请求：`POST /api/v2/data/temporaryData`。
   - 地址参数：`functionButtonCode=EmploymentRecord_LineOp_PositiveApproval`、`formViewCode=TenantBase.PositiveMultiFormNewView`、`businessDataId=<员工 UserID>`。
   - 请求体是整张表单的字段值（`metaFields`），带 `checkRequired:false`，所以必填项不填也能暂存。
3. 点「取消」关闭表单，没有“是否放弃”之类的确认。
4. 再次点同一人的「转正申请」，表单顶部出现提示「已带出上次暂存信息」和一个「点击清除」按钮，填过的文字原样带回。
   - 草稿是随表单定义一起返回的：`GET /api/v2/UI/FormView` 的返回里带 `_isHaveTemporaryData:"true"`，字段值里也有暂存的内容。
5. 浏览器本地没有存这份草稿：localStorage、sessionStorage 里都找不到填写的文字；本站点没有 IndexedDB 库，也没有 Cache Storage。
6. 「我的审批 → 我的申请」列表里看不到暂存的草稿（暂存不会生成审批单）。

**结论**
- 草稿存在服务端，按「操作按钮 + 表单 + 被转正的员工」保存。
  - 换浏览器或换设备，应能带出同一份草稿；这一点是从存储位置推断的，没有用第二台设备实测。
  - 别的操作人打开同一员工的转正申请时，能不能看到这份草稿，也没有测（🟡）。
- 同一员工只保留一份草稿：再次暂存会覆盖上一份。
- 清理情况：测试文字已清空，并重新暂存覆盖掉。
  - 服务端仍有一份不含测试文字的草稿（只有系统默认带出的字段），`_isHaveTemporaryData` 仍为 true。
- 「点击清除」只清前端表单，不删服务端草稿（2026-10-31 补测，用户同意后点击）：
  - 点击后提示条消失，字段回到系统默认值（转正类型、转正日期等按员工数据重新带出）。
  - 点击时只发了重新加载表单的请求（`GET /api/v2/UI/FormView`）和下拉数据源请求，没有任何删除或改写 `temporaryData` 的请求。
  - 两次加载表单的参数不同：带出草稿的那次多带了 `formStorageKey`、`formStorageButton=true`；清除后重载的那次没有。推断「清除」就是不带草稿参数重载一次（🟡，参数含义未见文档）。
  - 关掉表单再打开同一员工的「转正申请」：顶部又出现「已带出上次暂存信息」，`_isHaveTemporaryData` 仍为 true。草稿还在服务端。
  - 所以原站草稿只会被下一次「暂存」覆盖；提交后会不会删，没有测（🟡）。
- 规格 PB-R21 里转正考核的「草稿」状态，指的是考核记录本身的状态，跟这里的表单暂存不是一回事。员工自评、经理评价那一步有没有暂存按钮，要用员工账号才能看到，这次没有测（🟡）。

**对复刻**
- 转正申请表单提供「暂存」：
  - 草稿存服务端，按（业务动作，员工）只保留一份；
  - 暂存不校验必填，不生成审批单，也不进入「我的申请」。
- 再次打开时自动带出草稿，顶部提示「已带出上次暂存信息」，并提供「清除」。原站的「清除」只清本次表单、不删服务端草稿，下次打开仍会带出；复刻建议「清除」同时删除服务端草稿（与原站不同，属复刻取舍，待 00 确认）。
- 提交成功后删除草稿。原站这一点没有实测，这是复刻自己的设计。
- 「发起转正考核」表单不提供暂存，和原站一致。
