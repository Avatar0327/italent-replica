## 2. 档位定义

| 档位 | 含义 |
|---|---|
| L3 | 真实实现：后端接口 + 持久化 + 权限 + 审计，页面直连 |
| L2 | 演示桩或简化：页面画出，数据来自 `apps/web/src/demo-stubs/`，或接口缺口用占位 / 降级（如只筛当前页、关联对象显示 ID） |
| L1 | 仅画面：无数据、禁用占位或静态示意 |
| 后端 L3·无页面 | 后端接口与持久化已到 L3、复刻系统页面未做（演示时只能经接口或种子体现） |
| 未做 | 前后端都没有；各文件第 3.1 节写明原因（DEC-456② 暂停、F 任务后补、首版不做等） |

档位起点是各模块 `apps/web/src/<模块>/annotations.ts` 的 `level`，再按代码核到“能力”粒度；注释与代码不一致的地方在对应文件里注明
（如 06 的 `settings.snapshot` 注释仍标 L2，#313 后实际已读服务端快照）。

## 3. 工作量口径

**已投入**（各文件 §5.1）：
- 行数为已合并 PR 的新增行（GitHub REST `pulls/:n/files` 逐文件统计），按路径分类：产品代码、测试（`tests/`、`*.test.*`、`*.spec.*`、冒烟）、
  文档（`docs/`）、生成物（`packages/db/migrations/meta/`、F-039 `route-policy/baseline` 与 `required/digests`、lockfile）；表中只列产品代码与测试。
- “审查记录”为 PR 评论首行含“审查原文 / 复审原文 / 交叉审计”的条数，含合 main 后快审，近似审查轮次；早期 PR 部分审查不在评论里，记“—”。
  全部 242 个已合并 PR 中有审查记录的 215 个，平均每个约 4 条。
- 一个 PR 只计入一个模块；共用的前端片 #296（01 / 02）、#300（09 / 10）按 `apps/web/src/<模块>` 目录行数拆分，测试按比例折算，审查记录两边都写
  并标“共用”。跨模块的底座 PR（如 #1、#8、#22）计入 06，会使 06 偏高。合计行按此去重，仍是参考量级。

**剩余**（各文件 §5.2，L2 → L3 与未做能力）：
- 单位为一名熟悉本仓库的全栈工程师的人日；后端 L3（接口 + 持久化 + 权限 + 审计 + 验收测试）约 400 行 / 人日，前端页面（含冒烟）约 500 行 / 人日；
- 行数先按本模块或相邻模块同类 PR 的实际行数类比估出，再折人日；需开工前取证的点每点 +0.5 人日，需单独契约 / 设计 PR 的 +1～3 人日；
- 审查返工系数 ×1.3；
- 首版明确不做（如管理委托 DEC-064、流程时效 DEC-035）与范围未定的能力不计入；各文件“估算依据”列写明类比对象。
