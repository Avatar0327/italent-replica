# 交叉审查清单

目标：Claude 审查的严格程度与 astra（DEC-090 / DEC-136）一致。审查结论直接决定能否合并（合并授权见编排窗口规则），所以**宁可写清“未核实”，也不写“看起来没问题”**。

规则本身以仓库文档为准，本 skill 只规定审查**怎么做、怎么定级、怎么写**：
- 硬规则与平台约定：`AGENTS.md` §2、§9、§10
- 决策：`docs/00_状态/02_已确认决策.md`（重点 DEC-057/058/063/067/136）
- 派发单：`docs/09_派发/` 中该任务的提示词与附加要求
- 取证门禁：`docs/09_派发/取证与开发衔接.md`、`node scripts/evidence-gate.mjs <任务号>`

## 0. 审查纪律

- **只读**：不改源码、不推送、不合并、不在 PR 上评论。审查结果交给编排窗口，由它发到 PR 并汇总修改清单。
- 在独立工作树中审查（如 `git worktree add ~/Code/wt-<PR>-review <head>`），结束时工作区保持干净。
- 每个结论都要有证据：`文件:行号`、测试名、CI 链接或命令输出。没有证据的写“未核实”。
- 不把未取证的原站行为写成事实；与原站有关的判断引用取证编号或 DEC。

## 1. 先确定审查类型和档位

| 类型 | 范围 | 档位（DEC-136） |
|---|---|---|
| 首审 | 整个 PR 对照派发单逐项核验 + 第 3 节全部必查项 | 核心模块（审批、任职版本链、调动、权限）按最高强度；其余按常规 |
| 复审（第二轮起） | **只**核验上一轮 P0～P2 是否修复，以及本轮新增提交的改动；不重新全面审 | 常规 |
| 小 PR | 改动小于约 500 行业务代码、无迁移或只有简单迁移 | 常规，可只报 P0～P2 |

复审时先列出上一轮问题编号，逐条给出“已修复 / 部分修复 / 未修复 / 修复引入新问题”。新发现的问题必须落在本轮改动或上一轮修复引入的代码上，否则不阻塞，记为建议。

## 2. 基线与运行结果

1. 记录审查 head SHA、与远端 main 的 merge base（`git merge-base`）。
2. CI：用 `gh pr view <n> --json statusCheckRollup,headRefOid` 确认 CI 跑在审查 head 上；PGlite 与 PostgreSQL 16 两个 job 的通过 / 跳过 / todo 数写进报告。**全量测试以 CI 为准**（DEC-136 之后的约定），本地只跑本 PR 相关测试。
3. 本地跑 `pnpm lint`、`pnpm typecheck` 和本 PR 新增 / 修改的测试文件。只在真 PostgreSQL 上执行的用例（竞争、锁）要到 CI 日志里确认**确实执行了**，而不是被跳过。
4. 迁移：新迁移由 `pnpm db:generate` 生成（手写 SQL 走 `--custom`），快照 `prevId` 接在 main 最新快照之后，两个迁移守卫（库结构与快照一致、RLS 标准形态）在 CI 中通过。

## 3. 必查项

逐项检查，报告里每项给一句结论和证据。

1. **派发项与 AC**：派发单每一条、每个 AC 都有实现和测试；“未覆盖”的必须在 PR 描述里说明并有 DEC 或用户决定支持。替身（fake / stub）不能代替验收要求的生产实现：测试绿但生产装配走默认放行，算未落实。
2. **八条硬规则**（AGENTS.md §2）：数据范围默认空、任职版本链只追加、“变更前”取上一条、审批通过 ≠ 生效、多维组织层级、身份与范围多对一、租户隔离、流程匹配不跨类型兜底。
3. **租户隔离**：新表强制 RLS（标准 `tenant_isolation` 形态）；外键为含 `tenant_id` 的复合外键；缓存、定时任务、outbox 都带租户维度；平台级入口不暴露给租户 HTTP。
4. **权限**：每次请求服务端重验成员、按钮权限和数据范围；范围过滤在**分页之前**；返回内容按字段权限裁剪（含错误信息、跳过清单、日志）；撤权后的幂等重放仍按当前权限裁剪；审批安全（DEC-057 只看本单字段、DEC-058 禁止盲审自审、DEC-063 管理员不代签）。
5. **并发与锁**：写请求校验 `revision`，不一致返回 409；锁顺序与现有约定兼容（员工 → 业务 → 实例；跨员工按全局顺序，见 PR #50 / F-008）；锁键规范化（UUID 小写等）；有竞争风险的路径有真 PG 强制交错测试。
6. **幂等**：写命令有命令 ID 和台账；同键同内容幂等、同键异内容报冲突；命令登记早于业务写入，避免并发时先各自写入后才报冲突。
7. **事务一致性**：业务变更、审计、outbox 同一事务；失败分“业务失败 / 存储不可写 / 结果未知”三类；回滚边界清楚（保存点 / 事务）。
8. **状态机与时间**：状态转移非法时返回 409；业务日期按租户时区，事件时间存 UTC；同日多条按操作先后（DEC-108），**混合路径**（直接业务与待生效申请交错）也要一致。
9. **与决策和取证一致**：实现符合派发单引用的 DEC；暂定口径收在一处；`TODO(需取证 Q-M0-xx)` 编号在清单中存在；跑一次 `evidence-gate` 确认没有开工前未完成项或待决 D。
10. **测试的证明力**：失败测试提交早于实现提交；断言能区分新旧行为（换回旧代码应失败）；“目录完整”类测试的期望值来自规格而非实现本身；并发测试用屏障或锁卡点而不是 `Promise.all` 碰运气；不跳过、不删除他人测试。
11. **边界与归属**：只改归属目录；共享文件（`packages/db/src/schema/*`、路由注册、公共类型、迁移序号）的改动在 PR 描述中列出；不改 `docs/00_状态/00_会话状态与恢复点.md`（AGENTS.md §3.5）；无凭据或真实个人数据；没有照搬 `reference/` 的反模式。

## 4. 定级口径（与 astra 对齐）

| 级别 | 含义 | 典型例子 | 是否阻塞 |
|---|---|---|---|
| **P0** | 跨租户泄露、数据丢失或不可恢复的损坏、凭据泄露、迁移破坏已有数据 | RLS 缺失导致跨租户可读；迁移覆盖任职数据 | 阻塞 |
| **P1** | 越权；违反硬规则；主流程结果错误；业务与审计 / outbox 不一致 | 范围在分页后过滤导致越权可见；自审可通过；“变更前”单独建列 | 阻塞 |
| **P2** | 可达的边界场景结果错误；验收要求未真实落实；测试证明不了修复；与 DEC 不一致 | 同日混合路径顺序倒置；生产装配默认放行而测试用替身；锁键大小写不一致导致并发漏锁 | 阻塞 |
| **P3** | 可读性、防御性、补充测试建议、极端并发边角 | 建议增加命令执行前占位；补权限负例 | **不阻塞**（DEC-136），可登记后续任务 |

定级要求：
- 每个 P0～P2 必须写：**定位**（文件:行号）、**可达场景**（编号步骤，从真实入口出发）、**期望 vs 实际**、**修法**、**回归测试**（说明为什么旧代码会失败）。
- 写不出可达场景的，降为 P3 或列为“疑问”，不得阻塞。
- 需要产品取舍的（例如要不要延期某项验收），不定级，放进“需要产品决策”，由编排窗口找用户。

## 5. 报告格式

```markdown
## PR #<n> Claude 交叉审查（<首审 | 第 k 轮复审>，head <短 SHA>）

审查结论：**<可以合并 | 发现 x 个 P0～P2 阻塞问题，当前不可以合并>**。

### 一、运行结果
- 审查 head / merge base
- 本地：lint、typecheck、相关测试（通过 / 跳过数）
- CI：PGlite、PostgreSQL 16 结果与链接；真 PG 专项用例是否确实执行
- 迁移与守卫

### 二、逐条核验
（首审：派发项 / AC 表格；复审：上一轮问题编号 → 已修复 / 部分 / 未修复 / 引入新问题）
| 项 | 实现与测试证据 | 结论 |

补充核验：第 3 节必查项逐项一句话结论 + 证据。

### 三、新发现问题（P0 → P3）
**P2-1：<一句话>**
定位 / 可达场景 / 期望 vs 实际 / 修法 / 回归测试

**P3 建议（不阻塞）**：…

### 四、需要产品决策的问题
### 五、结论
```

结论规则：**没有未解决的 P0～P2 才能写“可以合并”**。P3 不影响结论。

## 6. 本项目踩过的坑（审查时重点看）

- 测试用替身注入，生产装配默认放行（PR #53 编制检查）。
- 只测了“两条都待生效”，漏了“先申请、后直接业务”的混合路径（PR #53 同日顺序）。
- 测试在旧代码上也能通过，证明不了修复（PR #35 第三轮：`Promise.all` 并发测试、409 断言）。
- 授权判断依赖最近 200 条的展示窗口（PR #35 F1）。
- 锁键里的 UUID 大小写不一致，同一人被当作两把锁（PR #35 R6-1）。
- 跳过清单、错误信息里泄露操作人看不到的员工信息（PR #41）。
- 迁移编号与其他在审 PR 撞号：不算问题，按合并顺序由后合并者重排，审查时不报。
