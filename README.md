## 本地演示（F-025）

在本机浏览器里以不同角色走 R1 调动主线。**仅限开发环境**：开发身份切换与本地 PGlite 只在 `NODE_ENV=development` 下可用，生产构建与生产进程里都不存在。

### 前置
- Node ≥ 22.12、pnpm（版本见 `package.json` 的 `packageManager`），已执行 `pnpm install --frozen-lockfile`。
- 不需要 PostgreSQL：未设 `DATABASE_URL` 时后端用本地 PGlite（数据在仓库根 `.demo/`，已被 git 忽略）。
- 签名密钥放仓库根 `.env.local`（已被 git 忽略）；没有时 `pnpm demo` 自动生成随机 `DEV_IDENTITY_SECRET`。键名见 `.env.example`。

### 命令
| 用途 | 命令 |
|---|---|
| 写入演示数据（幂等）并同时启动后端 `:3000` 与前端 `http://localhost:5173` | `pnpm demo` |
| 只写入演示数据（已存在则不重复写；不复原被用户接管的种子单据，要复原用 `pnpm demo:reset`） | `pnpm demo:seed` |
| 重置：删除本地 PGlite 与演示清单后重新写入（**先 Ctrl+C 停掉 `pnpm demo`**；只删除 `.demo/` 下带 PGlite 标记的目录） | `pnpm demo:reset` |

打开 http://localhost:5173 ，页面顶部的黄色“本地演示”条里有“切换演示身份”下拉；选人后自动跳到该角色的入口，各页面的租户已预填。浏览器只记住“选了谁”（Cookie），身份头由本地 vite 开发代理用 `.env.local` 里的密钥签名后转发，密钥不进浏览器。

### 演示租户的数据规模
- 组织（行政维度，编码 `DEMO-ORG-001…032`）：租户根（集团）→ 3 个事业部（研发中心、运营中心、职能中心）→ 9 个部门 → 20 个小组，共 32 个，设立日期 2018-01-01；除平台 / 数据研发部由演示经理负责外，其余组织的负责人取自生成员工，HR 专员兼任全部组织 HRBP。
- 职务体系：3 个职层、9 个职等、2 个职级类别（P1–P6 / M1–M3）、6 个序列、22 个职务；每个小组 2–3 个职位（含“负责人”职位）。
- 员工：共 200 名（工号 `DEMO001…007` 是演示身份，`DEMO-0001…0193` 是确定性生成的员工；固定随机种子 + 固定姓氏 / 名字表，入职日期 2019–2025，少量实习生）。生成员工都有登录邮箱（入职必填，`demo.sNNNN@example.com`）但不是演示身份：切换工具条里仍只有上面 9 个人。手机号、证件号一律留空。
- 调动与审批：15 张，在途 6、已完成 6、驳回 2、撤回 1。发起人并不都是九个演示身份：6 张已完成单和 1 张在途单（`DEMO-TRF-02`）由生成员工的账号本人发起，其余由演示员工甲乙丙与审计管理员（本人入口）、两位经理（经理入口）、HR 专员（HR 入口）发起；审批一律由节点上的演示身份完成（经理 → HR 专员）。已完成的单按 25–120 天前的历史日期提交并生效。调动审批流“演示调动流程”：**直接上级审批**（暂以被调动人所在部门负责人近似，DEC-230；审批人表达式“直接上级”待 F-028）→ **调入部门 HRBP 审核**，两个节点都开启了“自审回避”。被调动人都是平台 / 数据研发部直属的生成员工，或演示员工甲乙丙与审计管理员（演示身份的部门 / 职位保持不变）。
- 演示时要注意的三处：① 经理给自己部门的员工发起、HR 自己发起的单，本人节点自审跳过后转给异常管理员；异常管理员没有任职记录字段的查看权限，**不能直接审批**（403），要在审批中心把任务**转交给 HR 专员**，再切到 HR 专员审批。② 审计管理员那张在途申请（`DEMO-TRF-03`，本人入口，财务部不变）的第一节点落在生成的财务部负责人，不在九人切换清单里，保持在途即可；要走通同样先转交。③ 普通员工没有“撤回”按钮，种子里的撤回单（`DEMO-TRF-15`）由 HR 发起并撤回。

### 幂等与恢复
`pnpm demo:seed` 分阶段执行：组织 → 职务体系 → 员工 → 授权与负责人 → 调动流程与调动单；每一阶段按自然键先查后建（组织编码、职务体系编码、工号、调动场景的确定性命令 ID），重复运行只补缺失，不重复写。调动场景的每一步（发起、审批、驳回、撤回）都用确定性命令 ID 提交，与业务写入同事务记入命令台账，这就是种子台账（发起 `demo-seed:<租户>:DEMO-TRF-nn`，之后每步 `demo-seed-step:DEMO-TRF-nn:r<轮次>:<操作>:<任务或实例 ID>`）；用户自己提交的申请不会被认领。**用户接管（DEC-477）**：种子单据上一旦出现种子台账外的任何操作（转交、加签、审批、撤回、催办、重提、管理员转交 / 干预等），就视为用户接管，种子此后永不再动这张单。每个调动场景到达目标状态后记入 `.demo/seed-state.json` 的 `transfers`，判定为接管的记入 `takenOver`（按租户 ID 区分，reset 后自然失效），之后每次启动（`pnpm demo` 会先跑种子）都跳过；该文件缺失或损坏时每次重新做接管判定，结果相同。种子中途失败（或被打断）后直接再运行一次即可从缺失处继续。**重跑种子不复原被接管的单据**：要回到干净的演示数据，用 `pnpm demo:reset` 删库重建（本段之前种下的旧演示库与新数据不兼容，升级后请先 reset 一次）。全量种子在本地 PGlite 实测约 70 秒（机器空闲时；多个开发窗口同时占着 CPU 时可到数分钟，耗时主要在员工入职：每人一次建档 + 一次入职，经完整授权与审计），之后重复运行约 3 秒。

### R1 主线走查
1. 切换为“平台研发员工甲（演示）”→ 员工自助 → 人事申请 → 本人调动：调动日期选今天，部门改为“前端开发组”，提交（状态“审批中”）。
2. 切换为“平台研发部经理（演示）”：管理者工作台“待处理”里出现这张单（列表里还有种子里的其他在途单，按员工姓名找）；审批“直接上级审批”节点。
3. 切换为“HR专员（演示）”：审批“调入部门HRBP审核”节点。生效日不晚于今天时审批通过即生效；生效日在以后的，到期后由定时生效任务落地（演示进程 30 秒轮询一次）。
4. 结果：员工自助“任职记录”出现新部门的一条记录；经理工作台“已处理”可见；HR 在调动管理里选该员工时，调动前信息已是新部门；审计管理员调 `/api/tenant/audit/data-changes` 可查到本次变更。

> 前端暂时没有审批中心页面（同意 / 驳回）：界面审批待 F-027（DEC-229）。在那之前，第 2、3 步用已有接口完成，例如在浏览器开发者工具里调用：`GET /api/tenant/approval/todos` 取待办，`GET /api/tenant/approval/instances/{instanceId}` 取 `revision`，再 `POST /api/tenant/approval/tasks/{taskId}/approve`（请求头 `x-tenant-id`、`If-Match: "<revision>"`、`Idempotency-Key`，请求体 `{}`）。
