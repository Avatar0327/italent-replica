# 招聘需求草稿与提交预验收

原站页面证据BC-R01/02已核实；不代表已在原站实测审批结果。

1. HR在合成岗位创建需求，可选填新增/顶替/储备、紧急程度、提出/期望到岗日期、职责与资格。保存草稿后应为待提交，HR有提交待办，管理者无审批待办；不得接收候选人。
2. HR点击提交审批，需求进入待审批，其他具备组织权限且从未参与编写/修改/提交的人可批准或退回。重复提交拒绝，在审内容不能静默修订。
3. 退回后HR修订并保存仍是草稿，需再次提交。曾编写、修改或提交的人即使切换管理角色也不能自审。
4. 批准后才可添加合成候选人，继续面试→录用申请→独立批准→登记接受→按计划日期入职。已有岗位、编制、名额和事务规则保持。
5. 需求进度报表区分待提交/待审批/待修订/招聘中，新增字段与详情一致；跨组织与员工角色不可读取报表。

旧版无显式提交标识的draft是既有待审记录，保持可审批；一旦修订转入新草稿规则。API没有把所有旧记录批量改成待提交，也未迁移真实数据。保存草稿与保存并发起审批分为两个明确按钮；后一操作只产生一个原子修订，失败不残留草稿。也可从列表单独提交已保存草稿。

测试角色owner/manager/hr/employee使用内存SQLite合成数据，并非线上密码。站点访问仍仅现有所有者；多真实身份人工业务验收未执行，生产未验收。

限制：字段暂均为可选补充，除已有名称/岗位/人数/招聘依据要求；尚未确认原站完整必填规则。预算币种口径、负责人解析/共享、原站需求编号生成、Offer各类人数计算口径、完整职位发布/面试官流程与集成仍在范围。期望到岗和需求提出日期为业务资料，不自动改变实际入职日期或权限。

## 网络中断后恢复

新建需求、候选人、面试记录的同一打开表单会复用创建请求键。若服务器已完成但客户端未收到响应，保持内容不变重试应返回同一记录；不会再创建副本。若改了内容，会提示先核对原记录，而不会用同键覆盖数据。关闭重开表单是新请求，不承诺跨重开防重；原候选邮箱约束仍适用。

API仅这三个创建操作支持Idempotency-Key（同租户、同调用账号隔离），其他状态转换继续由CAS/业务状态保护。同键异内容409、无当前角色或组织权限403；重放不增加审计/业务修订，不退回已经变化的业务状态。键与请求摘要仅内部保存，不在列表/历史中暴露。此为本系统可靠性策略，未声称原站采用相同实现。
